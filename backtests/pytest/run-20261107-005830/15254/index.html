tmp_path / tmp_path_factory.mktemp list the whole basetemp on every call: O(N^2) over a session

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches remove the per-call listing of basetemp on the hot path, and the three independent performance tests pass on both. They differ on the invariant the issue states explicitly: "The numbering rule is unchanged: one more than the highest existing number ... Directory names are unchanged as long as only pytest writes into the basetemp."

Patch A replaces the rule with a per-prefix counter that starts at 0 and skips names that already exist. That is a deliberate behaviour change (its own changelog and docstring say so), and it shows up in the independent tests: with tmp_path_retention_policy=failed a removed tmp_path's number is no longer reused (test_retention_removal_names_unchanged fails on A), and a pre-existing 'logs7' created well before the call yields 'logs1' instead of 'logs8' (test_mktemp_honours_foreign_entry_after_clock_tick fails on A). The retention case is an ordinary pytest-only session, so A breaks the issue's "names unchanged in every ordinary session" guarantee, not just the foreign-writer edge. Names stay unique, so this is not a safety bug, but it resolves the issue by changing documented semantics rather than preserving them. A is otherwise clean, small, and its tests (counter without listing, skipping dirs/files/dangling symlinks, listing once after a 10-run, overlapping prefixes, give-up after 20, PermissionError retry) are meaningful.

Patch B implements the issue's sketch: a NumberedDirListing on the factory, validated by the root's stat (dev/ino/mtime/ctime/nlink), updated for the factory's own mkdir and the retention rmtree with an nlink-delta check, invalidated on mkdir failure, and never cached on whole-second timestamps. It reproduces max(parse_num(find_suffixes)) semantics faithfully, including case-insensitive ASCII matching, the KELVIN-sign non-ASCII fallback, negative numbers and the '<prefix>current' symlink counting as -1. All eight independent tests pass. Its tests are substantive: scandir counted exactly once over 200 mktemp calls, a 50-test retention session asserting both exact names and a single listing, name equality against a live listing across mixed prefixes with foreign files/dirs and removals, a missed-entry path proving an existing directory is never returned, foreign changes seen via stat, and coarse timestamps disabling the cache.

B's costs are real: ~200 lines of new caching/index machinery in pathlib (more surface for subtle bugs), and on filesystems where a directory's nlink does not track subdirectories (Windows, btrfs) the nlink-delta check invalidates every call, so the speedup is absent there (its own tests skip in that case). That is a limited fix on those platforms, but no worse than base, and the issue's author acknowledges Linux-only testing. Weighing correctness first, B fixes the root cause while honouring the issue's stated numbering invariant; A fixes the performance but violates that invariant in ordinary sessions, which the independent tests confirm. B wins.

TempPathFactory.mktemp() (and so tmp_path) finds the next free number with make_numbered_dir(), which lists the whole base temporary directory on every call. The directory gains entries with every test, so test N lists about 2N entries and a session does O(N^2) work: each test is slower than the one before. #11859 made the listing cheaper but, as it says, "doesn't fix the underlying issue (iterating the directory)".

Reproducer

# test_repro.py: N=1000 pytest -q test_repro.py; then N=2000, N=4000
import os, pytest

@pytest.fixture(autouse=True)
def workdir(tmp_path_factory):
    return tmp_path_factory.mktemp("work")

@pytest.mark.parametrize("i", range(int(os.environ.get("N", "1000"))))
def test_many(i, tmp_path):
    (tmp_path / "f").write_text("x")

Fix sketch (PR to follow)

TempPathFactory keeps the listing of its own basetemp (names and the directory's os.stat(): device, inode, mtime, ctime, link count) and passes it to make_numbered_dir() through a private keyword argument. The listing is reused while the stat is unchanged. The factory records its own mkdir and the tmp_path retention removal in it, keeping the new stat only if the link count changed by exactly one. The numbering rule is unchanged: one more than the highest existing number, with the same case-insensitive matching. The listing is only a hint; mkdir decides, and on failure the directory is listed again. Other callers of make_numbered_dir(), including the pytest-of-<user> session root, are unchanged, and filesystems with 1-2 s timestamps are not cached. The listing lives on the factory, so it is plain per-session state: no lock, no fork handling, and rm_rf() does not need to know about it. It could instead live inside make_numbered_dir() for every caller, but that makes it global state; I would rather keep it on the factory unless you see it differently.

Limits

  • Directory names are unchanged as long as only pytest writes into the basetemp. That covers every ordinary session; each xdist worker has its own basetemp.
  • If something else (another process, or test code writing into getbasetemp() directly) creates or removes entries there within one filesystem clock tick of a mktemp call, the root's stat can miss it. A different free number can then be chosen, never an existing directory. The clock tick is about 1-4 ms on Linux before 6.13, and about 16 ms on Windows. On Linux 6.13+ with multigrain timestamps it only happens on tmpfs, for a removal plus a creation within ~1 ms.
  • In a simulation with a realistic clock (ticks not aligned to milliseconds) and a foreign writer in the same tick, 299 of 1,500 random sequences differed from main at 4 ms, and 1,001 of 1,500 at 16 ms. All names were still unique. With pytest as the only writer, 0 differed.
  • Tested on Linux only; coarse clocks were simulated. Not tested: Windows, macOS, NFS.
