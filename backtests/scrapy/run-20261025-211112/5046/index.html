H2DownloadHandler: bytes_received signal

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches thread the crawler down to the Stream and send bytes_received/headers_received via check_stop_download, handle the HEADERS/DATA-with-END_STREAM case by tolerating StreamClosedError on reset, and build the partial response via make_response(stop_download=...). The decisive difference is flow control. In Patch A, receive_data returns early after a StopDownload without acknowledging the frame's flow_controlled_length, so every stopped download leaks connection-level window; the independent test test_connection_usable_after_stop_download shows the consequence directly: after several stopped downloads on one HTTP/2 connection the next request times out (DownloadTimeoutError) under Patch A but passes under Patch B. That is exactly the production scenario the issue implies (a spider stopping downloads from bytes_received during a crawl), so Patch A leaves the feature unusable beyond a few requests per connection. Patch B explicitly calls acknowledge_received_data before stopping, uses ErrorCodes.CANCEL (the semantically correct code for a client-abandoned stream), and also guards window_updated against late WINDOW_UPDATE frames for streams already removed locally. On tests, both un-skip the shared crawler-based StopDownload tests, but Patch B additionally adds targeted tests for the END_STREAM edge cases, for connection reuse after a stop, and for the window_updated guard; Patch A adds none. On scope/craft, Patch B keeps crawler as an optional keyword argument so existing H2ConnectionPool/H2ClientFactory/H2ClientProtocol callers (including the existing protocol tests) keep working, whereas Patch A changes the positional settings parameter to crawler across three classes, which is unnecessary churn for the ask. Patch B also passes body_length=-1 for unknown length, consistent with the HTTP/1.1 handler, and adds a news entry. Patch A's only advantage is slightly less code, which does not offset the real correctness defect.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Each saw the issue and the two patches, labelled A and B in random order (two of them saw ours as A), with issue links and version numbers removed. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours. The reasoning above is one judge's, shown verbatim.
