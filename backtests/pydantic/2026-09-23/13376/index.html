PrivateAttr(default_factory=...): takes_validated_data_argument re-runs inspect.signature on every instantiation (uncached) → CPU + cyclic-GC memory churn

Worse

The merged fix was judged better than our patch.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches eliminate the per-instantiation recomputation, but they differ meaningfully on the highest-weighted criterion, correctness/root-cause. Patch A precomputes the flag once and stores it on the shared `ModelPrivateAttr` instance (mirroring how regular `FieldInfo` fields bake this in), fixing BOTH per-instance call sites the issue names: the previously-uncached `default_factory_takes_validated_data` property now memoizes into a new slot, and `resolve_default_value` no longer calls `takes_validated_data_argument` at all (it receives the flag as a parameter). Because the cache lives on the class-scoped attribute, it is freed when the class is, with no global retention. Patch B just decorates `takes_validated_data_argument` with `@cache`. That is the issue's 'simplest' suggestion and it does stop the repeated `inspect.signature` work, but it installs an unbounded, process-lifetime module-level cache keyed on arbitrary user-supplied callables — holding strong references to every distinct factory (and its enclosing closure) forever. For a library that routinely builds models dynamically (`create_model`, generics, per-call lambda factories) this reintroduces exactly the class of unbounded RSS growth the issue is about; it trades one leak for a milder one, i.e. it masks rather than cleanly resolves. On tests, Patch B is stronger: it adds a focused regression test that asserts signature inspection is not re-run per instantiation (fails before, passes after) — directly targeting the bug. Patch A's test changes are largely adaptive (updating `resolve_default_value`'s new keyword-only signature) plus an unrelated `__repr_args__` repr test; it notably lacks a test proving the recomputation is gone. On scope, Patch B is far tighter (one line), whereas Patch A carries drive-by churn (a new `__repr_args__` method and a docstring rewording unrelated to the perf fix) and a somewhat invasive internal signature change. Net: B wins tests and scope, but A wins the top-priority correctness criterion decisively by fixing the root cause at both sites without introducing a new unbounded-cache retention hazard on a bug that is fundamentally about long-running memory growth. That edge on the highest-weighted axis outweighs B's advantages, so A is the better fix — though it is close and A's scope creep is a real mark against it.

Initial Checks

Description

For a private attribute with a default_factory, every model instantiation re-derives whether the factory takes the validated data by calling takes_validated_data_argument(default_factory=...), which runs inspect.signature() on the factory (pydantic/_internal/_fields.py:694) — not cached, even though it's a pure function of the factory object. It runs twice per instantiation, from two separate sites in init_private_attributes() (pydantic/_internal/_model_construction.py:377): once via the ModelPrivateAttr.default_factory_takes_validated_data property, and once via get_default() → resolve_default_value() (_fields.py:718). Both are uncached.

Regular Field(default_factory=...) is not affected — it computes this once at schema-build time via FieldInfo.default_factory_takes_validated_data and bakes it into the core validator. Only the PrivateAttr path recomputes per instance.

For a factory whose inspect.signature() succeeds via CPython's inspect._signature_fromstr (list, tuple, set, threading.Lock, …), that call does sys.modules.copy() and builds closures that capture the copy — reference cycles the plain refcounter can't free, only the cyclic GC can. Instantiating such a model at a high rate in a long-running process accumulates this garbage faster than the collector reclaims it (and pymalloc keeps the freed arenas), so RSS climbs steadily.

Concretely: Sculptor has a BaseModel with _wait_lock: Lock = PrivateAttr(default_factory=Lock) that is instantiated constantly. It was harmless on Python ≤3.12 — there inspect.signature(Lock) raises ValueError: no signature found, so pydantic falls back cheaply — but began leaking multi-GB of RSS on 3.13+, because CPython 3.13 gave threading.Lock an inferrable signature and flipped every instantiation onto the _signature_fromstr path. We mitigated it by memoizing this check: imbue-ai/sculptor#205.

With default_factory=list it reproduces on every CPython tested (3.12.11, 3.13.5, 3.14.6) and on pydantic 2.13.4 through main (2.14.0a1) — ~52k objects of cycle-only garbage per 1000 instantiations. list/tuple have always had signatures, so the bug isn't tied to a Python version; the set of other builtins that trigger it just grows over time (set, threading.Lock at 3.13).

Example Code

import gc
from pydantic import BaseModel, PrivateAttr
from pydantic._internal import _fields

# (1) It's recomputed on every instantiation, uncached:
calls = 0
_orig = _fields.takes_validated_data_argument
def _counting(*args, **kwargs):
    global calls
    calls += 1
    return _orig(*args, **kwargs)
_fields.takes_validated_data_argument = _counting

class M(BaseModel):
    _items: list = PrivateAttr(default_factory=list)

M()                       # warm
calls = 0
for _ in range(1000):
    M()
print("takes_validated_data_argument calls:", calls)   # -> 2000

# (2) Each call leaves cycle-only garbage (default_factory=list):
gc.collect(); gc.disable()
before = len(gc.get_objects())
for _ in range(1000):
    M()
after = len(gc.get_objects())
freed = gc.collect(); gc.enable()
print("objects grew:", after - before, "| freed only by cyclic gc:", freed)
# -> objects grew: ~54000 | freed only by cyclic gc: ~52000

Suggested fix

The simplest fix is to memoize takes_validated_data_argument (a pure function of the factory, e.g. functools.cache) — after the first call per factory, both per-instance calls become cache hits.

Alternatively, do what regular fields do and compute the flag once at class-construction time, storing it so both sites can read it. Note this is more than "reuse the property": ModelPrivateAttr.default_factory_takes_validated_data (pydantic/fields.py:1451) is itself an uncached @property that re-runs inspect.signature on every access — it's one of the two per-instance calls, so it has to be precomputed too, not just read from resolve_default_value.

Happy to open a PR if you'd like.

What the agent reported

The fix is verified and correct. The reviewer flagged that @cache narrows accepted factories to hashable ones — but this is exactly the fix the report proposed as simplest, and unhashable callable factories are a niche case. I'll keep the change minimal per the report's own suggestion and note the tradeoff.

Summary

What was wrong: For a private attribute with a default_factory, every model instantiation re-derived whether the factory takes validated data by calling takes_validated_data_argument in pydantic/_internal/_fields.py, which runs inspect.signature() on the factory. It was uncached and ran twice per instantiation (via the ModelPrivateAttr.default_factory_takes_validated_data property in init_private_attributes, and again via get_default → resolve_default_value). For factories like list/Lock whose signature is inferred through CPython's _signature_fromstr, each call leaves cycle-only garbage, causing RSS to climb in long-running processes. Regular Field(default_factory=...) was unaffected because it bakes the flag into the core schema once at build time.

What I changed (both left as uncommitted working-tree edits):

  • pydantic/_internal/_fields.py: added the @cache decorator to takes_validated_data_argument. from functools import cache was already imported, so this is a one-line change. After the first call per factory, both per-instance call sites become cache hits — the expensive signature inspection no longer runs per instantiation. This is the exact "simplest fix" the report proposed.
  • tests/test_private_attributes.py: added test_private_attribute_factory_signature_inspection_cached, which warms a PrivateAttr(default_factory=list) model once, patches _typing_extra.signature_no_eval with a counter, instantiates 50 times, and asserts it is never called again (0 calls).

Test evidence:

  • Regression test failed before the fix: assert 100 == 0 (signature inspected twice per instantiation × 50).
  • After the fix, the full tests/test_private_attributes.py suite passes: 36 passed, including the new test. No previously passing tests regressed.

Reviewer note (not blocking): @cache now requires factories to be hashable and retains them for the process lifetime. All common factories (list, dict, set, functions, lambdas, classes, partial) are hashable, and this matches the report's explicitly suggested approach and the reporter's own upstream mitigation, so I kept it minimal rather than switching to the more invasive precompute-at-class-construction alternative.

Requirements disposition

  1. Memoize takes_validated_data_argument so both per-instance calls become cache hits (primary suggested fix) — ✅ Implemented (@cache) with a regression test that fails before and passes after.
  2. Alternative: precompute the flag once at class-construction time (incl. the uncached property at fields.py) — ⏭️ Skipped as the explicitly-offered alternative to the primary fix. Evidence it's unnecessary: the @cache fix drives the underlying signature_no_eval calls to 0 across repeated instantiations (regression test asserts this), fully resolving the reported CPU/GC churn without touching the property or __slots__. The report presents these as either/or; the simpler one is sufficient.
  3. Fix must not affect the regular Field(default_factory=...) path — ✅ Confirmed: that path calls the same now-cached function once at schema-build time (_generate_schema.py:2654); caching only makes it a hit if reused. All 36 private-attribute tests pass.
