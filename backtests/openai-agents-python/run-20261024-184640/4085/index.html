Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Correctness: the issue explicitly asks for auto-pagination in four methods: list_tools, list_prompts, list_resources, and list_resource_templates. Patch A only changes list_tools and list_prompts and leaves list_resources/list_resource_templates untouched, so a server with multiple resource pages still silently drops items; the independent tests confirm this (both resource tests FAIL-ASSERT on A, PASS on B). Patch B adds a single _fetch_all_pages helper and applies it to all four methods, keeping the cursor parameter on the resource methods for backward compatibility and auto-exhausting only when cursor is None, exactly as the issue proposes. B also retries each tools page independently inside the loop (fetch_tools_page wraps _run_with_retries per page) and preserves _maybe_serialize_request per request. One caveat for B: it treats an empty-string nextCursor as end-of-list, which is a narrow edge case; A's integration server happens to use '' as a cursor, but the spec treats cursors as opaque non-empty strings in practice. A notable uncertainty: A calls session.list_tools(params=PaginatedRequestParams(...)) while B calls session.list_tools(cursor) positionally; the base code already calls session.list_resources(cursor) positionally, so B is consistent with the pinned client API as visible in the repo. Tests: B adds a focused test module covering all four methods, cache holding all pages, filter applied after accumulation, per-page retry without restart, repeated-cursor detection, single-page behaviour when a cursor is passed, and MCPUtil seeing all tools; these would fail before and pass after. A's tests are extensive for tools/prompts (including a real stdio server integration test) but necessarily omit resources since the fix omits them. Scope/craft: A adds a large amount of cursor-redaction and traceback-scrubbing machinery (del fetch_pages, clearing locals, BaseExceptionGroup wrapping) that is beyond the issue's ask and makes the core pagination loop hard to follow; B's helper is small, generic, and readable, with updated docstrings. B resolves the full reported issue; A resolves half of it.

Describe the bug

Summary

Three MCP listing methods in _MCPServerWithClientSession do not follow the
MCP pagination spec. When a server returns a nextCursor, items beyond the
first page are silently dropped.

Affected methods in src/agents/mcp/server.py

MethodAccepts cursor?Auto-paginates?
list_tools()❌ No❌ No
list_prompts()❌ No❌ No
list_resources()✅ Yes (manual, one page)❌ No
list_resource_templates()✅ Yes (manual, one page)❌ No

list_tools() and list_prompts() don't even expose a cursor parameter,
making external pagination impossible. list_resources() and
list_resource_templates() accept a cursor but leave full pagination to the
caller with no helper.

Expected behaviour

Each method should loop using nextCursor until exhausted and return the
complete result set, per the
MCP pagination spec.

Proposed fix

I intend to submit a PR that adds auto-pagination to all three methods:

  • list_tools() — loop with nextCursor, accumulate into unfiltered cache (per local MCP server lifecycle contract — unfiltered list is the cacheable value; filters applied on a copy per request)
  • list_prompts() — loop with nextCursor, return accumulated results
  • list_resources() / list_resource_templates() — loop internally, keep cursor param for backward compat but auto-exhaust when not provided

Each paginated call will be wrapped in _run_with_retries and
_maybe_serialize_request to preserve retry semantics and shared-session
serialization per iteration.

Tests will cover:

  • tests/mcp/test_caching.py — tool cache holds all pages
  • tests/mcp/test_tool_filtering.py — filters applied after full accumulation
  • tests/mcp/test_client_session_retries.py — retries per-page, not restart
  • tests/mcp/test_runner_calls_mcp.py — runner sees all tools across pages
  • New tests for paginated list_prompts() and list_resources()

Debug information

  • Agents SDK version: It's not fixed in latest one too
  • Python version - NA, its SDK associated.
