Issue with chained resource transformations

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches produce correct content for the reported scenario, but they take different structural approaches and A is the cleaner root-cause fix. The bug is that once a chain runs, the inner `target` is replaced by the transformed resource, yet TransformWithContext still appends the new transform to the FULL chain (`append(r.transformations, t...)`), so the already-applied transforms (e.g. css.Build) get re-applied on top of an already-transformed target — exactly the 'wrongly including the full chain' the issue describes. Patch A recognizes the transformed state (atomic `transformed` flag set in doInit) and, when set, starts a fresh chain of ONLY the new transforms against the already-transformed target: [css.Build] is dropped, [fingerprint] is applied once to the built CSS. This is the conceptually correct model (the target already embodies the prior chain) and it avoids re-executing the prior transforms and re-publishing their side effects — a real concern here since the trigger (`.Data.Artifacts`) already published artifacts. Patch B instead keeps the full [t1,t2] chain but redirects `target` back to a newly-tracked original `sourceTarget`, re-running the entire chain (including css.Build) from scratch. That yields correct content but re-does expensive work and risks duplicate publishing of the artifacts that were already emitted; it also adds a latent hazard: cloneTo sets `sourceTarget = newtTarget` from `r.target`, which if cloneTo runs after a transform captures a transformed target as the supposed 'source'. On tests, A's unit test is at the exact transformation layer, fails-before (would yield 'start-t1-t1-t2') / passes-after, and crucially asserts `assertNoDuplicateWrites`, guarding the side-effect concern; B's integration test faithfully reproduces the issue with SHA assertions and also fails-before/passes-after, but does not guard against duplicate writes. Scope and craft are comparable in size, but A uses atomic access (appropriate given Hugo's concurrent rendering) and clear issue-referencing comments, while B's cloneTo mutation and re-run semantics are riskier. A resolves the issue at the root with less wasted work and a safer side-effect profile.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

View on GitHub

See the fix in #15188.

This has been an issue since we added this feature, but we haven't noticed it (or gotten reports about it) because the common setup is to set up the entire chain before starting to use it:

{{- with . | css.Build $opts }}
	{{- if hugo.IsDevelopment }}
		<link rel="stylesheet" href="{{ .RelPermalink }}">
	{{- else }}
		{{- with . | fingerprint }}
			<link rel="stylesheet" href="{{ .RelPermalink }}" integrity="{{ .Data.Integrity }}">
		{{- end }}
	{{- end }}
{{- end }}

In the above:

  • .RelPermalink triggers the transformation of the entire chain in a streaming way.

With the recently added .Data.Artifacts in css.Build I discovered this issue by accident when doing something ala:

{{- with . | css.Build $opts }}
	{{ range .Data.Artifacts }}
		{{ if eq .MediaType.MainType "font" }}
			<link rel="preload" href="{{ .RelPermalink }}" as="font" type="{{ .MediaType.Type }}">
		{{ end }}
	{{ end }}
	{{- if hugo.IsDevelopment }}
		<link rel="stylesheet" href="{{ .RelPermalink }}">
	{{- else }}
		{{- with . | fingerprint }}
			<link rel="stylesheet" href="{{ .RelPermalink }}" integrity="{{ .Data.Integrity }}">
		{{- end }}
	{{- end }}
{{- end }}

In the above:

  • .Data triggers the css.Build transformation.
  • Then fingerprint starts a new transformation with correct .Content, but wrongly including the full chain, including css.Build

The above could be rewritten to the below and it would work as expected:

{{- with . | css.Build $opts }}
	{{- if hugo.IsDevelopment }}
		<link rel="stylesheet" href="{{ .RelPermalink }}">
	{{- else }}
		{{- with . | fingerprint }}
			{{ range .Data.Artifacts }}
				{{ if eq .MediaType.MainType "font" }}
					<link rel="preload" href="{{ .RelPermalink }}" as="font" type="{{ .MediaType.Type }}">
				{{ end }}
			{{ end }}
			<link rel="stylesheet" href="{{ .RelPermalink }}" integrity="{{ .Data.Integrity }}">
		{{- end }}
	{{- end }}
{{- end }}
{{- end }}

Summary

What was wrong

In resources/transform.go, TransformWithContext unconditionally did append(r.transformations, t...) when chaining a new transformation onto a resource. That is fine when the whole chain is built before first use (the common pattern), but broken when the chain is executed partway — e.g. accessing .Data/.Content runs css.Build and bakes the result into the adapter's target, yet the transformations slice still lists css.Build. Chaining | fingerprint then produced a chain of [css.Build, fingerprint] applied to the already-built target, wrongly re-running css.Build.

What I changed (resources/transform.go, minimal 3-part fix)

  1. Added a transformed atomic.Bool field to resourceTransformations (and the sync/atomic import). Since that struct is embedded as a pointer, the flag is shared across the value-copied adapter.
  2. In doInit, set r.transformed.Store(true) inside the transformationsInit.Do closure once the chain has actually executed.
  3. In TransformWithContext, when r.transformed.Load() is true, start a fresh chain from the already-transformed target using only the newly supplied transformations t; otherwise keep the original append behavior. This leaves the "build chain before first use" path (existing Content two/Content two chained subtests) unchanged.

Test evidence (resources/transform_test.go)

Added regression subtest TestTransform/Content read then chained transform, using non-idempotent append transformations and reading .Content between the two Transform calls to trigger the bug.

  • Before the fix: FAIL — got start-t1-t1-t2 (t1 applied twice), wanted start-t1-t2.
  • After the fix: PASS. The full TestTransform and the entire resources package pass, with 0 failures across the whole -run TestTransform ./... build.

Reviewer verdict: correct, minimal, and complete; no unrelated changes. One low-risk out-of-scope observation was noted (a rebuild-granularity optimization in hasTransformationPermalinkHash for an unusual reverse ordering; no effect on output correctness or the reported bug) — I intentionally left it untouched to keep the change minimal.

All changes are left uncommitted in the working tree. (The AGENTS.md/CLAUDE.md deletions shown in git diff were pre-existing before this task and are unrelated.)
