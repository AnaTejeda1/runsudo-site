suspense.resolve() is called without a pending branch.

Worse

The merged fix was judged better than our patch.

In this judgment, Patch B = our agent, Patch A = the merged fix.

The warning fires because the parent Suspense gets resolved while its own pending branch is still being patched. `patchSuspense` then calls `resolve()` again after the patch, when there is no pending branch left.

Patch A wraps the same-root pending-branch patch with `suspense.deps++` / `suspense.deps--`. While the patch runs, nothing inside it can drop the boundary's deps to zero. That blocks every route to an early resolve:
- a nested suspensible Suspense resolving synchronously;
- the existing unmount path, where an unresolved async component removed from the pending branch decrements `parentSuspense.deps` and calls `resolve()` when it hits 0.

The unmount path matches the issue's scenario. A router view is patched in place, and the pending async page is replaced because its setup navigated away. Removing that page drops the outer deps to 0 mid-patch, and the outer `patchSuspense` then calls `resolve()` a second time. A's guard covers this generically, and the parent resolves exactly once after the patch completes.

Patch B targets only the nested-suspensible-Suspense path. It passes `sync=true` to every `resolve` call in `patchSuspense` and defers the parent's resolve to a guarded post-flush callback. This does fix the nested case, but it leaves the unmount-triggered mid-patch resolve untouched, so the direct router/async-page case can still warn.

B also changes resolution timing more broadly. Any parent of a Suspense patched outside the parent's own patch now resolves in post-flush instead of immediately. That adds behavioural risk beyond the issue.

Both patches add meaningful regression tests. A's second test also checks that a later sibling registering an async dep in the same patch is not skipped by a premature resolve. B's tests are thorough for the nested case, including the pending-branch-while-active-shown variants.

Overall, A is minimal, targets the root cause in a way that covers more of the paths behind the reported warning, and carries less risk. B is broader in mechanism but narrower in what it actually fixes.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
