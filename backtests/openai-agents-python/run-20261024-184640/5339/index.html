RunState.add_input input is silently dropped under stop_at_tool_names

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches make the same core change: in RunState.add_input they widen the stop_at_tool_names check from the interrupted tools only to every function call in the last processed response (adding both name and qualified_name), which is exactly the root cause the issue identifies and matches the set resolve_interrupted_turn evaluates. The independent tests confirm both fix the reported scenario identically (base FAIL on the rejection and silent-drop tests, both patches PASS, control case passes everywhere). The meaningful difference is B's additional condition that skips the completed-sibling names when the interrupted response also contains a pending handoff. In the runner, handoffs are resolved before the tool_use_behavior final-output check, so a response with a handoff continues with the receiving agent and does call the model again; in that case A would wrongly refuse valid input (a false rejection against the contract the issue states: raise only when the model will not be called again), while B accepts it and its parametrized test asserts the input reaches the delegate's model call. B's test also covers the qualified-name case via tool_namespace, the unrelated-stop-name control, streamed and serialized variants, in one table. A's tests are also solid (4 parametrizations, a nested agent-as-tool stop case, and a control case) and A's code is simpler and conservative, but it over-rejects in the handoff case. Minor craft nit against B: the handoff carve-out applies only to the completed siblings, not to the pre-existing interrupted-tool-name set, which is slightly inconsistent, and both patches' test helpers (from_json/from_string, namespace kwarg, model.extend) could not be verified here. On balance B models the resume semantics more precisely without adding unrelated churn, so B is the better fix.

Describe the bug

When one model response contains a tool listed in stop_at_tool_names that needs no approval and a sibling call that needs approval, the stop tool runs and the turn is interrupted. RunState.add_input(...) accepts new input on that state. After the approval, the resumed run ends on the stop tool's output without calling the model again (the behaviour #5240 introduced), so the staged input is never sent to the model and does not appear in to_input_list(). No error or warning is raised. With tool_use_behavior="stop_on_first_tool" the same add_input call is refused with UserError: Cannot add input to an interrupted RunState whose tool result may end the run.

On 0.22.3 the input did reach the model, because the resume ignored the completed stop tool (#5239). Since 0.23.0 the input is lost.

@function_tool
def finish(x: str) -> str:
    """Stop tool."""
    return f"finish:{x}"


@function_tool(needs_approval=True)
def protected(y: str) -> str:
    """Approval-gated tool."""
    return f"protected:{y}"


async def run_case(label: str, behavior) -> None:
    model = ScriptedModel(
        steps=[
            [
                function_call("finish", {"x": "x"}, call_id="f1"),
                function_call("protected", {"y": "y"}, call_id="p1"),
            ],
            [assistant_message("model-ran-again")],
        ]
    )
    agent = Agent(name="a", model=model, tools=[finish, protected], tool_use_behavior=behavior)
    first = await Runner.run(agent, "go")
    state = first.to_state()
    try:
        state.add_input("please also do Z")
        add_input = "accepted"
    except Exception as exc:
        add_input = f"rejected ({type(exc).__name__})"
    for item in first.interruptions:
        state.approve(item)
    resumed = await Runner.run(agent, state)
    seen_by_model = any("please also do Z" in str(call.input) for call in model.calls)
    in_history = "please also do Z" in str(resumed.to_input_list())
    print(
        f"  {label:34} add_input={add_input:20} final_output={resumed.final_output!r} "
        f"model_calls={len(model.calls)} "
        f"input_sent_to_model={seen_by_model} input_in_history={in_history}"
    )


async def main() -> None:
    await run_case("stop_on_first_tool", "stop_on_first_tool")
    await run_case(
        "stop_at_tool_names=['finish']", {"stop_at_tool_names": ["finish"]}
    )
    print(
        "expected: with stop_at_tool_names=['finish'] add_input is rejected the same way as "
        "under stop_on_first_tool, because the resumed run ends on the completed 'finish' "
        "result and never calls the model again"
    )


asyncio.run(main())

Expected behavior

With stop_at_tool_names=["finish"], add_input should raise the same UserError it raises under stop_on_first_tool, because the resumed run is going to end on the completed finish result and never call the model again. Input that the state accepted should not disappear without an error.

Cause. RunState.add_input (src/agents/run_state.py 1072-1087 at 125efa02) decides whether the resume can end the run by intersecting stop_at_tool_names with the names of the interrupted tools only. Since #5240, resolve_interrupted_turn (src/agents/run_internal/turn_resolution.py 2869-2904) also feeds the outputs of siblings that already completed in the same response into the tool_use_behavior check, so a stop tool that already ran ends the run, and add_input does not account for that.

Possible fix. In add_input, compare stop_at_tool_names with every function call in the interrupted response (the completed siblings as well as the pending ones), the same set that resolve_interrupted_turn now evaluates, and add a test with a stop tool plus an approval-gated sibling that asserts add_input raises.
