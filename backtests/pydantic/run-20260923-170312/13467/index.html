Its single combined test is weaker coverage. Description

Ellipsis is a builtin type that pydantic does not support. Its usage is infrequent, but it can be useful to express placeholders:

This is a bit of a contrived example, but:

class Model(pydantic.BaseModel):
    m: list[list[float]]
    subset: tuple[int | Ellipsis, int | Ellipsis]

    def subset_arr(self) -> np.NDArray:
        return np.asarray(self.m)[*self.subset]

Here's how I implement this right now with an adapter: https://github.com/psalvaggio/scientific_pydantic/blob/main/src/scientific_pydantic/ellipsis.py

However, since this is a standard library type, I think this would be a good thing to live in pydantic itself.

What the agent reported

The change is complete and reviewed. Here's the final report.

What was wrong

Pydantic did not support the standard-library types.EllipsisType (the type of ...). Annotating a field with it raised PydanticSchemaGenerationError: Unable to generate pydantic-core schema for <class 'ellipsis'>, because there was no handler registered for it in the core-schema dispatch table.

What I changed

  1. pydantic/_internal/_generate_schema.py
  2. Imported EllipsisType from types (line 26).
  3. Added a handler to the _handlers dispatch dict, next to the existing None/NoneType/MISSING singleton handlers: EllipsisType: lambda self, obj: core_schema.literal_schema([...]). This validates only the ... singleton and serializes ... in Python mode.
  1. pydantic/json_schema.py — literal_schema handler: ... has no JSON representation, so to_jsonable_python(...) would raise invalid-json-value. Since a literal schema can only contain ... via an EllipsisType annotation (Literal[...] is unspellable), the handler now filters out Ellipsis values and raises PydanticOmit if nothing remains — mirroring how missing_sentinel_schema is omitted from JSON schema. Ordinary literals are computed identically (no behavior change when no Ellipsis is present).
  1. tests/test_types.py — added test_ellipsis_type (after test_none), asserting validation of ..., literal_error on bad input, Python-mode serialization round-trip preserving the singleton, JSON-schema omission, and union usage (int | EllipsisType, where the Ellipsis branch is dropped from the JSON schema).

Test evidence

  • ./bt-test tests/test_types.py -k test_ellipsis_type → passed. Without the production change the test errors at class-definition time (unhandled type), so it captures the regression.
  • Blast-radius gate ./bt-test tests/test_types.py tests/test_json_schema.py tests/test_missing_sentinel.py -k "literal or none or ellipsis or missing_sentinel" → 40 passed, 1 xfailed (the xfail is the pre-existing pickle test), confirming the shared literal_schema JSON handler change breaks no existing literal/none/sentinel behavior.
  • Reviewer confirmed the diff is minimal, correct, touches no unrelated code or existing tests, and leaves no scratch files.

Requirements disposition

  • Support Ellipsis / types.EllipsisType as a validatable field type — Implemented, with test evidence above (validation + invalid-input error).
  • Serialization (model_dump) — Implemented; Python-mode round-trips ... by identity (tested). JSON-mode serialization of ... isn't meaningful (no JSON representation) and isn't required by the report.
  • JSON schema behavior — Implemented; Ellipsis fields are omitted (consistent with the MISSING sentinel precedent), tested for both bare and union cases.
  • The report's "Affected Components" checklist boxes were all left unchecked by the reporter; the concrete ask (a contrived tuple[int | Ellipsis, ...] placeholder use-case) is served by supporting EllipsisType in unions, which is tested.

All changes are left uncommitted in the working tree.
