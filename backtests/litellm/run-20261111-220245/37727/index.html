In this judgment, Patch A = our agent, Patch B = the merged fix.

Each patch fixes only one half of what the issue asks, so the question is which half matters more and which patch is the cleaner fix.

Patch A changes only the OCR dispatch layer: when the global `enable_azure_ad_token_refresh` is on and the provider is `azure_ai`, it forwards that flag into the native OCR route's kwargs so the shared Azure AD token resolution can run. The independent tests confirm this is the real gap: all five key-less OCR scenarios (sync, async, default route, native route, and Router row) fail on base with the exact 'Missing Azure AI API Key' error the issue quotes and pass with A. A also adds end-to-end tests that stand up a fake managed-identity endpoint and Foundry server, parametrize over both OCR routes, assert the route actually served the request (so the native case can't silently fall back), and cover Router usage. Its own MAI image tests exercise the issue's named image route without any image code change, which suggests that path already honours the token on this base; A does not break it.

Patch B never touches OCR. The issue's hard-failure case (`litellm.ocr` refusing before the call) remains broken under B, as all five OCR tests show. B instead reworks header/auth handling in `AzureChatCompletion.image_generation` (the `openai/deployments` path), which makes a key-less `azure_ai/gpt-image-1` deployment send a Bearer token. That is a legitimate adjacent gap under the issue's 'any other azure_ai non-chat' clause, and B's tests are solid, but B also pulls in extra surface: a new `lru_cache`d token-provider keyed only by scope, generic auth-header injection, and log redaction. Those are reasonable hardening but add risk in a hot path and obscure the fix, and they do not address the OCR failure the reporter measured.

Weighing correctness first: A resolves the issue's explicitly reported, still-failing OCR case at the point the credential is dropped, with tests that fail before and pass after. B fixes an image variant the issue only mentions generically while leaving the quoted OCR failure intact. A is the better fix.

The Feature

Make the azure_ai/ provider's non-chat paths honour the same Entra ID token fallback that the azure/ provider and the azure_ai/ chat path already have, so a Foundry deployment can be called key-less with a managed identity.

Today (v1.97.0), with litellm_settings.enable_azure_ad_token_refresh: true and AZURE_CLIENT_ID set (user-assigned managed identity), a model row that resolves no api_key behaves three different ways depending on the route:

routekey-less result
azure/* chat, embeddings (via initialize_azure_sdk_client / get_azure_ad_token)✅ token from get_azure_ad_token_provider → 200
azure_ai/* chat (AzureAIStudioConfig.validate_environment → BaseAzureLLM._base_validate_azure_environment)✅ Authorization: Bearer <token> → 200 (tested with a MaaS deployment on *.services.ai.azure.com)
azure_ai/* image generation (llms/azure_ai/image_generation, MAI /mai/v1/images/generations)❌ request goes out with no credential at all; provider answers 401 Access denied due to invalid subscription key
azure_ai/* OCR (/v1/ocr, llms/azure_ai/ocr)❌ litellm refuses before calling: Missing Azure AI API Key - A call is being made to Azure AI but no key is set either in the environment variables or via params

The ask: route the image-generation and OCR (and any other azure_ai non-chat) validate_environment through the shared Azure AD token resolution (get_azure_ad_token / get_azure_ad_token_provider, scope https://cognitiveservices.azure.com/.default, which *.services.ai.azure.com accepts) when api_key is None, instead of hard-requiring a key. The chat path already shows the pattern.

User Flow

Before: an operator running the proxy on Azure with a managed identity (keyless everywhere) adds Foundry image/OCR deployments.

  1. The operator sets enable_azure_ad_token_refresh: true, attaches a UAMI with Cognitive Services User / Cognitive Services OpenAI User on the Foundry accounts, and creates rows with api_base only.
  2. azure/gpt-* and azure_ai/<MaaS chat model> rows serve 200 with a token.
  3. azure_ai/MAI-Image-2.5* rows return 401 from the provider; azure_ai/mistral-document-ai-* / mistral-ocr-* rows fail with "Missing Azure AI API Key".
  4. The operator has to keep account keys in the DB for exactly those rows — a split fleet (some rows keyless, some keyed) on the same Foundry account.

After: the same rows pick up the Entra token like the chat route does, and the Foundry account key can be retired.

How far you got

Measured on the proxy, ghcr.io/berriai/litellm:1.97.0, Azure Container Apps, user-assigned managed identity with Cognitive Services OpenAI User + Cognitive Services User on the resource group holding the Foundry accounts, AZURE_CLIENT_ID set, enable_azure_ad_token_refresh: true:

  • azure/gpt-5-nano row, api_base only → 200, correct x-litellm-response-cost.
  • azure_ai/DeepSeek-V4-Pro chat row, api_base: https://<account>.services.ai.azure.com, no key → 200.
  • azure_ai/MAI-Image-2.5-Flash image row, same account shape, no key → litellm.AuthenticationError: Azure_aiException - {"error":{"code":"401","message":"Access denied due to invalid subscription key or wrong API endpoint. ..."}}.
  • azure_ai/mistral-document-ai-2512 OCR row, no key → litellm.APIConnectionError: Azure_aiException - Missing Azure AI API Key - A call is being made to Azure AI but no key is set either in the environment variables or via params.
  • Re-adding the key to the same image/OCR rows → 200, so the endpoints and RBAC are fine; only the credential resolution differs per route.

Happy to test a branch against the same deployments.
