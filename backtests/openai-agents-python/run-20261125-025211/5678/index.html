Issue #5678 Merged fix PR #6041 Run 25 Nov 2026 · run-20261125-025211 openai/openai-agents-python

After a RunState JSON round trip, the next nested handoff embeds the previous history summary instead of flattening it

Tie

The judges split evenly between our patch and the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the root cause identified in the issue: `_extract_nested_history_transcript` only accepted string content, so the `[{"type": "output_text", "text": ...}]` shape written by `RunState._serialize_input` was never recognized and the old summary got JSON-dumped into the next one. All eleven independent tests (run and run_streamed, to_string and to_json, repeated round trips, two chained JSON resumes, to_input_list) fail on base and pass on both A and B, so neither leaves the reported behaviour broken.

The difference is in how wide the new acceptance is. Patch A unwraps any assistant message whose content is a single `output_text` part, regardless of other keys. That also matches ordinary model-generated messages (which carry `id`, `type: message`, and `annotations` on the part), so a model that emits text starting with the summary preamble and wrappers would now be flattened into history, where on base it was preserved. Patch B restricts the unwrap to the exact shape RunState writes (`status == completed`, item keys exactly role/status/content, part keys exactly type/text), which keeps the change targeted at the serialization rewrite the issue blames and preserves the existing behaviour for genuine model output. B adds a case to `test_nest_handoff_history_preserves_assistant_content_with_wrapper_markers` using a real message run item to pin that down. The exact-key matching is brittle to future serialization drift, but B's end-to-end round-trip test would fail loudly if that happened, so the brittleness is mitigated.

On tests: A adds a solid parametrized regression test comparing model input and to_input_list between in-memory and JSON resumes, plus a focused unit test for the extractor including a two-part negative case. B instead strengthens the existing `test_nested_handoff_history_partition_survives_interruption_resume`, which the issue explicitly called out as passing despite the bug, parametrizes it over streamed/non-streamed, compares restored vs in-memory for both model input and replay, and asserts `1. user: start` appears as its own line. Both test sets would fail before and pass after. B's tests cover one more design point (no false positive on model output) that A's do not.

Scope and craft are comparable; A is simpler and mirrors the issue's proposed diff, B is slightly more verbose but its comment explains why the shape is matched so narrowly. The narrower, better-guarded acceptance and the extra negative test tip this to B.

Describe the bug

With RunConfig(nest_handoff_history=True), a handoff replaces the history with one assistant summary message whose content is a string. On the next handoff, _extract_nested_history_transcript recognizes that summary and flattens its records into the new transcript.

RunState.to_string() / to_json() rewrites assistant string content as [{"type": "output_text", "text": ...}]. The summary sits in the run's original input, so it gets rewritten too. After RunState.from_string(), the detector no longer recognizes it, because it only accepts string content. The next handoff then JSON-dumps the whole previous summary into the new one as a single record. The receiving agent sees the user's turn buried in an escaped string, and result.to_input_list() carries the same doubly nested summary.

A run that isn't interrupted, or one resumed from the in-memory RunState, produces the normal flat transcript.

Expected behavior

A run resumed from a serialized RunState hands off with the same flattened transcript as an uninterrupted run or an in-memory resume.

Root cause

  • RunState._serialize_input turns assistant string content into a single output_text part (run_state.py#L1564). That's intentional and covered by test_serializes_assistant_messages.
  • The summary built by _build_summary_message (history.py#L386) is part of the original input, so it gets the same rewrite.
  • _extract_nested_history_transcript returns None unless content is a str (history.py#L485). _flatten_nested_history_messages then keeps the restored summary as an ordinary item, and the next summary JSON-dumps it.

test_nested_handoff_history_partition_survives_interruption_resume runs this same scenario, but its summary.count("once") == 1 check (L1849) still passes when the old summary is embedded, since the text appears once either way.

A possible fix

Accept the single-output_text shape that RunState itself writes. The serialized format stays the same, and the existing preamble and wrapper checks still decide whether the text is a summary.
