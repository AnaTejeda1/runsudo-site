Description

Three examples on the error-reference pages no longer raise the error they document, and the documentation test suite cannot detect it.

Every example on those pages has the same shape: do something that should fail, catch it, then print or assert the error code. The only assertion lives inside the except branch. When the operation stops failing, that branch never runs, so nothing is printed and no assert is evaluated. run_print_check compares printed output against the #> comments, and an example whose print never ran produces no output to disagree with, so the example exits 0 and CI stays green while the page documents behaviour that no longer exists.

I checked this exhaustively rather than by sampling. I injected a sentinel as the first statement of every except block on both error pages and ran each example. Of the 152 examples containing a try/except at v2.13.5, all 152 run, and exactly 3 never enter their except branch. On main the count is 3 of 157. None of the three is marked test="skip", so all three are executed by CI today.

1. complex_type, docs/errors/validation_errors.md

Model(num=False) now validates successfully to 0j, so the #> 'complex_type' line never prints. This changed in 2.13.0b1 with #12498, which made complex validation call the complex() constructor unconditionally in Python mode, and complex(False) is 0j.

2. string_sub_type, docs/errors/validation_errors.md

The section says a strict str field rejects an instance of a str subclass. It does not: the example returns a plain str with the value 'foo', and #> 'string_sub_type' never prints. pydantic_core 2.49.0 still declares the error ("Input should be a string, not an instance of a subclass of str"), but I could not find any str schema that raises it. Building core_schema.str_schema() directly with strict=True, without strict, and with strict=True plus a pattern all accept a str subclass and return a plain str.

This looks intentional rather than accidental. #6261 reported exactly this behaviour as a bug in June 2023, was labelled bug V2, and was closed with the conversation moved to pydantic-core#786. So the check appears to have been removed on purpose and this documentation section was left behind describing it.

3. invalid-for-json-schema, docs/errors/usage_errors.md

ImportString has had a JSON schema since 2.8.0 via #9344, so Model.model_json_schema() succeeds and returns a plain string schema. The assert exc_info.code == 'invalid-for-json-schema' inside the except block has not executed since that release.

Output of the example code below

Identical on 2.13.5 and on main at 2.14.0b2:

1. no exception; num = 0j
2. no exception; accepted 'foo'
3. no exception; {'properties': {'a': {'title': 'A', 'type': 'string'}}, 'required': ['a'], 'title': 'ImportStringModel', 'type': 'object'}

Suggested fixes

  1. complex_type is a one-word fix. Model(num='not a complex number') still raises complex_type, and so do [], {} and a bare object(). Replacing False with any of those restores the example.
  2. string_sub_type needs a decision rather than a fix, which is the main reason I am opening an issue instead of sending a patch. Given the trail through #6261, the section probably wants deleting rather than repairing, and possibly the error variant too, but that is your call.
  3. invalid-for-json-schema needs a type that genuinely has no JSON schema, in place of ImportString.

Separately, the blind spot itself is fixable. If an example on these pages had to demonstrate that the error occurred, for instance by printing inside the except and also failing loudly when nothing was raised, then a future change like #12498 would turn the docs red instead of silently making a section untrue. I am happy to send a PR for any or all of this, including that check as a test, if you tell me which direction you prefer.

What the agent reported

All stages complete. Here's the final report.

What was wrong

Three examples on pydantic's error-reference doc pages documented errors that are no longer raised, and the docs test harness (run_print_check) couldn't detect it: the only assertion in each example lives inside an except branch, so when the operation stops failing, that branch never runs and there is no printed output to disagree with the #> comment — the example exits 0 and CI stays green.

What I changed

Doc fixes

  • docs/errors/validation_errors.md — complex_type: changed Model(num=False) (which now validates to 0j) to Model(num='not a complex number'), which still raises complex_type.
  • docs/errors/validation_errors.md — deleted the entire ## \string_sub_type\`section. That error is declared in pydantic-core but has no construction site (confirmed: no RustValErrorproduces it; nostrschema rejects astr` subclass), so it cannot be demonstrated. Clean single-blank-line spacing preserved into the next section.
  • docs/errors/usage_errors.md — invalid-for-json-schema: replaced a: ImportString (which has had a JSON schema since 2.8.0) with a: Callable[[int], int] (imported from collections.abc, per ruff UP035), which genuinely has no JSON schema and raises invalid-for-json-schema.

Tests

  • tests/test_docs.py — added test_error_reference_examples_reach_except, the report's suggested blind-spot fix: it collects every example on both error pages, AST-instruments each except handler, executes the example as an isolated module, and fails loudly if any handler never runs. This closes the detection gap so a future change like #12498 turns the docs red.
  • tests/test_docs.py — added expected_validation_error_codes.remove('string_sub_type') to test_validation_error_codes, mirroring the existing timezone_offset carve-out. This was required, not optional: deleting the doc section removes it from the documented set, but string_sub_type must remain in core_schema.ErrorType because pydantic-core's own test_errors.py asserts that literal exactly mirrors the Rust list_all_errors(). It is the same category as timezone_offset — a valid core code not reachable from pydantic. I did not remove the Rust variant (would need a rebuild and would break pydantic-core's suite — out of scope).

Test evidence

  • The new regression test was red before the fixes: 3 failed — exactly validation_errors.md:227 (complex_type), validation_errors.md:1852 (string_sub_type), usage_errors.md:622 (invalid-for-json-schema).
  • After the fixes: ./bt-test tests/test_docs.py → 783 passed, 117 skipped, 0 failed, including the new test, test_validation_error_codes, test_error_codes, and re-execution of all examples on both pages.
  • Reviewer confirmed all three examples genuinely raise/print the documented error, the carve-out hides no bug, the new test cannot pass vacuously for the three targets, and there is no scope creep or scratch files.

Requirements disposition

  1. complex_type fix — Implemented; regression test + example execution pass.
  2. string_sub_type decision — Resolved by deletion (report's lean), with the forced ErrorType-bijection reconciliation via the test's own carve-out mechanism. Evidence: audit + Rust source confirm no construction site; deletion verified; tests green.
  3. invalid-for-json-schema fix — Implemented with Callable; except/assert now runs; verified.
  4. Blind-spot detection test ("separately… I'm happy to send a PR… if you tell me which direction") — Implemented as test_error_reference_examples_reach_except; shown red-before / green-after.
  5. Remove the pydantic-core error variant (offered as "your call") — Skipped, with evidence: pydantic-core/tests/test_errors.py:550-556 requires the Python literal to mirror Rust, so removing it needs a Rust change + rebuild; left in place and carved out instead.
