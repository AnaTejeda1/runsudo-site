suspense.resolve() is called without a pending branch.

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

The issue is a page whose setup navigates away while Suspense is pending, which leads to the 'suspense.resolve() is called without a pending branch' warning. Patch A targets the 'toggled back to current active branch' path in patchSuspense. When the router redirects back to the already-active page while the new page is pending, the active branch is patched while `suspense.pendingBranch` is still set. Any async dep mounted during that patch is counted against the pending branch. `resolve(true)` then clears pendingBranch, and when the stray dep later resolves, it calls `suspense.resolve()` with no pending branch, producing the reported warning. Patch A temporarily nulls pendingBranch during the patch so such deps are not counted, then restores it for the forced resolve. That addresses this sequence directly. Its test models the issue: page B redirects to A during its async setup, and A renders a new async child. The test asserts that no unhandled rejection or error occurs and that the final DOM is correct. Patch B instead changes the same-root-type pending-branch path with a deps++/deps-- guard and tests nested `suspensible` Suspense scenarios. Those scenarios do not involve navigating away during setup and are not the issue's reproduction. Patch B may be a valid hardening for nested suspense, but it does not address the reported toggle-back case. Patch A is the better fix on correctness and test relevance.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

What the agent reported

The "without a pending branch" error is fixed. The new regression test fails on the old code and passes with the fix. I reproduced it with a simulated redirect (a shared ref the page's setup changes), not with vue-router or the codesandbox.

What was wrong: say a page has rendered inside <Suspense>, the user moves to a page whose setup() is async, and that setup() sends them back to the first page before it finishes. Suspense then patches the page that is already showing (packages/runtime-core/src/components/Suspense.ts, the "toggled back" branch of patchSuspense). During that patch the suspense still looked like it was waiting on something. So any new async component mounted during the patch was counted as something to wait for. resolve(true) then cleared the pending state, but that count stayed above zero. When the async component later finished, it called suspense.resolve() with nothing pending and threw the error. It's thrown inside a promise, which is why the app keeps working, as the report says.

What I changed (Suspense.ts:344-359, 4 lines): in that branch, the pending state is cleared while the visible page is patched, then put back just before suspense.resolve(true), which still needs it. The page being patched has already resolved, so async components inside it now resolve on their own, as they do in any resolved suspense.

Test evidence:

  • New test: async dep mounted while toggling back to active branch before resolve in packages/runtime-core/__tests__/components/Suspense.spec.ts. Page B's async setup() sends the user back to page A, which then mounts a new async child. The test checks that the child renders and that no error is thrown.
  • Before the fix it failed with "suspense.resolve() is called without a pending branch.".
  • After the fix it passes, as do all 60 tests in that file.
  • The page check alone passes even without the fix, because the child renders before the error. So the test catches the error through a temporary unhandled-rejection listener; that is less direct than a plain assertion.
  • Nearby suites: all 1386 tests in runtime-core and server-renderer pass. In runtime-dom and vue, 290 pass and 1 is skipped. No existing test was changed.
  • Review: a read-only review found the fix correct and the diff limited to these two files. It noted that while the visible page is patched, its effects, transitions and teleports now run as they would on a normal update. That is right for a page already on screen.

Requirements:

  1. No "suspense.resolve() is called without a pending branch" error when a page's setup sends the user to another page: fixed and covered by the new test above.
  2. The app keeps working (it already did): the test checks that the content still renders (<div>async child</div>).
  3. Leaving to some other page instead of going back: no change. Reading the code, that path starts a new pending round and ignores the earlier page's result, so it doesn't reach this error. I didn't write a test for it.

The changes are uncommitted in the working tree.
