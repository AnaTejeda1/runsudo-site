Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the reported problem: the independent tests show every scenario (schema without `self`, instance state, async, two instances, run_sync) passing on A and B alike. The difference is in how robustly each gets there.

Patch A detects a class-body function whose first positional parameter is `self` (via qualname plus signature), derives the schema by binding a placeholder receiver so `inspect.signature`/docstring handling drop `self` through the normal path, and on instance access builds a genuinely new FunctionTool through the same `_create_function_tool` path with a real bound method. It reuses the existing invocation code unchanged, handles `RunContextWrapper` in the second position for free, deliberately avoids caching on the instance (so copy/deepcopy/pickle of the owner keep working, and tests prove it), and gives a clear UserError when the class-level tool is invoked. Its tests cover schema, docstring args, name_override, context, async, undocumented methods (guarding the `inspect.getdoc` class-fallback trap it explicitly comments on), copy/deepcopy/pickle of the owning object, non-method functions that happen to have a `self` parameter, and a full Runner run with FakeModel. The main cost is that each attribute access regenerates the pydantic schema, a performance smell rather than a correctness bug.

Patch B changes the public `function_schema` to strip any unannotated first `self`/`cls` and adds a `skips_receiver` field, then in `function_tool` duplicates the entire ~45-line invocation body into a receiver-aware variant. Binding in `__get__` is done by `copy.copy(self)` and then poking the private `_invoke_tool_impl` attribute on the copied `_FailureHandlingFunctionToolInvoker`; this only stays isolated per instance because the tool's copy machinery happens to rebind the invoker, and it silently returns an unbound copy if the handler is a different type. Its heuristic also misses methods whose `self` is annotated (e.g. `Self`) and treats any plain function with an unannotated `self`/`cls` first param as a method. Tests are reasonable (schema unit tests, descriptor behavior, context, async, unbound error) but stop at `on_invoke_tool`; there is no agent/Runner-level test, no copy/deepcopy coverage, and the `cls` test exercises a bare function rather than a real classmethod.

On scope, B's edits to `function_schema` and the duplicated invoker widen the blast radius for no additional benefit on the issue's ask. On craft, A integrates with existing construction and error-handling paths and documents the new behavior in the `function_tool` docstring, while B relies on private internals and copy semantics. A is the better fix.

The issue

View on GitHub

I group my tools into classes, and they leverage attributes of the instantiated object to work properly. The function_tool decorator doesn't seem to support this. For example, the following works (as expected):

@function_tool
def get_random_number() -> int:
    """Get a random number."""
    return random.randint(0, 100)

agent = Agent(
    name="Assistant",
    instructions="You are a helpful assistant",
    tools=[get_random_number]
)
result = Runner.run_sync(agent, input="Get me a random number")
print(result.final_output)

But the following doesn't:

class Tools:
    @function_tool
    def get_random_number(self) -> int:
        """Get a random number."""
        return random.randint(0, 100)

tools = Tools()

agent = Agent(
    name="Assistant",
    instructions="You are a helpful assistant",
    tools=[tools.get_random_number]
)
result = Runner.run_sync(agent, input="Get me a random number")
print(result.final_output)

Running this produces an error like:

openai.BadRequestError: Error code: 400 - {'error': {'message': "Invalid schema for function 'get_random_number': In context=('properties', 'self'), schema must have a 'type' key.", 'type': 'invalid_request_error', 'param': 'tools[0].parameters', 'code': 'invalid_function_parameters'}}

i.e., the self parameter isn't accounted for.

There's probably a ton of different ways of approaching this, but I've been utilizing the class-based tool pattern quite extensively and I've found it works pretty well for keeping tooling clean and simple. I'm happy to consider alternative approaches, but if there was just a way to ignore the self parameter, then I think everything else would just work, no?
