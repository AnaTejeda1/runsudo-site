Subtest durations become negative when time is mocked (subtests.py bypasses _pytest.timing)

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches make the identical core change in subtests.py: replace the direct `time.time()`/`time.perf_counter()` lookups with `timing.Instant()` and `.elapsed()`, which is exactly the root-cause fix the issue proposes, and all four independent tests pass under both. The difference is everything else. Patch A stops there, adds a changelog entry, and adds a regression test that mocks both clock functions inside a subtest, sleeps on the real clock, and checks the SubtestReport's duration/start/stop plus the junitxml `time` attribute; that test would fail on base (negative duration) and pass after. Patch B bundles the same fix with an unrequested redesign of `CallInfo`: it removes the `start`/`stop`/`duration` constructor parameters in favour of a `timing.Duration` object, turns the three fields into properties with setters, relaxes `Instant`'s `init=False` on both fields, adds a `timing.UNMEASURED` sentinel, and rewrites the unittest subtest path. That widens the blast radius for a one-function bug: it changes a constructor signature that third-party plugins may call (the patch itself acknowledges plugins assign these attributes), and the setters have surprising semantics (setting `stop` only changes the wall-clock field while setting `duration` only changes the perf-counter field, so `stop - start` and `duration` can silently disagree). None of this is needed to resolve the issue and it adds regression risk and review burden. Patch B's regression test is also valid (mocks perf_counter to -1e9 and asserts non-negative duration and consistent start/stop), and the unittest timing test is fine but unrelated. On correctness the patches are equal; on tests roughly equal; on scope and craft Patch A is clearly better because it fixes the reported problem precisely, matches the existing `runner.py` pattern, and introduces no API churn.

Description

When a test mocks time.perf_counter / time.time (as clock-mocking libraries like freezegun and time-machine do), subtests report negative durations and a stop timestamp of 0.0 (January 1, 1970). Normal tests are unaffected by the same mocking.

Reproducer

# test_repro.py
import time

def test_normal(monkeypatch):
    real_sleep = time.sleep
    monkeypatch.setattr(time, "perf_counter", lambda: 0.0)
    monkeypatch.setattr(time, "time", lambda: 0.0)
    real_sleep(0.3)

def test_with_subtest(subtests, monkeypatch):
    real_sleep = time.sleep
    with subtests.test(msg="frozen clock"):
        monkeypatch.setattr(time, "perf_counter", lambda: 0.0)
        monkeypatch.setattr(time, "time", lambda: 0.0)
        real_sleep(0.3)
$ pytest -q --junitxml=out.xml
.u.                                                                      [100%]
2 passed, 1 subtests passed in 1.23s

$ grep -o 'name="[^"]*" time="[^"]*"' out.xml
name="test_normal" time="0.301"
name="test_with_subtest" time="-1194.217"

Both tests sleep 0.3s under a mocked clock. The normal test reports 0.301s; the subtest reports −1194s (the exact value depends on the machine's uptime).

Cause

Normal test execution and subtests handle timing differently.

In src/_pytest/runner.py, pytest uses timing.Instant() and instant.elapsed() from _pytest.timing. However, src/_pytest/subtests.py imports the time module directly and calls time.time() and time.perf_counter():

$ grep -n "time\." src/_pytest/subtests.py
219:        self._start = time.time()
220:        self._precise_start = time.perf_counter()
245:        precise_stop = time.perf_counter()
247:        stop = time.time()

_pytest.timing imports perf_counter directly using from time import perf_counter, so it keeps its original function reference even if time.perf_counter is patched later. subtests.py looks up the function on the time module whenever it is called, so it picks up the patched value.

So if a subtest starts on the real clock and the test then patches time.perf_counter to return 0.0, the subtest computes its duration from the real start time and the patched end time, giving a negative duration. The same happens with time.time(), giving a stop timestamp of 0.0.

This is the situation _pytest.timing exists to prevent. Its docstring says pytest grabs time functions internally "to avoid tests mocking "time" to affect pytest runtime information (issue #185)", and #7764 covered the freezegun case for --durations. The subtests module, merged later, doesn't follow that rule.

Proposed fix

Switch subtests.py to timing.Instant() / .elapsed(), matching runner.py. If this approach sounds right, I'd be happy to send a PR with a regression test.

Related

#14412 (fixed in #14670) addressed how subtest timings are aggregated in the terminal with console_output_style='times'. This is a separate problem: the timing values themselves are wrong when time is mocked, and it still reproduces on main after #14670.
