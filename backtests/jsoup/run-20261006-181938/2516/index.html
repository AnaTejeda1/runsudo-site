Review HttpClient's thread use under heavy request load

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the root cause the same way: requests with no authenticator and no custom SSLContext now share one static HttpClient instead of each Connection building its own client with its own selector and worker threads. Both also rebuild the shared client when the JVM default SSLContext changes.

Patch A goes further with a weakly keyed pool of shared clients per custom SSLContext. That extra machinery (WeakHashMap plus WeakReference values) is beyond the issue's ask and adds some subtlety: clients can be collected and rebuilt. Patch A also keeps the old unsynchronized per-connection logic for the authenticator path. Its standout test is an integration test that counts SelectorManager threads across repeated `Jsoup.connect` calls, which directly measures the reported symptom.

Patch B introduces an immutable ClientState holding (client, authenticator, sslContext) with a single `matches` check. It uses double-checked locking for both the shared client and the per-connection client, so concurrent requests on a session can't race to create duplicate clients. It replaces the two loosely coupled fields (`client`, `lastAuth`) with one volatile state field, which is clearer and fixes a latent ordering quirk in the old reuse logic. Its tests check:
- sharing across connections
- that concurrent lazy initialization yields a single client
- default-SSL refresh
- rebuilds when the authenticator or SSL context changes
- an integration test that mixed proxied and direct concurrent requests through the now-shared client keep proxy routes isolated

That last test covers the main new risk of sharing a client, since proxy settings are per-request thread-locals. Patch B's test refactor to @AfterEach is minor churn but harmless.

Overall, both are correct. Patch B's design is more robust under the concurrent heavy-load scenario the issue describes, and its tests better cover the correctness risks introduced by sharing. Patch A has the nicer direct thread-count test but more complex pooling and no concurrency hardening.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
