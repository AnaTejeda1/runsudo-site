[Bug]: default_priority not being used when no priority provided

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the root cause the same way: acompletion resolves the explicit priority or the router's default_priority (handling 0 correctly, unlike the original `or`), pops it from kwargs, and runs the request through `_schedule_factory` with `async_function_with_fallbacks`, while `schedule_acompletion` delegates to acompletion so the request is queued exactly once. Both cover prompt-management models, atext_completion, and the /queue route, and both pass all seven independent tests. The difference is scope and risk. Patch A is a focused fix with targeted unit tests (default used when absent, explicit 0 overrides default, schedule_acompletion queues once, prompt-management and text-completion paths) that would fail before and pass after. Patch B wraps the same fix in a large redesign: a new request_priority module with pydantic validation, a new behavior that rejects non-integer priorities with a 400 (reversing an existing integration test that previously asserted such values bypass the scheduler and are forwarded), drop_params resolution across request/router/deployment levels, default_priority parsing with warnings, a change to `_wait_for_scheduler_turn` for pinned deployments, queue-route error remapping, and hundreds of lines of integration tests including one explicitly skipped as a known unfixed bug. None of that was asked for by the issue, it changes observable client behavior, and it makes the actual fix much harder to review and more likely to regress something adjacent. On correctness they are equivalent; on tests A's are sufficient and direct; on scope A clearly wins; on craft A is consistent with the surrounding code without introducing a parallel validation layer.

What happened?

I'm using litellm-helm to deploy my litellm, I've configured it to have a default_priority as this :

proxy_config:
  router_settings:
    default_priority: 10

When using my client, it does not send a priority and so I get the following error :

Error: API error from litellm (model: code): LLM backend error [litellm]
  status: 500 Internal Server Error
  reason: Internal Server Error
  request_id: N/A
  endpoint: <proxy>/chat/completions
  model: code
  provider_message: Router.schedule_acompletion() missing 1 required positional argument: 'priority'
  body_excerpt: {"error":{"message":"Router.schedule_acompletion() missing 1 required positional argument: 'priority'","type":"None","param":"None","code":"500"}}
  payload_summary: {"model":"code","message_count":4,"approx_chars":13499,"temperature":0.2,"has_tools":true,"tool_choice":"auto"}

As I have seen in the following code (router.py):

request_priority: Final = kwargs.get("priority") or self.default_priority
            start_time: Final = time.time()

the variable request_priority which get the potential default value isn't used in the call to the schedule_acompletion method hence the error.

  2. The HTTP response is 200 and the default_priority configured is used.
