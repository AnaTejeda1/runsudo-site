model_dump_json crashes on a SecretStr field with an unvalidated None default (internal AttributeError instead of null/warning)

Worse

The merged fix was judged better than our patch.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Patch A fixes the root cause with a one-line change. Setting `when_used='unless-none'` on the `_SecretField` plain serializer means pydantic-core never passes `None` to `_serialize_secret_field`, so it falls through to default handling and produces `{"f":null}`. That is the issue's preferred outcome 1, matching how `Optional[SecretStr]` and `int = None` behave. Valid secrets serialize exactly as before, `model_dump()` is unchanged, and the risk is minimal. Its test reproduces the reported failure and checks both python and JSON output, so it would fail before the fix and pass after.

Patch B takes the second route: it raises `PydanticSerializationUnexpectedValue` so core falls back and emits a warning. It also extends this to `Secret`, `ByteSize`, `EncodedBytes`/`EncodedStr` and `Pattern`. That approach is defensible, but it has costs:
- It changes python-mode behavior. `model_dump()` on a `SecretStr = None` model previously returned `None` silently; now it emits a warning. The issue explicitly calls that path fine, and B's own test has to suppress warnings there.
- It alters several unrelated serializers, such as `ByteSize` moving from `int` to an isinstance-checked `_serialize`, which changes JSON-schema default handling. These changes can affect union serializer selection and existing users' outputs, which adds risk well beyond the issue's ask.
- Its main test asserts a `UserWarning` while also including `n: int = None`, which may itself produce the warning. That weakens the test as evidence for the secret-specific behavior.

The extra hardening earns no credit and adds risk. Patch A delivers the cleaner, consistent `null` outcome with a targeted, correct change.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Description

A model field annotated SecretStr with an unvalidated None default crashes serialization to JSON. Per models docs, field defaults are only validated when validate_default=True, so constructing such a model without arguments is legal — and every other scalar annotation serializes the unvalidated default as null. For SecretStr, however, model_dump_json() raises instead.

Note this is specific to the JSON path and to the non-nullable annotation:

  • model_dump() (python mode) returns None fine;
  • Optional[SecretStr] = None dumps to JSON correctly ({"s":null});
  • a control field n: int = None also dumps fine — so only the combination "non-nullable SecretStr + None default + JSON serializer" hits the broken path.

Example Code

import warnings
from typing import Optional
from pydantic import BaseModel, SecretStr

class M(BaseModel):
    n: int = None          # same pattern, control group
    s: SecretStr = None    # crashes

with warnings.catch_warnings(record=True) as w:
    warnings.simplefilter("always")
    print(M().model_dump())          # {'n': None, 's': None}  -- OK
    try:
        print(M().model_dump_json())
    except Exception as e:
        print(type(e).__name__, "|", e)
    print("warnings emitted:", len(w))

class O(BaseModel):
    s: Optional[SecretStr] = None

print(O().model_dump_json())         # {"s":null} -- OK

Actual behavior

{'n': None, 's': None}
PydanticSerializationError | Error calling function '_serialize_secret_field': AttributeError: 'NoneType' object has no attribute 'get_secret_value'
warnings emitted: 0
{"s":null}

The exception escapes even though the value mismatch is exactly the situation the serialization layer normally degrades gracefully on (serialize as-is / warn). No UserWarning about the mismatched default is emitted either.

Looking at _serialize_secret_field, it calls .get_secret_value() unconditionally when the serializer runs with when_used='always'; there is no guard for value is None on a non-optional annotation, while core handles None defaults for other types before user serializers are reached.

Expected behavior

Either of the consistent-with-everything-else outcomes:

  1. serialize the unvalidated default as null: {"n":null,"s":null} (matching how int = None, str = None etc. behave), or
  2. at minimum emit the standard serialization-mismatch UserWarning instead of raising an internal AttributeError wrapped into PydanticSerializationError.

The current traceback points users at pydantic internals rather than their own model definition.
