Add encoding.HexDecode/Encode

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

The production code is functionally identical in both patches: `HexDecode` and `HexEncode` on the encoding namespace use `cast.ToStringE` plus `encoding/hex`, with the same method mappings and examples in `init.go`. Correctness is therefore equal, and the difference comes down to tests and craft. Patch B's unit tests are more thorough. They cover uppercase hex input, empty strings, invalid characters (`zz`), odd-length input (`486`), non-string input (42), and a round-trip check that encoding then decoding reproduces the original. Patch A's unit tests have only one happy-path case and one type-error case per function. Both patches add an integration test that checks the issue's motivating case: building an SRI string with `crypto.SHA256 | encoding.HexDecode | encoding.Base64Encode` and comparing it to the `Data.Integrity` of a fingerprinted resource. Patch B puts this test in a new `encoding_integration_test.go` next to the feature it exercises, and it also checks plain encode and decode output. Patch A puts its test in `tpl/templates/decorator_integration_test.go`, which is an odd place unrelated to the encoding package, and it pulls in decorator, Store and CSP-header machinery that obscures what the test is for. Patch B also adds documentation pages for both functions, including the SRI use case. That earns little credit on its own but adds no risk. Overall, Patch B has stronger edge-case tests and better-placed integration tests for the same implementation.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The issue

View on GitHub

See https://github.com/gohugoio/hugo/issues/15060#issuecomment-4790405347

It's clumsy that you need to create a resource (making up an unique filename) to get a SRI hash.

I suggest we add crypto.Fingerprint with a similar signature to https://gohugo.io/functions/resources/fingerprint/

hash.Fingerprint [ALGORITHM] any -> string

The function name is a little clumsy, but we need to keep the two very similar functions in line.

Where any typically is a string (but can also be a Resource -- we have similar unwrappers elsewhere).

It would then return e.g. sha256-Yuh...rfE=.

Note to implementer: There's some obvious code reuse potential here.
