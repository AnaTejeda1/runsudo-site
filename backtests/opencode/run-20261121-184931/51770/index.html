Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches attack the same root causes: the question text was never bounded or scrollable, and the dock's max height ignored the visual viewport that iPhone browser bars and the keyboard shrink. Both make the details region scroll in a capped share of the dock, listen to visualViewport resize/scroll, scroll the text back to top on question switch, and ship 393x852 component tests for both the classic and experimental UIs. The independent iPhone-screen tests fail on base and pass on both, so the evidence does not separate them; the difference is in how completely and how cleanly each one fixes it.

Patch B goes further on correctness. It removes the unconditional 240px floor (questionMaxHeight caps the floor at what the screen shows), which is exactly the thing that can push Next/Submit off a short visual viewport when the keyboard is up; Patch A leaves `Math.max(240, ...)` in both docks. B ignores the visual viewport while pinch-zoomed (scale !== 1), where offsetTop/height would otherwise produce a bogus bottom; A uses it unconditionally. B's experimental text height (max(40% of room, room - answers)) lets a long question use the space a short list leaves and vice versa, whereas A pins the prompt to a fixed 45% of (max-120) regardless of list length, wasting room when the list is short. B also factors the mask logic into textFeathers instead of duplicating paint's mask arithmetic inline in the onScroll handler as A does.

On tests, both component suites are substantive (viewport checks on Next/Submit, scrolling the text box to its last line, tapping the last option, completing the flow). B additionally unit-tests the extracted layout rules (floor never exceeding the visible screen, keyboard-panned viewport, pinch zoom), which directly encode the issue's constraint and would fail on base.

On scope and craft, A carries more unexplained adjacent churn: a redundant `edge` computed from the same parent element as `column`, `data-scrollable` attributes with no visible consumer, focus/scrollTop micromanagement replacing native focus scrolling, and an `optionsHeight` change for minimize that is unrelated to the report. B's non-test diff is tighter and its intent is documented; its surviving lockfile hunk is ignored per the ground rules. Overall B resolves more of the scenario (short visual viewport, pinch zoom, room sharing) with clearer, testable code, so B wins.

Description

In the V2 web app, long Question tool prompts or many options push Next and Submit below the mobile viewport. Long question text can also leave the options inaccessible. Users cannot finish answering the agent.

Reported on an iPhone 15 Pro and reproduced at a 393 × 852 browser viewport. The question and options should scroll while the navigation buttons stay visible.

Related reports: #23730 and #38286. Both are closed; #38286 was closed for inactivity. This still reproduces on v2.

Plugins

Reproduced with the production question component and fixture data; no plugin required.

OpenCode version

2.0.18, v2 at 0caae608a2

Steps to reproduce

  1. Open the V2 web app on an iPhone 15 Pro or use a 393 × 852 mobile viewport.
  2. Ask the agent to use the Question tool with 12 options, each with a long label and description.
  3. Try to reach the last option and tap Next or Submit.
  4. Repeat with question text longer than the screen height.
