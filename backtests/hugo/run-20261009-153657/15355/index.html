tpl/transform: Strip BOM prior to unmarshaling a resource or string

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the reported problem at the same root: they trim the UTF-8 BOM inside metadecoders.Decoder.Unmarshal, which transform.Unmarshal uses for both resources and strings. Format detection in FormatFromContentString is index-based, so the CSV/JSON/TOML/XML/YAML cases in the issue work under either patch.

Patch B is more robust at the edges:
- It also trims in UnmarshalTo and UnmarshalYaml, so callers that bypass Decoder.Unmarshal are covered.
- It trims the string input in tpl/transform/unmarshal.go before the empty/whitespace check. A BOM-only string therefore returns nil, as an empty string would. Under Patch A, that string would fall through to format detection and likely error.
- It extends the same handling to i18n bundles (TOML/JSON/YAML), which the issue's 'same/similar problem' framing suggests. The added scope is low risk and is factored into a small, well-named TrimBOM helper instead of a repeated inline byte literal.

On tests, Patch B is clearly stronger:
- Unit tests in decoder_test.go cover every format, including ORG and empty-after-BOM.
- Integration tests cover data files, i18n, and transform.Unmarshal for both resources and strings in every format, plus the BOM-only case.
- Patch A has a single integration test that exercises only one string format.

Patch A also adds unrelated whitespace reformatting of existing test calls, which is noise in the diff. Overall, B is the better fix.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
