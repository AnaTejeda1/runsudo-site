Make .Render take additional data

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

The issue specifies the desired signature as `PAGE.Render [DATA] NAME`: the optional data comes first, and when DATA is set it is used as the template context instead of PAGE. Patch B implements exactly that argument order. With one argument it treats it as the layout name and passes the page as context. With two arguments it takes (data, name). It adds an integration test covering all three cases: no data, a dict containing the page plus extra keys, and a scalar data value. It also updates the docs signature and explanation to match. Patch A implements the reverse order, `Render VIEW [CONTEXT]`, which contradicts the signature the issue asks for. Templates written to the issue's documented form (`.Render (dict ...) "summary"`) would fail under A, because it would try to cast the dict to a view name. A does add error-path tests (too many args, non-string view), which is decent craft. Otherwise the two patches are mechanically equivalent: same interface change, same lazy/nop/test implementations, same cast.ToStringE. B's correctness against the requested API and its broader positive test coverage outweigh A's extra error tests.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

PAGE.Render NAME

This has been discussed before.

  • The contract has always been that the templates that .Renders gets the data context as e.g. page.html, a page.Page.
  • We can only pass 1 argument to Go's template renderer, which I guess is the blocking reason for not having done this sooner.

So, if we want to do:

PAGE.Render [DATA] NAME

I'm guessing we have 2 top-level options:

  • We say that if DATA is set, we use that as the context passed to the templates,. else PAGE.
  • We somehow (e.g. by embeding it in a { DataAdditionalContext, Page } struct or putting it into the current context.Context) wrap the Page so you can do both .RelPermalink and .DataAdditionalContext (naming of the latter is just picked out of a hat without thinking too hard.

What the agent reported

.Render now accepts an optional data argument: {{ .Render DATA NAME }}. When you pass DATA, the view template gets it as its context instead of the page. {{ .Render NAME }} works exactly as before. ./bt-test couldn't run any tests because its lane has no network and can't download Go modules (errors like lookup proxy.golang.org ... server misbehaving). I ran the same tests with go test, offline, against the module cache at /bt/cache/go-mod, and they pass.

What was wrong: Render(ctx, layout ...string) only took layout names, and it always passed the page as the template context, so there was no way to pass extra data. Go templates only accept one context value, so a second value can't be added alongside the page.

What I changed:

  • hugolib/page__per_output.go: Render now takes args ...any.
  • No arguments: the existing "no layout given" error.
  • One argument: it is NAME, and the page is the context.
  • Two arguments: the first is DATA and becomes the context; the second is NAME.
  • More than two: a "too many arguments" error.
  • Signature updates: the interface in resources/page/page.go (with an updated doc comment), page_nop.go, page_lazy_contentprovider.go, and the testPage helper in resources/page/testhelpers_test.go. The helper change is only the signature, which it needs to compile. The reviewer found no other code using the old signature.
  • Docs: docs/content/en/methods/page/Render.md now shows PAGE.Render [DATA] NAME with an example. It no longer says you "cannot pass additional context".
  • Test: TestRenderWithData in hugolib/page_test.go covers the plain .Render "myview", a dict holding the page plus other data, and a plain string as the data.

Test evidence:

  • Without the production change, TestRenderWithData fails with wrong type for value; expected string; got map[string]interface {}. With it, the test passes.
  • All Render tests in ./hugolib and all of ./resources/page/... pass, and go vet is clean.
  • I dropped a second test for the too-many-arguments error, because the old code already errors on three arguments, so it passed either way.

Requirements:

  1. PAGE.Render [DATA] NAME syntax: done, covered by TestRenderWithData.
  2. "If DATA is set, use it as the context, else the page": done, the one-argument call and the dict call in the same test cover both paths.
  3. Wrapping the page and DATA in one struct or a context.Context: not done. Only one of the two options was needed, and passing DATA directly is simpler. A wrapper would stop the context from being a real page.Page, which functions that expect a page would reject. Users who need both can pass (dict "page" . ...), which the test covers.
  4. Keep the existing contract that .Render NAME passes the page: kept. The existing Render tests still pass, including TestRenderWithoutArgument.

Behaviour to be aware of:

  • Two strings mean something new. The old version accepted several layout names but only used the first. {{ .Render "a" "b" }} now renders layout "b" with the string "a" as context. Nothing in the repo does this, but it may be worth a release note.
  • nil counts as DATA. {{ .Render nil "x" }} gives the template nil, not the page.

Everything is left as uncommitted changes. AGENTS.md and CLAUDE.md were already deleted in the working tree before I started, and I didn't touch them.
