Responses WebSocket server_error frames bypass model retry policies

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches touch the same condition in OpenAIResponsesWSModel.get_retry_advice and both pass every independent test, so the difference lies in how faithfully each matches the issue's specification and in test quality. The issue states that a pre-response frame with event_type="error" and error_type="server_error" should yield suggested=True, analogous to an HTTP 500, with no qualification on the code field. Patch B implements exactly that (`error_type == "server_error"`). Patch A adds an unrequested `code is None` restriction, so a server_error frame carrying any non-null code would still fall through to the common classifier and terminate the run, recreating the reported failure mode for a slightly different frame. Patch A even codifies this narrowing in a test asserting that `server_error` with code `invalid_request_error` is not retried, but that combination is not what the issue's 'invalid-request errors remain unaffected' boundary refers to; invalid-request frames have error_type="invalid_request_error", which neither patch matches. The existing `server_is_overloaded` branch, by contrast, keys on a code because that frame's type is service_unavailable_error, so B's type-based match is the consistent generalization. On tests, A only adds unit checks on get_retry_advice (plus a parametrized rewrite of the partial-overload test). B adds the same unit coverage for both stateless and previous_response_id cases, a partial-response unsafe case, and three end-to-end tests through stream_response_with_retry with provider_suggested() that verify the real retry path: stateless retry succeeds on a second connection, stateful request with previous_response_id is not replayed, and a server_error after response.created is not retried. Those exercise the exact runtime scenarios the issue enumerates and would fail on base. Scope and craft are otherwise comparable; B's extra test helpers are contained and reuse existing DummyWSConnection fixtures. B is the better fix.

The issue

View on GitHub

Please read this first

  • I read the Agents SDK model retry and Responses WebSocket documentation.
  • I searched open and closed issues for server_error, ResponsesWebSocketError, and related retry behavior.
  • I reviewed #3969 and its fix in #3978.

Describe the bug

When a Responses WebSocket returns a server_error frame before any response.* event for the current request, Runner.run_streamed() terminates with ResponsesWebSocketError instead of applying the configured model retry policy.

We captured the following raw server frame in four production occurrences within approximately three hours:

{
  "type": "error",
  "error": {
    "type": "server_error",
    "code": null,
    "message": "Sorry, something went wrong.",
    "param": null
  },
  "sequence_number": 2
}

The run had ModelRetrySettings(max_retries=2) configured with policies covering:

  • retry_policies.provider_suggested()
  • network errors
  • transient HTTP statuses

The upstream failure is intermittent, but the missing retry classification is deterministic.

Version 0.19.0 added retry advice for pre-response WebSocket errors whose code is exactly server_is_overloaded. This related error instead has:

  • event_type="error"
  • error_type="server_error"
  • code=None
  • no HTTP status
  • no retry headers

Consequently, OpenAIResponsesWSModel.get_retry_advice() delegates to the common OpenAI classifier, which returns no retry advice. Network and HTTP-status policies cannot match because this WebSocket error frame carries neither a network-error classification nor the equivalent 5xx status.

Debug information

  • Agents SDK version when observed: 0.18.2
  • Behavior also appears unhandled by the 0.19.0 retry classifier
  • openai package version: 2.45.0
  • Python version: 3.14.6
  • Transport: OpenAI Responses WebSocket
  • API interface: streaming

Reproduction

The provider error itself is intermittent, but the classifier behavior can be reproduced without making an API request:

from openai import AsyncOpenAI

from agents.models.openai_responses import (
    OpenAIResponsesWSModel,
    ResponsesWebSocketError,
)
from agents.retry import ModelRetryAdviceRequest


error = ResponsesWebSocketError(
    {
        "type": "error",
        "error": {
            "type": "server_error",
            "code": None,
            "message": "Sorry, something went wrong.",
            "param": None,
        },
        "sequence_number": 2,
    }
)

model = OpenAIResponsesWSModel(
    model="gpt-5.4",
    openai_client=AsyncOpenAI(api_key="test"),
)

for previous_response_id in (None, "resp_existing"):
    advice = model.get_retry_advice(
        ModelRetryAdviceRequest(
            error=error,
            attempt=1,
            stream=True,
            previous_response_id=previous_response_id,
        )
    )
    print(advice)

Actual output:

None
None

At runtime, retry_policies.provider_suggested() therefore receives no positive provider advice. The error terminates a stateless streamed run without applying the configured retry and backoff policy.

Expected behavior

A Responses WebSocket error with event_type="error" and error_type="server_error" received before any response.* event should produce positive provider retry advice, analogous to a transient HTTP 500 error.

Semantically, the advice should be equivalent to:

ModelRetryAdvice(
    suggested=True,
    replay_safety=None,
)

This should allow stateless requests using retry_policies.provider_suggested() to retry without universally declaring stateful requests replay-safe.

Existing retry-safety boundaries should remain unchanged:

  • Stateless pre-response requests may retry through provider_suggested().
  • Errors received after response processing begins must remain non-retryable.
  • Requests using previous_response_id, conversation_id, or other stateful continuation remain subject to the existing replay-safety gate.
  • Invalid-request and other non-transient WebSocket errors remain unaffected.

Additional context

This is related to, but distinct from, #3969 and #3978.

That fix matches only:

request.error.event_type == "error"
and request.error.code == "server_is_overloaded"

The production frame reported here instead uses error.type="server_error" with code=null, so it still falls through the retry classifier.
