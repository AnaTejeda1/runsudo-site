Suspense: reloading in quick succession with slow async setup() triggers HMR race

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the reported crash and the stale-render follow-up: the independent tests pass on A and B for both the nested-in-element and root-of-parent layouts, and both re-mark the instance dirty before calling parent.update() once the pending setup resolves, which is what the issue's analysis calls for.

B addresses the root cause more completely. The issue identifies the parent's postponement in componentUpdateFn via locateNonHydratedAsyncRoot as the reason the dirty mark goes stale. B reuses that exact function and loops: it waits on the instance's own asyncDep, then re-checks the parent's root chain and waits again if the freshly rendered instance exposed another pending async root (its nested test covers this). A only checks instance.asyncDep on the instance itself and then falls through to parent.update(); in the root-of-parent layout where the reloaded component's own root child is async and pending, A's parent.update() is postponed by the renderer, dirty.delete(instance) runs, and the child is patched rather than replaced, reproducing the 'keeps showing bar' symptom the issue describes. A's queueEffectWithSuspense trick only covers the case where the Suspense boundary itself is in a pending state, which is not the state these scenarios actually produce.

On edge handling the two trade blows: A's setupFailed fallthrough recovers after a rejected setup in the non-root layout without an errorHandler, while B silently drops the reload in that case (and both are stuck in the root layout). B's rejection test only covers the errorHandler path. A also adds a sensible adjacent guard in rerender() for a null job/update, which is useful but outside the issue's reload scenario and earns no credit by the rubric.

Tests: B's tests use explicit promise resolvers (deterministic) and cover both layouts, nested async roots, unmount during pending, and rejection; A's rely on wall-clock timeouts and cover both layouts, rejection, and rerender. One of B's test expectations on the versions array in the unmount test looks questionable, but the harness excludes patch-own test outcomes and I cannot verify it.

Craft: B guards with __FEATURE_SUSPENSE__ consistent with renderer.ts, uses try/finally to reset isHmrUpdating, and uses the scope.active check consistently; its only structural change is exporting locateNonHydratedAsyncRoot. A's design depends on Suspense effect-queue internals and a REQUEUE flag that rarely applies here.

Overall B's approach is the more principled and general fix of the mechanism the issue pinpoints, so B wins despite A's better behavior in one rejection edge case.

Steps to reproduce

In the repro, click "Reload twice".

  1. Show a page with a component whose <script setup> has a top-level await, e.g. await useFetch(...).
  2. Save two modules that the component depends on within a few milliseconds of each other. For example, save two translation message file together, or use a formatter that writes several files. Vite then sends one update per file.

What is expected?

Any additional comments?

Likely cause:

  • The first reload() remounts the instance.
  • The new instance's setup() is async, so mountComponent registers it with the Suspense and defers setupRenderEffect. Until that runs, instance.job is null.
  • The second reload() queues a job for that instance, and the job reads instance.job.flags. That check came from #13815, which assumes every instance has a job.

Guarding the null is not enough:

  • With instance.job ? !(instance.job.flags & DISPOSED) : !instance.isUnmounted, the error goes away, but the child keeps showing bar.
  • instance.parent.update() finds a pending async root (locateNonHydratedAsyncRoot) and postpones itself until asyncDep resolves.
  • By then, the queuePostFlushCb at the end of reload() has cleared hmrDirtyComponents, so isSameVNodeType matches and the child is patched instead of replaced.
  • The postponement is needed: the pending vnode has no el, so updating the parent at once fails in hostParentNode(prevTree.el).

Suggested fix: in the queued job, wait for the pending setup to resolve, mark the instance dirty again, and then replace it.
