SSR hydration warning: dynamic props on SVG elements are patched as properties instead of attributes

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the root cause the same way. In hydrateElement, they work out the element's own namespace from el.namespaceURI ('svg', 'mathml' or undefined) and pass it to patchProp instead of undefined. runtime-dom's shouldSetAsProp then sends SVG props to setAttribute. Both use the element's own namespace rather than getContainerType, so <foreignObject> is correctly treated as SVG. On correctness they are essentially equal. B also passes the namespace in the onClick fast path, which is harmless and consistent. B also null-checks namespaceURI, which avoids A's non-null assertion. The real difference is the tests. A's first test hydrates a plain <svg> in jsdom without making width, height or viewBox read-only. jsdom's SVGSVGElement does not expose these as settable properties, so `key in el` is likely false and setAttribute is used either way. That test would probably pass even without the fix. Only A's foreignObject test, which defines a getter, would actually fail before the fix. B adds a helper that makes the relevant SVG properties getter-only, which mimics how browsers behave. It then tests <svg> and a nested <rect> in dev mode, asserting no 'Failed setting prop' warning. It also covers production mode, <foreignObject> with an HTML child that is still patched as a property, and teleported SVG content. Each of these would fail before the fix and pass after it, and they directly reproduce the issue's symptom. The shared helper (getElementNamespace) is a clean, documented addition next to the existing namespace helpers. B wins on test quality and slightly on craft.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Steps to reproduce

  1. Open the reproduction.
  2. Open the browser devtools Console.
  3. Observe the [Vue warn]: Failed setting prop … error logged during hydration.

What is expected?

During hydration, dynamic props on SVG (and MathML) elements width, height, viewBox, etc. should be patched as attributes (via setAttribute) exactly as they are during normal client-side rendering. Hydration should be silent.

What is actually happening?

Since 3.5.39, dynamic props on SVG elements are patched as DOM properties during hydration, which throws for read-only SVG IDL properties:

[Vue warn]: Failed setting prop "viewBox" on <svg>: value 0 0 24 24 is invalid.
TypeError: Cannot set property viewBox of #<SVGSVGElement> which has only a getter
    at patchDOMProp
    at patchProp
    at hydrateElement
    at hydrateNode
    at hydrateSubTree
    at <App>

Nothing is visually broken but the console is flooded with warnings.

We ran across this issue in a Nuxt app but I believe the issue is coming from Vue core
