[Bug]: Bedrock Realtime hides provider throttles as normal WebSocket closes and lacks disconnect cleanup

Check for existing issues

  • I searched the existing issues and did not find one covering Bedrock Nova Sonic throttling and request-slot cleanup on /v1/realtime.

What happened?

When Bedrock's regional concurrent-session quota is exhausted, LiteLLM acknowledges the throttled Nova Sonic session as ready, emits no Realtime error event, and closes the client WebSocket with code 1000 and an empty reason.

This makes a capacity rejection indistinguishable from a successful, intentional session close. The application cannot identify a retryable throttle, apply backoff, fail over before sending audio, or report an actionable error.

There is also no WebSocket-lifecycle cleanup around the proxy's /v1/realtime route. Pre-call processing acquires proxy rate-limit state, including max_parallel_requests slots, but unlike the SSE streaming path the Realtime endpoint has no shielded finally that calls _arelease_max_parallel_requests_on_disconnect. When a WebSocket is cancelled or a provider failure is suppressed before a normal LiteLLM success/failure callback, the slot can remain until the limiter's one-hour TTL prunes it.

The Bedrock handler currently suppresses forwarding failures and then performs a normal close:

# litellm/llms/bedrock/realtime/handler.py
await asyncio.gather(
    client_to_bedrock_task,
    bedrock_to_client_task,
    return_exceptions=True,
)

...

except Exception as e:
    verbose_proxy_logger.debug(
        "Bedrock to client forwarding ended: %s", e, exc_info=True
    )
finally:
    await client_ws.close()

Because client_ws.close() has no error code or reason, Starlette sends a normal WebSocket close. Because the forwarding exception does not escape, the router cannot classify the attempt as throttled, update deployment health/cooldown state, or attempt an ordered deployment fallback before the session is committed.

Expected behavior:

  1. A Bedrock throttling or service-quota exception before provider readiness is propagated to the router as one logical failure.
  2. If another deployment is configured, LiteLLM attempts that deployment before acknowledging the session as ready.
  3. If no fallback is available, the client receives a Realtime error event containing a stable, retryable throttle classification, followed by an error close such as 1013 (try again later) or 1011, not 1000.
  4. session.updated is emitted only after the provider has accepted the session configuration and is ready to receive audio.
  5. Every WebSocket exit path releases exactly the proxy concurrency slot acquired for that session: normal completion, client disconnect, provider failure, cancellation, and pre-readiness fallback.
  6. Cleanup is idempotent so a logging callback and disconnect cleanup cannot double-decrement the limiter.

User flow

  1. Twenty clients establish Nova Sonic sessions in an AWS account/region whose concurrent-request quota is 20.
  2. A twenty-first client connects to LiteLLM and sends session.update.
  3. LiteLLM sends session.created and session.updated, so the client reasonably begins sending audio.
  4. Bedrock rejects that session because capacity is exhausted.
  5. LiteLLM emits no error event and closes with 1000, reason "".
  6. The client cannot distinguish this from a clean end-of-session and has no reliable throttle signal on which to base retry or failover behavior.

After a fix, step 3 does not occur until upstream readiness is established. A rejected attempt either falls back before audio is accepted or produces an explicit retryable error and non-normal close, and its concurrency slot is released immediately.

Proof the bug occurs

The reproduction used the deployed LiteLLM proxy, a team-scoped virtual key, and real Bedrock Nova 2 Sonic sessions. No mock provider was used.

The observed normal close follows directly from the handler source quoted above. The cleanup concern follows from the proxy lifecycle:

  • common_processing_pre_call_logic() runs before routing and invokes the proxy limiter hooks.
  • The v3 parallel limiter stores each acquired slot and gives it a 3,600-second TTL.
  • LiteLLM already provides ProxyLogging._arelease_max_parallel_requests_on_disconnect() and uses it from shielded SSE cleanup when no logging callback owns the release.
  • The /v1/realtime route has only try/except around routing; it has no corresponding finally cleanup.
  • The Bedrock forwarding coroutines suppress exceptions, so the outer route can return without a failure callback that would otherwise release/account for the request.

  1. Make the Bedrock duplex output raise a throttling exception while applying the first session.update.
  2. Assert session.updated has not been sent.
  3. With a second deployment configured, assert the exception reaches the router and the retained configuration is attempted there.
  4. Without a fallback, assert a Realtime error event and non-normal close are sent with a retryable throttle classification.
  5. Configure a virtual key with max_parallel_requests=1, connect and disconnect normally, and assert another session can immediately acquire the slot.
  6. Repeat step 5 for client cancellation, pre-readiness throttle, provider failure after readiness, and proxy task cancellation.
  7. Assert every acquired slot is released exactly once and no path waits for the 3,600-second TTL.
  8. Assert CloudWatch/provider throttles become LiteLLM deployment failures rather than successful sessions.
