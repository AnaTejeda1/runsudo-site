SSR hydration warning: dynamic props on SVG elements are patched as properties instead of attributes

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches make the same core fix at the root cause. In the hydration props loop, each derives the element's own namespace ('svg' / 'mathml') from `el.namespaceURI` and passes it to `patchProp` instead of `undefined`. That makes runtime-dom's `shouldSetAsProp` take the SVG path and use `setAttribute`. Both correctly use the element's own namespace rather than `getContainerType`, so `<foreignObject>` itself is still treated as SVG.

Correctness differences are small:
- Patch A uses a non-null assertion on `namespaceURI`. This is safe in practice but less defensive.
- Patch B wraps the logic in a named helper that handles null, with a comment explaining why it differs from `getContainerType`.
- Patch B also applies the namespace to the `onClick` fast path, a minor consistency improvement.

Tests:
- Patch A's first SVG test likely does not fail before the fix. jsdom's SVGSVGElement doesn't expose width/height/viewBox as properties, so `key in el` is false and the attribute path is taken anyway.
- Only Patch A's foreignObject test, which installs a getter-only `width`, truly exercises the bug.
- Patch A also toggles `__DEV__` off to sidestep mismatch warnings, which is somewhat hacky.
- Patch B mimics browser behavior by installing getter-only `viewBox` on `<svg>` and `width` on `<foreignObject>`. It uses `data-allow-mismatch` instead of disabling `__DEV__`, and asserts both the attribute values and the absence of the 'Failed setting prop' warning, which is the issue's exact symptom.
- Patch B adds a MathML case too, though that one may not fail pre-fix in jsdom.

Overall, Patch B's tests reproduce the reported failure more faithfully and its code is slightly cleaner, so B is the better patch.

Steps to reproduce

  1. Open the reproduction.
  2. Open the browser devtools Console.
  3. Observe the [Vue warn]: Failed setting prop … error logged during hydration.

What is expected?

During hydration, dynamic props on SVG (and MathML) elements width, height, viewBox, etc. should be patched as attributes (via setAttribute) exactly as they are during normal client-side rendering. Hydration should be silent.

What is actually happening?

Since 3.5.39, dynamic props on SVG elements are patched as DOM properties during hydration, which throws for read-only SVG IDL properties:

[Vue warn]: Failed setting prop "viewBox" on <svg>: value 0 0 24 24 is invalid.
TypeError: Cannot set property viewBox of #<SVGSVGElement> which has only a getter
    at patchDOMProp
    at patchProp
    at hydrateElement
    at hydrateNode
    at hydrateSubTree
    at <App>

Nothing is visually broken but the console is flooded with warnings.

We ran across this issue in a Nuxt app but I believe the issue is coming from Vue core
