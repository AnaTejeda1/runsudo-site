The source change is byte-identical in both patches: the single-line switch from index 0 to index i in the v1 messageAttachment add loop, which is exactly the root cause the issue names. So correctness and scope are tied, and the decision rests on the tests. Both tests exercise the issue's scenario (two items, binary fields 'data' and 'attachment', per-item binaryPropertyName) and both would fail on base because the second item would look up 'data', which is absent, and throw. Both assert getBinaryDataBuffer is called with (0,'data') and (1,'attachment'), which is the direct observable of the fix. The difference is Patch A's extra assertions. A mocks getBinaryDataBuffer to resolve Buffer.from('content') and then asserts the request body contains contentBytes 'c2Vjb25k', the raw base64 of the second item's binary data. Those two choices are mutually inconsistent: the node calls getBinaryDataBuffer precisely to build contentBytes from the buffer (the call would be pointless otherwise), so with that mock the real contentBytes would be the base64 of 'content', not 'c2Vjb25k', and A's test would most likely fail even with the fix applied. A also relies on a pass-through returnJsonArray mock and an exact result shape of [[{success:true},{success:true}]], which couples the test to downstream helpers that are not what the issue is about. That test is internally consistent and has no assertion that contradicts its own mocks. The independent harness runs crashed on all three trees, so they provide no signal either way. Given identical fixes, B wins on test craft: a focused test that is very likely to pass after the fix beats a broader test that probably fails because of a self-contradictory mock.

Bug Description

In packages/nodes-base/nodes/Microsoft/Outlook/v1/MicrosoftOutlookV1.node.ts, resource Message Attachment, operation Add, the per-item loop reads the binary property name with item index 0: this.getNodeParameter('binaryPropertyName', 0). The binary data checks right after it use items[i].

If the field name is an expression that differs per item, every item uses the field name of the first item. messageId and additionalFields in the same loop already use the current index i.

This is the same kind of bug as #44021, but not a duplicate. That issue covers the v2 operation (v2/actions/messageAttachment/add.operation.ts). This one covers the v1 node file, which is not fixed by the v2 PR.

To Reproduce

  1. Use Microsoft Outlook node version 1 (existing workflow). Resource: Message Attachment. Operation: Add.
  2. Two input items. Item 1 has binary data on the field "data". Item 2 has binary data on the field "attachment". Each item has a "field" value in its JSON that names its binary field.
  3. Set "Binary Property" to {{ $json.field }}.
  4. Run the node.
  5. Item 2 looks up "data" instead of "attachment" and fails.

Expected behavior

The binary field name is read with the current item index. Item 2 uses "attachment".

Debug Info

Found by reading the source on master. Verified with a unit test that uses two items with different binary field names. The test fails without the fix. A fix PR will follow.
