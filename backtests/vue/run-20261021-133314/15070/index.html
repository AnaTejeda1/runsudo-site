SSR memory leak after a render error in a dynamic component

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the reported leak and pass all four independent tests, so the decision rests on robustness and completeness. The root cause is that a throw inside the vdom fallback path (renderSlot/withCtx under a dynamic component) leaves `blockStack`/`currentBlock` populated, so every later `createVNode` is pushed into a stale, module-level block array and retained forever.

Patch A adds a `resetBlocks()` helper that clears both `blockStack` and `currentBlock`, and calls it at the two component render boundaries: `renderComponentRoot` (client/render-function path) and the SSR `renderComponentSubTree` ssrRender path. This follows the pre-existing design in `renderComponentRoot`, which already reset `blockStack.length = 0` on error, and it fixes that reset's latent incompleteness (it never cleared `currentBlock`, so vnodes created afterwards still went into the stale block until the next `closeBlock`). Because it resets at the boundary, it is a catch-all for any helper that opens a block and throws, not just the two helpers identified. In SSR no blocks are legitimately open when a component subtree renders (render functions run to completion before the buffer is walked), so a full reset is safe. Tests are thorough: a runtime-core unit test checking `blockStack`/`currentBlock` after a throwing render, an SSR test reproducing the issue and asserting block state directly, and a GC test wired into the `--expose-gc` project.

Patch B unwinds blocks locally in `renderSlot` (with a try/catch plus moving `_d = true` into a finally, which is good craft) and in `withCtx`. This is precise and preserves outer blocks, and its v-if test is a nice addition. However, it only covers the two openers it identified; any other block-opening path that throws during SSR vdom fallback would still leak, and it leaves the incomplete `blockStack.length = 0` reset in `renderComponentRoot` untouched, so `currentBlock` can still be stale there on the client. Its test coverage is a single GC file with no direct assertion on block state.

A addresses the problem at the boundary where errors are already handled, fixes the pre-existing partial reset, and ships more diagnostic tests, so it is the more complete and robust fix. B is a reasonable, targeted alternative but narrower.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Steps to reproduce

  • download the reproduction from stackblitz (won't work there, needs to be run locally)
  • run pnpm i && pnpm leak
  • see the heap size & alive app instances grow with each request after the single failed render

The script renders 500 fresh SSR apps, which all get garbage-collected. Then renders one app whose slot content throws, then renders 500 more identical healthy apps, which will never be garbage collected afterwards.

A dynamic component <component :is> with a <slot /> is needed for this to reproduce.

Card

<script setup>
    defineProps({ tag: { type: String, default: 'div' } })
</script>

<template>
    <component :is="tag" class="card">
        <slot />
    </component>
</template>

app:

<script setup>
    defineProps(['payload'])  // one request renders with `payload: null` → throws
</script>

<template>
    <main>
        <Card>{{ payload.title }}</Card>
    </main>
</template>

What is expected?

A failed renderToString should not affect subsequent renders and all apps rendered after it should get garbage collected.

What is actually happening?

Every app created after the single failed render is kept in memory forever.
