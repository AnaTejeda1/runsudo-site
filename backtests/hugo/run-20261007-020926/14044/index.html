Automatic summary may generate invalid HTML with blockquotes and lists

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the core bug the same way: after the word-count cutoff, they push the summary end forward until the open block elements are closed. Both add unit and integration tests for blockquotes and lists that would fail before the change and pass after it.

The main difference is correctness across markup formats.

**Patch A** tracks every non-void element, including `div` and `section`, for all formats. AsciiDoc output wraps entire sections in `div.sect1`/`div.sectionbody`, and Org output similarly nests whole sections in divs. Patch A would therefore stretch an AsciiDoc or Org summary to the end of the enclosing section, often most of the document. This is a likely regression for non-Markdown content. Patch A also relies on a hand-written HTML tag scanner. It handles comments, quoted attributes and raw-text elements, but it is a large amount of bespoke parsing code that adds maintenance risk. Finally, it rewrites the existing `BenchmarkSummaryFromHTML`, dropping its correctness assertions and replacing `b.Loop()` with `b.N`. That is unrelated churn that weakens existing coverage.

**Patch B** uses `golang.org/x/net/html`'s tokenizer, which is robust and already a Hugo dependency. It only tracks a curated set of block containers matching the elements listed in the issue's spec quote, plus raw-text elements. It deliberately treats `div`/`section` as containers only for Markdown and HTML, which avoids the AsciiDoc/RST/Org whole-section problem. Its tests cover several important cases:
- nested list and blockquote
- a div in Markdown
- a blockquote at the end of the document
- a `</p>` inside a script
- an RST document wrapper, showing that `WrapperStart`/`WrapperEnd` still work correctly

Its integration test also checks `Truncated` and `ContentWithoutSummary`.

Patch B's per-call map and tokenizer allocations are a minor performance cost. Overall, Patch B is the more correct and safer fix with better-targeted tests and no damage to existing tests.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Issue

Using a blockquote that extends past the .Summary cutoff causes the content below {{ .Summary }} to be treated as part of the blockquote until the end of the parent tag. Reproduction repo

<img width="848" height="652" alt="Image" src="https://github.com/user-attachments/assets/212f747c-af3c-4af5-89fe-78fe9dc04ebd" />

Hugo's .Summary may lead to blockquote end tag be below cutoff point

Explanation

In most modern browsers this html code will be parsed and rendered without errors

<!DOCTYPE html>
<html>
<head>
<meta charset="utf-8">
<meta name="viewport" content="width=device-width">
</head>
<body>
  <main>
    <blockquote>
      <p>1</p>
  </main>
</body>
</html>

Leading to shown in browser as a source

<!DOCTYPE html>
<html>
<head>
<meta charset="utf-8">
<meta name="viewport" content="width=device-width">
</head>
<body>
  <main>
    <blockquote>
      <p>1</p>
      <!-- This blockquote end tag was automatically inserted -->
    </blockquote>
  </main>
</body>
</html>

This is due to these parsing rules

An end tag whose tag name is one of: "address", "article", "aside", "blockquote", "button", "center", "details", "dialog", "dir", "div", "dl", "fieldset", "figcaption", "figure", "footer", "header", "hgroup", "listing", "main", "menu", "nav", "ol", "pre", "search", "section", "select", "summary", "ul"

If the stack of open elements does not have an element in scope that is an HTML element with the same tag name as that of the token, then this is a parse error; ignore the token.

Otherwise, run these steps:

Generate implied end tags.

If the current node is not an HTML element with the same tag name as that of the token, then this is a parse error.

Pop elements from the stack of open elements until an HTML element with the same tag name as the token has been popped from the stack.
