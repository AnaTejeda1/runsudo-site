SSR hydration warning: dynamic props on SVG elements are patched as properties instead of attributes

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the root cause the same way. During hydration they derive the element's namespace from `el.namespaceURI` and pass it to `patchProp` instead of `undefined`. `patchProp` then treats SVG and MathML props as attributes, which matches client-side mount behaviour. Both correctly use the element's own namespace, so `<foreignObject>` props are still patched as SVG.

Correctness is effectively equal. B is slightly more defensive: it null-checks `namespaceURI` rather than using a `!` assertion. B also passes the namespace on the `onClick`-only path, which is consistent and harmless.

Tests are the main difference.
- A's first test (plain svg with width, height and viewBox under jsdom) likely passes even without the fix. jsdom does not implement these as getter-only IDL properties, so `patchProp` would fall back to `setAttribute` either way.
- A's second test is meaningful. It defines a getter-only `width` on a `foreignObject` instance with `__DEV__` off, so the property-set path would fail silently and leave the attribute unchanged.
- B's test emulates browser behaviour directly by installing getter-only `viewBox` and `x` on `SVGElement.prototype`, covering both an `<svg>` and a nested `<foreignObject>`. It asserts the attributes are updated and that no 'Failed setting prop' warning appears, which reproduces the exact warning from the issue. It would fail before the fix, cleans up the prototype afterwards, and accounts for the expected mismatch warnings.

For craft, B extracts a small, well-commented `getElementNamespace` helper that explains how it differs from `getContainerType`. A uses an inline nested ternary with non-null assertions.

Overall, B's fix is equivalent but its regression test is stronger and its code is slightly cleaner.

Steps to reproduce

  1. Open the reproduction.
  2. Open the browser devtools Console.
  3. Observe the [Vue warn]: Failed setting prop … error logged during hydration.

What is expected?

During hydration, dynamic props on SVG (and MathML) elements width, height, viewBox, etc. should be patched as attributes (via setAttribute) exactly as they are during normal client-side rendering. Hydration should be silent.

What is actually happening?

Since 3.5.39, dynamic props on SVG elements are patched as DOM properties during hydration, which throws for read-only SVG IDL properties:

[Vue warn]: Failed setting prop "viewBox" on <svg>: value 0 0 24 24 is invalid.
TypeError: Cannot set property viewBox of #<SVGSVGElement> which has only a getter
    at patchDOMProp
    at patchProp
    at hydrateElement
    at hydrateNode
    at hydrateSubTree
    at <App>

Nothing is visually broken but the console is flooded with warnings.

We ran across this issue in a Nuxt app but I believe the issue is coming from Vue core
