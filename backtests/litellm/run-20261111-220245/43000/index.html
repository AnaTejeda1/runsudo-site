[Bug]: encrypted_content_affinity has no fallback when the pinned deployment is unavailable or removed, permanently bricking multi-turn Responses API conversations

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the reported scenario: with cooldowns disabled and no (api_base, api_key) peer, a follow-up pinned to an excluded or deleted origin now strips the undecryptable reasoning and dispatches to a healthy sibling. The independent tests confirm this equally (3 base failures flip to PASS under both; the rpm=0 test fails identically on all three trees and does not discriminate).

The difference is in how much they change and how well-scoped it is. Patch B keeps the existing contract exactly where it still makes sense: if the origin is a same-group member in an *active router cooldown*, it still fails fast with a 429 + Retry-After or 503 (a bounded, client-actionable window, which the issue itself lists as an acceptable outcome); in every other exclusion case (cooldowns disabled, rpm/tpm, admin block, removed id) it degrades and strips. The change is a small, well-commented reordering inside async_filter_deployments plus a simplification of _unavailable_origin_error, with a useful warning log added to the cooldown-read failure path. Its tests build a real litellm.Router with the issue's exact PrivateLink topology (shared key, distinct api_base per deployment, disable_cooldowns, encrypted_content_affinity enabled), run a real first turn, then exercise the blocked-origin case, repeated replays after delete_deployment, and the Anthropic bridge twin, asserting the upstream input was stripped. Existing fail-fast tests are adjusted to add an active cooldown rather than deleted.

Patch A removes the cooldown-aware fail-fast entirely (deleting _unavailable_origin_error, _get_origin_cooldown, the 429/Retry-After behavior and the routed-group membership discriminator), so even a transient same-group cooldown now silently drops the reasoning instead of giving the client a short backoff signal. That is a defensible design but a broader behavior change than the issue requires, and it removes functionality the surrounding code deliberately built. It also edits router.py to make the check runtime-toggleable via /config/update and modifies integration test support, apparently to make its integration tests work; this touches the callback-ordering logic (_move_before_deployment_affinity) via a generic toggle path and is unrelated to the issue's ask, adding risk and obscuring the core fix. Its unit tests are mostly rewrites of the deleted fail-fast tests to assert the opposite, plus one good regression test; the integration tests require a live gateway harness.

On correctness both resolve the issue; on scope and craft Patch B is the tighter, lower-risk fix with stronger end-to-end tests of the issue's own configuration, so B wins.

(Related but distinct: #41792/#41793 cover intentional model switching between deployments with shared credentials rejecting cross-model reasoning; #40364 covers the Chat Completions→Responses bridge never being pinned by affinity at all. This issue is about native /v1/responses requests that are correctly pinned by encrypted_content_affinity, but have no fallback or recovery path when the pinned deployment becomes transiently unavailable or is permanently removed.)

What happened?

EncryptedContentAffinityCheck.async_filter_deployments (litellm/router_utils/pre_call_checks/encrypted_content_affinity_check.py) pins a multi-turn /v1/responses request to the exact deployment (model_id) that produced its encrypted_content, and looks for a same-(api_base, api_key) peer if that exact deployment isn't in healthy_deployments. When a model group's deployments are architected with distinct api_base values per deployment (multi-region PrivateLink, multi-region Azure/Bedrock, or any topology where load-balancing exists specifically because each backend is a separate resource/region), no deployment can ever have a peer under this key — (api_base, api_key) uniquely identifies exactly one deployment. The moment the pinned deployment is excluded from healthy_deployments for any reason (rate-limit, transient provider-side issue, capacity throttling), the check has structurally zero fallback candidates and raises a hard ServiceUnavailableError (503), even though disable_cooldowns: true is set and other reasoning-capable deployments in the exact same model group are fully healthy and could serve the request (minus this one pinned turn).

A second, more severe variant of the same gap: if the model_id the response was pinned to is removed or reconfigured (e.g. a runtime /model/new + /model/{id}/update/delete registration, common for day-0 model support added outside values.yaml), router.get_deployment(model_id=...) returns None. The check then returns a BadRequestError telling the client to "re-issue the request without the stale encrypted_content items" — but OpenAI-Responses-API clients (Codex, and any client implementing previous_response_id/reasoning replay) have no such recovery path; they keep echoing the same encrypted_content/previous_response_id on every subsequent turn. The conversation becomes permanently unrecoverable: every future request in that session hits the identical dead end, with no way for the proxy or client to break the cycle short of the user starting an entirely new conversation.

Neither failure path offers:

  • a retry/backoff window before hard-failing (the originating deployment may recover in seconds — cooldowns are explicitly disabled in our config, so this is not a case the router's own health system is meant to guard against),
  • a degraded fallback (serving the turn from a non-peer deployment and accepting a possible provider-side invalid_encrypted_content rejection on that one call — which is the behavior that existed before encrypted_content_affinity was enabled at all), or
  • any mechanism to detect/react to a permanently-gone model_id other than surfacing an error the calling client cannot act on.

The actual gap

_find_deployments_on_same_encryption_boundary (lines 178-202) defines "peer" strictly as an exact (api_base, api_key) match:

@staticmethod
def _encryption_boundary_key(litellm_params) -> tuple | None:
    api_base = getter("api_base")
    api_key = getter("api_key")
    if not api_base or not api_key:
        return None
    return (api_base, api_key)

For any model group where deployments are deliberately split across distinct api_base values (which is the entire point of multi-region/multi-provider load balancing), this key guarantees boundary_matches == [] on every lookup. Combined with _unavailable_origin_error (lines 288-341) raising unconditionally when boundary_matches is empty, the check degrades to: one specific deployment must be healthy, or every request in the conversation fails, for the lifetime of the conversation, with no escape hatch.

Blast radius / impact — critical

  • Any model group with per-deployment credentials/endpoints and reasoning/Responses API usage is exposed — not a corner case. This includes standard multi-region PrivateLink and multi-region Azure OpenAI topologies, which are common production configurations specifically because they load-balance across otherwise-interchangeable backends.
  • Impact scales with the proxy's highest-traffic reasoning models, since the affinity pin activates on every multi-turn conversation carrying encrypted reasoning content — in our production environment we measured error rates as high as 52-63% of all traffic to two newly-onboarded high-volume model groups during a ~30 minute window when one PrivateLink deployment became transiently constrained, and a sustained 30-40% fault rate on one model group for over an hour afterward, entirely attributable to this gap (confirmed via full server-side stack traces terminating in encrypted_content_affinity_check.py:281).
  • Runtime/DB-registered model deployments (/model/new, common for day-0 model launch support before a model is added to git-tracked config) compound the risk: their model_id is mutable at any time by any admin-key holder, with no git review or deploy gate, and per LiteLLM's own architecture "the DB overrides file-based config" once registered. Any long-running Responses API conversation pinned to such a model_id is silently carrying an undocumented hard dependency that the exact model_id is never deleted or retargeted for the life of the conversation — with no visibility into which live conversations hold this dependency.
  • User-facing severity: once a conversation hits either failure mode, it does not self-heal. Every subsequent action in that conversation (including from long-lived agentic clients like Codex, which keep local multi-turn state and don't know to discard it) returns a 503/400 indefinitely, effectively bricking the session. Users have no client-side recovery action other than abandoning the conversation entirely and starting a new one — which is often undiscoverable to the end user, who just sees intermittent-looking failures with no clear cause.
  • We believe this is broadly applicable to any LiteLLM proxy deployment using encrypted_content_affinity with more than one api_base per model group (i.e., the exact scenario the feature is meant to support), making this a systemic gap in the feature's failure-mode handling, not a configuration issue on our end.

User Flow

Before a (hypothetical) fix: a developer/agent client (e.g. Codex) has a multi-turn Responses API conversation pinned to a deployment behind a transient capacity constraint, or whose model_id was later removed.

  1. Client sends POST /v1/responses with store: false, include: ["reasoning.encrypted_content"], against a model group with 2+ deployments each on a distinct api_base (e.g. 3 PrivateLink unified-N hosts sharing one api_key). Response includes an encrypted_content item wrapped/encoded with the originating deployment's model_id.
  2. Client sends a follow-up turn replaying that item (previous_response_id or the raw encrypted_content/item id, exactly as Codex does). The affinity check decodes the model_id and looks it up in healthy_deployments.

3a. Transient case: the originating deployment happens to be excluded from healthy_deployments at that instant (rate-limited, momentarily throttled — note disable_cooldowns: true means this is not the router's own cooldown mechanism). No peer exists (distinct api_base per deployment). Client receives 503 ServiceUnavailableError.
3b. Permanent case: the originating model_id was deleted/retargeted (e.g. via /model/{model_id}/update or a fresh /model/new + alias swap). router.get_deployment(model_id=...) returns None. Client receives 400 BadRequestError telling it to "re-issue the request without the stale encrypted_content items."

  1. Client (Codex or any client maintaining local conversation state) retries the same conversation state on the next user action, since it has no mechanism to know it must discard the encrypted_content and start fresh. Same failure recurs. Every future action in this conversation fails identically, forever.

After a (hypothetical) fix: the router either serves the turn from a non-peer deployment when the originating one is transiently unavailable (matching pre-affinity-feature behavior, i.e. worst case an occasional single-turn invalid_encrypted_content from the provider rather than a proxy-level hard failure), and/or a short bounded retry/backoff window before failing so a millisecond-scale transient exclusion doesn't escalate to a hard error, and/or a documented, client-actionable recovery signal for the permanent case that doesn't require the conversation to be manually abandoned.
