Test with infinite recursion error slows down pytest even if the exception is not shown to the user (because it’s marked as xfail).

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

The issue identifies the root cause explicitly: `TestReport.from_item_and_call()` runs `repr_failure()` for an xfail test whose traceback is never shown. Patch A fixes exactly that. A new `pytest_runtest_makereport` implementation in the skipping plugin detects that a failure will be reported as an expected failure (honouring `--runxfail`, `--xfail-tb`, `raises=` matching, imperative `pytest.xfail`, and the cheap no-pytrace `fail.Exception` case) and builds the report with a cheap `(path, lineno, message)` longrepr instead of walking the traceback. That tuple form mirrors what pytest already uses for skipped reports, so it is consistent with existing conventions. The xfail-matching logic is refactored into `_xfail_raises_matches` and reused by the existing wrapper, avoiding duplicated semantics. Its tests are strong: a conftest that makes any failure formatting raise, so every scenario (RecursionError, mark with/without raises, imperative xfail in setup/call/teardown, unittest expectedFailure, subtests) would fail before and pass after, plus a test that unexpected failures, `--xfail-tb` and `--runxfail` still format. Independent tests confirm: all three pass with A, with timing equal to the short-traceback case.

Patch B never addresses the root cause. It still formats the traceback for xfail tests; it just makes formatting cheaper by memoizing statement line numbers on the AST node and by truncating undetectable recursions to the first and last 10 frames. These are reasonable general optimizations, and the second one changes user-visible output for ordinary (non-xfail) RecursionError failures, which is beyond the issue's ask and carries some risk of hiding relevant frames. The independent tests show B cuts the time from roughly 0.21s to 0.04s but still leaves the xfail RecursionError report about 25x slower than a short-traceback xfail, so all three tests still fail. B's tests are fine for what they cover but verify the optimizations, not the reported xfail slowdown.

A resolves the issue at its root with thorough tests and minimal scope; B masks part of the symptom and adds an unrelated output change. A wins clearly.

The issue

View on GitHub

In the following code, calling f() fails with a RecursionError. Because test_recursion is marked as xfail, the test suite still passes.

import pytest

def f(x):
    f(x + 1)

@pytest.mark.xfail
def test_recursion():
    f(0)

Running with --durations 10 -vv gives the following output:

test_recursion.py::test_recursion XFAIL                                 [100%]

============================ slowest 10 durations =============================
0.00s call     test_recursion.py::test_recursion
0.00s teardown test_recursion.py::test_recursion
0.00s setup    test_recursion.py::test_recursion
============================= 1 xfailed in 0.41s ==============================

When commenting out the body of test_recursion():

test_recursion.py::test_recursion XPASS                                 [100%]

============================ slowest 10 durations =============================
0.00s setup    test_recursion.py::test_recursion
0.00s call     test_recursion.py::test_recursion
0.00s teardown test_recursion.py::test_recursion
============================= 1 xpassed in 0.01s ==============================

When putting the body of test_recursion() in an exception handler that suppresses the exception:

test_recursion.py::test_recursion XPASS                                 [100%]

============================ slowest 10 durations =============================
0.00s call     test_recursion.py::test_recursion
0.00s setup    test_recursion.py::test_recursion
0.00s teardown test_recursion.py::test_recursion
============================= 1 xpassed in 0.01s ==============================

Pytest takes much longer when the test function raises the exception, even though the test function itself completes quickly in all cases and the exception is not shown to the user if xfailing.

One issue is that TestReport.from_item_and_call() calls Function.repr_failure() (which is slow because of the long traceback) although the error is never shown to the user.

Another issue is that the durations don’t include the part of pytest where the majority of the time is spent. When trying to find why my test suite was slow, --durations didn’t help. It’s probably meant to help finding slow tests instead of performance problems in pytest. Still, I think it could be worthwhile to include timings for some of the code outside of the actual test (like for example generating the test report), as it’s not reasonable to expect users to profile pytest when running into a slowdown like this.
