Decimal JSON schema pattern rejects pydantic's own scientific notation serialization output (v2.12 regression)

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Patch A fixes the root cause the issue names. It adds an optional `[eE][+-]?\d+` exponent to every generated Decimal pattern. It also tightens the leading negative lookahead so strings like 'e5' or '.e5' are still rejected. In the constrained branches it adds an exponent alternative that bounds only the mantissa digits, and a comment documents that the exponent-dependent digit count cannot be expressed in a regex. This follows the first fix the issue suggests, keeps the existing feature (the patterns introduced in 2.12), and stays close to the surrounding code style. Its tests are targeted and meaningful, and they would fail on the old pattern: they serialize real values (1E-7, 0E-10, -1.23E+10, constrained cases) via `model_dump_json`/`dump_json`, check the output with `re.fullmatch` against both the validation and serialization schemas, round-trip the value, and confirm malformed exponent strings are rejected. Patch B instead drops the pattern from the default schema entirely. That makes the reported symptom disappear, but it does so by reverting the feature for everyone, which is a significant behavior change. It moves the logic into new public hooks (`get_decimal_pattern`, `build_decimal_pattern`) backed by a large, intricate regex builder that handles serialization-exact patterns, exponent ranges and inf/nan. Most of that machinery is opt-in, so the default-path fix is effectively 'remove the pattern'. The change adds considerable code and risk, and it includes unrelated churn (moving `_HashableJsonValue`). Its docs are confusing: two contradictory 'version-changed' blocks, one saying the pattern is included and one saying it no longer is. B's tests are extensive, but they mostly exercise the new opt-in builder rather than the default behavior the issue reports. On correctness and scope, A resolves the issue directly with low risk, while B is a broad redesign that masks the issue by default and adds complexity.

Description

model_json_schema(mode="serialization") pattern for Decimal breaks on scientific notation

The serialization schema for Decimal fields generates a regex that rejects values that model_dump_json() itself produces.

Specifically: pydantic-core's serializer calls str() on Decimal objects, which outputs scientific notation for small/large values. E.g. Decimal('0.0000001') becomes "1E-7". But the pattern added in #11987 (^(?!^[-+.]*$)[+-]?0*\d*\.?\d*$) has no [eE] component, so it'll never match those strings.

As a result, any downstream consumer validating model_dump_json() output against model_json_schema(), such as OpenAPI validators and codegen + validation tools like Orval + Zod, will intermittently reject perfectly valid serialized values. Intermittent because only certain Decimal values trigger scientific notation.

v2.11:

{"anyOf": [{"type": "string"}, {"type": "null"}]}

v2.12:

{"anyOf": [{"pattern": "^(?!^[-+.]*$)[+-]?0*\\d*\\.?\\d*$", "type": "string"}, {"type": "null"}]}

Two possible fixes:

  • Append (?:[eE][+-]?\d+)? to the pattern in serialization mode
  • Normalize Decimal to fixed-point during serialization before it ever hits the schema

Example Code

import json
import re
from decimal import Decimal
from pydantic import BaseModel

class MyModel(BaseModel):
    value: Decimal | None

schema = MyModel.model_json_schema(mode="serialization")
pattern = next(
    v for v in schema["properties"]["value"]["anyOf"] if v.get("type") == "string"
)["pattern"]
regex = re.compile(pattern)

# pydantic serializes this as "1E-7" which fails its own schema's pattern
m = MyModel(value=Decimal("0.0000001"))
serialized = json.loads(m.model_dump_json())["value"]

print(f"Pattern: {pattern}")
print(f"Serialized: {serialized!r}")
print(f"Matches: {bool(regex.match(serialized))}")
# Pattern: ^(?!^[-+.]*$)[+-]?0*\d*\.?\d*$
# Serialized: '1E-7'
# Matches: False
