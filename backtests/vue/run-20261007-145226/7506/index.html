suspense.resolve() is called without a pending branch.

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

The issue happens when a pending branch's async setup navigates back to the active branch. That forces a resolve and clears `pendingBranch`. When the abandoned async dep later settles, `registerDep` still decrements `deps` and calls `suspense.resolve()` with no pending branch, which triggers the warning. Patch A fixes exactly this. It adds a `suspense.pendingBranch` guard before decrementing and resolving in `registerDep`, and it resets `suspense.deps = 0` on resolve so stale deps don't gate the next pending branch. Its tests reproduce the issue's scenario (B's async setup sets the page back to A), check that no errors occur and that `onResolve` counts are correct, and confirm a later pending branch (D) still waits for its own dep. A second test covers a nested suspensible suspense in the same toggle-back case. Patch B instead wraps the same-root-type pending patch in `deps++`/`deps--` to stop a nested suspensible suspense from resolving the parent mid-patch. That is a different edge case. It does not touch the toggle-back path or the late-settling dep callback, so the reported warning would still appear. Its tests target nested-suspensible timing, not navigation during a pending component's setup. Patch A is correct for the reported problem and well tested; Patch B misses the root cause.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
