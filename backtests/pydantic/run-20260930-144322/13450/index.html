Experimental pipeline: Interval bounds of zero are silently dropped

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

The two source changes are identical. Both replace the four truthiness checks in the Interval branch of _apply_constraint with `is not None`. This fixes the root cause for all four bounds (ge/gt/le/lt), so the patches tie on correctness and scope. The difference is in the tests. The existing parametrized cases `Interval(ge=0, le=10)` with invalid [11] and `Interval(gt=0.0, lt=10.0)` with invalid [10.0] never checked the zero bound, which is why the bug went unnoticed. Patch B strengthens those rows directly: it adds -5 to the int case, and 0.0 and -5.0 to the float case. It then adds zero-bound cases for gt, le and lt. All of these fail before the fix and pass after, and they cover both int and float zero bounds, including the exact boundary value 0.0 for gt. Patch A leaves the weak existing rows as they are. It appends a new `Interval(ge=0, le=10)` row that near-duplicates an existing one, plus int-only rows for gt, le and lt. Those also fail before the fix, so A's tests are valid, but the suite ends up with a redundant row and still-blind originals, and it has no float zero-bound coverage. B's test changes are more thorough and integrate more cleanly with the existing parametrization, which gives it a modest edge.

Description

In pydantic/experimental/pipeline.py, _apply_constraint() handles annotated_types.Interval by delegating to the individual comparison constraints, but it tests each bound for truthiness rather than is not None:

elif isinstance(constraint, annotated_types.Interval):
    if constraint.ge:
        s = _apply_constraint(s, annotated_types.Ge(constraint.ge))
    if constraint.gt:
        s = _apply_constraint(s, annotated_types.Gt(constraint.gt))
    if constraint.le:
        s = _apply_constraint(s, annotated_types.Le(constraint.le))
    if constraint.lt:
        s = _apply_constraint(s, annotated_types.Lt(constraint.lt))

Since 0 is falsy, a bound of exactly zero is skipped and the constraint is silently dropped - there is no error, validation simply accepts out-of-range values. Interval(ge=0, le=10) happily accepts -5.

All four bounds are affected. Observed on 2.12.5:

constraintinputexpectedactual
Interval(ge=0, le=10)-5ValidationErroraccepted
Interval(ge=0, le=10)20ValidationErrorValidationError (le=10 works)
Interval(gt=0)-5ValidationErroraccepted
Interval(gt=0)0ValidationErroraccepted
Interval(le=0)5ValidationErroraccepted
Interval(lt=0)5ValidationErroraccepted
Interval(ge=1, le=10)-5ValidationErrorValidationError (control: non-zero bound is fine)

The non-zero control confirms the trigger is specifically the zero bound, not Interval in general. Zero is a very common lower bound, so this silently weakens validation in ordinary usage.

The fix looks like changing the four checks to if constraint.ge is not None: (and likewise for gt/le/lt).

This is related to, but distinct from, #13446 - that one is about Gt being dropped on a numeric type mismatch, whereas this is the Interval branch dropping zero bounds regardless of type.

Happy to open a PR if that would help.

Example Code

from typing import Annotated

import annotated_types
from pydantic import TypeAdapter
from pydantic.experimental.pipeline import validate_as

ta = TypeAdapter(Annotated[int, validate_as(int).constrain(annotated_types.Interval(ge=0, le=10))])

print(ta.validate_python(-5))  # -> -5   (expected: ValidationError, ge=0 is violated)
ta.validate_python(20)         # -> ValidationError (le=10 is enforced correctly)

# A non-zero lower bound behaves correctly:
ta2 = TypeAdapter(Annotated[int, validate_as(int).constrain(annotated_types.Interval(ge=1, le=10))])
ta2.validate_python(-5)        # -> ValidationError (correct)

What the agent reported

I fixed the bug: Interval bounds of zero are no longer silently dropped. The full tests/test_pipeline.py suite passes (70 tests).

What was wrong: In pydantic/experimental/pipeline.py:615-623, the annotated_types.Interval branch of _apply_constraint checked each bound with a plain if constraint.ge: (and the same for gt, le, lt). Zero counts as false in Python, so a bound of 0 was skipped and its constraint was never applied.

What I changed:

  • Fix: the four checks now use is not None. The Len branch in the same file already works this way. Nothing else in the file changed.
  • Tests: I added four cases to the existing test_interval_constraints list in tests/test_pipeline.py and left the five existing cases as they were.

Test evidence:

  • Before the fix, ./bt-test tests/test_pipeline.py -k interval gave 4 failed, 5 passed. All four new cases failed with DID NOT RAISE ValueError, which is the reported bug.
  • After the fix, ./bt-test tests/test_pipeline.py gave 70 passed.
  • git diff --stat shows only these two files changed (8 insertions, 4 deletions).
  • The reviewer subagent found no problems.
