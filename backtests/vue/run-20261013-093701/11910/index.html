Transition should sniff for teleport in custom components

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the core bug: a component whose root is a Teleport now gets its transition hooks forwarded to the teleported element instead of the Teleport vnode. Both include e2e tests showing the enter and leave classes applied to the teleported node.

Patch A redirects the hooks in two places (`renderComponentRoot` and the component branch of `setTransitionHooks`) using the exported `getInnerChild`. This works for the basic case. However, it blindly moves the hooks onto whatever non-comment child it finds. If the Teleport content is a Fragment or other non-transitionable node, the hooks land on a node that never calls `afterLeave`. That can stall `mode: "out-in"`. Its unit tests are fairly thin: a KeepAlive case, an empty-Teleport case, and a hook-update case. None of them directly checks enter/leave callbacks on teleported content.

Patch B makes Teleport transparent inside `setTransitionHooks` itself, so every path benefits, including HOC nesting and the update path. It forwards the hooks to the content only when that content can carry them (an element, a component, or a comment placeholder for v-if switches). Otherwise it keeps the hooks on the Teleport, which preserves `afterLeave` for out-in. It also guards against unnormalized children. The dev warning is made Teleport-aware, so it still fires for multi-root or non-element content but not for valid single-element content.

Patch B's tests are substantially stronger. They cover full leave/enter cycles with element assertions for a direct Teleport root, an HOC wrapper, component content, and out-in mode. They also cover warning behavior, the fallback of keeping hooks on the Teleport, and unnormalized children.

Patch B is more robust at the edges and better tested, with no added risk to the core fix.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

This is a follow up from

  • #5836

My Intention in #5836 was, that a user should be able to do this:

<Transition>
  <CustomComp />
</Transition>

<!-- Custom Comp -->
<Teleport>
  <div></div>
</Teleport>

However, the fix for #5836 only allows:

<Transition>
  <Teleport>
    <div></div>
  </Teleport>
</Transition>

For me as a user those 2 should feel equivalent.
The way it is now is not really useful. If you are not gonna use a custom component inside transition, you could just easily swap teleport and transition around (which already worked before the fix):

<teleport>
  <transition>
    <div></div>
  </transition>
</teleport>

But the whole point of #5836 was to allow to transition any component that teleports internally.
And since nesting a custom component into a transition works already, teleport should just be transparent in this case

Usecase:

  • modals <transition><Modal /></transition>
  • popovers
  • ...
