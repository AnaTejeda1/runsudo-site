Both patches make identical root-cause Rust fixes — adding serialization_exclude_if to SerField traversal, class to EnumSerializer traversal, and lookup to every EnumValidator<T> traversal — exactly the missing PyGcTraverse edges the issue identifies. On scope (criterion 3) and craft (criterion 4) A is clearly cleaner — minimal, focused, no risky drive-by edits — while matching B on correctness and tests. Hence A is the better fix.

Initial Checks

  • I confirm that I'm using Pydantic V2

Description

Transient BaseModel classes are not collected when either:

  • A model field references an Enum whose class defines a Python method.
  • A model field uses Field(exclude_if=<Python callable>).

After the defining module is removed from sys.modules and every ordinary strong reference is dropped, weak references to the model and enum classes remain alive after repeated full gc.collect() calls. Repeating this construction in disposable module namespaces causes linear memory growth.

Controls using an enum without methods or a field without exclude_if are collected normally.

I encountered this in combination with a Temporal workflow sandbox. With a large interconnected model graph and high volume Temporal workflows this can result in multi-GiB process growth relatively quickly.

The likely cause is missing PyGcTraverse edges for Python objects held by pydantic-core:

  • SerField owns serialization_exclude_if, but traverses only serializer: https://github.com/pydantic/pydantic/blob/c67a1397327c6abc1a2e2e921af01aebbbeedf1c/pydantic-core/src/serializers/fields.rs#L26-L38
  • EnumSerializer owns class, but traverses only serializer: https://github.com/pydantic/pydantic/blob/c67a1397327c6abc1a2e2e921af01aebbbeedf1c/pydantic-core/src/serializers/type_serializers/enum_.rs
  • Each EnumValidator<T> owns lookup, but traverses only class and missing: https://github.com/pydantic/pydantic/blob/c67a1397327c6abc1a2e2e921af01aebbbeedf1c/pydantic-core/src/validators/enum_.rs

Traversing py_schema does not compensate for another unreported direct reference: CPython’s collector accounts for every actual strong edge individually.

I tested a temporary build from Pydantic main at c67a1397327c6abc1a2e2e921af01aebbbeedf1c. Adding only these traversal edges made all objects in the reproduction collectible:

  • Add serialization_exclude_if to SerField traversal.
  • Add class to EnumSerializer traversal.
  • Add lookup to every EnumValidator<T> traversal.

For the enum case, changing only the serializer or only the validator was insufficient; both missing edges were required.

This appears related to earlier missing-traversal fixes such as:

  • https://github.com/pydantic/pydantic/issues/5136
  • https://github.com/pydantic/pydantic-core/pull/787
  • https://github.com/pydantic/pydantic-core/pull/1100

I would be happy to submit a focused patch.

import gc
import sys
import types
import weakref

def transient_module(name, source, class_names):
    module = types.ModuleType(name)
    sys.modules[name] = module
    exec(compile(source, f"<{name}>", "exec"), module.__dict__)
    refs = tuple(
        weakref.ref(module.__dict__[class_name])
        for class_name in class_names

    del sys.modules[name]
    del module

Summary

What was wrong

Transient BaseModel classes leaked (survived GC) when a field referenced an Enum whose class defines a Python method, or used Field(exclude_if=<callable>). The root cause was missing PyGcTraverse edges in pydantic-core: Rust structs held strong references to Python objects but didn't report them to CPython's cyclic collector, so reference cycles running through those objects were never collectible.

What I changed

Three minimal Rust edits, exactly as the report prescribed (adding fields to the impl_py_gc_traverse! macro invocations):

  • pydantic-core/src/serializers/fields.rs:38 — added serialization_exclude_if to SerField traversal.
  • pydantic-core/src/serializers/type_serializers/enum_.rs:51 — added class to EnumSerializer traversal.
  • pydantic-core/src/validators/enum_.rs — added lookup to all four EnumValidator<T> traversal impls (Plain/Int/Str/Float, lines 171/203/219/235).

Added a regression test tests/test_gc.py reproducing the report's exact scenario (transient modules, weakrefs, retry-based assert_gc) with three tests covering the enum-with-method leak, the exclude_if leak, and a control (enum without methods / field without exclude_if).

Test evidence (each ./bt-test run rebuilt/used the mounted editable .so; I recompiled the extension in the container with maturin develop after the fix since the gate runs --no-sync)

  • Before fix (stale binary reflecting unmodified source): test_gc_enum_with_method and test_gc_field_exclude_if failed ("Timeout waiting for GC"); test_gc_controls passed — reproducing the report.
  • After fix (rebuilt binary): all 3 tests in tests/test_gc.py passed.
  • Blast radius / adjacent tests: pydantic-core/tests/test_garbage_collection.py, pydantic-core/tests/validators/test_enums.py, pydantic-core/tests/serializers/test_enum.py → 30 passed, 1 skipped; top-level tests/types/test_enum.py → 19 passed. Adding traversal edges only exposes references to the collector and cannot change validation/serialization behavior.

Requirements disposition

  1. Enum-with-method field leak fixed → implemented (class on EnumSerializer + lookup on EnumValidator), test test_gc_enum_with_method fails before / passes after.
  2. Field(exclude_if=...) leak fixed → implemented (serialization_exclude_if on SerField), test test_gc_field_exclude_if fails before / passes after.
  3. Report's note that both enum edges (serializer class + validator lookup) are required → honored: all four validator impls and the serializer were patched together.
  4. Controls (enum without methods / field without exclude_if) collect normally → verified by test_gc_controls (passes before and after).

All changes are left uncommitted in the working tree.
