Make .Render take additional data

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the core ask the same way. Each changes `Render` to take `args ...any`, uses the optional extra argument as the template's data context in place of the Page, still resolves the template through the page, and updates every interface implementer (LazyContentProvider, nopPage, testPage). Both also report errors for zero arguments, more than two arguments, and a name that is not a string.

Patch B goes further in three ways:

- **Argument order.** It also accepts the issue's literal `PAGE.Render [DATA] NAME` order. It swaps the arguments only when the first is not a string kind and the second is. Checking the kind rather than the type keeps a `template.HTML` name from being swapped. This adds a small amount of heuristic magic, but the rule is narrow and deterministic.
- **Validation.** It rejects an empty layout name.
- **Docs.** It updates the documentation page.

Patch B's tests are also substantially stronger. They cover:

- NAME DATA and DATA NAME orders;
- the piped form (`dict ... | .Render "li"`);
- a string as data;
- no data;
- an HTML-typed name;
- that template lookup still follows the page's content type (`s1/li.html` for a page in `s1`);
- the too-many-arguments error.

Patch A's tests cover only the basic dict-context case and two error messages. Its implementation is simpler and arguably cleaner. However, it does not support the issue's suggested DATA-NAME syntax, and its tests are much thinner.

On balance, Patch B covers the issue more completely and verifies its behavior more thoroughly, with acceptable added complexity.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

PAGE.Render NAME

This has been discussed before.

  • The contract has always been that the templates that .Renders gets the data context as e.g. page.html, a page.Page.
  • We can only pass 1 argument to Go's template renderer, which I guess is the blocking reason for not having done this sooner.

So, if we want to do:

PAGE.Render [DATA] NAME

I'm guessing we have 2 top-level options:

  • We say that if DATA is set, we use that as the context passed to the templates,. else PAGE.
  • We somehow (e.g. by embeding it in a { DataAdditionalContext, Page } struct or putting it into the current context.Context) wrap the Page so you can do both .RelPermalink and .DataAdditionalContext (naming of the latter is just picked out of a hat without thinking too hard.
