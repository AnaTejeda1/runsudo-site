Throw an error on createVNode with using innerHTML and children at the same time

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Patch A fixes the behavior the issue asks for, and Patch B does not.

**Patch A.** The issue wants an element whose `innerHTML` is toggled between a value and `undefined` to fall back to its children. Patch A changes `patchElement` in two ways:
- The unset check now uses `!= null` instead of truthiness, so going from an empty-string `innerHTML` or `textContent` to `undefined` is handled.
- When the prop is removed and the new children are text, it restores that text immediately. Without this, the text-children diff sees the old and new text as equal, skips the update, and leaves the element empty.

This is the real root cause of the dynamic scenario the user describes ("change innerHTML of props and children dynamic at same time"). Its tests are behavioral and would fail before the change. Examples include `innerHTML: '<span>foo</span>'` → `undefined` with the same `'a'` child expecting `<div>a</div>`, the empty-string → `undefined` case, and the textContent variants. It also covers mount with `innerHTML: undefined`, array children, and a reactive component case. The change is small and sits next to the existing #9135 logic.

**Patch B.** It only adds a dev-mode warning when a non-nullish `innerHTML`/`textContent` is combined with children. It deliberately skips the nullish case, which is exactly the issue's reproduction (`innerHTML: undefined`), so it does nothing for that scenario. It also does not fix the update bug where the text fails to reappear after the prop is removed. Its tests only check that warnings appear, not rendering correctness. Adding warnings to existing SSR tests is unrelated churn. It also contradicts the user's stated intent to use both together, with `innerHTML` taking precedence when it is set.

Patch A is clearly the better fix.
