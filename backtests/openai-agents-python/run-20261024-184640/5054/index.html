Cancelling a MCP server work task does not stop the worker

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches make the independent test pass and preserve the CancelledServer contract, so the decision rests on root-cause fidelity and risk.

Patch B follows the design the issue itself sketches: on 3.11+ it uses the official `Task.cancelling()` signal, on 3.10 it substitutes a `Task` subclass that counts cancel requests and resets per command, and it adds the missing `uncancel()` to the fallback timeout path in `_run_with_timeout_in_task` so that path no longer leaves a stale request behind. It also handles the case where the command swallows the external cancellation (post-command `cancelling()` check), settles queued commands in a `finally`, and refuses new commands once the task is done (`_enqueue`). Because it relies on `cancelling()` on 3.11+, it correctly ignores anyio-style internal cancel/uncancel cycles that the real MCP transports perform. Its tests cover external cancel, swallowed cancel, queued commands, manager bookkeeping, CancelledServer, the pre-3.11 fallback timeout path, and anyio-like self-cancellation; the one skipped test is skipped only where the behaviour is genuinely undetectable (pre-3.11), and the core tests run everywhere.

Patch A instead hooks the loop's task factory to monkeypatch `task.cancel` on the instance and counts every cancel() call even on 3.11+, ignoring `cancelling()`/`uncancel()`. That counter is perturbed by any library that cancels the host task internally (anyio `fail_after`, task groups, which the MCP SDK uses), so a server-raised CancelledError that follows such internal activity would be misclassified as external and kill the worker, the exact distinction the issue asks to preserve. It does not handle a command that swallows the external cancellation, so that case reproduces the original hang. It also widens scope considerably: a new required constructor argument on `_ServerWorker`, temporary replacement of the loop's task factory, and an 'emergency cleanup' run inside the cancelled task. That cleanup is bounded only by `cleanup_timeout_seconds`; if that is None and cleanup hangs, the cancelled worker again never finishes, re-creating the issue's symptom. These additions add risk without being required by the issue.

B resolves the root cause more faithfully, with less risk and well-targeted tests; A's extra machinery introduces new misclassification and hang paths.

The issue

View on GitHub

Describe the bug

Cancelling a _ServerWorker task does not stop the worker. _ServerWorker._run
(src/agents/mcp/manager.py:93-110) wraps the command it is running in except BaseException, records the
error on the command's future and continues its loop. asyncio.CancelledError is a BaseException, so an
external cancellation is consumed as if it were a command failure and the worker goes back to
await self._queue.get().

The task stays alive in the cancelling state, so is_done stays False, the manager's
add_done_callback / _handle_worker_done bookkeeping never runs, and anything awaiting the task (including
loop shutdown) waits for a task that will not finish.

Debug information

  • Agents SDK version: main @ fbf59a40
  • Python version: 3.14.0

async def test_cancelling_the_worker_task_stops_the_worker() -> None:
    server = _BlockingServer()
    worker = _ServerWorker(cast(Any, server))

    caller = asyncio.create_task(worker.connect(timeout_seconds=None))
    await asyncio.wait_for(server.connect_started.wait(), timeout=1)

    worker._task.cancel()
    await asyncio.sleep(0.2)

    caller.cancel()
    try:
        await caller
    except BaseException:
        pass

    assert worker._task.done(), "the worker task survived cancellation and is still looping"

Result on main:

AssertionError: the worker task survived cancellation and is still looping
<Task cancelling name='Task-2' coro=<_ServerWorker._run() running at src/agents/mcp/manager.py:95>

Expected behavior

Cancelling the worker task ends it.

Why this is not a one-line re-raise

A server's own connect/cleanup may raise CancelledError deliberately — CancelledServer in
tests/mcp/test_mcp_server_manager.py, together with suppress_cancelled_error, depends on that error
reaching the caller through the command future. So the two cases need separating: an error raised *by the
command* (settle the future, keep looping) versus a cancellation of the worker itself (settle the future,
then stop).

asyncio.current_task().cancelling() > 0 distinguishes them on 3.11+, but the fallback timeout path in
_run_with_timeout_in_task (manager.py:135-148) calls task.cancel() and converts the result to
TimeoutError without a matching uncancel(), which would leave a pending cancellation request behind on
that path. cancelling() also does not exist on 3.10, which the project still supports.

Happy to send a PR with tests once you decide which behaviour you want.
