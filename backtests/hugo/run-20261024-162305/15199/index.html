related: Add option to tokenize headings

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Patch A implements exactly what the issue specifies: `tokenize` only affects heading titles in `fragments` indices (the tokenizing helper is only invoked inside the `TypeFragments` branch), heading identifiers are still indexed as `FragmentKeyword` alongside new `FragmentTokenKeyword` tokens, so exact-identifier matching (e.g. `pagerefs: ['something-else']`) keeps working with tokenize on, and definition terms are untouched. It strips HTML tags and unescapes entities before splitting (heading titles like `Running <em>hugo</em>` tokenize correctly), respects `ToLower`, dedups tokens per document, and extends the `applyFilter` path with a distinct keyword type so filtered headings are computed by re-tokenizing titles. It adds docs, a config-decode assertion, a unit test for the tokenizer, and an integration test covering on/off, HTML in headings, definition terms, and exact-ID matching.

Patch B diverges from the spec and has correctness bugs. It applies tokenization to basic indices via `ToKeywords` (string and []string), contradicting "Currently applies to heading titles in indices of type `fragments`"; the independent test TestBtJudgeTokenizeScopedToFragmentsIndices fails on B for exactly this reason. When tokenize is on it `continue`s past the heading identifier, so headings are no longer indexed by ID, breaking cross-page exact-identifier references on that index. Tokens are produced via `stringToKeyword` (a `StringKeyword`), yet the applyFilter branch only collects words from `kw.(FragmentKeyword)`, so `ff.words` is never populated and heading filtering silently stops working with tokenize enabled; B's own TestRelatedFragmentsTokenizeApplyFilter appears unable to pass as written. `splitWords` does not strip HTML tags, so a title containing `<em>hugo</em>` yields a garbage token like `em>hugo</em`. B also adds an unrequested `minTokenLength` option and no documentation, and includes whitespace churn in existing tests.

On correctness, scope, and tests A is clearly better; the one independent test that separates them does so for a reason the issue explicitly states.

Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours. I suggest using the name tokenize, documented as follows:

(bool) Whether to split multi-word values into individual keywords for indexing and matching. Currently applies to heading titles in indices of type fragments; non-heading fragments such as definition terms continue to use exact-identifier matching regardless of this setting. This increases index size in proportion to the average number of words per heading; use cardinalityThreshold to prune common words and reduce build time. Default is false.
