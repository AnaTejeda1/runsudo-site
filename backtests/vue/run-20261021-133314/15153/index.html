Custom elements: async components nested ≥3 levels crash with TypeError: Cannot read properties of null (reading 'provides') — chained child resolve races its parent's mount

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches attack the same root cause: the child's chain promise settled when the parent's `_resolveDef()` returned rather than when the parent mounted. Patch A fixes it by making `_resolveDef()` return the async `_pendingResolve` and returning it from the chain callback; Patch B fixes it by returning `this._pendingResolve` from the chain callback after calling `_resolveDef()`. Both make the chain settle after the parent's `resolve()` (which calls `_mount` synchronously), so the independent 3- and 4-level tests pass under either.

B goes further on correctness in a way that is tied to the same crash: it moves the `parent._pendingResolve` check ahead of the `_resolved` check, so an already-resolved child connected under a pending async parent is also deferred instead of mounting immediately into `_inheritParentContext` with `parent._instance === null`. Under A that path still dereferences a null parent instance. A's extra `isConnected` guard is a reasonable hardening against mounting a detached element, but it addresses a pre-existing behavior unrelated to the reported null dereference.

On tests, A's test is more deterministic (controlled promise resolution rather than real setTimeout delays), and B's 5/30/1 ms timing-based tests carry some flake risk. However B's suite covers more of the issue's variants table: 3 levels with slow middle, 4 levels with slow intermediates, plain div between levels, a sync middle, and provide/inject propagation at each level, plus the resolved-and-moved case. Both would fail on base.

Scope and craft are comparable; B's restructure is slightly larger but clearly commented and keeps the fix readable. Net: B resolves the root cause more completely with broader issue-aligned coverage, outweighing A's cleaner test style.

Steps to reproduce

  1. Open the reproduction link and watch the console: mounted x-inner never appears — the element crashes with an unhandled TypeError: Cannot read properties of null (reading 'provides') and never mounts. (The playground variant inserts the nested markup dynamically after the define() calls; dynamic and parser-created markup crash identically.)
  2. Parser-created (static server-HTML-style) variant — self-contained single file, no build step (save as repro.html, serve statically, open in any browser; Chromium, Firefox and WebKit all reproduce):

<x-outer>

    </div>

<script type="module">
  import {

    defineAsyncComponent,
    h,
  } from "https://unpkg.com/vue@3.5.40/dist/vue.esm-browser.js";

  // Delays chosen so the middle level settles AFTER its child: outer fast,
  // middle slow, inner fast. This crashes on 100% of loads.
  const delays = { "x-outer": 50, "x-middle": 300, "x-inner": 10 };

  const makeComponent = (name) => ({
    name,
    mounted() {
      console.log(`mounted ${name}`);
    },
    render() {
      return h("div", { style: "display:block;padding:6px;border:1px solid #888" }, [name, h("slot")]);
    },
  });

  const makeLoader = (tag) => () =>
    new Promise((resolve) => setTimeout(() => resolve(makeComponent(tag)), delays[tag]));

  // Define the three tags parent-first.
  for (const tag of ["x-outer", "x-middle", "x-inner"]) {
    customElements.define(tag, defineCustomElement(defineAsyncComponent(makeLoader(tag))));
  }

  window.addEventListener("error", (e) => console.error("UNCAUGHT:", e.message));
  window.addEventListener("unhandledrejection", (e) =>
    console.error("UNHANDLED REJECTION:", e.reason?.message ?? e.reason),
  );
</script>

What is expected?

All three elements mount ancestor-first: mounted x-outer, mounted x-middle, mounted x-inner. The nested-async chaining added in 3.5.0 (37ccb9b, "delay mounting of custom elements with async parent", closing #9341 / #8127 / #9351) exists to guarantee exactly this.

What is actually happening?

mounted x-outer
UNHANDLED REJECTION: Cannot read properties of null (reading 'provides')
mounted x-middle

x-inner crashes in VueElement._mount → _inheritParentContext (runtime-dom — parent._instance.provides is dereferenced guarded only by parent && this._app), never mounts, and is left permanently half-resolved: _resolved: true, _instance: null, shadow root empty. Nothing ever retries it, no error surfaces through app.config.errorHandler, and any provide/inject inheritance it should have received is lost. Its own descendants (at deeper nesting) then crash against it in cascade.

Any additional comments?

Analysis (why depth ≥ 3 is the trigger)

connectedCallback of a child under a pending async parent chains:

this._pendingResolve = parent._pendingResolve.then(() => {
  this._pendingResolve = undefined;
  this._resolveDef();
});
  • For an unchained parent (depth 2), parent._pendingResolve is the parent's own _resolveDef() flow, which settles after the parent has mounted → 2-level nesting is safe. The variants table below confirms: 2 levels never crash.
  • For a chained parent (depth ≥ 3), parent._pendingResolve is itself a chain promise — and that promise settles when the parent's _resolveDef() returns (i.e. when the parent's async load starts), not when the parent mounts.

So once the first unchained ancestor mounts, the whole chain unwinds within a few microtasks: every deeper level's loader fires nearly simultaneously and mount order degenerates to network settlement order. Any child whose async definition settles before its parent has mounted hits _inheritParentContext while parent._instance === null and throws. With real-network chunk timings the victim set varies per load, so in an app this presents as a flaky, page-dependent breakage; with the fixed delays above it is 100% deterministic.

Variants checked (each re-run in a real browser):

VariantResult
3 levels, middle slowestcrashes every load
3 levels, inner slowestclean (race direction confirmed)
2 levelsclean (chained parent required)
plain <div> between levelsstill crashes (structure-independent)
markup inserted dynamically after all define() callsstill crashes
all loaders instantclean (microtask FIFO protects when nothing is pending)

_inheritParentContext (#13219, ~3.5.14) did not introduce the race — it converted a pre-existing silent misordering into a hard crash. 3.4.38 (no chaining) and 3.5.13 (chaining, pre-#13219) fail with the same null dereference in the older _setParent provides-copy path.

Suggested direction — either (or both):

  1. Chain the child to the parent's actual mount, not to _resolveDef() returning — e.g. resolve the parent's _pendingResolve only after _mount() has run, so the guarantee the chaining was built for ("ancestor mounts before descendant") holds at any depth.
  2. Guard _inheritParentContext against parent._instance === null and defer context inheritance until the parent instance exists, instead of throwing away the child permanently on an unhandled rejection.
