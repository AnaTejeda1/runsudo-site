The issue

View on GitHub

Description

Tool input repair reads the current tool definition from ctx.tool.list(), but execution validates against the definition captured by Tool.snapshot(). If the registered schema changes after snapshot creation, repair can turn valid arguments into invalid ones.

I reproduced this with a live openai/gpt-6-luna session. The captured tool accepts { value: string }, and the model sends {"value":"false"}. After the live registry schema changes to { value: boolean }, repair converts the string to a boolean and validation fails:

Invalid arguments for tool "schema_probe":
- value: Expected string

Arguments provided:
{
  "value": false
}

The persisted tool record confirms the model originally sent a string. Disabling the repair plugin makes the same reproduction succeed with Received "false" (string).

Expected behavior: repair should use the same captured tool definition as validation and execution.

Plugins

Built-in ToolInputRepairPlugin and a local reproduction plugin, repro.captured-schema. The reproduction plugin changes the registered schema after snapshot creation; it does not modify model responses or tool-call arguments.

OpenCode version

V2 source at d1f8f5b35ef90499902797129457f2102abe18b6 (package version 2.0.22), built locally with Bun 1.4.2.

Steps to reproduce

  1. Register a direct tool named schema_probe with input schema Schema.Struct({ value: Schema.String }).
  2. In the first primary session.model.request hook, update its registered input schema to Schema.Struct({ value: Schema.Boolean }). The request has already captured the string schema.
  3. Ask the model to call schema_probe once with {"value":"false"}.
  4. Observe that the model sends a string, but validation reports a boolean and rejects the call.
  5. Disable opencode.tool.input.repair and repeat in a fresh standalone process. The captured tool now correctly receives the string.

Integration tests also reproduce the same mismatch through direct execution and Code Mode.
