Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the reported root cause identically: they stop re-quantizing the filtered result back onto the source's indexed palette by gating the `conf.TargetFormat == images.PNG` palette re-application on the action type. For issue 12543 the core correctness is equivalent — the offending code path is the `paletted` re-application after Overlay/Text, and both skip it for the filter action. Both also update the same two relevant golden fixtures (overlay.png, text.png), so the direct test evidence for THIS issue is a wash.

The decision turns on scope and robustness. Patch A is minimal and focused: one gated condition reusing the existing `images.Actions` whitelist (resize/crop/fit/fill), with a clear comment explaining that only geometric transforms preserve the source's colors while filters legitimately introduce new ones. The whitelist is also slightly more robust than Patch B's blacklist — any future non-geometric action defaults to NOT re-quantizing (the safe behavior), whereas Patch B's `conf.Action != images.ActionFilter` would wrongly re-apply the palette to any new filter-like action not literally named "filter".

Patch B, by contrast, bundles a substantial and unrelated fix for a different issue (12536, NRGBA/alpha-premultiplication in hex color handling): it rewrites Color.init, ColorGoToHexString, AddColorToPalette, and hexStringToColorGo, adds an ActionFilter constant, and touches a third golden file (padding-transparent-chained.png) plus new color_test.go cases. Those color changes are genuine improvements, but none of them are on the indexed-PNG-overlay path, and the diff itself cites "issue 12536" for them. Per the scope criterion, this unrelated bug fix and its tests count against B for a review scoped to 12543. With correctness and issue-specific tests essentially tied, Patch A's tighter scope and marginally safer whitelist logic make it the better fix for the reported issue.

func main() {
	// Get the background image (24 bit: indexed not true color)
	f, err := os.Open("background.png")
	if err != nil {
		log.Fatal(err)
	}
	bgImage, _, err := image.Decode(f)
	if err != nil {
		log.Fatal(err)
	}

	// Get the foreground image (24 bit with 8 bit alpha channel)
	f, err = os.Open("foreground.png")
	if err != nil {
		log.Fatal(err)
	}
	fgImage, _, err := image.Decode(f)
	if err != nil {
		log.Fatal(err)
	}

	// Create a new image with dimensions of the bgImage.
	dstImage := image.NewRGBA(bgImage.Bounds())
	// Copy the bgImage to the dstImage.
	gift.New().Draw(dstImage, bgImage)
	// Draw the fgImage over the dstImage at the (20, 20) position.
	gift.New().DrawAt(dstImage, fgImage, image.Pt(20, 20), gift.OverOperator)

	// Create the composite file.
	f, err = os.Create("composite.png")
	if err != nil {
		log.Fatal(err)
	}
	defer f.Close()

	// Encode the composite image.
	err = png.Encode(f, dstImage)
	if err != nil {
		log.Fatal(err)
	}
}

What the agent reported

Summary

What was wrong

Hugo issue #12543: overlaying (or adding text to) an indexed/paletted PNG background produced a low-quality composite because the output was clamped to the background's 256-color palette. GIF (also indexed) was unaffected.

The cause was in resources/image.go, doWithImageConfig. After the image was processed (the overlay/text composite is correctly built as a full-color NRGBA image), a post-processing block re-quantized the finished composite back onto the source PNG's palette whenever the target format was PNG and the source decoded as *image.Paletted:

if conf.TargetFormat == images.PNG {
    if paletted, ok := src.(*image.Paletted); ok {
        tmp := image.NewPaletted(converted.Bounds(), palette)
        draw.FloydSteinberg.Draw(tmp, tmp.Bounds(), converted, ...)
        converted = tmp
    }
}

This is fine for geometric transforms (resize/crop/fit/fill), which only rescale the image's own colors and benefit from a small indexed PNG. But for .Filter operations like Overlay/Text — which composite new colors not in the source palette — Floyd–Steinberg dithering onto that 256-color palette destroys quality. It was PNG-only, which is why GIF worked.

What I changed

Guarded the palette re-application so it runs only for geometric-transform actions, using the existing exported images.Actions map (contains only resize/crop/fit/fill):

if conf.TargetFormat == images.PNG && images.Actions[conf.Action] {

.Filter sets conf.Action == "filter" (not in the map), so overlay/text now keep the full-color composite; resize/crop/fit/fill behavior is unchanged. This is a one-condition change (resources/image.go, +7/−1 including an explanatory comment).

I also regenerated the two pre-fix baseline golden files for this issue — resources/images/testdata/images_golden/filters/paletted/overlay.png and text.png (committed in 62e24b7ed with the note "before any fix is applied"). They changed from indexed (PNG color-type 03) to truecolor (color-type 02), confirming the composite is no longer palette-clamped.
