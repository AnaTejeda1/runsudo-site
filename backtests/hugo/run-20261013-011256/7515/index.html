Patch B is the better fix.

**Correctness**
- B adds an opt-in `splitWords` option to the basic index type, which is exactly what the issue asks for (partial matching on e.g. `title`).
- Splitting uses `unicode.IsLetter`, `IsNumber` and `IsMark`, so non-ASCII text such as accented words and CJK is handled correctly.
- Keywords are deduplicated per document, so repeated words cannot inflate rank.
- It adds a `stopWords` list, which directly answers the issue's question about ignoring common words. The list can be configured per language, which addresses the i18n concern.
- `DecodeConfig` rejects `splitWords` on non-basic index types instead of misbehaving silently.

Patch A has a broader scope (tokenized fragments plus an `ApplyFilter` rewrite) with more risk:
- Tokenized fragment keywords are built through `stringToKeyword`, which returns a `StringKeyword`, not a `FragmentKeyword`.
- In `searchDate`, the `kw.(FragmentKeyword)` type assertion therefore never succeeds for tokenized words. `ff.words` stays empty, and the new heading filter appears to be dead code. Its `ApplyFilter` test looks likely to fail or to pass only by accident.
- On the basic path, A's `ToKeywords` does not deduplicate tokens, so repeated words over-weight a document.
- A offers only `MinTokenLength` as a crude stand-in for stop words.
- Whitespace-based splitting with punctuation trimming leaves hyphenated or joined words unsplit.

**Tests**
- B has focused unit tests (keyword splitting, stop words, non-ASCII input, search, config validation) and an integration test that checks a split index alongside an unsplit one.
- A has more integration tests, but they cover the riskier fragments path, including the questionable `ApplyFilter` behavior.

**Scope and craft**
- A includes unrelated whitespace churn in existing tests.
- B updates the docs and keeps the change small and coherent by routing through a single `stringsToKeywords` helper.

The issue

View on GitHub

When specifying the indices for related content, it would be useful to specify that some of them were split by word, so that their text could be matched partially. This would allow the title to be used for more in-depth indexing, rather than requiring the user to specify tags / keywords.

This would likely increase memory usage and decrease performance, so should definitely be opt-in!

I suspect common words (a, an, the etc) might want to be ignored? Although doing that in a sane, i18n-friendly manner might be a challenge!
