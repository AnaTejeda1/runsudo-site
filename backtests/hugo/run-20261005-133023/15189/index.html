Issue with chained resource transformations

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches find the same root cause. `TransformWithContext` reused `r.target`, but once the chain has run (for example, after `.Data` is accessed), that target holds the already-transformed resource. Re-applying the full chain to it double-transforms. Both fix this by keeping the original untransformed source and starting new chains from it.

The patches differ in two places.

1. **`cloneTo` (e.g. `resources.Copy`):**
   - Patch B sets `sourceTarget = r.target.cloneTo(...)`. If the adapter has already been transformed, `r.target` is the transformed resource, so the new source becomes transformed content. The transformation list is still attached, so the same double-application bug comes back through Copy.
   - Patch A handles this explicitly. With no transformations, the source is the new target. Otherwise it clones the untransformed `chainSource`.
   - Patch A's test covers this path: fingerprint, access `.Data`, Copy, access `.Data`, then minify.

2. **Slice aliasing:**
   - Patch A builds a fresh slice instead of `append(r.transformations, t...)`. This prevents two branches chained off the same base from sharing a backing array and overwriting each other's appended transformations.
   - Patch B keeps the aliasing-prone append.

**Tests:**
- Patch A adds a generic integration test. It checks that triggering via `.Data`, `.Content` or `.RelPermalink` before chaining, and the Copy case, all give the same output as the never-initialized chain. It also adds a css.Build `.Data.Artifacts` then fingerprint test, matching the issue's scenario.
- Patch B adds only the css.Build scenario, which relies on hard-coded hashes.

Scope is comparable and focused in both. Patch A is more correct at the edges and better tested.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The issue

View on GitHub

See the fix in #15188.

This has been an issue since we added this feature, but we haven't noticed it (or gotten reports about it) because the common setup is to set up the entire chain before starting to use it:

{{- with . | css.Build $opts }}
	{{- if hugo.IsDevelopment }}
		<link rel="stylesheet" href="{{ .RelPermalink }}">
	{{- else }}
		{{- with . | fingerprint }}
			<link rel="stylesheet" href="{{ .RelPermalink }}" integrity="{{ .Data.Integrity }}">
		{{- end }}
	{{- end }}
{{- end }}

In the above:

  • .RelPermalink triggers the transformation of the entire chain in a streaming way.

With the recently added .Data.Artifacts in css.Build I discovered this issue by accident when doing something ala:

{{- with . | css.Build $opts }}
	{{ range .Data.Artifacts }}
		{{ if eq .MediaType.MainType "font" }}
			<link rel="preload" href="{{ .RelPermalink }}" as="font" type="{{ .MediaType.Type }}">
		{{ end }}
	{{ end }}
	{{- if hugo.IsDevelopment }}
		<link rel="stylesheet" href="{{ .RelPermalink }}">
	{{- else }}
		{{- with . | fingerprint }}
			<link rel="stylesheet" href="{{ .RelPermalink }}" integrity="{{ .Data.Integrity }}">
		{{- end }}
	{{- end }}
{{- end }}

In the above:

  • .Data triggers the css.Build transformation.
  • Then fingerprint starts a new transformation with correct .Content, but wrongly including the full chain, including css.Build

The above could be rewritten to the below and it would work as expected:

{{- with . | css.Build $opts }}
	{{- if hugo.IsDevelopment }}
		<link rel="stylesheet" href="{{ .RelPermalink }}">
	{{- else }}
		{{- with . | fingerprint }}
			{{ range .Data.Artifacts }}
				{{ if eq .MediaType.MainType "font" }}
					<link rel="preload" href="{{ .RelPermalink }}" as="font" type="{{ .MediaType.Type }}">
				{{ end }}
			{{ end }}
			<link rel="stylesheet" href="{{ .RelPermalink }}" integrity="{{ .Data.Integrity }}">
		{{- end }}
	{{- end }}
{{- end }}
{{- end }}
