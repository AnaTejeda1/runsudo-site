Both patches are behaviorally equivalent and correctly fix the root cause: they reuse the parent's already-substituted PydanticExtraInfo when __pydantic_extra__ is only inherited, mirroring field inheritance. I traced the key scenarios — plain Sub(M[int]) (typevars_map empty → reuse parent's dict[str,int]), direct M[int] parametrization (typevars_map non-empty + complete → replace_types), local re-annotation (build from cls_annotations hint), and the 2-level Mid[int] chain — and both produce identical results. Patch A guards its base lookup with `'__pydantic_extra__' not in cls_annotations` and places the whole thing inside `if '__pydantic_extra__' in type_hints`, with an early `break` — so it does extra work only in the narrow inherited-extra case. Patch B is marginally more readable with its flat three-branch structure and per-scenario comments, but that craft edge does not outweigh A's tighter, better-scoped change given correctness and tests are equal.

Description

Follow-up to #13369 / #13391 (__pydantic_extra__ typevar substitution, currently main-only): the substitution works for direct parametrization (M[int]) but is lost in a plain (non-generic) subclass of a parametrized model (class Sub(M[int])). Extras on the subclass are silently unvalidated and the JSON schema loses the extras type.

M[int](x='nope')  -> ValidationError (correct, fixed by #13391)
Sub(x='nope')     -> accepted; m.x == 'nope'          # BUG
Sub(x='5').x      -> '5' (str)  vs  M[int](x='5').x == 5

M[int].model_json_schema()['additionalProperties']  -> {'type': 'integer'}
Sub.model_json_schema()['additionalProperties']     -> {}                  # BUG
Sub.__pydantic_extra_info__                          -> PydanticExtraInfo(annotation=dict[str, ~T], complete=True)

Root cause (from stepping through collect_model_fields in pydantic/_internal/_fields.py): for Sub, typevars_map is empty (its own __pydantic_generic_metadata__ is empty) and the inherited hint for __pydantic_extra__ is the parent's raw annotation dict[str, T] — so _generics.replace_types(ann, typevars_map) is a no-op and the raw ~T survives, producing extras_schema = {'type': 'any'}. Regular fields don't have this problem because they're copied from the parent's already-substituted model_fields; the extra-info path never consults the parent's __pydantic_extra_info__ (which on M[int] correctly holds dict[str, int]).

Note the 2-level generic chain (class Mid(M[T], Generic[T]); Mid[int]) works on main — only the plain-subclass case is broken.

I have a small fix working locally (reuse the parent's substituted PydanticExtraInfo annotation when __pydantic_extra__ is only inherited, mirroring how fields inherit; brings extra-info to exact parity with fields, including the same known deferred-annotation limitation as #12000), with a regression test in the style of test_extra_generic_class — it passes the test_main.py / test_generics.py / test_forward_ref.py / test_edge_cases.py suites with no new failures. Per the contributing guidelines I'd like to be assigned before opening the PR — happy to submit it right away.

Summary

What was wrong

In collect_model_fields (pydantic/_internal/_fields.py), the __pydantic_extra__ handling always re-read the parent's raw annotation (dict[str, T]) from type_hints and called _generics.replace_types(ann, typevars_map). For a plain non-generic subclass of a parametrized model (class Sub(M[int])), typevars_map is empty, so the substitution was a no-op and the raw ~T survived — making extras on Sub silently unvalidated and dropping the extras type from the JSON schema. Regular fields avoided this by copying from the parent's already-substituted model_fields; the extra-info path never consulted the parent's substituted __pydantic_extra_info__.

What I changed

  • pydantic/_internal/_fields.py: Added a parent_extra_info lookup (mirroring the existing parent_fields_lookup) and split the extra-info build into three branches mirroring the regular-field inheritance logic:
  • defined-on-class / no parent info → build from the type hint (unchanged behavior);
  • elif typevars_map (direct parametrization, M[int]) → substitute type vars into the parent's already-substituted annotation;
  • inherited-only (Sub(M[int])) → reuse the parent's substituted PydanticExtraInfo.
  • tests/test_main.py: Added test_extra_generic_subclass, styled after the sibling test_extra_generic_class.

Test evidence

  • Regression test test_extra_generic_subclass failed before the fix (additionalProperties was {} instead of {'type': 'integer'}) and passes after.
  • test_extra_generic_class (direct-parametrization) still passes — no regression.
  • Broader suites tests/test_main.py tests/test_generics.py tests/test_forward_ref.py tests/test_edge_cases.py: 640 passed, 27 skipped, 9 xfailed — no new failures.
  • Reviewer confirmed the diff is minimal, correctly scoped, and the elif branch cannot regress direct parametrization.

Requirements disposition

  1. Sub(x='nope') should raise ValidationError — implemented; covered by pytest.raises(ValidationError) in the regression test.
  2. Sub JSON schema additionalProperties should be {'type': 'integer'} — implemented; asserted in the regression test (was the failing assertion pre-fix).
  3. Bring extra-info to parity with fields, keeping the same deferred-annotation limitation as #12000 — implemented; incomplete parent info falls through to the existing rebuild_model_fields deferral path (confirmed by reviewer), scoped to collect_model_fields as the report specified.
  4. 2-level generic chain (Mid[int]) already works — must not break — verified; full test_generics.py passes with no new failures.
  5. Regression test in the style of test_extra_generic_class — implemented; test_extra_generic_subclass, structurally identical to the sibling.

All changes are left uncommitted in the working tree; no scratch files remain.
