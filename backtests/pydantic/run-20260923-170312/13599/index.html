PEP 695 type aliases don't work with callable discriminators

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

The two patches are functionally near-identical: both thread `definitions` through `apply_discriminator` into `_convert_schema` and add a `_resolve_ref` helper that resolves a `definition-ref` via `handler` (schema-gen path) or `definitions.get()` (deferred/callable path). Both fix the reported root cause—an unresolved PEP 695 type-alias `definition-ref` at the union root/choice level when a callable Discriminator is used on a field. Correctness is essentially a wash. B's code is marginally cleaner (LookupError encapsulated inside `_resolve_ref` so failure is uniformly signaled as None, no duplicated try/except at call sites, and a `cast` to `DefinitionReferenceSchema` for type-correct `schema_ref` access), whereas A keeps the more conservative `(handler is not None or definitions is not None)` guards and repeats the try/except at each call site. However, A's guard preservation is functionally equivalent (when both are None, B's `_resolve_ref` just returns None to the same effect), and B additionally drops the guard on the root branch so a both-None `definition-ref` now raises `MissingDefinitionForUnionRef` instead of falling through—a benign but slightly broader behavior change. The decisive difference is test quality, which ranks above craft: A's test exercises both union branches (asserts Foo for `{'type':'foo'}` AND Bar for `{'type':'bar'}`), asserts `isinstance`, and uses a realistic discriminator handling both dict and attribute access (`v['type'] if isinstance(v, dict) else v.type`). B's test checks only the single 'foo' branch with a dict-only lambda (`lambda v: v['type']`), so it never verifies tag selection actually distinguishes choices. With correctness tied, A's meaningfully more thorough test edges out B's cleaner-but-slightly-broader implementation.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Summary

What was wrong

PEP 695 type aliases (type X = ... / TypeAliasType) failed with callable discriminators applied via Field(discriminator=Discriminator(callable)), raising PydanticUserError:Tagnot provided for choice {...definition-ref...}.

The cause: for a PEP 695 alias, the field's core schema is a top-level definition-ref pointing to the union stored in the definitions dict. apply_discriminator() (pydantic/_internal/_discriminated_union.py) routed callable discriminators to Discriminator._convert_schema(schema) without forwarding the definitions dict. _convert_schema could unwrap definition-ref schemas only when a handler was present — but the Field/deferred path has handler=None. So the top-level definition-ref was never unwrapped; it got wrapped in a single-item union whose sole choice was the raw definition-ref with no Tag → the error. (String discriminators and old-style TypeAlias worked because they take a different code path / inline the members. The existing #12843 test passed because it uses Annotated[..., Discriminator(...)], which goes through the handler path that was already patched.)

What I changed

  • pydantic/types.py: Discriminator._convert_schema now accepts a definitions param and resolves definition-ref schemas (top-level union ref and per-choice refs) from either the handler or the definitions dict, via a small _resolve_ref helper. Behavior for the existing handler-present path is unchanged (when called from __get_pydantic_core_schema__, definitions is None, so the guard conditions are identical to before). Unresolvable top-level refs still raise MissingDefinitionForUnionRef (enabling deferral).
  • pydantic/_internal/_discriminated_union.py: apply_discriminator now forwards definitions to _convert_schema.
  • tests/types/unions/test_discriminated_union.py: added test_discriminated_union_type_alias_type_separate_field_callable_discriminator (issue #13599).

Test evidence

  • New regression test failed before the fix with the exact reported PydanticUserError (raised at Main class definition).
  • After the fix, ./bt-test tests/types/unions/test_discriminated_union.py tests/test_type_alias_type.py: 98 passed, 4 xfailed (the 4 pre-existing xfails unchanged; no previously passing test regressed; new test passes).
  • Reviewer confirmed the diff is minimal, targets the exact scenario, and does not alter the handler path.

  • M4 — old-style TypeAlias + callable discriminator: already worked; still passes (covered by existing suite; unchanged by the diff).
  • M1 / M2 — string-discriminator (Field(discriminator='type_')) with PEP 695 and old-style aliases: already worked; still pass (inferred-discriminator path, untouched; confirmed by the passing suite).
