multiple_of=0 still raises ZeroDivisionError for non-native numeric types

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Patch A fixes the cause the issue names: the Python fallback in `_validators.py` divides by `multiple_of` without checking it. A adds `check_multiple_of_constraint`, which runs at schema-build time whenever `multiple_of` falls back to the Python validator. That covers Fraction, timedelta, complex, any other type using `%`, and native types where the constraint can't be pushed down (e.g. `int` with an `AfterValidator`, which A tests). It also guards the same unchecked path in the experimental pipeline. Its edge handling is careful: values not comparable to `0` are compared to their own zero (timedelta), unordered values are checked for `!= zero` (complex), and NaN/inf are rejected. Tests cover Fraction (0, negatives, NaN, inf, Decimal NaN), timedelta, complex, the after-validator int case and the pipeline, plus positive cases confirming valid constraints still work. One minor weakness is that A raises `ValueError` with a slightly different message rather than core's `SchemaError`, but model definition still fails at schema generation as the issue asks. Patch B instead adds native `multiple_of` support for Fraction and timedelta in pydantic-core (Rust validators, `core_schema` types and constraint pairings). That is consistent with how int/float/Decimal raise `SchemaError`, but it is a much broader redesign spanning the Rust core. It also leaves the actual root cause untouched: the Python fallback still performs `x % 0` unchecked, so complex, wrapped/function schemas and other fallback types can still reach it. B's Rust changes add risk and churn, and its tests cover only Fraction and timedelta. On correctness at the root cause and breadth of coverage, A is the better fix.

Description

Field(multiple_of=0) is rejected during schema generation for int, float, and Decimal, but equivalent non-native numeric types still pass schema generation and raise an uncaught ZeroDivisionError during validation.

Reproduction

from fractions import Fraction
from pydantic import BaseModel, Field

class Model(BaseModel):
    value: Fraction = Field(multiple_of=0)

Model(value=Fraction(1, 2))

Actual: validation raises ZeroDivisionError rather than ValidationError.

Expected: model definition fails with a schema-generation error stating that multiple_of must be greater than zero, consistently with native numeric types.

The Python fallback in pydantic/_internal/_validators.py performs x % multiple_of without validating the divisor. Fraction, temporal types, and complex use this fallback. I found no existing report for the remaining types after the native numeric fix.
