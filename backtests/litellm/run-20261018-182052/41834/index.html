The issue

View on GitHub

Summary

In LiteLLM 1.100.0, Databricks service_tier="priority" can be dropped during request translation and parameter filtering. Databricks cost calculation also ignores the resolved tier, so configured priority input/output/cache-read rates are not used. Returned tiers are lost in response conversion and streaming aggregation.

These defects need to be handled together: fixing pricing alone can apply requested priority rates even when Databricks reports service_tier="default" after fallback.

Reproduction and environment

Reproduced with a clean installation of litellm[proxy]==1.100.0 on Python 3.11 in an isolated virtual environment. The portable pytest file will be attached in a follow-up comment. It uses synthetic model prices and response objects; no API credentials, provider calls, proxy, or downstream repository files are required.

Save the attached file as test_databricks_service_tier_upstream.py, outside any existing checkout, and run:

python3 -m venv /tmp/databricks-tier-repro
/tmp/databricks-tier-repro/bin/pip install 'litellm[proxy]==1.100.0' pytest
LITELLM_LOCAL_MODEL_COST_MAP=True /tmp/databricks-tier-repro/bin/python -m pytest -q test_databricks_service_tier_upstream.py

Observed results: 6 failed, 7 passed.

The synthetic pricing case has 100 input tokens (20 cached) and 50 output tokens. Standard rates are $1/$4 per million input/output tokens and $0.20 per million cached input tokens; priority rates are twice those values.

Default pricing, legacy Databricks model resolution, and returned-default fallback controls pass on stock 1.100.0. The fallback controls pass because stock Databricks pricing always uses standard rates; they must continue to pass after priority pricing is enabled. All 13 tests pass with a local fix.

Root cause

Source locations refer to LiteLLM 1.100.0:

  • litellm/llms/databricks/chat/transformation.py, DatabricksConfig.get_supported_openai_params (~line 259): service_tier is absent from the supported parameter list.
  • litellm/responses/litellm_completion_transformation/transformation.py, transform_responses_api_request_to_chat_completion_request (~line 340): reads kwargs.get("service_tier"), but the tier is in responses_api_request. Adding only the Databricks allowlist entry does not repair this earlier loss.
  • litellm/cost_calculator.py (~line 623) and litellm/llms/databricks/cost_calculator.py (~line 34): the Databricks dispatch/helper do not pass service_tier through to generic_cost_per_token.
  • litellm/litellm_core_utils/streaming_chunk_builder_utils.py: stream aggregation does not carry the returned tier, including when it arrives only on the final usage chunk. Databricks response parsing, stream-wrapper reconstruction, and Chat/Responses/Messages conversion also need to preserve it for end-to-end accounting.
  • completion_cost currently gives a requested tier precedence over a returned tier. For Databricks, a concrete returned default tier should override requested priority.

Additional Router/HTTP-interception tests exposed a related Messages-stream accounting issue: litellm/llms/anthropic/experimental_pass_through/adapters/streaming_iterator.py calls stream_chunk_builder without its existing request logging object. Standalone cost calculation can then miss Router pricing and cache a zero cost. Passing the logging object preserves the configured pricing context. This path is covered by the broader local regression suite, not the 13-test portable file.

Expected behavior

  • Forward supported Databricks default/priority tiers through Chat, Responses, and Messages bridges, including streaming.
  • Preserve provider-returned tiers through response parsing, adapters, stream reconstruction/aggregation, and accounting.
  • Apply configured tier-specific input, output, and cache-read prices.
  • Use a concrete returned Databricks tier over the requested tier; retain standard pricing and legacy model-name resolution.
  • If the provider omits a returned tier, do not manufacture one. Requested-tier pricing is an estimate, not evidence of the tier delivered or invoiced.

Databricks documents priority fallback and model/region availability here: https://docs.databricks.com/aws/en/machine-learning/foundation-model-apis/priority-mode

I searched open and closed issues for Databricks priority/service-tier symptoms and the affected function names and found no matching report. PR #35674 concerns cache pricing and does not address these tier-propagation gaps.
