LogCaptureHandler can be garbage collected when caplog fixture is in use

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

The issue's trigger is an old-style hookwrapper whose teardown raises (outcome.get_result() on the failing xfail test). On pluggy < 1.6 that aborts the remaining wrapper teardowns, so the logging plugin's pytest_runtest_call wrapper is left suspended; when the garbage collector finalises it during a later test, its catching_logs contexts exit and remove the shared LogCaptureHandler from the root logger. Patch B fixes this at the root by requiring pluggy>=1.6, where all wrapper teardowns run even if one raises. That also fixes the same leak for every other plugin wrapper (capture, etc.), not just logging. Its test reproduces the issue's exact conftest/test scenario, correctly runs in a subprocess (with a clear comment on why in-process would hide the bug), and would fail on the old dependency and pass after the bump. The change is minimal and the changelog explains the mechanism. Patch A instead works around the symptom inside catching_logs with module-level reference counts keyed by (logger, handler) plus a global ordered list of contexts that hand off orig_level to each other on out-of-order exit. It does make caplog survive a GC'd leaked context, and its tests exercise that, but it leaves the actual defect (skipped teardowns) in place for everything else, adds global mutable state and branching (including an 'attached by someone else' path) that is easy to get subtly wrong, and its main tests construct the leak artificially via private plugin API rather than the issue's scenario. The evidence note that the reference fix touches only config files is consistent with B's approach. B is the more correct, better-scoped fix with a more faithful regression test.

The issue

View on GitHub
  • a detailed description of the bug or problem you are having

In our tests we have had issues with the caplog fixture not correctly saving every log into caplog.messages and caplog.records. From what I can tell, the underlying issue is that in some circumstances the LogCaptureHandlers that caplog relies on can get garbage collected.

There seem to be a lot of issues in this area (#5160, #8977, #7335 etc.), but I'm not sure if any of them are the specific case that I have experienced.

  • minimal example if possible
