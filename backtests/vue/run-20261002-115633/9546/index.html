Issue #9546 Merged fix PR #15523 Run 2 Oct 2026 · run-20261002-115633 vuejs/core

defineProps options object loses properties when using generics

Worse

The merged fix was judged better than our patch.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches make the same root-cause fix. They replace the conditional `PropMethod<T>` with a plain function-like constructor type. The old conditional became a deferred generic conditional whenever `T` was a type parameter. That deferral is what made `RequiredKeys`/`OptionalKeys` unresolvable and dropped the non-required props. Removing the conditional lets the props object's member types be treated as ordinary (non-generic-object) types, so key partitioning resolves again.

Patch A then makes one small, well-commented change to `InferPropType`. When no default is present, it falls back to `V` instead of `D`, so the still-deferred `unknown extends V` / `IfAny` chain stays assignable to `V`. This is low-risk: when `D` is `unknown` (no default), `V` and `D` were effectively the same fallback before. Its test covers the issue's three shapes (shorthand, `{type}`, `{type, required: true}`), a `default: null` case, a plain `String` prop, and assignability to `{ bar: T }`.

Patch B goes further, and that adds risk:
- It rewrites `OptionalKeys` and `PublicOptionalKeys` as per-key `Pick`-based mapped types. This changes core key-partitioning logic that every component uses, and it isn't needed once `PropMethod` is fixed.
- It inserts a new early `InferPropType` branch that infers `V` from `PropType<infer V> | { type: PropType<infer V>; default?: undefined }`. That bypasses the existing `unknown extends V` / `IfAny` handling for every non-default prop, not just generic ones. Inference from the constructor union (e.g. `StringConstructor`, `NumberConstructor`, custom classes, `Function` types) could now yield different results, such as wrapper types vs. primitives or the `T & {}` form. This broad behavioral change on hot type paths is likely to cause subtle regressions elsewhere.

Patch B's tests are more extensive (`defineComponent`, `ExtractPropTypes`/`ExtractPublicPropTypes`, a `Function` prop), which is a real plus. But they don't offset the riskier, more invasive type-level changes. Patch A fixes the reported issue at its root with a minimal, targeted change and adequate tests, so it is the better patch.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
