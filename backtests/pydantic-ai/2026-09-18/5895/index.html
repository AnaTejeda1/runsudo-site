UsageLimits: add a per-request input-token (context size) limit

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches are behaviorally correct: each adds `per_request_input_tokens_limit`, enforces it against `count_tokens` output when `count_tokens_before_request=True` and against the response's provider-reported `input_tokens` otherwise, and neither accumulates it across requests. So correctness is essentially tied. The decision turns on tests and craft.

Tests: The core requirement in the issue is the per-request-vs-cumulative distinction. Patch A's `test_per_request_input_tokens_limit_not_summed_across_requests` proves this deterministically with a FunctionModel emitting exactly 30 input tokens per request under a limit of 50, then asserts the run succeeds AND `result.usage.input_tokens == 60` — i.e. cumulative (60) exceeds the limit while each request (30) does not. This exactly discriminates a correct per-request check from a buggy cumulative one. Patch B's analogous `test_per_request_input_tokens_limit_multiple_requests` relies on TestModel's implicit token counts and asserts only `call_count == 2` and `result.output is not None`, which is weak and could pass even under some incorrect implementations; it doesn't pin down that the cumulative total would have tripped the limit. Patch B does add a nice standalone unit test for its helper and a good post-response snapshot test, so its suite has breadth, but its central semantic test is the weaker of the two.

Craft: Patch A mirrors the existing error-message conventions the issue explicitly references — 'The next request would exceed the per_request_input_tokens_limit' for the pre-request path and 'Exceeded the per_request_input_tokens_limit' for the post-response path — matching how `input_tokens_limit` is worded in `check_before_request` vs `check_tokens`. Patch B uses a single 'Exceeded ...' message for both paths, diverging from that pre-request wording convention. Patch B's counterweight is genuinely good: a dedicated single-responsibility `check_per_request_input_tokens(int)` method that leaves the existing `check_before_request`/`check_tokens` signatures untouched, which is arguably cleaner scope-wise than A's threading of an optional `request_usage` param into two existing methods. That is a real point in B's favor.

On balance, with correctness tied, Patch A's more rigorous discriminating test for the issue's central 'not summed' semantics (priority 2) plus its closer adherence to existing error-message conventions outweighs B's cleaner method separation. A wins narrowly.

David's AICA here:

UsageLimits currently offers only cumulative limits: request_limit, tool_calls_limit, input_tokens_limit, output_tokens_limit, total_tokens_limit (pydantic_ai_slim/pydantic_ai/usage.py, UsageLimits). There is no way to limit the size of any single request's input -- the context window actually sent to the model.

With prompt caching now standard across providers (implicit on DeepSeek/GLM/Moonshot, explicit on Anthropic), cumulative input tokens is a poor guard:

  • Re-sent cached prefixes are cheap (e.g. DeepSeek bills cache reads at ~0.8% of input price), so a cumulative input cap mostly counts money that was never spent.
  • The thing that does hurt -- cost on cache misses and degraded model performance on very long contexts -- is per-request context size, which no limit covers.

Real-world failure that motivated this: our dogfooding PR-opening agent (Pydanty, running on team.pydantic.work) died with UsageLimitExceeded: Exceeded the input_tokens_limit of 500000 (input_tokens=517132) after 26 requests averaging ~20k context each. No single request was over ~30k tokens; the run was healthy and ~90% complete when the cumulative counter killed it. The limit we actually wanted to express was "no single request may exceed N tokens", with the cumulative cap relegated to a generous catastrophic ceiling.

Proposal: add per_request_input_tokens_limit: int | None = None (name open) to UsageLimits, checked against each request's input token count -- ahead of the request when count_tokens_before_request=True, otherwise against the provider-reported input_tokens of the response, mirroring how the cumulative limits are enforced today.

This also gives history processors / compaction strategies a principled trigger to align with: compaction keeps you under the per-request limit; the cumulative limits stay what they are good at (runaway-loop ceilings).

Summary

What was wrong

UsageLimits only offered cumulative token limits (input_tokens_limit, total_tokens_limit, etc.). With prompt caching now standard, cumulative input is a poor cost/health proxy — re-sent cached prefixes are cheap, so a cumulative cap counts money never spent and kills otherwise-healthy runs (the motivating failure: 26 healthy requests averaging ~20k context each tripped a 500k cumulative input_tokens_limit, even though no single request exceeded ~30k). There was no way to express "no single request may exceed N context tokens".

What I changed

pydantic_ai_slim/pydantic_ai/usage.py

  • Added per_request_input_tokens_limit: int | None = None to UsageLimits, with a docstring contrasting it against the cumulative input_tokens_limit and documenting both enforcement paths.
  • check_before_request(usage, request_usage=None) — new optional request_usage param; enforces the per-request cap against the counted request's input_tokens when counting ahead ("The next request would exceed…").
  • check_tokens(usage, request_usage=None) — new optional param; enforces the cap against a single response's input_tokens ("Exceeded…"). Both checks read only the single-request usage, never the cumulative RunUsage.

pydantic_ai_slim/pydantic_ai/_agent_graph.py

  • Pre-request path passes counted_usage (from model.count_tokens) to check_before_request.
  • _append_response passes response.usage to check_tokens.
  • Streaming (result.py) left unchanged: it calls check_tokens without request_usage, so per-request enforcement defers to the final response append (which always runs) — no mid-stream false accumulation, no slip-through.

Test evidence

Three new tests in tests/test_usage_limits.py, all failing before (TypeError: unexpected keyword argument 'per_request_input_tokens_limit') and passing after:

  • test_per_request_input_tokens_limit_exceeded — post-response path: input=60 vs cap 5 → UsageLimitExceeded: Exceeded the per_request_input_tokens_limit of 5 (request_input_tokens=60).
  • test_per_request_input_tokens_limit_not_summed_across_requests — the motivating scenario: two 30-token requests under a cap of 50 succeed with cumulative input_tokens == 60, proving per-request is not accumulated.
  • test_per_request_input_tokens_limit_before_request — count-ahead path: count_tokens_before_request=True → The next request would exceed the per_request_input_tokens_limit of 5 (request_input_tokens=60).
