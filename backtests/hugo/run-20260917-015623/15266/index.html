What the agent reported

The blast radius is clear now. Bumping mainImageVersionNumber changes the hash in every processed-image filename, which would break 42 filename assertions across 9 test files (avif/webp integration tests, resources/image_test.go, tpl/images, multihost, etc.), all of which would need their expected hashes regenerated.

Since this ticket is explicitly a judgment call ("Consider…", "I don't have a strong opinion either way") and the effect is broadly outward-facing (it forces a one-time full image-cache regeneration on every Hugo site on upgrade), I want to give you a recommendation rather than silently churn 42 tests on a coin-flip. Here's what I found.

What the version knobs are

resources/images/config.go:85-94:

// Increment to mark all processed images as stale. Only use when absolutely needed.
// See the finer grained smartCropVersionNumber.
mainImageVersionNumber = 1

// Increment a format's version number to mark all processed images targeting
// that format as stale ... finer grained than mainImageVersionNumber.
formatVersionNumbers = map[Format]int{
    AVIF: 1,
}

The value is folded into the cache-key hash at config.go:338-339, so bumping it invalidates every processed image of every format on every site. The codebase deliberately added the finer-grained smartCropVersionNumber and formatVersionNumbers knobs to avoid exactly that hammer — and the precedent commit e8fefc838 ("Force cache invalidation for AVIF target") chose the per-format knob rather than the global one.

What the two fixes actually touch

  • 9e7c978e6 — keep indexed PNG/GIF indexed through geometric filter chains → paletted (PNG/GIF) only.
  • 77856683d — transparent hex filter colors (e.g. images.Padding) + un-clamping images.Overlay/text from the source palette → filters using transparency/palette, which realistically means alpha/palette-capable outputs (PNG, GIF, WebP, AVIF). JPEG has no alpha and is unaffected.

Recommendation: don't bump mainImageVersionNumber

The affected surface is narrow (indexed images through filter chains + transparent filter colors), yet a global bump forces every site to regenerate all images and rewrites 42 test assertions. That's disproportionate, and it fails the code's own "only when absolutely needed" bar — the same reason e8fefc838 reached for the per-format knob instead.

If you do want affected users to pick up the fix automatically, the proportionate option is a formatVersionNumbers bump for the transparency/palette-capable formats (PNG, GIF, WebP — and AVIF is already at 1), which sidesteps the JPEG-and-everything-else regeneration and touches far fewer test hashes.

So, three options — tell me which and I'll direct the implementer + test-writer accordingly:

  1. Do nothing (my default given low impact + the "absolutely needed" guidance) — affected sites flush cache manually.
  2. Targeted: bump formatVersionNumbers for PNG/GIF (and WebP if you want the transparent-color path covered) — invalidates only the realistically affected formats.
  3. Global: bump mainImageVersionNumber to 2 — guaranteed coverage, but regenerates every image everywhere and requires updating ~42 test filename assertions.

Which would you like?
