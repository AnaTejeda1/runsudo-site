Make .Render take additional data

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches change the `Render` signature to `args ...any` the same way across the interface, the lazy provider, nopPage and testPage. When data is given, both pass it as the template context and otherwise fall back to the page. That is the issue's first option.

The difference is argument order. The issue writes the proposed form as `PAGE.Render [DATA] NAME`, with data before the name.

- Patch A accepts only `VIEW [CONTEXT]`. A call like `.Render (dict ...) "name"` fails in A with a cast error.
- Patch B accepts NAME, NAME DATA and DATA NAME. It finds the layout name by checking which argument is string-kinded, so it covers the issue's stated form and the alternative order. Its `reflect.Kind` check also accepts string types such as `template.HTML`.
- B has one ambiguity: when both arguments are strings, the first is treated as the name. That edge case would only bite string data in DATA-first order, and the doc comment documents the rule.

Tests:

- B's tests cover both orders, subdirectory views, scalar data, a safeHTML name, and error cases (no string argument, too many arguments, missing template).
- A's tests cover only name-first with a dict, plus two error cases.

B also updates the user docs for the new feature. That adds no risk.

Craft is comparable. B's `parseRenderArgs` helper is clean, and its error messages are informative.

On correctness against the issue's spec and on test breadth, B is the better fix.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The issue

View on GitHub

See https://gohugo.io/methods/page/render/#article
See #15076

PAGE.Render NAME

This has been discussed before.

  • The contract has always been that the templates that .Renders gets the data context as e.g. page.html, a page.Page.
  • We can only pass 1 argument to Go's template renderer, which I guess is the blocking reason for not having done this sooner.

So, if we want to do:

PAGE.Render [DATA] NAME

I'm guessing we have 2 top-level options:

  • We say that if DATA is set, we use that as the context passed to the templates,. else PAGE.
  • We somehow (e.g. by embeding it in a { DataAdditionalContext, Page } struct or putting it into the current context.Context) wrap the Page so you can do both .RelPermalink and .DataAdditionalContext (naming of the latter is just picked out of a hat without thinking too hard.
