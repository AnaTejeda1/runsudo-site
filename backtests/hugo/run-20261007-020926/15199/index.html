related: Add option to tokenize headings

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Patch B is the more correct and better-contained fix.

Patch B:
- Keeps the existing identifier-based `FragmentKeyword` entries and adds heading-word tokens alongside them. Exact identifier matching still works, including explicit `fragments` in search options and `fragmentrefs` pointing at heading IDs; its test covers this with p4/p5.
- Uses a distinct `headingTokenKeyword` type, so a word can never collide with a fragment ID.
- Makes `applyFilter` work with tokens: the type switch in `searchDate` collects token keywords, and `headingMatchesTokens` re-tokenizes heading titles for the filter.
- Tokenizes only heading titles, as the issue specifies. Definition terms keep exact matching, and a test asserts this.
- Handles HTML in titles by stripping tags and unescaping entities, and keeps Unicode combining marks inside words.
- Updates the docs with the exact wording from the issue.
- Tests cover both tokenize=true and tokenize=false, plus config decoding and the tokenizer itself.

Patch A has real correctness problems:
- When tokenize is on, it `continue`s past headings, so it no longer indexes their fragment identifiers. This silently breaks exact fragment-ID matching, for example `Related` with `fragments` options or `fragmentrefs` targeting headings.
- Its tokens are created with `stringToKeyword`, which produces `StringKeyword`. But the `applyFilter` path in `searchDate` only collects `kw.(FragmentKeyword)`, so `ff.words` is never populated. Heading filtering with tokenize therefore does not work as intended, and its own ApplyFilter test looks unlikely to pass for the right reason.
- It expands scope beyond the issue: tokenization for basic indices through `ToKeywords`, plus a new `MinTokenLength` option. This adds risk without being asked for.
- It adds no documentation and includes whitespace churn in an existing test file.

On correctness, scope and tests, B is clearly better.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

(bool) Whether to split multi-word values into individual keywords for indexing and matching.
