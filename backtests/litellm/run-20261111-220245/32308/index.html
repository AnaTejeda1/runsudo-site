Both patches make the four independent tests pass, so the decision rests on root cause, scope, and risk.

The issue

View on GitHub

What happened?

enable_weighted_failover is meant to retry a failed request inside its model group before falling back to a different group. When the model group also has deployment affinity enabled (session_affinity or another DeploymentAffinityCheck-based check), the retry can lose to a stale affinity pin and fall through to cross-group fallback even though a healthy sibling deployment exists.

Picture a model group with two deployments, A and B, weighted failover on, and session affinity on. A session's first request lands on A and pins there. A then fails. Weighted failover correctly works out that B is healthy and not on cooldown, so it should retry on B. But before the retry actually picks a deployment, the affinity callback runs first, sees the session is still pinned to A, and narrows the candidate list down to just A. Only after that does the exclusion filter drop A, leaving nothing, so the retry errors out and weighted failover gives up. The caller then falls through to the cross-group fallback, or fails outright if none is configured, instead of landing on the healthy B that was right there.

This defeats the purpose of weighted failover for any model group that also sets session_affinity or another affinity-based pre-call check. The router works out that a healthy alternative exists, then throws that information away by running the affinity filter before the exclusion filter instead of after.

This is the same shape of bug as #29760 and the path fixed in #31679 for /v1/messages: an exclusion list computed for a retry gets applied after a different filter has already collapsed the candidate set, so the exclusion runs too late to matter.

Expected behavior

When weighted failover retries a request with a deployment excluded, the exclusion should apply before the affinity callback narrows the candidate list, the same way cooldown and blocked-deployment filtering already do.

Steps to Reproduce

One model group with two deployments and session affinity on. Uses mock_response so no real keys are needed.

model_list:
  - model_name: claude-group
    litellm_params:
      model: anthropic/claude-sonnet-4-5
      mock_response: "served by A"
    model_info:
      id: dep-a
  - model_name: claude-group
    litellm_params:
      model: bedrock/anthropic.claude-sonnet-4-5
      mock_response: "served by B"
    model_info:
      id: dep-b

router_settings:
  routing_strategy: simple-shuffle
  enable_weighted_failover: true
  optional_pre_call_checks: ["session_affinity"]
  1. Send a request with a session id. It lands on dep-a and pins there.
  2. Make dep-a fail (point it at a bad key, or use a mock_response that raises), then send the same session id again.
  3. Expected: the retry lands on the healthy dep-b. Actual: the retry errors out internally and falls through to whatever fallback is configured, or fails if none is.

Relevant log output

With --detailed_debug, async_get_healthy_deployments narrows to the affinity-pinned deployment first, then the weighted-failover exclusion filter removes it, leaving an empty candidate list and a RouterRateLimitError that _maybe_run_weighted_failover swallows.

Version

v1.92.0 (present since weighted failover landed in v1.86.0)

Proposed fix

In async_get_healthy_deployments, the weighted-failover exclusion filter runs last in the filter pipeline, after the affinity callback. Moving it to run right after the existing blocked-deployment filter, before the affinity callback, makes the affinity check itself respect the exclusion instead of pinning to a deployment that has already been ruled out. Happy to send the PR.
