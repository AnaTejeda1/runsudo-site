Voice: add_audio(None) doesn't end the STT session, so the pipeline waits ~1000s for EVENT_INACTIVITY_TIMEOUT

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches send a final commit, tolerate the empty-buffer error, and wait for outstanding transcripts, but they differ in how the session actually ends. Patch B's `_finish_input` commits only when server VAD reported uncommitted speech, waits for pending `committed` items to get their transcripts (bounded by a 10 s deadline plus a 0.3 s quiet-period), and then closes the websocket itself so `_handle_events` receives `WebsocketDoneSentinel`. This is exactly the shape the issue proposes and does not depend on the server replying to anything after end of input. Patch A instead unconditionally sends `commit` + `clear` from inside `_handle_events` and only breaks once it has seen `input_audio_buffer.cleared` and all pending transcripts; it never closes the socket on its own. If the server does not answer the clear (the issue's own repro server, or any deviation in error code / event_id matching), A falls back to the full 1000 s `EVENT_INACTIVITY_TIMEOUT` and then raises an error, which is the very symptom the issue reports plus a new failure. The independent repro-server test confirms this: A still hangs past 5 s while B passes; A passes the four tests where the fake server cooperates. A also widens behaviour in risky ways beyond the ask: any `conversation.item.input_audio_transcription.failed` event now kills the whole session (previously ignored, and this applies mid-session, not just at EOF), and a server-side close after EOF becomes a hard error unless `close()` was called. B's additions are confined to end-of-input bookkeeping; its main cost is a small fixed 0.3 s grace delay on every EOF and reliance on `speech_started` to decide whether to commit, which matches the issue's suggested condition. On tests, both add real websocket-server tests through the public pipeline that would fail on base (the stream would hang) and pass after; A's matrix is broader but is tailored to A's commit/clear handshake. Correctness and robustness favour B decisively.

The issue

View on GitHub

Please read this first

  • Have you read the docs? Yes.
  • Have you searched for related issues? Yes. #1686 / #1687 documented None as the end-of-stream signal. #4995, #4259, #4825 and #4343 cover close during setup, dispatcher start, cancellation and close errors, not end of input.

Describe the bug

StreamedAudioInput.add_audio(None) is documented as "indicates the end of the stream". With OpenAISTTModel, the pipeline doesn't actually end: result.stream() keeps waiting for about 16.7 minutes and the STT websocket stays open.

In src/agents/voice/models/openai_stt.py, _stream_audio just breaks when it reads None. It sends no input_audio_buffer.commit, doesn't close the websocket, and doesn't tell _handle_events. After that, nothing on the client side ends the session:

  • _handle_events finishes only on WebsocketDoneSentinel (socket closed) or after EVENT_INACTIVITY_TIMEOUT = 1000 seconds without events.
  • So transcribe_turns() doesn't finish, _run_multi_turn never reaches output._done(), and session_ended is never emitted.

Consequences:

  1. async for event in result.stream() hangs for ~1000 s after the caller has said the input is over, and the websocket stays open for that time.
  2. Because no commit is sent, a final utterance that server VAD hasn't closed yet (for example push-to-talk released mid-phrase) is never transcribed.

Debug information

  • Agents SDK version: main at c467732e

    def __init__(self):
        self.incoming: asyncio.Queue[str] = asyncio.Queue()
        self.sent: list[dict] = []
        self.closed = asyncio.Event()
        self.incoming.put_nowait(json.dumps({"type": "session.created"}))

    async def __aenter__(self): return self
    async def __aexit__(self, *a): self.closed.set()

    async def send(self, payload: str):
        msg = json.loads(payload)
        self.sent.append(msg)
        if msg["type"] == "session.update":
            await self.incoming.put(json.dumps({"type": "session.updated"}))
        if msg["type"] == "input_audio_buffer.append" and sum(
            m["type"] == "input_audio_buffer.append" for m in self.sent) == 2:
            # server VAD detects end of speech and transcribes the turn
            await self.incoming.put(json.dumps({
                "type": "conversation.item.input_audio_transcription.completed",
                "item_id": "item_1", "transcript": "hello there"}))

    async def close(self): self.closed.set()

    def __aiter__(self): return self
    async def __anext__(self):
        get = asyncio.create_task(self.incoming.get())
        closed = asyncio.create_task(self.closed.wait())
        done, _ = await asyncio.wait({get, closed}, return_when=asyncio.FIRST_COMPLETED)
        if closed in done:
            get.cancel(); raise StopAsyncIteration
        closed.cancel(); return get.result()

Expected behavior

After add_audio(None), pending speech is committed and transcribed, then the STT session closes, session_ended is emitted and result.stream() finishes.

A possible fix: on None, commit the buffer if speech was detected but not yet committed (committing an empty buffer returns a server error, which the listener currently treats as fatal), then close the websocket once the committed items have their transcripts or after a short grace period, so _handle_events receives WebsocketDoneSentinel. I'm happy to share a patch if it helps.
