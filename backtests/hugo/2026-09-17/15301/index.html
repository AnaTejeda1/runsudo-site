Both patches document the http.urls override behavior well, and neither changes the override-skip itself (correct, since the maintainer calls that behavior pragmatically right). The issue explicitly invites 'see if this can be improved further,' and Patch B answers that: it identifies and closes a genuine bypass of the *same* SSRF-to-internal threat class the issue is about. Because newSecureBaseTransport clones http.DefaultTransport (which honors ProxyFromEnvironment), a set HTTP_PROXY silently routes GetRemote through the proxy, so CheckAllowedHTTPAddress only validates the proxy dial and never the true destination — a real hole the dial-time check left open. Patch B disables env proxies by default (base.Proxy=nil, all dials validated), gates them behind a new documented, versioned proxyFromEnvironment flag, and carries the proxy decision per-request in context so direct dials — even to the proxy's own address — are still validated. It backs this with substantive tests that fail-before/pass-after: default ignores the proxy and fetches directly, enabled dials the loopback proxy under the hardened policy, and enabled-but-direct destinations (including the proxy's own IP) are still denied. It also updates the serialization tests (ToTOML/docs.yaml) consistently. Patch A is clean, minimal, and exactly scoped, and its docs are arguably slightly richer prose, but it is documentation-only: it adds nothing to the codebase's actual defenses and no tests. Weighing correctness first, B resolves more of the root security concern with verifiable tests; its costs are real but bounded — larger scope and a behavioral change (proxies off by default, potentially breaking corporate builds) — which narrows the margin but does not overcome B's substantive, tested security improvement in the same threat domain.

In d6e6f9e500eebdeae8e28de830fff2e3bfc7d534 (unreleased) we added a dial-time URL validation to catch URLs that's valid according to the whitelist but that resolves to a loopback, private or link-local IP addresses. That check is skipped it if the user has a custom security.http.urls setup, as it would not make sense to block local development servers.

See CheckAllowedHTTPAddress.

This has been reported by @Reload3d as a potential security issue, and while I think the current behaviour is the pragmatic correct approach, I'm creating this issue for visibility and to see if this can be improved further (e.g. better documentation).

Summary

What the report flagged: The dial-time address check (CheckAllowedHTTPAddress, added in d6e6f9e) blocks connections resolving to loopback/private/link-local IPs under the default security.http.urls allowlist, but is silently skipped when a user customizes security.http.urls. The reporter deemed the behavior pragmatically correct and asked for improved visibility/documentation, not a logic change.

What I found: The Go code (config/security/securityConfig.go) already carries thorough doc comments explaining both the address check and the default-only skip logic, and the behavior is already covered by existing tests (TestCheckAllowedHTTPAddress, TestSecureBaseTransportBlocksInternalAddress, and hugolib/securitypolicies_test.go). The actual gap was user-facing documentation: docs/content/en/configuration/security.md described http.urls only as a URL allowlist and never mentioned the resolved-address check or that customizing http.urls opts out of it.

What I changed (documentation only, docs/content/en/configuration/security.md):

  1. Expanded the http.urls config entry to note that, at its default value, Hugo also performs a remote-address-validation check at connection time, and that customizing the setting disables that check — with an intra-page link.
  2. Added a new ## Remote address validation section explaining the SSRF/DNS-rebinding rationale, exactly what gets blocked (loopback, private, link-local, non-public, incl. cloud metadata endpoint), the default-only enforcement, and how to intentionally allow an internal address.

Test evidence: No production logic or tests were changed, so the existing behavior tests remain valid and no new gate applies. The reviewer verified every documented claim against the code (securityConfig.go:227-256, the skip condition at line 232, isPublicAddr at line 279, and the dial-hook wiring in create.go:153-167), confirmed the anchor slug resolves, confirmed markdown formatting consistency, and confirmed no Go/test files were touched.
