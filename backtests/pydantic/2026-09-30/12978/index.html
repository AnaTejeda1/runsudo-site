In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches make the same two code changes in pydantic/mypy.py. First, they register `_RootModelMetaclass` in `get_metaclass_hook`, so mypy's dataclass_transform spec is reset and the plugin handles RootModel classes. Second, they bypass the 'don't generate __init__ if one exists' guard when the class is `pydantic.root_model.RootModel` itself. That lets the plugin-generated `__init__` (untyped unless `init_typed` is set) replace RootModel's hand-written typed `__init__`. This fixes the root cause: `RootModel[float]('1.0')` and its subclasses now follow the same plugin settings as BaseModel fields. The only code difference is `self._cls.info.fullname` (A) versus `self._cls.fullname` (B), which are equivalent for a ClassDef. On tests, both add cases for a parametrized alias (`RootModel[float]`) and a subclass, with expected outputs for all three configs. Under plugin_ini (init_typed unset) there are no errors. Under the default configs the errors remain, so the tests would fail before the change and pass after. A also includes a BaseModel control case (`FloatModel(f='1.0')`) that shows parity with the issue's example. B adds an explanatory comment in the test and a clearer inline comment on why RootModel is excluded. A updates the docstrings. These are cosmetic, offsetting differences; correctness, coverage, and scope are the same.

Description

The below example code (named foo.py) passes when running python foo.py as the input "1.0"-string gets converted to float. However, running mypy foo.py (with or without --strict) gives the following error:

foo.py:11: error: Argument 1 to "RootModel" has incompatible type "str"; expected "float"  [arg-type]
Found 1 error in 1 file (checked 1 source file)

I would expect the BaseModel-fields and the RootModel-field to behave the same in this case. That is, if the value can be converted – either via a custom made validator or through the conversion table – then mypy should not raise an error.

Example Code

import pydantic


class Foo(pydantic.BaseModel):
    f: float


RFoo = pydantic.RootModel[float]

f = Foo(f="1.0")
rf = RFoo("1.0")

assert isinstance(f.f, float)
assert isinstance(rf.root, float)
assert f.f == rf.root

What the agent reported

I fixed this in the mypy plugin (pydantic/mypy.py). With the plugin on, RootModel[float]("1.0") now type-checks the same way Foo(f="1.0") does. A new regression test fails without the fix and passes with it. None of this is committed.

What was wrong. With the plugin's default settings, it gives model constructors Any-typed arguments, which is why Foo(f="1.0") is accepted. Two things kept RootModel from getting the same treatment:

  1. Direct use, RootModel[float](...): RootModel has its own __init__(self, /, root: RootModelRootType = ...). The plugin never replaces an existing __init__, so mypy always checked root against float.
  2. Subclasses, class Sub(RootModel[float]): these hit the same error. RootModel uses a special type-checking-only metaclass that carries its own @dataclass_transform. The plugin switches that off on the normal model metaclass but not on this one. So mypy's own dataclass handling built a strictly typed __init__(self, root: float) for subclasses.

Without the plugin, mypy rejects all three calls, including Foo(f="1.0"). That is already consistent, so I left that mode alone.

What I changed.

  • Added ROOT_MODEL_METACLASS_FULLNAME = 'pydantic.root_model._RootModelMetaclass'. get_metaclass_hook now switches off dataclass_transform for it too, just as it already did for the normal metaclass.
  • add_initializer now also generates __init__ for RootModel itself. So root is Any by default, and typed when init_typed = True or the model is strict, like any other field.
  • Tests: I added the report's scenario (a BaseModel with a float field, RootModel[float], and a RootModel[float] subclass, each called with '1.0') to tests/mypy/modules/root_models.py. I updated the expected outputs:
  • mypy-plugin_ini: no errors on those lines.
  • mypy-default_ini and pyproject-default_toml (no plugin): all three lines error, which is what happens today.

Test evidence.

  • mypy isn't installed in the project environment and installing packages was blocked, so ./bt-test skips all 53 mypy tests. I ran them with the locked version (mypy 1.18.2) taken from the local uv cache through PYTHONPATH, using pytest tests/mypy --test-mypy.
  • Without the fix: the new mypy-plugin.ini / root_models.py test fails, and the only difference is the two RootModel / subclass arg-type errors. The two no-plugin configurations pass.
  • With the fix: 48 passed, 5 failed. Those same 5 also fail on the untouched checkout: pydantic_settings.py under four configurations and strict_equality.py.
  • By hand, I confirmed that init_typed = True and strict=True still report the error, and that results without the plugin are unchanged.
  • ./bt-test tests/test_root_model.py tests/mypy: 78 passed, 53 skipped.

Side effects. Only mypy's view of RootModel changes; runtime and pyright are unaffected. One edge case gets stricter: with init_forbid_extra = True, calling RootModel[dict[str, int]](a=1) directly is now rejected, even though it works at runtime. Subclasses already behaved this way. No test covers that case, or the init_typed = True case; I checked the latter by hand but didn't add a test for it.

Requirements:

  1. Passing a convertible value to RootModel[float] should not raise [arg-type] under mypy: done when the plugin is on. Covered by the regression test above.
  2. BaseModel fields and the RootModel root should behave the same: done for plugin mode, and it now includes RootModel subclasses, which had the same bug. Without the plugin they already matched, since both error; the test outputs for that mode show this.
  3. The same should hold with or without --strict: this flag didn't affect the result either way. With the plugin, the Any typing follows init_typed and each model's own strict setting, the same as for BaseModel fields.
