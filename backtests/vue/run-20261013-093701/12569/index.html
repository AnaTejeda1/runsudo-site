Issue #12569 Merged fix PR # Run 13 Oct 2026 · run-20261013-093701 vuejs/core

Custom directive's unmounted event is not triggered on v-for element

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

**Root cause.** In the issue, the `<h1>` has a custom directive and children, so `transformElement` forces it into a block. Because it is a block, it skips the `NEED_PATCH` flag. When the `v-for` source is constant, the stable-fragment path in `transformFor` then turns it back into a plain vnode. The result is a vnode with no patch flag, which never enters the parent's `dynamicChildren`, so its directive unmount hook never runs. Both patches fix the reported symptom.

**Patch A** adds a post-hoc check in `vFor.ts`. When a child becomes a plain vnode, it adds `NEED_PATCH` if the vnode has directives or a static `ref`/`onVnode*` prop key. This is targeted and works for unmount and update hooks. However, it accepts that the element is no longer a block. That defeats the reason the block was forced in the first place: making directive and vnode `beforeUpdate` hooks run before children update. With Patch A, a stable `v-for` element with a custom directive or an inline `@vue:before-update` will call `beforeUpdate` after its children have patched. A's own test only checks that an `updated` call happens, not the ordering. A also re-derives the flag by pattern-matching the props object (`startsWith('onVnode')`), which is somewhat ad hoc.

**Patch B** has `buildProps` record two facts on the `VNodeCall`:
- `needsPatch`: the element would have needed `NEED_PATCH` had it not been forced into a block.
- `isBlockRequired`: the block exists for `beforeUpdate` ordering (a custom directive with children, or an inline before-update hook).

`transformFor` then keeps such children as blocks inside the stable fragment, which keeps them tracked and preserves hook ordering. It adds `NEED_PATCH` only when the child really becomes a plain vnode. For the issue's exact case (`h1` with `v-focus` and children), B keeps the block, so unmount is tracked and `beforeUpdate` ordering is correct.

B also:
- handles the camelized `vue:beforeUpdate` spelling;
- moves `hasRef` detection ahead of the constant-prop early return, so setup-const function refs are tracked and get called with `null` on removal.

B's tests cover the compiler flags and runtime behaviour, including `beforeUpdate` running before child updates, which A cannot satisfy.

**Risk.** B is more invasive. The `hasRef` move could change patch flags in other compiler output. Still, the design carries the information from the right place rather than guessing it later, and it addresses the full semantics.

**Verdict.** On correctness, B is the more complete root-cause fix, so B wins.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
