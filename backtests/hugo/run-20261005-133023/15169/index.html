Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Patch B fixes the root cause. TypeScript and VS Code reject non-relative entries in `paths` when `baseUrl` is unset, so B adds a `./` prefix to every entry that does not already start with `../`. The generated config stays valid and keeps the same mapping: `./*` still lets VS Code resolve bare imports like `imp1/index.js` against the assets dir. It also covers sub-roots such as `/a/assets/sub`, which would otherwise produce the non-relative `sub/*`. B's unit test checks parent-relative, same-dir and sub-dir cases. Its integration test reads the generated `assets/jsconfig.json` and asserts `./*`; it would fail before the change. Updating the checked-in `docs/assets/jsconfig.json` is consistent with the change. Patch A takes a different route and skips the root equal to `dir`. In the common single-root case this produces no jsconfig at all, which removes the lint warning but also removes the path mapping that gave editor resolution for non-relative imports. That masks the symptom rather than fixing the format. A also leaves sub-roots non-relative (e.g. `sub/*`), so the same warning can still appear. Its test only asserts a nil config, which checks the suppression rather than validity. B is more correct and better tested.

The issue

View on GitHub

When building a site that calls js.Build, the assets/jsconfig.json file looks like this:

{
 "compilerOptions": {
  "paths": {
   "*": [
    "*"
   ]
  }
 }
}

VS Code lints line 5 as follows:

Non-relative paths are not allowed when 'baseUrl' is not set. Did you forget a leading './'?
