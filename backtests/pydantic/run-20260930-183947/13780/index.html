Concurrent TypeAdapter construction raises RuntimeError on free-threaded Python

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the root cause the same way: they iterate over `vars(typ).copy()` in `_decorator_infos_for_class`, which is atomic, and they snapshot class namespaces in `LazyLocalNamespace.data`. Patch A is slightly broader. Its `_snapshot` helper also copies plain dicts, not just mapping proxies. It also hardens `collect_known_metadata`, a low-risk change. The decisive differences are tests and scope. Patch A's tests are deterministic and run on every interpreter. One uses a `__hash__` side effect to mutate a mapping proxy's backing dict during iteration. The other uses a `__class__` property, triggered by the `isinstance` checks during decorator collection, to add a class attribute mid-iteration. Both would raise 'dictionary changed size during iteration' before the fix and pass after it. Patch A also adds the issue's concurrent reproduction. Patch B's tests are all skipped unless the build is free-threaded. So in ordinary CI they give no regression protection, and even on free-threaded builds they are probabilistic. Patch B also rewrites `BaseModel.model_rebuild` in `main.py`. Instead of deleting non-mock core schema, validator and serializer attributes, it now calls `set_model_mocks` only when `already_complete`. That behavioral change is unrelated to the reported TypedDict/TypeAdapter race. It adds risk and makes the fix harder to read. Patch B's conftest addition is fine but only supports those skipped tests. Correctness on the reported issue is equivalent. Patch A wins on its reliable, deterministic tests and its tighter, lower-risk scope.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Description

Constructing separate TypeAdapter instances concurrently for the same new TypedDict can raise RuntimeError: dictionary changed size during iteration on free-threaded Python.

A full run produced 91 failures in 800 attempts with the GIL disabled and none with PYTHON_GIL=1. It also reproduces on Pydantic main at 1c8a330acc3077e77da64e3672c7c875fb4c6eaa.

Lazy annotation evaluation adds __annotations_cache__ while another thread iterates vars(typ).items() in _decorator_infos_for_class.

Example Code

from __future__ import annotations

import threading
from concurrent.futures import ThreadPoolExecutor

from pydantic import TypeAdapter
from typing_extensions import TypedDict


def run_round() -> None:
    class Record(TypedDict):
        value: int

    for index in range(1000):
        setattr(Record, f'metadata_{index}', index)

    barrier = threading.Barrier(8)

    def build(_: int) -> None:
        barrier.wait()
        TypeAdapter(Record).validate_python({'value': '42'})

    with ThreadPoolExecutor(max_workers=8) as executor:
        list(executor.map(build, range(8)))


for _ in range(100):
    run_round()

The synthetic attributes only widen the iteration window. They are not modified after the threads start.
