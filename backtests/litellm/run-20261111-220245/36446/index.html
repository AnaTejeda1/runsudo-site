The issue

View on GitHub

What happened

POST /config/update silently wipes router_settings.model_group_alias to {} on any router-settings edit that doesn't explicitly include the alias map — e.g. editing routing_groups or changing a routing_strategy through the Admin UI. API calls that depend on the alias (security → luna, etc.) then return 400 Invalid model name until the alias is manually re-added. It looks like the aliases get "wiped periodically"; in reality every router-settings save wipes them.

Root cause

In proxy_server.py, update_config() builds the router-settings update like this:

# proxy_server.py ~L14604-14608 (v1.95.0 and current main)
if config_info.router_settings is not None:
    existing = await _read_section("router_settings")
    updates = config_info.router_settings.dict(exclude_none=True)   # <-- bug
    new_router_settings = {**existing, **updates}                    # shallow merge
    await _upsert_section("router_settings", new_router_settings)

config_info.router_settings is UpdateRouterConfig, whose model_group_alias field has a Pydantic default of {} — not None (litellm/types/router.py):

class UpdateRouterConfig(BaseModel):
    model_group_alias: Optional[Dict[str, Union[str, Dict]]] = {}   # default is {}, not None

.dict(exclude_none=True) only drops None values, so the default {} is serialized into updates even when the caller never sent model_group_alias. The shallow merge {**existing, **updates} then overwrites the real alias map with {}.

The same pattern affects general_settings (~L14532) for any field defaulting to {}/[].

Reproduce

from litellm.proxy._types import ConfigYAML

# UI edits routing_groups and never sends model_group_alias
payload = {"router_settings": {"routing_groups": [
    {"group_name": "luna", "routing_strategy": "latency-based-routing", "models": ["luna"]}
]}}
updates = ConfigYAML(**payload).router_settings.dict(exclude_none=True)

existing = {"routing_groups": [], "model_group_alias": {"security": "luna"}, "timeout": 6000}
merged = {**existing, **updates}

print(merged["model_group_alias"])   # -> {}   (alias wiped)
print("model_group_alias" in updates)  # -> True (the {} default leaked in)

End-to-end: set model_group_alias: {"security": "luna"} via /config/update, then send a second /config/update that only touches routing_groups — GET /config now shows model_group_alias: {}.

Expected behavior

Fields the caller did not send should not overwrite existing values. A sent-but-empty map ({}) is ambiguous with "not sent" because of the Pydantic default, so the default should not be serialized into the update payload.

Suggested fix

Drop Pydantic defaults from the serialized update so they can't clobber existing values:

updates = config_info.router_settings.dict(exclude_none=True, exclude_defaults=True)

Verified: with exclude_defaults=True, a payload omitting model_group_alias produces updates with keys ['routing_groups'] only, and the shallow merge preserves {"security": "luna"}. (This is the workaround we run in-container.)

The general_settings handler has the identical pattern and likely needs the same treatment for any {}/[]-defaulted field.

Related

  • #31836 covers a different model_group_alias disappearance (DB JSON-string vs dict on reload). This one is the /config/update write path clobbering it via the Pydantic-default leak — distinct mechanism, same symptom.
  • #31308 (retry_policy dropped via /config/update) is a similar "field silently lost on update" class of bug, but that one was a missing Pydantic field, not a default leaking through exclude_none.

Environment

  • LiteLLM: v1.95.0 (ghcr.io/berriai/litellm:latest), reproduced against main and the v1.95.0 tag
  • Postgres-backed config (store_model_in_db: true), config edited via Admin UI / /config/update
