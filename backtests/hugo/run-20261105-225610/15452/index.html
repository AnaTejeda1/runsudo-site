Both patches make the identical core change in tpl/transform/transform.go: Emojify now returns string instead of template.HTML, so output flows through html/template's contextual escaping, and both update the existing unit-test expectations accordingly. The independent tests confirm both resolve the issue (both failing base tests pass under A and B). The differences are in tests, docs, and scope. Patch A adds an integration test (TestEmojifyEscapesUntrustedInput) that exercises the exact scenario in the issue — an untrusted title with a script tag piped through transform.Emojify and the emojify alias — asserting it is escaped while emoji replacement still works, and that explicit safeHTML still produces raw markup. That test would fail before the change and pass after, which is exactly what criterion 2 asks for. Patch B adds no new behavioral test; its only test change beyond the type update is a cosmetic reformatting of an unrelated Markdownify assertion, which is pure churn. Patch A also updates the documented returnType in the Emojify docs page from template.HTML to string; the issue explicitly notes the return type is 'clearly documented', so leaving the docs stale (as B does) would leave documentation contradicting the new behavior. On scope, A's extras are directly tied to the ask, while B's extra is unrelated noise. A is the better fix.

The issue

View on GitHub

I got this mailed as a security report, and I'll create this as a security hardening issue to set the boundaries: I'll label this as a security hardening issue, but I'm not creating a GitHub Security Advisory/CVE for (that's surprisingly lot of work, but that's not the reason).

The gist of it is in:

{{ .Title | transform.Emojify }}

transform.Emojify returns template.HTML and would mark the potentially unsafe .Title (from potentially untrusted content) as safe. But the templates are marked as trusted, the transform.Emojify's return type is clearly documented, and we have plenty of other cases where a user can create unsafe markup. E.g. the above is technically similar to:

{{ .Title | safeHTML }}

Thanks to @Reload3d for reporting this issue.
