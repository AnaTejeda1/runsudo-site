Both patches satisfy the issue's stated expected behaviour: under default eager setup a client session.update that cannot be applied now yields a client-visible invalid_request_error, and no second setup is sent. Description

With the default eager setup behavior, a Gemini Live voice session can connect and exchange audio while the client's initial session.update instructions and tools are discarded. The client receives no error explaining that its configuration was not applied

async_realtime sends the provider setup before starting the bidirectional relay. When the client sends session.update, the Gemini transformer sees that setup has already been sent and returns an empty list. Dropping a second setup avoids a provider disconnect, but it also silently loses the client's first configuration request

The normal path emits only a debug log. A later session.update with turn_detection.create_response set false now logs a warning, and every other dropped update stays at debug. The client still receives no error. A caller can therefore believe its instructions and functions are active when they are absent from the provider session

Config

The affected path is the OpenAI-compatible realtime WebSocket adapter for Gemini/Vertex Live, with LITELLM_GEMINI_LIVE_DEFER_SETUP unset or false. The adapter-only reproduction below needs no provider credentials or network access

The documented workaround is LITELLM_GEMINI_LIVE_DEFER_SETUP=true. That makes the first client session.update supply the initial provider setup. This report acknowledges that existing capability and concerns silent configuration loss under the default behavior

LiteLLM Version

Reproduced locally in a downstream build based on 1.107.0. The relevant behavior was also checked in upstream main at 18831b818c596f8b46091681cc2db65495799d52. A pristine upstream proxy has not been exercised end to end for this report
