The issue

View on GitHub

Summary

reject_unsupported_runtime_toolsets (pydantic_ai/durable_exec/_runtime_toolsets.py) aggregates the offending leaves into a set of kinds and renders only kind labels, so the resulting UserError says FunctionToolset cannot be passed to run(toolsets=...) at runtime with <engine> no matter how many toolsets are in play, and never identifies the toolset (id, type, or position) that actually failed the check.

That is fine when the user really did pass one toolset per-run. It is actively misleading when the rejected leaf is reached by descending through a tree the user did not assemble by hand.

Repro

from pydantic_ai.durable_exec._runtime_toolsets import reject_unsupported_runtime_toolsets
from pydantic_ai.toolsets import FunctionToolset

def a() -> str: return 'a'
def b() -> str: return 'b'

reject_unsupported_runtime_toolsets(
    [FunctionToolset(id='search-tools', tools=[a]), FunctionToolset(id='billing-tools', tools=[b])],
    unsupported_kinds=frozenset({'function', 'mcp', 'dynamic'}),
    engine='Prefect',
)
pydantic_ai.exceptions.UserError: FunctionToolset cannot be passed to `run(toolsets=...)` at runtime with
Prefect, because toolsets that execute their own tools or resolve dynamically must be registered for durable
execution when the agent is constructed. ...

Neither 'search-tools' nor 'billing-tools' is named, and the same message is produced whether one or both are at fault. The same message reaches users through BaseDurabilityCapability._reject_runtime_toolsets, which passes leaves it collected itself — at that point the user has no way to map the message back to a toolset at all.

Why it matters (the debugging story)

I hit this in a third-party durable engine built on BaseDurabilityCapability (pydantic-ai-absurd, issue / fix). A toolset contributed by a capability via AbstractCapability.get_toolset() was rejected at run time. The message said FunctionToolset cannot be passed to run(toolsets=...) at runtime — but:

  • the toolset was not passed at runtime, it was contributed at construction, and
  • the named FunctionToolset was registered; the unregistered node was the CapabilityOwnedToolset wrapper around it, which reject_unsupported_runtime_toolsets then descended through, classifying the inner (registered) toolset and naming it in the error.

Because the message names a kind rather than an instance, every signal it gives points away from the real cause. Naming the offending leaf (id='demo-tools') would have made it obvious in seconds that the reported toolset was one the engine had already registered, i.e. that the collection walk — not the user's code — was wrong.

Suggested change

Include the offending leaves in the message, e.g.:

FunctionToolset 'demo-tools' cannot be passed to `run(toolsets=...)` at runtime with Prefect, because ...

falling back to the type name when a leaf has no id, and listing each offender when there are several.

Related, lower priority: the two walks are still asymmetric

In BaseDurabilityCapability, registration uses visit_and_replace (_register_toolsets, leaf-only: WrapperToolset.visit_and_replace delegates through) while the construction snapshot in _reject_runtime_toolsets uses apply, which additionally visits CapabilityOwnedToolset because it overrides apply to visit itself. The built-in engines are correct today because the apply snapshot is a superset of the registered leaves and #6623 added an explicit isinstance(leaf, CapabilityOwnedToolset) skip for the freshly-built wrapper case.

It works, but it is a sharp edge: any engine (or future framework wrapper node that visits itself in apply) that snapshots construction-time toolsets with a different walk than the one used for collection gets a false rejection reported against an innocent inner toolset — exactly the failure above. Collecting candidates with the same traversal used to register, or documenting the invariant on BaseDurabilityCapability, would make the contract explicit for out-of-tree engines.

Versions checked: main @ ed0f40c0e, and pydantic-ai==2.14.1.

Summary

What was wrong

reject_unsupported_runtime_toolsets (pydantic_ai_slim/pydantic_ai/durable_exec/_runtime_toolsets.py) collected offending toolsets into a set of kinds and rendered only kind labels via a _KIND_LABELS lookup. The resulting UserError said e.g. FunctionToolset cannot be passed to run(toolsets=...) at runtime with <engine> regardless of how many toolsets were involved or which one failed — never naming the offending toolset by id, type, or position. This is actively misleading when the rejected leaf is reached by descending a toolset tree the user didn't hand-assemble (e.g. a CapabilityOwnedToolset wrapper), because every signal in the message points away from the real cause.

What I changed

  • pydantic_ai_slim/pydantic_ai/durable_exec/_runtime_toolsets.py: collect now accumulates the offending leaf objects (in traversal order) instead of kinds. The message builds labels from each leaf's existing .label property — which yields FunctionToolset 'demo-tools' when the leaf has an id, or bare FunctionToolset when it doesn't — joined with , so every offender is listed. Duplicates are removed by object identity (id(leaf)), so two distinct un-named toolsets both still appear. The rest of the message, the opt-out suffix logic, and the signature/docstring are unchanged. The now-unused _KIND_LABELS dict was removed.
  • tests/test_runtime_toolsets.py (new): regression test mirroring the report's repro — two named toolsets (both 'search-tools' and 'billing-tools' appear), a single named toolset ('demo-tools'), and the no-id fallback to the bare type name.
  • tests/test_prefect.py, tests/test_dbos.py, tests/test_temporal.py: updated the pre-existing rejection assertions whose toolsets carry ids so they now assert the id-bearing message (runtime_mcp, runtime_dynamic, runtime, iter_fn, per_run_fn, iter_mcp). These are strengthened — each checks the id in addition to the type. The three bare-name assertions (toolsets built with no id) were left unchanged, as their .label output is still bare.

Test evidence
