SSR hydration warning: dynamic props on SVG elements are patched as properties instead of attributes

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the root cause the same way. During hydration they derive the element's own namespace from `el.namespaceURI` and pass it to `patchProp` instead of `undefined`. SVG and MathML dynamic props then go through the SVG-aware `shouldSetAsProp` logic and are set with `setAttribute`. Both correctly treat `<foreignObject>` as an SVG-namespace element; using `getContainerType` would have gotten this wrong.

Correctness is effectively equal. Patch A extracts a small, documented helper, `getElementNamespace`, that guards against a null `namespaceURI`. Patch B uses non-null assertions inline; this is safe in practice but less defensive. Patch A also passes the namespace on the `onClick`-only path. That change is harmless and neutral.

Tests: Patch A puts a getter-only `viewBox` on `SVGElement.prototype` to simulate the read-only IDL property. Without the fix, the `key in el` check would route to `patchDOMProp`, which would throw and warn. So the test asserts the exact symptom from the issue (no 'Failed setting prop' warning, attribute updated) and covers both `<svg>` and `<foreignObject>`.

Patch B's first test likely passes even without the fix, because jsdom's SVGSVGElement does not expose `width`/`height`/`viewBox` as properties, so they already fall through to `setAttribute`. That makes it weak. Its second test, an instance getter on `foreignObject.width`, is a valid regression test. Its toggling of `__DEV__` is a less clean way to avoid the warning path.

Overall, Patch A has the more targeted test of the reported symptom and slightly cleaner, safer code.

Steps to reproduce

  1. Open the reproduction.
  2. Open the browser devtools Console.
  3. Observe the [Vue warn]: Failed setting prop … error logged during hydration.

What is expected?

During hydration, dynamic props on SVG (and MathML) elements width, height, viewBox, etc. should be patched as attributes (via setAttribute) exactly as they are during normal client-side rendering. Hydration should be silent.

What is actually happening?

Since 3.5.39, dynamic props on SVG elements are patched as DOM properties during hydration, which throws for read-only SVG IDL properties:

[Vue warn]: Failed setting prop "viewBox" on <svg>: value 0 0 24 24 is invalid.
TypeError: Cannot set property viewBox of #<SVGSVGElement> which has only a getter
    at patchDOMProp
    at patchProp
    at hydrateElement
    at hydrateNode
    at hydrateSubTree
    at <App>

Nothing is visually broken but the console is flooded with warnings.

We ran across this issue in a Nuxt app but I believe the issue is coming from Vue core
