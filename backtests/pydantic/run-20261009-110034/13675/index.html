TypeAdapter config not used for JSON Schema generation

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches apply the same core fix in `TypeAdapter.json_schema()`: they push `self._config` onto the generator's config stack. That resolves the issue's literal example (`TypeAdapter(bytes, config=...)`).

Patch A stops there, which leaves real gaps:
- **Nested types.** In `json_schema.py`, `typed_dict_schema` and `dataclass_schema` push `{}` (via `_get_typed_dict_config` / `getattr(cls, '__pydantic_config__', {})`) when the class has no config of its own. Pushing an empty config overrides the parent config. So `TypeAdapter(list[SomeTypedDict], config={'ser_json_bytes': 'base64'})` would still emit `format: binary` inside the TypedDict. That disagrees with the core schema, where config-less TypedDicts and plain dataclasses inherit the parent config. The same mismatch already exists for a BaseModel containing such types.
- **`TypeAdapter.json_schemas()`.** Patch A leaves this static method untouched, so per-adapter configs are still ignored there.
- **Test coverage.** Its single test uses `list[bytes]`, which sidesteps the nested-class problem.

Patch B addresses the root cause more completely:
- It returns `None` instead of `{}` for missing TypedDict/dataclass configs. The stack's `push(None)` is a no-op, so the parent config now carries through, matching core-schema behavior.
- It still passes `config or {}` to `_update_class_schema`, preserving the existing title and extra handling.
- It threads per-input configs into `generate_definitions` so `json_schemas()` respects each adapter's config.

Patch B's tests are substantially stronger:
- multiple config keys (`ser_json_bytes`, `ser_json_timedelta`, `json_schema_mode_override`)
- default behavior when no config is given
- nested TypedDict and dataclass under both a TypeAdapter and a BaseModel
- a TypedDict with its own config keeping that config
- the multi-adapter `json_schemas()` case

These would fail before the change.

The `_inputs_configs` attribute is a slightly awkward side channel, but it is documented, length-checked, and low-risk.

Overall, B is more correct and better tested.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
