Issue #15126 Merged fix PR #15136 Run 3 Oct 2026 · run-20261003-231210 vuejs/core

compileScript drops template imports from returned when analysis re-runs on a transformed template AST

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the root cause the same way. When the descriptor's template AST is already `transformed`, the import-usage and v-model analysis now re-parses the template source in `sfc` mode with `prefixIdentifiers`, passing the user's compiler options (e.g. delimiters) through from compileScript. This mirrors the guard in compileTemplate, so both hold up under the cache-eviction scenario in the issue.

Patch A covers one more path. It also threads `templateParseOptions` into `hmrShouldReload`/`shouldForceReload`, which calls `isImportUsed` and can hit the same transformed-AST path. Patch B leaves that call without options, so a transformed AST using custom delimiters would be re-parsed incorrectly there.

Patch B's advantages:
- It extracts a shared `resolveTemplateAST` helper and reuses it in compileTemplate, removing duplication.
- It honors a custom `compiler` for non-SSR parsing.

The cost is extra churn in compileTemplate, and it exports the internal `templateAnalysisCache` only so the test can clear it. These are craft trade-offs, not correctness wins.

On tests, A is clearly stronger. Its tests directly exercise the issue's cases on an AST transformed by compileTemplate:
- imports used in template expressions and in v-for
- v-model demotion to `let`
- delimiter-aware re-parse
- HMR comparison, with and without parse options

B has a single test covering a delimiter interpolation after manually clearing the cache. It is valid but does not cover the v-for case the issue highlights.

Overall, A is equally correct on the main path, more complete on HMR, and better tested.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Steps to reproduce

Compile more than 500 unique SFCs for client + SSR (non-inline mode), share each file's descriptor between the two passes (the same way @vitejs/plugin-vue does). The client pass compileTemplate changes the shared template.ast in place, when the analysis cache (capped at 500) evicts a file entry, its SSR compileScript pass re-runs the import usage analysis on that already transformed AST

What is expected?

__returned__ contains every import the template references, same output as when fewer than 500 templates are compiled. The analysis should re-parse when the AST was already transformed, the same guard compileTemplate has with if (inAST?.transformed) in line 214.

What is actually happening?

Imports referenced only from template expressions or with v-for are dropped from __returned__. While the render function still emits $setup.foo(...) and throws TypeError: $setup.foo is not a function at runtime. Because it only happens with more than 500 unique templates it only comes up in large apps in development, in production builds the template are inlined and are unaffected.
