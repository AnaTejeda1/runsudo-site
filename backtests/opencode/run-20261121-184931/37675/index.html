The issue's repro config has only `tools: { "postman*": false }` and an MCP server, no `permission` key, and the MCP tools still reach the provider. Patch B explains that directly: in `SessionTools.resolve` the non-code-mode path iterates `mcp.tools()` and registers every MCP tool without consulting the agent/session permission ruleset (the code-mode path already filters via `Permission.visibleTools`). B computes the merged ruleset once and filters MCP tools through `Permission.visibleTools` before they are converted and advertised, which is the point where the tools array sent to the provider is built. That fixes the issue at its root for both `postman*` and `*searchPostmanElements`, since the `tools` toggle compiles to a wholly-deny rule on that key. Its unit tests drive `SessionTools.resolve` with a mocked MCP service and would fail on a tree that does no filtering; they also check sensible edges (resource-scoped deny does not hide the tool, siblings under the same prefix survive).

Patch A never touches the tools-array construction. The issue

Description

The docs say MCP tools can be disabled through the global tools key with server-prefix globs ("mymcpservername_*": false). On 1.18.3 this has no effect on MCP tools: they are still included in the tools array sent to the provider.

I hit this because the Postman remote MCP server (https://mcp.postman.com/minimal) exposes a tool searchPostmanElements whose input schema uses refs like #/properties/filters/properties/$and/items/properties/createdBy instead of #/$defs/.... Moonshot rejects the request with:

[Moonshot AI] Invalid request: tools.function.parameters is not a valid moonshot flavored json schema, details: <At path 'properties.filters.properties.$and.items.properties.createdBy.$ref': references must start with #/$defs/>

Neither "postman*": false nor "*searchPostmanElements": false in the global tools key changes anything; the same 400 comes back. opencode debug config shows the tools entry resolved. Disabling the whole server via mcp.postman.enabled: false does work, so the only workaround is losing the entire server.

OpenCode version

1.18.3

Steps to reproduce

  1. Configure a remote MCP server with a tool schema Moonshot rejects, e.g. Postman minimal (https://mcp.postman.com/minimal, needs OAuth) and a Moonshot model:
{
  "model": "openrouter/moonshotai/kimi-k3",
  "tools": { "postman*": false },
  "mcp": {
    "postman": { "type": "remote", "url": "https://mcp.postman.com/minimal", "enabled": true }
  }
}
  1. opencode run "hi"
  2. 400 from Moonshot referencing the postman tool's schema path, despite the glob disabling it.

Expected: tools matching a disabled glob are excluded from provider requests.

Operating System

macOS 26 (Darwin 25.5.0)
