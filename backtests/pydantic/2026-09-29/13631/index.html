Description

When a discriminated union uses a bool discriminator (Literal[True] / Literal[False]), the generated JSON schema's discriminator.mapping uses the Python string representations "True" and "False" as keys:

"discriminator": {
    "mapping": {"False": "#/$defs/Disabled", "True": "#/$defs/Enabled"},
    "propertyName": "enabled"
}

Per the OpenAPI discriminator specification, mapping keys must match the serialized payload value of the discriminator property. For a boolean property, that value serializes to JSON true/false, so the keys should be "true" and "false". Tooling that resolves the mapping against the payload (code generators, validators such as openapi-generator or Redocly) fails to match either variant.

Expected:

"mapping": {"false": "#/$defs/Disabled", "true": "#/$defs/Enabled"}

Note that Enum discriminator keys are already normalized to their value (k.value) before stringification in GenerateJsonSchema.tagged_union_schema; bool keys just fall through to str(k).

Example Code

from typing import Literal

from pydantic import BaseModel, Field


class Enabled(BaseModel):
    enabled: Literal[True]
    config: str


class Disabled(BaseModel):
    enabled: Literal[False]


class Model(BaseModel):
    setting: Enabled | Disabled = Field(discriminator='enabled')


print(Model.model_json_schema()['properties']['setting']['discriminator'])
# {'propertyName': 'enabled', 'mapping': {'True': '#/$defs/Enabled', 'False': '#/$defs/Disabled'}}

Summary

What was wrong

In GenerateJsonSchema.tagged_union_schema (pydantic/json_schema.py), discriminator mapping keys were stringified via str(k). Enum keys were first normalized with k.value, but bool keys (from a Literal[True]/Literal[False] discriminator) fell through to str(k), producing the Python-style keys "True"/"False". The OpenAPI discriminator spec requires mapping keys to match the serialized payload value, which for a boolean is JSON true/false — so tooling (openapi-generator, Redocly) failed to match either variant.

What I changed

Added a bool branch after the Enum reduction in tagged_union_schema, converting bool keys to 'true'/'false':

if isinstance(k, bool):
    # Booleans serialize to JSON `true`/`false`; match the serialized
    # payload value per the OpenAPI discriminator spec (rather than `str(True)`).
    k = 'true' if k else 'false'

isinstance(k, bool) is checked explicitly (not via its int superclass), so integer discriminators are unaffected. Placing it after the Enum reduction also handles an Enum whose .value is a bool.

Added regression test test_discriminated_union_bool_discriminator_mapping in tests/test_json_schema.py, using the exact scenario from the report and asserting the discriminator equals {'propertyName': 'enabled', 'mapping': {'true': '#/$defs/Enabled', 'false': '#/$defs/Disabled'}}.

Test evidence

  • After the fix: the new test passes.
  • Gate over all discriminator tests in tests/test_json_schema.py and tests/types/unions/test_discriminated_union.py: 88 passed, 4 pre-existing xfailed — no regressions.
  • Reviewer confirmed the diff fully and minimally addresses the report, with no blast radius on int/str/enum discriminators and no stray files.
