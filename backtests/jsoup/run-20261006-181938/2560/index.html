W3CDom throws NPE for element names with invalid XML starts

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Patch B is the better fix: both resolve the reported NPE, but A widens the change into attribute handling without testing it, while B keeps the fix confined to tag names.

**Correctness.**
- Both patches stop the NPE by normalizing `1abc` to `_1abc` when the name cannot start an XML name.
- Patch A puts the fallback inside the shared `w3cSafeName` and deletes the `if (key == null) return;` guard in `setAttribute`. Attributes that were previously skipped as unrepresentable are now emitted with a `_` prefix, or as a bare `_` as the last resort.
- That contradicts the existing changelog note that unrepresentable attributes are skipped. It also allows several attributes to collapse to the same `_` key, or to collide with declaration handling.
- None of this attribute-path change is tested.
- Patch B fixes the root helper `Normalizer.xmlSafeTagName`, which is the shared tag-name normalizer, and applies it before QName normalization for element names only. Attribute behavior is unchanged.
- B also fixes the same root cause in `Element.safeTagName`, where XML-syntax serialization previously emitted `<null>`. That is a closely related symptom of the same null return, and it carries little risk.

**Tests.**
- Patch A tests `1abc` and `-abc` with a nested child and checks parentage.
- Patch B tests a renamed root (`1abc`), a prefixed name with an invalid local part (`p:2x` → `p:_2x`), and text content and serialized output.
- B also covers a programmatically created element (`9lives`) in an HTML document, matching both scenarios in the issue (created and renamed elements).
- B adds an `ElementTest` showing XML serialization is fixed while HTML syntax is unchanged.
- B's tests are broader and exercise the prefix case.

**Scope and craft.**
- Patch A's CHANGES entry is a plus, but its silent change to attribute semantics adds risk.
- Patch B's changes are cohesive: fix the helper, make it non-null, and update its callers.

The issue

View on GitHub

W3CDom conversion throws a NullPointerException when a programmatically created or renamed element has a name that cannot start an XML name, such as 1abc.

Document doc = Jsoup.parse("<root/>", "", Parser.xmlParser());
doc.firstElementChild().tagName("1abc");

new W3CDom().fromJsoup(doc);

Attribute.getValidKey() returns null, which is then dereferenced by W3CDom.

The name should instead be normalized to a valid XML name, such as _1abc.

Raw <1abc/> input is already treated as text by the parser, so this applies specifically to DOM construction and mutation.
