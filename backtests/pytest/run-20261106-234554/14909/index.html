The issue

View on GitHub

While looking at #14161 and its fix in #14209, I noticed that the same undo-ordering problem still exists in MonkeyPatch.delattr, MonkeyPatch.setitem, and MonkeyPatch.delitem.

These methods register an undo entry before attempting the mutation. If the mutation raises, the target remains unchanged, but undo() later tries to restore a change that never happened.

Minimal reproduction:

from types import MappingProxyType

import pytest


def test_failed_delattr(monkeypatch):
    class A:
        __slots__ = ()
        x = 1

    a = A()
    with pytest.raises(AttributeError):
        monkeypatch.delattr(a, "x")
    assert a.x == 1


def test_failed_setitem(monkeypatch):
    mapping = MappingProxyType({"x": 1})
    with pytest.raises(TypeError):
        monkeypatch.setitem(mapping, "x", 2)
    assert mapping["x"] == 1


def test_failed_delitem(monkeypatch):
    mapping = MappingProxyType({"x": 1})
    with pytest.raises(TypeError):
        monkeypatch.delitem(mapping, "x")
    assert mapping["x"] == 1

On current main, the original exceptions are caught and all three targets remain unchanged. However, fixture teardown calls undo() and produces another error for each test because the failed operations left stale undo entries.

I think the fix would be to follow the ordering already used by MonkeyPatch.setattr after #14209:

  • Save the original value.
  • Attempt the mutation.
  • Register the undo entry only after the mutation succeeds.

Successful operations would keep their existing behavior.

I reproduced this locally and have a small fix with regression tests ready. If maintainers agree that this is a bug and that the proposed approach is appropriate, I would be happy to submit a PR. Could this issue be assigned to me?

Environment:

  • pytest 9.2.0.dev204+gc0ab40c93
  • Python 3.12.13
  • Red Hat Enterprise Linux 9.8
