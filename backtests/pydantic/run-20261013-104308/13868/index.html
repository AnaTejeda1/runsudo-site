multiple_of=0 still raises ZeroDivisionError for non-native numeric types

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

The issue identifies the root cause precisely. The Python fallback in `_validators.py` runs `x % multiple_of` without checking the divisor, and Fraction, temporal types, complex and custom types all go through that path.

Patch B fixes it at that point. `check_multiple_of_constraint` runs during schema generation wherever the fallback `multiple_of` validator is attached, in both `apply_known_metadata` and the experimental pipeline's non-native branch. It rejects zero, negative, NaN and infinite divisors for ordered types, and zero for unordered types like complex. So every type that uses the fallback is covered, not just the two named examples, and it raises a SchemaError as the issue expects. Its tests cover the exact reproduction (a `BaseModel` with `Fraction = Field(multiple_of=0)`), Fraction with several invalid values, timedelta zero and negative, complex zero, and pipeline cases. All of these would have failed before the change. The edits to existing tests in `test_types.py` only swap a zero divisor for 2 so they keep testing incompatible-type errors; that is justified, not churn.

Patch A takes a different route. It adds native `multiple_of` support to pydantic-core's Fraction and Timedelta validators in Rust and Python schema definitions, and moves those types off the fallback.
- That does fix Fraction and timedelta, but it is a much larger redesign touching the Rust core.
- It leaves the fallback itself unguarded, so custom numeric types and the experimental pipeline path can still hit ZeroDivisionError. It does not address the root cause the issue points at.
- It adds new feature surface: a new timedelta microsecond-modulo implementation and a change to error-message format. That brings more risk than the issue requires.

Patch A's tests are solid for the types it covers but narrower. B resolves the root cause more completely, with less risk and broader tests.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Description

Field(multiple_of=0) is rejected during schema generation for int, float, and Decimal, but equivalent non-native numeric types still pass schema generation and raise an uncaught ZeroDivisionError during validation.

Reproduction

from fractions import Fraction
from pydantic import BaseModel, Field

class Model(BaseModel):
    value: Fraction = Field(multiple_of=0)

Model(value=Fraction(1, 2))

Actual: validation raises ZeroDivisionError rather than ValidationError.

Expected: model definition fails with a schema-generation error stating that multiple_of must be greater than zero, consistently with native numeric types.

The Python fallback in pydantic/_internal/_validators.py performs x % multiple_of without validating the divisor. Fraction, temporal types, and complex use this fallback. I found no existing report for the remaining types after the native numeric fix.
