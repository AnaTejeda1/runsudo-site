tpl/transform: Strip BOM prior to unmarshaling a resource or string

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches strip the UTF-8 BOM in `metadecoders.Decoder.Unmarshal`, which fixes the reported resource cases.

Patch B is more robust in three ways:

1. **String inputs.** It strips the BOM in `tpl/transform/unmarshal.go` before the `TrimSpace` emptiness check and before format detection on the raw string. A BOM-only string is then treated as empty, and detection does not see a leading BOM. Patch A relies only on the decoder-level strip, so string format detection may still see the BOM.
2. **Other entry points.** It also strips the BOM in `UnmarshalTo`, `UnmarshalYaml`, and `Remarshal`, so all decoding paths behave the same.
3. **Shared helper.** It adds a named `StripBOM` helper instead of an inline magic byte slice.

The i18n change is adjacent hardening. It is low-risk and tested.

**Tests.** Patch B's tests are much stronger:
- Unit tests across JSON, TOML, YAML, XML, CSV, ORG and empty input, plus `UnmarshalToMap` and `UnmarshalYaml`.
- Integration tests for every format via both resource and string input, Remarshal, BOM-only edge cases, and the issue's exact CSV test.
- Data-file and i18n tests.

Patch A has a single integration test, which is reasonable. However, it also adds unrelated formatting churn to existing tests by reflowing `AssertFileContent` and `ReplaceAll` calls.

On correctness, test coverage and craft, Patch B is better.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
