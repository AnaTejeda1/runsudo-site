Automatic summary may generate invalid HTML with blockquotes and lists

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the reported automatic-summary cases (all seven independent tests pass on A and B), so the decision rests on how each extends the cutoff and on test quality. Patch A balances every element opened since the wrapper start, including generic containers like div. That means any raw-HTML div wrapper in Markdown, or the first section of a multi-section AsciiDoc document, will push the summary to the end of that container, potentially swallowing the whole content; it only falls back to the original cut when the container never closes. Patch B restricts extension to a whitelist of block elements (blockquote, lists, dl, table, figure, details) and documents why div/section are excluded, with explicit tests showing AsciiDoc sections, RST document wrappers and intro divs are not over-extended while AsciiDoc quote blocks still close correctly. B also reuses golang.org/x/net/html's tokenizer, which is already a Hugo dependency and handles comments, attributes, raw-text elements and case-folding, instead of A's hand-rolled scanner. B additionally handles the manual divider placed inside a blockquote or list, which is beyond the issue's literal ask but is low-risk and tested. B's tests are broader (nested blockquotes, lists in blockquotes, void elements, unclosed elements, several markup wrappers, divider cases). A's tests are adequate but it also rewrites the existing benchmark from b.Loop to b.N for no clear reason. Correctness risk of over-expansion in A plus B's stronger tests and more robust parsing make B the better fix.

Hugo's .Summary may lead to blockquote end tag be below cutoff point

Explanation

In most modern browsers this html code will be parsed and rendered without errors

<!DOCTYPE html>
<html>
<head>
<meta charset="utf-8">
<meta name="viewport" content="width=device-width">
</head>
<body>
  <main>
    <blockquote>
      <p>1</p>
  </main>
</body>
</html>

Leading to shown in browser as a source

<!DOCTYPE html>
<html>
<head>
<meta charset="utf-8">
<meta name="viewport" content="width=device-width">
</head>
<body>
  <main>
    <blockquote>
      <p>1</p>
      <!-- This blockquote end tag was automatically inserted -->
    </blockquote>
  </main>
</body>
</html>

This is due to these parsing rules

An end tag whose tag name is one of: "address", "article", "aside", "blockquote", "button", "center", "details", "dialog", "dir", "div", "dl", "fieldset", "figcaption", "figure", "footer", "header", "hgroup", "listing", "main", "menu", "nav", "ol", "pre", "search", "section", "select", "summary", "ul"

If the stack of open elements does not have an element in scope that is an HTML element with the same tag name as that of the token, then this is a parse error; ignore the token.

Otherwise, run these steps:

Generate implied end tags.

If the current node is not an HTML element with the same tag name as that of the token, then this is a parse error.

Pop elements from the stack of open elements until an HTML element with the same tag name as the token has been popped from the stack.
