multiple_of=0 still raises ZeroDivisionError for non-native numeric types

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

The issue's root cause is that the Python fallback `multiple_of_validator` divides by `multiple_of` without checking it first. The issue names three affected families: Fraction, temporal types, and complex.

Patch B fixes this where the fallback is wired in. It adds `check_multiple_of_constraint`, which runs at schema-build time in `apply_known_metadata` and in the experimental pipeline's fallback path. It unwraps function-before/after/wrap schemas and rejects zero, negative and NaN divisors. That covers fraction, timedelta, complex (comparison raises TypeError, so it falls back to a falsiness check) and bool. The result is a SchemaError at model definition, which is the behaviour the issue expects. Its tests reproduce the issue's BaseModel case directly. They also cover TypeAdapter with Fraction(0), negative and NaN values, a wrapped AfterValidator schema, timedelta zero and negative, complex 0/0j, bool and pipeline. A valid-constraint sanity test confirms normal validation still works. All of these would fail before the change.

Patch A instead redesigns two types. It moves `multiple_of` for fraction and timedelta into pydantic-core, adding new Rust validator fields, TypedDict keys and schema-builder arguments, and changes the constraint routing tables. The Rust checks do reject non-positive divisors for those two types. However, complex is not handled at all: it still goes through the Python fallback and would still raise ZeroDivisionError, so one of the cases the issue lists remains broken. The redesign is also much riskier. It changes which layer enforces timedelta and fraction constraints, alters the error-message format, requires a core rebuild, and adds a new microsecond-arithmetic path. That is more surface than the bug needs. Its tests are reasonable for fraction and timedelta but say nothing about complex or the pipeline path.

On correctness, B fully covers the reported scenarios while A leaves complex unfixed. On scope and risk, B is a focused fix while A is a broader redesign. B wins.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Description

Field(multiple_of=0) is rejected during schema generation for int, float, and Decimal, but equivalent non-native numeric types still pass schema generation and raise an uncaught ZeroDivisionError during validation.

Reproduction

from fractions import Fraction
from pydantic import BaseModel, Field

class Model(BaseModel):
    value: Fraction = Field(multiple_of=0)

Model(value=Fraction(1, 2))

Actual: validation raises ZeroDivisionError rather than ValidationError.

Expected: model definition fails with a schema-generation error stating that multiple_of must be greater than zero, consistently with native numeric types.

The Python fallback in pydantic/_internal/_validators.py performs x % multiple_of without validating the divisor. Fraction, temporal types, and complex use this fallback. I found no existing report for the remaining types after the native numeric fix.
