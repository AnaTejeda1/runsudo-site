SSR memory leak - options API watchers are created and never stopped with async setup()

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the root cause the same way. In the async-setup `.then` branch, they put the SSR setup state back to true around `handleSetupResult`, so `applyOptions` creates watchers under the same SSR rules as a sync setup: no live non-immediate watchers, and sync-flush handles registered for cleanup. Correctness is essentially equal. Patch A saves and restores the previous `isInSSRComponentSetup` value instead of hard-resetting to false. That is slightly more robust against nesting or interleaving, though Patch B's reset matches the existing sync-path convention and is very likely safe in practice. The main difference is the tests. Patch A covers several cases that would fail before the fix: the issue's `watch` option case (also asserting no `__watcherHandles`), `this.$watch` inside `created`, an `immediate: true` watcher that runs exactly once and is not kept alive, and a `flush: 'sync'` watcher that is registered in `__watcherHandles` and stopped after render. Together these check that async setup now matches sync-setup SSR semantics. Patch B adds the issue's reproduction plus a GC-based retention test. That test is directly relevant to the memory-leak symptom, but it only runs when `global.gc` is exposed, so it is often skipped. Scope is equally tight in both. Patch A wins on the broader, more behavior-specific test coverage and the slightly more defensive state restoration.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Vue version

Steps to reproduce

originally reported in https://github.com/nuxt/nuxt/issues/30782

  1. create an options API component with an async setup(), a computed property that reads shared module-level state, and a watch on that
  2. render it on the server and then mutate the shared state after the render is done
  3. see that the watcher is still active on the server

Reproduction

test('options-api watchers should not be created for async setup components', async () => {
  const open = ref(true)
  const spy = vi.fn()

  const App = defineComponent({
    setup: () => Promise.resolve({}),
    computed: {
      isOpen() {
        return open.value
      },
    },
    watch: {
      isOpen: spy,
    },
    render() {
      return h('div', String(this.isOpen))
    },
  })

  const html = await renderToString(createSSRApp(App))
  expect(html).toBe('<div>true</div>')

  // mutating the state after the request is done should not trigger the watcher
  open.value = false
  await nextTick()
  expect(spy).not.toHaveBeenCalled()
})

What is expected?

the same behavior as with a synchronous setup: regular watchers declared via the watch option don't run during SSR and don't survive the render

mutating the shared state after renderToString resolves should not trigger anything

What is actually happening?

when setup() returns a Promise, the watch option creates a live watcher on the server that is never stopped

if this subscribes to state that outlives the request, it keeps the entire component instance (and app) reachable forever
