Preserve input values entered during hydration

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches use the same root-cause fix. During hydration, the v-model `created` hook runs on an element that is already attached to the DOM. Each patch detects that via `parentNode` and then, in `mounted`, syncs the user-entered DOM value back into the model instead of overwriting it.

Patch B only handles `vModelText` for `el.type === 'text'` and textarea. Common inputs such as email, password, search, number and tel are still reset, so the issue as reported (forms in general) is only partly fixed. It does not cover checkbox, radio or select at all. Its CR/LF normalization is a reasonable detail. Its single test covers just the basic text case.

Patch A covers text-like inputs of any type. It avoids false positives from browser value sanitization (range clamping, email trimming) by cloning the input and assigning `defaultValue` to the clone. It also applies `.number`/`.trim` casting, including the implicit cast for `type=number`. Beyond text, it handles:
- checkboxes, including several checkboxes bound to the same array/Set model, using a pending-model map so each assignment builds on the previous one;
- radios, where only the newly checked radio assigns;
- single and multiple selects, with careful default-selection detection that accounts for disabled options and optgroups;
- dynamic type through the existing delegation.

The event-handler logic is refactored into shared `assignCheckboxValue`/`assignSelectValue` helpers rather than duplicated.

Patch A's test suite is extensive and meaningful. It includes negative cases: an unmodified input, sanitized values that should not count as user input, and a select with no matching option. These tests would fail before the change.

The pendingCheckboxModels mechanism adds some complexity and risk. Even so, Patch A is far more complete against the issue's ask (preserving form input during hydration) and better tested. Patch B leaves most form controls broken.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Steps to reproduce

user loads a page with a slow internet connection
starts entering some values ​​into the input with v-model
after all browser resources loaded - input v-model reset to default value

What is expected?

entered input value is preserved once hydration completes

What is actually happening?

input value is reset to its default value

System Info

Any additional comments?

This is affecting UX when interacting with inputs/forms in slowly loading apps, where values entered during hydration phase are erased and the progress is lost. I have been blocking all forms myself until mounted hook fires to workaround this issue - it would be great to not have to!
