Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches add the three requested entries to `GetDependencyListNonGo`: aom v3.14.1, dav1d 1.5.3 and libavif v1.4.1. They use the same source strings and versions, so both resolve the issue.

Patch A goes further. It moves the version constants into `internal/warpc` and makes `common/hugo` import `internal/warpc` so it can call `GetWASMDeps()`. That moves versions closer to the WASM build, but it adds real risk and noise:
- **New dependency edge.** A low-level package (`common/hugo`) now imports the WASM runtime package with its embedded binaries. This could create an import cycle and couples a basic metadata package to a heavy internal one.
- **Not a single source of truth.** The constants are still hand-maintained copies with only 'keep in sync with Makefile' comments.
- **Unrequested KaTeX entry.** Its version, 0.16.21, cannot be checked from the diff.
- **Unrelated churn.** It reformats several call sites in `warpc.go` and in `hugo.go`, which obscures the actual fix.
- **Weaker test.** The testscript change only checks that the names appear in output, not the versions.

Patch B makes a minimal, low-risk change that matches the existing hardcoded convention and keeps the TODO. It adds a focused unit test asserting the exact `name="version"` strings, which would fail before the change and pass after. Given equal correctness, B has the more precise test, a smaller scope and no new coupling risk, so B is the better fix.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

What the agent reported

hugo env now lists aom, dav1d and libavif with their versions, but I couldn't run the new test. This environment can't download Go modules, so the common/hugo package never compiled: both test runs stopped at FAIL github.com/gohugoio/hugo/common/hugo [setup failed] with "dial tcp: lookup proxy.golang.org … server misbehaving". I have not seen the test fail before the fix or pass after it.

What was wrong: GetDependencyListNonGo() in common/hugo/hugo.go only had a hard-coded entry for libwebp. The AVIF libraries built into Hugo's WASM module were never added, so they didn't appear in the output.

What I changed:

  • common/hugo/hugo.go: added three entries next to libwebp. The versions and source paths come from internal/warpc/genavif/Makefile:
  • github.com/AOMediaCodec/libavif="v1.4.1" (the "v.14.1" in the report is a typo; the Makefile has v1.4.1)
  • aomedia.googlesource.com/aom="v3.14.1"
  • code.videolan.org/videolan/dav1d="1.5.3"
  • common/hugo/hugo_test.go: added TestGetDependencyListNonGo, which checks that the list contains all four WASM library entries.

Test evidence:

  • Before the fix: the test couldn't build. Reading the old code, it should fail on the aom entry.
  • After the fix: ./bt-test ./common/hugo/ -run 'TestGetDependencyListNonGo|TestGetBuildInfo' failed setup the same way.
  • What did run: gofmt reports no problems. The reviewer checked the diff by reading the code and found the versions match the Makefile, the code should compile, and nothing unrelated changed.

In plain hugo env output the new lines appear in the order libwebp, libavif, aom, dav1d, not alphabetically; this output was never sorted before either. With --logLevel info, the full list is still sorted.

Requirements:

  1. List aom in hugo env: done, using the source path from the report. Covered by the new test, not yet run.
  2. List dav1d: done, same status.
  3. List libavif: done, with the version corrected to v1.4.1. Same status.
  4. "Assuming I have the correct source strings": checked. All three paths match the clone URLs in the Makefile; only the libavif version was wrong.
