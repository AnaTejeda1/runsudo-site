Generic model parametrization drops field defaults and typevar substitution after __annotations__ is read on a metaclass (Python <= 3.13)

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

The core fix is the same in both patches. On Python <= 3.13, when `obj` is a class, both read `obj.__dict__.get('__annotations__', {})` instead of using `getattr`. That addresses the root cause described in the issue: a plain dict planted on the metaclass shadows the `type.__annotations__` descriptor, so attribute lookup falls through to the parent's annotations. Both patches fix both call sites (`get_model_type_hints` and `collect_model_fields`), so they are equally correct. The differences are in tests and craft. Patch A's test checks `safe_get_annotations(Sub) == {}` using a plain metaclass. It would fail before the fix and pass after, but it only exercises the helper, not the reported symptom. Patch B's test reproduces the reported scenario end to end. It uses a `ModelMetaclass` subclass with `__annotations__` read, then a generic model with a TypeVar field and a defaulted field. It asserts that `G[str]` substitutes the TypeVar (`annotation is str`), keeps the default (`default == 5`), validates `{'x': 'hi'}` with `a == 5`, and rejects a non-str `x`. It would fail before the fix and directly guards against the regression the issue reports (dropped defaults and missing typevar substitution). On craft, Patch B adds a clear comment in the source explaining why `__dict__` is used, which matters for a subtle CPython quirk like this. Patch A adds no comment and leaves a `"""<link>"""` placeholder docstring in its test. Scope is equally minimal in both. Patch B wins on test quality and clarity.

Description

This is a regression on main (2.14.0a1); I could not reproduce it on any released version (checked 2.13.4 and 2.10.6 under the same conditions). It affects Python 3.10–3.13 (verified on 3.10, 3.12 and 3.13); Python 3.14 is unaffected.

If __annotations__ has ever been read on a metaclass appearing in a model's metatype MRO (e.g. ModelMetaclass itself, or abc.ABCMeta), then any generic model parametrized for the first time afterwards gets a broken schema:

  • type variables are not substituted (x: T ends up with an any schema), and
  • field defaults are dropped (fields with defaults become required).

Parametrizations built before the read keep working, since their schemas are already cached — which makes this very order-dependent and confusing to track down in a real test suite.

Reading an attribute sounds like an odd trigger, but it happens in the wild: on CPython ≤ 3.13, reading __annotations__ on a (heap) class that has none auto-creates a plain __annotations__ = {} entry in that class's __dict__ (see the annotations HOWTO). langgraph does such a read at import time (get_cached_annotated_keys in langgraph/_internal/_fields.py has a getattr(base, "__annotations__", None) fallback — added for Python 3.14 compat, ironically — which ends up planting {} on abc.ABCMeta). So a plain import langgraph.prebuilt breaks all subsequently-parametrized generic models. We found this via the pydantic/logfire weekly CI job testing against pydantic main, where pydantic_evals.Dataset.from_dict() fails with 3 validation errors for _DatasetModel[...] — Field required for exactly its three defaulted fields — but only in test runs where a langchain test ran first (failing run).

Mechanism:

  1. The planted {} lives in the metaclass's __dict__. For a model class M, attribute lookup of M.__annotations__ searches type(M).__mro__ (e.g. (ModelMetaclass, ABCMeta, type, object)) and now finds the plain dict before reaching the type.__annotations__ getset descriptor. A plain dict is not a data descriptor, so lookup falls back to M's own MRO — and for a class with no own __annotations__ (like a freshly created generic submodel), this returns the parent's annotations. (Normally the type.__annotations__ data descriptor intercepts the lookup and auto-creates/returns the class's own empty dict, which is what makes getattr look safe.)
  2. safe_get_annotations() in pydantic/_internal/_typing_extra.py uses getattr(obj, '__annotations__', {}) on < 3.14, so for the new submodel G[str] it returns the origin's annotations instead of {}: clean: safe_get_annotations(G[str]) == {} poisoned: safe_get_annotations(G[str]) == {'x': ~T, 'a': <class 'int'>}
  3. In collect_model_fields(), cls_annotations is "only used to determine if an annotation comes from a parent class". The leak makes ann_name in cls_annotations true for every inherited field, so instead of copying the parent FieldInfo and applying typevars_map (via _recreate_field_info), it takes the plain FieldInfo.from_annotation(ann_type) branch: no typevar substitution, and no default — the origin's class-attribute default is long gone because it was delattr'd during the origin's own field collection.

Possible fix: for classes on ≤ 3.13, read own annotations via obj.__dict__.get('__annotations__', {}) (what inspect.get_annotations() does) rather than getattr. Both call sites of safe_get_annotations() seem to want own-class annotations anyway: get_model_type_hints() iterates the MRO itself and calls it per base, and cls_annotations in collect_model_fields() is explicitly meant to be the current class's own annotations.

What the agent reported

I fixed the bug: G[str] now keeps its default and gets x: str even after __annotations__ has been read on a metaclass. The regression test fails without the fix and passes with it. The full suite has one failure, and it also fails without my change.

What was wrong: on Python 3.13 and older, safe_get_annotations() in pydantic/_internal/_typing_extra.py used getattr(obj, '__annotations__', {}). If __annotations__ had been read on a metaclass, a plain {} sat in that metaclass's __dict__ and hid the normal lookup. For a fresh parametrized class like G[str], which has no annotations of its own, getattr then returned the parent's annotations. collect_model_fields() took that to mean every inherited field was declared on G[str] itself, so it built bare FieldInfos. Those had no default and no type-variable substitution.

What I changed:

  • The fix (pydantic/_internal/_typing_extra.py, 6 lines added): on Python 3.13 and older, classes now read their own annotations with obj.__dict__.get('__annotations__', {}), which is what inspect.get_annotations() does. Functions and partials still go through getattr, and the Python 3.14 path is unchanged.
  • The test (tests/test_generics.py): test_generic_parametrization_metaclass_annotations_leak defines a local subclass of ModelMetaclass, reads __annotations__ on it, and then builds G[str]. Using a local metaclass keeps the planted {} from leaking into other tests. It checks that x has type str, that a defaults to 5, that model_validate({'x': 'hi'}) works, and that x=1 is rejected.

Test evidence (Python 3.13.15):

  • Your example script failed with a: Field required before the fix and prints x='hi' a=5 after it.
  • The new test fails on the unfixed code (assert ~T is str) and passes with the fix.
  • The generics, dataclasses, main, forward-ref, edge-case, typing, validate-call, fields and internal test files: 1082 passed, 30 skipped, 12 xfailed.
  • Full suite: 12273 passed, 1 failed. The failure is tests/test_validators.py::test_v1_validator_deprecated, which checks a hardcoded file path (/work/... vs /workspace/...). It fails the same way with my changes stashed, so it comes from this environment.

Other code that uses this function: it's also called from get_model_type_hints and get_cls_type_hints (which go through each base class in turn), from dataclass field collection in _fields.py, and from pydantic/dataclasses.py. All of them want a class's own annotations, so each is now correct in the affected case as well. For normal classes the result is the same as before. The one difference is that reading annotations no longer writes an empty {} into a class's __dict__ as a side effect. The reviewer checked every caller and found nothing blocking.
