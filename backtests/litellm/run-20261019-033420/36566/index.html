[Bug]: litellm_content_filter evaluations missing from request logs and Guardrails Monitor

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

The issue describes ordinary successful chat requests where five litellm_content_filter guardrails appear in applied_guardrails (so they ran and were marked applied) yet leave no guardrail_information entry, while block_code_execution does. Patch A identifies a root cause that matches that shape: content filters that scan the raw request run against a throwaway snapshot, and the standard_logging_guardrail_information entry they write lands on the discarded snapshot's metadata bucket. A carries those entries (and applied names) back to the live request and re-syncs the logging object, in both the sequential and parallel pre_call paths, guards against double-filing when the snapshot shares the live logging object, and runs the carry-back in a finally so a blocking guardrail's intervention record also survives. Its tests use the real ContentFilterGuardrail and BlockCodeExecutionGuardrail through pre_call_hook, cover sequential/parallel, block, and shared-logging-object dedup, and would fail on base. The independent tests reproducing the issue's actual scenario (benign chat through six global guardrails, sequential and parallel) fail on base and B, pass only on A.

Patch B addresses a different gap: when skip_system_message scoping leaves nothing to scan, it records a 'not_run' entry. That only explains missing entries for system-only requests, which cannot plausibly account for 33 of 33 normal chat requests, and 'not_run' is not the 'completes successfully' evaluation record the issue asks for. B also fans out into usage tracking metrics, compliance checks, and a large UI redesign (not_run badges, timeline changes, type changes) — scope beyond the ask that adds risk without fixing the reported behaviour. The one independent test B passes checks a system-only scenario the issue does not describe.

A fixes the root cause with focused, well-tested changes; B masks a tangential case and leaves the reported bug in place.

What happened?

Guardrails Monitor does not show evaluations for five configured global litellm_content_filter guardrails, even though the associated request metadata lists all six guardrails in applied_guardrails.

For recent successful LLM requests:

  • applied_guardrails contains all six configured global guardrails.
  • guardrail_information contains only one entry: Block Code Execution.
  • The five litellm_content_filter guardrails have no individual guardrail_information entries.

In Guardrails Monitor for the same one-day date range:

  • Total Evaluations: 33
  • Active Guardrails: 6
  • Block Code Execution: 33 requests
  • Each of the following guardrails: 0 requests
  • Prompt Injection: System Prompt
  • Prompt Injection: Malicious Code
  • Prompt Injection: SQL
  • Prompt Injection: Data Exfiltration
  • Prompt Injection: Jailbreak

User Flow

Expected behavior

Every guardrail listed in applied_guardrails should have a corresponding persisted evaluation record when it completes successfully, so Guardrails Monitor and Export Data accurately show request counts and outcomes for each configured guardrail.

Actual behavior

Only Block Code Execution has persisted detail and Monitor request counts. The five litellm_content_filter guardrails are listed in applied_guardrails but have no corresponding individual evaluation records in guardrail_information.

Proof the bug occurs

  1. Configure these global guardrails through the Admin UI/API, each with mode: pre_call and default_on: true:
  2. block_code_execution
  3. Five litellm_content_filter guardrails
  4. Send successful chat-completion requests through the proxy.
  5. Inspect the request’s spend-log metadata.

  7. Open Guardrails Monitor for the same date range.
  8. Observe that only Block Code Execution has request counts; the five content filters show zero requests.
