SSR memory leak after a render error in a dynamic component

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the reported leak: a block opened via openBlock() in vnode-mode slot code (renderSlot inside `<component :is>`) is never closed when the slot throws. The leftover currentBlock then collects every vnode created afterwards.

Patch B fixes this where the block is opened. renderSlot gets a try/catch that unwinds the stack, and withCtx unwinds blocks left by inline blocks such as v-if. That is a precise fix and also helps the client. However, it leaves renderComponentRoot's existing `blockStack.length = 0`, which empties the array without resetting `currentBlock`. So a render-function or functional component that throws mid-block still leaves a stale currentBlock that retains later vnodes. That is the same leak class through a sibling path. B also adds bookkeeping to withCtx, which runs on every slot invocation on the client.

Patch A closes the blocks left open at the SSR ssrRender boundary, recording the depth before render and unwinding to it on throw. This covers the issue scenario, the v-if variant and any other vnode-mode code that throws mid-block. It also replaces `blockStack.length = 0` with `closeBlocksAbove(0)`, which properly resets currentBlock and fixes the render-function path that B misses. It restores currentRenderingInstance when handleError rethrows, preventing the failed instance and its scope id from leaking. It also wraps renderComponentSubTree in try/finally so the dev warning context is popped. These are directly related leak paths from a failed SSR render, not unrelated churn. The re-indentation of renderComponentSubTree obscures the diff somewhat, but the logic is clear.

Tests: B's GC/WeakRef tests directly measure the reported symptom, which is strong evidence. A's tests use `createBlock('div').dynamicChildren` to detect a leaked open block. They would fail before the fix, and they cover four scenarios: the issue case, v-if, the stale warning context, and the render-function path that leaks the rendering instance. B's tests are slightly more faithful to the symptom; A's cover more failure modes.

Overall, A fixes the reported case plus closely related leak paths that B leaves open, so A is the more complete and robust fix.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Steps to reproduce

  • download the reproduction from stackblitz (won't work there, needs to be run locally)
  • run pnpm i && pnpm leak
  • see the heap size & alive app instances grow with each request after the single failed render

The script renders 500 fresh SSR apps, which all get garbage-collected. Then renders one app whose slot content throws, then renders 500 more identical healthy apps, which will never be garbage collected afterwards.

A dynamic component <component :is> with a <slot /> is needed for this to reproduce.

Card

<script setup>
    defineProps({ tag: { type: String, default: 'div' } })
</script>

<template>
    <component :is="tag" class="card">
        <slot />
    </component>
</template>

app:

<script setup>
    defineProps(['payload'])  // one request renders with `payload: null` → throws
</script>

<template>
    <main>
        <Card>{{ payload.title }}</Card>
    </main>
</template>

What is expected?

A failed renderToString should not affect subsequent renders and all apps rendered after it should get garbage collected.

What is actually happening?

Every app created after the single failed render is kept in memory forever.
