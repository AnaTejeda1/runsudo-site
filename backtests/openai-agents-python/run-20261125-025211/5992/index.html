run_demo_loop never asks for tool approval, the paused call goes out without its output

Worse

The merged fix was judged better than our patch.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the root cause the same way: after each run they check `result.interruptions`, prompt y/N per interruption, approve/reject on `result.to_state()`, and re-run with the state before copying `to_input_list()` forward. All eight independent tests pass on both, so correctness on the issue's core scenarios is equal.

The differences are at the edges the issue implies and in test depth, and they favor A.

Edge handling: A routes the approval prompt through the same `_read_input` helper as the main prompt, so EOF/Ctrl+C or typing exit/quit at the approval prompt stops the loop, consistent with the existing REPL behavior. B's `_ask_for_approval` catches EOF/KeyboardInterrupt and returns False, which silently rejects the tool and then makes another model call before returning to the main prompt; in a REPL, Ctrl+C turning into 'reject and keep running' is surprising and inconsistent with how the same key behaves at ` > `.

Context on resume: A passes `context=None` when the input is a RunState so the state's own (possibly mutated) context is used, and adds a test showing context modified by an on_handoff hook survives the approval resume. B re-passes the original `context` alongside the RunState, which risks clobbering mutations made before the interruption. A also prints richer detail (arguments, namespace, hosted-tool fields like action/commands) so the user actually knows what they are approving, which matters for a `[y/N]` prompt on something like a shell call.

Tests: B's tests cover approve and reject in both modes and verify no stray 'y'/'n' user turn and correct outputs, which is adequate and matches the repro. A's tests go further: mixed approve/reject across two interruptions in one turn, a second resume cycle, verification that the next user turn carries the full history, namespace labeling for deferred tools, handoff-context preservation, and exit during approval with no tool execution. A's tests depend on more existing helpers (`agents.decorators.tool`, `make_shell_call`, `function_call(namespace=...)`), which I cannot verify, but they target real behaviors of the fix.

Scope/craft: B's `_run_turn` extraction is clean and minimal; A's inner `while True` with the details dict is a bit denser but still readable. A's extra detail printing is directly relevant to the approval UX rather than unrelated churn. Overall A is the more robust fix with stronger tests.

Describe the bug

with a needs_approval=True tool, run_demo_loop pauses the run but never asks for approval, it just waits for the next message
whatever you type next (even "y") goes out as a new user turn next to the paused function_call with no output for it, and the tool never runs
the loop copies result.to_input_list() into the next turn and never checks result.interruptions (repl.py#L52-L77), same with stream=True and stream=False

Debug information

  • Agents SDK 0.24.0 and main at 64fbde5d, Python 3.14.7, macOS
  • no model needed (ScriptedModel), happens every time
