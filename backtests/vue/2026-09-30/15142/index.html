Suspense: flushing buffered effects overflows the call stack when many effects accumulate while pending (RangeError: Maximum call stack size exceeded)

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches replace the spread pushes the issue names with plain loops: `pendingPostFlushCbs.push(...cb)` in `queuePostFlushCb`, `activePostFlushCbs.push(...deduped)` in nested `flushPostFlushCbs`, and `parent.effects.push(...effects)` in Suspense's merge into a pending parent. So both resolve the reported root cause in the same way.

Patch A also fixes a fourth spread site, `suspense.effects.push(...fn)` in `queueEffectWithSuspense`. This is exactly where a component's lifecycle hook array enters the suspense buffer. A large hook array would overflow there before ever reaching the scheduler. The change is low-risk and makes the fix complete across every path that buffers suspense effects, rather than leaving one spread in the same data flow.

Tests also favor A.
- **B's nested-merge test does not isolate the path it claims to test.** It calls `queuePostFlushCb(cbs)` with a 1M array inside the active flush, so before the fix it would overflow in `queuePostFlushCb` first. It never checks the `activePostFlushCbs` merge on its own.
- **A's nested test isolates that path.** It queues the callbacks in 10k chunks so only the merge into `activePostFlushCbs` sees the full-size array. It also catches the error so a failure doesn't corrupt scheduler state for later tests.
- **A adds a Suspense integration test that B lacks.** In it, an inner suspense resolves first and merges 1M buffered `onMounted` effects into a still-pending outer suspense. This exercises the `parent.effects` merge and `queueEffectWithSuspense` paths end to end, and checks that the effects are deferred and then all run.

B adds no test for the Suspense code it changed.

Craft is comparable: B's comments are slightly more explanatory, but this doesn't outweigh A's more complete fix and better-targeted tests.

Steps to reproduce

  1. Open the playground and show the Preview pane.
  2. The app renders a <Suspense> whose default slot contains an async component (resolves after ~4s) plus a large tree (2000 rows, each with a few flush: 'post' watchers).
  3. While the suspense is pending, a timer keeps mutating a ref, so the still-mounted tree re-renders repeatedly. Each re-render buffers its post effects into suspense.effects (via queueEffectWithSuspense).
  4. When the async component resolves, the suspense flushes the buffered effects.

What is expected?

The buffered effects flush and the app keeps working.

What is actually happening?

Uncaught (in promise): RangeError: Maximum call stack size exceeded — thrown from queuePostFlushCb called by suspense.resolve():

RangeError: Maximum call stack size exceeded
    at queuePostFlushCb (runtime-core.esm-bundler.js:331)
    at Object.resolve   (runtime-core.esm-bundler.js:7426)

The scheduler dies mid-flush, leaving the app permanently wedged (blank page).

Root cause

suspense.effects is unbounded — every post effect of every component under a pending suspense boundary is buffered into it. On resolve, the whole array is flushed with a spread call:

  • scheduler.ts: pendingPostFlushCbs.push(...cb)
  • scheduler.ts (flushPostFlushCbs nested case): activePostFlushCbs.push(...deduped)
  • Suspense.ts (merge into pending parent): parent.effects.push(...effects)

Spreading an array into a function call is limited by the engine's call stack (~100k–200k args in V8), so once enough effects accumulate the flush itself throws.

Real-world impact

We hit this in production in a Nuxt app: a kanban board page with ~1000 mounted cards that re-renders once per second (elapsed-time ticker). Navigating to another page keeps the board mounted under <NuxtPage>'s pending Suspense; its buffered effects exceed the spread limit and every SPA navigation away from the board crashes with a permanent white screen (hard reload of the target URL works fine, since there is no pending suspense in that case).

Suggested fix

Replace the unbounded spread pushes with plain loops. I have a PR ready with the fix and a regression test (queuePostFlushCb with a 1M-entry array).

What the agent reported

I fixed the crash: a suspense with a very large number of buffered effects now flushes them without RangeError: Maximum call stack size exceeded. The full suite passes with the fix (./bt-test: 182 files passed, 1 skipped; 3635 tests passed, 6 skipped, 0 failed).

What was wrong: while a <Suspense> is pending, its post effects pile up in suspense.effects with no limit. Several places then copied whole arrays using push(...array). Passing a huge array as function arguments is limited by the call stack, so once enough effects build up, the flush throws partway through and the scheduler stops working.

What I changed: I replaced each push(...array) with a plain for loop that pushes the same items in the same order.

  • packages/runtime-core/src/scheduler.ts:
  • queuePostFlushCb: pendingPostFlushCbs.push(...cb)
  • flushPostFlushCbs, nested case: activePostFlushCbs.push(...deduped)
  • packages/runtime-core/src/components/Suspense.ts:
  • resolve(), merging into a pending parent: parent.effects.push(...effects)
  • queueEffectWithSuspense: suspense.effects.push(...fn). The report didn't list this one, but a component's array of lifecycle hooks goes through it before any of the other three, so the same scenario would still crash there.

Tests added:

  • scheduler.spec.ts, "should not overflow the call stack when queueing a large array": calls queuePostFlushCb with 1,000,000 callbacks and checks they all run. This is the test the report suggested.
  • scheduler.spec.ts, "should not overflow the call stack when nested flushPostFlushCbs merges a large queue": covers only the nested merge.
  • Suspense.spec.ts, "nested suspense (child resolves first) with a large number of buffered effects": this is the reported scenario. An inner suspense holding 1M onMounted hooks resolves while the outer one is still pending. The test checks the final rendered output and that all 1M hooks ran.

Test evidence:

  • Without the fix: I set the production changes aside and ran the two spec files directly with vitest. All three new tests failed with RangeError: Maximum call stack size exceeded, and the other 95 tests passed.
  • With the fix: the new Suspense test passed on its own, and the full ./bt-test run above includes all three new tests.
  • ./bt-test with file arguments refused to run (exit 64; its fixed command can't take extra arguments). That's why the targeted runs used vitest and the gate was the full suite.
  • A reviewer agent checked the diff and found no blocking issues. It suggested that 1M entries makes the tests slower than needed and 200k–500k would still trigger the bug. I kept 1M to match the report's suggested test.

Requirements:

  1. Fix the spread in queuePostFlushCb: done, covered by the first scheduler test.
  2. Fix the spread in the nested flushPostFlushCbs case: done, covered by the nested scheduler test.
  3. Fix the spread when merging into a pending parent suspense: done, covered by the Suspense test.
  4. Use plain loops, as the report suggested: done.
  5. Add a regression test with a 1M-entry queuePostFlushCb array: done.
