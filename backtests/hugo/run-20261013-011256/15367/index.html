Allow symlinks for mount source for the main project

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

The production code changes are the same. Both wrap the `isSymlinkOrHasSymlinkParent` check in `if !rm.IsProject`, so the main project's mount roots and their parent directories may be symlinks while theme and module mounts are still filtered. This fixes the root cause in the issue: commit 938c820 dropped every symlinked mount root without exempting the trusted main project. Neither patch differs in correctness or scope. B's code comment gives a slightly better rationale (the project can already use absolute sources, so a symlink adds no new risk), but that is minor.

The tests decide it. Patch A reproduces the issue's exact scenario. It mounts `_build/includes/project-a` to `content/project-a`, where `project-a` is a symlink to an external directory sitting under a real parent directory. It then checks that the external page is resolved (`site.GetPage "/project-a/extpage"` returns the title) and published (`project-a/` and `extpage` appear in the public tree). It correctly re-adds the `content` mount, because user mounts replace the defaults. It also covers a symlinked root and a symlinked parent for asset mounts, checking actual file content. It narrows the negative glob to `theme*/**`, so the theme-symlink rejection is still tested. It keeps `! stdout rootdirfile` valid by using `.Content` instead of `.Publish`.

Patch B tests only asset mounts (a symlinked root, a symlinked parent, and a subdir via the root). It keeps the theme negatives with `thememount*/**` and `! stdout thememount`. It is adequate, but it never exercises the content-mount case from the issue. It also drops the `! stdout rootdirfile` guard and replaces it with a weaker check.

Both test sets would fail before the change and pass after it, but A's coverage maps directly to the reported use case, so A is better.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The issue

View on GitHub

Hugo 0.166.0 introduced commit https://github.com/gohugoio/hugo/commit/938c820626bd0a524dc1482cbe83b6c2e1171d20 (hugofs: Drop symlinked mount roots) that breaks a legit use-case of symlinks.

In my case, I mount a directory in my hugo.yaml:

module:
  mounts:
    - source: "content"
      target: "content"
    # Mount content generated in another repository
    - source: "_build/includes/project-a"
      target: "content/project-a"

_build/includes/project-a itself can be a symlink to another local directory, e.g. ../../../project-a, which allows quick local debugging. In production, a CI workflow may clone the Git repo of project-a to this destination which does not trigger the problem.

I am not familiar with the internals of hugofs and the security concept, but would appreciate if users could trust certain mounts, and therefore bypass the newly introduced hard drop of symlinks.
