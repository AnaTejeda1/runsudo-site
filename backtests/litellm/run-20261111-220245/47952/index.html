[Bug]: /v1/messages/count_tokens returns 500 for a search_result block, and for any content block type the local counter does not list

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the issue the same way at the root: a `search_result` TypedDict, a counting branch for title/source/content, a `ValueError` subclass for unknown block types, and a mapping of that subclass to a 400 `invalid_request_error`. All ten independent tests pass on both, so correctness is equal on the issue's scenarios. The differences are in where the 400 is produced and what the client sees. Patch B maps the error inside `count_request_tokens` in proxy_server.py, around the local estimate call, so every caller of the shared counting path (not only the Anthropic route) stops answering 500, and it emits a clean message ("Token counting does not support content blocks of type 'future_block'") carrying the type on the exception and preserving the chain with `from e`. Patch A maps it only in the Anthropic endpoint and returns the internal wrapped string as the client message ("Error getting number of tokens from content list: Invalid content item type: ... default_token_count=None"), which names the type but leaks counter internals; its `raise (X if isinstance(...) else ValueError)(...)` re-raise is also awkward. B's TypedDict includes the documented `cache_control`/`citations` fields consistent with the neighbouring document param and has an explicit `_count_search_result_tokens` that recurses through `_count_content_list` for nested content; A reuses the generic `_count_anthropic_content` and adds the type to the user/tool_result unions, which is reasonable too. On tests, A is slightly stronger: it includes a negative control (an `image` without `source` still yields 500 api_error) and a default_token_count fallback check, while B covers unit, nested, and endpoint-level 200/400 cases without that control. Weighing craft of the fix and user-facing error quality over A's marginally better tests, B is the better patch.

Description

POST /v1/messages/count_tokens answers HTTP 500 when a message contains a search_result content block, which is a documented Messages content block (Search results). The same happens for any block type the local token counter does not know, so a client that counts a conversation before sending it (as coding agents do for context management) gets a server error instead of a count or a clean refusal.

Expected: count_tokens accepts the same content as /v1/messages and returns {"input_tokens": n} (for search_result, counting its title, source and content text, as the other text-bearing blocks are counted); a block type it cannot count is refused with a 400 invalid_request_error naming the type, per the Anthropic Token counting guide ("supports the same structured list of inputs" as Messages). Never a 500.

Observed on LiteLLM 1.105.1 / vLLM 0.31.0 dev build, 2026-10-22. (On 1.105.1 the body is FastAPI's {"detail": ...}; #46815 moves it to the Anthropic envelope in 1.105.3 / 1.106.2, but the status stays whatever the route maps a ValueError to.)

Steps to Repro

  1. A search_result block:
curl -s -w '\nHTTP %{http_code}\n' http://localhost:4000/v1/messages/count_tokens \
  -H "Authorization: Bearer $LITELLM_API_KEY" -H 'anthropic-version: 2023-06-01' -H 'content-type: application/json' \
  -d '{"model":"glm-5.3","messages":[{"role":"user","content":[{"type":"search_result","source":"https://docs.example.invalid/notes","title":"Project notes","content":[{"type":"text","text":"The code word is 7f3a."}]},{"type":"text","text":"Reply with only the code word you were given, or NONE."}]}]}'

HTTP 500:

{"detail":{"error":"Internal server error: Error getting number of tokens from content list: Invalid content item type: search_result. Expected str or dict with 'type' field (text, image_url, image, document, file, tool_use, tool_result, thinking, redacted_thinking, tool_reference)., default_token_count=None"}}
  1. A block type the counter does not list (a stand-in for a block introduced by a newer client):
curl -s -w '\nHTTP %{http_code}\n' http://localhost:4000/v1/messages/count_tokens \
  -H "Authorization: Bearer $LITELLM_API_KEY" -H 'anthropic-version: 2023-06-01' -H 'content-type: application/json' \
  -d '{"model":"glm-5.3","messages":[{"role":"user","content":[{"type":"text","text":"Reply with the single word: ok"},{"type":"future_block","future_block":{"value":"ignore me"}}]}]}'

HTTP 500, same message with Invalid content item type: future_block.

  1. Expected: (1) HTTP 200 {"input_tokens": <n>}; (2) HTTP 400 {"type":"error","error":{"type":"invalid_request_error","message":"... future_block ..."}}. Control on the same proxy: the same request with a document, image, tool_result or redacted_thinking block instead returns 200 with a count.

Possible cause (a lead, not a confirmed cause): _count_content_list() in litellm/litellm_core_utils/token_counter.py handles text, image_url, image, document, file, tool_use, tool_result, thinking, redacted_thinking and tool_reference, and raises ValueError("Invalid content item type: ...") for anything else; the route turns that into a 500. On main the list is the same. A search_result branch (count title, source and the text in content), and mapping the remaining ValueError to a 400 rather than a 500, would cover both cases. We have not run main, where #46772 added a 400 for blocks the OpenAI and Gemini count conversions cannot handle; it is not clear to us whether that path is taken for a locally counted hosted_vllm deployment.

Related: #44784 (open, same error for compaction blocks), #47858 (open, tool_addition / tool_removal), #46772 (merged), #46815 (merged, error envelope).
