ValueError: zip() argument 2 is shorter than argument 1 for a generic type alias with type parameter defaults used with fewer arguments (regression in 2.14)

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the root cause the same way: when `__args__` is shorter than `__parameters__`, the missing trailing parameters are filled from `__default__` via `replace_types` (so defaults referring to earlier parameters work), and all six independent tests pass on both. The difference is in the surrounding behaviour. Patch A routes `get_standard_typevars_map` through the generic-model argument checker, so any length mismatch now raises `TypeError`. That is reasonable for the model path, where it fires at `Model[...]` subscription time, but in `get_standard_typevars_map` the lengths can legitimately differ: a `TypeVarTuple`/`Unpack` or `ParamSpec` parameter in a generic dataclass, TypedDict, or type alias yields more (or fewer) args than parameters, and A would turn the pre-2.14 working behaviour into a 'Too many/Too few arguments' TypeError raised mid schema generation. Patch B explicitly drops `strict=True` for that reason, restoring the 2.13 leniency (missing no-default parameter is left unmapped, as before) and only adds the default-filling loop, which is the minimal change the issue asks for. A's refactor also allocates a `typing_extensions.Sentinel` on every call and changes the error type on an unrelated path, which is risk beyond the ask. On tests, B is more thorough: it covers the TypeAliasType case, a model field, a default referring to an earlier parameter, the no-default omission, the variadic case, and the exact PEP 695 `type Pair[A, B = int]` example from the issue (skipped below 3.13, which is unavoidable since the syntax requires it). A's single test covers defaults and a default referring to another parameter but not the model-field scenario from the issue. A's deduplication of the mapping logic is a craft plus, but it is outweighed by the behavioural risk it introduces on variadic/ParamSpec generics and B's broader test coverage.

The issue

View on GitHub

Initial Checks

  • I confirm that I'm using Pydantic V2

Description

Since 2.14.0, a generic type alias (PEP 695 type statement or typing_extensions.TypeAliasType) whose trailing type parameter has a default (PEP 696) can no longer be subscripted with fewer arguments than it has type parameters. Schema generation fails with a bare ValueError raised by zip(). In 2.13.5 the same code works and the missing argument falls back to its default.

Traceback (most recent call last):
  ...
  File ".../pydantic/_internal/_generate_schema.py", line 1464, in _type_alias_type_schema
    typevars_map = get_standard_typevars_map(obj)
  File ".../pydantic/_internal/_generics.py", line 239, in get_standard_typevars_map
    return dict(zip(parameters, args, strict=True))
ValueError: zip() argument 2 is shorter than argument 1

At runtime Pair[str].__args__ is (str,), while Pair.__type_params__ has two parameters, so the strict zip() raises. strict=True was added to get_standard_typevars_map() in #13070 (Drop support for Python 3.9), together with the other zip() calls in the code base, so this looks like an unintended side effect rather than a deliberate change.

On 2.14.3, the related cases still work:

  • a generic BaseModel with a type parameter default (class Model[A, B = int](BaseModel) used as Model[str]),
  • the bare alias without subscription (TypeAdapter(Pair)), which uses the default,
  • the fully parameterized alias (Pair[str, int]).

Expected: missing trailing arguments are filled from the type parameters' __default__, as they are for generic models. If partially parameterized aliases are not meant to be supported, a PydanticSchemaGenerationError would be clearer than a bare ValueError from zip().

Example Code

from pydantic import BaseModel, TypeAdapter

type Pair[A, B = int] = tuple[A, B]

print(TypeAdapter(Pair[str, int]).validate_python(('a', 1)))  # works

print(TypeAdapter(Pair[str]).validate_python(('a', 1)))
# 2.13.5: ('a', 1)
# 2.14.3: ValueError: zip() argument 2 is shorter than argument 1


class Model(BaseModel):
    value: Pair[str]  # same error at class creation


# typing_extensions.TypeAliasType with TypeVar defaults fails the same way:
import typing_extensions

A = typing_extensions.TypeVar('A')
B = typing_extensions.TypeVar('B', default=int)
TEPair = typing_extensions.TypeAliasType('TEPair', tuple[A, B], type_params=(A, B))
TypeAdapter(TEPair[str])  # 2.14.3: same ValueError
