Worse

The merged fix was judged better than our patch.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the root cause the same way: they iterate over a shallow copy (`slice()`) of `this.scopes` in `pause()`, `resume()` and `stop()`. Both `stop()` regression tests are valid; each would throw before the fix and pass after. Patch B's test asserts a little more, such as the sibling's dispose spy firing once and the scopes being cleared. Patch A goes further on the issue's own complaint about the `resume()` loop: it also copies `this.effects` before calling `effect.resume()`. That loop has the same crash. A resumed sync watcher can run its callback, which stops a sibling watcher, and the watcher handle's stop removes that effect from `scope.effects`. The cached-length loop then reads past the end of the array. Patch A adds a test for exactly this case (pause, trigger, resume with `flush: 'sync'` watchers), and that test would fail without the change. So Patch A fixes a second real path to the same mutation-during-traversal crash, with low risk and code consistent with the rest of the fix. Patch B leaves that path vulnerable. Apart from this, the two patches are essentially identical in craft and scope, so the extra resume coverage gives A the edge.

Steps to reproduce

Open the reproduction link.
Click the "Trigger сrash" button.
Observe the output status on the screen or check the browser console.

What is expected?

The parent scope should stop all its children successfully. When a child scope stops a sibling scope during the cleanup phase, the parent traversal loop should handle the array mutation gracefully without throwing errors.

What is actually happening?

The application crashes with the following error: TypeError: Cannot read properties of undefined (reading 'stop')

This happens because EffectScope.stop loops over this.scopes using a cached length l. During iteration, one child's onScopeDispose calls stop() on its sibling. The sibling removes itself from the parent's scopes array, reducing the array size. When the parent loop continues to the cached index l, it tries to access an element out of bounds (which is undefined), causing the runtime crash.

System Info

System: OS: macOS, Browser: Chrome, Node: v20.19.5

Any additional comments?

The bug lies in packages/reactivity/src/effectScope.ts.

Inside EffectScope, the methods pause(), resume(), and stop() loop over this.scopes using a cached length without accounting for array mutations. Creating a shallow copy of the array before iterating (e.g. const scopes = this.scopes.slice()) safely resolves the issue.

What the agent reported

Calling parent.stop() no longer crashes when one child scope stops a sibling during cleanup. The new regression test failed before the fix and passes after it, and the wider test run passes.

What was wrong: In packages/reactivity/src/effectScope.ts, stop() walks this.scopes using the length it read before the loop started. Child scopes are stopped with stop(true), so they normally stay in the parent's list. But when a child's onScopeDispose calls stop() on a sibling without that flag, the sibling removes itself from the parent's scopes array. The array gets shorter, the loop reaches an index past the end, gets undefined, and throws TypeError: Cannot read properties of undefined (reading 'stop').

What changed:

  • Fix: pause(), resume() and stop() now loop over a shallow copy (const scopes = this.scopes.slice()) instead of the live array. In stop(), a sibling that already stopped itself is still in the copy, but stopping it again does nothing because it is already inactive. stop() still empties this.scopes afterwards. The loops over effects and cleanups are unchanged.
  • Test: I added one test to packages/reactivity/__tests__/effectScope.spec.ts, "should not throw when a child scope stops a sibling scope during parent stop". It builds a parent with child1 and child2, where child1's onScopeDispose calls child2.stop(). It then checks that parent.stop() doesn't throw, that all three scopes are inactive, that child2's cleanup ran exactly once, and that parent.scopes ends up empty.

Test evidence:

  • Before the fix: the new test failed with exactly the reported error. The other 20 tests in the file passed.
  • After the fix: the file passes, 21 of 21.
  • Wider check: every component and watcher uses EffectScope, so I also ran ./bt-test packages/reactivity packages/runtime-core: 59 test files passed and 1 was skipped; 1475 tests passed and 4 were skipped. No existing test was changed.
  • Review: a read-only review found the fix correct and in scope. git diff --stat shows only the two files above changed.

Requirements:

  1. The parent stops all its children without throwing when one child stops a sibling during cleanup: done, and covered by the new test (failed before, passes after).
  2. Fix the loop in stop() with a shallow copy, as the report suggests: done.
  3. Apply the same fix to pause() and resume(), which the report also names: done, without dedicated tests.
  4. resume() can run queued effects, which is user code that could stop a sibling scope, so the copy protects a real path. I didn't write a test for that path.
  5. pause() never runs user code, so its copy is only for consistency with the other two methods and the report's suggestion.
  6. The existing pause/resume tests still pass.

Everything is left as uncommitted edits in the working tree.
