Both patches resolve the core ask: mapping EllipsisType so `...` validates and round-trips in Python (Patch A via a new dedicated 'ellipsis' core schema in the Rust core; Patch B via reusing core_schema.literal_schema([...])). The decisive difference is on the top criterion, correctness, specifically JSON serialization. Ellipsis is not JSON-serializable. Patch A's tests are also broader and each is targeted (dedicated ellipsis_error, schema function, error-type table, JSON schema, and the type-adapter round trip), whereas B has a single test that verifies validation and Python dump but skips JSON dump. Patch B has real merits: it is minimal, pure-Python, avoids a coordinated pydantic-core rebuild, and its JSON-schema handling (PydanticOmit) is deliberately consistent with the existing MISSING sentinel precedent — arguably better craft than A's choice to raise handle_invalid_for_json_schema, which diverges from that precedent. Weighing correctness and test coverage (criteria 1 and 2) above the JSON-schema consistency and scope considerations, Patch A is the better fix.

Description

Ellipsis is a builtin type that pydantic does not support. Its usage is infrequent, but it can be useful to express placeholders:

This is a bit of a contrived example, but:

class Model(pydantic.BaseModel):
    m: list[list[float]]
    subset: tuple[int | Ellipsis, int | Ellipsis]

    def subset_arr(self) -> np.NDArray:
        return np.asarray(self.m)[*self.subset]

Here's how I implement this right now with an adapter: https://github.com/psalvaggio/scientific_pydantic/blob/main/src/scientific_pydantic/ellipsis.py

However, since this is a standard library type, I think this would be a good thing to live in pydantic itself.

Affected Components

  • Compatibility between releases
  • Data validation/parsing
  • Data serialization - .model_dump() and .model_dump_json()

  • Plugins and integration with other tools - mypy, FastAPI, python-devtools, Hypothesis, VS Code, PyCharm, etc.

What the agent reported

The change is complete. Here is the summary.

What was wrong

pydantic did not support types.EllipsisType (the type of the ... singleton) as a field type. A model with a field like subset: tuple[int | EllipsisType, int | EllipsisType] raised PydanticSchemaGenerationError: Unable to generate pydantic-core schema for <class 'ellipsis'>. (Note: the report's literal int | Ellipsis uses the value ..., which raises TypeError at annotation time in Python; types.EllipsisType is the correct spelling — the same one the reporter's own reference adapter uses.)

What I changed

Two production files, mirroring the existing MISSING sentinel singleton precedent:

  1. pydantic/_internal/_generate_schema.py — imported EllipsisType and added it to the _handlers dict right after NoneType: EllipsisType: lambda self, obj: core_schema.literal_schema([...]). This makes an EllipsisType field validate only the ... singleton (raising literal_error otherwise) and serialize it in Python mode.
  2. pydantic/json_schema.py — added a guard at the top of literal_schema: if schema['expected'] == [...]: raise PydanticOmit. Since ... has no JSON representation, the field is omitted from the JSON schema exactly as the MISSING sentinel does. A normal Literal can never contain the ... singleton, so ordinary literals are unaffected.

Test evidence

  • Added test_ellipsis_type in tests/test_types.py (after test_none) covering the report's scenario: bare EllipsisType field, int | EllipsisType union, and the tuple[...] example; asserts singleton validation, literal_error on bad input, Python-mode model_dump round-trip, and the exact JSON schema.
  • Confirmed the test failed before the fix (PydanticSchemaGenerationError) and passes after.
  • Blast-radius gate: ./bt-test tests/test_json_schema.py tests/test_missing_sentinel.py tests/test_types.py → 1482 passed, 6 skipped, 3 xfailed — no regressions in literal/JSON-schema handling.
  • Reviewer approved; verified no unrelated changes and no scratch files.

Requirements disposition

  • Support Ellipsis/EllipsisType as a field type — ✅ implemented (validation + Python serialization), with test evidence.
  • Report's example (tuple[int | EllipsisType, int | EllipsisType]) — ✅ works and is asserted in the regression test.
  • JSON schema behavior — ✅ handled: the non-JSON-representable field is omitted, mirroring the MISSING sentinel (reviewer flagged, and confirmed, this as a defensible choice — for a required bare field the schema is mildly lossy, but ... is fundamentally inexpressible in JSON).
  • JSON value serialization (model_dump_json) — not implemented: serializing ... to JSON raises PydanticSerializationError, since the singleton has no JSON form (consistent with the MISSING sentinel). Not requested in the report; left as-is deliberately rather than inventing a surprising encoding (e.g. null, which would be ambiguous in unions).

All changes are left uncommitted in the working tree.
