Add method Elements.before(Node node)

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches add `Elements.before(Node)` and `after(Node)`, and both resolve the issue. They differ in what happens to the supplied node.

Patch A follows jQuery's model. Each target except the last gets a deep clone, and the last target gets the original node, which is moved. The clones are all made before any insertion, so they don't capture earlier insertions into the node's own subtree. A test (`beforeNodeContainingMatches`) covers this case.

Patch B clones for every target and leaves the original untouched. That matches the user's `outerHtml()` workaround, so it is also reasonable. However, B makes each clone lazily inside the loop. If the supplied node contains any of the matched elements, earlier insertions change the node before it is cloned again, and later copies include those earlier clones. B neither handles nor tests this.

Placement: A puts the logic in `Nodes`, alongside the existing `Nodes.before(String)` and `after(String)`, and adds covariant overrides in `Elements`. This follows the existing class split and also gives the feature to `Nodes<TextNode>` and similar collections. B adds the methods only to `Elements`.

Tests: A's are stronger. They cover identity of the original versus the clones, a single-element chain, the self-containing case, and the `Nodes` variants. B tests output and that the original keeps a null parent.

Scope: B also adds `prepend(Node)` and `append(Node)`. That is beyond the ask, so it is neutral. B also removes the `Iterator` and `Predicate` imports from `Elements.java`. That is unrelated churn, and if either import is still used it breaks compilation.

Overall, A is more complete, better structured, better tested and lower risk.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
