The issue

View on GitHub

Currently, when you invoke .Page.Render and pass it the name of a non-existent template, the method returns an empty string without warning or error. This isn't anything new; Hugo has behaved this way since 0.54.0, and probably earlier.

There may be a good reason for the existing behavior, but it was surprising to me.

Reviewer returned PASS. The fix is complete and verified.

Summary

What was wrong
In hugolib/page__per_output.go, the (*pageContentOutput).Render method resolved the requested layout via resolveTemplate, which returns a found boolean. When a template/view name passed to .Render didn't exist, found was false and the method silently did return "", nil — producing empty output with no error (issue 15052).

What I changed

  • hugolib/page__per_output.go — the single !found branch now returns an error instead of swallowing it: go if !found { return "", pco.po.p.wrapError(fmt.Errorf("failed to resolve layout %q", layout[0])) } This mirrors the existing partial "not found" pattern. It's scoped only to the user-invoked .Render path (which sets LayoutFromUserMustMatch = true); the normal site-render path in site_render.go calls resolveTemplate() with no args and still tolerates missing layouts, so page building is unaffected. No imports added (fmt/errors already present).
  • hugolib/hugolib_integration_test.go — added the regression test TestRenderViewNotFound verbatim from the report (asserting err is non-nil when .Render "view_bar" targets a missing view), plus the qt "github.com/frankban/quicktest" import.

Test evidence (via ./bt-test, in-container go test)

  • Test-writer confirmed the regression test FAILS pre-fix: got nil value but want non-nil.
  • Clean gate run with the fix, EXIT=0, no build/setup issues:
  • TestRenderViewNotFound → pass (regression)
  • TestRenderWithoutArgument → pass (existing, related)
  • TestRenderString → pass (existing, related)

Notes

  • One deliberate behavioral tradeoff (flagged by the reviewer, non-blocking): a view existing for one output format but not another will now hard-error rather than emit empty output — this is exactly the "fail loudly" behavior the issue requested.
  • A transient [setup failed] during one run was a harness artifact (missing zz_probe_test.go), not related to the change; a clean rerun confirmed green.
  • The AGENTS.md / CLAUDE.md deletions in the working tree are pre-existing and out of scope — left untouched. All changes are left uncommitted.
