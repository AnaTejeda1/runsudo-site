Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

The issue identifies the root cause as the Python fallback in `_validators.py` doing `x % multiple_of` without validating the divisor, and names Fraction, temporal types, and complex as users of that fallback. Patch A fixes exactly that: it adds `check_multiple_of_constraint` and calls it at the fallback site in `apply_known_metadata` (and in the experimental pipeline's Python path), so every type routed through `multiple_of_validator` now fails at schema generation with the same message pydantic-core uses for int/float/Decimal. That covers Fraction, timedelta, complex, and also int/Decimal wrapped in function schemas (AfterValidator), with careful handling of Decimal('1e400'), huge ints, NaN/inf, and non-float types. Its tests are broad and would fail before the change (Fraction, timedelta, complex, int/Decimal function-schema, pipeline), and the test_types.py edit preserves the original intent of that test now that a 0 divisor is rejected earlier.

Patch B instead adds native `multiple_of` support to the Rust Fraction and Timedelta validators and reroutes those two types to core. That is a larger cross-repo feature (pydantic-core Rust + schema TypedDicts + a required core release) rather than a fix of the stated root cause. The unvalidated fallback remains: `complex` (explicitly named in the issue), int/Decimal under function schemas, and the pipeline still raise ZeroDivisionError. Its tests only cover Fraction and timedelta. Both patches pass the independent tests, but those tests only probe Fraction and timedelta, so they do not expose B's remaining gap.

A resolves the issue at its root with narrower, lower-risk scope and stronger tests; B masks the symptom for two types via a redesign and leaves the reported fallback problem in place for others.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Description

Field(multiple_of=0) is rejected during schema generation for int, float, and Decimal, but equivalent non-native numeric types still pass schema generation and raise an uncaught ZeroDivisionError during validation.

Reproduction

from fractions import Fraction
from pydantic import BaseModel, Field

class Model(BaseModel):
    value: Fraction = Field(multiple_of=0)

Model(value=Fraction(1, 2))

Actual: validation raises ZeroDivisionError rather than ValidationError.

Expected: model definition fails with a schema-generation error stating that multiple_of must be greater than zero, consistently with native numeric types.

The Python fallback in pydantic/_internal/_validators.py performs x % multiple_of without validating the divisor. Fraction, temporal types, and complex use this fallback. I found no existing report for the remaining types after the native numeric fix.
