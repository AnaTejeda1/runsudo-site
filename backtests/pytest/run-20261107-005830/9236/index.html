LogCaptureHandler can be garbage collected when caplog fixture is in use

Worse

The merged fix was judged better than our patch.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Root cause: the conftest hookwrapper's `outcome.get_result()` raises in its teardown, and older pluggy then skips the remaining old-style wrapper teardowns, leaving the logging plugin's `pytest_runtest_call` wrapper suspended inside `with catching_logs(caplog_handler)`. When that generator is later garbage collected, the `with` exit removes the shared caplog handler from the root logger mid-way through the next test. Patch A fixes this at the source by requiring pluggy>=1.6, where remaining wrapper teardowns are run even after one raises; this also fixes the same skipped-teardown hazard for every other wrapper (capture, etc.), not just logging. Its regression test reproduces the issue's exact scenario (noop hookwrapper + failing test + gc.collect in a caplog test), runs in a subprocess with a clear explanation of why in-process would mask it, and would fail on the old pluggy / pass on the new one. The changelog entry is in the correct packaging category. Patch B instead papers over the symptom inside pytest: it adds a module-level global registry of active `catching_logs` blocks, out-of-order exit detection, handler-sharing checks, and a heuristic hand-off of `orig_level` to the newest active block. This is a non-trivial amount of new global mutable state and logic for a situation that only arises because of a pluggy bug, it leaves that bug (skipped wrapper teardowns) unaddressed for every other plugin, and it adds risk of subtle level/handler mismanagement in nested or multi-handler uses of `catching_logs`. B's unit tests are well constructed and would fail-before/pass-after, which is a genuine strength, but correctness at the root cause and scope weigh more heavily. A resolves the reported issue cleanly and minimally; B is a broader defensive redesign that masks rather than fixes.

The issue

View on GitHub
  • a detailed description of the bug or problem you are having

In our tests we have had issues with the caplog fixture not correctly saving every log into caplog.messages and caplog.records. From what I can tell, the underlying issue is that in some circumstances the LogCaptureHandlers that caplog relies on can get garbage collected.

There seem to be a lot of issues in this area (#5160, #8977, #7335 etc.), but I'm not sure if any of them are the specific case that I have experienced.

  • minimal example if possible

Some debugging has got me to the stage where I have a MWE that reproduces the problem:

test.py:
