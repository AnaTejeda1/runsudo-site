[Bug]: MCP tools/call with an unprefixed tool name on /{server_name}/mcp resolves via the global tool-name mapping, not the server in the path (404 when cold, 403 when another server has a tool with the same name)

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches make the same core change: when the request is scoped to a single server (/{server_name}/mcp or x-mcp-servers), pass that server's id as requested_server_id to execute_mcp_tool so an unprefixed name resolves against the path server rather than the last-listed-wins global mapping. Both pass all six independent tests covering cold, collision, flip, and delete scenarios. The differences are at the edges. Patch B's narrowing condition (`mcp_servers` non-empty and allowed servers narrowed to one) is a closer match to 'the scope names one server' than Patch A's requirement that the raw list have exactly one entry, so B also handles a header naming two servers where only one is allowed to the key, or an alias plus id for the same server. More importantly, B keeps billing consistent with routing: on base, dispatch and billing_auth_for_tool_call both consulted the tool-name mapping, so they agreed. Patch A changes dispatch to the scoped server but leaves billing on the mapping, so in the issue's collision scenario the call now runs on server_b while spend is attributed to server_a's granting team. B threads mcp_servers into billing_auth_for_tool_call and adds a test (including case-insensitive scope) proving the billed team matches the routed server. That is adjacent work, but it closes a mismatch the fix itself creates, so it counts for correctness rather than being neutral churn. Costs of B: an extra allowed-servers lookup on the billing path and a lazy import from operations inside the auth module, both modest. Patch A's strengths are a tidy named helper, a fresh-manager test rig, and a useful negative test that an ambiguous bare name still 404s rather than being guessed; B's integration test against the global manager with manual save/restore is more fragile. On balance B is the more complete fix for the scenarios the issue describes.

The issue

View on GitHub

Description

On a single-server MCP endpoint (/{server_name}/mcp), a tools/call with an unprefixed tool name is not resolved against the server in the URL path. LiteLLM resolves it through the process-wide tool_name_to_mcp_server_name_mapping, which is keyed by the unprefixed tool name, filled only by tools/list, and overwritten by whichever server was listed last. So the outcome depends on what any caller listed before:

  1. Cold mapping → 404. If nobody has listed the server since startup (or since another server was deleted, which removes its entries), the call returns Error: Tool '<tool>' not found. This still happens on v1.104.0, which already includes #42072 (_list_tools_before_first_call). The prefixed name works on the same cold worker.
  2. Name collision → 403. If two servers expose a tool with the same name, the mapping points to the server listed last. Calling the tool on the other server's endpoint returns Error: User not allowed to call this tool., even though the key can access the server in the path. Listing the second server flips it, and the first server starts returning 403.

One caller's tools/list changes how another caller's tools/call resolves. In our deployment, several servers share tool names (they are instances of the same MCP app, and all of them expose a common get_task_result tool), so calls fail intermittently depending on traffic.

The prefixed name (<alias>-<tool>) always works.

Config

Kubernetes, 1 replica, DB-managed MCP servers (store_model_in_db: true), virtual keys

LiteLLM Version

v1.104.0

Steps to Repro

Setup:

  • Single replica and single worker.
  • Two DB-managed MCP servers, server_a and server_b, created through POST /v1/mcp/server with transport: http and auth_type: none. Both expose a tool with the same name, list_items.
  • $KEY is a virtual key with access to both servers.
  • The proxy has just been restarted.

Helper used in the steps below:

H=http://localhost:4000
call() {
  curl -s -X POST "$H/$1/mcp" \
    -H "Authorization: Bearer $KEY" \
    -H "Accept: application/json, text/event-stream" \
    -H "Content-Type: application/json" \
    -d "{\"jsonrpc\":\"2.0\",\"id\":1,\"method\":\"$2\",\"params\":$3}"
}

1. Cold mapping, unprefixed name → 404. It keeps failing on retries.

call server_b tools/call '{"name":"list_items","arguments":{}}'
{"jsonrpc":"2.0","id":1,"result":{"content":[{"type":"text","text":"Error: Tool 'list_items' not found"}],"isError":true}}

2. Same call with the prefixed name → OK.

call server_b tools/call '{"name":"server_b-list_items","arguments":{}}'

3. List server_a, then call server_b unprefixed → 403.

call server_a tools/list '{}'
call server_b tools/call '{"name":"list_items","arguments":{}}'
{"jsonrpc":"2.0","id":1,"result":{"content":[{"type":"text","text":"Error: User not allowed to call this tool."}],"isError":true}}

4. List server_b → server_b works, but server_a now returns 403.

call server_b tools/list '{}'
call server_b tools/call '{"name":"list_items","arguments":{}}'   # OK
call server_a tools/call '{"name":"list_items","arguments":{}}'   # 403
{"jsonrpc":"2.0","id":1,"result":{"content":[{"type":"text","text":"Error: User not allowed to call this tool."}],"isError":true}}

5. Delete server_b → unprefixed calls to server_a return 404 until server_a is listed again.

curl -s -X DELETE "$H/v1/mcp/server/<server_b_id>" -H "Authorization: Bearer $MASTER_KEY"
call server_a tools/call '{"name":"list_items","arguments":{}}'
{"jsonrpc":"2.0","id":1,"result":{"content":[{"type":"text","text":"Error: Tool 'list_items' not found"}],"isError":true}}

Expected behaviour

On /{server_name}/mcp, an unprefixed tool name should resolve against the server in the path. The result should not depend on which servers any caller listed earlier, and two servers exposing the same tool name should not affect each other.

Relevant code (v1.104.0, litellm/proxy/_experimental/mcp_server/)

  • mcp_server_manager.py (~6536): after listing, tool_name_to_mcp_server_name_mapping[original_name] = server.name. The key is the unprefixed name, so the last server listed wins.
  • mcp_server_manager.py (~6553): resolution checks that mapping first.
  • operations.py (~1890): first_call_target uses requested_server for unprefixed names. Since we still get 404 for unprefixed calls on /{server_name}/mcp, requested_server seems not to be set from the URL path on the MCP protocol route; #42655 points at the same thing. I haven't traced it further.
  • operations.py (~1965): when the mapping points to a server outside the ones allowed for the request path, the call returns User not allowed to call this tool.
  • mcp_server_manager.py (~2823-2846): deleting a server removes its mapping entries, which re-colds tools that other servers share.

Related

  • #42655 / #42072: single-server endpoint does not use the server in the path. Fixed for the cold-worker case in v1.104.0-rc.1, but unprefixed names on /{server_name}/mcp still fail.
  • #44373, #39751, #24089: cold or empty tool_name_to_mcp_server_name_mapping → 404.
  • None of these cover the cross-server collision (403) case.
