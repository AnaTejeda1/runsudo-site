In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches make the same three doc fixes. Each replaces `False` with `'not a complex number'` for `complex_type`. Each deletes the stale `string_sub_type` section. Each swaps `ImportString` for a `Callable`, which has no JSON schema, so the `invalid-for-json-schema` example raises again. Bare `Callable` versus `Callable[..., object]` makes no practical difference.

The patches differ in what else they do.

Patch B addresses the root cause the issue highlights: the docs suite cannot detect an example whose `except` branch never runs. B adds `test_error_examples_enter_except`. This test uses an AST transformer to record a sentinel at the start of every `except` block in the error-docs examples, then fails if any block is never entered. It honours skip, xfail and `requires` settings. It would have failed on all three broken examples before the fix and passes after, so it is a real regression test for the blind spot. B also keeps `test_validation_error_codes` consistent by excluding `string_sub_type` with a clear comment, rather than changing pydantic-core.

Patch A adds no test for the blind spot, so a future change like the complex-validation one could again silently make a docs section untrue. A also removes the `StringSubType` variant from the Rust error enum, the public `ErrorType` literal and the core error tests. The issue explicitly called this a maintainer decision, and the change is breaking for anyone constructing or matching that error type. A also makes an unrelated edit to `docs/concepts/experimental.md`, changing the partial-JSON example input from a truncated string `"12` to a closed `"12"`. This alters what that example demonstrates and its expected output, which is risky churn outside the issue's scope.

On correctness, both fix the three examples. On tests, B adds a meaningful detector and A adds nothing. On scope, A adds breaking-API and unrelated-docs risk. B is the better fix.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Description

Three examples on the error-reference pages no longer raise the error they document, and the documentation test suite cannot detect it.

Every example on those pages has the same shape: do something that should fail, catch it, then print or assert the error code. The only assertion lives inside the except branch. When the operation stops failing, that branch never runs, so nothing is printed and no assert is evaluated. run_print_check compares printed output against the #> comments, and an example whose print never ran produces no output to disagree with, so the example exits 0 and CI stays green while the page documents behaviour that no longer exists.

I checked this exhaustively rather than by sampling. I injected a sentinel as the first statement of every except block on both error pages and ran each example. Of the 152 examples containing a try/except at v2.13.5, all 152 run, and exactly 3 never enter their except branch. On main the count is 3 of 157. None of the three is marked test="skip", so all three are executed by CI today.

1. complex_type, docs/errors/validation_errors.md

Model(num=False) now validates successfully to 0j, so the #> 'complex_type' line never prints. This changed in 2.13.0b1 with #12498, which made complex validation call the complex() constructor unconditionally in Python mode, and complex(False) is 0j.

2. string_sub_type, docs/errors/validation_errors.md

The section says a strict str field rejects an instance of a str subclass. It does not: the example returns a plain str with the value 'foo', and #> 'string_sub_type' never prints. pydantic_core 2.49.0 still declares the error ("Input should be a string, not an instance of a subclass of str"), but I could not find any str schema that raises it. Building core_schema.str_schema() directly with strict=True, without strict, and with strict=True plus a pattern all accept a str subclass and return a plain str.

This looks intentional rather than accidental. #6261 reported exactly this behaviour as a bug in June 2023, was labelled bug V2, and was closed with the conversation moved to pydantic-core#786. So the check appears to have been removed on purpose and this documentation section was left behind describing it.

3. invalid-for-json-schema, docs/errors/usage_errors.md

ImportString has had a JSON schema since 2.8.0 via #9344, so Model.model_json_schema() succeeds and returns a plain string schema. The assert exc_info.code == 'invalid-for-json-schema' inside the except block has not executed since that release.

Output of the example code below

Identical on 2.13.5 and on main at 2.14.0b2:

2. no exception; accepted 'foo'
3. no exception; {'properties': {'a': {'title': 'A', 'type': 'string'}}, 'required': ['a'], 'title': 'ImportStringModel', 'type': 'object'}

Suggested fixes

  1. complex_type is a one-word fix. Model(num='not a complex number') still raises complex_type, and so do [], {} and a bare object(). Replacing False with any of those restores the example.
  2. string_sub_type needs a decision rather than a fix, which is the main reason I am opening an issue instead of sending a patch. Given the trail through #6261, the section probably wants deleting rather than repairing, and possibly the error variant too, but that is your call.
  3. invalid-for-json-schema needs a type that genuinely has no JSON schema, in place of ImportString.

Separately, the blind spot itself is fixable. If an example on these pages had to demonstrate that the error occurred, for instance by printing inside the except and also failing loudly when nothing was raised, then a future change like #12498 would turn the docs red instead of silently making a section untrue. I am happy to send a PR for any or all of this, including that check as a test, if you tell me which direction you prefer.
