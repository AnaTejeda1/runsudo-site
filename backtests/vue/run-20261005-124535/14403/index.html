Preserve input values entered during hydration

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches use the same core approach. During hydration, `created` runs on an element that already has a parent, so each patch compares the element's live state with its markup-derived default, keeps the user's value, and writes it back to the model in `mounted`. They differ mainly in coverage.

**Patch A**
- It only handles elements whose `type` is exactly 'text' or 'textarea'.
- Every other `v-model` text-like input still gets reset during hydration: email, password, search, tel, url and number.
- Checkboxes, radios and selects also still get reset.
- These are exactly the form fields a user fills in on a slow page, so A only fixes part of the reported problem.
- Its CR/LF normalization is careful, but it is guarding a narrow case.
- It ignores the implicit `type="number"` cast that the existing `created` hook applies (`castToNumber`).
- It adds one test, for a plain text input only.

**Patch B**
- It detects user modification for every `v-model` target: all input types, textarea, checkbox, radio, select and select multiple.
- It handles browser value sanitization (range clamping, number parsing) by comparing against a fresh element with the same attributes. This avoids false positives on untouched fields.
- It works out the default select index the same way the browser does, including disabled options and optgroups.
- It handles the tricky case of several checkboxes sharing one array or Set model during hydration. It accumulates the pending assignments, because the binding value is stale until the next re-render.
- It applies the same cast for implicit `type=number` as the existing `created` hook.
- It refactors the existing change handlers into shared helpers (`assignCheckboxValue`, `assignSelectValue`) without changing their behavior.
- Its tests cover every element kind, the `.trim`/`.number` modifiers and a dynamic `type`. They also include a negative test showing untouched fields (including range and select defaults) still follow the model.
- Every one of these tests would fail before the change.

**Trade-off**
B is more complex: a module-level `WeakMap` and per-element pristine-clone creation, though the clone is only created when the value differs. That complexity is justified by the issue's general 'inputs/forms' scope and does not obscure the fix.

B resolves the issue much more completely and has much stronger tests, so B is the better patch.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

entered input value is preserved once hydration completes

What is actually happening?

input value is reset to its default value

Any additional comments?

This is affecting UX when interacting with inputs/forms in slowly loading apps, where values entered during hydration phase are erased and the progress is lost. I have been blocking all forms myself until mounted hook fires to workaround this issue - it would be great to not have to!
