panic: slice bounds out of range in contentNodeShifter.Delete when removing draft pages from a multilingual taxonomy

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

The two production changes are essentially the same. Both change `Shifter.Delete` to return (updated, deleted, wasDeleted, isEmpty) and `DeleteFunc` to return (updated, isEmpty). Both stop mutating the slice in place while ranging over it, which was the source of the out-of-range panic when several entries in one `contentNodes` matched. Both also write the updated value back to the tree in `NodeShiftTree.delete` and `DeleteFuncRaw` when the node is not empty. The only logic difference is in the `contentNodes` branch: when a child is not deleted, A keeps the original child, while B keeps `updated` unless `isEmpty` is set. Every shifter case returns the original child when nothing was deleted, so the two behave the same apart from a trivial edge case (an already-empty nested map). Correctness is therefore a wash.

The difference is in the tests. B's test only calls the shifter directly, covering multiple matches, delete-all and delete-none. A tests the shifter directly for both `Delete` and `DeleteFunc` with multiple matches. It also adds tree-level tests that insert a multi-site `contentNodes`, delete one language at a time through `Shape(...).Delete` and `DeleteFuncRaw`, and check the stored value after each step. That covers the second half of the root cause (the tree keeping a stale or corrupted slice between deletes across languages) and matches the issue's scenario of dropping pages in several languages. Scope and craft are comparable. A's more complete, integration-level tests make it the better patch.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The 0x35 in delete(..., {…, 0x35}) is 53, exactly the byte length of the key being removed (/blog/ plus a 47-character slug).

Only on the page-removal path

hugo -D (drafts included) builds fine. The panic appears only when a page is removed from the tree, which makes it invisible in local preview and fatal only in production.

A future publishDate panics identically. Setting [_build] render = "never" / list = "never" on the same pages avoids it entirely — consistent with those pages never being added to the tree, so nothing is deleted.

What I ruled out

Site: 8 languages, ~1,490 pages per language, ~11,455 content files, categories taxonomy.

  • Not a regression. 0.159.1 and 0.164.0 behave identically.
  • Not the number of drafts. 96 draft pages build fine; 16 panic.
  • Not slug length. The panicking key was 47 chars, but renaming an unrelated post to exactly 47 chars builds fine.
  • Not the slug. Renaming the offending page does not help.
  • Not byte layout. Deleting a front-matter line, or adding a blank one, still panics.

Swapping page content at a fixed path isolates it to front matter. Changing categories = ["Airport Operations"] on the offending page to any other value clears the panic — and so does moving a different page out of that same category while leaving the offending one alone. So the trigger is combinatorial: some particular set of pages being deleted from one taxonomy term corrupts the shifter, rather than any single page being malformed.

Reproducer

I have not managed to minimise it, and I want to be upfront about that. Synthetic multilingual sites (8 languages, 12 blog + 200 glossary pages sharing one taxonomy term, varying draft counts) do not reproduce, so something else in the real tree is required. The affected repository is private.

I am happy to run patches or instrumented builds against the real site and report back, which may be faster than guessing at a minimal case.

What the agent reported

I fixed the panic and it's covered by new unit tests, but I couldn't reproduce it with a full site build, so no test builds a real site. The trigger in your site is still unidentified.

What was wrong. When one page path holds several nodes (for example one per language), those nodes sit in a list at that tree key. contentNodeShifter.Delete and DeleteFunc in hugolib/content_map_page_contentnodeshifter.go had two bugs in how they removed items from that list:

  1. They shortened the list while still looping over its original length. If more than one entry matched, the next removal went past the end, which is the slice bounds out of range [5:4] panic.
  2. The tree never received the shortened list. It kept the old length with the last entry duplicated. A production build drops a draft or future-dated page once per language, so the next delete at that key saw duplicates and panicked.

That fits what you saw: -D never drops anything, publishDate in the future fails the same way, _build never adds the pages, and the trigger looked like a combination of pages rather than one bad page. I checked this with a standalone copy of both loops: the old one panics on the 5th per-language delete of the same key, the new one doesn't.

What I changed:

  • content_map_page_contentnodeshifter.go: Delete and DeleteFunc now build a new list of the entries they keep instead of editing the list mid-loop, and return it.
  • hugolib/doctree/nodeshifttree.go: the internal Shifter.Delete and DeleteFunc interface now returns that updated value too. NodeShiftTree.delete and DeleteFuncRaw store it back in the tree when something was deleted and entries remain. The public NodeShiftTree methods keep their signatures.
  • hugolib/doctree/nodeshiftree_test.go: I only changed the signatures of the test shifter's Delete and DeleteFunc so it still compiles; no assertion changed.

Tests. There are four new tests in hugolib/content_map_page_contentnodeshifter_test.go:

  • Two call Delete and DeleteFunc directly on a list where two entries match the language being deleted.
  • Two delete one language at a time at a single tree key, which is what happens when a draft is dropped in each language. They check what the tree holds after each step, down to the key being removed.

Test evidence. ./bt-test could not run: every run ended with [setup failed] because the module proxy is unreachable. I ran go test directly against the module cache at /bt/cache/go-mod instead.

  • With the fix: all 4 new tests pass, go vet is clean, and every package under ./hugolib/... passes except 4 tests in hugolib itself. Those 4 are TestGitInfoFromGitModule* (3 tests) and TestModulePrivateRepo, and they fail the same way on the original code.
  • On the original code: both tree tests fail, with the tree holding ["b","c","c"] where ["b","c"] was expected. That is the duplicated-entry bug. The two direct tests can't compile against the old signatures, so they have no before-run.
