JSON schema ignores propagated config for stdlib dataclasses (extra='forbid' validates but no additionalProperties: false)

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the root cause the same way. In `dataclass_schema`, when the class's own config doesn't settle `extra`, they read `extra_fields_behavior` from the core schema config. That is the config validation actually uses after the earlier core-schema fix, so the JSON schema now agrees with the validator for both the nested-model and the `TypeAdapter(list[DC], config=...)` scenarios. Neither patch leaks the parent's title or `json_schema_extra` into the nested schema.

Patch A matches the issue's stated expectation exactly: it applies the propagated `extra` only when the dataclass has no `__pydantic_config__`. It builds a fresh config containing only `extra`, with a comment explaining why the other parent keys are skipped.

Patch B applies the fallback whenever `'extra'` is missing from the class config. In practice this is equivalent, because a class with its own config produces a core config without the parent's extra. But the condition is less direct, and readers must reason about that interaction to see it is safe.

On tests, both add parametrized forbid/allow/ignore cases that fail before the fix and pass after it, and both check consistency with validation. Patch A additionally asserts that the parent's title and `json_schema_extra` do not leak into the nested schema, and it covers a TypedDict alongside the dataclass. Patch B covers more dataclass variants, including one with its own `extra` and a pydantic dataclass. B also rewrites the unrelated `test_dataclass_with_extra_forbid`, which is a reasonable correction of a mislabeled test but is churn outside the issue's ask.

Overall the correctness is effectively equal. Patch A is slightly tighter in scope and clearer in intent, and its tests directly guard against the over-propagation risk.

Description

The docs (Configuration propagation) say that configuration is propagated to stdlib dataclasses that don't set their own. Validation does this. JSON schema generation doesn't.

#10928 fixed this in the core-schema generator (_internal/_generate_schema.py) by changing the default so the parent's config is used:

-            config = getattr(dataclass, '__pydantic_config__', ConfigDict())
+            config = getattr(dataclass, '__pydantic_config__', None)

The JSON-schema generator still has the same pattern. GenerateJsonSchema.dataclass_schema in json_schema.py, unchanged on main:

config = cast('ConfigDict', getattr(cls, '__pydantic_config__', {}))

with self._config_wrapper_stack.push(config):
    json_schema = self.generate_inner(schema['schema']).copy()

self._update_class_schema(json_schema, cls, config)

_update_class_schema then decides additionalProperties from that config, which for a stdlib dataclass without its own config is always {}, whatever the parent says.

So with a parent extra='forbid':

  • the nested stdlib dataclass rejects unknown keys (unexpected_keyword_argument);
  • its JSON schema doesn't say additionalProperties: false. Under JSON Schema rules, that means extra keys are allowed.

The schema and the validator disagree. This matters most where the schema is handed to a client that fills it in, such as LLM tool calling. The model is told extra keys are fine, then its answer is refused.

The same applies to TypeAdapter(list[SomeStdlibDataclass], config=ConfigDict(extra='forbid')).

Expected: for a stdlib dataclass with no __pydantic_config__, dataclass_schema uses the propagated config (the one validation uses) when deciding additionalProperties, so extra='forbid' produces additionalProperties: false.

Example Code

import dataclasses

from pydantic import BaseModel, ConfigDict, TypeAdapter, ValidationError


@dataclasses.dataclass
class Line:
    qty: int


class Order(BaseModel):
    model_config = ConfigDict(extra='forbid')
    line: Line


try:
    Order.model_validate({'line': {'qty': 1, 'typo': 2}})
except ValidationError as e:
    print(e.errors()[0]['type'], e.errors()[0]['loc'])
    #> unexpected_keyword_argument ('line', 'typo')    <- propagated: forbid

schema = Order.model_json_schema()
print(schema.get('additionalProperties'))
#> False
print(schema['$defs']['Line'].get('additionalProperties'))
#> None    <- expected False

adapter = TypeAdapter(list[Line], config=ConfigDict(extra='forbid'))
try:
    adapter.validate_python([{'qty': 1, 'typo': 2}])
except ValidationError as e:
    print(e.errors()[0]['type'])
    #> unexpected_keyword_argument
print(adapter.json_schema()['$defs']['Line'].get('additionalProperties'))
#> None    <- expected False
