RetryMiddleware doesn't actually retry HttpCompressionMiddleware errors

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

The issue asks that decompression failures in HttpCompressionMiddleware actually get retried, as the RETRY_EXCEPTIONS comment promises. Patch A delivers that under default settings: it catches the decompression error family in process_response and calls get_retry_request, honoring RETRY_ENABLED, RETRY_TIMES, dont_retry, max_retry_times, priority_adjust and give_up_log_level, and re-raises once retries are exhausted. The independent tests confirm it: all three fail on base and pass on A. Its tests are substantive (parametrized over gzip/deflate/br/zstd, exhausted-retry, dont_retry, RETRY_ENABLED=False, and a no-retry check for the max-size IgnoreRequest path), and the manager-level test shows a Request coming out of the full middleware chain. Weaknesses: it duplicates retry policy inside the compression middleware rather than routing through RetryMiddleware, ignores RETRY_EXCEPTIONS, and will retry even if RetryMiddleware itself is removed from DOWNLOADER_MIDDLEWARES. Those are design compromises, not failures to fix the issue.

Patch B attacks the root cause more structurally (exceptions from process_response reach the remaining process_exception methods, plus a new DecompressionError in RETRY_EXCEPTIONS), but gates the fix behind a new setting DOWNLOADER_MIDDLEWARE_RESPONSE_EXCEPTIONS that defaults to False. With defaults, nothing is retried; the independent tests fail on B exactly as on base, just with a renamed exception. Its own manager-level default test still asserts the failure propagates. So for existing projects the reported bug remains, and users who relied on catching OSError/BadGzipFile in errbacks now get a different exception type. B also carries significant unrelated churn and risk: it rewrites DownloaderMiddlewareManager to store None placeholders in the method deques, adds CloseSpider handling in the scraper and downloader manager with its own crawl tests, emits a deprecation warning on every process_response exception (including IgnoreRequest raised to drop a response) when any user process_exception exists, and changes the project template. None of that is needed to make retries work, and it widens the blast radius of the change.

On correctness for the scenario the issue describes, A resolves it and B does not by default; A's tests are stronger for the issue's behavior; B's scope expansion adds risk. A wins.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Each saw the issue and the two patches, labelled A and B in random order (two of them saw ours as A), with issue links and version numbers removed. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours. The reasoning above is one judge's, shown verbatim.

The issue

View on GitHub

A comment in the code of RetryMiddleware says

    # IOError is raised by the HttpCompression middleware when trying to
    # decompress an empty response

when including IOError in the exceptions to retry.

But IOError would be raised in HttpCompressionMiddleware's process_response(), errors from which are not handled by process_exception() in downloader middlewares.
