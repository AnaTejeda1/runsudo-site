Add resources.Publish

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches implement the same core fix. Each adds a `Publish` method on the resources namespace, registers it in `init.go`, type-asserts to `resource.Source`, calls `Publish()` and returns the resource. Either one lets `resources.Get "main.js" | js.Build | resources.Publish` work, so on correctness of the main path they are about equal.

The edge cases differ. Patch A takes `any` and checks the input explicitly:
- A nil input (for example, `resources.Get` on a missing file) gets a clear "must provide a Resource object" error.
- A non-resource value such as a string gets "string is not a Resource".
- A resource that cannot be published gets "can not be published".

Patch B takes `resource.Resource` directly. A nil input therefore surfaces as "<nil> can not be published", and a string fails during template argument conversion with a less specific message. Both behave safely, but A's errors are clearer for the cases users are likely to hit.

On tests, Patch A is much more thorough:
- It covers a plain resource, a minified transformation, and an image resize.
- It checks that a resource not passed through Publish is not written (`c.txt` absent), which shows publishing is actually triggered by the function.
- It adds table-driven failure tests for nil, page, and string inputs.

Patch B has a single happy-path test with minify. That test would fail before the change and is valid, but it is minimal.

On scope, Patch A also adds user docs and a `docs.yaml` entry. This is neutral to slightly positive and adds no risk.

Overall, Patch A wins on tests and on handling the edge cases.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
