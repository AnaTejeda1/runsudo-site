Issue #15153 Merged fix PR #15154 Run 1 Oct 2026 vuejs/core

Custom elements: async components nested ≥3 levels crash with TypeError: Cannot read properties of null (reading 'provides') — chained child resolve races its parent's mount

Worse

The merged fix was judged better than our patch.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the root cause the same way: the chained child's `_pendingResolve` now waits on the promise that settles after the element itself has loaded and mounted.

- Patch B does this by returning `this._pendingResolve` after calling `_resolveDef()` inside the chain callback.
- Patch A has `_resolveDef()` return the async loader promise (and the existing pending promise on early return), then returns that from the chain callback.

In both, the chain promise a grandchild captured at connect time now settles only after the middle element's async load and mount. That restores ancestor-first ordering at any depth and removes the null `parent._instance` dereference. On correctness they are effectively equivalent for the reported scenario.

Patch A also skips resolving a child that was disconnected while its parent was pending. This is extra hardening beyond the issue's ask, so it earns no credit on its own. It is small, guarded by `isConnected`, and covered by its own test, so it adds little risk.

The tests separate the two patches:
- Patch A's ancestor-first test uses manually controlled promises. It deterministically reproduces the exact race (inner and outer resolve first, middle resolves last) and checks both mount order and provide/inject inheritance through the shadow DOM output. It would fail before the fix and is not timing-sensitive.
- Patch B's test reproduces the issue's delay-based scenario with real `setTimeout` delays and a 100ms wait. It would also fail before the fix and checks provide/inject too, but it depends on wall-clock timing and is more prone to flakiness.

On craft, Patch B is slightly more minimal and has a helpful comment, while Patch A's `_resolveDef` return-value change is clean and consistent. Overall, the fixes are equal in correctness, and Patch A wins on its more deterministic tests.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

What is expected?

All three elements mount ancestor-first: mounted x-outer, mounted x-middle, mounted x-inner. The nested-async chaining added in 3.5.0 (37ccb9b, "delay mounting of custom elements with async parent", closing #9341 / #8127 / #9351) exists to guarantee exactly this.

What is actually happening?

mounted x-outer
UNHANDLED REJECTION: Cannot read properties of null (reading 'provides')
mounted x-middle

x-inner crashes in VueElement._mount → _inheritParentContext (runtime-dom — parent._instance.provides is dereferenced guarded only by parent && this._app), never mounts, and is left permanently half-resolved: _resolved: true, _instance: null, shadow root empty. Nothing ever retries it, no error surfaces through app.config.errorHandler, and any provide/inject inheritance it should have received is lost. Its own descendants (at deeper nesting) then crash against it in cascade.

Any additional comments?

Analysis (why depth ≥ 3 is the trigger)

connectedCallback of a child under a pending async parent chains:

this._pendingResolve = parent._pendingResolve.then(() => {
  this._pendingResolve = undefined;
  this._resolveDef();
});
  • For an unchained parent (depth 2), parent._pendingResolve is the parent's own _resolveDef() flow, which settles after the parent has mounted → 2-level nesting is safe. The variants table below confirms: 2 levels never crash.
  • For a chained parent (depth ≥ 3), parent._pendingResolve is itself a chain promise — and that promise settles when the parent's _resolveDef() returns (i.e. when the parent's async load starts), not when the parent mounts.

So once the first unchained ancestor mounts, the whole chain unwinds within a few microtasks: every deeper level's loader fires nearly simultaneously and mount order degenerates to network settlement order. Any child whose async definition settles before its parent has mounted hits _inheritParentContext while parent._instance === null and throws. With real-network chunk timings the victim set varies per load, so in an app this presents as a flaky, page-dependent breakage; with the fixed delays above it is 100% deterministic.

Variants checked (each re-run in a real browser):

VariantResult
3 levels, middle slowestcrashes every load
3 levels, inner slowestclean (race direction confirmed)
2 levelsclean (chained parent required)
plain <div> between levelsstill crashes (structure-independent)
markup inserted dynamically after all define() callsstill crashes
all loaders instantclean (microtask FIFO protects when nothing is pending)

_inheritParentContext (#13219, ~3.5.14) did not introduce the race — it converted a pre-existing silent misordering into a hard crash. 3.4.38 (no chaining) and 3.5.13 (chaining, pre-#13219) fail with the same null dereference in the older _setParent provides-copy path.

Suggested direction — either (or both):

  1. Chain the child to the parent's actual mount, not to _resolveDef() returning — e.g. resolve the parent's _pendingResolve only after _mount() has run, so the guarantee the chaining was built for ("ancestor mounts before descendant") holds at any depth.
  2. Guard _inheritParentContext against parent._instance === null and defer context inheritance until the parent instance exists, instead of throwing away the child permanently on an unhandled rejection.

What the agent reported

Async custom elements nested three or more levels deep now mount parent-first. The crash from the report is gone, and the full suite passes. The changes are uncommitted in the working tree.

What was wrong: In VueElement.connectedCallback (packages/runtime-dom/src/apiCustomElement.ts:313), a child under a parent that is still loading waits on that parent's pending promise. When the parent was itself waiting on its own parent, that promise was the parent's chain promise, which settled as soon as the parent's _resolveDef() returned. That is when the parent's async load starts, not when it mounts. So at depth 3, the inner element could finish loading and mount while the middle element's _instance was still null, and _inheritParentContext threw Cannot read properties of null (reading 'provides').

What I changed: One line plus a comment. The chain callback now ends with return this._pendingResolve. The chain promise then waits for the element's own async load, which settles only after resolve() → _mount(). Descendants therefore can't start before their parent has mounted, at any depth. For synchronous definitions _pendingResolve is undefined after _resolveDef(), so their behaviour doesn't change.

Test evidence:

  • New test: async & multiple levels of nested async custom elements (middle resolves last) in packages/runtime-dom/__tests__/customElement.spec.ts uses the report's setup: three async levels where the middle loads slowest (5ms / 30ms / 1ms). It checks that the mount order is outer → middle → inner, that the inner shadow root rendered, and that provide/inject works across all three levels.
  • Before the fix: the test failed on the inner element missing from the mount order, along with the exact TypeError ... reading 'provides' at _inheritParentContext.
  • After the fix: the whole spec file passes (78 passed, 1 skipped).
  • Full suite: ./bt-test won't accept targeted arguments, so I ran single files with the repo's vitest binary (unit-jsdom project) and then the full suite with ./bt-test: 3,637 tests, 0 failures, 0 errors.

Blast radius: Only elements that were waiting on an async parent are affected; they now wait for the parent to mount instead of for its load to start. That ordering is what the 3.5.0 chaining was meant to guarantee. The existing 2-level and multi-level nested tests still pass.

Reviewer notes: The reviewer found no blocking issues. One minor side effect: if a loader rejects, each element waiting on it now also reports its own unhandled rejection. Before, only the loader's rejection surfaced. This matches what direct children of a failing element already did.

Requirements:

  1. 3-level nesting where the middle loads last crashes; expected order outer → middle → inner: fixed, with the new test as evidence (fails before, passes after).
  2. Inner element left half-resolved, with lost provide/inject inheritance: fixed. The test checks the inner shadow root content and the injected foo and bar values.
  3. Suggested direction 1, wait for the parent's actual mount: implemented; this is the fix described above.
  4. Suggested direction 2, guard _inheritParentContext against a null parent instance: not done. With direction 1 in place, a waiting child never reaches _inheritParentContext before its parent has mounted. A silent guard would only hide that ordering bug and skip context inheritance instead of failing loudly, and I kept the change minimal.
  5. Variants table: the 2-level and instant-loader cases are covered by the existing nested-async tests, which still pass. The plain-<div>-between-levels case is in the new test. I didn't add separate tests for parser-created vs dynamically inserted markup, or for the case where the inner element loads slowest. Both go through the same connectedCallback code, and the second never crashed.
