Issue #15358 Merged fix PR #15363 Run 5 Nov 2026 · run-20261105-225610 gohugoio/hugo

tpl/collections: intersect/union/uniq collapse or drop distinct big integers beyond the float64 exact range

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the root cause the same way: `normalize` now keys integers exactly (int64/uint64) and only falls back to float for non-integral floats, and `intersector.handleValuePair` uses `hreflect.CompareNumbers` instead of float64 coercion. All independent tests pass on both, so correctness on the issue's own scenarios is equal.

The difference is in what else each patch changes and the risk it carries.

Patch A is tightly scoped. Its only non-number change is a narrow Union tweak that keeps an unconvertible big integer when the result slice is `[]any`. It also uses distinct named key types (`intKey`, `uintKey`, `floatKey`) so normalized numbers cannot collide with the raw `uint64` hashes that `normalize` already emits for uncomparable values; Patch B's `numericKey` returns bare `int64`/`uint64`/`float64`, which reintroduces a (rare) collision path between a big uint and a hashed map/slice that base did not have. A's tests cover in/intersect/union/uniq/complement/symdiff at unit and integration level, including mixed int/uint/float and the exact template from the issue.

Patch B rewrites `handleValuePair` to `hreflect.Indirect` both sides before the switch. That dereferences pointers, so the Pointer/Struct branch now compares `types.Unwrapv(v1.Interface()) == types.Unwrapv(v2.Interface())` on the pointee structs rather than on pointer identity. For Hugo's most common intersect use (`intersect site.RegularPages ...`), the pointees are `*pageState`, which contains slice fields and is not comparable, so this comparison would panic at runtime; even for comparable pointees it silently changes semantics from identity to value equality. The string branch also drops the `ToStringE` coercion, changing cross-type string/number intersect behaviour. B further rewrites Union's conversion logic (changing existing test expectations, e.g. `[]any{1,2} ∪ []int8{2,3}` now yields `int8(3)`) and makes a sizeable rewrite of `where.go`'s `in`/`not in` handling, dropping the float path and the type-mismatch guard. Some of that is arguably an improvement, but it is well beyond the issue's ask and each piece carries regression risk that the issue did not require.

B's tests are good (a thorough exact-number table across all ops plus where tests), roughly on par with A's. But on scope and craft, A delivers the fix with far less risk, and B's intersect change plausibly breaks a core use case. A wins.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours.
