Description

Description

When using a tool with a bare list parameter (e.g., def foo(items: list)), pydantic-ai sends the schema to OpenAI with strict=True, but OpenAI rejects it because
items: {} is invalid in strict mode.

The OpenAIJsonSchemaTransformer correctly handles other strict-incompatible features (like default values, oneOf, partial required, etc.) by either auto-fixing
them or marking the schema as is_strict_compatible = False. However, it doesn't check for empty items: {} in arrays.

Minimal Reproduction

  import asyncio
  from pydantic_ai import Agent
  from pydantic_ai.models.openai import OpenAIResponsesModel


  def tool_with_bare_list(items: list) -> str:
      """A tool that takes a bare list parameter."""
      return f"Got {len(items)} items"


  async def main():
      agent = Agent(
          model=OpenAIResponsesModel("gpt-5.1"),
          tools=[tool_with_bare_list],
      )
      result = await agent.run("Call tool_with_bare_list with items ['a', 'b']")
      print(result.output)


  asyncio.run(main())

Expected Behavior

Either:

  1. pydantic-ai detects that items: {} is not strict-compatible and sets strict=False, allowing the call to succeed in lenient mode
  2. Or raises a helpful UserError explaining that list needs a type parameter (e.g., list[str])

Actual Behavior

pydantic_ai.exceptions.ModelHTTPError: status_code: 400, model_name: gpt-5.1, body: {'message': "Invalid schema for function 'tool_with_bare_list': In context=('properties', 'items', 'items'), schema must have a 'type' key.", 'type': 'invalid_request_error', 'param': 'tools[0].parameters', 'code': 'invalid_function_parameters'}

Root Cause

In pydantic_ai/profiles/openai.py, the OpenAIJsonSchemaTransformer.transform() method handles various strict-incompatible features but the transformer doesn't check for empty items in arrays.

P.S: If the maintainers can confirm this, I would really like to fix this and make an open source contribution.

What the agent reported

The reviewer confirms the fix is correct, on-scope, and introduces no regressions. The work is complete.

Summary

What was wrong

OpenAIJsonSchemaTransformer.transform() (in pydantic_ai_slim/pydantic_ai/profiles/openai.py) had branches for objects, oneOf, default, and other strict-incompatible features, but no branch for arrays. A bare list parameter produces an array schema whose inner items is empty ({'type': 'array', 'items': {}}). OpenAI strict mode rejects items: {} ("schema must have a 'type' key"), yet the transformer left is_strict_compatible = True, so strict=True was still sent — causing the reported 400 ModelHTTPError.

What I changed

Added a type-dispatch branch chained off the existing if schema_type == 'object'::

elif schema_type == 'array':
    # OpenAI strict mode requires array items to define a schema with a type.
    # A bare `list` produces empty/missing `items` (e.g. `items: {}`), which strict mode rejects.
    if not schema.get('items') and self.strict is None:
        self.is_strict_compatible = False

This implements option 1 from the report: when the tool's strict is unset (None), the transformer now detects the incompatible empty items and reports is_strict_compatible = False. Downstream (models/__init__.py lines 1370/1380) that flips the request to lenient mode, where OpenAI accepts items: {}. Arrays with typed items (list[float] → items: {'type': 'number'}) are unaffected, and the explicit strict=True path is untouched.

Test evidence

  • New regression test tests/models/test_openai.py::test_strict_compatible_bare_list — builds {'type': 'array', 'items': {}} inside a valid object schema, walks the transformer with strict=None, and asserts is_strict_compatible is False.
  • Before the fix: FAILED (assert True is False).
  • After the fix: PASSED.
  • Adjacent strict/transformer tests re-run together (test_strict_schema, test_transformer_adds_properties_to_object_schemas, test_strict_compatible_bare_list): 3 passed, no regressions.

Requirements checklist

  1. Detect items: {} as strict-incompatible and set strict=False so the call succeeds in lenient mode (report's option 1) — Implemented, covered by the passing regression test.
  2. Alternative — raise a helpful UserError (report's option 2) — Skipped deliberately. The report offered these as mutually-exclusive alternatives ("Either 1 … Or …"); option 1 is less disruptive, matches how every other strict-incompatible feature is already handled, and makes the exact repro succeed. No UserError was added, so no behavior change for that path.
  3. Leave changes uncommitted — done; only openai.py (+6) and test_openai.py (+14) changed. (The .claude/settings.json, AGENTS.md, CLAUDE.md deletions were already present in the working tree at session start and are unrelated environment noise, not part of this fix.)

One reviewer note worth surfacing: the guard not schema.get('items') also downgrades fixed-tuple schemas (tuple[int, str], emitted as prefixItems with no items) to lenient mode when strict is None. This is harmless and arguably more correct, since OpenAI strict mode doesn't properly support prefixItems either; no existing test relies on those being strict-compatible.
