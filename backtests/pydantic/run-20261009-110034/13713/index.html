str_min_length and str_max_length are enforced by the validator but absent from the JSON schema

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches add a config fallback in `str_schema`, so both fix the basic config-only rows in the issue's precedence table.

Patch A puts the fallback on every call to `str_schema`. Several callers produce strings that pydantic-core never checks against `str_min_length`/`str_max_length`:
- `decimal_schema` builds its string branch through `str_schema`.
- Format and to-string serializer output goes through it.
- `PlainSerializer(return_type=str)` output goes through it.

Under Patch A, a model with `str_max_length=3` and a `Decimal` field would emit `maxLength: 3` on the decimal's string form. That makes JSON Schema reject inputs pydantic accepts, which is the issue's defect class in reverse. Patch A also leaves config scoping alone. Plain dataclasses and TypedDicts without their own config push an empty config, and core-schema definitions (reused or recursive types) are generated outside the model's config. So in those cases the schema still omits constraints the validator enforces.

Patch B handles these cases explicitly:
- It suppresses the config lengths for decimals and serializer output.
- It keeps the parent config in effect for config-less dataclasses and TypedDicts, matching how validation behaves.
- It applies the root schema's config while generating definitions.

Patch B's tests are much stronger. The parametrized test covers every row of the issue's precedence table and cross-checks the schema against actual validation for lengths 0–12. Further tests cover TypeAdapter, list, dict keys and values, Optional, nested models with their own config, plain dataclasses and TypedDicts, definitions and recursive aliases, and the unvalidated-string cases. Patch A's single test covers only the config-only case and the field-override case.

Patch B is larger, and its config-stack changes carry some risk. However, that work is needed to make the schema faithful rather than adding new mismatches, and it is well commented. Patch B is the more correct and better-tested fix.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Initial Checks

Description

str_min_length and str_max_length are enforced by the validator but do not appear in the JSON schema, so a JSON Schema validator silently accepts input the model rejects.

class Model(BaseModel):
    model_config = ConfigDict(str_min_length=3)
    s: str

Model.model_json_schema()['properties']['s']
#> {'title': 'S', 'type': 'string'}       <-- no minLength

Model(s='ab')                             #> ValidationError
jsonschema.validate({'s': 'ab'}, Model.model_json_schema())   #> accepted

The same holds for str_max_length. This is the same class of defect as #13704 — a constraint pydantic applies that a consumer of the schema cannot see — but it comes from a different place, so that fix will not cover it.

Why it happens

A field-level constraint lands on the core schema, where GenerateJsonSchema.str_schema finds it:

'schema': {'type': 'str', 'min_length': 3}

A config-level one does not. It stays in the model's config block and is applied by pydantic-core at validation time, leaving the string node bare:

{'type': 'model',
 'schema': {'type': 'model-fields',
            'fields': {'s': {'type': 'model-field', 'schema': {'type': 'str'}}}},   # <-- nothing here
 'config': {'str_min_length': 3, 'title': 'Model'}}

str_schema only reads the core schema node, so the constraint is invisible to it.

Precedence

Worth stating because it decides what the schema should say when both are present: a field-level length replaces the config one rather than narrowing it. Measured on main (952c239):

configfieldrejected lengthsschema today
str_max_length=5—8, 12{} — nothing emitted
—max_length=1012maxLength: 10 ✅
str_max_length=5max_length=1012maxLength: 10 ✅
str_max_length=10max_length=58, 12maxLength: 5 ✅
str_min_length=3—1{} — nothing emitted
str_min_length=3min_length=1noneminLength: 1 ✅

So only the config-only rows are wrong, and the fix is to fall back to the config value when the field left the key unset — the rows that already work keep working untouched.

str_strip_whitespace, str_to_lower and str_to_upper are not affected: they transform rather than constrain, and the result is still a string, so the schema stays accurate.

Example Code

import jsonschema
from pydantic import BaseModel, ConfigDict, ValidationError


class Model(BaseModel):
    model_config = ConfigDict(str_min_length=3, str_max_length=5)

    s: str


schema = Model.model_json_schema()
print(schema['properties']['s'])
#> {'title': 'S', 'type': 'string'}

for value in ('ab', 'abcdef'):
    try:
        Model(s=value)
    except ValidationError:
        print(f'pydantic rejects {value!r}')
    jsonschema.validate({'s': value}, schema)
    print(f'jsonschema accepts {value!r} -- constraint lost')
