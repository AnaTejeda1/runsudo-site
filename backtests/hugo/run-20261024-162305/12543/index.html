Issue #12543 Merged fix PR # Run 24 Oct 2026 · run-20261024-162305 gohugoio/hugo

resources/images: Poor overlay quality when background image is an indexed (not true color) PNG

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches contain the identical root-cause fix: introduce an images.ActionFilter constant, use it in Filter(), and skip the 'apply source palette' step in doWithImageConfig when the action is a filter, so overlay/text/padding output on an indexed PNG is no longer clamped to the source's 256-color palette. Both update the same golden files and both pass all three independent tests that failed on base. The difference is in tests and scope. Patch B adds a focused integration test for this issue that would fail on base (it asserts the overlay results are not *image.Paletted and have more than 256 colors, that the text color absent from the source palette appears in the output, and that the padding pixel is the exact requested color) while confirming that plain resize still preserves the palette; that is a meaningful regression test for exactly the reported behaviour. Patch A adds no test for the reported issue; its test changes are to color unit tests covering a separate concern. Patch A also bundles an unrelated change set in color.go (parsing hex to NRGBA instead of RGBA, normalizing Color.init, value-based palette comparison, un-premultiplying in ColorGoToHexString) for a different transparency issue, which alters an extra golden file (padding-transparent-chained.png) and changes the concrete color type returned by the public hex parser. That may be a legitimate adjacent fix but it is outside this issue's ask, adds behavioural risk, and obscures the actual fix. On craft the two are equivalent, with B slightly clearer by documenting that ActionFilter is not a valid spec action. B is the better fix for this issue.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Each saw the issue and the two patches, labelled A and B in random order (two of them saw ours as A), with issue links and version numbers removed. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours. Before getting into the details, I have verified that this is not an upstream issue with disintegration/gift. I tested with this:

<details>
<summary>main.go</summary>

package main

import (
	"image"
	"image/png"
	"log"
	"os"

	_ "image/png"

	"github.com/disintegration/gift"
)

func main() {
	// Get the background image (24 bit: indexed not true color)
	f, err := os.Open("background.png")
	if err != nil {
		log.Fatal(err)
	}
	bgImage, _, err := image.Decode(f)
	if err != nil {
		log.Fatal(err)
	}

	// Get the foreground image (24 bit with 8 bit alpha channel)
	f, err = os.Open("foreground.png")
	if err != nil {
		log.Fatal(err)
	}
	fgImage, _, err := image.Decode(f)
	if err != nil {
		log.Fatal(err)
	}

	// Create a new image with dimensions of the bgImage.
	dstImage := image.NewRGBA(bgImage.Bounds())
	// Copy the bgImage to the dstImage.
	gift.New().Draw(dstImage, bgImage)
	// Draw the fgImage over the dstImage at the (20, 20) position.
	gift.New().DrawAt(dstImage, fgImage, image.Pt(20, 20), gift.OverOperator)

	// Create the composite file.
	f, err = os.Create("composite.png")
	if err != nil {
		log.Fatal(err)
	}
	defer f.Close()

	// Encode the composite image.
	err = png.Encode(f, dstImage)
	if err != nil {
		log.Fatal(err)
	}
}

</details>

Details:

  • Background image is a 24 bit indexed PNG file with 256 colors in its palette
  • Foreground image is a 24 bit true color PNG with an 8 bit alpha channel
  • The final (composite) image seems to be limited to the palette of the background image
