Consider bumping mainImageVersionNumber

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

The issue asks for a bump to mainImageVersionNumber so that cached images built with the old buggy code are invalidated.

Patch B does exactly that: it sets mainImageVersionNumber to 2. It also fixes a real gap at the root. `Filter` overwrote `confMain.Key` with a hash of only the filters, which dropped the version suffixes appended by DecodeImageConfig. B now hashes `confMain.Key` together with the filters, so any version bump also invalidates filtered images. That matters because the fixes in question (filters on transparent colors, geometric filter chains) live largely in the filter path. B adds a meaningful test, TestMainImageVersionNumberInvalidatesCache. It builds a site, changes the version number through a test-only export hook, rebuilds, and asserts that every link changes, including Filter outputs. This test would fail before the Filter key change. B also regenerates the expected hashes and golden files consistently.

Patch A does not bump the main version number. It adds a PNG entry to the format version map, which leaves non-PNG outputs stale (e.g. paletted GIFs and transparent-color filters targeting other formats). It also exports the global variables `MainImageVersionNumber` and `FormatVersionNumbers` as mutable package state just so `image.go` can reach them. This duplicates logic already in DecodeImageConfig rather than reusing `confMain.Key`, and it widens the API. A adds no test proving invalidation, only hash updates. It also carries unrelated formatting churn (reflowed AssertFileContent calls) in several test files.

B is more correct, better tested and cleaner.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
