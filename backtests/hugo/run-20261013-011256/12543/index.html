Issue #12543 Merged fix PR # Run 13 Oct 2026 · run-20261013-011256 gohugoio/hugo

resources/images: Poor overlay quality when background image is an indexed (not true color) PNG

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the root cause the same way: they skip re-quantizing the output to the source palette when filters can add new colors. That is what clamps an Overlay onto an indexed PNG to the background's 256 colors. Both update the paletted overlay.png and text.png golden images to match.

Patch B is more precise. It still keeps the source palette when every filter is geometric (images.Process specs or orientation filters). It drops the palette only when a color-introducing filter such as Overlay, Text, Padding or Grayscale is present. Patch A drops palette preservation for every `Filter` call, so `$img.Filter (images.Process "resize 100x")` or AutoOrient on an indexed PNG now loses its palette. That is an unnecessary behavior regression relative to the plain Resize path.

Patch A also bundles a separate change for a different issue (12536). It switches hex color parsing from RGBA to NRGBA and rewrites ColorGoToHexString, Color.init and AddColorToPalette. This alters semantics beyond the issue and changes an unrelated golden image (padding-transparent-chained.png). That adds risk and obscures the fix.

On tests, Patch B adds a targeted integration test. It checks pixel by pixel that the overlay keeps the foreground's colors and that the text color and padding color are preserved. It checks that grayscale output is truly gray and that a purely geometric Process still yields a paletted image. This test would fail before the fix. Patch A's test changes are mostly about the unrelated hex/NRGBA work, and it relies on golden-image updates for the actual issue.

B is more correct, better tested and better scoped.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Before getting into the details, I have verified that this is not an upstream issue with disintegration/gift. I tested with this:

<details>
<summary>main.go</summary>

package main

import (
	"image"
	"image/png"
	"log"
	"os"

	_ "image/png"

	"github.com/disintegration/gift"
)

func main() {
	// Get the background image (24 bit: indexed not true color)
	f, err := os.Open("background.png")
	if err != nil {
		log.Fatal(err)
	}
	bgImage, _, err := image.Decode(f)
	if err != nil {
		log.Fatal(err)
	}

	// Get the foreground image (24 bit with 8 bit alpha channel)
	f, err = os.Open("foreground.png")
	if err != nil {
		log.Fatal(err)
	}
	fgImage, _, err := image.Decode(f)
	if err != nil {
		log.Fatal(err)
	}

	// Create a new image with dimensions of the bgImage.
	dstImage := image.NewRGBA(bgImage.Bounds())
	// Copy the bgImage to the dstImage.
	gift.New().Draw(dstImage, bgImage)
	// Draw the fgImage over the dstImage at the (20, 20) position.
	gift.New().DrawAt(dstImage, fgImage, image.Pt(20, 20), gift.OverOperator)

	// Create the composite file.
	f, err = os.Create("composite.png")
	if err != nil {
		log.Fatal(err)
	}
	defer f.Close()

	// Encode the composite image.
	err = png.Encode(f, dstImage)
	if err != nil {
		log.Fatal(err)
	}
}

</details>

Details:

  • Background image is a 24 bit indexed PNG file with 256 colors in its palette
  • Foreground image is a 24 bit true color PNG with an 8 bit alpha channel
  • The final (composite) image seems to be limited to the palette of the background image
