Panic when deleting a directory in static when server is running

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches address the same two-part root cause: (1) SourceFilesystem.Contains depended on the mount directory still existing on disk, so IsStatic returned false for a removed static directory and the event leaked into the dynamic rebuild path, and (2) processPartialFileEvents' component switch had no case for static. The independent tests confirm both patches fix every scenario (subdir, nested dir, root, mounted dir, rename, mixed batch). The difference is in how they get there. Patch B's Contains is a two-line reuse of the existing ReverseLookup(filename, false) machinery, which is already stat-free and already handles mounts, overlays and single-file mounts consistently with the rest of BaseFs; its switch change is the minimal, self-documenting 'handled by the static file syncer' case that keeps the rest of the loop (path parsing, cache-buster compilation) untouched. Patch A instead adds a new public RootMappingFs.MountDirs API, reimplements prefix matching by walking the filesystem stack and comparing r.To and r.Meta.Component, and restructures the pss loop to drop static paths entirely before cache-buster compilation. That is more surface area and more behavioural change than the issue asks for, and the early `continue` silently excludes static paths from cache busting rather than just from the component switch; it also leaves the original switch panic in place for any static path that might still arrive by another route. On tests, Patch A's Go rebuild tests (TestRunning + RemoveFiles for subdir and root deletion) are deterministic and directly mirror the issue, and its basefs unit test pins the Contains contract; these are stronger than Patch B's timing-based testscripts (`sleep 2`, `! stderr .`), which also only exercise module.mounts cases rather than a plain static/ subdirectory. That test advantage is real but does not outweigh B's cleaner, lower-risk fix: B resolves the root cause with less new code, better reuse of existing abstractions, and no change to the handling of non-static events, so B is the better patch.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Each saw the issue and the two patches, labelled A and B in random order (two of them saw ours as A), with issue links and version numbers removed. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours. The reasoning above is one judge's, shown verbatim.
