Issue with chained resource transformations

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the same root cause. When a transformation chain runs, the shared `resourceAdapterInner.target` is replaced with the transformed result. `TransformWithContext` then appended new transformations but reused that already-transformed `target`, so the earlier steps (e.g. `css.Build`) ran a second time. Each patch keeps a reference to the original, untransformed resource and starts new chains from it.

Patch A puts a `source` field on the inner struct and sets `target: r.source` in `TransformWithContext`. Patch B puts `sourceTarget` on the outer `resourceAdapter` value, which is copied by value, so it is untouched when the inner `target` is mutated. It then uses it in `TransformWithContext`. Both resolve the scenario in the issue: `.Data` triggers `css.Build`, then `fingerprint` should apply only fingerprinting to the original chain rather than re-running `css.Build` on its output.

The patches differ in `cloneTo`. Patch A handles it more carefully: it clones the untransformed source when transformations exist. Patch B sets `sourceTarget` to the clone of the current target, which could be the transformed result if the chain has already executed. That is a narrow edge case outside the issue's ask. Both share the same small risk that any other construction site of the adapter or inner struct could leave the new field nil.

On tests, Patch B adds an integration test that reproduces the exact scenario from the issue. It ranges over `.Data.Artifacts`, then reads `.Content`, then fingerprints, and asserts that the fingerprint hash matches the built CSS hash. That test would fail before the fix. Patch A adds no tests.

Correctness is roughly equal for the reported scenario, with Patch A slightly more thorough in `cloneTo`. Patch B's meaningful regression test makes it the better overall submission.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The issue

View on GitHub

See the fix in #15188.

This has been an issue since we added this feature, but we haven't noticed it (or gotten reports about it) because the common setup is to set up the entire chain before starting to use it:

{{- with . | css.Build $opts }}
	{{- if hugo.IsDevelopment }}
		<link rel="stylesheet" href="{{ .RelPermalink }}">
	{{- else }}
		{{- with . | fingerprint }}
			<link rel="stylesheet" href="{{ .RelPermalink }}" integrity="{{ .Data.Integrity }}">
		{{- end }}
	{{- end }}
{{- end }}

In the above:

  • .RelPermalink triggers the transformation of the entire chain in a streaming way.

With the recently added .Data.Artifacts in css.Build I discovered this issue by accident when doing something ala:

{{- with . | css.Build $opts }}
	{{ range .Data.Artifacts }}
		{{ if eq .MediaType.MainType "font" }}
			<link rel="preload" href="{{ .RelPermalink }}" as="font" type="{{ .MediaType.Type }}">
		{{ end }}
	{{ end }}
	{{- if hugo.IsDevelopment }}
		<link rel="stylesheet" href="{{ .RelPermalink }}">
	{{- else }}
		{{- with . | fingerprint }}
			<link rel="stylesheet" href="{{ .RelPermalink }}" integrity="{{ .Data.Integrity }}">
		{{- end }}
	{{- end }}
{{- end }}

In the above:

  • .Data triggers the css.Build transformation.
  • Then fingerprint starts a new transformation with correct .Content, but wrongly including the full chain, including css.Build

The above could be rewritten to the below and it would work as expected:

{{- with . | css.Build $opts }}
	{{- if hugo.IsDevelopment }}
		<link rel="stylesheet" href="{{ .RelPermalink }}">
	{{- else }}
		{{- with . | fingerprint }}
			{{ range .Data.Artifacts }}
				{{ if eq .MediaType.MainType "font" }}
					<link rel="preload" href="{{ .RelPermalink }}" as="font" type="{{ .MediaType.Type }}">
				{{ end }}
			{{ end }}
			<link rel="stylesheet" href="{{ .RelPermalink }}" integrity="{{ .Data.Integrity }}">
		{{- end }}
	{{- end }}
{{- end }}
{{- end }}

What the agent reported

I've fixed the bug in resources/transform.go, but none of it has been compiled or tested. This environment can't download Go modules, so every ./bt-test build fails. I also removed the regression test from the diff, because I never saw it fail before the fix or pass after it.

What was wrong: reading .Data on a css.Build result runs the transformation chain, and that replaces the resource's target with the transformed output. Piping that result into another transformation (such as fingerprint) then built a new resource with the full chain and the already-transformed target. So css.Build ran a second time on its own output. When the whole chain is set up before anything is read, the target is still the original file, which is why the common pattern worked.

What I changed (resources/transform.go only):

  • Added a source field to resourceAdapterInner: the original, untransformed resource. It is set in newResourceAdapter and never changes afterwards.
  • TransformWithContext now applies the full chain to source instead of target. The result is the same whether or not the parent was already evaluated, and it has the same cache key as the "whole chain first" case.
  • cloneTo (used by resources.Copy) sets source as well. With no transformations it is the copy itself; otherwise it is the original moved to the copy's path.
  • Every place that builds resourceAdapterInner now sets source, and the cache-hit path keeps a valid one, since equal cache keys mean equivalent sources. The reviewer confirmed both and found nothing else changed.

Behaviour change to know about: say a transformed resource is passed to resources.Copy, evaluated, and then transformed again. The chain now re-runs on the original file at the copy's path. That means relative imports in js.Build or Sass would resolve from the copy's directory. This is how copies made before evaluation already behaved; before the fix, copies made after evaluation had the chain applied twice instead. I kept it this way so results don't depend on what the template read first.

Test evidence:

  • ./bt-test ./resources/ ./tpl/css/ produced no test results. Every package failed to build with errors like github.com/bep/helpers@v0.12.0: Get "https://proxy.golang.org/...": dial tcp: lookup proxy.golang.org ... server misbehaving. The module cache is empty and there is no vendor/ directory.
  • The gate didn't report this as an infrastructure failure, but it is one.
  • gofmt is clean.

Dropped regression test: the test-writer wrote TestCSSBuildTransformChainAfterDataAccess for tpl/css/build_integration_test.go. It renders css.Build (inline sourcemap, with an @import), reads {{ $d := .Data }}, then pipes to fingerprint. It checks that the output is identical to css.Build | fingerprint without .Data, and that it contains background: red. I removed it, so the diff contains no test — the requirement to include one isn't met. There's also an open question: if esbuild produces the same output when run twice on its own output, the test would pass even on the old code, and a js.Build chain would be a better check. I kept a copy at /tmp/regression_test.diff, outside the repo; apply it with git apply once modules are available, then run ./bt-test ./tpl/css/ -run TestCSSBuildTransformChainAfterDataAccess.

Requirements:

  1. Accessing .Data on a css.Build result, then fingerprint, must apply css.Build only once — fixed, not tested (the build failure above).
  2. The existing "whole chain first" pattern must keep working — reasoned unchanged, not tested. Before evaluation, target and source are the same object, so the behaviour and cache key are the same as before.
  3. The report's workaround (reading .Data.Artifacts after fingerprint) — not needed after the fix; nothing changed there.
