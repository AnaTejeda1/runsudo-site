TypeAdapter config not used for JSON Schema generation

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the reported `TypeAdapter.json_schema()` case the same way. They push `self._config` onto the generator's `_config_wrapper_stack` around `generate()`, which addresses the root cause: the adapter config is not part of the core schema, so the generator never saw it.

Patch B stops there. The sibling public API `TypeAdapter.json_schemas()` still ignores each adapter's config and would keep emitting `format: binary` for a `ser_json_bytes='base64'` adapter. The issue title reads "TypeAdapter config not used for JSON Schema generation", so leaving that path broken is an incomplete fix.

Patch A also handles `json_schemas()`. It lets `generate_definitions` accept an optional fourth element per input (a per-input config) and pushes that config during both generation passes, so each adapter gets its own config. The change is backward compatible: 3-tuples still work and `None` configs push nothing meaningful. The union tuple typing is a bit awkward, but it adds little risk.

On tests, Patch A covers:
- the exact issue scenario;
- a no-config baseline;
- the `json_schemas` path with mixed config and no-config adapters.

All of these fail before the change. Patch B's single test (`list[bytes]`) is valid and shows nested propagation, but it covers only one path.

On craft, Patch B has a helpful explanatory comment. Patch A's docstring update documents the new tuple element.

Overall, Patch A resolves the bug more completely, with better tests and little added risk.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
