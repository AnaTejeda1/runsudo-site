In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches remove the two base-code paths that caused the full-catalog restatement (a namespace arriving with a description, and any listing reshuffle in a partial catalog both returned `replacement`), and both keep the delta-vs-replacement size guard. Correctness: B gets closer to the root cause. It persists every tool path in the summary and diffs the real inventory, so a browser attach reports only the browser namespace (line plus listings capped by a 1000-token update budget) and a detach reports only "namespace `browser` no longer available"; tools that merely shifted out of the inline budget because another namespace arrived are not mentioned. It also detects a same-count swap of unshown tools and can show a new tool's signature via `lookup` even when the catalog would not display it. A keeps the old `count`/`shown` summary, so it cannot distinguish a reshuffle from a real change and deliberately reports every listing change: on each attach it tells the model that still-callable github/nas_ops tools are "no longer listed; find them with search before calling them", and on detach it re-lists them under "Additional tools are now listed". B adds comparable unit tests plus an end-to-end session-runner scenario that exercises the real instruction pipeline through repeated steps, compaction and fork, verifying no spurious update is emitted when the catalog is rebuilt unchanged. The independent tests were MISSING on all three trees and give no signal.

Scope/risk: B is the riskier patch. The issue

Summary

When the Code Mode tool tree changes, OpenCode re-injects the entire catalog (~8.8k chars) into the conversation as a system message (description: "Instructions updated: core/codemode"), which the provider layer renders to the model as a user message. The tool tree also changes on transient, expected events — desktop-browser connect/disconnect, MCP reconnect, location recycling — so normal usage (opening/closing a session tab, opening/closing the desktop app) repeatedly dumps the full catalog into context. In one 22-day deployment this produced 419 notices / 2.27M chars of injected context, up to 67 notices in a single day.

Environment

  • opencode version: v2.0.29
  • OS: Linux 6.18.18.c1107-trim (linux x64) — official container image ghcr.io/anomalyco/opencode:2.0.29
  • Terminal: Unavailable — headless server driven by the desktop app over the local server API (TERM=xterm-256color)
  • Shell: Unavailable
  • Install/channel: release container image
  • Active plugins: none ("plugins": [])

Reproduction

  1. Run opencode serve with the desktop app attached to a session (so the browser namespace is registered).
  2. In the desktop app, open and close the session tab (or toggle the embedded browser) a few times.
  3. Inspect the session: each attach/detach cycle appends a type:"system" message whose text is the full catalog and whose description is Instructions updated: core/codemode.

Observed during a single turn of ~10 tool calls: 4 browser attach/detach cycles → 2 notices, and the catalog alternated browser (45 tools, 5 shown) github (46, 6) nas-ops (35, 6) opencode (8, 7) ↔ github (46, 9) nas-ops (35, 8) opencode (8).

Expected Behavior

A change notification should be proportional to the change and debounced: a short "catalog changed, re-run search" note, or a diff. Transient connect/disconnect of the desktop browser (or MCP) should not be treated as a semantic instruction change, and a flap that immediately reverses should not produce two full-catalog injections.

Actual Behavior

  • Every tool-tree change injects the full catalog (~8.8k chars; 14.4k observed max).
  • No debounce: attach→detach = two changes = two injections.
  • The injected system message is converted to a user message before reaching the model, so the model sees repeated fake user turns.
  • The notices accumulate in the session context until a compaction drops them.

Additional Context

Mechanism (extracted from the v2.0.29 binary):

  • Vl(e, A={}) renders the catalog under a fixed budget (A.budget ?? 2000); jl() calls Vl(e) without a budget, so the full catalog is regenerated each time. Rl(prev, next) compares and returns the "changed" text.
  • InstructionState.prepare (observe + commit) runs only for the currently-draining session, at each step boundary — so a session that happens to have a step inside the flap window gets the notice; sessions with no step in the window do not.
  • The projector appends a type:"system" message; the AI-SDK adapter converts role:"system" to role:"user".

Not a duplicate of the existing "tools unavailable" issues: #51849 / #46190 / #52505 describe a namespace missing (calls fail with Unknown tool). This report is about the repeated full-catalog injection on every flap, regardless of whether the tools are callable.

Workarounds tried: none — the notice is not suppressible from the server side.
