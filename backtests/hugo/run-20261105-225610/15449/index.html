Build hangs forever after 10 page render errors: renderPages blocks on pages <- p after errorCollator calls Stop

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches apply the identical root-cause fix: the walker's send becomes `case pages <- p:` inside the select on `s.h.Done()`, so the walk can always exit after `errorCollator` calls `Stop`, and `renderPages` reaches `close(pages)`, `wg.Wait()` and `<-errs`. Independent tests confirm both resolve the hang (both FAIL-ASSERT on base, PASS on A and B), so correctness on the reported scenario is equal.

Patch B goes slightly further in ways the issue itself points at and that reduce risk rather than add it. It buffers `errs` (the issue's own suggestion) so the collator can never block on its final send. More importantly, it fixes the existing early return on `w.Walk` error: on base and on Patch A, a walk error returns before `close(pages)`/`wg.Wait()`, leaving the `pageRenderer` goroutines parked on `<-pages` and the collator parked on `errs` forever. The issue explicitly warns about exactly this class of early return. Patch B's restructuring (capture `walkErr`, always close/wait/drain, then return `walkErr` first) is small, easy to reason about, and preserves the error precedence. This is the kind of edge-case error handling the craft criterion asks for, not unrelated churn.

Tests are near-equivalent: same reproducer (50 pages, GOMAXPROCS=1, NUMWORKERMULTIPLIER=2, 10 iterations with a timeout), both would fail before and pass after. Patch B additionally asserts the collated error mentions the layout path, slightly strengthening the check that errors are actually reported, and lives in the existing build-errors test file next to related tests, with a comment explaining the regression. Patch A creates a new file and uses a tighter 10s timeout, which is marginally more prone to false failures on slow CI. Both share the same minor hazard of mutating process-global GOMAXPROCS in a package with parallel tests, so that is a wash.

Patch B also adds an explanatory comment at the select explaining why the send must select on Done, which helps future readers. Net: equal on the core fix, B better on edge handling and craft with no added risk.

What happened

When a build has 10 or more page render errors, hugo sometimes never exits.
It prints no error, uses no CPU, and waits forever. A SIGQUIT dump shows the
page walker in renderPages blocked sending to pages, and errorCollator
blocked on its final send to errs. No pageRenderer goroutines are left.

The hang is a race. With default settings, the reproducer below hung in 26 of
500 builds on a 16-CPU linux/amd64 machine. With `GOMAXPROCS=1
HUGO_NUMWORKERMULTIPLIER=2` (the script's defaults; they only change
scheduling), it hung in 30 of 30 builds (3 runs of the script, 10 builds each,
about 50 seconds per run).

Expected

The build fails promptly and prints the collated render errors.

Reproducer

POSIX shell. It creates a site in $(mktemp -d) whose pages all fail to render
(.Content on a nil resource), builds it RUNS times, treats a build that
doesn't exit within LIMIT seconds as hung, and prints the goroutine dump of
the first hung build (timeout -s QUIT). It deletes the site when done.

#!/bin/sh
# Build a site whose pages all fail to render, RUNS times; report builds
# that don't exit within LIMIT seconds and print the first one's goroutines.
HUGO=${HUGO:-hugo}
PAGES=${PAGES:-50}
RUNS=${RUNS:-10}
LIMIT=${LIMIT:-5}
# Scheduling settings that make the race hit almost every time.
# Set both to "" to use Hugo's defaults (the hang is then much rarer).
export GOMAXPROCS="${GOMAXPROCS-1}"
export HUGO_NUMWORKERMULTIPLIER="${HUGO_NUMWORKERMULTIPLIER-2}"

dir=$(mktemp -d) || exit 1
trap 'rm -rf "$dir"' EXIT
trap 'exit 130' INT TERM

site=$dir/site
mkdir -p "$site/layouts" "$site/content"
printf 'disableKinds = ["taxonomy", "term", "rss", "sitemap"]\n' > "$site/hugo.toml"
# .Content on a nil resource: every page fails to render.
printf '{{ (resources.Get "missing.svg").Content }}\n' > "$site/layouts/single.html"
cp "$site/layouts/single.html" "$site/layouts/list.html"
i=1
while [ "$i" -le "$PAGES" ]; do
  printf -- '---\ntitle: p%s\n---\n' "$i" > "$site/content/p$i.md"
  i=$((i + 1))
done

"$HUGO" version
echo "GOMAXPROCS=$GOMAXPROCS HUGO_NUMWORKERMULTIPLIER=$HUGO_NUMWORKERMULTIPLIER PAGES=$PAGES"
hung=0 n=1
while [ "$n" -le "$RUNS" ]; do
  timeout -s QUIT "$LIMIT" "$HUGO" -s "$site" -d "$dir/public" > "$dir/log" 2>&1
  if [ $? = 124 ]; then
    hung=$((hung + 1))
    echo "build $n: hung (no exit after ${LIMIT}s)"
    [ "$hung" = 1 ] && cp "$dir/log" "$dir/first-hang"
  else
    echo "build $n: exited"
  fi
  n=$((n + 1))
done
echo "hung in $hung of $RUNS builds"
if [ "$hung" -gt 0 ]; then
  echo "--- output of first hung build (SIGQUIT goroutine dump) ---"
  cat "$dir/first-hang"
  exit 1
fi

Run it with HUGO=/path/to/hugo sh repro.sh. For Hugo's default scheduling,
run GOMAXPROCS= HUGO_NUMWORKERMULTIPLIER= RUNS=500 sh repro.sh.

Analysis

Line numbers are for the v0.168.0 tag.

0 L91–L104,
the walk handler in renderPages, checks for cancellation only before it
blocks:

select {
case <-s.h.Done():
	return radix.WalkStop, nil
default:
	pages <- p // L98
}

0 L1574–L1588,
errorCollator, calls s.h.Stop() after maxErrors (10) errors (L1583–L1586)
and stops reading results. Each pageRenderer then sees Done() in
sendErr on its next error
(0 L132–L139)
and returns, so nothing reads pages any more.

If the walker passed its Done() check before Stop() and is blocked on the
full pages channel (buffered to numWorkers, L75), the send at L98 never
completes. The walk never returns, so close(pages), wg.Wait() and
err := <-errs
(L110–L116)
are never reached. The deferred errs <- ... in errorCollator (site.go
L1577, unbuffered errs, site_render.go L76) then blocks too, and the
collated errors are never returned or printed.

Suggested fix

Make the send itself select on Done(), so the walker can always leave:

select {
case <-s.h.Done():
	return radix.WalkStop, nil
case pages <- p:
}

With that, renderPages always reaches <-errs, so the collator's final send
completes. Making errs buffered (make(chan error, 1)) would also stop the
collator goroutine blocking if a future change returns early before L116.
