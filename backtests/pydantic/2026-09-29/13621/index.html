Initial Checks

  • I confirm that I'm using Pydantic V2

Description

Transient BaseModel classes are not collected when either:

  • A model field references an Enum whose class defines a Python method.
  • A model field uses Field(exclude_if=<Python callable>).

After the defining module is removed from sys.modules and every ordinary strong reference is dropped, weak references to the model and enum classes remain alive after repeated full gc.collect() calls. Repeating this construction in disposable module namespaces causes linear memory growth.

Controls using an enum without methods or a field without exclude_if are collected normally.

I encountered this in combination with a Temporal workflow sandbox. With a large interconnected model graph and high volume Temporal workflows this can result in multi-GiB process growth relatively quickly.

The likely cause is missing PyGcTraverse edges for Python objects held by pydantic-core:

  • SerField owns serialization_exclude_if, but traverses only serializer: https://github.com/pydantic/pydantic/blob/c67a1397327c6abc1a2e2e921af01aebbbeedf1c/pydantic-core/src/serializers/fields.rs#L26-L38
  • EnumSerializer owns class, but traverses only serializer: https://github.com/pydantic/pydantic/blob/c67a1397327c6abc1a2e2e921af01aebbbeedf1c/pydantic-core/src/serializers/type_serializers/enum_.rs
  • Each EnumValidator<T> owns lookup, but traverses only class and missing: https://github.com/pydantic/pydantic/blob/c67a1397327c6abc1a2e2e921af01aebbbeedf1c/pydantic-core/src/validators/enum_.rs

Traversing py_schema does not compensate for another unreported direct reference: CPython’s collector accounts for every actual strong edge individually.

I tested a temporary build from Pydantic main at c67a1397327c6abc1a2e2e921af01aebbbeedf1c. Adding only these traversal edges made all objects in the reproduction collectible:

  • Add serialization_exclude_if to SerField traversal.
  • Add class to EnumSerializer traversal.
  • Add lookup to every EnumValidator<T> traversal.

For the enum case, changing only the serializer or only the validator was insufficient; both missing edges were required.

This appears related to earlier missing-traversal fixes such as:

  • https://github.com/pydantic/pydantic/issues/5136
  • https://github.com/pydantic/pydantic-core/pull/787
  • https://github.com/pydantic/pydantic-core/pull/1100

I would be happy to submit a focused patch.

import gc
import sys
import types
import weakref

def transient_module(name, source, class_names):
    module = types.ModuleType(name)
    sys.modules[name] = module
    exec(compile(source, f"<{name}>", "exec"), module.__dict__)
    refs = tuple(
        weakref.ref(module.__dict__[class_name])
        for class_name in class_names
    )
    del sys.modules[name]
    del module
    return refs

Final report

What was wrong

A memory leak in pydantic-core: transient BaseModel classes were never garbage-collected when a field referenced an Enum whose class defines a Python method, or used Field(exclude_if=<callable>). The cyclic GC could not see certain strong edges because three impl_py_gc_traverse! macro calls omitted fields that hold Python references. CPython's collector accounts for every real strong edge individually, so an untraversed Py<...> field makes the whole cycle appear externally-referenced and immortal.

What I changed

Added the missing traversal edges — exactly the fix the report prescribed (and reported as tested on main), matching the established codebase pattern (e.g. LiteralValidator already traverses lookup):

  • pydantic-core/src/serializers/fields.rs:38 — SerField: added serialization_exclude_if (Option<Py<PyAny>>).
  • pydantic-core/src/serializers/type_serializers/enum_.rs:51 — EnumSerializer: added class (Py<PyType>).
  • pydantic-core/src/validators/enum_.rs:171,203,219,235 — added lookup (Box<LiteralLookup<Py<PyAny>>>) to all four EnumValidator<T> monomorphizations (Plain/Int/Str/Float).

New regression test tests/test_garbage_collection.py (top-level suite — the only one bt-test runs) with test_gc_enum_with_method and test_gc_field_exclude_if, faithfully reproducing the report's transient-module scenarios and asserting the weakrefs die after gc.collect().

Test evidence

  • Baseline (pre-fix, current binary): I reproduced the leak directly — all three objects stay alive (enum alive: True, enum model alive: True, exclude_if model alive: True). The test-writer confirmed both new tests FAIL on this build (transient class(es) were not garbage collected).
  • Post-fix gate: could not be executed. The fix is in Rust and requires recompiling the _pydantic_core extension, but this environment cannot build it: the crates.io index is unreachable (CONNECT tunnel failed, response 403 — an egress-proxy denial, confirmed even with the sandbox disabled), and there is no local registry/vendor cache (/usr/local/cargo/registry is empty; cargo build --offline fails at resolution: no matching package named base64 found). make build-dev (maturin develop --uv) fails at Updating crates.io index. Because bt-test runs pytest tests with --no-sync against the pre-built (stale) .so, running it would exercise the un-fixed binary and report a misleading failure that reflects the compile block, not the change — so I did not run it. The diff is verified by: (a) direct git diff inspection (minimal, no unrelated edits), (b) reviewer confirmation that every added identifier is a real Py<...>-holding field whose type implements PyGcTraverse, and (c) exact correspondence to the report author's independently-tested patch and the existing codebase idiom.

Once compiled in a network-enabled environment, ./bt-test tests/test_garbage_collection.py should pass.
