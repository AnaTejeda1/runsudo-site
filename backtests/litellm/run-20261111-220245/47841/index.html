The issue

View on GitHub

Description

On the proxy, spend_logs_metadata sent with a Gemini Interactions API request (POST /v1beta/interactions, call_type=acreate_interaction) never reaches LiteLLM_SpendLogs: metadata.spend_logs_metadata is null on every row, whichever way it is sent (x-litellm-spend-logs-metadata header, body metadata.spend_logs_metadata or body litellm_metadata.spend_logs_metadata). The same three ways work on /v1/chat/completions against the same deployment. Tags and the session id do arrive. Anyone who attributes spend through spend_logs_metadata loses it on the Interactions route.

Expected: the header and litellm_metadata (as on /v1/responses) land in metadata.spend_logs_metadata.

Seen on v1.106.1 and v1.104.0.

Root cause (traced on v1.106.1 with a debug hook that logged key names at each step):

  1. interactions is not in LITELLM_METADATA_ROUTES (litellm/proxy/litellm_pre_call_utils.py), so the proxy puts the request metadata (spend_logs_metadata, tags, user_api_key_*) under metadata.
  2. The router puts the deployment metadata (model_group, deployment, model_info, api_base, retry fields) under litellm_metadata, so litellm.interactions.create receives both dicts.
  3. get_logging_payload (litellm/proxy/spend_tracking/spend_tracking_utils.py) reads them through get_litellm_metadata_from_kwargs (litellm/litellm_core_utils/core_helpers.py). That function returns litellm_metadata whenever it is non-empty, after add_missing_spend_metadata_to_litellm_metadata has copied over only the keys containing user_api_key. So spend_logs_metadata is dropped there, even though kwargs["litellm_params"]["metadata"]["spend_logs_metadata"] and standard_logging_object["metadata"]["spend_logs_metadata"] both still hold it at that point.

Candidate fix, verified locally: route /interactions like /responses.

 LITELLM_METADATA_ROUTES: Final = (
     "batches",
     "bedrock",
     "/v1/messages",
     "responses",
     "files",
+    "interactions",
 )

With that line, the header and body litellm_metadata are both recorded on /v1beta/interactions; body metadata is not, which matches the /v1/responses convention. Chat completions are unchanged. A broader alternative would be to have add_missing_spend_metadata_to_litellm_metadata also carry over spend_logs_metadata (as #47790 did for litellm_received_at), which would cover any other route where the two dicts split.

Related: #34905 (the same merge helper drops the router's model_group when a guardrail plants litellm_metadata), #47790 (merged 2026-10-21; carries litellm_received_at across the same merge, not spend_logs_metadata), #39749 (store: false rows dropped on this route, which is why the repro below uses store: true).
