SSR memory leak after a render error in a dynamic component

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Root cause: in SSR, a dynamic component with a slot goes through the vdom `renderSlot`. It calls `openBlock()` and then the slot throws, so `blockStack`/`currentBlock` stay stale. Every vnode created afterwards is then pushed into that orphaned block and retained forever.

Patch A fixes this at two levels:
- **Local fix:** `renderSlot` closes its block on throw and restores `_d`.
- **Boundary fix:** a new `resetBlockTracking()` clears both `blockStack` and `currentBlock`. It is used in `renderComponentRoot`'s catch, which previously cleared only `blockStack.length` and left `currentBlock` dangling, a real latent bug. It is also used in a catch around SSR `renderComponentSubTree`.

The SSR-boundary reset means any other dangling blocks are discarded before the error escapes the render. This includes nested inline blocks such as `v-if` inside the slot, and blocks opened outside a slot. That makes the fix robust beyond the specific reproduction.

Patch A's tests assert the global state directly (`blockStack.length === 0`, `currentBlock === null`) in three places: the unit test for `renderSlot`, the `renderComponentRoot` error path, and the issue's SSR scenario. Each would fail before the change.

Patch A also fixes the unbalanced warning-context push/pop on error. That is extra scope, but low risk.

Patch B also fixes the reported case. It unwinds blocks back to the previous stack depth in `renderSlot` and adds a `finally` in `withCtx` that covers `v-if` inline blocks inside slots. However:
- It leaves the `renderComponentRoot` catch setting only `blockStack.length = 0` with a stale `currentBlock`.
- It has no SSR-level safety net, so dangling blocks outside `withCtx` are not handled.
- It adds a loop to the hot `withCtx` path on every slot invocation.

Patch B's tests are GC/WeakRef based. They are valid but only run in the gc project and are skipped without `--expose-gc`. They are also more indirect and potentially timing-sensitive compared with A's deterministic state assertions.

Overall, A addresses the root cause more completely and has stronger, deterministic tests.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Steps to reproduce

  • download the reproduction from stackblitz (won't work there, needs to be run locally)
  • run pnpm i && pnpm leak
  • see the heap size & alive app instances grow with each request after the single failed render

The script renders 500 fresh SSR apps, which all get garbage-collected. Then renders one app whose slot content throws, then renders 500 more identical healthy apps, which will never be garbage collected afterwards.

A dynamic component <component :is> with a <slot /> is needed for this to reproduce.

Card

<script setup>
    defineProps({ tag: { type: String, default: 'div' } })
</script>

<template>
    <component :is="tag" class="card">
        <slot />
    </component>
</template>

app:

<script setup>
    defineProps(['payload'])  // one request renders with `payload: null` → throws
</script>

<template>
    <main>
        <Card>{{ payload.title }}</Card>
    </main>
</template>

What is expected?

A failed renderToString should not affect subsequent renders and all apps rendered after it should get garbage collected.

What is actually happening?

Every app created after the single failed render is kept in memory forever.
