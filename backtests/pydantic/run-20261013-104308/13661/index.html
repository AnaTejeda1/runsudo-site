Runtime by_name/by_alias arguments dropped by model_validator(mode="wrap")

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

The Rust changes in generator.rs are functionally identical. Both add `by_alias`/`by_name` fields to `InternalValidator`, capture them from `extra` in `new()`, and forward them in both `validate()` and `validate_assignment()` instead of hardcoding `None`. This fixes the root cause: the wrap-validator handler (and the generator item validator) built a fresh `Extra` that dropped the runtime settings. Field placement differs slightly, which is immaterial, so correctness is a tie.

The difference is in testing.

Patch A's tests cover every path its change touches:
- **Wrap handler, core level:** `validate_python`, `validate_json` and `validate_strings` through a wrap validator, compared directly against an unwrapped validator.
- **Assignment path:** `validate_assignment` through a wrap handler, which exercises the second modified method.
- **Generator path:** the `InternalValidator` used for lazy generator items.
- **Issue repro:** the exact pydantic-level scenario from the issue (alias_generator, `TypeAdapter.validate_python`, `model_validate_json`), comparing Plain vs Wrapped across three by_alias/by_name combinations.

All of these would fail before the fix.

Patch B's tests are narrower:
- **First test:** checks a wrap model validator and a nested wrap field validator with `model_validate`. This would fail before the fix and is relevant.
- **Second test:** covers strict/extra/from_attributes/context forwarding. These were already forwarded before the patch, so it adds no regression value for this issue.
- **Gaps:** nothing covers JSON validation, the `validate_assignment` code path, or the generator path, even though the patch modifies them.

Scope and craft are comparable. Patch A wins on test coverage of the changed behavior.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Description

The handler passed to a wrap-mode model validator appears to silently drop the passed-in by_name/by_alias arguments from the top-level validate_python methods.

Example Code

from typing import Self
from pydantic import BaseModel, TypeAdapter, ValidatorFunctionWrapHandler, model_validator

CFG = {"alias_generator": lambda s: s.replace("_", "-"), "validate_by_name": True}

class Plain(BaseModel):
    model_config = CFG
    build_depends: list[str] = []

class Wrapped(BaseModel):
    model_config = CFG
    build_depends: list[str] = []

    @model_validator(mode="wrap")
    @classmethod
    def _noop(cls, data, handler: ValidatorFunctionWrapHandler) -> Self:
        return handler(data)

data = {"build_depends": ["x"]}  # field name, not the alias
print(TypeAdapter(Plain).validate_python(data, by_alias=True, by_name=False))    # build_depends=[]    correct
print(TypeAdapter(Wrapped).validate_python(data, by_alias=True, by_name=False))  # build_depends=['x'] wrong
