Panic when deleting a directory in static when server is running

Worse

The merged fix was judged better than our patch.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches stop the panic, but Patch A also fixes why static events end up in the partial rebuild.

Patch A has two parts. First, it adds an explicit `ComponentFolderStatic` case to the component switch in `processPartialFileEvents`. This matches the existing `ComponentFolderArchetypes` "ignore" case and removes the panic directly. Second, it rewrites `SourceFilesystem.Contains` to use `ReverseLookup`, which does not stat files. The old version iterated mounts, required `dir.IsDir()`, and did prefix matching. That breaks for deleted directories, since a removed mount no longer reports `IsDir`, and for single-file mounts. In those cases the static syncer did not recognise the event as static, so the event fell through to the partial build and hit the panic. With the new `Contains`, the static syncer can classify and sync deletions correctly, so the removed files also disappear from the published output. That is the behaviour a user actually needs.

Patch A's two testscripts cover deleting a directory mounted into static and a file mounted into static while the server runs, and they assert no stderr output (no panic). These are realistic end-to-end reproductions of the reported scenario.

Patch B filters static components out of the resolved paths before parsing. This avoids the panic but only treats the symptom. If `Contains` still misclassifies a deleted static directory, the event is silently dropped from the build and never reaches the static syncer, so stale files may stay in `public`. It also restructures the loop (preallocated slice to append) more than needed. Its Go integration test exercises static add/edit/remove under `TestRunning` and is a reasonable regression test for the panic. However, it does not check that deleted static files are removed from the output, and it does not cover mounts.

On correctness at the root cause, Patch A is stronger. Its scope remains focused, with a small and clear change consistent with the surrounding code.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
