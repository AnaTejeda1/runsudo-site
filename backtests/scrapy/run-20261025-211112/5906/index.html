Add possibility to use Selector (bytes) added in parsel 1.8.0.

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Patch B does not actually achieve the issue's goal. It passes body/encoding to parsel, but the very next line still calls get_base_url(response), which on base reads response.text[0:4096] and thereby decodes and caches the entire body as a str. The independent tests confirm this: every 'does not use Response.text' and memory-peak test fails on B exactly as on base ('Response.text was used', retained decoded copy of the same size). So B's change is effectively a no-op for RAM. B also has correctness gaps: it feeds response.encoding directly to parsel, ignoring that TextResponse.text gives a BOM precedence over declared encodings, and it ignores the gb18030 custom error handler and utf-16/32 endianness defaults, so output can diverge from the previous .text-based behaviour. Beyond that, B bumps parsel/cssselect minimums and strips jmespath compat code and tests, which is unrelated churn with compatibility risk, and it adds no test that would fail before and pass after. Patch A addresses the root cause end to end: it builds the selector from bytes (gated on a parsel version that decodes in Python rather than truncating at bad bytes), and it adds _text_head so get_base_url/get_meta_refresh decode only the first few KB instead of the whole body, which is what makes the memory saving real. It mirrors TextResponse.text semantics (BOM precedence, utf-16/32 BE default, gb18030 and unknown-encoding fallbacks, cached-ubody reuse), keeps the root-ignored warning path, and ships substantive tests (forbid-text mocks, equivalence-with-.text parametrizations, head-decoding boundary cases, old-parsel fallback). Its skipif only triggers on old parsel, which is the fallback path by design. All independent tests pass on A and the encoding-correctness tests remain green. A is clearly the better fix.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Each saw the issue and the two patches, labelled A and B in random order (two of them saw ours as A), with issue links and version numbers removed. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours. The reasoning above is one judge's, shown verbatim.

Summary

Please review possibility to apply RAM memory efficient Selector that can accept bytes as input
added as result of https://github.com/scrapy/parsel/issues/210 (added in parsel 1.8.0) in scrapy (as default)

Currently UnifiedSelector (subclass of parsel's Selector used in scrapy) configured to use Response.text as input
Response.text (property) -> creates new object (Response.body -> converted to str) which is memory intensive and not needed
https://github.com/scrapy/scrapy/blob/5a37af146f4f036168ac562918fca43adb4ac65f/scrapy/selector/unified.py#L66-L73

Motivation

As mentioned on https://github.com/scrapy/parsel/issues/210 usage of str input for creating Selector object is more RAM memory intensive

Describe alternatives you've considered

At this stage it will require to.. separately create Selector object with bytes input inside spiders callback method (and not use Response.Selector)

Additional context

Removing other usages of Response.text will significantly reduce RAM required to processing response
