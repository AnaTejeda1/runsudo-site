resources/images: Poor overlay quality when background image is an indexed (not true color) PNG

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches make the same core fix in `resources/image.go`: they skip re-applying the source image's palette when the action is a filter. This addresses the root cause, since `images.Overlay` and `images.Text` output was being clamped back to the indexed PNG's palette. Both also update the paletted overlay and text golden images. Patch A adds an `ActionFilter` constant, which is slightly cleaner than B's string literal "filter". However, Patch A also bundles a separate change for a different issue (12536). It switches hex parsing from `color.RGBA` to `color.NRGBA`, normalizes `Color.init` to NRGBA (which changes stored colors and luminance input), and rewrites `ColorGoToHexString` and `AddColorToPalette` equality semantics. It also regenerates an unrelated golden file (`padding-transparent-chained.png`) and edits existing color test expectations. That is unrelated behavior change in a widely used color path, so it adds regression risk and obscures the actual fix. On tests, Patch B adds a targeted integration test. It overlays a JPEG onto an indexed PNG, then asserts the output is not paletted and has more distinct colors than the source palette. This test would fail before the fix and pass after it. Patch A's coverage for this issue is only the regenerated golden images; its new unit tests concern the unrelated hex/NRGBA change. With equal correctness on the reported issue, B wins on a real regression test and a tighter, lower-risk scope.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

package main

import (
	"image"
	"image/png"
	"log"
	"os"

	_ "image/png"

	"github.com/disintegration/gift"
)

func main() {
	// Get the background image (24 bit: indexed not true color)
	f, err := os.Open("background.png")
	if err != nil {
		log.Fatal(err)
	}
	bgImage, _, err := image.Decode(f)
	if err != nil {
		log.Fatal(err)
	}

	// Get the foreground image (24 bit with 8 bit alpha channel)
	f, err = os.Open("foreground.png")
	if err != nil {
		log.Fatal(err)
	}
	fgImage, _, err := image.Decode(f)
	if err != nil {
		log.Fatal(err)
	}

	// Create a new image with dimensions of the bgImage.
	dstImage := image.NewRGBA(bgImage.Bounds())
	// Copy the bgImage to the dstImage.
	gift.New().Draw(dstImage, bgImage)
	// Draw the fgImage over the dstImage at the (20, 20) position.
	gift.New().DrawAt(dstImage, fgImage, image.Pt(20, 20), gift.OverOperator)

	// Create the composite file.
	f, err = os.Create("composite.png")
	if err != nil {
		log.Fatal(err)
	}
	defer f.Close()

	// Encode the composite image.
	err = png.Encode(f, dstImage)
	if err != nil {
		log.Fatal(err)
	}
}

Details:

  • Background image is a 24 bit indexed PNG file with 256 colors in its palette
  • Foreground image is a 24 bit true color PNG with an 8 bit alpha channel
  • The final (composite) image seems to be limited to the palette of the background image

What the agent reported

I fixed the bug: an overlay or text filter on an indexed PNG now keeps the new colors instead of being squeezed back into the background's palette. I couldn't verify it through ./bt-test, though. Its test run can't download Go modules because there's no network, so the package failed to build and no tests ran. All the results below come from running go test directly against the module cache already on disk (GOMODCACHE=/bt/cache/go-mod GOPROXY=off).

What was wrong: After any image operation, doWithImageConfig in resources/image.go checked whether the source was an indexed PNG. If it was, it redrew the result using only the source's palette (at most 256 colors). That's fine for resize, fit, fill and crop, which don't add colors. But overlays and text do add colors, so the composite was reduced to the background's palette. GIFs weren't affected because this step only runs for PNG output.

What I changed:

  • The fix (resources/image.go:441): that palette step is now skipped when the operation is a filter (conf.Action != "filter"). Resize, fit, fill and crop still keep the palette.
  • Golden images: I regenerated resources/images/testdata/images_golden/filters/paletted/overlay.png and text.png. The most recent commit added them with the note that they were made before any fix. So they captured the bad output, and the old overlay.png is itself an indexed 256-color image. I didn't change the test code in TestImagesGoldenFiltersPaletted, and no other golden files changed.
  • New test: TestFilterPalettedPNGNotClampedToSourcePalette in resources/images/images_integration_test.go. It overlays sunset.jpg on the indexed gohugoio8.png with images.Overlay. It then checks that the published PNG is not indexed and has more distinct colors than the source palette.

Test results:

  • Before the fix: TestImagesGoldenFiltersPaletted passed against the bad golden files.
  • Fix applied, old golden files: it failed on overlay.png. After regenerating, it passes.
  • New test with the fix temporarily removed: it failed (the output was still indexed). With the fix, it passes.
  • Wider runs: ./resources/images/, ./resources/ and ./tpl/images/ all pass. Across ./resources/..., only two tests failed: TestGetRemoteHead and TestGetRemoteResponseHeaders. Both fetch https://gohugo.io/img/hugo.png and got "Forbidden" because there's no network, so they're unrelated to this change.

Side effects:

  • Any filter on an indexed PNG, including grayscale or brightness, now writes a full-color PNG, so those files can be larger. This makes sense because any filter can add colors, but it may be worth a release note.
  • Filtered images already cached in resources/_gen will keep the old output until that cache is cleared. Bumping the PNG format version would force a refresh, but it would also invalidate every cached PNG, so I didn't do it.

What the report asked for:

  1. Better overlay quality on an indexed PNG background: done, with the new test and the updated golden overlay.png.
  2. Output no longer limited to the background's palette: done. The new test checks the output isn't indexed and has more colors than the palette.
  3. Confirm it isn't an upstream gift problem: it isn't. The palette step was in Hugo's resources/image.go, not in gift.
  4. GIFs work fine: unchanged. The palette step only applies to PNG output, and the GIF tests still pass.

Everything is left as uncommitted changes. AGENTS.md and CLAUDE.md were already showing as deleted before I started, and I didn't touch them.
