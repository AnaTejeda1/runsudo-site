Element.appendChild allows self-parenting and creates a cyclic DOM tree

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the reported `e.appendChild(e)` case. Each adds a check that rejects inserting a node that is the target itself or one of its ancestors, with the same fast exit for childless nodes. Both check every child before moving any, so a rejected batch leaves the tree unchanged.

Patch A puts the check inside `setParentNode`, so it covers any path that reparents a node. To do that it restructures `addChildren`, `replaceChild` and the in-place fast path around a new `setParentNodeUnchecked`. That is broader, but it is more churn in hot code, and it changes the fast path, which now goes through `removeChild` logic it skipped before.

Patch A also misses one case. When a detached node calls `replaceWith(in)`, it borrows `in`'s parent before any check runs. If `in` is a descendant of that node, the node's parent pointer is already set to its own descendant. That is a parent cycle, and it can stay in place when the operation then fails.

Patch B checks at each entry point: `appendChild`, `before`/`after`, `replaceChild`, both `addChildren` overloads, and explicitly that detached `replaceWith` case, before any mutation. It is a smaller, less risky change to the existing code. It also moves `noNullElements` ahead of the fast path, which is a small robustness gain.

On tests, both suites would fail before the fix and pass after. Patch B's suite is broader: self and ancestor checks for append, prepend, insert, `appendTo`, `before`/`after`, `replaceWith`, the fast path, the detached-replace case, and a check that legitimate same-parent moves still work. Patch A tests atomic batch rejection and moving a populated subtree, both useful, but not `before`/`after` or the detached case.

Patch A's CHANGES entry is a minor plus. Overall, Patch B covers more edge cases with less risk and better tests.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Description

When this test is executed, it does not terminate and appears to enter an infinite loop.
The problem seems to be triggered by:

 e.appendChild(e);

This operation appears to make the element its own parent and child. The subsequent assertion failure may cause JUnit to serialize the cyclic element while constructing the failure message, which also does not terminate.
Should appendChild() reject self-parenting and prevent cyclic DOM structures, or is this behavior considered a problem with the test?
