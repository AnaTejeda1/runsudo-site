SSR memory leak after a render error in a dynamic component

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

**Root cause.** In SSR, a dynamic component that resolves to an element renders its slot children in vnode mode, which goes through `renderSlot` → `openBlock()`. If the slot throws before `createBlock()`, the module-level `blockStack` and `currentBlock` are left pointing at a stale array. Every vnode created by later renders is pushed into that array and kept alive. SSR has no client-style re-render that would later reset the block state.

**Patch A** unwinds blocks locally in `renderSlot` (on throw) and in `withCtx` (in `finally`). This fixes the reported slot scenario and inline `v-if` blocks inside slots. However:
- It only covers slot paths. Any other throw between `openBlock()` and `createBlock()` in SSR still leaves `currentBlock` stale. One example is a non-compiled render function. `renderComponentRoot`'s catch only does `blockStack.length = 0` and never clears `currentBlock`, and Patch A leaves that untouched.
- It adds work to `withCtx`, which runs on every slot invocation on the client. That adds risk and overhead to a hot path for an SSR-specific problem.
- Its tests are GC-based and are skipped when `--expose-gc` isn't available. They are faithful to the issue, but they need a vitest config change and depend on GC timing.

**Patch B** fixes the state at the SSR boundary.
- It adds `resetBlockStack()`, which clears both `blockStack` and `currentBlock`, so the stale `currentBlock` bug is actually fixed.
- It calls this from `renderComponentSubTree`'s catch, so any synchronous render error during SSR, from any source, leaves no block state behind.
- It also corrects `renderComponentRoot`, which previously reset only the stack and not `currentBlock`.
- It restores the rendering instance when `handleError` rethrows, and pops the dev warning context via `finally`. Both are closely related retention leaks on the same error path.
- The client hot path is unchanged; only error paths are touched.
- Its tests directly assert `blockStack.length === 0`, `currentBlock === null`, and that the rendering instance and scope id are reset after the failed render. These would fail before the fix, run deterministically without GC, and cover the issue scenario, a `v-if` inside the slot, a non-compiled render function, and warning-context leakage.
- Splitting out `doRenderComponentSubTree` is a small, clear refactor.

A full reset could in theory discard outer blocks if a caller caught the error mid-render, but SSR aborts the whole render on such errors, so this risk is minimal.

**Verdict.** Patch B addresses the root cause more completely, with deterministic and more thorough tests and less risk to client performance.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Steps to reproduce

  • download the reproduction from stackblitz (won't work there, needs to be run locally)
  • run pnpm i && pnpm leak
  • see the heap size & alive app instances grow with each request after the single failed render

The script renders 500 fresh SSR apps, which all get garbage-collected. Then renders one app whose slot content throws, then renders 500 more identical healthy apps, which will never be garbage collected afterwards.

A dynamic component <component :is> with a <slot /> is needed for this to reproduce.

Card

<script setup>
    defineProps({ tag: { type: String, default: 'div' } })
</script>

<template>
    <component :is="tag" class="card">
        <slot />
    </component>
</template>

app:

<script setup>
    defineProps(['payload'])  // one request renders with `payload: null` → throws
</script>

<template>
    <main>
        <Card>{{ payload.title }}</Card>
    </main>
</template>

What is expected?

A failed renderToString should not affect subsequent renders and all apps rendered after it should get garbage collected.

What is actually happening?

Every app created after the single failed render is kept in memory forever.
