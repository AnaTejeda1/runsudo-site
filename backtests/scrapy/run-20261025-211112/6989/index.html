Proposal: CLI improvements

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

The issue's concrete complaints are (1) `scrapy runspider spider3` with a name from `scrapy list` just says 'File not found' with no guidance, (2) crawl/runspider are not clearly distinguished in help/docs, and (3) running naively yields no stored output, which surprises users. Patch A addresses all three: `runspider` now detects when the argument is a project spider name (guarded by `inside_project()`, WARN_ONLY, and a broad except so the hint can never mask the original error) and tells the user to run `scrapy crawl <name>`; `crawl`, `check`, `fetch`, `shell`, and `parse` route unknown names through a shared `_load_spider` that raises a UsageError with a context-sensitive hint (use runspider for a file, `scrapy list` inside a project, 'no active project' otherwise) instead of a KeyError traceback; and both `crawl` and `runspider` gain `long_desc` text plus docs explaining that items are not stored unless `-o/-O` or FEEDS is used. The change to `crawl` (loading the class then passing it to `crawler_process.crawl`) is behaviour-preserving since `crawl()` already accepts a class. The `parse` change from log-and-continue to UsageError is a reasonable tightening. Patch A also adds a substantial test class covering unknown names across commands, the file-path-to-crawl hint, outside-project behaviour, the runspider-to-crawl hint, broken spider modules not hiding the error, over-long names, and help text content; these would fail on base and are not tautological. Patch B only reworded two `short_desc` strings and a few doc sentences; it adds no tests and leaves the actual error-message scenario from the issue unchanged (runspider still just says 'File not found'), and its docs edit oddly replaces the `crawl` line in the command list example with `runspider`. Independent tests confirm this: A passes all five, B fails the runspider-hint test and both help-text tests. A's extra scope (shared loader helper across commands) is in service of the same confusion the issue describes and adds little risk given the defensive guards. A is clearly the better fix.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Each saw the issue and the two patches, labelled A and B in random order (two of them saw ours as A), with issue links and version numbers removed. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours. The reasoning above is one judge's, shown verbatim.

Summary

  • Improve consistency in CLI arguments.
  • Modernize the usage.
  • Possibly implement introduce a new, higher level command with its own sub-commands so as not to break existing code.

Motivation

I find the CLI a little awkward and asymmetric: I'm always a little surprised about what's required to get expected results although I've used Scrapy for years.

Here's one example that I just experienced:

Now, let me see what spiders are available.

$ scrapy list

spider1
spider2
spider3

Ah hah. I want to run spider3. Let's see how to do it:

$ scrapy

Scrapy 2.13.3 - active project: my_project

Usage:
  scrapy <command> [options] [args]

Available commands:
  bench         Run quick benchmark test
  check         Check spider contracts
  crawl         Run a spider
  edit          Edit spider
  fetch         Fetch a URL using the Scrapy downloader
  genspider     Generate new spider using pre-defined templates
  list          List available spiders
  parse         Parse URL (using its spider) and print the results
  runspider     Run a self-contained spider (without creating a project)
  settings      Get settings values
  shell         Interactive scraping console
  startproject  Create new project
  version       Print Scrapy version
  view          Open URL in browser, as seen by Scrapy

Use "scrapy <command> -h" to see more info about a command

Ok, runspider - Run a self-contained spider (without creating a project) rings a bell.

And I definitely don't want to create a new project, so that sounds right.

$ scrapy runspider spider3

Usage
=====
  scrapy runspider [options] <spider_file>
scrapy: error: File not found: spider3

Ok, I need to refer to it by filename...

$ scrapy runspider path/to/spider3

Hmm. No output at the command line (stdout) nor to a file. (??) Let me look at the CLI help...

Etc. There are several other scenarios I can think of. Another is that crawl and runspider could be documented to more clearly distinguish them.

Describe alternatives you've considered

Writing a wrapper script using a modern Python CLI library.

Additional context

I've written a couple of dozen Scrapy Spiders, but these things still trip me up every time. Especially how running crawl or runspider naively with no options is basically a fail.

Is there interest in a set of Issues to address various opportunities for improvements and PRs for them?
