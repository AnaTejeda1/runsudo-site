Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the root cause (the `continue` on content-less candidates in `_process_candidates`) and both pass all nine independent tests, so the decision rests on edge handling and risk. Patch A keeps the change tight: it adds the NO_IMAGE/IMAGE_* mappings, appends an empty assistant choice with `native_finish_reason` only for the content-less case, maps `content_filter` to Anthropic `refusal`, and derives Responses `incomplete_details` from the finish reason. A's tests exercise the streaming `/v1/messages` path end-to-end through `AnthropicStreamWrapper`, which B only covers at the chunk level. Patch B is well-crafted and has broader tests (core_helpers table, adapter unit tests, Responses precedence test, multi-candidate state isolation), and fixing the shared per-candidate state in the loop is a legitimate improvement. But B also changes every Gemini choice to carry `provider_specific_fields={'native_finish_reason': ...}`, changes `tools` initialisation from `[]` to `None`, rewrites the finish-reason key set via `get_args`, and adds three more unmapped reasons; these widen the blast radius of the fix into all Gemini responses without evidence from the full suite, which is where scope beyond the ask counts against it. A's streaming reliance on the existing `_apply_stream_candidates` fallback is slightly less uniform than B's single path, but it is correct and verified. On balance A resolves the issue as specified with the fewest behavioural changes and the more careful handling of the refusal edge, so A edges it.

What happened?

When Gemini answers with a candidate that has a finishReason but no content, the gateway drops the candidate. gemini-2.5-flash-image served with modalities: ["image"] and asked a text-only question is a deterministic way to get one: Gemini returns finishReason: NO_IMAGE and no parts. Since PR #40294 the gateway no longer answers HTTP 500 on that shape, but what it returns instead carries no trace of why the model produced nothing: /v1/chat/completions comes back with "choices": [] and no finish_reason, /v1/messages comes back with "content": [] and "stop_reason": "end_turn", and /v1/responses comes back with an empty output and "status": "completed". A client cannot tell a declined request from an empty answer, and the same drop hides MALFORMED_FUNCTION_CALL and OTHER. A thinking model that spends its whole budget on thoughts (finishReason: MAX_TOKENS, no content) hits the same branch and arrives with nonzero output_tokens: that case is #36881, with fix PRs #36870, #38301 and #40252 open, so a fix here should build on one of those rather than duplicate it

Expected: the completion carries one choice with an empty assistant message and a finish_reason mapped from Gemini's finishReason (raw value kept in the provider-specific fields), /v1/messages maps it to the matching Anthropic stop_reason, and /v1/responses carries the matching incomplete_details. Which OpenAI and Anthropic values NO_IMAGE and the other non-STOP reasons map to is a decision for the fix PR to record with its alternatives. Gemini safety blocks are a different path and already come back as a content_filter choice

User Flow

Before a (hypothetical) fix: a developer asking an image model a text-only question gets an empty 200 with no reason attached, so their app shows a blank answer and logs nothing to explain it

  1. They send POST https://litellm-domain/v1/chat/completions with "model": "gemini-2.5-flash-image" and a text-only user message
  2. They get HTTP 200 with "choices": [] and "completion_tokens": 0, no finish_reason anywhere
  3. They send the same question as POST https://litellm-domain/v1/messages and get HTTP 200 with "content": [] and "stop_reason": "end_turn", which reads as a normal, complete answer
  4. They send it as POST https://litellm-domain/v1/responses and get HTTP 200 with "output": [] and "status": "completed"

After a (hypothetical) fix: the same requests still return 200, and each one says why the model produced nothing

  1. They send POST https://litellm-domain/v1/chat/completions with "model": "gemini-2.5-flash-image" and a text-only user message
  2. They get HTTP 200 with one choice, an empty assistant message, a finish_reason mapped from NO_IMAGE, and the raw NO_IMAGE value in the provider-specific fields
  3. POST https://litellm-domain/v1/messages returns HTTP 200 with "content": [] and the matching stop_reason
  4. POST https://litellm-domain/v1/responses returns HTTP 200 with the matching incomplete_details instead of a bare completed
