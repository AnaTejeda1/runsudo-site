related: Add option to tokenize headings

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both correctly add Tokenize gated to fragment headings while preserving exact matching for non-heading fragments. But Patch A has two genuine correctness defects: (1) it appends a doc to a token's posting list once per heading containing that token and duplicates query keywords likewise, so searchDate double-counts weight and inflates rank/reorders related results; (2) its FieldsFunc tokenizer emits garbage tokens from HTML entities in titles (e.g. 'amp','34') causing spurious matches. Patch B fixes both — deduplicating index- and query-side via seenKW and unescaping entities in splitWords — and backs each with a fail-before/pass-after test, alongside a much more comprehensive suite (fragments, entities, apply-filter, case-sensitivity, dedup, splitWords unit table). Patch A is tighter-scoped and includes the exact docs the issue requests (content page + docs.yaml) with cleaner DRY helpers, whereas B ships no docs, adds an out-of-scope undocumented MinTokenLength option, extends tokenization to basic indices beyond the documented fragments-only contract, and adds whitespace churn. Since correctness and test quality are the top two weighted criteria and B is meaningfully stronger on both, B wins despite A's superior scope and documentation.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Summary

What was requested: Add a tokenize option to Hugo's related-content feature so that multi-word heading titles in fragments-type indices are split into individual keywords for indexing and matching, while non-heading fragments (e.g. definition terms) keep exact-identifier matching. Default false.

Root situation: For type = "fragments" indices, documents were only ever indexed/queried under their exact heading identifiers (slugified IDs) as FragmentKeywords, so two pages could relate only if they shared a full heading ID. There was no mechanism to relate pages that merely share a word within a heading.

What I changed (all in related/inverted_index.go, plus docs):

  • Added Tokenize bool to IndexConfig (decoded automatically via mapstructure.WeakDecode; default false).
  • Added two helpers: tokenizeTitle (splits a title into normalized word tokens, honoring ToLower) and fragmentsToKeywords (tokenizes a heading's title into FragmentKeyword tokens only when Tokenize is on and the identifier is a real heading in HeadingsMap with a non-empty title; otherwise emits the exact FragmentKeyword(id)).
  • Routed both Add (indexing) and Search (query building) through fragmentsToKeywords, keeping them symmetric. Explicit user-supplied opts.Fragments stay exact.
  • Made the ApplyFilter/HeadingsFiltered predicate in searchDate tokenize-aware, while leaving the non-tokenize path byte-identical (fragmentsFilter.Contains(h.ID)).
  • Documented the option in docs/content/en/configuration/related-content.md and docs/data/docs.yaml.
  • Added regression test related/related_tokenize_integration_test.go.
