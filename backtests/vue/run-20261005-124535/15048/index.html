Scoped slot transforms array argument if rendered conditionally

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the core issue the same way: when a key is injected into a slot outlet, it goes to a new trailing `renderSlot` argument instead of being merged into the slot props, so a `v-bind` array reaches the slot unchanged.

**Patch B** is more precise and more thorough.
- It only takes the separate-key path when the props are a single `v-bind` expression, which is the case that actually breaks. Plain-object props keep their existing behavior, so existing snapshots are unchanged.
- It also fixes a closely related path the same root cause reaches: the `ref_for` marker merged by `v-for` with `v-bind` on a slot outlet, which also turns arrays into objects. It does this by skipping `pushRefVForMarker` for slot outlets.
- In custom element mode, it puts the key on the wrapping Fragment.
- Its tests are strong:
  - compiler-level tests for `v-if` and keyed `v-for`;
  - a negative test confirming `mergeProps` is kept when other props exist;
  - an end-to-end compiler+runtime integration test that checks `Array.isArray` on the slot props across `v-if`/`v-else`, keyed and unkeyed template `v-for`, and `v-for` on `<slot>`, including toggling;
  - an SSR hydration test.
- These would clearly fail before the change.

**Patch A** is broader and riskier.
- It routes every injected slot key through the new argument, even for plain object props. That changes generated output for all `v-if` slots, changes the props slots receive (`key` disappears), and rewrites existing snapshot expectations.
- It leaves the `v-for` `ref_for` merging path unaddressed, so `<slot v-for v-bind="arr">` still converts the array.
- Its snapshot changes look suspect. A `v-for` snapshot entry was added to `transformElement.spec.ts.snap`, and the diff shows identical blob hashes for that file and `vFor.spec.ts.snap`. That suggests accidental snapshot churn.
- Its tests are mostly compiler-shape and `renderSlot` unit tests. There is no end-to-end check that the slot receives an array.

Overall, B fixes the root cause more completely, with less churn and stronger behavioral tests.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Steps to reproduce

  1. Create a component with a scoped slot that is rendered conditionally
  2. Pass an array as the sole argument to the slot

What is expected?

Array is rendered normally.
If you render items of that array in v-for loop, you only see items inside that array

What is actually happening?

Array is transformed into object. Items and their indexes are staying the same, key field is added
