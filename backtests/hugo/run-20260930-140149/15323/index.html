tpl/collections: union silently returns an empty list when the two slice types differ

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Patch B is the better fix.

**Patch B**
- It merges two numeric slices of different types into a `[]any`.
- Deduplication goes through `appendIfNotSeen`, which normalizes numbers, so `1` and `1.0` collapse to one element while `1.5` survives as a distinct value. No data is lost.
- It works no matter which argument is empty, because it does not rely on the l1/l2 prototype logic.
- It moves the uncomparable-type check ahead of the early return. That fixes the second symptom the issue reports: `union (slice (slice 1)) (slice 2)` now errors instead of silently returning `[]`.
- Tests:
  - Unit cases cover numeric merges in both directions and with non-integral floats, plus a `[][]int ∪ []int` error case.
  - Integration tests reproduce the issue's template exactly and the uncomparable-error case.
  - All of these would fail before the patch.

**Patch A**
- It lets numeric mixed types fall through into the existing per-element conversion, which converts l2's elements to l1's element type.
- This keeps l1's concrete type (e.g. `[]int`). Float-to-int conversion is therefore lossy: `[]int{1} ∪ []float64{1.5}` would truncate or collapse the 1.5 rather than preserve it.
- Its own guard means `[]int{} ∪ []float64{1.0}` returns `[]int{}`. That is the same silently-empty result the issue complains about, and Patch A enshrines it in a test as expected behavior.
- It does not address the uncomparable-check ordering problem the issue explicitly calls out.

**Shared gap**
- Neither patch handles non-numeric mixed types such as int and string, which still return empty.

Within that shared gap, B resolves more of the issue, avoids lossy conversion, and has stronger tests.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Does this issue reproduce with the latest release?

I built master at ae07063 and reproduced it there. I did not run a tagged release binary, so I have not confirmed it against one directly, though Union is unchanged in tpl/collections/collections.go.

What did you expect to see?

union either returning the union of its two arguments, or returning an error. It already errors for the other argument shapes it cannot handle, for example union does not support slices or arrays of uncomparable types and can't iterate over ....

What did you see instead?

union returns an empty slice, with no error, whenever the two arguments have different slice types and neither has an interface element type.

layouts/index.html:

{{ printf "%T" (slice 1) }}
{{ printf "%T" (slice 1.0) }}
union int,int    -> {{ union (slice 1) (slice 2) }}
union int,float  -> {{ union (slice 1) (slice 1.0) }}
union int,string -> {{ union (slice 1) (slice "a") }}
union lists      -> {{ union (slice 1 2) (slice 2.0 3.0) }}
intersect lists  -> {{ intersect (slice 1 2) (slice 2.0 3.0) }}

Output:

[]int
[]float64
union int,int    -> [1 2]
union int,float  -> []
union int,string -> []
union lists      -> []
intersect lists  -> [2]

intersect handles the same two mixed-type lists and returns [2], so the sibling functions disagree about whether these arguments are usable at all.

The cause is this early return in Union:

if l1v.Type() != l2v.Type() &&
	l1v.Type().Elem().Kind() != reflect.Interface &&
	l2v.Type().Elem().Kind() != reflect.Interface {
	return ins.r.Interface(), nil
}

ins.r is the empty slice made just above, so a caller gets an empty list rather than an error. It is reachable from ordinary templates because slice 1 is []int and slice 1.0 is []float64, and it also runs before the uncomparable-types check, so union (slice (slice 1)) (slice 2) returns [] instead of the error that check would raise.

Adding one element of another type to the first argument avoids it, since the slice then becomes []interface {}: union (slice 1 "x") (slice 1.0) returns [1 x].

Stack traceback or browser console output

None, no error is raised. That is the problem.

This is a different mechanism from #3411, which was closed in 2017 and is now locked with a note asking that related bugs be opened as new issues.

Happy to send a PR. Returning an error here would be a small change; making union accept mixed types the way intersect does is bigger, so I would rather you pick the direction first.

What the agent reported

I fixed union so mixed int/float slices now give a real union, and union (slice (slice 1)) (slice 2) now raises the uncomparable-types error. One case is still wrong: union (slice 1) (slice "a") still returns [] with no error, because existing tests require that. The new tests pass in a direct go test run, but ./bt-test never actually ran any tests, because it couldn't download the Go modules.

What was wrong. In Namespace.Union (tpl/collections/collections.go), an early return handed back an empty slice of the first argument's type whenever the two slice types differed and neither had any elements. Because slice 1 is []int and slice 1.0 is []float64, ordinary templates hit it. It also ran before the uncomparable-types check, so [][]int ∪ []int returned [] instead of the error. The doc comment was also wrong: it said the first list is returned.

What I changed (production code is only tpl/collections/collections.go):

  • Uncomparable check moved earlier. It now runs before the type comparison, so union (slice (slice 1)) (slice 2) raises "union does not support slices or arrays of uncomparable types".
  • Mixed numeric slices. When both element types are numbers, the two lists are merged into a []any. Duplicates are compared by numeric value, the way intersect compares them, and values keep their original type with nothing rounded. So union (slice 1) (slice 1.0) gives [1], union (slice 1 2) (slice 2.0 3.0) gives [1 2 3], and [1] ∪ [1.5] gives [1 1.5].
  • Other mismatches unchanged. For example, []int ∪ []string still returns an empty slice, for the reason below.
  • Doc comment. Rewritten to describe what the function actually does.

Conflict with existing tests. The report asks for an error or a real union for int ∪ string. Two existing rows in TestUnion (collections_test.go:667-668), {[]string{"1","2"}, []int{3}, []string{}, false} and {[]int{1,2}, []string{"1","2"}, []int{}, false}, require exactly the empty, no-error result. Either direction would break them, and I wasn't allowed to change existing tests. Changing this is a maintainer decision.
