Align void elements list to spec

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches make the same core fix. They drop `command`, `device`, and `menuitem` from the known tags and void tags in TagSet. They also drop `command` from the InHeadEmpty and InBodyStartToHead lists in HtmlTreeBuilderState. So both resolve the issue equally at its root.

The difference is in tests and extra changes. Patch A adds tests aimed directly at the issue:
- a parameterized parse test showing each obsolete tag now holds content and needs an end tag;
- a test that `<command>` in head breaks out into body and is no longer redirected to head processing from body;
- a TagTest check that these tags are now unknown, not empty and not self-closing, while real spec void elements stay void.

These tests would fail before the change and pass after it.

Patch B adds no tests for `command`, `device`, or `menuitem`. Its only new test covers a separate change: it removes the `!tag.isKnownTag()` shortcut in InBody so unknown tags rebuild active formatting elements. That may be spec-aligned, but it goes beyond the issue's ask. It changes parsing for every custom or unknown tag, which adds risk and hides the actual fix. Its single test covers only that side change.

With equal correctness on the issue, Patch A's focused and meaningful tests, and its smaller blast radius, make it the better fix.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
