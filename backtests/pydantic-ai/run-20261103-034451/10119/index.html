Both patches make `from pydantic_ai.agent import *` work and both are confirmed by the independent tests, so the decision rests on which resolution better fits the issue's root cause and intent. The issue notes the original commit used the `RealtimeEvent as RealtimeEvent` re-export idiom, meaning the name was meant to be a public export and only the runtime half was missed. Patch A completes that intent with a module-level `__getattr__` that lazily resolves `RealtimeEvent` from `pydantic_ai.realtime`, exactly the arrangement the issue points to as already used by `pydantic_ai.ui`, and it preserves the import-time constraint (the independent lazy-load test still passes). It also raises a correctly formatted AttributeError for unknown names, so star-import and `hasattr` semantics stay sane. Patch B instead drops the export from both the `TYPE_CHECKING` block and `__all__`, which is a legitimate option the issue allows, but it removes a public typed name (requiring an API-compatibility allowlist entry) rather than making the advertised name work, effectively reversing the original commit's intent. On tests, A's first test exercises the real star-import path for every `__all__` entry, checks identity against the `pydantic_ai.realtime` class, and checks the unknown-name error; its second test guards the 120 ms lazy-import property in a fresh interpreter, which is the key constraint the issue calls out. B's single `hasattr` invariant test is a good general guard and would fail on base, but is narrower. One caveat against A: the `@pytest.mark.subprocess` marker may not be registered in the repo, which could produce an unknown-mark warning/error depending on pytest config; this is a craft risk in the test only and does not affect the fix itself. Scope and craft are otherwise comparable; B's allowlist bookkeeping is appropriate for its approach, and A's fix is minimal and matches existing package conventions. Overall A resolves the issue at its root while keeping the public name usable, so it is the better fix.

Description

pydantic_ai.agent.__all__ advertises RealtimeEvent, but the name is only bound inside that module's if TYPE_CHECKING: block, and pydantic_ai/agent/__init__.py has no module-level __getattr__. __all__ is a runtime contract — a star-import resolves each entry with getattr — so the module advertises a name that no caller can actually import:

$ python -c "from pydantic_ai.agent import *"
AttributeError: module 'pydantic_ai.agent' has no attribute 'RealtimeEvent'

$ python -c "from pydantic_ai.agent import RealtimeEvent"
ImportError: cannot import name 'RealtimeEvent' from 'pydantic_ai.agent'

Nothing catches it today: pyright counts a TYPE_CHECKING binding as a module symbol, so type checking and CI stay green while hasattr and __all__ disagree:

$ python -c "import pydantic_ai.agent as m; print('RealtimeEvent' in m.__all__, hasattr(m, 'RealtimeEvent'))"
True False

A note for whoever fixes this: pydantic_ai.realtime is the optional realtime extra, and import pydantic_ai deliberately does not load it (unlike pydantic_ai.agent, which the root package does load). Importing pydantic_ai.realtime eagerly from pydantic_ai.agent adds roughly 120 ms of provider and codec modules to every import pydantic_ai, which is what the TYPE_CHECKING block exists to avoid. A module-level __getattr__ — the arrangement pydantic_ai.ui already uses for DEFAULT_HTML_URL/OFFLINE_HTML_URL — keeps the advertised name working without paying that cost; dropping the entry from __all__ is the other option, which is your call, not mine.

Introduced in d6d66de54 (#6324), which added both RealtimeEvent as RealtimeEvent to the TYPE_CHECKING block and 'RealtimeEvent' to __all__; the explicit as alias is the "this is a re-export" idiom, so the runtime half looks like it was simply missed. As a sanity check, every other __all__ entry in the package does resolve (596 names across 292 importable modules).

Minimal, Reproducible Example

from pydantic_ai.agent import *  # AttributeError: module 'pydantic_ai.agent' has no attribute 'RealtimeEvent'
