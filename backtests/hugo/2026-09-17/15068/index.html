In this judgment, Patch A = our agent, Patch B = the merged fix.

The issue's substantive request (body + linked comment) is explicit: 'It's clumsy that you need to create a resource... to get a SRI hash. I suggest we add crypto.Fingerprint with a signature like hash.Fingerprint [ALGORITHM] any -> string' returning 'sha256-...'. Patch A implements exactly that root-cause fix: hash.Fingerprint(value) / hash.Fingerprint(algo, value) returning the SRI form 'sha256-HY1v...nw4='. It correctly matches the requested signature and pipe ergonomics (with two args, algo is args[0] and value args[1], so `value | hash.Fingerprint "sha256"` works), unwraps both hugio.ReadSeekCloserProvider and resource.ContentProvider so `any` can be a string OR a Resource as the issue calls for, defaults to sha256, and returns clear errors for bad algo/arity. It also acts on the implementer note about 'obvious code reuse potential' by hoisting NewHash into common/hashing and having integrity.go delegate to it — a scoped, motivated refactor that removes duplication rather than incidental churn. Its test fails before/passes after and covers default, explicit sha256, sha512 prefix, unsupported algo, and arity errors. Patch B instead implements encoding.HexDecode/HexEncode (matching only the issue *title*), which does NOT resolve the core complaint: to get an SRI hash the user must still chain `$s | crypto.SHA256 | encoding.HexDecode | encoding.Base64Encode` and manually build the `sha256-` prefix — precisely the clumsy, multi-step workaround the issue asks to eliminate. Patch B's tests (including a nice end-to-end integration test) are well-crafted and correct, but they verify a symptom-level workaround rather than the requested primitive. On the top-weighted criterion (correctness / root-cause resolution) Patch A clearly wins; both have solid, non-tautological tests and reasonable scope/craft, so A is the better fix overall.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The issue

View on GitHub

See https://github.com/gohugoio/hugo/issues/15060#issuecomment-4790405347

It's clumsy that you need to create a resource (making up an unique filename) to get a SRI hash.

I suggest we add crypto.Fingerprint with a similar signature to https://gohugo.io/functions/resources/fingerprint/

hash.Fingerprint [ALGORITHM] any -> string

The function name is a little clumsy, but we need to keep the two very similar functions in line.

Where any typically is a string (but can also be a Resource -- we have similar unwrappers elsewhere).

It would then return e.g. sha256-Yuh...rfE=.

Note to implementer: There's some obvious code reuse potential here.
