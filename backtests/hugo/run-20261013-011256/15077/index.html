Make .Render take additional data

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches make the same core change. Each widens `Render` to `...any`, updates every implementer (pageContentOutput, LazyContentProvider, nopPage, testPage), and passes the optional data as the template context instead of the Page. Template resolution stays keyed to the page's content type in both.

Correctness: the issue writes the signature as `PAGE.Render [DATA] NAME`, with data first. Patch A accepts both `NAME DATA` and `DATA NAME` through `parseRenderArgs`. It tells them apart by which argument is a string, and if both are strings it treats the first as the name. Patch B accepts only `NAME [CONTEXT]`. Calling it in the order the issue shows, e.g. `.Render (dict ...) "lid"`, makes B try to cast a map to a string and fail. Patch A therefore covers the scenario the issue describes, and Patch B misses half of it.

Edge handling: Patch A rejects non-string layout names such as `42`, rejects an empty name, and limits the call to two arguments, each with a clear error. Patch B checks the argument count but uses `cast.ToStringE`, so a numeric name is silently accepted as "42". When the data argument is nil, Patch A falls back to the Page. That choice is debatable but defensible, and it is tested.

Tests: Patch A tests both argument orders and confirms that a content-type-specific layout (`books/lid.html`) is still chosen when data is passed. It also covers string data, nil data, and five error cases. Patch B's tests are thinner: one data case using a dict that imitates a Title field, and two error cases. Both sets of tests would fail without their fix.

Scope/craft: Patch A also updates the user docs to describe the new argument, which is reasonable because the feature is user-facing. Its code keeps parsing separate from execution and is cleaner for that. Patch B is shorter, but it renames the concept to "view" in its error messages, which doesn't match the existing "layout" wording.

Overall, Patch A matches the issue's stated syntax, handles more edge cases, and is better tested.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The issue

View on GitHub

See https://gohugo.io/methods/page/render/#article
See #15076

PAGE.Render NAME

This has been discussed before.

  • The contract has always been that the templates that .Renders gets the data context as e.g. page.html, a page.Page.
  • We can only pass 1 argument to Go's template renderer, which I guess is the blocking reason for not having done this sooner.

So, if we want to do:

PAGE.Render [DATA] NAME

I'm guessing we have 2 top-level options:

  • We say that if DATA is set, we use that as the context passed to the templates,. else PAGE.
  • We somehow (e.g. by embeding it in a { DataAdditionalContext, Page } struct or putting it into the current context.Context) wrap the Page so you can do both .RelPermalink and .DataAdditionalContext (naming of the latter is just picked out of a hat without thinking too hard.
