Panic when deleting a directory in static when server is running

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches add the same core fix: a `files.ComponentFolderStatic` case in `processPartialFileEvents`, so the reported panic goes away with either one. Patch B goes further in a way that matters for the delete scenario. The old `SourceFilesystem.Contains` only checked directory mounts, via `dir.IsDir()`, with a prefix match. Deleted paths, especially file mounts such as `myfiles/robots.txt -> static/robots.txt`, may therefore not be recognised as belonging to the static filesystem, and the static syncer in the commands package would never see them. Patch B makes `Contains` stat-free by using `ReverseLookup`, so the static syncer can correctly identify deleted static files and directories, including file mounts. That addresses the underlying handling of deletions, not just the panic. On tests, Patch B adds two server testscripts that run the real `hugo server`, delete a mounted static file and a mounted static directory, and assert no stderr output, so a panic would fail them. These exercise the actual reported scenario end to end. Patch A's integration test removes a static directory in a `TestRunning` builder and only checks that the home page still renders. It likely does trigger the panic path, but it does not cover mounts or syncing. The `Contains` change carries some risk because it alters semantics for other callers, but the new behaviour is the more correct membership check. Overall, B is more complete and better tested.

What the agent reported

I fixed the panic when a directory in static is deleted while hugo server is running. The new regression test fails on the old code with the reported panic and passes with the fix. ./bt-test couldn't build anything in this sandbox, so every test result below comes from running go test directly.

What was wrong: the switch pathInfo.Component() in processPartialFileEvents (hugolib/hugo_sites_build.go) has no case for static, and its default: panics with unknown component. Static files are normally filtered out earlier: commands/hugobuilder.go sends an event to the static syncer only if SourceFilesystems.IsStatic says the path is static. That check depends on RootMappingFs.Mounts (hugofs/rootmapping_fs.go:257), which quietly drops any mounted directory that no longer exists. So after a mounted static directory is deleted, its event can be misrouted to HugoSites.Build and hit the panic.

Change: one line in hugolib/hugo_sites_build.go. I added a no-op case files.ComponentFolderStatic: with a comment, next to the existing no-op for archetypes. Nothing in that code builds anything from static files, so skipping them loses nothing there.

Test: TestRebuildDeleteDirInStatic, added at the end of hugolib/rebuild_test.go. It builds a site with static/mydir/foo.txt, deletes the file and then the directory, rebuilds, and checks the home page still renders.

  • Without the fix: --- FAIL ... panic: unknown component: "static" at hugo_sites_build.go:1084, matching the report.
  • With the fix: --- PASS.

Test runs:

  • ./bt-test couldn't build any package: its module cache is empty and the network is blocked, so the report shows FAIL github.com/gohugoio/hugo/hugolib [setup failed]. I ran go test against the existing module cache instead (GOMODCACHE=/bt/cache/go-mod GOPROXY=off).
  • On the full ./hugolib package, the only failures are TestModulePrivateRepo and the three TestGitInfoFromGitModule* tests. They fail the same way on the unmodified code and depend on network or git module access.
  • ./commands has no tests.

Requirements:

  1. No panic when deleting a directory in static while the server runs: done. The regression test fails before the fix and passes after.

Not fixed: the fix stops the crash, but a misrouted event still never reaches the static syncer. So when a whole mounted static directory is deleted, its copied files can stay in the publish directory until the next full static sync. Fixing that means changing how IsStatic checks mounts, which affects code outside this bug, so I left it out.

The test harness sends events straight to HugoSites.Build, so it skips the command-layer routing. That means the test covers the panic, not the routing. I couldn't pin down exactly which paths get misrouted in the reporter's setup.

Everything is left as uncommitted edits in hugolib/hugo_sites_build.go and hugolib/rebuild_test.go. The AGENTS.md and CLAUDE.md deletions in the working tree were there before I started.
