SSR memory leak after a render error in a dynamic component

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the core leak the same way: `renderSlot` now restores the block stack in a try/catch and resets `_d` in a `finally`. A failing slot inside `<component :is>` therefore no longer leaves a stale `currentBlock` that collects every later vnode, which is what retains the later apps.

The difference is in the other paths each patch covers.

Patch B adds a cleanup to the `finally` of `withCtx`. This handles inline blocks (such as `v-if`) inside any compiled slot function, including slots called directly by SSR helpers. It is a fairly general hook.

Patch A covers more of the codebase:
- The custom-element fallback branch of `renderSlot`.
- `normalizeChildren` slot invocation, which is the dynamic-element case its second SSR test exercises.
- A real latent bug in `renderComponentRoot`: the catch block set `blockStack.length = 0` but never reset `currentBlock`, so it kept pointing at a dead block. Patch B leaves this untouched.
- The dev warning-context stack, now popped in `finally` in both `setupComponent` and `renderComponentSubTree`, so a failed render no longer leaves stale vnode/app references on that stack.

Patch A also adds a small `resetBlockDepth` helper instead of repeating the inline loop.

Tests: both add GC-based SSR regression tests covering the issue scenario and a `v-if` variant. Patch A also adds targeted unit tests:
- `blockStack` and `currentBlock` invariants after slot, fallback and custom-element-fallback throws.
- Nested blocks.
- `_d` restoration.
- The `renderComponentRoot` reset.
These fail before the fix and are precise. Patch A's GC test also deliberately avoids `expect().rejects` retaining the rejected render.

Patch B's `withCtx` hook does cover one case Patch A misses: an inline block thrown inside a compiled slot invoked directly by `ssrRenderSlot`. On balance, Patch A fixes more of the unclosed-block leak paths, including the clear `currentBlock` bug, and has stronger tests, so A is the better fix.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Steps to reproduce

  • download the reproduction from stackblitz (won't work there, needs to be run locally)
  • run pnpm i && pnpm leak
  • see the heap size & alive app instances grow with each request after the single failed render

The script renders 500 fresh SSR apps, which all get garbage-collected. Then renders one app whose slot content throws, then renders 500 more identical healthy apps, which will never be garbage collected afterwards.

A dynamic component <component :is> with a <slot /> is needed for this to reproduce.

Card

<script setup>
    defineProps({ tag: { type: String, default: 'div' } })
</script>

<template>
    <component :is="tag" class="card">
        <slot />
    </component>
</template>

app:

<script setup>
    defineProps(['payload'])  // one request renders with `payload: null` → throws
</script>

<template>
    <main>
        <Card>{{ payload.title }}</Card>
    </main>
</template>

What is expected?

A failed renderToString should not affect subsequent renders and all apps rendered after it should get garbage collected.

What is actually happening?

Every app created after the single failed render is kept in memory forever.

after 500: created=500 finalized=500 alive=0 heap=20.6MB

--- phase 2: 500 healthy renders (identical to phase 1) ---
after 500: created=1001 finalized=500 alive=501 heap=29.0MB

FINAL: created=1001 finalized=500 alive=501
