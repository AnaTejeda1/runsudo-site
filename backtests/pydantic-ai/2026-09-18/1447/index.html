Description

The OpenAI Agents SDK is probably one of the first SDKs that supports voice agents OOTB and I think that it would be a nice addition to PydanticAI.

Essentially, these are native speech-to-speech models that can perform tool calling, transcription, interruption detection, etc.

The implementation differs slightly between providers (Google, AWS, OpenAI...) but the idea is similar with normal LLMs: send user input, capture all the steps that happen (tool calls, partial transcriptions) and then returning output.

OpenAI Agents SDK have implemented them using a VoicePipeline, as shown here:

https://openai.github.io/openai-agents-python/voice/quickstart/

Although probably not as pressing as supporting Prompt Caching, this is definitely a use case that people are willing to switch framework for, especially companies looking to augment customer service with AI Agent triage.

Does it sound like something that Pydantic would be interested in supporting?

Final Report

What the report asks for

Issue #1447 is a feature request / RFC, not a bug report. Its explicit asks are:

  1. Add native speech-to-speech ("realtime") model support à la the OpenAI Agents SDK VoicePipeline.
  2. Cover OpenAI Realtime API and equivalents (AWS Nova Sonic, Google live/bidi).
  3. Support the realtime-specific capabilities: tool calling, live transcription, interruption detection, and bidirectional user-input → intermediate-steps → output flow.
  4. It closes with a literal question — "Does it sound like something that Pydantic would be interested in supporting?" — i.e. it is soliciting a design/roadmap decision, not reporting a broken, testable behavior.

What I found (evidence)

  • No existing scaffolding. Broad case-insensitive greps for realtime, voice, speech, live, session, transcription, and bidirectional streaming across the package and docs/ return only incidental hits (test cassette names, mock files). There is nothing to fix or complete.
  • The core Model ABC is request/response-shaped, not bidirectional. pydantic_ai_slim/pydantic_ai/models/__init__.py:636 — request() (:662) returns a single ModelResponse; request_stream() (:685) yields a one-directional StreamedResponse. There is no session/interruption/live-audio abstraction, and audio is input-only (messages.py AudioUrl/BinaryContent; no audio-output content type exists). A realtime feature would require a brand-new public bidirectional abstraction — a design decision owned by the maintainers.
  • The project's own rules route this out of core. docs/contributing.md:53-62 ("Rules for adding new models"): anything "that requires more logic" should ship as a separate pydantic-ai-xxx package inheriting from the Model ABC. Multi-provider realtime S2S is squarely in that category (and network/gh access is blocked here, so upstream cannot be added anyway).

Disposition — why no code change was made

This cannot be resolved by "the smallest production-code change" backed by a regression test:

  • There is no defined, user-visible bug behavior to reproduce or assert against — the report asks for a new capability and a roadmap answer.
  • A faithful implementation is thousands of lines spanning a new bidirectional API abstraction, new audio-output content types, and per-provider client integrations (OpenAI Realtime, Nova Sonic, Google live) — the opposite of a minimal fix, and per the repo's own contribution rules it belongs in a separate package.
  • Any test I could add would either be trivial (passing before and after — explicitly forbidden by the workflow) or would only exercise a public API I invented myself, which would not match whatever the maintainers ultimately design. Per the rules, shipping such a test is "worse than no test."

I therefore did not fabricate a speculative framework, and I left the working tree unchanged (the three D entries in git status — .claude/settings.json, AGENTS.md, CLAUDE.md — pre-date my session; I created and modified nothing).
