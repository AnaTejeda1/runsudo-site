[Bug]: minimax provider silently drops top-level reasoning_effort (M3.1-Flash supports low|medium|high|max)

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches make the independent tests pass, so the decision rests on root-cause fit, risk, and scope. Patch A fixes the exact cause the issue names: it adds reasoning_effort to MinimaxChatConfig.get_supported_openai_params unconditionally, so the parameter survives drop_params and is forwarded for the provider to judge, matching how the OpenAI-compatible base behaves. Its map_openai_params override is small and defensible (unwraps an {'effort': ...} object to the bare level, skips the 'default' sentinel, and uses the existing warn_dropped_reasoning helper when nothing usable remains), and its tests drive a real litellm.completion through an httpx MockTransport and assert the body carries each of low/medium/high/max. Patch B gates the whitelist on litellm.supports_reasoning, which makes the fix depend on cost-map data: it adds a new MiniMax-M3.1-Flash entry with pricing figures the issue gives no basis for and a reasoning_effort_levels list that includes 'xhigh', contradicting the issue's stated low|medium|high|max set. It then adds a blanket '^minimax/' generalization rule marking every unmapped MiniMax id as reasoning-capable, which is a provider-wide behavior change well beyond the ask. Because litellm normally loads the cost map remotely, B's fix only reaches production once the hosted JSON updates, and in deployments pinned to an older map it would still drop the parameter; A has no such dependency. B's extra tests are thorough but mostly exercise the new cost-map rule and the fabricated entry rather than the reported bug. A resolves the issue at its root with less risk and tighter scope, so A is the better fix.

The issue

View on GitHub

What happened

reasoning_effort sent at the top level of a Chat Completions request to a MiniMax deployment is silently dropped: it never reaches the upstream and no warning is logged.

  • litellm: 1.106.6 (proxy, image ghcr.io/berriai/litellm:latest)
  • deployment: model_name: minimax-flash → litellm_params.model: minimax/MiniMax-M3.1-Flash

Repro

curl -s $LITELLM/v1/chat/completions -H 'Content-Type: application/json' \
  -d '{"model":"minimax-flash","messages":[{"role":"user","content":"..."}],"max_tokens":1500,"reasoning_effort":"low"}'
curl -s $LITELLM/v1/chat/completions -H 'Content-Type: application/json' \
  -d '{"model":"minimax-flash","messages":[{"role":"user","content":"..."}],"max_tokens":1500,"reasoning_effort":"high"}'

Observed

usage.completion_tokens_details.reasoning_tokens is the same for low and high — the parameter is stripped before the upstream call.

Proof the drop is on the litellm side, not MiniMax:

Requestreasoning_tokens (max_tokens 1500)
extra_body: {"reasoning_effort": "low"}410
extra_body: {"reasoning_effort": "high"}1499
top-level reasoning_effort: "low" / "high"identical (dropped)
same deployment as openai/MiniMax-M3.1-Flash + top-level reasoning_effortlow 410 / high 1499 (works)

Cause

litellm/llms/minimax/chat/transformation.py::get_supported_openai_params only appends reasoning_split (and thinking when supports_reasoning), so reasoning_effort is not in the accepted-params set for MiniMax deployment names and gets removed by the drop-params path.

MiniMax-M3.1-Flash does accept the effort levels directly — verified against the upstream API, low|medium|high|max all work when the parameter is forwarded.

Related

  • #48933 (merged 2026-10-30) added "requested reasoning level was dropped" WARNINGs to the remaining drop sites for anthropic, bedrock, azure_ai, deepseek, fal — minimax is still silent, so callers get no signal at all.
  • #47515 attempts to preserve Flash effort levels, but it is currently mergeable=false (dirty) and CLA-unsigned since 2026-10-20.

Ask

Whitelist reasoning_effort for the minimax provider so it is forwarded (Flash supports low|medium|high|max), or — if that is intentional — emit the same drop WARNING added in #48933 so the silent stripping stops being invisible.
