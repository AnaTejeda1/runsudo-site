Summary

What was wrong

When a site calls js.Build, Hugo generates assets/jsconfig.json from resources/jsconfig/jsconfig.go. In Builder.Build, each source root's path is computed with filepath.Rel(dir, filepath.Join(root, "*")). When a source root is the same directory as the build dir, filepath.Rel returns just "*" — a non-relative path. The result is "paths": {"*": ["*"]}, which VS Code flags:

Non-relative paths are not allowed when 'baseUrl' is not set. Did you forget a leading './'?

Adding a baseUrl was not an option: the existing TestJsConfigBuilder asserts the JSON must not contain baseUrl (issue 14991). So the correct fix is to make the paths relative with a leading ./.

What I changed (resources/jsconfig/jsconfig.go, production code only)

  • Added the strings import.
  • In Builder.Build, any filepath.Rel result that is not already relative (i.e. does not start with ..) is prefixed with ./ (using the OS separator). So "*" → "./*", "sub/*" → "./sub/*", while already-relative "../../c/assets/*" paths are left unchanged. No baseUrl is introduced.

I used the .. prefix as the "already relative" check (rather than a bare .) because filepath.Rel only ever emits relative results starting with ..; this also correctly handles hidden-directory roots like .config/*, which a bare-. check would have wrongly left non-relative (a point raised by the review).

Regression test (resources/jsconfig/jsconfig_test.go, tests only)

  • Added TestJsConfigBuilderRelativePaths, which builds with a same-dir root and a nested root and asserts every emitted path begins with . and that the same-dir case is ./* and the nested case ./sub/*. The existing TestJsConfigBuilder was left untouched.

Test evidence (via ./bt-test, output in test-report.json)

  • Before the fix: TestJsConfigBuilderRelativePaths failed (got "*", want leading "."), confirming the reported behavior.
  • After the fix: both TestJsConfigBuilder and TestJsConfigBuilderRelativePaths pass.

All changes are left uncommitted in the working tree.
