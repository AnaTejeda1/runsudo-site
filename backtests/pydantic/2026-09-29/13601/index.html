In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches correctly identify the root cause: when a serializer is gated off by when_used, the false/fallback branch must preserve the caller's include/exclude instead of clearing it to empty. Both would resolve the reported issue and both add tests that fail before and pass after. The decision comes down to scope and craft. Patch A is a clean, minimal change: it adds one small accessor (include_exclude()) and threads the correct IncludeExclude into the existing single scoped_include_exclude call per method (empty for the ran-serializer case, the current state for the fallback case). Patch B's tests are marginally more thorough (parametrizing json-unless-none), but that does not outweigh A's tighter, more idiomatic implementation with far less duplication. Initial Checks

Description

When a model declares @model_serializer(mode="wrap") with when_used="json" (or "json-unless-none"), the runtime exclude argument passed to model_dump() is silently ignored in python mode. The same call in JSON mode behaves correctly.

Expected: model_dump(exclude={"b"}) omits b regardless of when_used, since the gate concerns which serializer runs and not which fields the caller asked to drop.

Actual: b is present in python mode.

Example Code

from pydantic import BaseModel, SerializerFunctionWrapHandler, model_serializer


class Gated(BaseModel):
    a: int
    b: int

    @model_serializer(mode="wrap", when_used="json")
    def _serialize(self, handler: SerializerFunctionWrapHandler) -> object:
        return handler(self)


class Always(BaseModel):
    a: int
    b: int

    @model_serializer(mode="wrap")
    def _serialize(self, handler: SerializerFunctionWrapHandler) -> object:
        return handler(self)


  # Gated to JSON: python mode ignores exclude.
  print(Gated(a=1, b=2).model_dump(exclude={"b"}))               # {'a': 1, 'b': 2}  <-- expected {'a': 1}
  print(Gated(a=1, b=2).model_dump(mode="json", exclude={"b"}))  # {'a': 1}          <-- correct

  # Identical model without the gate: python mode honours exclude.
  print(Always(a=1, b=2).model_dump(exclude={"b"}))              # {'a': 1}

  Output:

  gated  python: {'a': 1, 'b': 2}
  gated  json  : {'a': 1}
  always python: {'a': 1}

What the agent reported

Summary

What was wrong

A model with @model_serializer(mode="wrap"|"plain", when_used="json"|"json-unless-none") silently ignored the runtime exclude=/include= passed to model_dump() in python mode, while mode="json" worked correctly.

Root cause (Rust core). The bug is entirely in pydantic_core (the pydantic Python layer just forwards exclude/include/mode to the compiled serializer with no post-processing — confirmed by investigation). In pydantic-core/src/serializers/type_serializers/function.rs, the function_type_serializer! macro (shared by FunctionPlainSerializer and FunctionWrapSerializer) did:

let (ret_serializer, v) = match self.call(value, state) {
    Ok((true, v))  => (&*self.return_serializer, v),      // serializer ran
    Ok((false, v)) => (self.get_fallback_serializer(), v), // when_used gated it OFF
    Err(...) => { ...; return infer_*(...); }
};
let state = &mut state.scoped_include_exclude(IncludeExclude::empty()); // ← cleared unconditionally
ret_serializer.to_python(v.bind(py), state)

Clearing include/exclude is only correct in the true branch (the wrap handler already applied filtering, or a plain function fully owns its output). In the false branch — taken when when_used gates the serializer off, e.g. when_used="json" in python mode — the fallback is the model's own serializer, which must still honor the caller's exclude/include. Clearing it there dropped the filter.

What I changed

pydantic-core/src/serializers/type_serializers/function.rs — in all three methods (to_python, json_key, serde_serialize), the clearing is now conditional (filtering_done): applied only when the serializer function actually ran (Ok((true, …))), and not in the fallback branch (Ok((false, …))). Err paths and the JSON-mode/when_used="always" paths are unchanged. A reviewer confirmed the change is syntactically valid, borrow-check-plausible, correctly scoped, and introduces no unrelated behavior change.

tests/test_serialize.py — added test_model_serializer_wrap_when_used_json_respects_exclude and test_model_serializer_plain_when_used_json_respects_exclude, each parametrized over ["json", "json-unless-none"], asserting python-mode exclude/include parity with json mode (the exact reported scenario).

Test evidence — and an important honesty caveat

I could not compile the fix or see the test pass in this environment, for an infrastructural reason (not a defect in the fix):

  • The bug is in the Rust core, but the core cannot be rebuilt here. The cached dependency rlibs were built with rustc 1.98.1 (2026‑09‑01); only rustc 1.90.0 is installed, so rustc/cargo reject them with E0514: incompatible version of rustc. The dependency sources are absent and the network is blocked (crates.io returns 403), so cargo cannot resolve/rebuild them either. bt-test loads the prebuilt (stale, buggy) .so, so it cannot reflect a Rust source change.
  • What I did verify with bt-test: the new regression test fails against the current prebuilt core, reproducing the bug precisely — model_dump(exclude={'b'}) returns {'a': 1, 'b': 2} instead of {'a': 1} (all 4 parametrizations fail). This confirms the test asserts the correct outcome and reproduces the report at the pydantic API level. It will pass once the core is rebuilt with this fix by a normal toolchain.

Per the guidance about not shipping a test "you have not seen pass," I want to be explicit rather than silently drop it: the test is a correct, non-vacuous regression test that fails today only because the fixed core cannot be built in this sandbox. I kept it in the diff so the patch is complete for a maintainer who can build, and I'm flagging clearly that its post-fix pass is unverified in this environment.
