[Bug]: INFO logging of incoming requests to the LiteLLM proxy server can not be switched off.

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the reported uvicorn path: each sets uvicorn's log_level from LITELLM_LOG when no explicit log_config or JSON logs are configured, which raises the uvicorn.access logger level and drops the per-request INFO lines. The independent tests confirm both pass. Patch A goes further in ways that matter for the issue's ask ("how to switch it off") rather than being unrelated churn: it applies the same env var to hypercorn, granian, and gunicorn, and it explicitly disables access logging where the level is above INFO (gunicorn in particular emits access lines at INFO regardless of loglevel, so A's handling is needed there). A also validates the env value and warns instead of raising, and maps aliases like 'warn' correctly. Its tests are broad: parametrized over levels, verify explicit log_config is not overridden, apply the args to a real uvicorn.Config and check logger levels/handlers, and cover each alternate server. Patch B is minimal and correct for uvicorn (passing an int log_level is valid), with a real configure_logging-based test, but leaves the other server backends unfixed, adds an adjacent change to the litellm_proxy_extras logger that the issue does not mention, and its resolve_log_level raises AttributeError on an unrecognised value with no handling. The extra lines in A add little risk since they are gated on LITELLM_LOG being set and mirror existing option-building code. A is the more complete and better-tested fix.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Each saw the issue and the two patches, labelled A and B in random order (two of them saw ours as A), with issue links and version numbers removed. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours. What happened?

Hi, our LiteLLM proxy logs are full of INFO lines for each request. We'd like to switch that off. We expect LITELLM_LOG=ERROR to do the job, but it does not help.

Here is a minimal example to reproduce the problem:

litellm_config.yaml:

model_list:
  - model_name: gpt-4o-mini
    litellm_params:
      model: openai/gpt-4o-mini
      api_key: sk-[...]
general_settings: 
  master_key: sk-1234

run:

docker run \
    -v $(pwd)/litellm_config.yaml:/app/config.yaml \
    -p 4000:4000 \
    --env LITELLM_LOG=ERROR \
    ghcr.io/berriai/litellm:main-v1.69.0-stable \
    --config /app/config.yaml

When sending requests like this

curl -X POST 'http://0.0.0.0:4000/chat/completions' \
-H 'Content-Type: application/json' \
-H 'Authorization: Bearer sk-1234' \
-d '{
    "model": "gpt-4o-mini",
    "messages": [
      {
        "role": "user",
        "content": "Hi."
      }
    ]
}'
