Experimental pipeline: every constraint chained after ge/lt/le is dropped from the JSON schema

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the root cause (the fallback `_check_func` being applied unconditionally after the native core-schema field is set) and both include the same key regression tests proving the JSON schema now carries every chained bound (ge.le, le.ge, constrain(Interval), ge.le.multiple_of). The decision turns on scope and correctness risk. Patch B is the minimal, targeted fix: it introduces a `native_constraint_applied` flag and only falls back to the function check when the native field was NOT set — exactly the shape the issue author endorses (from #13473) and applies it symmetrically across all five branches (Gt/Ge/Lt/Le/MultipleOf), which the issue explicitly calls for. It preserves every existing behavior, including routing genuine type mismatches (e.g. `.ge(0.0)` on an int schema, a `Decimal` bound on a float schema) to the function check as before. Patch A goes further than the issue requires: it deletes the per-type `isinstance` guards entirely and assigns `s['gt'] = gt` directly, relying on an unstated assumption that 'pydantic-core does the casting.' That is a behavioral change beyond the reported schema bug — a mismatched-type bound (e.g. a float `0.0` written into an int core schema) is now emitted as a native constraint, which can leak into validation and produce a float-valued `minimum` in the published JSON schema rather than the previous, deliberate function-check fallback. Patch A does add more validation test cases covering those mismatch/transform scenarios, but that thoroughness is partly documenting the very scope expansion that makes it riskier, and the test evidence does not confirm they pass. Weighing correctness (B avoids the pydantic-core casting assumption and preserves the guard semantics), scope (B is as small as a correct fix allows; A is a refactor that removes guards), and consistency with the in-flight convention, Patch B is the better fix. Patch A's extra schema/validation tests are a genuine plus but do not outweigh its broader, riskier change.

Initial Checks

Description

In the experimental pipeline API, chaining constraints silently drops every bound after the first from the generated JSON schema. Validation stays correct - only the published schema is wrong, which makes it easy to miss.

All bounds below are non-zero, so this is not #13450 (falsy zero bounds in Interval). Observed identically on released 2.13.4 and on main (2.14.0a1).

expressionJSON schemavalidation
validate_as(int).ge(1).le(100){"minimum": 1, "type": "integer"}0 reject, 50 accept, 200 reject
validate_as(int).le(100).ge(1){"maximum": 100, "type": "integer"}0 reject, 50 accept, 200 reject
validate_as(int).constrain(Interval(ge=1, le=100)){"minimum": 1, "type": "integer"}0 reject, 50 accept, 200 reject
validate_as(int).ge(1).le(100).multiple_of(5){"minimum": 1, "type": "integer"}correct
validate_as(int).gt(1).lt(100) (control){"exclusiveMinimum": 1, "exclusiveMaximum": 100, ...}correct
Annotated[int, Ge(1), Le(100)] (control){"minimum": 1, "maximum": 100, ...}correct

So .ge(1).le(100).multiple_of(5) publishes a schema advertising any integer >= 1, while the validator rejects 200 and 52. For FastAPI that means the OpenAPI component and every generated client disagree with the server.

Cause

In _apply_constraint(), the Ge, Lt and Le branches apply their fallback function validator unconditionally - including when the native core-schema field was just set:

elif isinstance(constraint, annotated_types.Ge):
    ge = constraint.ge
    if s and s['type'] in {'int', 'float', 'decimal'}:
        s = s.copy()
        if s['type'] == 'int' and isinstance(ge, int):
            s['ge'] = ge          # native constraint applied...
        ...

    def check_ge(v: Any) -> bool:
        return v >= ge

    s = _check_func(check_ge, f'>= {ge}', s)   # ...and then wrapped anyway

_check_func wraps the schema in function-after. The next constraint in the chain sees s['type'] == 'function-after', which is not in {'int', 'float', 'decimal'}, so it cannot set its own native field and survives only inside an opaque callable that JSON-schema generation cannot read. Core schema for .ge(1).le(100):

{'type': 'function-after',
 'function': ...,                       # <- le(100) lives in here, invisible to the schema
 'schema': {'type': 'function-after',
            'function': ...,            # <- redundant ge check
            'schema': {'type': 'int', 'ge': 1}}}

Gt is the control that works, and only by accident: its fallback sits in an else:, so nothing is wrapped when the native constraint applies.

Relationship to the open PRs in this function

Two in-flight PRs each fix one branch of this, for unrelated reasons, and between them they leave Ge, Lt and Le untouched:

  • #13473 adds a native_constraint_applied flag to MultipleOf to avoid a float parity problem. Same shape as the fix needed here.
  • #13446 restructures Gt so the fallback lands inside the numeric branch.

Worth flagging on the second one: #13446's description argues that Gt is uniquely broken and holds up Ge/Lt/Le/MultipleOf as the correct model, because they "always apply" the check and so enforce the bound on a type mismatch. That is true of validation, but always applying it is exactly what destroys the schema. Gt is uniquely broken for validation; the other four are broken for schema. Whichever way this is fixed, it probably wants to be one symmetric change across all five branches rather than three separate patches.

Summary

What was wrong. In pydantic/experimental/pipeline.py, _apply_constraint() applied a fallback _check_func after-validator unconditionally in the Ge, Lt, Le, and MultipleOf branches — even when the native core-schema field (e.g. s['ge'] = ge) had just been set. That wrapped the schema in a function-after type, so the next chained constraint saw s['type'] == 'function-after' (not in {'int','float','decimal'}) and could not attach its own native bound. The constraint survived only inside an opaque callable invisible to JSON-schema generation. Result: .ge(1).le(100) published {'minimum': 1} with no maximum, while validation stayed correct. Gt avoided the schema bug only by nesting its fallback in an else, but that idiom is itself subtly wrong (it silently drops the check when the schema type matches but the bound's value type doesn't).

What I changed. Applied the native_constraint_applied flag pattern (the shape from #13473) symmetrically across all five numeric branches — Gt, Ge, Lt, Le, MultipleOf. The flag is set True only where a native field is actually assigned, and the _check_func fallback runs only when the flag is False. This preserves the raw int/float/decimal schema type so subsequent chained constraints attach their bounds natively, and it fixes Gt's latent validation gap on type-mismatched bounds. Len, Timezone, and all other branches are untouched. No test files were modified by the implementer.
