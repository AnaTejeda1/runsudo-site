Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches stop the AttributeError at its source (the handler now works on a dict-or-empty view of the body) and both make the surrogate-repair fallback in read_request_body stop handing a raw list/scalar to callers, which is the path that still 500s on current main (the independent tests show only the NaN/Infinity/1e400 cases fail on base, i.e. the json.loads repair branch). All independent tests pass on both. The difference is scope and risk. Patch A is a tight fix: an isinstance guard in the handler, a small _json_object_body helper applied to both parse paths so a non-object body consistently yields {}, and tests at three layers (handler with every body shape from the issue including BudgetExceededError, end-to-end user_api_key_auth with raw bytes including the repair-fallback inputs, and read_request_body itself). Patch B goes much further: it turns pydantic ValidationError into a 400 inside read_request_body and then bolts on a route-sniffing carve-out (importing pass-through and lens modules into http_parsing_utils, inspecting request.scope['route'], checking APIRoute.body_field.is_required() and whether the stripped body equals b'null'). That heuristic is fragile and coupled: it had to add path_params to an unrelated vertex pass-through test to keep it working, it rewrites the protobuf and lens buffering tests, and any non-pass-through endpoint that legitimately accepts a list body would now get a 400 from the auth dependency with no carve-out. It also changes _parse_binary_body behaviour. None of that is required by the issue, which explicitly accepts 'the normal 401', and it adds surface for regressions that A does not. B's handler-side change (as_str_mapping, widening the parameter type to object) is fine, and its parametrized classification test is good, but the parsing-layer redesign counts against it. A resolves the issue at the root with less risk and adequate, non-tautological tests.

Bug Report

Describe the bug

Any request whose JSON body is valid JSON but not an object ([], null, "s", 1, true) causes an
unhandled AttributeError and a 500 on unauthenticated endpoints. The auth failure handler assumes the
parsed body is a dict and calls .get() on it.

To Reproduce

No API key needed:

curl -i -X POST http://localhost:4000/v1/chat/completions \
  -H 'Content-Type: application/json' -d '[]'

Result: 500 Internal Server Error. {} correctly gives 401, so the difference is purely the body type.

All of these 500: [], [1], [1,2], null, "s", 1, true, [[]], [[1]].

Traceback

File "litellm/proxy/auth/user_api_key_auth.py", line 2280, in user_api_key_auth_builder
    return await UserAPIKeyAuthExceptionHandler.handle_authentication_error(
File "litellm/proxy/auth/auth_exception_handler.py", line 222, in handle_authentication_error
    model=request_data.get("model"),
AttributeError: 'list' object has no attribute 'get'

Root cause

litellm/proxy/auth/auth_exception_handler.py:

seed_request_identity(
    user_api_key_dict,
    model=request_data.get("model"),
)

and again a few lines later:

budget_model: Final = request_data.get("model")

request_data is whatever json.loads produced, so it is only a dict when the client sent an object. There is
no isinstance(request_data, dict) guard.

Expected behavior

A non-object body on an unauthenticated request should give the normal 401 (or a 4xx validation error), not a
500 with a traceback.

Your Environment

  • LiteLLM 1.106.3 (litellm/litellm:latest); the same unguarded lines are present on current main
  • Linux, aarch64, official container image
  • Default config, no database

Impact

Unauthenticated 500 + traceback per request, trivially triggerable by any client. Low severity (DoS-ish /
log noise), but it is on the auth-failure path, so it fires for every malformed client that sends an array.
