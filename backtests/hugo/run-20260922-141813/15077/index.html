The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches correctly resolve the root cause: they widen Render's signature to `args ...any`, select the page or supplied data as the template context, and execute with it. The single-argument form stays backward compatible in both. The decisive differences are argument order, tests, and craft. Patch A implements `[DATA] NAME` (context first, layout last), which literally echoes the issue's off-hand proposal but conflicts with Hugo's universal templating convention where the template/name comes first and context second (partial NAME CONTEXT). Patch A's rule that 'the last argument is always the layout name' makes the meaning of position 0 shift depending on argument count, which is more surprising and error-prone. Patch B implements `VIEW [CONTEXT]`, keeping the first argument's meaning stable and matching `partial`, the closest analog — the least-surprising extension for a Hugo user. On craft, Patch B uses `cast.ToStringE` for the view name, which is the idiomatic Hugo pattern (cast is used throughout for arg coercion), whereas Patch A uses a strict type assertion. On tests, both add a positive test that fails before and passes after, but Patch B additionally covers two error edges (too many arguments, non-castable view) with regex-matched messages, giving stronger coverage of the boundaries the new signature introduces. Patch A's only clear advantages are faithfulness to the issue's suggested `[DATA] NAME` wording and its inclusion of documentation updates (a genuine plus for a user-facing feature), but the issue text is an open design discussion, not a spec, and the doc benefit does not outweigh the reversed-order usability wart plus weaker error-path tests. Net: Patch B is the better fix on convention-consistency, idiomatic conversion, and test thoroughness.

PAGE.Render NAME

This has been discussed before.

  • The contract has always been that the templates that .Renders gets the data context as e.g. page.html, a page.Page.
  • We can only pass 1 argument to Go's template renderer, which I guess is the blocking reason for not having done this sooner.

So, if we want to do:

PAGE.Render [DATA] NAME

I'm guessing we have 2 top-level options:

  • We say that if DATA is set, we use that as the context passed to the templates,. else PAGE.
  • We somehow (e.g. by embeding it in a { DataAdditionalContext, Page } struct or putting it into the current context.Context) wrap the Page so you can do both .RelPermalink and .DataAdditionalContext (naming of the latter is just picked out of a hat without thinking too hard.

What the agent reported

The work is complete. Here is my final report.

What was wrong

Hugo's PAGE.Render NAME template method could only render a view with the Page itself as the template context — there was no way to pass additional data (issue #15076). The blocker was that Go's template renderer takes a single data argument, and the method signature (Render(ctx, layout ...string)) treated every argument as a layout name and always passed the *pageState as context (hugolib/page__per_output.go:107, doc docs/.../Render.md:28 explicitly said "You cannot pass additional context.").

What I changed

Adopted the maintainer's first-listed option (simplest, consistent with partial, no field-shadowing risk): the last argument is the layout NAME; an optional leading argument is DATA that becomes the template context. With no DATA, behavior is byte-identical to before.

  • hugolib/page__per_output.go — Rewrote Render to Render(ctx, args ...any): last arg → layout name (string), optional first arg → data context (defaults to the *pageState). Added errors for 0 args, >2 args, and a non-string name.
  • resources/page/page.go — Updated the PageRenderProvider.Render interface signature + doc comment to args ...any.
  • resources/page/page_nop.go, resources/page/page_lazy_contentprovider.go — Updated the other two implementers (the lazy one forwards args...).
  • resources/page/testhelpers_test.go — Updated the testPage stub signature (kept body).
  • hugolib/page_test.go — Added TestRenderWithAdditionalData (issue #15076).
  • docs/content/en/methods/page/Render.md — Updated signature to PAGE.Render [DATA] NAME, the comparison-table row, the front-matter description, and added a "Pass additional data" example section.

Test evidence

  • Fail-before verified: with only the production/helper changes reverted (scoped git stash), TestRenderWithAdditionalData FAILED — template execution error at .Render (dict …) "withdata" (old ...string signature rejects a dict). Changes then restored.
  • Pass-after: ./bt-test ./hugolib/ -run TestRender → 43/43 PASS, including the new test and all 9 existing TestRenderView* tests plus RenderString/render-hook tests.
  • Blast radius: ./bt-test ./resources/page/ (touched by the interface/nop/lazy/testhelpers changes) → all PASS, 0 fails.
  • Reviewer confirmed correctness, backward compatibility, consistent implementers, both-path test coverage, and no unrelated/scratch changes.

Requirements checklist

  1. PAGE.Render [DATA] NAME — DATA becomes the context when set, else PAGE (maintainer's option 1) — ✅ Implemented; asserted by the data path (hello-2) and no-data path (.Title → p1) in TestRenderWithAdditionalData.
  2. Maintainer's option 2 (wrap Page in a {Data, Page} struct / context.Context) — ⏭️ Skipped as the chosen alternative.
