Issue with chained resource transformations

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Root cause: once the chain has run, `resourceAdapterInner.target` is replaced by the transformed resource. `TransformWithContext` then copies that transformed target but keeps the full transformation list, so the earlier steps (e.g. css.Build) run a second time on output that is already built.

Patch A stores the original untransformed target in a new `sourceTarget` field and always starts new chains from it. This fixes the basic Data-then-fingerprint case, and replaying the full chain from source also keeps cache keys consistent. However, `cloneTo` sets `sourceTarget` to a clone of `r.target`. If the transformation has already been applied, that is the transformed resource, while the full chain is still attached. So `resources.Copy` on an already-triggered resource, followed by another transformation, would re-apply the chain to transformed content: the same class of bug. Patch A's only test is the css.Build/Data.Artifacts/fingerprint scenario.

Patch B tracks an `applied` flag and an `appliedCount`. The `transform` loop skips transformations already applied to the target. `sourceKey` keeps the cache key equal to that of a chain built in one go, and the full chain is kept so `hasTransformationPermalinkHash` stays correct. It also avoids sharing the slice backing array with the previous chain, which is a latent aliasing hazard when appending. Finally, `cloneTo` propagates `applied`, explicitly covering the copy case.

B's tests are broader. They trigger the transformation through Data, Content and RelPermalink, check that the chaining result is identical to the untriggered case, test copy before and after the trigger, and include the css.Build artifacts scenario with output file assertions.

B is more complex, but its added logic is well commented and addresses edge cases A misses. On correctness and test coverage, B is the stronger fix.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The issue

View on GitHub

See the fix in #15188.

This has been an issue since we added this feature, but we haven't noticed it (or gotten reports about it) because the common setup is to set up the entire chain before starting to use it:

{{- with . | css.Build $opts }}
	{{- if hugo.IsDevelopment }}
		<link rel="stylesheet" href="{{ .RelPermalink }}">
	{{- else }}
		{{- with . | fingerprint }}
			<link rel="stylesheet" href="{{ .RelPermalink }}" integrity="{{ .Data.Integrity }}">
		{{- end }}
	{{- end }}
{{- end }}

In the above:

  • .RelPermalink triggers the transformation of the entire chain in a streaming way.

With the recently added .Data.Artifacts in css.Build I discovered this issue by accident when doing something ala:

{{- with . | css.Build $opts }}
	{{ range .Data.Artifacts }}
		{{ if eq .MediaType.MainType "font" }}
			<link rel="preload" href="{{ .RelPermalink }}" as="font" type="{{ .MediaType.Type }}">
		{{ end }}
	{{ end }}
	{{- if hugo.IsDevelopment }}
		<link rel="stylesheet" href="{{ .RelPermalink }}">
	{{- else }}
		{{- with . | fingerprint }}
			<link rel="stylesheet" href="{{ .RelPermalink }}" integrity="{{ .Data.Integrity }}">
		{{- end }}
	{{- end }}
{{- end }}

In the above:

  • .Data triggers the css.Build transformation.
  • Then fingerprint starts a new transformation with correct .Content, but wrongly including the full chain, including css.Build

The above could be rewritten to the below and it would work as expected:

{{- with . | css.Build $opts }}
	{{- if hugo.IsDevelopment }}
		<link rel="stylesheet" href="{{ .RelPermalink }}">
	{{- else }}
		{{- with . | fingerprint }}
			{{ range .Data.Artifacts }}
				{{ if eq .MediaType.MainType "font" }}
					<link rel="preload" href="{{ .RelPermalink }}" as="font" type="{{ .MediaType.Type }}">
				{{ end }}
			{{ end }}
			<link rel="stylesheet" href="{{ .RelPermalink }}" integrity="{{ .Data.Integrity }}">
		{{- end }}
	{{- end }}
{{- end }}
{{- end }}
