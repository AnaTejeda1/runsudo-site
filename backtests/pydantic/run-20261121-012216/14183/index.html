pydantic-core-2.50.2: test needs pydantic

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches make the same core fix: `tests/test_tzinfo.py` drops `from pydantic import TypeAdapter` and validates the datetime via `SchemaValidator(core_schema.datetime_schema())`. The independent tests confirm both resolve the collection error and let the whole suite pass without pydantic. The difference is in the guard added and in scope.

Patch B adds a regression test (`test_tests_do_not_import_pydantic`) that AST-scans every test file for unguarded `pydantic` imports, correctly tolerating the `try/except ImportError` guard already used in conftest. It fails on base (test_tzinfo offends) and passes after, and it runs as part of pytest, so packagers and CI would catch any future reintroduction. The diff is two files and clearly readable.

Patch A instead adds a `tests/ruff.toml` banning `pydantic` via TID251, which is a reasonable lint-level guard but only fires when ruff runs, not during the test run the issue is about. More importantly, the fix is buried in ~46 files of unrelated ruff-driven churn: `__all__` reordering in the public `__init__.py` and `.pyi` stubs, removal of `__repr__`/`__str__` from the `Url`/`MultiHostUrl` stubs, a TypeVar rename, `__slots__` reordering across dozens of tests, `dict(...)`→literal rewrites, and a `ruff_ignore` change to the docstring-example test. Several of these alter test semantics rather than just style: `assert ''.join(['a']) in fields_set` becomes `assert 'a' in fields_set`, defeating the explicit "Non-interned strings" check; `assert not tz != ALWAYS_EQ` becomes a duplicate `==` assertion, losing `__ne__` coverage; `assert fields_set <= fields_set` / `assert not fields_set < fields_set` are deleted outright. Under the scope criterion this churn adds risk and obscures the fix, and some of it weakens existing coverage.

On correctness both are equal; on tests B's executable guard is stronger for the stated scenario; on scope and craft B is clearly better. B wins.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Each saw the issue and the two patches, labelled A and B in random order (two of them saw ours as A), with issue links and version numbers removed. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours.
