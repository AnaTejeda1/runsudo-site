In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches make the identical core change: they wrap the `yield` in `try`/`finally` in both `_FieldNameStack.push()` and `_ModelTypeStack.push()`. That fixes the root cause the issue describes, so correctness on the reported bug is equal. The difference lies in the tests. Patch A's test in `tests/test_internal.py` builds a `GenerateSchema` and checks both stacks directly. It asserts `get()` is None after a push whose body raised. It then does a later unrelated push/pop and checks the stack returns to None. This is the issue's exact scenario, it would clearly fail before the fix (`get()` would return the stale entry), and it doesn't depend on how schema generation routes internally. Patch B's tests are end-to-end: a custom `__get_pydantic_core_schema__` swallows a schema-generation error from a TypedDict, then the test checks `Self` resolution and `handler.field_name`. They are realistic and show real-world impact, and they likely fail before the fix. But they are indirect and fragile: they only exercise the bug if TypedDict schema generation happens to push onto these stacks in that order. A future refactor could make them pass vacuously. Patch A also applies the same `try`/`finally` fix to `generic_recursion_self_type` in `_generics.py`, with a targeted regression test. That is extra hardening, so it is neutral under the scope criterion. It is the same pattern, small and low-risk, so it doesn't count against A. Overall, the fixes are equivalent and A's tests are the more direct and robust regression guard, so A wins narrowly.

The issue

View on GitHub

Description

_FieldNameStack.push() and _ModelTypeStack.push() in pydantic/_internal/_generate_schema.py (around lines 2910/2929) push onto their internal list, yield, then pop:

@contextmanager
def push(self, field_name: str) -> Iterator[None]:
    self._stack.append(field_name)
    yield
    self._stack.pop()

If the code inside the with self.field_name_stack.push(...): block raises (schema generation is deeply recursive and can legitimately raise, e.g. PydanticUserError for a circular reference a few lines above this class in the same file), the yield's continuation - the .pop() - never runs. The stale entry stays on the stack forever, and corrupts every later, otherwise-unrelated push()/get() on that same GenerateSchema instance, not just the one that failed.

Reproduction

Isolated (no pydantic-core needed to demonstrate - this is pure Python control flow, verified against the actual class body copied verbatim):

from contextlib import contextmanager

class _FieldNameStack:
    __slots__ = ('_stack',)
    def __init__(self):
        self._stack = []
    @contextmanager
    def push(self, field_name):
        self._stack.append(field_name)
        yield
        self._stack.pop()
    def get(self):
        return self._stack[-1] if self._stack else None

stack = _FieldNameStack()

try:
    with stack.push('some_field'):
        raise ValueError('boom')  # simulates any exception during schema generation
except ValueError:
    pass

print(stack.get())  # 'some_field' - already wrong, nothing is being processed

# The real damage: this leaks into a completely unrelated, later, successful push.
with stack.push('other_field'):
    pass
print(stack.get())  # 'some_field' again - should be None, 'other_field' was popped
                     # correctly but the stale entry underneath it was never cleared

Output:

some_field
some_field

Both lines should print None.

Fix

Wrap the yield in try/finally so the pop runs unconditionally, the same guarantee a class-based context manager's __exit__ gets for free:

@contextmanager
def push(self, field_name: str) -> Iterator[None]:
    self._stack.append(field_name)
    try:
        yield
    finally:
        self._stack.pop()

Same fix applies identically to _ModelTypeStack.push() a few lines below - same shape, same bug.

I have a fix + regression test ready (asserts .get() returns None after a push whose body raised) and I'm happy to open a PR, per the note in the PR template about discussing non-trivial changes here first.
