JSON Schema ignores ser_json_temporal, so serialization schemas contradict model_dump_json() output

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches correctly resolve the timedelta precedence half of the issue: each checks membership in `config_dict` for `ser_json_temporal` before falling back to `ser_json_timedelta`, mirroring pydantic-core, and both add tests that fail-before/pass-after for that case. The decisive difference is the date/time/datetime path. Patch A checks the explicit condition `self._config.ser_json_temporal in ('seconds', 'milliseconds')`, so it returns the numeric schema only for the two numeric formats and falls through to the string/format schema for everything else — correct whether the unset default of `ser_json_temporal` is `None` or `'iso8601'`. Patch B routes those methods through `_common_temporal_schema(..., self._config.ser_json_temporal)` and treats *anything* that is `!= 'iso8601'` as `{'type': 'number'}`. That is only safe if the config default is exactly `'iso8601'`; if the unset value is `None` (a plausible sentinel, and the presence-based precedence semantics the issue describes strongly suggest a None sentinel — which is also why both patches probe `config_dict` for the timedelta case rather than trusting the attribute), Patch B would emit `{'type': 'number'}` for every date/datetime/time in the default no-config case, a serious regression of default behavior. Patch B's own added tests only exercise the explicitly-set cases and would not catch this; it relies on the existing suite. Patch B is cleaner in craft (a shared helper, a slightly more thorough parametrized precedence matrix), but robustness/correctness is weighted higher: there is no scenario where B is more correct than A, and at least one plausible scenario where A is correct and B is broken. Hence A is the safer, more defensively-correct fix.

Description

ser_json_temporal landed in v2.12 and controls how datetime, date, time and timedelta are serialized to JSON. GenerateJsonSchema was never told about it, so a mode='serialization' schema still says these fields are strings even when model_dump_json() writes numbers.

With ser_json_temporal='seconds' (same with 'milliseconds'), every temporal field is affected:

schema:  {'dt': {'type': 'string', 'format': 'date-time'}, 'td': {'type': 'string', 'format': 'duration'}}
dump:    {'dt': 1577836800.0, 'td': 86400.0}

Running that payload through a JSON Schema validator fails with 1577836800.0 is not of type 'string', so the schema pydantic publishes rejects the output pydantic itself just produced. date_schema, time_schema and datetime_schema read no config at all right now.

There is a second mismatch that goes the other way, on timedelta. timedelta_schema only looks at the older ser_json_timedelta setting. The docs for ser_json_temporal say it takes precedence over ser_json_timedelta, and pydantic-core implements exactly that: SerializationConfig::from_config and TimeDeltaSerializer::build both check whether ser_json_temporal is present in the config before falling back to ser_json_timedelta. The JSON schema layer does not, so setting ser_json_temporal='iso8601' together with ser_json_timedelta='float' gives you the reverse problem:

schema:  {'td': {'type': 'number'}}
dump:    {'td': 'P1D'}

For anyone generating an OpenAPI document from a model this is a silent wrong answer rather than a crash, which is probably why it has gone unnoticed since the setting was added.

I have a patch that mirrors the pydantic-core resolution in the four temporal schema methods, plus tests. Happy to open a PR if you want to assign this to me.

print(json.loads(Precedence(td=timedelta(days=1)).model_dump_json()))
#> {'td': 'P1D'}

What the agent reported

Done. Here is the summary.

What was wrong

GenerateJsonSchema never learned about the ser_json_temporal config setting (added in v2.12), so mode='serialization' JSON schemas contradicted model_dump_json() output:

  • date_schema, time_schema, datetime_schema read no config and always emitted {'type': 'string', 'format': ...}, even when ser_json_temporal='seconds'/'milliseconds' made model_dump_json() write floats.
  • timedelta_schema read only the older ser_json_timedelta, ignoring that ser_json_temporal takes precedence over it (as pydantic-core implements), producing the reverse mismatch.

What I changed

In pydantic/json_schema.py (4 methods):

  • date_schema, time_schema, datetime_schema: return {'type': 'number'} when self._config.ser_json_temporal in ('seconds', 'milliseconds'), else the original string/format value.
  • timedelta_schema: check self._config.config_dict.get('ser_json_temporal') for presence (the attribute always returns the 'iso8601' default, so it can't detect "set" — the raw config_dict can). When present, temporal decides (numeric modes → number, else duration string); when absent, it falls back to the prior ser_json_timedelta behavior unchanged. This mirrors pydantic-core's SerializationConfig::from_config/TimeDeltaSerializer::build.

I did not touch encode_default — I verified it already emits numeric defaults for these modes via to_jsonable_python, so schema type and default are now consistent.

Test evidence

Added test_model_ser_json_temporal (parametrized over seconds/milliseconds/iso8601 across datetime/date/time/timedelta) and test_ser_json_temporal_timedelta_precedence (both precedence directions plus the unset fallback, and asserting schema type matches actual json.loads(model_dump_json()) output — 'P1D'→string, 86400.0→number) in tests/test_json_schema.py.

  • Before the fix: 3 failed, 1 passed (the iso8601 case already correct).
  • After the fix, gate ./bt-test tests/test_json_schema.py -k "temporal or timedelta or bytes or datetime or date or time": 31 passed (new tests plus all adjacent existing temporal/timedelta/bytes/datetime tests — no regression).

Diff is minimal: pydantic/json_schema.py (+11) and tests/test_json_schema.py (+90), no scratch files, no existing tests modified, uncommitted.

Requirements disposition

  1. datetime/date/time schemas ignore ser_json_temporal — Fixed; covered by test_model_ser_json_temporal (seconds/milliseconds → number).
  2. timedelta_schema precedence: ser_json_temporal over ser_json_timedelta — Fixed; covered by test_ser_json_temporal_timedelta_precedence in both directions, plus fallback preserved when temporal unset.
  3. Schema consistent with actual model_dump_json() output — Verified in the test via json.loads(...model_dump_json()) assertions tied to schema type.

One note from review, left as-is intentionally: because these schema methods are shared across modes (like the pre-existing bytes_schema and timedelta_schema), the numeric type also now appears in mode='validation' schemas. This matches established convention in the file, keeps the change minimal, and is outside the reported (serialization-only) scenario; datetime validation also accepts numeric timestamps, so it is not invalid.
