panic: slice bounds out of range in contentNodeShifter.Delete when removing draft pages from a multilingual taxonomy

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

The core fix is essentially the same in both patches. Each changes the `Delete` and `DeleteFunc` shifter methods to build a fresh `remaining` slice instead of doing `v = append(v[:i], v[i+1:]...)` while ranging over `v`. Each changes the shifter interface to return the updated value. Each changes `NodeShiftTree.delete` and `DeleteFuncRaw` to write the updated value back with `tree.Insert` when something was deleted but the node is not empty.

That write-back is the real root cause. Before the fix, the tree kept the original slice header, whose backing array had been shuffled in place. A later delete in another dimension then ranged past the shrunk length, producing the `[5:4]`-style panic. Both patches fix this, and the `contentNodesMap`, `contentNodeForSite` and default cases are equivalent. Minor differences, such as A introducing `vv` in the default case and the `testShifter` returning `n` versus `nil` as the deleted value, have no effect on behaviour.

The tests are where the patches differ.

Patch A unit-tests the shifter's `Delete` in isolation with a hand-rolled `testContentNodeForSite` type. Its five-element case with two matching entries does reproduce the old in-place-append out-of-bounds panic. However, it never exercises the tree write-back path, so it does not cover the stale-value-in-tree mechanism that makes the bug appear only after several deletions on the same key. It also relies on an ad-hoc type that must satisfy the internal `contentNode` interfaces, which adds fragility.

Patch B tests through the real `doctree.NodeShiftTree` with the real `contentNodeShifter` and an existing `resourceSource` node type. It deletes dimension v1 and then v2 from the same key; with the old code, the second delete hits exactly the stale-backing-array panic described in the issue. It then checks the remaining vectors, a no-op re-delete, and full removal of the key. It also adds a `DeleteFuncRaw` test covering adjacent deletions and deletion of everything, which verifies the second changed code path.

Patch B's tests therefore better reproduce the actual failure scenario and cover both modified tree paths. Its explanatory comments about the shared backing array also add clarity. Scope is comparable.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The 0x35 in delete(..., {…, 0x35}) is 53, exactly the byte length of the key being removed (/blog/ plus a 47-character slug).

Only on the page-removal path

hugo -D (drafts included) builds fine. The panic appears only when a page is removed from the tree, which makes it invisible in local preview and fatal only in production.

A future publishDate panics identically. Setting [_build] render = "never" / list = "never" on the same pages avoids it entirely — consistent with those pages never being added to the tree, so nothing is deleted.

What I ruled out

Site: 8 languages, ~1,490 pages per language, ~11,455 content files, categories taxonomy.

  • Not a regression. 0.159.1 and 0.164.0 behave identically.
  • Not the number of drafts. 96 draft pages build fine; 16 panic.
  • Not slug length. The panicking key was 47 chars, but renaming an unrelated post to exactly 47 chars builds fine.
  • Not the slug. Renaming the offending page does not help.
  • Not byte layout. Deleting a front-matter line, or adding a blank one, still panics.

Swapping page content at a fixed path isolates it to front matter. Changing categories = ["Airport Operations"] on the offending page to any other value clears the panic — and so does moving a different page out of that same category while leaving the offending one alone. So the trigger is combinatorial: some particular set of pages being deleted from one taxonomy term corrupts the shifter, rather than any single page being malformed.

Reproducer

I have not managed to minimise it, and I want to be upfront about that. Synthetic multilingual sites (8 languages, 12 blog + 200 glossary pages sharing one taxonomy term, varying draft counts) do not reproduce, so something else in the real tree is required. The affected repository is private.

I am happy to run patches or instrumented builds against the real site and report back, which may be faster than guessing at a minimal case.
