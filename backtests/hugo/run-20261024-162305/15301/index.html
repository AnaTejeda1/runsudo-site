Improve/document security.http.urls override behavior

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

The issue asks to improve or better document the behavior where the dial-time private-address check is skipped when security.http.urls is customized. Patch A addresses exactly that: it factors the decision into HTTP.IsPrivateAddressAllowed, adds an explicit tri-state security.http.allowPrivateAddresses so users with a broad custom allowlist can keep the check (the reported security concern) and users with the default allowlist can opt out, and documents the whole mechanism in a dedicated 'Resolved address check' section with a warning and concrete examples. Its tests cover all four combinations at both the config level and the real transport, and would fail before the change. Patch B documents the existing behavior adequately (the independent docs test passes for both), but its code change is a different feature: it disables HTTP(S)_PROXY support by default and adds a proxyFromEnvironment knob. That is a breaking default-behavior change for users behind corporate proxies, is not what the issue asked for, and does nothing to let a user with a custom urls allowlist keep the private-address check. The proxy plumbing (context-carried proxy URL, canonicalAddr mirror, custom RoundTripper) adds nontrivial risk and surface area that obscures rather than improves the override behavior in question. Patch A is more correct for the stated issue, better tested for it, and tightly scoped.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Each saw the issue and the two patches, labelled A and B in random order (two of them saw ours as A), with issue links and version numbers removed. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours. The reasoning above is one judge's, shown verbatim.

The issue

View on GitHub

In d6e6f9e500eebdeae8e28de830fff2e3bfc7d534 (unreleased) we added a dial-time URL validation to catch URLs that's valid according to the whitelist but that resolves to a loopback, private or link-local IP addresses. That check is skipped it if the user has a custom security.http.urls setup, as it would not make sense to block local development servers.

See CheckAllowedHTTPAddress.

This has been reported by @Reload3d as a potential security issue, and while I think the current behaviour is the pragmatic correct approach, I'm creating this issue for visibility and to see if this can be improved further (e.g. better documentation).
