The issue

View on GitHub

Description

#8812 (released in 2.52.0) changed bare structured output on thinking Claude requests to native output where supported. This exposes existing Decimal fields to Bedrock's stricter schema validation, even when an application never requested NativeOutput.

With Pydantic 2.13.4 and Pydantic AI 2.61.0, Bedrock request preparation selects native output and preserves the Decimal string pattern:

^(?!^[-+.]*$)[+-]?0*\d*\.?\d*$

Bedrock does not support lookaround in structured-output patterns. A downstream Anthropic-shaped Bedrock token-count request failed with:

output_config.format.schema: Invalid regex in pattern field: Quantifier '?' without preceding element

The same prepared schema is used for native inference. Local request-preparation reproduction confirms the unsupported pattern survives; I have not replayed the inference request live.

Compatibility guidance checked

I checked #8812's description, changed thinking/provider docs, comments and the 2.52.0 release notes. They explain the output-mode change but do not identify the Decimal/Pydantic compatibility consequence. Both 2.52.0 and current main still declare pydantic>=2.12.

Pydantic #13672 removes default Decimal patterns in 2.14. The stable 2.14.0 release was on 8 October, after Pydantic AI 2.52.0 shipped on 30 September, so that upgrade was not available at the time of the output-mode change. It is an effective workaround now: with 2.14.1, the same request preparation selects native output but emits only number/string/null branches, with no Decimal pattern. Local Decimal validation remains intact.

Reproduction

A normal agent declaration that reaches the affected mode is:

from decimal import Decimal
from pydantic import BaseModel
from pydantic_ai import Agent

class Output(BaseModel):
    amount: Decimal | None

agent = Agent(
    'bedrock:eu.anthropic.claude-opus-4-7',
    output_type=Output,
    model_settings={'thinking': 'high'},
)

With Pydantic 2.13.4, inspect the prepared native output schema: the string branch contains the lookahead above. With 2.14.1, it does not. I verified this through BedrockConverseModel.prepare_request without network calls.

Expected

Document the affected Pydantic versions and upgrade workaround alongside the automatic native-output behavior, and decide how to preserve compatibility for older Pydantic versions still allowed by package metadata (for example, provider schema normalization or a clear compatibility guard).

Related: #5508 / #5519 addressed the corresponding OpenAI regex problem, and pydantic/pydantic#13630 tracks the underlying Decimal lookaround issue.
