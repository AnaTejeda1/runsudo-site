Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches make essentially the same core change in `pydantic/mypy.py`. They register `_RootModelMetaclass` with the metaclass hook so the dataclass_transform spec is reset. They also let the plugin generate `__init__` for `RootModel` itself instead of keeping its explicit typed `__init__`. This fixes the root cause: with the plugin and `init_typed` unset, `RootModel[float]('1.0')` is accepted, just as `BaseModel` fields are. The only code difference is `self._cls.info.fullname` (A) versus `self._cls.fullname` (B). Both resolve to the same value, so correctness is equal. A also updates the metaclass-callback docstring to mention the RootModel metaclass, a small craft point.

The real difference is test coverage. B tests only the type-alias and subclass forms, and only in `root_models.py` with and without the plugin. A tests three forms: the alias, direct `RootModel[float]('1.0')` (the issue's form), and a subclass. It adds a `BaseModel` comparison case to show parity. It also adds cases to `plugin_fail.py` that run under the `init_typed=True` (strict) configs. There the expected errors appear for both `BaseModel` and `RootModel`, confirming that RootModel now follows the plugin's `init_typed` setting rather than always being typed. That covers the other half of the behavior change, which B leaves untested. A's 5 'removed' test lines are just the updated import lines. A is the stronger patch because of its broader and more meaningful tests.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Initial Checks

  • I confirm that I'm using Pydantic V2

Description

The below example code (named foo.py) passes when running python foo.py as the input "1.0"-string gets converted to float. However, running mypy foo.py (with or without --strict) gives the following error:

foo.py:11: error: Argument 1 to "RootModel" has incompatible type "str"; expected "float"  [arg-type]
Found 1 error in 1 file (checked 1 source file)

I would expect the BaseModel-fields and the RootModel-field to behave the same in this case. That is, if the value can be converted – either via a custom made validator or through the conversion table – then mypy should not raise an error.

Example Code

import pydantic


class Foo(pydantic.BaseModel):
    f: float


RFoo = pydantic.RootModel[float]

f = Foo(f="1.0")
rf = RFoo("1.0")

assert isinstance(f.f, float)
assert isinstance(rf.root, float)
assert f.f == rf.root
