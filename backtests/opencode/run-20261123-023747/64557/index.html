The issue

View on GitHub

Summary

Requests to Gemini 4 Argon via the OpenCode Go subscription (opencode.ai/zen/go/...
route) fail with an upstream 403 policy rejection, even for trivial prompts ("test").
Other models on the same subscription (e.g. GLM-5.3) work minutes later, so client auth
and billing are fine. The rejection comes from the Google upstream behind the relay.
The error is also mislabeled in the UI as an "Authentication error".

Environment

  • opencode version: v2.3.0
  • OS: macOS 15 (Darwin 24.6.0, arm64)
  • Terminal: iTerm.app (xterm-256color, truecolor)
  • Shell: /bin/bash
  • Install/channel: latest stable desktop app (v2.3.0, /Applications/OpenCode.app)
  • Active plugins: none

Reproduction

  1. In the desktop app, select opencode-go/gemini-4-argon (OpenCode Go subscription).
  2. Send a trivial prompt, e.g. test.
  3. Request fails immediately; two consecutive attempts failed at 2026-11-17 ~19:11 ET (2026-11-18 00:11 UTC).

Expected Behavior

The prompt completes. If the upstream provider rejects it on policy grounds, the error
is surfaced as a provider policy rejection, not as an "Authentication error".

Actual Behavior

Verbatim error shown in the chat UI (twice):

Authentication error: Authentication failed for https://opencode.ai/zen/go/v1/chat/completions.
Status: 403 Forbidden. Response: Upstream request failed: [403] Request rejected in
accordance with our terms of use and policies.

Additional Context

  • The upstream message is Google Gemini's verbatim policy-block message. It is currently reported widely as false positives against coding-agent traffic, including trivial prompts, paid accounts, and third-party apps/relays:
  • https://discuss.ai.google.dev/t/antigravity-403-permission-denied-tos-false-positive-request-for-manual-review/196053
  • https://discuss.ai.google.dev/t/gemini-4-carbon-and-argon-403-policy-rejection-on-vertex-ai/199768
  • https://discuss.ai.google.dev/t/197895 (Gemini 4 Argon 403, same key works in AI Studio)
  • opencode service status reports a healthy server (http://127.0.0.1:49374). The server log shows no stream error entries at the failure timestamp, so the failure surfaced client-side only.
  • Workaround: switching to another model on the same subscription (e.g. GLM-5.3) works.
  • Possible asks: (1) check whether the Zen relay's Google upstream project is being ToS-flagged, (2) consider routing/fallback, (3) consider distinguishing upstream policy 403s from auth errors in the UI.
