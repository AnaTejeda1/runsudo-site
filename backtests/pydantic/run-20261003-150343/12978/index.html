In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches make the same core change. In `add_initializer`, they stop treating `RootModel`'s own hand-written `__init__` as a reason to skip generating the plugin `__init__`. That means `RootModel[float]('1.0')` gets the plugin's untyped (`Any`) signature when `init_typed` is unset, and the `fullname` vs `info.fullname` difference between them is cosmetic. Patch A also registers `pydantic.root_model._RootModelMetaclass` in `get_metaclass_hook`. In `root_model.py`, that class exists only under `TYPE_CHECKING` and is decorated with `dataclass_transform`, so `RootModel` and its subclasses use a different metaclass from `ModelMetaclass`. Without the hook, the plugin never clears that metaclass's `dataclass_transform_spec`. mypy's built-in dataclass_transform handling can then still synthesize or check an `__init__` for `RootModel` classes alongside the pydantic plugin. Patch A closes that gap at its source, which makes root models consistent with how the plugin already handles `BaseModel`. Patch B relies on the plugin-generated `__init__` winning over mypy's dataclass_transform handling, which is less robust. On tests, Patch B is broader: it adds a generic subclass (`Box[T]`), `assert_type` checks, a keyword `root=` call, and an `init_typed=True` module showing errors are kept in strict mode. That is valuable coverage. Patch A extends the existing `root_models.py` fixture and updates the expected outputs for the plugin and non-plugin configs. That directly captures the issue: no error with the plugin, while the non-plugin configs still report errors as expected. Both have tests that fail before the fix. Patch B's test coverage is better, but Patch A's more complete handling of the root-model metaclass makes it the more correct fix overall.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Initial Checks

Description

The below example code (named foo.py) passes when running python foo.py as the input "1.0"-string gets converted to float. However, running mypy foo.py (with or without --strict) gives the following error:

foo.py:11: error: Argument 1 to "RootModel" has incompatible type "str"; expected "float"  [arg-type]
Found 1 error in 1 file (checked 1 source file)

I would expect the BaseModel-fields and the RootModel-field to behave the same in this case. That is, if the value can be converted – either via a custom made validator or through the conversion table – then mypy should not raise an error.

Example Code

import pydantic


class Foo(pydantic.BaseModel):
    f: float


RFoo = pydantic.RootModel[float]

f = Foo(f="1.0")
rf = RFoo("1.0")

assert isinstance(f.f, float)
assert isinstance(rf.root, float)
assert f.f == rf.root
