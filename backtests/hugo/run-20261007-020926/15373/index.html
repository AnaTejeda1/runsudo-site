Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches implement the requested feature the same basic way. They resolve names beginning with './' or '../' against the calling partial's directory, walk up from decorator inner templates to the template the block was written in, and handle deferred blocks. Both also resolve the name before building the partialCached key, so same-named partials in different directories get separate cache entries. Both add integration tests that would fail without the change.

Patch A is more robust at the edges:

1. Safe type handling. A uses a checked type assertion on CurrentTemplateInfoOps and checks for a nil PathInfo. B uses an unchecked `.(*TemplInfo)` assertion and calls `ti.PathInfo.Dir()` without a nil check, so an unexpected context could panic.
2. Less side-effect risk on deferred templates. A adds an `origin` back-pointer to the deferred template and leaves its other fields alone. 3. Degenerate names. A rejects names like './' and '../' with a clear error. B passes them through to `path.Join`.

5. Tests. The issue

View on GitHub

Right now partial calls only supports path relative to layout/partials and themes/<THEME>/layouts/partials/*<PARTIALNAME> (taken from the documentation).

This is fine when we have few partials but can become a pain if we need to organize them in subdirectories.

What i propose is to add support for relative paths like in this example :

{{ partial "./foo" ... }}
{{ partial "../bah" ... }}

Why ?

Having this feature could be beneficial in a lot or ways :

  • it avoid us having to remember and write the full partial path when it's not needed (for example utility partials that are only called and only used by a on partial)
  • It could allow us to reorganize partials way more easily, as relative paths would full path independent

How to implement

If the path in a partial call starts with "./" or "../", it's a relative path. Otherwise it's an "absolute" path (relative to layout/partials).

I'm against adding the current directory of the current partial to the lookup search directly though, as theme and site authors currently assume this would call to the partial root directory. Perhaps we could add this to the future, if my proposal is adopted by the community.
