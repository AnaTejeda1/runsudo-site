Align <body> and <frameset> fragment parsing to the spec

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches make the same production change in HtmlTreeBuilderState. Each replaces `(stack.size() > 2 && !stack.get(1).nameIs("body"))` with `!stack.get(1).nameIs("body")` for both the `body` and `frameset` start-tag branches. This fixes the root cause: a 2-element stack such as [html, span] in a body fragment was not being ignored. Correctness is therefore equal.

The difference is in the tests. Patch A adds one test, and it covers only `<frameset>` (body and div contexts, plus an html-context check). It never exercises the `<body>` start-tag branch it also changed.

Patch B tests both branches:
- `<span><frameset>…` and `<span><body class=x>…` in a body context, checking that later content still lands in the span and that body attributes are not merged.
- The same cases through `Jsoup.parseBodyFragment`.
- A template context.
- Full-document regression checks showing that `<body>` attribute merging and the frameset-ok replacement of an implied body still work in normal parsing.

These tests would fail before the fix and pass after it. They also guard against the obvious risk of over-ignoring in document parsing.

Scope and craft are close. Patch A adds a CHANGES.md entry and drops the `// only in fragment case` comment; Patch B keeps the comment. Neither choice matters much. Patch B wins on more thorough, meaningful test coverage of both changed code paths.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The issue

View on GitHub

The spec says to ignore either start tag when the second open element is not body, but the current impl doesn't do that exactly. For example, parsing <span><frameset> as a body fragment currently returns <frameset> instead of <span>.
