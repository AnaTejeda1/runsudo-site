Panic when deleting a directory in static when server is running

Worse

The merged fix was judged better than our patch.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the root cause the same way. They replace the stat-dependent, directory-only `Contains` check with a `ReverseLookup`-based check. That check still classifies events for deleted mount roots and covers single-file mounts, so static events go back to the static syncer instead of the partial rebuild.

The differences are in error handling and tests:

- **Error handling.** Patch B calls `panic(err)` when `ReverseLookup` returns an error. That adds a new panic path to file-event classification in the running server, which is the kind of crash the issue reports. Patch A ignores the error and returns false, which is safer for a classification helper.
- **Fallback case.** Patch A also adds a `ComponentFolderStatic` case to the `processPartialFileEvents` switch. This is a defensive fallback rather than the fix itself. It could quietly drop a misrouted static event, but since the static syncer owns those events anyway, the risk is low and it prevents the reported panic outright.
- **Tests.** Patch A adds two server testscripts that reproduce the reported scenario end-to-end: deleting a mounted static directory and deleting a single-file static mount while the server runs, then asserting nothing is written to stderr. Patch B adds a focused unit test of `IsStatic` and `IsContent` after removing mount roots, plus a single-file mount check. That test is precise and would fail before the fix, but it does not exercise the server event path where the panic happened.

Overall, Patch A is more robust, with no new panic and a defensive switch case, and its tests reproduce the issue directly.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
