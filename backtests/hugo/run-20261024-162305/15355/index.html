tpl/transform: Strip BOM prior to unmarshaling a resource or string

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the issue at the same root: trimming the UTF-8 BOM at the top of metadecoders Decoder.Unmarshal, which is the path transform.Unmarshal uses for both resources and strings. The independent tests confirm both go from FAIL-ASSERT on base to PASS for CSV, JSON, TOML, YAML and XML, as resources and as strings, so correctness on the issue's scenarios is equal. The differences are in scope hygiene, tests, and craft. Patch A mixes in unrelated reformatting of existing test calls (splitting AssertFileContent and ReplaceAll argument lists across lines), which removes eight lines and adds noise that obscures the actual fix. Patch B keeps the existing tests untouched. Patch B also factors the BOM into a named constant and a small stripBOM helper instead of an inline byte literal with a trailing comment, and applies it consistently to UnmarshalTo and UnmarshalYaml and the i18n bundle; that extra coverage is beyond the ask and earns no credit on its own, but it is low risk (a trailing-whitespace-style prefix trim) and does not complicate the core change. On tests, both add a multi-format integration test that would fail before and pass after. B additionally includes the issue's own reproduction verbatim and exercises the site.Data path and i18n files, so its tests are broader without being tautological. A's test is adequate but narrower and ships alongside churn. Weighing scope (A's unrelated churn counts against it) and craft (B's named helper and constant), B is the better patch by a modest margin.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Each saw the issue and the two patches, labelled A and B in random order (two of them saw ours as A), with issue links and version numbers removed. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours. The reasoning above is one judge's, shown verbatim.
