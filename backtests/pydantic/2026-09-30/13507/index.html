Issue #13507 Merged fix PR #13516 Run 30 Sep 2026 pydantic/pydantic

Experimental pipeline: every constraint chained after ge/lt/le is dropped from the JSON schema

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the reported schema bug the same basic way. The fallback `function-after` check is now skipped when the native core-schema field is set, so later constraints still see a numeric schema and land in the JSON schema. Both add the issue's JSON-schema cases (`ge(1).le(100)`, `le(100).ge(1)`, `Interval`, the `multiple_of` chain, `lt(100).gt(1)`).

The patches differ in how they guard the native path, and that decides it.

Patch A introduces a validation regression. It drops the type-matching checks and assigns the native field whenever the schema is int, float or decimal. It also never checks whether that field is already set. Because no wrapping happens anymore, a repeated constraint silently overwrites the earlier one:
- `validate_as(int).ge(5).ge(1)` ends up as `{'type': 'int', 'ge': 1}` and accepts 3.
- `.multiple_of(3).multiple_of(5)` enforces only 5.

Before Patch A, both constraints were enforced by the stacked function validators. So Patch A trades a schema-only bug for a real validation bug, which is the more serious failure the issue stressed was not present.

Patch A also relies on pydantic-core to coerce mismatched bound types. Its tests only use exactly-representable values like `ge(0.0)` on int. A fractional bound on an int schema (`ge(1.5)`) is either rejected at schema build or silently changed, and nothing tests that.

Patch B follows the `native_constraint_applied` shape the issue proposes, applied symmetrically to all five branches. It sets the native field only when the value type matches and the field is not already present. Otherwise it falls back to the function check, so:
- type mismatches are still enforced;
- repeated constraints stack instead of overwriting;
- the common chained cases get a correct native schema.

Patch B's tests cover exactly these edges: the issue's schema cases plus a float mixed-bound case, validation of the chained expression, type-mismatch fallbacks for all five constraints, and repeated-constraint enforcement. Patch A would fail the repeated-constraint tests.

Patch B is more verbose, but it is correct and consistent with the existing branching style.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The issue

Initial Checks

  • I confirm that I'm using Pydantic V2

Description

In the experimental pipeline API, chaining constraints silently drops every bound after the first from the generated JSON schema. Validation stays correct - only the published schema is wrong, which makes it easy to miss.

All bounds below are non-zero, so this is not #13450 (falsy zero bounds in Interval). Observed identically on released 2.13.4 and on main (2.14.0a1).

expressionJSON schemavalidation
validate_as(int).ge(1).le(100){"minimum": 1, "type": "integer"}0 reject, 50 accept, 200 reject
validate_as(int).le(100).ge(1){"maximum": 100, "type": "integer"}0 reject, 50 accept, 200 reject
validate_as(int).constrain(Interval(ge=1, le=100)){"minimum": 1, "type": "integer"}0 reject, 50 accept, 200 reject
validate_as(int).ge(1).le(100).multiple_of(5){"minimum": 1, "type": "integer"}correct
validate_as(int).gt(1).lt(100) (control){"exclusiveMinimum": 1, "exclusiveMaximum": 100, ...}correct
Annotated[int, Ge(1), Le(100)] (control){"minimum": 1, "maximum": 100, ...}correct

So .ge(1).le(100).multiple_of(5) publishes a schema advertising any integer >= 1, while the validator rejects 200 and 52. For FastAPI that means the OpenAPI component and every generated client disagree with the server.

Cause

In _apply_constraint(), the Ge, Lt and Le branches apply their fallback function validator unconditionally - including when the native core-schema field was just set:

elif isinstance(constraint, annotated_types.Ge):
    ge = constraint.ge
    if s and s['type'] in {'int', 'float', 'decimal'}:
        s = s.copy()
        if s['type'] == 'int' and isinstance(ge, int):
            s['ge'] = ge          # native constraint applied...
        ...

    def check_ge(v: Any) -> bool:
        return v >= ge

    s = _check_func(check_ge, f'>= {ge}', s)   # ...and then wrapped anyway

_check_func wraps the schema in function-after. The next constraint in the chain sees s['type'] == 'function-after', which is not in {'int', 'float', 'decimal'}, so it cannot set its own native field and survives only inside an opaque callable that JSON-schema generation cannot read. Core schema for .ge(1).le(100):

{'type': 'function-after',
 'function': ...,                       # <- le(100) lives in here, invisible to the schema
 'schema': {'type': 'function-after',
            'function': ...,            # <- redundant ge check
            'schema': {'type': 'int', 'ge': 1}}}

Gt is the control that works, and only by accident: its fallback sits in an else:, so nothing is wrapped when the native constraint applies.

Relationship to the open PRs in this function

Two in-flight PRs each fix one branch of this, for unrelated reasons, and between them they leave Ge, Lt and Le untouched:

  • #13473 adds a native_constraint_applied flag to MultipleOf to avoid a float parity problem. Same shape as the fix needed here.
  • #13446 restructures Gt so the fallback lands inside the numeric branch.

Worth flagging on the second one: #13446's description argues that Gt is uniquely broken and holds up Ge/Lt/Le/MultipleOf as the correct model, because they "always apply" the check and so enforce the bound on a type mismatch. That is true of validation, but always applying it is exactly what destroys the schema. Gt is uniquely broken for validation; the other four are broken for schema. Whichever way this is fixed, it probably wants to be one symmetric change across all five branches rather than three separate patches.

from typing import Annotated

from pydantic import TypeAdapter

What the agent reported

I fixed the bug: chained constraints like .ge(1).le(100) now all appear in the JSON schema, and validation still enforces every bound. The pipeline tests (88), tests/test_types.py, tests/test_json_schema.py and tests/test_docs.py all pass. The changes are uncommitted in the working tree.

What was wrong

In _apply_constraint (pydantic/experimental/pipeline.py), the Ge, Lt, Le and MultipleOf branches always wrapped the schema in a function-after validator, even after setting the bound directly on the numeric schema. The next constraint in the chain then saw a function-after schema instead of an int/float/decimal one. It could only be enforced through an opaque function that JSON-schema generation can't read, so it vanished from the schema while validation stayed correct.

Gt had the opposite problem, which is a validation bug. On a numeric schema where the bound's type doesn't match (e.g. an int schema with gt(1.5)), it set nothing and added no check, so the constraint was silently dropped: validate_as(int).gt(1.5) accepted 1.

What I changed

  • One symmetric change across all five branches (Gt, Ge, Lt, Le, MultipleOf), using the native_constraint_applied flag the report points to from #13473. The fallback check is only added when the bound wasn't set directly on the schema.
  • A fix for a problem the first change introduced, found in review. With the fallback gone, chaining the same constraint twice let the second value overwrite the first: .ge(5).ge(1) accepted 3. Each branch now sets the bound directly only if that field isn't already set; otherwise it adds the fallback check. Before this change the same overwrite already happened for .gt(5).gt(1), and that is fixed too.

Tests added (tests/test_pipeline.py)

  • Seven new test_json_schema cases, checking both validation and serialization schemas. They cover ge(1).le(100), le(100).ge(1), constrain(Interval(ge=1, le=100)), ge(1).le(100).multiple_of(5), lt(100).gt(1), multiple_of(5).ge(1) and float ge(1.5).lt(10.5). All seven failed before the fix and pass now.
  • test_chained_numeric_constraints_validation: 50 is accepted; 0, 200 and 52 are rejected. It passed before and after, which is expected since validation was never broken; it guards against a regression.
  • test_numeric_constraint_type_mismatch: gt/ge/lt/le/multiple_of with a float bound on an int schema. The gt case failed before (1 was accepted); the others guard the fallback path.
  • test_repeated_numeric_constraint: the same constraint chained twice. Five of the six cases failed against the first version of the fix and pass now.

tests/test_validators.py::test_v1_validator_deprecated fails both with and without my changes (checked by stashing them), so it is an unrelated existing failure. I didn't change or skip any existing test.
