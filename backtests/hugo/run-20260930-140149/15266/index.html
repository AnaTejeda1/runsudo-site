What the agent reported

I left the working tree unchanged: bumping mainImageVersionNumber wouldn't reach the images these two fixes change. I also couldn't run any tests here, so the one worthwhile change isn't applied.

Why the bump wouldn't help

  • The main version number only goes into ImageConfig.Key, which DecodeImageConfig builds (resources/images/config.go:338-340).
  • .Filter then replaces that key with its own: confMain.Key = hashing.HashString(gfilters) (resources/image.go:325). So filtered images never include the main version number.
  • Both commits only change .Filter output:
  • 77856683d: the palette skip applies to ActionFilter only, and the hex-color parsing change only affects colors that aren't fully opaque, as used by filters like images.Padding. Fully opaque colors produce the same result as before.
  • 9e7c978e6: this only changes the behaviour of filter chains.
  • Bumping it would invalidate every resized, cropped, fitted and filled image on every site, none of which changed. It would still leave the stale filtered images in place.

What would work: a filter-only version number, like the existing smartCropVersionNumber and formatVersionNumbers:

// resources/images/config.go, in the version var block
FilterVersionNumber = 1

// resources/image.go, Filter()
if images.FilterVersionNumber > 0 {
	confMain.Key = hashing.HashString(gfilters, images.FilterVersionNumber)
} else {
	confMain.Key = hashing.HashString(gfilters)
}

I had this implemented, then reverted it:

  • Tests can't run here. Module downloads are blocked, so ./bt-test fails at build setup ([setup failed]), even on the unmodified tree. I couldn't compile the change or see any test pass.
  • Three pinned filter filenames would change. They are in tpl/images/images_integration_test.go: lines 164-165 (qr_hu_d5f06fd7594d0594.png), 187-188 (.webp) and 217 (qr_hu_6b5f59be9c4d3b3a.webp). The new values come from gohugoio/hashstructure, which isn't available offline, so I couldn't work them out. Shipping the change would leave those tests failing.

On the "few sites are affected" argument: a filter-only bump is cheap, because it only re-processes filtered images. If you want it, apply the snippet above, run go test ./tpl/images/ ./resources/... and update those three expected filenames. That run is also the regression evidence.

Requirements

  1. Bump mainImageVersionNumber: not done. It wouldn't invalidate the affected images (evidence above) and would invalidate every other processed image.
  2. Make site owners see the fixes without flushing their cache: not done. The right fix is FilterVersionNumber above, but it can't be tested here, so there's no test in the diff.
  3. Weigh "very few sites affected": the smaller filter-only bump makes this concern mostly moot.

The AGENTS.md and CLAUDE.md deletions were already in the working tree when I started, and I left them alone.
