# Build the /backtests section of runsudo.dev

## Goal
A public, read-only section where YC partners and prospects can see our backtest results: every repo, every run, every ticket, with the verdict and both patches. A reader should understand it within 2 minutes and be able to check every claim themselves.

## Hosting constraint (read first)
runsudo.dev is one static `index.html` served by GitHub Pages, with no build step on GitHub's side. GitHub Pages serves files as they are and can't route `/backtests/pydantic/run-20260930-144322/13771` to a template. So:
- Add a small generator script, e.g. `scripts/build-backtests.mjs` (Node, no dependencies or minimal ones). It reads `data/backtests/**` and writes a real `index.html` for every URL: `backtests/index.html`, `backtests/<repo>/index.html`, `backtests/<repo>/<run-id>/index.html` and `backtests/<repo>/<run-id>/<ticket>/index.html`.
- The generated HTML is committed, so "push to deploy" keeps working. Don't use a 404.html single-page-app fallback.
- Share CSS between the homepage and backtests pages, e.g. by moving the homepage's `:root` tokens into `styles.css`, or duplicate the tokens exactly. Either way, the pages must look identical to the homepage.
- Pages must work with JavaScript off, apart from the small interactive parts: chart tooltips, ticket filters and "Show full issue".

## Look and feel
- Dark theme, matching the runsudo.dev homepage exactly. Reuse the homepage's fonts (Inter via `--sans`, plus its `--mono`), its colors and CSS variables, its spacing and its header/nav/footer. Don't add a new font or color scheme.
- Verdict colors are used consistently everywhere (pills, bars, chart):
  - **Better**: green
  - **Par**: grey
  - **Worse**: red
  - **Error**: yellow/amber
  Pick shades that read well on the dark background and meet contrast (4.5:1 for text). Pair each color with its text label, so the color is never the only cue.
- Works at phone width with no horizontal page scroll. Diffs may scroll horizontally inside their own box.
- Add a "Backtests" link to the homepage nav and hero.

## Routes
- `/backtests/`: overview
- `/backtests/<repo>/`: repo page (e.g. `/backtests/pydantic/`), showing the latest run
- `/backtests/<repo>/<run-id>/`: a specific run (e.g. `/backtests/pydantic/run-20260930-144322/`)
- `/backtests/<repo>/<run-id>/<ticket>/`: a ticket (e.g. `/backtests/pydantic/run-20260930-144322/13771/`)

The run is part of the URL because we rerun the same tickets, so a ticket link must always point at one specific run. Runs are addressed by the harness run id, not the date, because a repo can be run more than once in a day. The date is shown on every page but is display only.

## Page 1: `/backtests/` (overview)
1. **Intro.** Heading and 1–2 sentences: we replay real, already-fixed GitHub issues from public repos. Our agent gets the issue and the code as it was before the fix, works in an isolated container with the network locked down, and never sees the real fix. A blind judge then compares our patch to the one maintainers merged, labelled only A and B.
2. **Headline card.** Latest result for the featured repo: "20 / 30 judged better than the merged fix", a stacked bar (better / par / worse / error) and counts. Links to that run.
3. **Progress chart.**
   - X-axis: dates. Y-axis: % of tickets judged better (0–100%).
   - One line per repo. Each point is one run on that repo's fixed ticket sample. Never mix repos into one line. Two runs on the same day are two points, placed by the time of day in the run id so they sit side by side rather than on top of each other.
   - Hovering or tapping a point shows: date, repo, better/par/worse/error counts and the note. Clicking a point opens that run.
   - **Event markers:** vertical dashed lines with a labelled dot at the top, for major dates (e.g. "Opus 5.5"). Two kinds: `product` (solid dot) and `measurement` (hollow dot, for fixes to how we measure or verify). Add a legend and a one-line caption explaining the two kinds.
   - Inline SVG, generated by the build script. No chart library needed. It must look right on the dark theme.
4. **"How to read a verdict".** Four short cards, one per verdict, in the verdict colors:
   - **Better:** our patch passes the full test suite and the judge preferred it to the merged fix.
   - **Par:** both are equally good.
   - **Worse:** the merged fix was better, or our patch broke a test that passed before. We show every one.
   - **Error:** the harness couldn't finish the ticket. Counted in the total, never dropped.
5. **Repos table.** Columns: repo, language, latest run date, stacked bar with better·par·worse counts, % better. Each row links to its repo page. A repo with no valid run yet shows "Rerun scheduled" and no numbers.

Do NOT add a "Start here" or featured-tickets section.

## Page 2: `/backtests/<repo>/[<run-id>/]` (repo / run page)
1. Breadcrumb: Backtests / <repo>
2. **Header.** Repo name, one-line description, languages, and short chips for the run being shown (e.g. "0 contaminated", "0 errors"). Summary card with the big % better, stacked bar and counts.
3. **"Runs on this sample".** A list of all runs of this repo's ticket sample, newest first. Columns: **date (with the run id under it) | better · par · worse · error | notes**. Same-day runs are told apart by the id. Do NOT show a model column. The notes are free text we write, e.g. "Updated to Opus 5.5" or "Found a test-replay bug that marked 5 correct patches as worse; fixed". The run being viewed is highlighted, and the others link to their run URL.
4. **Tickets table** for the run being viewed. Columns: issue #, title, verdict pill, changed lines (ours / merged), test suite ("No new failures" or "N failing"). Filter buttons: All / Better / Par / Worse / Error, each with its count. The Error button appears only if the run has errors. Each row links to the ticket page.
5. Optional footnote per run (free text), e.g. "This run was split across two harness runs because…"

## Page 3: `/backtests/<repo>/<run-id>/<ticket>/` (ticket page)
1. Breadcrumb: Backtests / <repo> / <run-id> / #<ticket>
2. **Header.** Issue #, merged fix PR # (both linking to GitHub), run date, and the issue title as the heading.
3. **Verdict block.** A large verdict pill and one line, e.g. "Our patch was judged better than the merged fix."
   - Show the **judge's reasoning exactly as written: verbatim, unedited, not summarised.** It refers to "Patch A" and "Patch B".
   - Directly above it, show the mapping clearly: "In this judgment, Patch A = our agent, Patch B = the merged fix. The order was randomized per ticket, and the judge never knew which was which." Take it from `judge.agent_is`, because it differs per ticket.
   - Keep any placeholders like `<link>` in the reasoning exactly as they are, escaped so they display as text. They come from scrubbing issue links before judging.
   - Under it, a small note: "The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed."
4. **Stat cards.** Solve time and agent turns; full test suite result (total / passed / skipped / new failures); contamination audit result; patch size (changed lines, ours vs merged).
5. **The issue.** The issue text rendered as markdown, collapsed after roughly 15 lines with "Show full issue", plus a link to it on GitHub.
6. **The two patches, side by side** (stacked on mobile). Left: "Our patch" with +/− counts. Right: "Merged fix · PR #N" with +/− counts. Unified diff with file headers, hunk headers, and added/removed lines tinted. Keep the added/removed tints distinct from the verdict colors.
7. **What the agent reported.** The agent's final summary, rendered as markdown, verbatim.
8. Previous / next ticket links and "All tickets in this run".

## Data (static JSON in this repo; we generate it from our harness)
All pages are generated from files under `data/backtests/`. No backend.

`data/backtests/index.json`: repos, runs and chart events:
```json
{
  "repos": [
    {
      "slug": "pydantic", "name": "pydantic/pydantic",
      "description": "Data validation library for Python, with a Rust core.",
      "languages": ["Python", "Rust"], "status": "active",
      "runs": [
        { "date": "2026-09-30", "id": "run-20260930-144322", "tickets": 30,
          "better": 20, "par": 2, "worse": 8, "error": 0,
          "notes": "Updated to Opus 5.5", "footnote": "" },
        { "date": "2026-09-29", "id": "run-20260929-204949", "tickets": 30,
          "better": 12, "par": 2, "worse": 12, "error": 3,
          "notes": "All verification fixes in place", "footnote": "" }
      ]
    },
    { "slug": "pydantic-ai", "name": "pydantic/pydantic-ai", "languages": ["Python"],
      "status": "pending", "runs": [] }
  ],
  "events": [
    { "date": "2026-09-30", "label": "Opus 5.5", "kind": "product" },
    { "date": "2026-09-29", "label": "Verification fixes", "kind": "measurement" }
  ]
}
```
In `runs`, count 1 no-patch ticket as `error` for display.

`data/backtests/<repo>/<run-id>/tickets.json`: one entry per ticket. The folder name is the run's `id` from `index.json`, which must be unique within the repo:
```json
[
  {
    "number": 13771, "title": "`validate_call` cannot call a function with a keyword parameter named `self`",
    "verdict": "better", "pr": 13773,
    "issue_url": "https://github.com/pydantic/pydantic/issues/13771",
    "pr_url": "https://github.com/pydantic/pydantic/pull/13773",
    "judge": { "reasoning": "<verbatim text>", "agent_is": "A" },
    "solve": { "duration_s": 77, "turns": 8 },
    "tests": { "total": 13007, "passed": 12498, "skipped": 509, "new_failures": 0 },
    "audit": { "verdict": "clean" },
    "lines": { "ours": 14, "merged": 12 },
    "issue_md": "<issue markdown>",
    "agent_summary_md": "<agent final summary markdown>",
    "patches": { "ours": "<unified diff>", "merged": "<unified diff>" }
  }
]
```
Treat all of this text as untrusted input. Render markdown with a sanitizer (no raw HTML) at build time, and HTML-escape diffs and judge text, never inserting them as raw HTML.

## How we update it
After a run, one of us (Adalai or Roman):
1. Drops the new `tickets.json` into `data/backtests/<repo>/<run-id>/`.
2. Adds the run's entry with its notes to `index.json`, and adds an event there if it's a major date.
3. Runs `node scripts/build-backtests.mjs`.
4. Commits and pushes. GitHub Pages redeploys.

There's nothing to edit by hand in the generated pages. Add a short `data/backtests/README.md` explaining these steps.
