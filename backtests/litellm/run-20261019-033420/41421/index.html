[Bug]: LiteLLM Proxy 1.100.0 serializes image-edit uploads as strings for OpenAI GPT Image models

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches address the same root cause: `_read_request_body` re-parses the multipart body, so the `image[]`/`mask[]` parts survive in `data` as raw UploadFiles alongside the converted `image`/`mask` buffers, and the SDK stringifies them into text parts. Both independent tests pass for both patches. Patch A drops exactly the two bracketed keys; Patch B drops any UploadFile under the four known file keys and converts any other leaked UploadFile to BytesIO rather than letting it be stringified. B's approach is keyed on the actual failure condition (a raw UploadFile in the forwarded payload) rather than on two literal key names, so it is more robust at low risk; the extra conversion for unknown upload fields is out of scope but adds no risk and is tested. On tests, B is clearly stronger: beyond unit checks on the captured dict, it adds an end-to-end regression that drives `litellm.aimage_edit` through an httpx MockTransport and asserts the real multipart body contains a filename-bearing file part with the PNG bytes and no `UploadFile(`/`BytesIO` text, which mirrors the issue precisely. A's tests are adequate but only inspect the captured dict. On scope, A includes unrelated reformatting of existing test lines (the 8 removed lines), which is churn; B touches only what it needs. Craft is comparable; B's comment explains why the filtering exists, and its `StarletteUploadFile` annotation is correct since FastAPI's UploadFile subclasses it. B is the better fix.

What happened?

Image edits through the LiteLLM Proxy fail in version 1.100.0 for OpenAI GPT Image models. The uploaded image file is being converted to a string representation of a Python BytesIO object ("<_io.BytesIO object at 0x7f0d0bc73600>") before being sent to OpenAI.

OpenAI rejects this with:

{
  "error": {
    "message": "Invalid type for 'image[0]': expected a file, but got a string instead.",
    "type": "invalid_request_error",
    "param": "image[0]",
    "code": "invalid_type"
  }
}

The same request succeeds in LiteLLM version 1.95.0.

User Flow

Before a fix: A user sends an image-edit request through LiteLLM Proxy 1.100.0 using a multipart/form-data request to POST /v1/images/edits with an uploaded image file and a prompt (e.g., "Make this image photorealistic"). LiteLLM receives the UploadFile correctly but serializes it to a string before forwarding to OpenAI. OpenAI rejects the request because it expects a file object, not a string representation.

  1. User sends: curl -X POST "http://localhost:4000/v1/images/edits" -F "model=openai/gpt-image-2" -F "prompt=Make this image photorealistic" -F "image[]=@./input.png;type=image/png"
  2. LiteLLM receives UploadFile with filename, size, and content-type headers
  3. LiteLLM converts the UploadFile's BytesIO object to a string
  4. LiteLLM forwards stringified image to OpenAI
  5. OpenAI rejects with invalid_type error

After a fix: The same user flow succeeds. LiteLLM preserves the UploadFile/BytesIO object and forwards it to OpenAI as a multipart file, and OpenAI processes it successfully.
