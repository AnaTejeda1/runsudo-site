Issue #15207 Merged fix PR # Run 2 Oct 2026 · run-20261002-200313 gohugoio/hugo

panic: slice bounds out of range in contentNodeShifter.Delete when removing draft pages from a multilingual taxonomy

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

The two production fixes are essentially identical. Both change the `Delete` and `DeleteFunc` shifter contracts to return an updated node. Both stop mutating the `contentNodes` slice in place while ranging over it, which is the root cause: `append(v[:i], v[i+1:]...)` inside a range shifts elements under the iterator. This corrupts the shared backing array, leaves a stale duplicated tail in the stored value, and later causes the slice-bounds panic. Both then re-insert the updated value into the tree when something was deleted but the node isn't empty. They also handle `DeleteFuncRaw` the same way.

Minor code differences are negligible:
- B preallocates `kept` with `make` and adds a comment explaining why the slice is never modified in place.
- A uses nil-initialised `remaining` and a separate `vv` variable in the default case.

The difference is in the tests.

**Patch A** tests only the shifter in isolation with a hand-rolled fake node type. It checks the returned counts and `updated` values. It never exercises the tree path that actually panicked: repeated `NodeShiftTree.delete` calls on the same key, with the updated value stored back.

**Patch B** tests through the real `NodeShiftTree` with real `resourceSource` nodes:
- It deletes languages sequentially in a non-trivial order, which is the multi-delete scenario that left a stale tail and panicked.
- After each step it verifies the stored raw value's length and identity.
- It checks that repeated deletes are no-ops and that the original slice isn't mutated.
- It covers nested `contentNodesMap` inside `contentNodes`.
- It covers `DeleteFuncRaw` with adjacent and trailing deletions, which is exactly the skip-element bug the old in-place loop had.

These tests reproduce the reported failure mode end-to-end and would fail against the old logic. B's tests are therefore materially stronger and more faithful to the issue, so B wins.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The 0x35 in delete(..., {…, 0x35}) is 53, exactly the byte length of the key being removed (/blog/ plus a 47-character slug).

Only on the page-removal path

hugo -D (drafts included) builds fine. The panic appears only when a page is removed from the tree, which makes it invisible in local preview and fatal only in production.

A future publishDate panics identically. Setting [_build] render = "never" / list = "never" on the same pages avoids it entirely — consistent with those pages never being added to the tree, so nothing is deleted.

What I ruled out

Site: 8 languages, ~1,490 pages per language, ~11,455 content files, categories taxonomy.

  • Not a regression. 0.159.1 and 0.164.0 behave identically.
  • Not the number of drafts. 96 draft pages build fine; 16 panic.
  • Not slug length. The panicking key was 47 chars, but renaming an unrelated post to exactly 47 chars builds fine.
  • Not the slug. Renaming the offending page does not help.
  • Not byte layout. Deleting a front-matter line, or adding a blank one, still panics.

Swapping page content at a fixed path isolates it to front matter. Changing categories = ["Airport Operations"] on the offending page to any other value clears the panic — and so does moving a different page out of that same category while leaving the offending one alone. So the trigger is combinatorial: some particular set of pages being deleted from one taxonomy term corrupts the shifter, rather than any single page being malformed.

Reproducer

I have not managed to minimise it, and I want to be upfront about that. Synthetic multilingual sites (8 languages, 12 blog + 200 glossary pages sharing one taxonomy term, varying draft counts) do not reproduce, so something else in the real tree is required. The affected repository is private.

I am happy to run patches or instrumented builds against the real site and report back, which may be faster than guessing at a minimal case.
