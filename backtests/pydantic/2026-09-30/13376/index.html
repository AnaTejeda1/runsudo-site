In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches store the takes-validated-data flag on ModelPrivateAttr, so after the first call neither re-runs inspect.signature per private-attribute instantiation. Patch A is the better fix.

Correctness and risk:
- Patch A keys its cache on the factory's identity, so reassigning `default_factory` still gives a correct result.
- Patch A adds an optional `default_factory_takes_validated_data=None` keyword to `resolve_default_value` and falls back to computing it when absent. The internal helper stays backward compatible.
- Patch A only passes the precomputed flag when it will actually be used.
- Patch B makes `resolve_default_value` fully keyword-only and adds a new required argument. Any caller not shown in the diff would break.
- Patch B changes `FieldInfo.get_default` to always evaluate `FieldInfo.default_factory_takes_validated_data`, even when `call_default_factory=False`. That property is uncached, so Patch B adds inspect.signature calls to a path that previously had none.

Initial Checks

  • I confirm that I'm using Pydantic V2

Description

For a private attribute with a default_factory, every model instantiation re-derives whether the factory takes the validated data by calling takes_validated_data_argument(default_factory=...), which runs inspect.signature() on the factory (pydantic/_internal/_fields.py:694) — not cached, even though it's a pure function of the factory object. It runs twice per instantiation, from two separate sites in init_private_attributes() (pydantic/_internal/_model_construction.py:377): once via the ModelPrivateAttr.default_factory_takes_validated_data property, and once via get_default() → resolve_default_value() (_fields.py:718). Both are uncached.

Regular Field(default_factory=...) is not affected — it computes this once at schema-build time via FieldInfo.default_factory_takes_validated_data and bakes it into the core validator. Only the PrivateAttr path recomputes per instance.

For a factory whose inspect.signature() succeeds via CPython's inspect._signature_fromstr (list, tuple, set, threading.Lock, …), that call does sys.modules.copy() and builds closures that capture the copy — reference cycles the plain refcounter can't free, only the cyclic GC can. Instantiating such a model at a high rate in a long-running process accumulates this garbage faster than the collector reclaims it (and pymalloc keeps the freed arenas), so RSS climbs steadily.

Concretely: Sculptor has a BaseModel with _wait_lock: Lock = PrivateAttr(default_factory=Lock) that is instantiated constantly. It was harmless on Python ≤3.12 — there inspect.signature(Lock) raises ValueError: no signature found, so pydantic falls back cheaply — but began leaking multi-GB of RSS on 3.13+, because CPython 3.13 gave threading.Lock an inferrable signature and flipped every instantiation onto the _signature_fromstr path. We mitigated it by memoizing this check: imbue-ai/sculptor#205.

With default_factory=list it reproduces on every CPython tested (3.12.11, 3.13.5, 3.14.6) and on pydantic 2.13.4 through main (2.14.0a1) — ~52k objects of cycle-only garbage per 1000 instantiations. list/tuple have always had signatures, so the bug isn't tied to a Python version; the set of other builtins that trigger it just grows over time (set, threading.Lock at 3.13).

Example Code

import gc
from pydantic import BaseModel, PrivateAttr
from pydantic._internal import _fields

# (1) It's recomputed on every instantiation, uncached:
calls = 0
_orig = _fields.takes_validated_data_argument
def _counting(*args, **kwargs):
    global calls
    calls += 1
    return _orig(*args, **kwargs)
_fields.takes_validated_data_argument = _counting

class M(BaseModel):
    _items: list = PrivateAttr(default_factory=list)

M()                       # warm
calls = 0
for _ in range(1000):
    M()
print("takes_validated_data_argument calls:", calls)   # -> 2000

# (2) Each call leaves cycle-only garbage (default_factory=list):
gc.collect(); gc.disable()
before = len(gc.get_objects())
for _ in range(1000):
    M()
after = len(gc.get_objects())
freed = gc.collect(); gc.enable()
print("objects grew:", after - before, "| freed only by cyclic gc:", freed)
# -> objects grew: ~54000 | freed only by cyclic gc: ~52000

Suggested fix

The simplest fix is to memoize takes_validated_data_argument (a pure function of the factory, e.g. functools.cache) — after the first call per factory, both per-instance calls become cache hits.

Alternatively, do what regular fields do and compute the flag once at class-construction time, storing it so both sites can read it. Note this is more than "reuse the property": ModelPrivateAttr.default_factory_takes_validated_data (pydantic/fields.py:1451) is itself an uncached @property that re-runs inspect.signature on every access — it's one of the two per-instance calls, so it has to be precomputed too, not just read from resolve_default_value.

Happy to open a PR if you'd like.

What the agent reported

I fixed it: PrivateAttr(default_factory=...) now checks the factory's signature once instead of twice on every model instantiation. The new regression test failed before the change and passes after, and the surrounding test files pass.

What was wrong: When a model was created, init_private_attributes called _fields.takes_validated_data_argument twice per private attribute. That function runs inspect.signature, and nothing cached the result. One call came from the ModelPrivateAttr.default_factory_takes_validated_data property. The other came from get_default(), which calls resolve_default_value(). For factories like list and, on Python 3.13+, threading.Lock, each call leaves reference cycles that only the cyclic garbage collector can free.

What I changed:

  • pydantic/fields.py, ModelPrivateAttr:
  • There is a new slot, _default_factory_takes_validated_data_cache, which stores the factory and the result together.
  • The property computes the result on first access and reuses it after that. The cache is keyed on the factory object itself, so if someone reassigns default_factory, it is recomputed.
  • get_default() passes the cached value down to resolve_default_value when it actually calls the factory.
  • I added a small __repr_args__ override. The base class builds the repr from __slots__, so without it the new slot would have shown up in the repr. The output is unchanged.
  • pydantic/_internal/_fields.py, resolve_default_value: it takes a new optional keyword, default_factory_takes_validated_data. If it isn't passed, the function computes the value as before, so other callers such as FieldInfo.get_default behave exactly as they did.

Tests:

  • New test: test_private_attr_default_factory_takes_validated_data_computed_once in tests/test_private_attributes.py. It counts calls to takes_validated_data_argument (by wrapping the function, not mocking it) and checks that the defaults are still correct.
  • Before the fix it failed with assert 20 == 0: 10 instantiations made 20 calls.
  • After the fix it passes. It covers default_factory=list and a factory that takes the validated data.
  • Gate: ./bt-test on tests/test_private_attributes.py, test_main.py, test_fields.py, test_construction.py, test_pickle.py, test_dataclasses.py and test_edge_cases.py gave 893 passed, 28 skipped, 2 xfailed, 0 failed.
  • Not tested: I didn't re-run the report's garbage-collection measurement (the ~52k objects), because pydantic_core isn't installed outside the test lane. The test shows the root cause is gone: after the first instance, inspect.signature isn't called again.
  • Review: the reviewer found no blocking issues. One side effect: a ModelPrivateAttr pickled with this version can't be unpickled by an older pydantic. Old pickles still load in this version.

Scope of the change: only ModelPrivateAttr and an optional new keyword on resolve_default_value. FieldInfo is unchanged, as is ModelPrivateAttr's equality check, and no existing tests were modified.

Requirements:

  1. Stop the check running on every instantiation: done. The new test shows 0 calls after the first instance.
  2. Both call sites (the property and get_default → resolve_default_value): done. Both now use one cached value, and the test counts calls from both.
  3. Suggested fix A, functools.cache on takes_validated_data_argument: not used, on purpose. A global cache would hold strong references to every factory forever, including dynamically created lambdas. It would also raise TypeError for callables that can't be hashed. Caching on the ModelPrivateAttr avoids both problems.
  4. Suggested fix B, compute once and make the property cached too: done, but on first use rather than when the class is built. The property itself is now cached. It is computed on the first instantiation, which the test allows for by resetting its counter after the first instance.
  5. Regular Field(default_factory=...) is not affected: left unchanged, as the report says. FieldInfo is untouched and tests/test_fields.py passes.
  6. The default_factory=list and threading.Lock examples: list is covered directly by the test. Lock goes through the same code path, so the same caching applies; I didn't write a separate test for it.

The changes are uncommitted in the working tree, with no scratch files left behind.
