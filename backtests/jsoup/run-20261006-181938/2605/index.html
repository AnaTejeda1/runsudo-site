Parser reuse interrupts StreamParser

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the root cause the same way. `StreamParser` now drives `parser.getTreeBuilder().newInstance()` instead of sharing the supplied parser's tree builder. The supplied `Parser` is still passed into parse initialisation, so configuration and error tracking stay on it. Both therefore resolve the two scenarios in the issue: reusing the parser mid-stream, and `Element.append(String)` on a streamed element.

Tests are comparable in quality:
- **Patch A** adds tests for parser reuse mid-stream, including `parseInput`, `parseFragmentInput` and `unescape`. It also tests append mid-stream, checking the remaining streamed elements via `stream().forEach` and the final document, and tests that errors land on the supplied parser.
- **Patch B** adds equivalent reuse and append tests, plus a settings/errors-sharing test. Both sets would fail before the fix and pass after.
- Both update existing tests that reached into `parser.getTreeBuilder()`. A preserves the adoption-recovery tests' use of `StreamParser` by giving the test subclass a proper `newInstance()` override. B rewrites that helper to drive the tree builder directly, bypassing `StreamParser`.

The difference is scope and risk. Patch B also makes changes the fix does not need:
- It flips `stopped` to `true` by default, which changes iterator semantics before `parse()`.
- It removes the `document = treeBuilder.doc` refresh from `document()`. That makes correctness depend on `parse()`/`parseFragment()` always assigning the field, which the diff does not show.
- It widens the `treeBuilder` field to package-private.

These extra behavioural edits add risk without being required by the issue. Patch A makes the minimal core change, adds a narrow package-private accessor, and documents the reasoning inline. Patch B's CHANGES entry is a minor plus but does not outweigh the added risk.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The issue

View on GitHub

Reusing a Parser supplied to a StreamParser overwrites the active streaming parse state.

And calling Element.append(String) on a streamed element has the same effect, because it uses that parser to parse the added HTML.

The fix will just copy the treebuilder, while preserving configuration and error diagnostics on the supplied parser.
