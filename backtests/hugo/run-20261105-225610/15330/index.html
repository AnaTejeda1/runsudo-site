hugo server: page cut at its previous length when another content file changes in the same batch

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Root cause: collectDir dedupes on the walked directory via seenDirs, so when two changed files share a directory the second collectDir call returns early and its file-specific filter never runs; that file is never re-collected and is later rendered with stale metadata against new bytes (hence the old-length cut, U+FFFD, and slice-bounds panic). Both patches address this and both pass all five independent tests, so the decision rests on completeness and robustness.

Patch A changes the dedupe key from directory to path (dirPath.Path()). This is minimal and fixes the reported scenario, but it does so by discarding what the dedupe was for: a batch with N changed files in one directory now walks that directory N times, and overlapping filters (e.g. a structural directory change plus a file change inside it, keyed differently as dir path vs file path) can hand the same file to the rungroup twice. It also leaves a direct variant of the issue broken: fileEventsContentPaths still drops regular files below a leaf bundle, so editing index.md and p1.md of the same bundle in one batch never re-collects p1.md, producing the exact stale-length symptom the issue title describes. A's single test covers grow and shrink only.

Patch B keeps one walk per directory but groups the per-id filters and ORs them, which preserves the dedupe's intent while guaranteeing every changed path's filter is applied. The helper collectDirPath makes the grouping key identical to collectDir's seenDirs key, so nothing can be lost. It also removes the leaf-bundle drop in fileEventsContentPaths, with an accurate comment explaining why (the leaf bundle filter only matches the bundle file in the non-structural case), fixing the index+resource same-batch variant. The closure deferral relies on Go per-iteration loop variables, which modern Hugo requires. B's five tests cover grow (exact match), shrink, edit+add in a batch, two bundle resources, and bundle index+resource, each of which fails on base and passes with the fix. The site.go change is extra scope, but it is the same bug class and is reasoned, not churn.

B is the more complete root-cause fix with stronger tests; A is correct for the headline case but degrades the collector's dedupe and leaves the bundle variant unfixed.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Each saw the issue and the two patches, labelled A and B in random order (two of them saw ours as A), with issue links and version numbers removed. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours.
