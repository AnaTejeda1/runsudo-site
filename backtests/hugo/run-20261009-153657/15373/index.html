Support relative path calls in partials

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches take the same basic approach. They resolve `./` and `../` names against the calling partial's directory before lookup and before the partialCached cache key is computed. Both also add a `decoratorOwner` link so that `with partial` decorator inner blocks resolve against the template that wrote them. The differences are in robustness.

1. **Deferred-template collisions.** Patch A changes the deferred-template hash in `handleWith` to include the owner's partial directory. Without this, two partials in different directories with identical `templates.Defer` bodies (e.g. `{{ partial "./item.html" . }}`) share one deferred template ID. Only the first registration's PathInfo is kept, so the second resolves against the wrong directory. Patch B leaves the hash unchanged, so it has this bug. Patch A's `TestIncludeRelativePathDefer` exercises this case directly.

2. **Deferred-template ownership.** Patch A sets `decoratorOwner: owner` on deferred templates, which also correctly follows deferred blocks nested in decorators. Patch B instead copies `owner.category` onto the deferred TemplInfo, which was previously left at its zero value. That changes a field other code may consult and adds risk. It also copies `owner.decoratorOwner`, which works but is less direct.

3. **Edge-case handling.** Patch B uses an unchecked type assertion `cur.CurrentTemplateInfoOps.(*TemplInfo)`, which can panic. Patch A uses the comma-ok form. Patch A also rejects names that don't name a file (`./`, `..`). It verifies that the resolved path stays under the partials root, and it handles the legacy `layouts/partials` directory and inline-defined partials, with tests for each.

4. **Tests.** Patch A's suite is broader: cache-key separation, legacy directory, inline partials, decorators, defer, and table-driven error cases. Patch B's tests cover the main paths, decorator, defer and two error cases, but miss the hash collision.

Patch B adds documentation, which is a nice touch but neutral under the scope criterion. Overall, Patch A is more correct and better tested.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The issue

View on GitHub

Right now partial calls only supports path relative to layout/partials and themes/<THEME>/layouts/partials/*<PARTIALNAME> (taken from the documentation).

This is fine when we have few partials but can become a pain if we need to organize them in subdirectories.

What i propose is to add support for relative paths like in this example :

{{ partial "./foo" ... }}
{{ partial "../bah" ... }}

Why ?

Having this feature could be beneficial in a lot or ways :

  • it avoid us having to remember and write the full partial path when it's not needed (for example utility partials that are only called and only used by a on partial)
  • It could allow us to reorganize partials way more easily, as relative paths would full path independent

How to implement

If the path in a partial call starts with "./" or "../", it's a relative path. Otherwise it's an "absolute" path (relative to layout/partials).

I'm against adding the current directory of the current partial to the lookup search directly though, as theme and site authors currently assume this would call to the partial root directory. Perhaps we could add this to the future, if my proposal is adopted by the community.
