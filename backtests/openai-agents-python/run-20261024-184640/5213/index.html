Streamed runs swallow consumer cancellation and skip run cleanup while a parallel input guardrail is running

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches make the same core change: `_await_task_safely` and `input_guardrail_tripwire_triggered_for_stream` switch from `await task` to `asyncio.wait((task,))`, forward consumer cancellation to the task, and re-raise, so a cancelled guardrail task no longer looks like the waiter's own cancellation. Both pass the four independent tests for the issue's two repro scenarios (consumer timeout/cancel swallowed; result.cancel() during an in-flight tool skipping cleanup).

The decisive difference is the fifth independent test: `result.cancel()` called after the model finished, while the run loop's `finally` is already waiting on the guardrail. Here the CancelledError genuinely belongs to the run-loop task, so both patches' guardrail helper re-raises it. Patch A then lets it abort the rest of `start_streaming`'s `finally`, so computers are never disposed and the trace/spans never finish (independent test: FAIL-ASSERT on A, 'computer created for the run was not disposed'). Patch B explicitly catches that CancelledError in run_loop.py, finishes `dispose_resolved_computers()`, span/trace finish, and the completion sentinel, then re-raises it. The issue's stated expectation is general: 'cancelling the run should still finish the trace/spans and dispose per-run computers', and this is a very plausible ordering (fast model, slow moderation guardrail, user cancels). B resolves it; A does not. B also adds a regression test (`test_cancel_while_run_loop_awaits_input_guardrail_finishes_run_cleanup`) for exactly this path.

Patch A's additional work is mixed. The try/finally around model-provider/sandbox cleanup in `stream_events` is reasonable hardening now that cancellation propagates, but the base already skips those cleanups on the `cancelled` path, so B's behaviour is consistent with existing semantics rather than a regression. A's `ignore_cancelled` keyword on `input_guardrail_tripwire_triggered_for_stream` adds API surface and forces a signature change in an unrelated existing test's monkeypatched finalizer; B's unconditional `if not task.cancelled(): task.result()` is simpler and matches the issue's root-cause description. A's extra `await asyncio.wait((task,))` after `task.cancel()` preserves old direct-await settlement, which is defensible but not required by the issue.

Tests: both add deterministic, event-gated tests that would fail on base. B's are more directly mapped to the issue's scenarios (consumer cancel, consumer timeout, result.cancel during tool, consumer cancel during tool, cancel while run loop awaits guardrail, consumer cancel during run-loop cleanup wait). B's only skip is the `asyncio.timeout()` test on Python < 3.11, and it is paired with a non-skipped CancelledError equivalent, so coverage holds. A's parametrized consumer-cancellation test and cleanup-ordering test are solid but one of A's tests relies on fairly intricate monkeypatching of internals.

On correctness, B covers strictly more of the issue's stated expected behaviour, confirmed by the independent run, with a smaller and clearer change. B wins.

View on GitHub

Please read this first

  • Have you read the docs? Yes, including the streaming cancellation section.
  • Have you searched for related issues? Yes. #2222 fixed cancellation while stream_events() waits for the next event; this report covers the remaining waits on the input guardrail task and the run-loop task, which still swallow cancellation.

Describe the bug

Streamed runs mishandle cancellation while a parallel input guardrail is still running. Parallel is the default for input guardrails, and a guardrail that outlasts the model, such as a moderation call, is common.

  1. The consumer's cancellation is swallowed. When the model has finished but the guardrail has not, stream_events() waits for the guardrail after the final event. If the consumer is cancelled or its asyncio.timeout() expires during that wait, the guardrail is cancelled, but stream_events() returns normally. The caller never sees CancelledError/TimeoutError and continues with result.final_output, even though the input guardrail never produced a verdict.
  2. Run cleanup is skipped after result.cancel(). If result.cancel() (or consumer cancellation) happens while the guardrail is running, the run loop's finally awaits the cancelled guardrail task, gets its CancelledError, and aborts the rest of cleanup. The trace plus the task and agent spans are never finished, and computers created by a ComputerProvider for the run are never disposed.

async def cancel_skips_cleanup() -> None:
    tool_started = asyncio.Event()

    @function_tool
    async def slow_tool() -> str:
        tool_started.set()
        await asyncio.sleep(3600)
        return ""

    traces.open.clear()
    agent = make_agent([[function_call("slow_tool", {}, call_id="call_1")]], tools=[slow_tool])
    result = Runner.run_streamed(agent, "hi")

    async def consume() -> None:
        async for _ in result.stream_events():
            pass

    consumer = asyncio.create_task(consume())
    await tool_started.wait()
    result.cancel()
    await consumer
    await asyncio.sleep(0.1)
    print("2) result.cancel(): unfinished traces =", len(traces.open))


async def main() -> None:
    await timeout_is_swallowed()
    await cancel_skips_cleanup()

Output on main:

1) timeout: stream_events() returned normally, final_output = 'done'
2) result.cancel(): unfinished traces = 1

Expected behavior

1) timeout: TimeoutError raised
2) result.cancel(): unfinished traces = 0

Cancelling a stream consumer should propagate to that consumer, and cancelling the run should still finish the trace/spans and dispose per-run computers.

Root cause

Both waits await the shared task directly:

  • RunResultStreaming._await_task_safely() runs await task and suppresses CancelledError. Awaiting a task forwards the waiter's cancellation into the task, so after the consumer is cancelled the task ends cancelled. The CancelledError the consumer then receives looks like the task's own cancellation and is swallowed.
  • input_guardrail_tripwire_triggered_for_stream(), which the run loop's finally calls before disposing computers and finishing spans, runs await task. When the guardrail task was cancelled by cancel(), awaiting it raises CancelledError in the run loop and the remaining cleanup is skipped.

Ordering for (1): the model completes, QueueCompleteSentinel is queued, the consumer takes the sentinel and awaits the guardrail task, and the consumer is cancelled. The guardrail is cancelled, the consumer suppresses the resulting CancelledError, and stream_events() ends normally.

Ordering for (2): a tool (or the model) is in flight while the guardrail runs, and result.cancel() cancels the run loop and the guardrail. The run loop enters its finally, awaits the cancelled guardrail task, gets CancelledError, and exits before dispose_resolved_computers(), span.finish(), and trace.finish().

Waiting with asyncio.wait((task,)) avoids both problems: the task's own cancellation is not raised into the waiter, and a CancelledError there always belongs to the waiter. That waiter can then forward its cancellation to the task, as await did, and re-raise it.
