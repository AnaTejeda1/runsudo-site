Allow arbitrary core schemas for serialization

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Patch B is the better fix on correctness, tests and craft.

**Correctness.** Patch B adds an explicit `SchemaSerSchema` (`{'type': 'schema', 'schema': CoreSchema}`) with a `schema_ser_schema()` helper. Its Rust handling is small and unambiguous: it builds the inner schema as a full serializer and gives a clear error when `schema` is missing. B then does what the issue asks:
- It replaces the identity wrap-serializer workaround everywhere it appears: `ValidateAs`, `PlainValidator`, `InstanceOf`, `SkipValidation`, and the mapping lax_or_strict case in `_generate_schema`.
- It updates JSON-schema generation (`ser_schema` and `_get_ser_schema_for_default_value`) so the new type is reflected in serialization JSON schemas and default serialization.

Patch A takes a different route: every non-special `serialization` dict is treated as a core schema and passed to `Self::build`. This creates a namespace collision. `function-plain`/`function-wrap` validator schemas cannot be used, because those type names are already taken by the ser-function schemas, and A admits this in a comment. `model` also overlaps with `ModelSerSchema`. A tries to paper over the collision with a Python-side `as_ser_schema` helper, but never uses it. The `ValidateAs` workaround stays in place with only the TODO reworded.

A also leaves JSON-schema generation unaware of core schemas used as serialization schemas: `ser_schema()` returns None for a `list_schema`. And it declares `SerSchema` as a string forward-reference alias, which forces `Union` workarounds and casts elsewhere. A's switch from `find_serializer` to `build` for every existing ser type also changes behaviour broadly, which adds risk.

**Tests.** Both add solid pydantic-core tests. B also adds end-to-end pydantic tests (ValidateAs, SkipValidation, InstanceOf, PlainValidator, Counter/defaultdict/OrderedDict). These cover serialization, include/exclude, and serialization JSON schema through the code paths that actually changed. A's pydantic-side test only exercises an unused helper.

**Overall.** B resolves the gap cleanly, removes the workarounds the issue points to, and keeps JSON schema consistent. A leaves the issue's concrete workaround in place and has an ambiguous design.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The issue

View on GitHub

As per the TODO in https://github.com/pydantic/pydantic/pull/13487:

There is currently no way to tell pydantic-core "serialize this value using this core schema". SerSchema is:

SerSchema = Union[
    SimpleSerSchema,
    PlainSerializerFunctionSerSchema,
    WrapSerializerFunctionSerSchema,
    FormatSerSchema,
    ToStringSerSchema,
    ModelSerSchema,
]

The only member that expresses "use this schema" is SimpleSerSchema, and it does not take a schema at all, only a name from a closed literal:

ExpectedSerializationTypes = Literal[
    'none', 'int', 'bool', 'float', 'str', 'bytes', 'bytearray', 'list', 'tuple',
    'set', 'frozenset', 'generator', 'dict', 'datetime', 'date', 'time', 'timedelta',
    'url', 'multi-host-url', 'json', 'uuid', 'any',
]

class SimpleSerSchema(TypedDict, total=False):
    type: Required[ExpectedSerializationTypes]

So an arbitrary schema (a model, a dataclass, list[int], a TypedDict, anything constructed by the schema generator) cannot be used directly. Every place in Pydantic that needs it works around the gap the same way: it wraps the schema in a wrap serializer whose function is the identity, purely so the schema can ride along in the schema argument.

From ValidateAs.__get_pydantic_core_schema__():

https://github.com/pydantic/pydantic/blob/27f95c789b20aa23306e5ce559327db0e9a10a6e/pydantic/functional_validators.py#L911-L917
