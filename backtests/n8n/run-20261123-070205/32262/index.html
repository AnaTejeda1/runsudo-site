Javascript expression: Using ` (template literals) adds UNINTENDED SPACE after underscore if there's a fixed string before it

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches apply the same root-cause fix: they stop replacing individual TemplateElements (which recast patches in place, inserting a space between a trailing identifier character like `_` and the following `${`) and instead rebuild the whole TemplateLiteral with `original = null` so recast reprints it from scratch. Both gate the rebuild on the literal containing a real newline, so literals without newlines are no longer touched at all. On the core issue they are equivalent and both resolve the `chk_ 123` symptom at its cause.

The differentiator is a side effect of reprinting the whole literal. Recast's printer builds each quasi via `fromString(raw)`, which treats leading whitespace as indentation and re-emits leading tabs as spaces when concatenating. In the base code only quasis containing a newline were reprinted; with the whole-literal rebuild, every quasi of a multiline literal is reprinted, so a quasi such as `\tb_` that previously survived untouched now has its leading tab expanded to spaces under Patch A. Patch B anticipates this by escaping tabs to `\t` in the rebuilt elements (a semantically identical change to the cooked value, consistent with how newlines are already escaped) and adds a 'keeps tabs' test for it. This is adjacent to the issue, but it directly neutralises a regression the shared approach would otherwise widen, so it counts as a correctness advantage rather than scope creep.

Tests: Patch B's suite is more thorough and more faithful to the report: a direct `people.map(p => \`...\`).join('')` reproduction, fixed text plus multiple code chunks, nested literals, tagged templates, tabs, and a workflow-package test with the issue's expression shape. Patch A adds two tournament tests plus a compatibility-corpus row that cover the core case and nesting but less of the surrounding surface. All of these tests would fail on base and pass after their respective patch for the core scenario; neither could be executed by the harness (all runs crashed), so I weighed them on content only.

Craft is comparable: A uses an object spread with an `original: null` type intersection, B assigns `literal.original = null` on a `{ original?: null }` type; both are clear, and B's comment explains the recast behaviour in more detail. Overall B is the better fix by a modest but real margin on correctness at the edges and on test coverage.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Each saw the issue and the two patches, labelled A and B in random order (two of them saw ours as A), with issue links and version numbers removed. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours. The reasoning above is one judge's, shown verbatim.

Bug Description

Javascript expression: Using ` (template literals) adds UNINTENDED SPACE after underscore if there's a fixed string before it.
The example flow below creates this output, showcasing the buggy behaviour in the first line of the output:


- There's an unwanted space between the "chk_" and the variable-string: chk_ 123
- When I change the _ to a - the unwanted space disappears: chk-123
- When I use a variable in front of the _ instead of a fixed string, the unwanted space disappears as well: John_123

- There's an unwanted space between the "chk_" and the variable-string: chk_ 456
- When I change the _ to a - the unwanted space disappears: chk-456
- When I use a variable in front of the _ instead of a fixed string, the unwanted space disappears as well: Max_456


------------

- There's NO unwanted space between the "chk_" and the variable-string anymore when not using template literals: chk_123
- There's NO unwanted space between the "chk_" and the variable-string anymore when not using template literals: chk_456
