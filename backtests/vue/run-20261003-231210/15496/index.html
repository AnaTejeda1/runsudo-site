looseEqual: comparing Map/Set values with circular references throws RangeError (regression in 3.5.42)

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the root cause the same way. Each tracks the (a, b) pairs currently on the comparison stack, threads that state through the array, collection and object recursion, and removes entries on unwind. Both handle every repro in the issue: mutually-referencing Set elements, Map values, and self-containing Sets. Both also fix the cyclic plain-object/array case.

Correctness differences:
- Patch A enforces a bijection: a re-encountered `a` must map back to the same `b`, and vice versa. So `looseEqual(self, first)`, where self->self and first->second->first, returns false. Those structures are structurally indistinguishable, and the issue asks for structurally identical cyclic data to compare equal. A's stricter rule is defensible but can give false negatives. Patch B returns true there.
- Patch A changes the exported `looseEqual` signature by adding an optional third `seen` parameter. This leaks internal state into the public API and risks misuse if `looseEqual` is ever passed as an array callback, where the third argument would be the array. Patch B keeps `looseEqual(a, b)` unchanged and uses a private `looseEqualImpl`.
- Patch B allocates tracking state only when both sides are objects. Its one minor wart is that empty inner Sets are not removed from the map; this is harmless and bounded per call.

Tests:
- Patch B adds unit tests for cyclic Sets, Maps (including a map containing itself), and objects/arrays. It includes negative cases (`makeGraph(3)`, `s3`) proving it does not simply return true on cycles.
- Patch B also adds two runtime-dom `<select v-model>` render tests that mirror the issue's actual reproduction path.
- Patch A's tests cover the unit cases plus a shared-reference case, but have fewer meaningful negative cases. Its 'symmetric' test locks in the debatable false result.

Scope and craft: both are focused. Patch B follows the issue's suggested design closely and has a clear explanatory comment. Patch A's `looseCompareObjects` extraction is extra churn.

Overall, B is cleaner, keeps the API stable, and is better tested.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Steps to reproduce

Open the reproduction above: a <select v-model> whose option :values are Sets containing mutually-referencing objects. The component throws during mount, before any interaction.

<script setup>
import { ref } from 'vue'

const makeGraph = () => {
  const n1 = { id: 1 }
  const n2 = { id: 2 }
  n1.peer = n2
  n2.peer = n1  // circular reference
  return new Set([n1, n2])
}

const optA = makeGraph()
const optB = makeGraph()
const selected = ref(optB)
</script>

<template>
  <select v-model="selected">
    <option :value="optA">A</option>
    <option :value="optB">B</option>
  </select>
</template>

What is expected?

Mounting the select should not throw. looseEqual should safely terminate on cyclic structures (e.g. by tracking already-visited pairs) and return true for two structurally identical cyclic Sets/Maps.

Any additional comments?

This is a regression introduced by #15328 ("fix(shared): correctly compare Map and Set values", released in v3.5.42), which added looseCompareCollections in packages/shared/src/looseEqual.ts:

function looseCompareCollections(
  a: Map<any, any> | Set<any>,
  b: Map<any, any> | Set<any>,
) {
  if (a.size !== b.size) return false
  const candidates = Array.from(b)
  const matched = new Uint8Array(candidates.length)
  for (const item of a) {
    let index = -1
    for (let i = 0; i < candidates.length; i++) {
      if (!matched[i] && looseEqual(item, candidates[i])) {
        index = i
        break
      }
    }
    if (index < 0) return false
    matched[index] = 1
  }
  return true
}

looseEqual(item, candidates[i]) recurses into each [key, value] pair (Map) or element (Set), so a Map/Set whose entries point back to the collection itself or to each other causes unbounded recursion. Before 3.5.42, Maps/Sets never recursed into their entries (they fell through to String() comparison), so this exact code path — a <select v-model> with Map/Set values, which is precisely the scenario #15320/#15328 added support for — did not throw on 3.5.41; it silently compared wrong, which #15328 fixed.

Note: #5318 covers the same root cause for cyclic plain objects (pre-existing, still open). The Map/Set case is new in 3.5.42: cyclic Maps/Sets did not throw before.

Suggested fix: make looseEqual cycle-safe by tracking visited (a, b) pairs (e.g. with a WeakMap<object, Set<object>> and returning true on re-encounter), which also fixes #5318.

Additional local repro cases that all throw RangeError on current main:

  • looseEqual(new Set([a1, a2]), new Set([b1, b2])) where a1.peer = a2; a2.peer = a1 and b1.peer = b2; b2.peer = b1
  • looseEqual(mapA, mapB) where both maps hold mutually-referencing values
  • looseEqual(s1, s2) where s1.add(s1) and s2.add(s2)
