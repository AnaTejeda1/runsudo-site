Errors thrown in async setup are caught silently during SSR

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the root cause the issue names: the `.catch(NOOP)` that wrapped the whole setup promise is narrowed so it only swallows onServerPrefetch failures, and both also handle a synchronous throw from a prefetch call (A via `Promise.resolve().then(...)`, B via try/catch). All six independent tests pass on both, and both add tests that fail on base and cover the key regressions (async setup with/without render function, prefetch registered then throw, sync prefetch error still rendering, errorCaptured for prefetch errors in A).

The meaningful difference is what happens once setup errors actually propagate. renderComponentVNode's promise is pushed into the SSR buffer and only awaited by unrollBuffer in order. With Patch A, if an earlier sibling is still pending (e.g. a real I/O fetch) when a later component's setup rejects, that rejection is unhandled for at least one tick, which Node reports as an unhandled rejection and, under the default `--unhandled-rejections=throw`, crashes the process. The issue's scenario (async setup throwing during SSR) makes this a realistic consequence of the fix, not a hypothetical. Patch B anticipates it with `p.catch(NOOP); return p`, which marks the rejection as observed while still returning the rejecting promise to the caller, and it adds tests ('while awaiting an earlier sibling' with setImmediate) that would surface the unhandled rejection under Patch A. B also makes renderToString/renderToStream stop registered watchers and settle in-flight buffer promises on a failed render, which is defensible cleanup now that renders can reject, though it is beyond the ask.

On scope, B is considerably broader (new cleanupFailedRender/settleBuffer helpers, stream error path change, test helper change to reject with the error). That breadth adds some risk and a reviewer could reasonably prefer A's minimal diff, but the core fix in B is equally correct and the extra code is cohesive and tested. A is the cleaner minimal patch and its tests are well targeted, but it leaves a real process-crash hazard that B's fix handles, so B is the better fix overall.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Each saw the issue and the two patches, labelled A and B in random order (two of them saw ours as A), with issue links and version numbers removed. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours. Steps to reproduce

Open the reproduction link, which performs the following steps:

  1. Throws an error from a component's async setup.
  2. Renders the component using renderToString.

What is expected?

The error should propagate up to the renderToString call, causing it to return a rejected promise.

In the minimal reproduction, that rejection would be uncaught, so the error would appear in the Node.js console.

What is actually happening?

There's no uncaught error or unhandled promise rejection. The console only displays the following warnings:

[Vue warn]: Unhandled error during execution of setup function 
  at <App>
[Vue warn]: Component App is missing template or render function. 
  at <App>

Also, if there is a render function in the component throwing the error, it renders successfully as if no error occurred.

Any additional comments?

This bug is caused by https://github.com/vuejs/core/commit/349eb0f0ad78f9cb491278eb4c7f9fe0c2e78b79#diff-96591cb7eb061552355cc70e508472b1acc2688c3449ad0daa19c3cbac08cc97R100, where onServerPrefetch was added. Originally, the bug only occurred when the setup synchronously calls onServerPrefetch.

That line intended to catch errors thrown from onServerPrefetch callbacks, but the .catch was mistakenly applied to the entire setup promise.

The bug was expanded to occur in all async setups in https://github.com/vuejs/core/commit/6039e25e04a8c1db5821955f011d57f1615807ab#diff-96591cb7eb061552355cc70e508472b1acc2688c3449ad0daa19c3cbac08cc97R110 by no longer gating the .catch behind if (prefetches).
