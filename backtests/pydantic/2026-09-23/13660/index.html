None is not treated as Literal[None] when annotating the discriminator in discriminated unions.

Worse

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches correctly identify the root cause: `_infer_discriminator_values_for_inner_schema` never handled the `{'type': 'none'}` core schema produced by a bare `None` annotation, and both add the `[None]` branch that resolves the reported validation error. The decisive difference is completeness of the fix. When the discriminator value is `None`, JSON-schema generation in `json_schema.py` runs the key through `str(k)`, yielding the mapping key `'None'` — which does not match the serialized JSON payload (`null`). Patch A leaves this wrong: it fixes validation but silently produces an invalid discriminator mapping for the exact feature it enables, and its test only exercises validation, never `model_json_schema()`, so it never catches this. Patch B adds the `elif k is None: k = 'null'` branch and includes a test asserting the mapping is `{'A': ..., 'null': ...}` plus round-trip validation of both branches — genuinely fail-before/pass-after coverage of both dimensions. Patch A is markedly tighter in scope (4 lines) and B carries real costs against it: a wholesale rewrite of the if/elif chain into a `match` statement (unrequested churn), widening `list[str | int]`→`list[Any]` and `Hashable`→`Any` in core_schema.py (largely gratuitous, since `None` is itself hashable), and weakening the existing `test_bool_discriminated_union` to assert only a subset — a coverage regression. These are meaningful marks against B on scope and craft. But correctness is the first criterion, and A ships a subtly incorrect JSON schema for the feature it introduces while B handles the feature end-to-end and proves it. That correctness edge outweighs B's scope churn. Narrow call.

Description

Literal[None] and None should be semantically equivalent type annotations, to the point that flake8-pyi and ruff have warnings for the former: https://docs.astral.sh/ruff/rules/redundant-none-literal/

Pydantic does however not treat them as semantically equivalent for the purposes of discriminated unions.

Example Code

from typing import Annotated, Literal

from pydantic import BaseModel, Field


class A(BaseModel):
    field: Literal["A"] = "A"


class B(BaseModel):
    field: None = None


class Foo(BaseModel):
    a_or_b: Annotated[A | B, Field(discriminator="field")]

# Results in the error below. 
# If `: None` is replaced with `: Literal[None]` then there is no error.
# ...
# pydantic.errors.PydanticUserError: Model 'B' needs field 'field' to be of type `Literal`
# 
# For further information visit https://errors.pydantic.dev/2.13/u/discriminator-needs-literal

What the agent reported

The fix is complete and verified. Here's my final report.

What was wrong

In discriminated unions, a member whose discriminator field was annotated with bare None (e.g. field: None) failed to build, raising a spurious PydanticUserError: ... needs field ... to be of type Literal (code discriminator-needs-literal). Meanwhile Literal[None] worked fine. The two annotations should be semantically equivalent.

Root cause: In pydantic/_internal/_discriminated_union.py, _infer_discriminator_values_for_inner_schema inspects the discriminator field's core schema type. Literal[None] produces a 'literal' schema (handled), but a bare None produces a 'none' core schema, which wasn't recognized and fell through to the else branch that raises the error.

What I changed

  • pydantic/_internal/_discriminated_union.py — added an elif schema['type'] == 'none': return [None] branch, treating a bare None discriminator annotation as equivalent to Literal[None]. This path is distinct from the existing outer-union 'none' handling (which sets _should_be_nullable), so nullable-union behavior is untouched.
  • tests/types/unions/test_discriminated_union.py — added test_discriminated_union_none_discriminator, reproducing the reported scenario (A with Literal['a'], B with bare None) and asserting {'field': 'a'} selects A and {'field': None} selects B.

Test evidence

  • The new test failed before the fix with the exact reported error (Model 'B' needs field 'field' to be of type Literal).
  • After the fix: ./bt-test tests/types/unions/test_discriminated_union.py → 80 passed, 4 xfailed (the new test passes; no previously passing test regressed).
  • Reviewer confirmed the change is minimal, correctly targeted, no scratch files, no weakened tests, and no blast-radius concern (the 'none' discriminator-field path does not collide with the existing nullable outer-union path; None is a valid Hashable tag key).

Requirements disposition

  • Treat bare None as Literal[None] for discriminated-union discriminators — ✅ Implemented and covered by the passing regression test exercising the report's exact example.

One minor, pre-existing note (not addressed, non-blocking): the function's return annotation list[str | int] doesn't include None, but this is cosmetic loose typing already present in the surrounding code and has no runtime effect. Changes are left uncommitted in the working tree.
