The issue

View on GitHub

TL;DR: the generated package.json has no "private": true and a checkout-derived name, so committed copies are publishable under names sites don't control. Suggested fix: emit "private": true and a stable (ideally scoped) default name.

What version of Hugo are you using (hugo version)?

hugo v0.165.0-76a5e1880ab46688155b02e99bab9be2a6134492+extended darwin/arm64 BuildDate=2026-08-12T14:26:28Z VendorInfo=gohugoio

Does this issue reproduce with the latest release?

Yes (transcript below is v0.165.0). The behavior is in master's package_builder.go.

What happened

hugo mod npm pack writes packages/hugoautogen/package.json with:

  • a name derived from the checkout directory, so it varies per clone and can be a registry name the site doesn't control, and
  • no "private": true, npm's do-not-publish guard for internal packages.

The file is regenerated wholesale on each run, so hand-set fields don't survive. From a fresh clone of a repo whose committed copy was hand-normalized:

$ git clone https://github.com/google/docsy-example.git site-a && cd site-a
$ grep -E '"(name|version|private)"' packages/hugoautogen/package.json
  "name": "@docsy/hugoautogen",
  "version": "0.1.0",
  "private": true
$ hugo mod npm pack
$ grep -E '"(name|version|private)"' packages/hugoautogen/package.json
  "name": "site-a",
  "version": "0.1.0"

A sibling clone of the same repo into site-b yields "name": "site-b".

Why it matters

Sites that commit the generated workspace (e.g. so npm ci works without running Hugo first) end up carrying a manifest that npm workspace publishing and common release tools treat as publishable by default: npm publish --dry-run --workspaces packs it as site-a@0.1.0, while with "private": true npm skips the workspace. The name variance also churns the committed manifest, and the lockfile's workspace entry, across differently named checkouts.

What did you expect

The generated internal workspace is non-publishable ("private": true) and has a stable, project-controlled default name rather than the checkout directory's basename. Ideally the default is scoped: a bare name can be claimed on the registry by anyone, a scoped one only by the scope owner.

Workaround

docsy-example#487 follows each pack invocation with a single npm pkg set line restoring a scoped name and private.

Happy to send a PR for the private field (and for the name default, if you have a preference for what it should be).

What the agent reported

hugo mod npm pack now marks the generated packages/hugoautogen/package.json as "private": true and always names it @gohugoio/hugoautogen, no matter which directory the site is checked out into. The new regression test failed before the change and passes after it. The three mod_npm* command tests could not run here because they need to fetch modules from github.com and there is no network.

What was wrong: In Pack (modules/npm/package_builder.go), the name field came from the site root directory's name, so cloning into site-a gave "name": "site-a". The file also had no private field. Hugo rewrites the whole file on every run, so any fields set by hand were lost.

What I changed:

  • modules/npm/package_builder.go: added a constant autoGenPackageName = "@gohugoio/hugoautogen" and dropped the code that read the directory name. The generated file now has "name": "@gohugoio/hugoautogen", "private": true and "version": "0.1.0", plus the dependencies as before.
  • docs/content/en/hugo-modules/nodejs-dependencies.md: one sentence stating the package's name and that it is private.
  • Tests:
  • A new test, TestPackageBuilderAutoGenPackageJSONPrivateAndStableName in modules/npm/package_builder_integration_test.go, runs the pack on the real filesystem from two differently named checkout folders (mycheckout, other-checkout-dir). It checks that name, private and version come out the same in both.
  • I updated the expected output in testscripts/commands/mod_npm.txt, mod_npm__moduleorder.txt and mod_npm_withexisting.txt. In each, the old "name": "script-…" line (which came from the test's own folder name) became the new name plus "private": true. This follows from the fix rather than loosening the tests. The checksum lines in those files don't change, because the checksum never includes the generated file.

Test evidence:

  • Before the fix: the new test failed with got: "mycheckout" and got: "other-checkout-dir" against want: "@gohugoio/hugoautogen". The existing TestPackageBuilder passed.
  • After the fix: everything in ./modules/npm/ passes, including both new subtests and TestPackageBuilder, and gofmt reports nothing.
  • Command tests: TestCommands/mod_npm* stop at their first hugo mod npm pack with Could not resolve host: github.com. They would fail the same way without my change, so their updated expected output is checked by reading it against the JSON encoder's output, not by a run.
  • Setup note: ./bt-test only worked with GOMODCACHE=/bt/cache/go-mod GOPROXY=off added, because the default Go module cache here is nearly empty and can't download.

Impact on existing behaviour: the only thing that used the old folder-based name was this file's name field. Sites that commit the file will see a one-time change to name and private in the file and in the lockfile's workspace entry, and after that it stays the same across clones. A reviewer pass found no unrelated changes.
