tpl/transform: Strip BOM prior to unmarshaling a resource or string

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the root cause: they strip the UTF-8 BOM in `metadecoders.Decoder.Unmarshal`, which is the path `transform.Unmarshal` uses for both resources and strings. That resolves the reported CSV/JSON/TOML/XML/YAML failures.

Patch A is more thorough. It also strips the BOM in `UnmarshalTo` (used by `UnmarshalToMap` and `UnmarshalFileToMap`, so front matter, config and data paths are covered) and in `UnmarshalStringTo`, so every decoder entry point behaves the same. The helper and constant are named clearly and cite the issue.

Patch A's tests are stronger. It adds unit tests for `UnmarshalStringTo` with a BOM, the issue's CSV integration test, and a broader integration test. That test covers every format as a resource, every format as a string via `.Content`, and BOM-prefixed files in the `data/` directory through `hugo.Data`. Patch B's test covers each format as a resource and only JSON as a string.

Patch B also reformats several unrelated existing test calls (`AssertFileContent` and `strings.ReplaceAll` argument wrapping). That churn obscures the diff without adding value. Its fix is minimal and correct for the issue, but narrower.

Overall Patch A has comparable correctness, broader consistency, better tests and no unrelated churn.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
