Allow symlinks for mount source for the main project

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches make the same core change: skip the symlinked-mount-root rejection in NewRootMappingFs when rm.IsProject is set. That directly resolves the reported scenario (a project mount whose source directory is a symlink), and all three independent tests pass on both. The difference is completeness and test coverage. Patch B only lifts the check at mount-construction time; a project mount whose source is a single symlinked file still dies in statRoot's per-file symlink rejection, so the 'main project is trusted' rule B states in its comment is only half-implemented. Patch A carries the exemption through consistently: statRoot follows the symlink only when the mapping is a project single-file mount (root.fiSingleFile != nil, after rename/inclusion filtering has pinned filename to the mounted file), and componentFsDir keeps the corresponding entry under the same narrow condition. The extra code is small and guarded, so it adds little risk, and it closes an inconsistency a user hitting this issue would plausibly trip over next. Patch A's testscript is also stronger: it reproduces the issue's exact shape (an explicit 'content' mount plus a symlinked 'projectcontentroot' mounted at content/project-a, checked via site.GetPage), covers the symlinked-parent and single-file cases, and keeps the negative assertions that theme symlinked mounts, in-tree symlinked assets, and the symlinked page are still dropped, which guards against the exemption leaking to directory contents. Patch B's test is adequate but narrower, covering only asset directory mounts. No flaws found in B beyond the gap above; A is the more complete fix with better tests.

The issue

View on GitHub

Hugo 0.166.0 introduced commit https://github.com/gohugoio/hugo/commit/938c820626bd0a524dc1482cbe83b6c2e1171d20 (hugofs: Drop symlinked mount roots) that breaks a legit use-case of symlinks.

In my case, I mount a directory in my hugo.yaml:

module:
  mounts:
    - source: "content"
      target: "content"
    # Mount content generated in another repository
    - source: "_build/includes/project-a"
      target: "content/project-a"

_build/includes/project-a itself can be a symlink to another local directory, e.g. ../../../project-a, which allows quick local debugging. In production, a CI workflow may clone the Git repo of project-a to this destination which does not trigger the problem.

I am not familiar with the internals of hugofs and the security concept, but would appreciate if users could trust certain mounts, and therefore bypass the newly introduced hard drop of symlinks.
