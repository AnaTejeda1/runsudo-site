Telegram send rich message deletes transitions to a new line!

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Correctness: The issue is that single newlines in a Markdown rich message are collapsed, and the reporter expects them preserved as in Send Text (Markdown). Patch A fixes this by default on the shared sendRichMessage/sendRichMessageDraft path, converting single newlines into CommonMark hard breaks (two trailing spaces) while leaving blank lines, fenced code, and existing hard breaks alone. Trailing-space hard breaks are the canonical Markdown mechanism and degrade to a no-op where a hard break is not meaningful (end of headings, list items, table rows), so the worst case is unchanged output. Patch B gates the fix behind a new 'Preserve Line Breaks' additional field that defaults to false, so out of the box the reported behaviour is unchanged; the issue's exact scenario with default options still produces jumbled lines. B also relies on inserting raw `<br>` tags into Markdown, whose failure mode (if Telegram's Markdown doesn't accept raw HTML) is literal '<br>' text in messages, a worse outcome than A's no-op. Tests: both add real unit tests that would fail before and pass after; A covers the issue text verbatim plus CRLF, fences, and the draft operation; B's tests are extensive but mostly exercise heuristics the issue never asked for. Scope/risk: B adds ~190 lines of regex heuristics (tables with/without pipes, nested blockquotes, backtick-run counting for multi-line code spans, HTML block-tag lists, '#hashtag' treated as heading, HTML paragraph doubling) based on unverified assumptions about Telegram's parser; this surface area adds risk and obscures the core fix, and the HTML-mode rewriting is beyond the ask. A is small, clearly documented, and matches surrounding conventions. Independent tests crashed on all trees and provide no signal, but the first scenario explicitly requires default options, which only A satisfies.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Each saw the issue and the two patches, labelled A and B in random order (two of them saw ours as A), with issue links and version numbers removed.
