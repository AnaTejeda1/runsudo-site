Add encoding.HexDecode/Encode

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

The core implementations are functionally identical. Both add `HexDecode` and `HexEncode` to the encoding namespace using `cast.ToStringE` plus `encoding/hex`, and both register method mappings with examples. Both let users build an SRI hash via `crypto.SHA256 | encoding.HexDecode | encoding.Base64Encode` without creating a resource, so correctness is a wash. The difference is in testing and completeness. Patch B's unit tests cover more edge cases: uppercase hex, empty input, a non-string numeric input (42), invalid characters ('zz') and odd-length input ('abc'). Its integration test is placed in the encoding package and checks encode, decode, roundtrip and a hardcoded SRI value; that value is the correct base64 of SHA-256('Hello world'). It also has an integration test for the invalid-hex error path. Patch A's unit tests have only one positive and one error case each. Its integration test does compare the computed SRI against `fingerprint`'s `Data.Integrity`, which is a nice equivalence check. However, it lives oddly in `decorator_integration_test.go` and involves unrelated machinery (custom output formats, `hugo.Store`, `templates.Inner`), which obscures what is being tested. Patch B also adds user documentation, including the SRI use case that motivated the issue. Overall B has broader edge-case coverage, better test placement and docs, with no added risk.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The issue

View on GitHub

See https://github.com/gohugoio/hugo/issues/15060#issuecomment-4790405347

It's clumsy that you need to create a resource (making up an unique filename) to get a SRI hash.

I suggest we add crypto.Fingerprint with a similar signature to https://gohugo.io/functions/resources/fingerprint/

hash.Fingerprint [ALGORITHM] any -> string

The function name is a little clumsy, but we need to keep the two very similar functions in line.

Where any typically is a string (but can also be a Resource -- we have similar unwrappers elsewhere).

It would then return e.g. sha256-Yuh...rfE=.

Note to implementer: There's some obvious code reuse potential here.
