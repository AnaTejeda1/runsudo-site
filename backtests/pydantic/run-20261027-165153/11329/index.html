Bug: false Unexpected keyword argument in pydantic.mypy plugin (in very specific case)

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches attack the same root cause: a subclass's transform runs while the plugin has started but not finished the base model (deferred because of unresolved forward refs in an import cycle), so the base's fields and extra='forbid' config are missing from the generated __init__/model_construct signatures. Both mark the base's TypeInfo metadata at the start of transform and make the subclass defer when it sees a marked-but-unfinished base, falling through on the final iteration. On the core scenario they are equivalent.

B is slightly more robust in the details. It removes the 'incomplete' marker when the transform completes (and explicitly on the final iteration when fields can't resolve), so the check is a true in-progress flag rather than A's permanent tag combined with an absence-of-METADATA_KEY test; that also covers the case where a base is re-transformed after its metadata was already stored. B calls defer() right where it returns (None, None), keeping the deferral paired with the wait, whereas A relies on the caller to defer. Neither leaves stale state in the cache in practice.

Tests: A adds a compact two-module cycle test that would fail before (missing inherited 'name') and asserts the real error ('nam') still fires, which is adequate, but it also edits pyproject's codespell ignore list purely to accommodate the test's typo, which is unrelated churn. B reproduces the issue's actual structure (forbid base, Node with Annotated tagged union, Circle/Square in sibling modules, TYPE_CHECKING imports) and checks valid inherited-field calls produce no errors, that extra='forbid' still rejects unknown kwargs, and that model_construct gets the inherited/own field types right. One oddity in B's test is that Square derives from Node while Circle derives from BaseShape, but that doesn't weaken it. Independent tests were all skipped and provide no signal.

Overall B wins on marginally better state handling and a more faithful, broader test, with A carrying a small unrelated config change.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Description

Summary: In a particular scenario using a base class with ConfigDict(extra="forbid"), recursive models (in my case with tagged unions) can result in a false Unexpected keyword argument mypy error on the subclasses.

Example code

This issue is best explained demonstrated with an actual repo, so I created a mwe repo (which models a simple node graph) here: https://github.com/tlambert03/pydantic-mypy-err

git clone https://github.com/tlambert03/pydantic-mypy-err.git
cd pydantic-mypy-err

pip install mypy==1.14.1 pydantic==2.10.5
mypy example.py

Apologies that this can't be summed up in a simpler example, but hopefully that MWE should immediately demonstrate the problem and allow you to play with some variations.

This file contains the most interesting config, and is reproduced here:

from typing import TYPE_CHECKING, Annotated, ClassVar

from pydantic import BaseModel, ConfigDict, Field

if TYPE_CHECKING:
    from .circle import Circle

    # note, if square were defined after Node in THIS file, mypy is happy.
    from .square import Square

    # Note: without this additional base with extra="forbid" mypy is happy.

AnyNode = Annotated["Circle | Square", Field(discriminator="node_type")]


class Node(_MyBase):
    name: str | None = Field(default=None, description="Name of the node.")
    parent: AnyNode | None = None
