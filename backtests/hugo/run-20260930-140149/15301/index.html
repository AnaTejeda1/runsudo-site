Improve/document security.http.urls override behavior

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

The issue asks to improve or document how a custom `security.http.urls` disables the dial-time resolved-address check (`CheckAllowedHTTPAddress`).

Patch B addresses this directly:
- It documents the behavior in security.md: the default value enables resolved-address validation, any deviation from the default disables it, and custom patterns should be narrow and anchored.
- It adds a clarifying code comment.
- It adds a `reason` to `AccessDeniedError`, so a dial-time denial now says why it happened and notes that a custom urls setting disables the check. Before, the error was confusing because the URL itself had passed the allowlist.
- Its tests are meaningful. They check that the new message appears for address denials and not for URL-text denials, that changing other http settings keeps the check, and that a custom urls value disables it. The message assertions would fail before the change.

Patch A also adds similar documentation for `http.urls`. However, most of the patch is a new `security.http.proxyFromEnvironment` feature that the issue does not request. It sets `base.Proxy = nil` by default, which silently stops honoring HTTP_PROXY/HTTPS_PROXY for all users. That is a notable behavior change and will break proxied corporate or CI environments. It also brings in a new `httpproxy` dependency, a custom `RoundTripper`, context-key plumbing and a hand-rolled `canonicalAddr` mirror of net/http internals, all of which add maintenance risk. The proxy test is solid, but it tests the extra feature rather than the issue's ask.

Patch A's scope expansion adds real risk and obscures the documentation fix. Patch B is focused, low-risk, and improves both the docs and the user-facing error. B is the better fix.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The issue

View on GitHub

In d6e6f9e500eebdeae8e28de830fff2e3bfc7d534 (unreleased) we added a dial-time URL validation to catch URLs that's valid according to the whitelist but that resolves to a loopback, private or link-local IP addresses. That check is skipped it if the user has a custom security.http.urls setup, as it would not make sense to block local development servers.

See CheckAllowedHTTPAddress.

This has been reported by @Reload3d as a potential security issue, and while I think the current behaviour is the pragmatic correct approach, I'm creating this issue for visibility and to see if this can be improved further (e.g. better documentation).

What the agent reported

I kept the current behaviour (a custom security.http.urls still turns off the resolved-address check) and made it visible in the error message, the docs and the code comment. The new test fails without the change and passes with it, but only in my offline go test runs. ./bt-test never ran any tests: it failed three times with [setup failed] because the test box can't download Go modules (lookup proxy.golang.org … server misbehaving, later Forbidden).

What was wrong. Nothing was broken. CheckAllowedHTTPAddress blocks connections where an allowed URL resolves to a loopback, private or link-local address, but only when security.http.urls is the default. That exception wasn't documented. And when the check did block something, the error just said "169.254.169.254" is not whitelisted in policy "security.http.urls". That's confusing, because the URL itself had passed the allowlist.

What I changed

  • config/security/securityConfig.go:
  • AccessDeniedError has a new optional reason. Only the blocked-connection error sets it: "the URL's host resolved to a non-public (e.g. loopback, private or link-local) address, which the default policy blocks; a custom security.http.urls disables this check".
  • Every other denial message (exec, getenv, URL text, methods, allowContent) is unchanged.
  • The code comment now says that any value that differs from the default, even one that only adds a host, turns the check off, so custom patterns should stay narrow.
  • docs/content/en/configuration/security.md: the http.urls entry now explains:
  • With the default value, Hugo refuses to connect when an allowed URL's host resolves to a non-public address (e.g. 169.254.169.254).
  • Changing the setting turns that check off, leaving the allowlist as the only protection.
  • Keep patterns anchored and narrow, and avoid .* when building untrusted content.
  • config/security/securityConfig_test.go: new test TestCheckAllowedHTTPAddressCustomURLs. It checks that the default config blocks 169.254.169.254:80 with the new explanation, and that URL-text denials don't get it. It also checks that changing only http.methods keeps the check, while a custom urls = ['^http://localhost:1313/'] lets 127.0.0.1:1313 and 169.254.169.254:80 through.

Test evidence. I ran go test directly with GOMODCACHE=/bt/cache/go-mod GOPROXY=off, a module cache I found on the machine:

  • Before the change: the new test fails with no substring match found … want: "resolved to a non-public".
  • After the change: ok github.com/gohugoio/hugo/config/security (all tests), and ok github.com/gohugoio/hugo/hugolib for -run TestSecurity, the other tests that match on the error text.
  • resources/resource_factories/create: TestGetRemoteHead and TestGetRemoteResponseHeaders fail both with and without my change, because they fetch https://gohugo.io and there's no network (Forbidden).
