The Feature

Add x-litellm-trace-id to LiteLLM Proxy HTTP responses whenever the request has a recording OpenTelemetry server span. Its value should be the root trace ID as a 32-character lowercase W3C trace ID

The response already includes x-litellm-call-id, but a gateway user who receives that ID cannot reliably open the exact trace that handled the request. The proposed response header would make a client response, the request trace, and the existing call ID directly navigable across tracing and logging backends

For any response that has both values, the root server span should also carry the same litellm.call_id as x-litellm-call-id. This establishes an explicit relationship between the response, root span, and downstream LLM spans

Expected behavior:

  1. Return the header on successful JSON responses and the initial headers of streaming responses
  2. Return the header on validation, authentication, authorization, rate-limit, provider, and unhandled-error responses
  3. Preserve incoming traceparent propagation and return the resulting request trace ID
  4. Omit the header when OpenTelemetry is disabled or no recording request span exists
  5. Keep x-litellm-call-id behavior unchanged

This is a LiteLLM Proxy / AI Gateway feature only. It does not change the Python SDK or WebSocket behavior

Related: #31864 covers request identity in JSON logs. This request covers the gateway HTTP response and its OpenTelemetry root span

User Flow

Before this feature (today): a gateway developer investigating a failed model request reaches the response's call ID but cannot navigate directly to the trace that handled it

  1. They send POST https://gateway.example.com/v1/chat/completions with their model and messages
  2. The gateway returns 400 Bad Request or a provider error with x-litellm-call-id: 7ac48d62-40a1-44e6-8b50-19da641835a5
  3. They search the observability backend for that call ID and manually inspect matching LLM spans, logs, or request time ranges to identify the parent request trace
  4. Their workaround is to correlate timestamps and child-span fields, which is slow and ambiguous when several retries or requests are in flight

After this feature (ideal user flow): the same developer can open the exact request trace from the gateway response

  1. They send the same POST https://gateway.example.com/v1/chat/completions with the same model and messages
  2. The gateway returns the same status and x-litellm-call-id, plus x-litellm-trace-id: af353cab815b907430a117c9b97b4d0e
  3. They paste af353cab815b907430a117c9b97b4d0e into their observability backend and open the one server trace for that gateway request
  4. They use the call ID visible on that trace to correlate request logs and downstream model spans without matching timestamps by hand
