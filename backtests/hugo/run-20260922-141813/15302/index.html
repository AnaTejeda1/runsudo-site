Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both add the `proxyFromEnvironment` flag defaulting off and both correctly disable the environment proxy in the default case, so the default hardening is equivalent. The decisive difference is the opt-in path. Patch A, when the flag is enabled, leaves the cloned transport's `base.Proxy = http.ProxyFromEnvironment` but keeps the same `Control`/`CheckAllowedHTTPAddress` dialer for every dial. Since a proxied request is dialed to the proxy address, the dial-time address check then runs against the *proxy*, so a proxy on a loopback or private address is rejected. That is exactly the scenario the issue names ('HTTPS_PROXY set on users machine or in CI') — a localhost/internal proxy — so Patch A's opt-in fails to actually let those users through under the default allowlist; it re-enables the proxy but re-blocks it. Patch B builds a per-request proxy resolution (proxyTransport + context-carried proxy URL + canonicalAddr) so the dial to the proxy bypasses the address check (the user has opted into trusting the proxy), while direct/NO_PROXY dials — and even a direct dial to the proxy's own address — remain validated, closing the obvious hole. This resolves the root cause for the described case. Tests: Patch A only asserts `tr.Proxy == nil`/`!= nil`, a near-tautological field check that would not catch the loopback-proxy failure; Patch B stands up real httptest proxy and target servers and asserts default-ignored, enabled-via-loopback-proxy, and still-denied direct loopback dials — tests that genuinely fail before and pass after and exercise the security boundary. Patch B is larger and adds user-facing docs (security.md, docs.yaml) and an httpproxy dependency, but the docs are appropriate for a new security config option and the complexity is proportionate to correctly handling internal proxies. Patch A is more surgical and lacks docs, but its incompleteness on the core scenario outweighs its smaller footprint. B wins on correctness and tests.

This is a security hardening issue.

In d6e6f9e500eebdeae8e28de830fff2e3bfc7d534 (unreleased) we added a dial-time URL validation.

If proxied (e.g. HTTPS_PROXY set on users machine or in CI) the above validation will only see the proxy address. There's no workaround for that, but I suggest by adding a new security.http.proxyFromEnvironment bool config flag (default disabled).

Thanks to @Reload3d for reporting this issue.

What the agent reported

The fix is complete, reviewed, and the gate passes. Here is the final report.

What was wrong

Commit d6e6f9e5 (unreleased) added a dial-time destination-address check (CheckAllowedHTTPAddress, installed as a net.Dialer Control hook in newSecureBaseTransport) so that a hostname resolving to an internal address can't reach internal endpoints via resources.GetRemote. But Hugo's HTTP transport is a clone of http.DefaultTransport, whose Proxy is http.ProxyFromEnvironment. When a proxy is configured in the environment (HTTPS_PROXY, etc., common in CI), the dialer connects to the proxy address, so the dial-time check only ever validates the proxy — silently bypassing the protection with no workaround.

What I changed

  1. config/security/securityConfig.go — Added a new field to the HTTP struct: go ProxyFromEnvironment bool `json:"proxyFromEnvironment"` with a doc comment. Default is the zero value false (DefaultConfig unchanged), so the environment proxy is disabled by default and DecodeConfig picks it up automatically.
  1. resources/resource_factories/create/create.go — In newSecureBaseTransport, gated the cloned transport's proxy: go if !sec.HTTP.ProxyFromEnvironment { base.Proxy = nil } By default this forces direct dials, so the dial-time address check sees the real destination. Setting the flag re-enables the environment proxy for users who need it.

Test evidence

  • resources/resource_factories/create/proxy_test.go (new) — TestNewSecureBaseTransportProxyFromEnvironment: with default config asserts tr.Proxy == nil; with the flag set asserts tr.Proxy != nil. The default-case assertion fails on pre-change code (where Proxy was http.ProxyFromEnvironment, non-nil), so it is a genuine regression guard for the exact reported scenario.
  • config/security/securityConfig_test.go — added TestDecodeConfigHTTPProxyFromEnvironment (default false; true when set via TOML); updated the TestToTOML golden string to include proxyFromEnvironment = false in alphabetical order (mechanical, no existing assertion weakened).
  • Gate: ./bt-test ./config/security/... ./resources/resource_factories/create/... → exit 0. All new and pre-existing tests pass.
  • Reviewer confirmed correct implementation, default-safe posture, meaningful test, no scope creep or scratch files.

Requirements disposition

  • Add security.http.proxyFromEnvironment bool config flag — ✅ Implemented (securityConfig.go), verified by TestDecodeConfigHTTPProxyFromEnvironment and TestToTOML.
  • Default disabled (false) — ✅ Implemented (zero value; not present in DefaultConfig), verified by default-case assertions in both new tests.
  • When disabled, the environment proxy must not be honored (so the dial-time check isn't bypassed) — ✅ Implemented (create.go sets base.Proxy = nil), verified by TestNewSecureBaseTransportProxyFromEnvironment (default Proxy == nil; opt-in Proxy != nil).
