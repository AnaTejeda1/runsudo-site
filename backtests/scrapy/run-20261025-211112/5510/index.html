Support per-request download handler override

Worse

The merged fix was judged better than our patch.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches resolve the issue: the independent tests pass on both, and each lets a request pick a handler different from its scheme handler without routing other requests through it. The difference is in design coherence and completeness.

Patch A integrates the feature into the existing handler machinery: a `DOWNLOAD_HANDLERS_BY_NAME` setting registers handlers under names, the `download_handler` meta key selects by name (or by an existing scheme), lookups reuse the same `_get_handler`/`_load_handler` path (so lazy/skip_lazy, NotConfigured memoization, old-style handler detection and `_close` all work unchanged), clashes between the two settings are rejected, and named handlers are explicitly kept from becoming downloadable URL schemes. It also handles a real consequence of the feature that B ignores: the default fingerprinter now distinguishes requests that differ only by handler, so a request routed to e.g. a browser handler is not dropped as a duplicate of the same URL fetched normally. Tests cover the clash, name-in-meta, scheme-in-meta, unknown ID, the scheme/name separation, fingerprint caching after meta mutation and the robots propagation. The robots.txt inheritance is a debatable policy choice, but it is documented with an escape hatch and does not break anything.

Patch B puts a class object or import path directly in request meta and builds a parallel subsystem: three new dicts (`_meta_handlers`, `_meta_notconfigured`, `_meta_old_style_handlers`), a copy of `_load_handler`'s try/except/warn block, a copy of the old-style dispatch in `_download_with_meta_handler`, instance-reuse-by-class heuristics spliced into `_load_handler`, and identity dedup in `_close`. That duplication is the kind that drifts. It also leaves dedup unaddressed, so two requests to one URL with different handlers collide in the dupefilter. B's tests are thorough for the module (reuse, close, NotConfigured, buggy, invalid path, end-to-end crawl), which is a genuine strength, but they test a more fragile design.

On correctness both fix the issue; A additionally handles the fingerprint interaction. On scope A's setting and fingerprint changes are larger but purposeful; B's extra reuse logic adds complexity without a clear need. On craft A is cleaner and consistent with the surrounding code. A wins.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Each saw the issue and the two patches, labelled A and B in random order (two of them saw ours as A), with issue links and version numbers removed. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours. The reasoning above is one judge's, shown verbatim.
