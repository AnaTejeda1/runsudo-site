SSR memory leak after a render error in a dynamic component

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches address the core mechanism. In SSR, a dynamic `<component :is>` is rendered in vnode mode. `renderSlot` calls `openBlock()`, the slot throws, and `currentBlock` is left pointing at a stale array that keeps collecting every vnode created afterwards.

Patch B fixes this precisely where blocks are opened. It unwinds to the previous stack depth in `renderSlot` and `withCtx`, which also covers inline `v-if` blocks. That is a targeted, low-risk fix for the reported scenario. It does nothing for the other retention paths a render error leaves behind:
- the dev warning-context stack is never popped;
- `currentRenderingInstance` stays set after a rethrown render-function error;
- the setup `currentInstance` is not restored;
- SSR watcher handles are never stopped when rendering rejects.

B's test only checks apps created after the failure and uses `expect().rejects`, so it never verifies that the failed app itself is collected.

Patch A attacks the problem at the SSR boundary. It resets the block stack, now correctly clearing `currentBlock` too; the old `blockStack.length = 0` in `renderComponentRoot` left `currentBlock` stale. It also makes cleanup exception-safe: `popWarningContext` in `finally`, restoring the rendering instance when `handleError` rethrows, `resetTracking`/`reset` in `finally` around `setup`, and stopping watchers on failure in both `renderToString` and the stream path.

Resetting the whole stack on an `ssrRender` throw is safe, because the error aborts the synchronous render anyway. A's test matrix is much stronger:
- six failure shapes (slot of a dynamic component, `v-if` branch, plain template, render function, child setup, sync watcher on shared state);
- both `renderToString` and stream rendering;
- the failed app itself is included in the `WeakRef` set.

A is broader, but every addition targets the same class of bug (render-error leaks) and adds little risk. A wins on robustness and test coverage.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Steps to reproduce

  • download the reproduction from stackblitz (won't work there, needs to be run locally)
  • run pnpm i && pnpm leak
  • see the heap size & alive app instances grow with each request after the single failed render

The script renders 500 fresh SSR apps, which all get garbage-collected. Then renders one app whose slot content throws, then renders 500 more identical healthy apps, which will never be garbage collected afterwards.

A dynamic component <component :is> with a <slot /> is needed for this to reproduce.

Card

<script setup>
    defineProps({ tag: { type: String, default: 'div' } })
</script>

<template>
    <component :is="tag" class="card">
        <slot />
    </component>
</template>

app:

<script setup>
    defineProps(['payload'])  // one request renders with `payload: null` → throws
</script>

<template>
    <main>
        <Card>{{ payload.title }}</Card>
    </main>
</template>

What is expected?

A failed renderToString should not affect subsequent renders and all apps rendered after it should get garbage collected.

What is actually happening?

Every app created after the single failed render is kept in memory forever.
