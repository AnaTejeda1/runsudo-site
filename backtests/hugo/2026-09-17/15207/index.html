Issue #15207 Merged fix PR # Run 17 Sep 2026 gohugoio/hugo

panic: slice bounds out of range in contentNodeShifter.Delete when removing draft pages from a multilingual taxonomy

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the immediate panic — the classic 'mutate the slice while ranging it by index' bug (`v = append(v[:i], v[i+1:]...)` inside `for i, nn := range v`), which produces exactly the reported `slice bounds out of range [5:4]` when 2+ elements delete. But they differ sharply on completeness of the root-cause fix.

Correctness (decisive): The original code's in-place `append` was an attempt to shrink the stored slice, yet the tree never re-inserts, and the mutated local header never propagates back — so even pre-panic, the multi-node path corrupted the tree (stale/duplicate entries). Patch B recognizes this: it threads an `updated` node out of `Delete`/`DeleteFunc` and has `NodeShiftTree.delete`/`DeleteFuncRaw` re-`Insert` the remaining nodes (or `Delete` the key when empty). This actually removes the deleted node from the tree while keeping the others. Patch A only builds a local `kept` slice to compute emptiness but never updates the tree at all in the non-empty case, so the deleted node stays in the tree structure (relying solely on `MarkStale` downstream) — a weaker, symptom-level fix that abandons the original delete-from-tree intent. Crucially, Patch A also leaves the *identical* mutate-during-range bug untouched in `DeleteFunc`'s `contentNodes` case (`ss = append(ss[:i], ss[i+1:]...)`), which can panic the same way on the DeleteFunc path; Patch B fixes that too.

Tests: Patch A's test is valid and would panic pre-fix (5 all-matching nodes), but only asserts `deleted` length and `isEmpty`. Patch B's test additionally verifies the `remaining`/`updated` slice contents and the identity of surviving nodes, plus delete-all and delete-none cases, and updates the doctree `testShifter` to the new signature — directly exercising the correctness semantics that are the actual fix. Both are non-tautological regression tests.

Scope: This is the one axis favoring A — Patch B changes the `Shifter` interface signatures for `Delete`/`DeleteFunc` and ripples through `nodeshifttree.go` and the test shifter, which is more surface area. But that churn is the necessary cost of the complete fix (returning the updated node), not incidental refactoring, and the diff appears to update every affected implementation/caller.

Craft: Patch B's naming (`updated`/`remaining`/`deleted`) and updated doc comments are clear and consistent with the surrounding code. Since correctness is the top-weighted criterion and Patch B fixes the actual root cause across both the panic and the tree-staleness in both Delete and DeleteFunc, it is the better fix despite being larger.

What I ruled out

Site: 8 languages, ~1,490 pages per language, ~11,455 content files, categories taxonomy.

  • Not a regression. 0.159.1 and 0.164.0 behave identically.
  • Not the number of drafts. 96 draft pages build fine; 16 panic.

Swapping page content at a fixed path isolates it to front matter. So the trigger is combinatorial: some particular set of pages being deleted from one taxonomy term corrupts the shifter, rather than any single page being malformed.

What the agent reported

The reviewer confirms the fix is correct, minimal, and well-covered. Done.

What was wrong

hugolib/content_map_page_contentnodeshifter.go — in contentNodeShifter.Delete, the case contentNodes: branch mutated the very slice it was ranging over:

for i, nn := range v {
    if vv, ok, _ := s.Delete(nn, vec); ok {
        deleted = append(deleted, vv)
        v = append(v[:i], v[i+1:]...)   // shrinks v while range keeps counting to the original length
    }
}

range captures the slice length once. After the first deletion v is shorter, but i keeps climbing to the original last index, so v[i+1:] eventually slices past the end — panic: slice bounds out of range [5:4]. This fires exactly when 2+ pages are dropped from one node (multiple drafts / future publishDate pages sharing a taxonomy term), which is why hugo -D builds fine but a production build panics. It also silently skipped elements even when it didn't crash.

What I changed

hugolib/content_map_page_contentnodeshifter.go (only the contentNodes branch) — range by value into two fresh slices instead of mutating during iteration:

case contentNodes:
    var deleted contentNodes
    var kept contentNodes
    for _, nn := range v {
        if vv, ok, _ := s.Delete(nn, vec); ok {
            deleted = append(deleted, vv)
        } else {
            kept = append(kept, nn)
        }
    }
    if len(deleted) == 0 {
        return nil, false, false
    }
    return deleted, true, len(kept) == 0

Return semantics are preserved: the deleted node(s), true when anything was deleted, and len(kept)==0 as the "node now empty" signal that NodeShiftTree.delete uses to drop the tree key.

hugolib/content_map_page_contentnodeshifter_test.go (new) — regression test TestContentNodeShifterDeleteMultipleFromContentNodes with "all match" (5 deleted → empty) and "some match" (3 of 5 deleted → not empty) subtests, both deleting 2+ elements from a contentNodes slice.
