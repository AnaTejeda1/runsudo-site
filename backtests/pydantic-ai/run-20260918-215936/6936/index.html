The issue

View on GitHub

Description

safe_download connects to a resolved IP while preserving the logical hostname in Host and SNI. HTTPX therefore stores response cookies against the IP request URL. If a redirect target has a different hostname on the same IP, the cookie jar can replay the first host cookie to the second host.

A probe with a real httpx2.AsyncClient and MockTransport reproduced this. This is separate from #6810, which covers caller-configured headers.

Expected behavior

Server-set cookies must follow logical URL cookie semantics rather than resolved-IP identity. Cookies must not cross host, domain, public-suffix tenant, path, or Secure boundaries, while valid same-host and domain/subdomain redirects must continue to work. Cookies are not isolated by port, and non-Secure cookies are not isolated by scheme.

Chosen fix

Use a logical-URL cookie jar inside safe_download, with strict host-only matching and Public Suffix List-aware Domain= handling. Apply and extract cookies against the validated logical URL, then clear HTTPX resolved-IP jar after every response. Caller-supplied Cookie headers retain precedence and the existing redirect stripping policy.

What the agent reported

The fix is complete and verified. Here is my final report.

What was wrong

pydantic_ai._ssrf.safe_download connects to a DNS-resolved IP while carrying the logical hostname only in the Host header and TLS SNI. HTTPX (httpx2) keys its per-client cookie jar on the request URL — which is the resolved-IP URL. So when host A returned a Set-Cookie during a redirect and the redirect target host B resolved to the same IP, httpx treated both hops as the same origin (the shared IP) and replayed A's cookie to B. Server-set cookies escaped their logical-host scope. (Distinct from #6810, which covers caller-configured headers — that policy was left untouched.)

What I changed

pydantic_ai_slim/pydantic_ai/_ssrf.py only (production), purely additive:

  • Added a per-call logical-URL cookie jar (_new_logical_cookie_jar) built on httpx2.Cookies with a custom _LogicalCookiePolicy(http.cookiejar.DefaultCookiePolicy).
  • In the redirect loop: cookies are extracted from each response (_store_logical_cookies) and applied to each request (_logical_cookie_header) against the validated logical URL (current_url), never the IP URL.
  • After every response, httpx's resolved-IP jar is cleared (client.cookies.clear(), guarded by isinstance(client.cookies, httpx2.Cookies) — always true in production; a no-op only for the file's client mocks).
  • _LogicalCookiePolicy.set_ok_domain refuses a Domain= naming a public suffix (_is_public_suffix + a curated _PUBLIC_SUFFIXES subset; single-label TLDs handled algorithmically). Host-only, path, and Secure boundaries come from DefaultCookiePolicy; port is not isolated and non-Secure cookies are not scheme-isolated, per spec.
  • Caller-supplied Cookie retains precedence: the jar only fills a Cookie header when the caller left it unset; the existing sensitive-header redirect-stripping policy is unchanged.

tests/test_ssrf.py: new TestServerSetCookieIsolation class (real httpx2.AsyncClient + MockTransport, matching the report's probe).

Test evidence

  • Before the fix: test_set_cookie_not_replayed_across_host_boundary failed (assert 'session=leak' is None) and test_domain_cookie_shared_with_subdomain failed (assert None == 'session=ok') — the exact reported leak plus the collateral drop of legitimate subdomain sharing.
  • After the fix: ./bt-test tests/test_ssrf.py tests/test_web_fetch.py → 298 passed (includes the SSRF suite, the new cookie tests, the redirect/sensitive-header suites, and the downstream web_fetch consumers).

Honest note on coverage: two new tests are true fail-before/pass-after regressions (host boundary, subdomain sharing). The other four (same_host_redirect_keeps_server_cookie, public_suffix_cookie_not_shared_across_tenants, secure_cookie_not_sent_over_http, caller_cookie_takes_precedence_over_server_cookie) pass on the pre-fix baseline too — because the old IP-keyed jar coincidentally produced the same observable outcome for those specific cases (it dropped all Domain= cookies and shared only host-only cookies). I kept them as guard tests: each exercises the new code and pins a report-required boundary (a public-suffix/Secure/precedence regression within the fixed code would fail its test), and they guard against over-isolation. It is structurally impossible to write a fail-before public-suffix test in this same-IP harness, since the baseline drops every Domain= cookie — so a guard test is the only available coverage for that required boundary.
