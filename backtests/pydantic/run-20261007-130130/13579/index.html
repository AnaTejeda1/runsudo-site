Allow arbitrary core schemas for serialization

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Patch A fixes the issue directly. It adds an explicit `SchemaSerSchema` (`{'type': 'schema', 'schema': CoreSchema}`) with a `schema_ser_schema()` helper and registers it in `SerSchema`. It also adds it to the self-schema in `self_schema.py`, so schema validation accepts it. In Rust it builds a full serializer from the inner schema via `CombinedSerializer::build`, so nested `serialization` keys, definitions and polymorphism are respected. It then does what the issue's TODO asks: it replaces the identity wrap-serializer workarounds in `ValidateAs`, `SkipValidation`, `InstanceOf`, `PlainValidator` and the OrderedDict/defaultdict mapping schema. It also teaches `GenerateJsonSchema.ser_schema` about the new type, so serialization-mode JSON schemas keep working. Tests cover pydantic-core behaviour (lists, models with exclude, definition refs, nested serialization, typed-dict field exclusion, wrong-type warnings, missing or invalid inner schema). On the pydantic side they check that the new ser type is emitted and that dumps and JSON schemas still match, and they would fail before the change.

Patch B instead makes any core schema a valid `serialization` value by routing every non-special type through `build`. This creates an inherent ambiguity: `function-plain`/`function-wrap` validator schemas collide with the function ser schemas. B acknowledges this and needs a separate `as_ser_schema` helper to work around it. B does not update `self_schema.py`, so with schema validation active, arbitrary core schemas in `serialization` would likely be rejected. It also does not update `GenerateJsonSchema.ser_schema` to handle arbitrary core schemas, so serialization-mode JSON schema would silently fall back. Crucially, B never replaces the workaround: it only rewrites the TODO comment and leaves the wrap serializer in `ValidateAs` and elsewhere. It also adds unrelated churn and risk: a stringified `SerSchema` TypeAlias, a `Union` with noqa, a rewrite to `match` statements, and a `cast`.

On correctness, completeness and scope, A is the cleaner and more complete fix.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The issue

View on GitHub

As per the TODO in https://github.com/pydantic/pydantic/pull/13487:

There is currently no way to tell pydantic-core "serialize this value using this core schema". SerSchema is:

SerSchema = Union[
    SimpleSerSchema,
    PlainSerializerFunctionSerSchema,
    WrapSerializerFunctionSerSchema,
    FormatSerSchema,
    ToStringSerSchema,
    ModelSerSchema,
]

The only member that expresses "use this schema" is SimpleSerSchema, and it does not take a schema at all, only a name from a closed literal:

ExpectedSerializationTypes = Literal[
    'none', 'int', 'bool', 'float', 'str', 'bytes', 'bytearray', 'list', 'tuple',
    'set', 'frozenset', 'generator', 'dict', 'datetime', 'date', 'time', 'timedelta',
    'url', 'multi-host-url', 'json', 'uuid', 'any',
]

class SimpleSerSchema(TypedDict, total=False):
    type: Required[ExpectedSerializationTypes]

So an arbitrary schema (a model, a dataclass, list[int], a TypedDict, anything constructed by the schema generator) cannot be used directly. Every place in Pydantic that needs it works around the gap the same way: it wraps the schema in a wrap serializer whose function is the identity, purely so the schema can ride along in the schema argument.
