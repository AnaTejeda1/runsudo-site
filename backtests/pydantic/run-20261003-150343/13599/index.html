PEP 695 type aliases don't work with callable discriminators

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the root cause the same way. They pass `definitions` from `apply_discriminator()` into `Discriminator._convert_schema()`, so definition-refs created by PEP 695 aliases can be resolved when the discriminator is applied through `Field(discriminator=...)`. Both would fix the M3 case in the issue.

The differences show up at the edges:

1. **Recursive or forward-referenced aliases.** Patch B handles an alias choice whose definition isn't available yet by raising `MissingDefinitionForUnionRef`. This lets the discriminator application be deferred, mirroring `_ApplyInferredDiscriminator._handle_choice()`. Patch A falls through to the `Tag not provided` `PydanticUserError` instead, so recursive alias cases are likely to fail with a misleading error rather than being deferred.

2. **Behavior when nothing can resolve the ref.** Patch A drops the `handler is not None` guard on the root definition-ref check. When both `handler` and `definitions` are None, it now raises `MissingDefinitionForUnionRef`, which is a behavior change from before. Patch B keeps that path guarded.

3. **Choice handling.** Patch B leaves the choice as a reference and only reads tag metadata from the resolved definition. Patch A replaces the choice with the inlined definition schema, which is less faithful to reference semantics in the deferred path.

**Tests.** Patch A adds one basic test for the issue scenario. Patch B adds that scenario plus coverage for:
- a generic alias with type params,
- alias-typed union members,
- invalid-tag errors,
- two recursive alias cases that exercise the new deferral path.

These tests would fail before the change and meaningfully cover the edges.

**Craft.** Patch B also simplifies the tag logic and documents the method. Overall, Patch B is more correct at the edges and much better tested.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Description

New type aliases prefixed with the type keyword are not supported as the type annotation for a callable discriminator.

M1, M2, M4 ok
M3

pydantic.errors.PydanticUserError: `Tag` not provided for choice {'type': 'definition-ref', 'schema_ref': '__main__.TaggedAnyA:2210408548368'} used with `Discriminator`

Example Code from #12843 also doesn’t work.
