Allow SingleAgentVoiceWorkflow to receive Runner context

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches make the identical core change: add a keyword-only `context` parameter to `SingleAgentVoiceWorkflow.__init__`, store it, and forward it to `Runner.run_streamed` on every turn. The independent tests confirm both fully resolve the issue (all eight pass on A and B), so correctness is a wash. The differences are in tests and craft. Patch B's test directly exercises every scenario the issue names: dynamic instructions, a context-dependent tool, a handoff `is_enabled` predicate, a second turn after the current agent changes via handoff, identity of the context object across turns, and a separate test enforcing keyword-only. Patch A's test covers only a tool over two turns and, more worryingly, imports `tool` from `agents.decorators`, which is not the visible public decorator (`function_tool`, exported from `agents`, is what the rest of the codebase and Patch B use); if that module does not exist, the import would break collection of the whole existing test file. A's test also indexes `item["output"]` on a `TResponseInputItem` union, which is fragile under the repo's type checking. On craft, B keeps the existing `Agent[Any]` convention and types `context: Any | None` with a clear docstring stating it is forwarded as-is to `Runner.run_streamed`, matching the issue's 'normal Runner behavior' requirement. A swaps to `Agent[TContext]`/`TContext | None`, which reads as tighter typing but is a function-scoped TypeVar on a non-generic class whose values are stored on instance attributes, a slightly awkward leak rather than a real gain. Net: equivalent fix, but B has meaningfully stronger and safer tests and cleaner consistency with surrounding code.

Related: #819 documented this limitation and was later closed after the reporter worked around it by creating a custom VoiceWorkflowBase implementation. I could not find an existing PR that adds context support to SingleAgentVoiceWorkflow itself.

Describe the feature

SingleAgentVoiceWorkflow is the convenience path for a single-agent voice workflow, but its internal call is currently fixed to:

Runner.run_streamed(self._current_agent, self._input_history)

That means an agent that relies on normal Runner context cannot use the convenience workflow directly. Context-dependent instructions, tools, handoffs, and is_enabled predicates require users to copy the workflow implementation into a custom subclass just to pass context=....

A narrow API addition would be to accept an optional keyword-only context when constructing SingleAgentVoiceWorkflow and forward that same context to each internal Runner.run_streamed() call.

For example:

context = UserContext(user_id="user-123")
workflow = SingleAgentVoiceWorkflow(agent, context=context)
pipeline = VoicePipeline(workflow=workflow)

Desired semantics

  1. Existing SingleAgentVoiceWorkflow(agent) and SingleAgentVoiceWorkflow(agent, callbacks) calls remain unchanged.
  2. context= is optional and keyword-only.
  3. The supplied context is forwarded to every streamed Runner turn, including later turns after the workflow updates its input history/current agent.
  4. Context behavior remains the normal Runner behavior; the voice layer does not introduce a separate context wrapper or lifecycle.
  5. Custom VoiceWorkflowBase implementations remain the supported path for broader per-turn Runner customization.

Non-goals

  • no change to VoicePipeline.run() arguments;
  • no new voice-specific context abstraction;
  • no automatic copying or serialization of application context;
  • no broader RunConfig, session, or conversation-state API in this change.

This keeps the convenience workflow useful for context-dependent agents without expanding the voice pipeline contract.
