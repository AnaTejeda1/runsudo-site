Issue #12460 Merged fix PR #16120 Run 6 Nov 2026 · run-20261106-192752 vuejs/core

Directives mounted called after beforeUpdate

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches make the independent reproduction tests pass, so the decision rests on root cause versus workaround and on risk.

The reporter's diagnosis is that the queued `mounted` hooks run after a same-flush `beforeUpdate`, so the stale initial binding is restored into the input. Patch A fixes that ordering: it records the post-flush callbacks queued by a component's mount (`startMount`/`endMount`), and when that component updates later in the same flush it runs those pending mounted hooks, refs and subtree hooks first (`flushPendingMountCbs`), with a `WeakMap` so an element mounted during a parent's update and patched again in the same flush also gets `mounted` before `beforeUpdate`. The resulting order (`mounted:bug`, `beforeUpdate:ok`, `updated:ok`) matches the documented lifecycle, and it also corrects component `onMounted` and template refs, which suffer from the same ordering defect. The uid-based filter that keeps post watchers of earlier components out of the early run is a heuristic, but it is commented and tested, and I could not construct a scenario where it runs a callback for a non-descendant.

Patch B keeps the wrong order and instead rewires `invokeDirectiveHook` so a pending `mounted` is invoked with the latest vnode's bindings (`_mount`/`_latest` chain on vnodes, with a copied binding to reset `oldValue`). Its own tests codify `beforeUpdate 1 0` running before `mounted 1 undefined 1`, so a directive that initializes state in `mounted` and relies on it in `beforeUpdate` stays broken, and `mounted` now receives a vnode other than the one that was mounted with `prevVNode` null. It is a tidy, localized workaround and it also handles the Suspense-deferred variant that A deliberately skips, but that variant is outside the issue's scenarios, and the fix addresses the symptom (value) rather than the cause (order) named in the issue title.

On tests, both add meaningful, non-tautological tests that fail on base; A covers the directive, component lifecycle, element-patched-during-update and post-watcher-isolation paths plus v-model; B covers v-model text/checkbox, Suspense and inherited directives. On scope, A is a larger scheduler change that touches hot paths (an extra array push per post cb during a flush, a WeakMap lookup per patchElement, a Map lookup per component update), which is real added risk, but it is contained to the same-flush mount-then-update case and cleared at flush end. Weighing root-cause correctness first, A is the better fix despite its larger footprint.

Here's what I found out when debugging this myself:

The input is driven by a v-model, so the value is not really "rendered" by script setup, but it's instead set on elements by vModelText core directive. This will explain why the interpolation {{ val }} is rendered with the correct value, whereas the <input> shows the initial value instead.

The reproduction is setup in such a way that vModelText hooks are called in incorrect order.
After event onSetup is processed by Wrapper, the component is rendered again, and vModelText.beforeUpdate is called with the new value. If you break at this point you'll see the repro displaying the correct values.

But then, it looks like the directive mounted hook has not been executed yet. It is enqueued by Vue core mountElement function here:
https://github.com/vuejs/core/blob/fc4bbf95c1f9c8d9591e82571008578da15d7677/packages/runtime-core/src/renderer.ts#L715-L725

The issue seems to be that this call has captured the initial directive value and so restores the previous, incorrect value into the input element.
