Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

The issue asks for `resources.Copy` to accept `[STRING or MAP] RESOURCE` with `targetPath` and `importContext` keys. The stored import context should then be honored by css.Build, js.Build/Batch, css.Sass and TailwindCSS.

Patch B implements exactly that design:
- `Namespace.Copy` accepts a string or an options map, with case-insensitive keys, unknown-key errors, and `targetPath` defaulting to the resource's own path.
- The `ImportContext` lives in an unexported field on `genericResource`, read through `InternalResourceImportContext`, which follows the `resources.Internal*` pattern the issue suggests.
- The context is included in `TransformationKey` and the copy cache key. The key covers content hashes, so two `FromString` resources with the same name but different content stay distinct.
- It flows into `ResourceTransformationCtx`, so every transformer picks it up: esbuild (css.Build/js.Build), js.Batch with fallback precedence, the PostCSS/Tailwind inline importer, Dart Sass and LibSass. Node_modules imports are correctly excluded.
- Tests cover the issue's exact scenario (`@import "foo.css" screen`), mounts, Page contexts with rebuild, same-name/different-content caching, Sass (nested relative imports), js.Batch precedence, option-validation errors, and unit tests for the resolvers. Docs are updated.

Patch A does not touch `resources.Copy` at all. It adds `importContext` as a per-transformer option (css.Build/js.Build opts, Sass opts, PostCSS/Tailwind InlineImports), which is not the API the issue requests. It also brings significant risky churn:
- It bumps the hashstructure dependency to a new major version.
- It rewrites global hashing (`UnwrapFunc` replacing `toHashable`), which affects every hash in Hugo.
- It removes `pageState.Key` and adds `pageOutput.Key`.
- It changes the `Color` hashing method and the `Resources.Mount` implementation.
- It removes func support from `unwrapResourceGetter`.
- It adds a new `testinginternal` template namespace.

Its hash-pinning test asserts exact magic numbers, which is brittle. The js.Build import context is only consulted through the relative-path fallback added in resolve.go, which looks fragile.

B matches the requested design, is broader in transformer coverage, and is better tested with less unrelated risk.

The issue

View on GitHub

The example below (and variations of it) isn't possible in Hugo:

{{ $r := resources.FromString "foo.css" "body { color: blue; }" }}
{{/* How do I get $r to resolve as an import in main.css?  */}}
{{ $css := resources.Get "css/main.css" | css.Build }}

And in assets/css/main.js:

@import "foo.css" screen;
@import "bar.css" print;

The example above uses css.Build, but this is also relevant for (at least) css.Sass, js.Build and js.Batch. There are more or less ugly workardounds for the above (e.g. resources.Concat or passing in css vars in a map), but it would be nice to have a direct way that worked for all (I have a new proposal in mind that would need this).

I suggest we add importContext to resources.Copy and make the logic that's currently implemented in js.Batch also work for the other relevant funcs, e.g:

{{ $foo := resources.FromString "foo.css" "body { color: blue; }" }}
{{ $bar := resources.FromString "bar.css" "body { color: green; }" }}
{{ $main := resources.Get "css/main.css" | resources.Copy (dict "importContext" (slice $foo $bar)) }}
{{ $css := $main | css.Build }}

The current signature of resources.Copy is:

resources.Copy TARGETPATH RESOURCE

I suggest we

resources.Copy [STRING or MAP] RESOURCE

And make it optional (we can determine a path from RESOURCE). So for the MAP options it would look like:

{{ $opts := dict
   "targetPath" "foo.css"
   "importContext" (slice $foo $bar)
}}

In the above importContext is the same as described in inputContext -- which also allows constructs ala:

{{ $common := resources.Match "/js/headlessui/*.*" }}
{{ $importContext := (slice $.Page ($common.Mount "/js/headlessui" ".")) }}
{{ $opts := dict
   "importContext" $importContext
}}

Some implementation hints:

  • We would store this new importContext in some unexported field. I suggest we follow the pattern in the funcs resources.Internal* to access this internal state.
  • js.Batch takes importContext as an option. That import handling is more advanced than we need here, but we look at that for inspiriation/reuse.
  • I suggest that we start with css.Build and, once that looks good, implement it in js.Build/Batch, css.Sass and css.TailwindCSS.
