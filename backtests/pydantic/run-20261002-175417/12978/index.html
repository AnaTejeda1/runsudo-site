mypy [arg-type]-error when passing in type that can be converted to RootModel

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches register `_RootModelMetaclass` with the metaclass hook so the plugin processes `RootModel` itself. They differ in how they loosen the `root` argument when `init_typed` is unset.

Patch B removes the guard for `RootModel` and lets `add_initializer` replace `RootModel`'s declared `__init__` with a plugin-generated one where `root` is `Any`. That fixes the reported `RootModel[float]('1.0')` case and the subclass case. However, it also removes the only place the class type variable appears in the constructor signature. A call on the unparametrized class, such as `RootModel(1)`, can then no longer infer the type parameter and likely resolves to `RootModel[Never]`. That is a regression in a common usage pattern. B neither handles nor tests it. Replacing the hand-written `__init__` wholesale (positional-only `root`, `**data`) with the generic generated one also carries some risk.

Patch A rewrites only the `root` argument of the existing `RootModel.__init__` to `Any`, which keeps the rest of the signature intact. It then adds a function-signature hook that restores the type variable when the call has unsolved type variables, so `RootModel(1)` still infers `RootModel[int]`. Its tests cover:
- the alias call, the keyword call and the subscripted call (`RootModel[float]('1.0')`), with `assert_type` checks;
- inference on the unparametrized class (`assert_type(RootModel(1), RootModel[int])`);
- subclasses;
- a new strict-ini case confirming that typed init still reports errors.

These tests directly guard the regression that B leaves open. A is more code, but it is well documented and consistent with the surrounding conventions. A is the more correct and better-tested fix.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Initial Checks

Description

The below example code (named foo.py) passes when running python foo.py as the input "1.0"-string gets converted to float. However, running mypy foo.py (with or without --strict) gives the following error:

foo.py:11: error: Argument 1 to "RootModel" has incompatible type "str"; expected "float"  [arg-type]
Found 1 error in 1 file (checked 1 source file)

I would expect the BaseModel-fields and the RootModel-field to behave the same in this case. That is, if the value can be converted – either via a custom made validator or through the conversion table – then mypy should not raise an error.

Example Code

import pydantic


class Foo(pydantic.BaseModel):
    f: float


RFoo = pydantic.RootModel[float]

f = Foo(f="1.0")
rf = RFoo("1.0")

assert isinstance(f.f, float)
assert isinstance(rf.root, float)
assert f.f == rf.root
