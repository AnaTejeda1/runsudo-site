Suspense: flushing buffered effects overflows the call stack when many effects accumulate while pending (RangeError: Maximum call stack size exceeded)

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the issue at its root cause: they replace the unbounded `push(...arr)` spreads with plain loops in `queuePostFlushCb`, in the nested `flushPostFlushCbs` merge into `activePostFlushCbs`, and in Suspense's merge into a pending parent's `effects`. Those are exactly the three sites the issue names.

Patch B also converts the spread in `queueEffectWithSuspense` (`suspense.effects.push(...fn)`). This is another place where an unbounded array, a component's lifecycle hook array, is spread while the boundary is pending. It is a genuine instance of the same bug class, carries no added risk, and B includes a test for it (1M `onMounted` hooks under a pending Suspense).

On tests, A adds only scheduler-level unit tests. Both are valid regressions for the queue and nested-merge paths, but neither touches the Suspense merge-into-parent path it changed.

B adds the same scheduler-level coverage plus integration tests through Suspense:
- A pending boundary buffering 1M post-watcher jobs, which would throw at `queuePostFlushCb` before the fix.
- A nested-Suspense case where the inner boundary's 1M effects merge into a pending parent. This exercises the `parent.effects.push` site and also checks that the effects stay deferred until the outer boundary resolves.
- The lifecycle-hook buffering case.

These tests mirror the issue's real scenario rather than only the scheduler primitive.

Scope and craft are comparable: both keep the loops minimal and add explanatory comments. B's broader fix and more thorough, scenario-faithful tests make it the stronger patch.

Steps to reproduce

  1. Open the playground and show the Preview pane.
  2. The app renders a <Suspense> whose default slot contains an async component (resolves after ~4s) plus a large tree (2000 rows, each with a few flush: 'post' watchers).
  3. While the suspense is pending, a timer keeps mutating a ref, so the still-mounted tree re-renders repeatedly. Each re-render buffers its post effects into suspense.effects (via queueEffectWithSuspense).
  4. When the async component resolves, the suspense flushes the buffered effects.

What is expected?

The buffered effects flush and the app keeps working.

What is actually happening?

Uncaught (in promise): RangeError: Maximum call stack size exceeded — thrown from queuePostFlushCb called by suspense.resolve():

RangeError: Maximum call stack size exceeded
    at queuePostFlushCb (runtime-core.esm-bundler.js:331)
    at Object.resolve   (runtime-core.esm-bundler.js:7426)

The scheduler dies mid-flush, leaving the app permanently wedged (blank page).

Root cause

suspense.effects is unbounded — every post effect of every component under a pending suspense boundary is buffered into it. On resolve, the whole array is flushed with a spread call:

  • scheduler.ts: pendingPostFlushCbs.push(...cb)
  • scheduler.ts (flushPostFlushCbs nested case): activePostFlushCbs.push(...deduped)
  • Suspense.ts (merge into pending parent): parent.effects.push(...effects)

Spreading an array into a function call is limited by the engine's call stack (~100k–200k args in V8), so once enough effects accumulate the flush itself throws.

Real-world impact

We hit this in production in a Nuxt app: a kanban board page with ~1000 mounted cards that re-renders once per second (elapsed-time ticker). Navigating to another page keeps the board mounted under <NuxtPage>'s pending Suspense; its buffered effects exceed the spread limit and every SPA navigation away from the board crashes with a permanent white screen (hard reload of the target URL works fine, since there is no pending suspense in that case).

Suggested fix

Replace the unbounded spread pushes with plain loops. I have a PR ready with the fix and a regression test (queuePostFlushCb with a 1M-entry array).
