The issue

View on GitHub

What happened?

When a retryable error is raised after a non-streaming provider response has already completed success processing, the router retries with the same Logging object. The first attempt has already set has_logged_async_success/has_logged_sync_success, so success logging for the later successful attempt is skipped.

This causes the final response usage and reported cost to describe different attempts. In the reproduction, the response body contains the final attempt's cache-read usage, while both the accounting callback and x-litellm-response-cost retain only the discarded first attempt's cache-write cost.

For example, a provider can return a billable response marked as a content-policy refusal. LiteLLM maps that provider refusal to ContentPolicyViolationError and retries. If the retry succeeds, its cost is then skipped because the first attempt already marked success logging as complete.

Reproduction

The test below uses only stock LiteLLM APIs and a local fake Bedrock endpoint. The first response is fully priced, then the test raises ContentPolicyViolationError; the configured router retry succeeds with different usage.

Save as test_retry_cost_accounting_upstream_repro.py, then run:

pip install 'litellm[proxy]==1.104.5' pytest pytest-asyncio
pytest -q test_retry_cost_accounting_upstream_repro.py

Observed on litellm[proxy]==1.104.5:

AssertionError: recorded_costs=[0.147], header_cost=0.147
Expected records: [0.147, 0.036]
Expected measurable request cost: 0.183

The request itself succeeds with HTTP 200, reports one attempted retry, and its response body contains the final attempt's cache-read usage.

Root cause

Router.async_function_with_retries carries litellm_logging_obj into later attempts. In litellm/litellm_core_utils/litellm_logging.py, Logging.should_run_logging() returns false once the shared object contains has_logged_<success event> = True. As a result, the later attempt does not run _process_hidden_params_and_response_cost and does not emit its accounting event.

The proxy subsequently reads stale first-attempt state when constructing x-litellm-response-cost.

Expected behavior

Every provider response with billable usage should be accounted exactly once, including a later successful attempt after a post-response retry. The request-level cost must not silently omit later attempts. Please confirm whether x-litellm-response-cost is intended to aggregate all billable attempts; the missing final-attempt accounting record is a defect independently of that public header contract.

Affected area

  • Router retries after post-response errors
  • Non-streaming success logging/accounting
  • Reproduced with Anthropic Messages semantics through Bedrock

Related but distinct from #26475, #37105, #40736, #19216, and #42663.
