Leakage of NUMBER option out of docstring scope

Worse

The merged fix was judged better than our patch.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the same root cause the same way: pytest's runner raises out of DocTestRunner.run (on failure without --doctest-continue-on-failure, on exceptions, and on skip/xfail outcomes) before CPython's __run reaches its `self.optionflags = original_optionflags` restore, so per-example directives leak into later doctests sharing the module runner. Patch A saves/restores around `self.runner.run` in `DoctestItem.runtest`; Patch B overrides `run` in the custom runner class. Since runtest is the only caller of run, the two are functionally equivalent, and the independent tests confirm both pass every scenario (including exception and continue-on-failure). B's placement is slightly more self-contained, but A's placement is equally correct and simpler.

The difference is in tests. Patch A adds two parametrized regression tests that use `assert_outcomes` with exact counts, cover failure and exception in the first doctest, cover enabling NUMBER, enabling ELLIPSIS, and disabling ELLIPSIS (the opposite direction of leakage, where a leaked `-ELLIPSIS` would make a later test wrongly fail), and separately cover skip and xfail outcomes, which also bypass doctest's restore. Each of these would fail before the fix and pass after. Patch B's single test covers failure/exception/skip with +NUMBER only and asserts merely that some failing nodeid ends with the second test's name, a weaker check that does not pin down total outcomes. Neither test is skipped at runtime (the `pytest.skip` in B is inside a doctest example, not the test itself).

Scope and craft are comparable: both add a one-line changelog and an accurate comment; B's changelog is more specific, A's mentions skip/xfail. On balance A wins narrowly on more thorough, precise test coverage with an equivalent fix.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Each saw the issue and the two patches, labelled A and B in random order (two of them saw ours as A), with issue links and version numbers removed. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours. The reasoning above is one judge's, shown verbatim.

This was originally noted in #9892, but there is a more targeted MRE here.

MRE

Running pytest --doctest-modules test_x.py with x=1, 2 or 3 results in the following pattern of failing and passing tests. The test inside test_wo_number incorrectly passes only on the cases (test_1.py and test_2.py) where a failing test that uses NUMBER (test_w_off_by_2_number) also exists in the same module. This leakage does not occur when there are tests that pass that utilize NUMBER (test_3.py)

# test_1.py
def test_w_number():
    """
    Correctly Passes

    Examples
    --------
    >>> 1.  # doctest: +NUMBER
    0.
    """

def test_w_off_by_2_number():
    """
    Correctly Fails

    Examples
    --------
    >>> 0.  # doctest: +NUMBER
    2.
    """

def test_wo_number():
    """
    Incorrectly Passes

    Examples
    --------
    >>> 1.
    0.
    """
