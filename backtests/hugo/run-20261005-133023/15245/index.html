Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches remove the checkout-derived name and add `"private": true`, which is the core of the issue. They differ in the default name and in how they treat existing files.

Correctness:
- Patch B always emits a fixed scoped name, `@gohugoio/hugoautogen`, plus `private: true`. This gives every clone the same output and meets the issue's stated ideal: a scoped name that only the scope owner can claim.
- Patch A defaults to the bare `hugoautogen`. The issue explicitly warns that anyone can claim a bare name on the registry.
- Patch A also copies `name`, `version` and `private` from any existing generated file. That causes a migration problem. Repos that committed a file generated by older Hugo already carry checkout-derived names like `site-a`, and Patch A keeps those stale names forever. The upgrade would never fix the name part of the bug for existing users.
- Patch A also lets `private: false` persist, which weakens the do-not-publish guard.
- Preserving hand edits is a plausible feature, but it adds behavior the issue did not require and partly undermines the fix.

Tests:
- Both update the golden testscripts and add an integration test that would fail before the change.
- Patch B's test runs `Pack` from two different working directories (`/site-a`, `/site-b`) and checks the parsed JSON. It directly reproduces the issue's scenario of differently named checkouts.
- Patch A's test covers the new defaults and its preservation round-trip. It does not vary the checkout directory and relies on string-contains checks.

Scope and craft:
- Patch B is minimal and clear. It adds a named constant with a rationale comment and a short docs note.
- Patch A adds more logic, silently ignores JSON parse errors, and has more edge-case behavior.

Overall, Patch B is the more robust and complete fix.

The issue

View on GitHub

TL;DR: the generated package.json has no "private": true and a checkout-derived name, so committed copies are publishable under names sites don't control. Suggested fix: emit "private": true and a stable (ideally scoped) default name.

What version of Hugo are you using (hugo version)?

hugo v0.165.0-76a5e1880ab46688155b02e99bab9be2a6134492+extended darwin/arm64 BuildDate=2026-08-12T14:26:28Z VendorInfo=gohugoio

Does this issue reproduce with the latest release?

Yes (transcript below is v0.165.0). The behavior is in master's package_builder.go.

What happened

hugo mod npm pack writes packages/hugoautogen/package.json with:

  • a name derived from the checkout directory, so it varies per clone and can be a registry name the site doesn't control, and
  • no "private": true, npm's do-not-publish guard for internal packages.

The file is regenerated wholesale on each run, so hand-set fields don't survive. From a fresh clone of a repo whose committed copy was hand-normalized:

$ git clone https://github.com/google/docsy-example.git site-a && cd site-a
$ grep -E '"(name|version|private)"' packages/hugoautogen/package.json
  "name": "@docsy/hugoautogen",
  "version": "0.1.0",
  "private": true
$ hugo mod npm pack
$ grep -E '"(name|version|private)"' packages/hugoautogen/package.json
  "name": "site-a",
  "version": "0.1.0"

A sibling clone of the same repo into site-b yields "name": "site-b".

Why it matters

Sites that commit the generated workspace (e.g. so npm ci works without running Hugo first) end up carrying a manifest that npm workspace publishing and common release tools treat as publishable by default: npm publish --dry-run --workspaces packs it as site-a@0.1.0, while with "private": true npm skips the workspace. The name variance also churns the committed manifest, and the lockfile's workspace entry, across differently named checkouts.

What did you expect

The generated internal workspace is non-publishable ("private": true) and has a stable, project-controlled default name rather than the checkout directory's basename. Ideally the default is scoped: a bare name can be claimed on the registry by anyone, a scoped one only by the scope owner.

Workaround

docsy-example#487 follows each pack invocation with a single npm pkg set line restoring a scoped name and private.

Happy to send a PR for the private field (and for the name default, if you have a preference for what it should be).
