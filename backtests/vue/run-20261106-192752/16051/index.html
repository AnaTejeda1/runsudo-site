compiler-dom: stringifyStatic renders :disabled="0" as a present attribute

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the root cause the same way: after evaluateConstant, every boolean attribute (and `hidden`) is dropped when includeBooleanAttr(evaluated) is false, and all independent tests pass on both. The difference is in craft, tests, and scope.

Patch B's core change is cleaner. It removes the now-redundant source-text `exp.content === 'false'` check and the odd `typeof` gating on `hidden`, leaving a single rule `(isBooleanAttr(arg) || arg === 'hidden') && !includeBooleanAttr(evaluated)` that matches the runtime/SSR rule the issue cites. Patch A keeps the old string check and adds a `typeof evaluated === 'number' || 'boolean'` clause for `hidden` that is dead weight (strings are either truthy or `''`, both kept by includeBooleanAttr; null is already filtered), so the resulting condition is harder to read than it needs to be.

Tests: Patch B covers a wider matrix of falsy constants (`0`, `-0`, `!1`, `1 > 2`, `0 / 0`, `null`, `void 0`) across disabled/checked/readonly/hidden, plus retained cases (`true`, `1`, `''`, `'false'`), plus a compiler+runtime integration test that mounts a stringified tree and asserts the button is enabled and clickable, which mirrors the issue's actual symptom. Patch A's tests are adequate (0 and !1 for three attrs, a truthy keep case, and `!1` added to the hidden test) but narrower.

Scope: Patch B goes beyond the ask by making analyzeNode bail on custom elements with boolean-attribute bindings and threading `context` through to do so. This is a behavior change (custom elements with `:disabled="true"` now deopt out of stringification) that the issue did not request, and it is the main mark against B. It is justified in a comment and covered by tests, and the signature change is contained to one call site, so the added risk is modest rather than disqualifying. Patch A is minimal and tightly scoped, which is its strongest point.

Weighing it: equal on correctness for the reported issue, B stronger on tests and on clarity of the core fix, A stronger on scope. The scope creep in B is defensible and tested, so B edges out overall.

The issue

Vue version

Link to minimal reproduction

https://github.com/DaZuiZui/vue-stringify-boolean-0

This cannot be shown in the SFC Playground. stringifyStatic is the Node compiler's hoist transform, and the browser build sets transformHoist to null.

Steps to reproduce

<template>
  <article>
    <p>Paragraph 0 of a static article.</p>
    <!-- 18 more static paragraphs -->
    <p>Paragraph 19 of a static article.</p>
    <button :disabled="0">Save article</button>
  </article>
</template>

The same binding on its own, in a separate component, is the control:

<template>
  <button :disabled="0">Save</button>
</template>
  1. Clone https://github.com/DaZuiZui/vue-stringify-boolean-0 and run npm install && npm run dev.
  2. Save article is not clickable. Save is clickable.
  3. npm run build. The production bundle contains <button disabled="0">Save article</button>.

The same output is produced by @vue/compiler-dom directly. Once the static tree reaches the stringify threshold, the render function is:

_createStaticVNode(
  "<p>Paragraph 0 of a static article.</p>...<button disabled=\"0\">Save article</button>",
  21,
)

Mounting that render function sets button.disabled === true and getAttribute('disabled') === '0'. The tree that is too small to stringify compiles to { disabled: 0 }, and that button stays enabled.

What is expected?

disabled is omitted on both buttons.

From the boolean attributes guide: the attribute is included for a truthy value or '', and omitted for other falsy values. 0 is falsy. includeBooleanAttr(0) is false, and that is the rule the runtime and the SSR compiler already follow. A tree that is too small to stringify, and :disabled="false" inside a stringified tree, both omit the attribute.

What is actually happening?

Save article is disabled. The stringified HTML is <button disabled="0">, and a browser treats any present disabled attribute as true. The standalone Save button, compiled to a vnode prop, stays enabled.

Any additional comments?

compiler-sfc turns hoistStatic on by default in compileTemplate, so a production SFC build hits this without any compiler option being set. It only starts once a static chunk reaches 20 nodes or 5 elements with bindings, which is why the same binding is correct in a small template.

stringifyElement only drops a boolean attribute when the source text is the string "false". A numeric constant is evaluated and then written out as text. 0 and NaN both fail includeBooleanAttr, but only hidden gets that numeric check:

The string `"false"` case was fixed in #6617. The same omission should apply to every boolean attribute (`disabled`, `checked`, `readonly`, and the rest) after the constant is evaluated, using `includeBooleanAttr`, the way `hidden` already does.
