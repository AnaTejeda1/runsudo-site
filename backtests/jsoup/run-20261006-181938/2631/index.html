Malformed </ end tag should consume the /

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches make the same production change: they remove the `commentPending.append('/')` line in the EndTagOpen fallback branch, so the bogus comment no longer includes the consumed `/`. That is the root cause, and it gives `</ COMMENT >` → `<!-- COMMENT -->` as the spec requires. On correctness the two are identical, and both update the existing test that expected `<!--/tag-->`.

The difference is in the new tests.
- **Patch A** covers more ground. It checks the exact issue case in context (`<div>One</ COMMENT >Two</div>`, asserting both the serialized HTML and `Comment.getData()`), at top level, and with a different invalid start char (`</?foo>` → `<!--?foo-->`). It also adds an XML-parser test, confirming the shared tokeniser behaves the same in XML mode.
- **Patch B** adds a table-driven test with `</#` (the EOF path), `</ COMMENT >` and `</ COM--MENT >`. These are useful, but only check top-level comment data in the HTML parser.

All of these tests would fail before the change and pass after it. Patch A replaces the removed comment with an explanatory one about spec behaviour, which is slightly clearer. Patch B's CHANGES.md entry is neutral under the scope criterion. Because the fixes are identical, the decision rests on test coverage, where A is modestly ahead (in-context HTML plus XML).

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
