Normalize re2j exceptions

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the root cause the issue describes. Before either change, only re2j compile was guarded; a StackOverflowError raised during re2j matching (Matcher.find, which is where re2j#77's recursion occurs) escaped as a raw Error. Both patches wrap Re2jRegex's find() and rethrow a ValidationException, so on correctness for the reported re2j case they are equivalent.

Patch A also adds the same handling to the JDK regex path, in both compile and find. That is extra hardening beyond the issue's re2j ask, so it earns no credit on its own. It is mostly harmless, but it widens the behavior change to every jsoup user, not just re2j users.

On craft, Patch A keeps the `"Pattern complexity error: " + e.getMessage()` form. StackOverflowError usually has a null message, so users will typically see "Pattern complexity error: null". Patch B emits a clean "Pattern complexity error" message via a named constant, which matches the issue's wording exactly.

On tests, Patch B adds a focused regression test that reproduces the real-world scenario: a selector query (`[data-key~=(a|){824}]`) run through doc.select with re2j enabled. It asserts the exact normalized message, and it would fail before the change with a raw StackOverflowError. Patch A's tests are broader but weaker in two ways. Its re2j compile test exercises a path that was already guarded before the patch, so it would pass without the fix. Its other tests depend on 100k-deep inputs and default stack sizes, which makes them heavier and potentially environment-sensitive, though its re2j find test is a valid regression test.

Overall, B delivers the issue's fix more cleanly and precisely, with a tighter targeted test. A adds broader but unrequested scope and produces a sloppy 'null'-suffixed message.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The issue

View on GitHub

re2j can throw a Stack Overflow if the input regex causes a deep recursion. We should normalize that into an Pattern complexity error ValidationException (which is an IllegalArgumentException) so it's clearer what the issue is.

Underlying root cause is https://github.com/google/re2j/issues/77
