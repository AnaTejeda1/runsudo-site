Make .Render take additional data

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

The issue explicitly proposes the signature `PAGE.Render [DATA] NAME`, with DATA coming before the template name. Patch B implements this form. It also accepts `NAME DATA`, resolving the ambiguity deterministically: when both arguments are strings, it treats them as DATA NAME, which matches the issue's stated order. Patch A only supports `VIEW [CONTEXT]`, so the issue's proposed call `.Render (dict ...) "summary"` fails with a cast error. A therefore does not deliver the requested API shape. Both patches adopt the issue's first option, using the supplied data as the context instead of the page, and both preserve the default of passing the page when no data is given. Both update the interface, lazy provider, nop page and test helpers consistently. On tests, B's integration test covers data-first, data-last, no data, string data and slice data, and its error cases cover too many arguments, missing layout name, non-string layout and template not found. B also adds focused unit tests for the parsing helper. A tests only the trailing-context form plus two error cases. B also isolates argument parsing in a small documented helper, `ResolveRenderArgs`, and updates the user docs. The one minor caveat is that B's dual-order acceptance adds a little ambiguity, but its string precedence rule is documented and tested. Overall, B matches the issue's requested semantics where A does not, and B is more thoroughly tested.

PAGE.Render NAME

This has been discussed before.

  • The contract has always been that the templates that .Renders gets the data context as e.g. page.html, a page.Page.
  • We can only pass 1 argument to Go's template renderer, which I guess is the blocking reason for not having done this sooner.

So, if we want to do:

PAGE.Render [DATA] NAME

I'm guessing we have 2 top-level options:

  • We say that if DATA is set, we use that as the context passed to the templates,. else PAGE.
  • We somehow (e.g. by embeding it in a { DataAdditionalContext, Page } struct or putting it into the current context.Context) wrap the Page so you can do both .RelPermalink and .DataAdditionalContext (naming of the latter is just picked out of a hat without thinking too hard.
