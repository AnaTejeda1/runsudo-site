Output guardrail trip leaves orphaned tool call on streamed resume

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches make the same core change: add a flag to `_finalize_streamed_final_output` so the resumed-turn call site persists the turn's items (the approved tool's `function_call_output`) before output guardrails run, choosing the issue's policy (a) and matching the non-streamed path. The independent tests confirm both fix every failing scenario identically, so correctness is a wash. The differences are in craft and tests. Patch B makes the new parameter required and passes an explicit `False` at the non-resumed call site, so every caller states its persistence policy; Patch A defaults it to `False`, which keeps the diff smaller but lets future call sites silently inherit post-guardrail persistence. B's name `persist_before_output_guardrails` is also more precise given that tool guardrails exist in the same code path. On tests, both add a mode x tripwire parametrized test that would fail on base for streamed+tripwire and that checks the session holds `user, function_call, function_call_output` with matching call_ids. Patch A additionally asserts the tool executed exactly once across the two runs, which is a nice check of the 'approved side effect committed' intent. Patch B goes further on the issue's own follow-on concern: after the tripped turn it runs another turn with the guardrail cleared and asserts the model input replays the call/output pair rather than having the call stripped by `drop_orphan_function_calls`, directly covering the 'following turn' behaviour the issue describes. That end-to-end check plus the more explicit API make B the slightly better fix; A's smaller footprint does not offset it.

The issue

View on GitHub

Describe the bug

On a resumed approval turn where tool_use_behavior='stop_on_first_tool', an output-guardrail
tripwire leaves the two entry points with different session contents — and leaves run_streamed
with a function_call that has no matching function_call_output.

### tripwire=True
   run       blocked  ['user', 'function_call', 'function_call_output']
   streamed  blocked  ['user', 'function_call']            <<< orphaned call
### tripwire=False  (control)
   run       ok       ['user', 'function_call', 'function_call_output']
   streamed  ok       ['user', 'function_call', 'function_call_output']

The orphan is currently survivable rather than fatal: drop_orphan_function_calls strips the
dangling call when the history is next prepared, so a following turn sends
['user:turn one', 'user:turn two'] to the model without erroring. But the stored state is
inconsistent, any consumer reading the session directly (analytics, audit, a custom
session_input_callback, an AdvancedSQLiteSession query) sees a call with no result, and the
non-streamed path disagrees.

Root cause

The resumed turn's items are persisted by save_resumed_turn_items at src/agents/run.py:965,
on the resume branch, which runs before any output-guardrail evaluation. Traced calls for the
tripwire case:

SAVE run.py:1548 : ['tool_call_item', 'tool_approval_item']
SAVE run.py:965  : ['tool_call_output_item']      <-- persisted here, pre-guardrail

That site is reached only when resuming, so it is untouched by the two open/recent PRs in this area
(#3998 and my now-closed #4123, both of which change the NextStepFinalOutput handling further
down in the non-resumed loop). I confirmed the behaviour is byte-identical at the merge base, at
#3998's head, and on my branch.

Note the asymmetry direction here is the opposite of the plain message case: for a message-final
turn run_streamed is the correct reference (it withholds the rejected message), but for this
resumed case run_streamed produces the worse state. So "make run match run_streamed" is
not the right fix — the orphan needs handling either way.

There is also a genuine design question I don't think has an obvious answer, which is why I'm
filing this as an issue rather than a PR: the tool executed after an explicit human approval.
Discarding its output on an unrelated output-guardrail trip discards a durable user decision, and
re-running it on the next turn re-executes a side effect the user approved once. The two coherent
options seem to be (a) keep both the call and its output, treating approved tool execution as
committed — which is what the non-streamed path already does — or (b) roll back both together so
no orphan can exist. Silently keeping only the call is the one behaviour that isn't defensible.

Debug information

  • Agents SDK version: v0.9.3 (reproduced at main, and at the merge base 6e2095d)
  • Python version: 3.10 (Windows); nothing platform-specific in the repro
  • Model: FakeModel from the test suite — no network calls needed

import asyncio
from typing import Any

from agents import (
    Agent, GuardrailFunctionOutput, ModelSettings, OutputGuardrail,
    OutputGuardrailTripwireTriggered, RunContextWrapper, Runner, function_tool,
)
from tests.fake_model import FakeModel
from tests.test_responses import get_function_tool_call
from tests.utils.simple_session import SimpleListSession


@function_tool(name_override="secret_tool", needs_approval=True)
def secret_tool(query: str) -> str:
    return "SECRET-TOOL-OUTPUT"


def gr(trip: bool) -> OutputGuardrail:
    async def f(ctx: RunContextWrapper[Any], agent: Agent[Any], output: Any):
        return GuardrailFunctionOutput(output_info=None, tripwire_triggered=trip)
    return OutputGuardrail(guardrail_function=f)


async def drive(mode: str, trip: bool):
    session = SimpleListSession()
    model = FakeModel()
    model.set_next_output([get_function_tool_call("secret_tool", '{"query": "q"}')])
    agent = Agent(
        name="t", model=model, tools=[secret_tool],
        model_settings=ModelSettings(tool_choice="secret_tool"),
        tool_use_behavior="stop_on_first_tool",
        output_guardrails=[gr(trip)],
    )

    async def run_once(inp):
        if mode == "run":
            return await Runner.run(agent, inp, session=session)
        r = Runner.run_streamed(agent, inp, session=session)
        async for _ in r.stream_events():
            pass
        return r

    first = await run_once("please do it")
    state = first.to_state()
    state.approve(first.interruptions[0])          # explicit human approval
    try:
        await run_once(state)                      # resumed turn == final-output turn
        outcome = "ok"
    except OutputGuardrailTripwireTriggered:
        outcome = "blocked"

    items = await session.get_items()
    types = [(i if isinstance(i, dict) else {}).get("type")
             or (i if isinstance(i, dict) else {}).get("role") for i in items]
    return outcome, types


async def main():
    for trip in (True, False):
        print("### tripwire=%s" % trip)
        for mode in ("run", "streamed"):
            print("   %-9s %-8s %s" % ((mode,) + await drive(mode, trip)))

asyncio.run(main())

Expected behavior

The two entry points should agree, and the session should never hold a function_call without its
function_call_output — whichever of the two policies above is chosen. The control case
(tripwire=False) already agrees, so this is specifically about the tripwire path.

Happy to send a PR once there's a call on which policy is intended; I didn't want to encode that
choice unilaterally, since it decides whether an approved tool's result survives an unrelated
guardrail rejection.
