hugo --gc deletes in-use image cache files when on-disk path case differs from the cache key (case-insensitive filesystems)

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the root cause in the pruner's usage check: an on-disk name that differs from a seen cache key only in case is no longer treated as unused.

Patch A:
- It looks up the seen ids that share the walked name's lowercase form, stats each one, and keeps the file only if `os.SameFile` confirms the id resolves to the very same file.
- This asks the filesystem directly how it resolved the read, which is the issue's exact criterion. It is correct on both case-insensitive and case-sensitive filesystems.
- The lowercase index is built lazily, so the extra work only happens on a mismatch. The change is small and local.
- Its test is clever. On case-sensitive CI (Linux) it emulates case-insensitive resolution with a hard link, and it adds a negative case (a distinct `Other/x.jpeg` still gets pruned). So the fix is exercised on every platform rather than skipped.

Patch B:
- It uses an indirect heuristic: defer the decision and remove the mixed-case file only if the exact-case key was also walked.
- This works in the common scenarios, but it infers sameness from absence rather than checking it. On a case-sensitive filesystem, a stale mixed-case file survives if the exact-case key file isn't present on disk.
- `seenByLower` keeps only one id per lowercase key, so seen ids that differ only by case collide.
- It restructures the walk more heavily (a remove closure and a post-walk pass).
- Its main tests (the case-insensitive unit test and the testscript) are skipped on case-sensitive CI, so the fix path is not exercised there.
- It adds unrelated test infrastructure (a `base64decode` command, a testscript condition, an htesting helper), which adds churn.

Patch A is more precise, simpler, and better tested across platforms.

The issue

View on GitHub

What happens

On a case-insensitive filesystem (macOS APFS, Windows), hugo --gc deletes image cache files under resources/_gen that the build actively uses, if the on-disk path case differs from the cache key. The build itself works fine (the case-insensitive filesystem resolves the read), but the pruner's usage check is a case-sensitive string comparison, so the just-used file is considered unused and removed.

The relevant code is in cache/filecache/filecache_pruner.go (unchanged on master):

if !shouldRemove && c.entryLocker.seen.Len() > 0 {
    // Remove it if it's not been touched/used in the last build.
    shouldRemove = !c.entryLocker.seen.Has(name)
}

seen contains the cache key (for images: the lowercased target path, via ImageCache.getOrCreate → c.fcache.ReadOrCreate(relTargetPath, …)), while name is the real on-disk name from the filesystem walk. If they differ only in case, seen.Has(name) is false and the file is deleted.

Why the case can differ in practice

Page paths have been lowercased since the v0.123 page-system rewrite, so cache keys for page-bundle images are lowercase. Caches created by older Hugo versions preserve the source directory case (e.g. resources/_gen/images/collections/PastFuture/…). Such caches are common in the wild: committed to git for CI cold-start speed, restored by CI cache plugins, or simply carried forward on a developer machine across Hugo upgrades.

The result is a permanent rebuild/evict cycle: --gc deletes the in-use entries → the next build silently re-processes all of them → the new files land inside the surviving mixed-case directory (the prune walk visits directories before deleting their files, so the directory is never seen empty and survives; on a case-insensitive filesystem the re-created file then lands in it) → the next --gc deletes them again. On the real site where we found this, every build re-scaled 267 images (~35 s per build, forever).

Minimal reproduction (macOS)

hugo new site repro && cd repro
mkdir -p content/MyBundle layouts/_default
printf 'baseURL = "https://example.org/"\ndisableKinds = ["taxonomy", "term", "rss", "sitemap"]\n' > hugo.toml
printf -- '---\ntitle: My Bundle\n---\n' > content/MyBundle/index.md
cp /path/to/any.jpeg content/MyBundle/cover.jpeg
printf '{{ with .Resources.GetMatch "cover.jpeg" }}{{ with .Resize "100x" }}<img src="{{ .RelPermalink }}">{{ end }}{{ end }}' > layouts/_default/single.html
printf 'home' > layouts/_default/home.html

hugo                      # creates resources/_gen/images/mybundle/cover_hu_<hash>.jpeg
# simulate a cache written by an older Hugo (or copied from elsewhere):
mv resources/_gen/images/mybundle resources/_gen/images/tmp
mv resources/_gen/images/tmp resources/_gen/images/MyBundle

hugo --gc                 # build succeeds (16 ms, cache hit), but reports "Cleaned 1"
find resources -type f    # -> empty: the file the build just used is gone

hugo                      # re-processes the image (474 ms) — and writes it back
                          # into the surviving MyBundle/ dir, so the cycle repeats

Observed output of the --gc build:

Processed images │  1
Cleaned          │  1
Total in 16 ms

A cache file that was read 16 ms earlier is deleted as "not been touched/used in the last build".

What I expected

--gc should never delete a cache entry that the same build read. On case-insensitive filesystems the usage check should match the way the filesystem resolved the read — e.g. compare case-insensitively (or normalize walk names against the seen set) when the cache filesystem is case-insensitive. Renaming the on-disk entry to the key's case would even self-heal old caches.

What the agent reported

I fixed the pruner so hugo --gc no longer deletes a cache file the same build just read when the file's on-disk case differs from its cache key. The new regression test fails without the fix and passes with it. I couldn't run it through ./bt-test, because that tool can't build this package here (details under test evidence).

What was wrong: In cache/filecache/filecache_pruner.go, Prune decides whether a file was used by checking the on-disk name against the set of cache keys the build touched, and that check is case-sensitive. On macOS or Windows, MyBundle/cover.jpeg on disk and the key mybundle/cover.jpeg are the same file, but the check treats them as different, so the file is deleted.

What I changed: When the exact name isn't in the set, Prune now looks for keys that match ignoring case. For each one, it keeps the file only if the key resolves to the very same file on disk (c.Fs.Stat(id) plus os.SameFile). The lowercase index of keys is built at most once per prune, and only when some file fails the exact check.

  • macOS / Windows: the key resolves to the mixed-case file, so it is kept.
  • Linux (e.g. an old mixed-case cache copied into CI): the key points to a different file or none, so the stale file is still removed as before.
  • In-memory filesystems: os.SameFile never matches, so nothing changes.

Test: TestPruneCaseInsensitiveFilesystem in cache/filecache/filecache_pruner_test.go runs on a real disk in a temp directory.

  1. A first build creates the cache entries.
  2. The directory is renamed mybundle → MyBundle, as in the report.
  3. On a case-sensitive disk (like this Linux machine), a hard link mybundle/cover.jpeg → MyBundle/cover.jpeg stands in for case-insensitive lookup.
  4. A second build must be a cache hit, then prune runs.
  5. It checks that MyBundle/cover.jpeg still exists. It also checks that a separate stale Other/x.jpeg (key other/x.jpeg) is still deleted on a case-sensitive disk.

Requirements:

  1. --gc must never delete an entry the same build read — done; the new test covers it.
  2. Compare case-insensitively on case-insensitive filesystems (the report's suggestion) — done. Instead of guessing whether the filesystem is case-insensitive, it checks that the matching key is the same physical file.
  3. The reproduction scenario (a MyBundle/ cache left by an older Hugo) — covered by the test. The endless rebuild-and-delete cycle also stops, because the file is no longer deleted.
  4. Renaming entries to the key's case to self-heal old caches — not done. The report offered it only as an optional extra; renaming directories that differ only in case on case-insensitive filesystems needs a two-step rename and adds risk. With the fix, old caches stay valid and simply keep their mixed-case directory names.
  5. Keep deleting truly stale files on case-sensitive filesystems — kept; the Other/x.jpeg check in the test covers it.
