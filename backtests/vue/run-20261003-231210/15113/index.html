SSR memory leak - options API watchers are created and never stopped with async setup()

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the root cause the same way. They set the SSR-setup flag around `handleSetupResult` in the async-setup `.then` branch. As a result, `applyOptions` (options API `watch`, `$watch` in `created`, etc.) runs with `isInSSRComponentSetup` true, just as it does for sync setup. Non-immediate watchers are then skipped, and sync/immediate watchers get registered into `__watcherHandles` for cleanup.

The core difference is how the flag is reset. Patch A unconditionally sets it to `false` afterwards. Patch B saves and restores the previous value. Patch B is the more defensive choice: if this continuation runs while the flag is already `true` for another reason, such as a nested or concurrent setup or a `withAsyncContext` restore, A would clobber it and B would not. The added risk in A is small but real, and B's comment explains why it restores.

On tests, both include the issue's reproduction. A adds a GC-based retention test, which only runs with `--expose-gc` and so is skipped in many environments. B adds tests for `$watch` called in `created` and for a `flush: 'sync'` options watcher being tracked in `ctx.__watcherHandles` and stopped after render. Those exercise more of the paths affected by the fix and run unconditionally.

Scope is equivalent and both diffs are minimal. B wins on slightly safer state handling and broader meaningful test coverage.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The issue

Vue version

Steps to reproduce

originally reported in https://github.com/nuxt/nuxt/issues/30782

  1. create an options API component with an async setup(), a computed property that reads shared module-level state, and a watch on that
  2. render it on the server and then mutate the shared state after the render is done
  3. see that the watcher is still active on the server

Reproduction

test('options-api watchers should not be created for async setup components', async () => {
  const open = ref(true)
  const spy = vi.fn()

  const App = defineComponent({
    setup: () => Promise.resolve({}),
    computed: {
      isOpen() {
        return open.value
      },
    },
    watch: {
      isOpen: spy,
    },
    render() {
      return h('div', String(this.isOpen))
    },
  })

  const html = await renderToString(createSSRApp(App))
  expect(html).toBe('<div>true</div>')

  // mutating the state after the request is done should not trigger the watcher
  open.value = false
  await nextTick()
  expect(spy).not.toHaveBeenCalled()
})

What is expected?

the same behavior as with a synchronous setup: regular watchers declared via the watch option don't run during SSR and don't survive the render

mutating the shared state after renderToString resolves should not trigger anything

What is actually happening?

when setup() returns a Promise, the watch option creates a live watcher on the server that is never stopped

if this subscribes to state that outlives the request, it keeps the entire component instance (and app) reachable forever
