EffectScope stop() causes runtime crash (Cannot read properties of undefined) when dynamic scope cleanup mutates parent.scopes array during traversal

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches make the same source change in effectScope.ts. Each one iterates over a `.slice()` copy of `this.scopes` in pause(), resume() and stop(), and of `this.effects` in resume(). So both fix the root cause equally: the cached-length loop breaks when a child removes itself from the parent's array during traversal. They also harden the same adjacent paths, so correctness is a wash.

The difference is in tests and craft.

Patch A adds two tests, and both would fail before the fix:
- a sibling scope stopped from a cleanup during `parent.stop()`;
- a sync watcher that stops a sibling watcher during `resume()`.
They are minimal, mostly checking that nothing throws plus a couple of state checks.

Patch B adds three tests covering all three mutation paths the fix touches:
- `stop()` with a child cleanup stopping a sibling;
- scope `resume()` where a resumed effect stops a sibling scope;
- effects `resume()` where a `once` watcher removes itself.
Its assertions are stronger. They check that every child (including the third, which must not be skipped) ends up inactive, that each cleanup runs exactly once, that `parent.scopes` is emptied, and that the remaining effects actually re-run with the right values. That verifies the traversal still reaches every element, not just that it no longer crashes.

Patch B also adds brief comments explaining why the copies are needed. This helps future readers who might otherwise 'optimize' the slice away.

With identical fixes, Patch B's more thorough and more meaningful tests and its clearer intent give it the edge.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Steps to reproduce

Open the reproduction link.
Click the "Trigger сrash" button.
Observe the output status on the screen or check the browser console.

What is expected?

The parent scope should stop all its children successfully. When a child scope stops a sibling scope during the cleanup phase, the parent traversal loop should handle the array mutation gracefully without throwing errors.

What is actually happening?

The application crashes with the following error: TypeError: Cannot read properties of undefined (reading 'stop')

This happens because EffectScope.stop loops over this.scopes using a cached length l. During iteration, one child's onScopeDispose calls stop() on its sibling. The sibling removes itself from the parent's scopes array, reducing the array size. When the parent loop continues to the cached index l, it tries to access an element out of bounds (which is undefined), causing the runtime crash.

System Info

System: OS: macOS, Browser: Chrome, Node: v20.19.5

Any additional comments?

The bug lies in packages/reactivity/src/effectScope.ts.

Inside EffectScope, the methods pause(), resume(), and stop() loop over this.scopes using a cached length without accounting for array mutations. Creating a shallow copy of the array before iterating (e.g. const scopes = this.scopes.slice()) safely resolves the issue.
