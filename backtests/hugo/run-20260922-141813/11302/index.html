In this judgment, Patch A = our agent, Patch B = the merged fix.

Patch A fixes the reported bug at its root. The issue is that when an inner shortcode that uses .Inner (img) is left unclosed, the parser lets img greedily consume the outer's closing tag ({{< /figure >}}), so figure later hits EOF and reports 'unclosed shortcode figure' — blaming the wrong shortcode. Patch A adds a name-match check at the point a closing token is encountered in extractShortcode: if the close token's name differs from the current shortcode's name, the current (inner) shortcode's own close is missing, and it errors against that shortcode ('shortcode "img" must be closed or self-closed'). This correctly identifies the actually-unclosed shortcode. Its test reproduces the exact issue scenario (figure/img/figcaption) and asserts the error names img, not figure — it fails before and passes after. Patch B misidentifies the problem: its test uses a different scenario ({{< outer >}}{{< inner >}}{{< /outer >}}) producing a 'template for shortcode "inner" not found' error, not the reported 'unclosed shortcode' error. Its change only wraps errors *returned* from the nested extractShortcode call with a position; but in the reported repro the inner shortcode consumes the outer's closing tag and returns successfully, so the 'unclosed figure' error is generated by the outer's own loop at EOF and is never routed through the nested-error path Patch B touches. Thus Patch B likely does not fix the reported bug and only adjusts error position/wrapping for an unrelated case. Both patches are similar in scope and craft, but correctness — the dominant criterion — decisively favors A.

What the agent reported

The fix is complete and verified. Here is my final report.

What was wrong

Hugo issue #11302: when an outer shortcode that renders .Inner (e.g. figure) contains a nested inner shortcode that also evaluates .Inner (e.g. img) but is left without its closing tag, the unclosed inner shortcode greedily consumes the following tokens — including the outer shortcode's {{< /figure >}} closing tag. Hugo then reported the error against the outer shortcode (shortcode "figure" must be closed or self-closed), which is misleading: the actually-unclosed shortcode is the inner img.

Root cause: in hugolib/shortcode.go, extractShortcode's case currItem.IsShortcodeClose(): handler consumed any closing tag as if it closed the current shortcode, never checking that the closing tag's name matched. So a recursing inner img swallowed figure's close, leaving figure unclosed and wrongly blamed.

What I changed

hugolib/shortcode.go — one guard in the close handler. When a closing tag's shortcode name does not match the current shortcode's sc.name (i.e. the tag belongs to an ancestor, so the current inner shortcode is the one missing its close), it now returns the error naming the current (inner) shortcode:

if !sc.isInline && sc.name != "" && next.IsShortcodeName() && next.ValStr(source) != sc.name {
    // The closing tag is for an ancestor shortcode ... See #11302.
    return sc, fmt.Errorf("%s: shortcode %q must be closed or self-closed", errorPrefix, sc.name)
}

tpl/tplimpl/shortcodes_integration_test.go — added TestShortcodeNestedInnerIssue11302, replicating the ticket's exact markdown (figure → unclosed inner img that evaluates .Inner, plus a properly closed figcaption sibling), asserting the error names "img" and not "figure".

Test evidence

  • Teeth verified: with the fix reverted, the regression test fails — the error reads shortcode "figure" must be closed or self-closed (exactly the #11302 bug). With the fix, it passes (error names img).
  • Gate (all with fix in place): hugolib shortcode/inner/nested tests — 28 pass / 0 fail; parser/pageparser — 103 pass / 0 fail; tpl/tplimpl shortcode integration (incl. the new test) — 25 pass / 1 pre-existing skip / 0 fail.
  • Reviewer confirmed no false positives in valid nesting (matched closes, self-closing, inline, empty-name, top-level self-close all fall through untouched) and no unrelated changes.

Requirements checklist

  1. Fix the misleading error that names the outer shortcode instead of the inner one (#11302) — Implemented. The error now correctly names the unclosed inner shortcode; regression test proves before/after behavior.
  2. "Compiled fine before v0.111.0" / the exact ticket markdown — Investigated with evidence. I first built the literal markdown treating img as a normal self-closing (non-.Inner) shortcode: it builds successfully on current HEAD (that variant was never the bug — the lexer and semantic parser at v0.111.1 are functionally identical to current, so valid input always compiled). The real failure requires the inner shortcode to evaluate .Inner and be left unclosed, which a probe confirmed still produced the outer-named error on current HEAD — that is the scenario the fix and regression test target.
