What happened?

A proxy with a single Vertex Model Garden Grok deployment (vertex_ai/xai/grok-4.6) serves that model correctly on /v1/chat/completions, but the same model_name on the unified Gemini-style endpoint POST /v1beta/models/grok-4.6:generateContent fails.

On the same proxy and the same endpoint:

  • gemini-* deployments succeed.
  • Vertex Claude deployments succeed (they are translated to their own chat protocol).
  • vertex_ai/xai/grok-* deployments fail.

Expected: /v1beta/models/{model}:generateContent should serve a Vertex xai/grok-* deployment the same way it already serves other non-Gemini Vertex publisher models (Claude, Mistral, gpt-oss, Qwen, MiniMax, Moonshot, Z.ai, Gemma MaaS) — by translating the request to that model's chat-completions protocol and returning a normal candidates[...] response — instead of treating Grok as a native Gemini model.

Suspected cause (for maintainers): two different checks decide how a Vertex model is served, and they disagree about the xai/ publisher.

  • litellm/llms/vertex_ai/common_utils.py::get_vertex_ai_model_route() has an explicit model.startswith("xai/") branch returning MODEL_GARDEN, so chat completions work.
  • litellm/utils.py::ProviderConfigManager.get_provider_google_genai_generate_content_config() falls back to the litellm.completion() adapter only when VertexAIPartnerModels.is_vertex_partner_model() is true, and PartnerModelPrefixes has no xai/ entry, so Grok is handed to VertexAIGoogleGenAIConfig (native Gemini) instead.

Note that simply adding xai/ to PartnerModelPrefixes would regress chat completions: is_vertex_partner_model() is evaluated before the xai/ Model Garden branch, and the partner handler raises Unknown partner model for xai/. The narrow fix is to make the generateContent handler selection use the same Model Garden determination that chat routing already uses.
