"dictionary changed size during iteration" during model_rebuild

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

The issue is a race: concurrent `model_rebuild()` calls mutate the class `__dict__` (delattr/setattr of schema/validator/serializer) while another thread iterates `vars(cls)` during annotation evaluation. Patch A only patches the single visible symptom — it makes `LazyLocalNamespace.data` take an atomic copy so iteration won't raise `RuntimeError: dictionary changed size`. But the issue text explicitly notes the same race also produces `AttributeError: ... has no attribute '__pydantic_core_schema__'` from the delattr block, plus the risk of a parent validator being resolved mid-mutation; Patch A does nothing about those. It masks one manifestation of an unsynchronized mutation. Patch B attacks the root cause by serializing rebuilds with a global reentrant lock, with double-checked completeness (unlocked fast path, re-check inside the lock), and correctly reasons about why the lock must be reentrant (nested rebuild via `__class_getitem__` parametrization) and global rather than per-class (deadlock avoidance). It also broadens the mock check to `(MockCoreSchema, MockValSer)` so mock attrs aren't deleted, preventing concurrent readers from resolving a parent's validator. With rebuilds serialized, no thread iterates `vars(cls)` while another mutates it, so the dictionary-changed-size crash, the AttributeError, and the wrong-validator races are all eliminated. Tests: Patch A's test simulates a mutation-during-iteration mapping — reasonable but narrow. Patch B adds a reentrancy test (guards against the lock deadlocking on nested parametrization rebuilds) and a genuine two-thread serialization test that gates schema generation to prove the second thread blocks on the lock and returns `None` after the first completes, exercising the double-checked path and the on-complete hook firing once. Patch B's tests better exercise the actual concurrency semantics being fixed. Scope: Patch B touches more (main.py, dataclasses.py) but each change is on-point to the race. Patch B is the stronger, root-cause fix.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Setup: a module using `from __future__ import annotations` defines models whose
field types are only defined *later* in the same module. Building such a model's
schema fails during class creation, so pydantic leaves it incomplete (mock
validator) and defers the build to the first instantiation via
`model_rebuild(raise_errors=False)`.

`model_rebuild()` for the same class simultaneously. `model_rebuild()` mutates
the class `__dict__` (delattr/setattr of `__pydantic_core_schema__`,
`__pydantic_validator__`, `__pydantic_serializer__`), while

    RuntimeError: dictionary changed size during iteration

Each round executes the module source into a fresh module (fresh, incomplete

def worker(barrier: threading.Barrier, model: type) -> None:

What the agent reported

The work is complete. Here is my final report.

What was wrong

Concurrent lazy model_rebuild() calls raised RuntimeError: dictionary changed size during iteration in LazyLocalNamespace.data (pydantic/_internal/_namespace_utils.py).

NsResolver.types_namespace appends the live class __dict__ (vars(typ), a mappingproxy) into a LazyLocalNamespace (line 276). LazyLocalNamespace.data then iterated that mapping live via a dict comprehension over ns.items(). When a second thread ran model_rebuild() for the same class — deleting/setting __pydantic_core_schema__, __pydantic_validator__, __pydantic_serializer__ on the class __dict__ — the in-flight iteration observed the size change and crashed. FastAPI's threadpool serving the first requests after process start is a natural trigger.

What I changed

pydantic/_internal/_namespace_utils.py — rewrote LazyLocalNamespace.data to copy each namespace before merging instead of iterating it live:

data: dict[str, Any] = {}
for ns in self._namespaces:
    data.update(ns.copy() if hasattr(ns, 'copy') else ns)
return data

dict.copy() / mappingproxy.copy() are atomic C-level operations that don't call back into Python and can't observe a partially-mutated state (I verified mappingproxy.copy() delegates to the underlying dict.copy(), and a dict subclass's .copy() returns a plain dict without invoking any overridden items()). Merge semantics are unchanged — later namespaces still override earlier ones.

tests/test_forward_ref.py — added test_lazy_local_namespace_data_mutated_during_iteration, which deterministically (no threads) reproduces the failure using a namespace whose items() mutates itself mid-iteration, then asserts .data still resolves keys.
