What happened

Every model entry under the chatgpt/ provider prefix is missing its reasoning-capability annotations, even though the identical underlying models are fully annotated under the openai/ and azure/ prefixes.

All 14 chatgpt/* entries in model_prices_and_context_window.json (main) have zero reasoning keys — no supports_reasoning, no supports_*_reasoning_effort:

The inconsistency

Same model, three prefixes, two different answers:

  "litellm_provider": "chatgpt",

  "max_output_tokens": 128000,

  "supports_vision": true

// gpt-5.6-sol (litellm_provider: openai) — annotated
{
  "mode": "chat",
  "supports_reasoning": true,
  "supports_none_reasoning_effort": true,
  "supports_minimal_reasoning_effort": false,
  "supports_xhigh_reasoning_effort": true

// azure/gpt-5.6-sol — annotated
{
  "mode": "chat",

  "supports_minimal_reasoning_effort": false,
  "supports_xhigh_reasoning_effort": true
}

chatgpt/gpt-5.6-sol is a reasoning model — it accepts reasoning_effort, and /model/info lists it in supported_openai_params. It just never says so in the cost map.

Impact

Any consumer that reads capabilities from /model/info sees a reasoning model advertising no reasoning support. Concretely, for a route declared as:

model_list:
  - model_name: high
    litellm_params:
      model: chatgpt/gpt-5.6-sol

/model/info returns supports_reasoning: null and every supports_*_reasoning_effort: null. Downstream clients that gate their thinking/effort UI on these flags disable reasoning controls entirely, or fall back to a hardcoded subset. The only workaround is to hand-write model_info per route:

    model_info:
      supports_reasoning: true
      supports_none_reasoning_effort: true
      supports_minimal_reasoning_effort: false
      supports_xhigh_reasoning_effort: true
      supports_max_reasoning_effort: true

which duplicates data LiteLLM already carries for the openai/ and azure/ spellings of the same model.

Secondary: supports_max_reasoning_effort missing on all gpt-5.6 variants

Separate from the chatgpt/ gap — no gpt-5.6 entry under any prefix declares supports_max_reasoning_effort, though the models do accept effort: "max". models.dev reports for openai/gpt-5.6-sol:

"reasoning_options": [
  { "type": "effort", "values": ["none", "low", "medium", "high", "xhigh", "max"] }
]

Verified end-to-end against a live proxy — reasoning_effort: "max" against a chatgpt/gpt-5.6-sol route is accepted and returns reasoning_tokens > 0.

For reference, the flag is well-established in the map (supports_max_reasoning_effort appears on 32 entries, supports_xhigh_reasoning_effort on 63), so this is a per-model omission rather than a schema question.

Suggested fix

Propagate the reasoning annotations from the openai/ entries to their chatgpt/ counterparts, and add supports_max_reasoning_effort: true to the gpt-5.6 family. For chatgpt/gpt-5.6-{sol,terra,luna}:

{
  "supports_reasoning": true,
  "supports_none_reasoning_effort": true,
  "supports_minimal_reasoning_effort": false,
  "supports_xhigh_reasoning_effort": true,
  "supports_max_reasoning_effort": true
}

(medium/high intentionally omitted — consistent with the rest of the map, which never declares them and treats them as the implicit baseline.)

Happy to open a PR for the data change if that's the preferred route.
