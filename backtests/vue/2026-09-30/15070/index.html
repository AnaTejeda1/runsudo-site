SSR memory leak after a render error in a dynamic component

Worse

The merged fix was judged better than our patch.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches target the root cause. When the slot function throws inside `renderSlot` after `openBlock()`, the block is never closed. `currentBlock` then stays pointing at a stale array, and every vnode created by later renders gets pushed into it and retained. Both fixes resolve the exact scenario in the issue, where text slot content throws inside a `<component :is>` forwarding `<slot />`.

Patch A is more robust in two ways:

1. It records `blockStack.length` before opening and unwinds back to that size on error. This also correctly closes nested blocks the slot content may have opened before throwing. Patch B calls `closeBlock()` exactly once. If the slot content contains an inline block, such as `(openBlock(), createElementBlock(...))` from `v-if`, and throws while evaluating its children, B pops only that inner block and leaves `renderSlot`'s own block dangling, so the leak persists.
2. Patch A applies the same unwinding in `withCtx`. That covers inline blocks inside compiled slot functions even when they are not wrapped by `renderSlot`. A also moves the `_d` restoration into `finally`, which is cleaner than B's duplicated reset in the catch branch.

Tests: Patch A adds real GC-based leak tests using WeakRefs and wires them into the existing `unit-gc` vitest project with `--expose-gc`. The tests cover both the issue's repro and the `v-if` inline-block variant, and they directly assert the reported symptom (apps not collected). Patch B's test is reasonable: a probe `createBlock` at top level shows non-empty `dynamicChildren` if a block was leaked, so it would fail before the fix. However, it calls `createBlock` without a matching `openBlock`, which pops the block stack unbalanced and could disturb shared state. It also does not exercise the nested-block case that B's fix misses.

Scope: A's extra `withCtx` change is a directly related hardening of the same failure mode and adds little risk. Overall A is the more correct and better-tested fix.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

A dynamic component <component :is> with a <slot /> is needed for this to reproduce.

    defineProps({ tag: { type: String, default: 'div' } })

<template>
    <component :is="tag" class="card">
        <slot />
    </component>
</template>

app:

<script setup>
    defineProps(['payload'])  // one request renders with `payload: null` → throws
</script>

<template>
    <main>
        <Card>{{ payload.title }}</Card>
    </main>
</template>

What is expected?

A failed renderToString should not affect subsequent renders and all apps rendered after it should get garbage collected.

What is actually happening?

Every app created after the single failed render is kept in memory forever.

What the agent reported

A slot that throws during SSR no longer leaves block tracking open, so apps rendered after a failed renderToString are no longer held in memory. The fix is in packages/runtime-core/src/helpers/renderSlot.ts, and the new regression test fails without it and passes with it.

What was wrong: In SSR, <component :is="tag"> with a string tag builds an element vnode, and building it calls the default slot through the runtime helper renderSlot. renderSlot calls openBlock(), then runs the slot (and the fallback, if any), then calls createBlock(), which is the step that closes the block. When the slot threw (payload.title on null), the block was never closed. That left currentBlock in packages/runtime-core/src/vnode.ts pointing at a stale array. SSR-compiled code never opens or closes blocks itself, so nothing reset it. Every component vnode created by later renders, starting with the root vnode renderToString creates, was pushed into that array. Those vnodes hold their component instances and app contexts, so every later app stayed reachable. That matches the report's "alive=501".

What I changed: In renderSlot.ts, running the slot and the fallback is now wrapped in a try/catch. On error it calls closeBlock(), resets the slot's _d flag (which was also left wrong on the error path), and rethrows. The normal path builds the same vnode as before.

Test evidence:

  • New test: reset block tracking after rendering error in slot in packages/server-renderer/__tests__/render.spec.ts. It uses the report's exact Card and App templates and first renders with payload: null, which throws. It then checks that a healthy render still outputs <main><div class="card"><!--[-->ok<!--]--></div></main>. Finally it checks that no block was left open: a fresh top-level createBlock('div') must not collect any vnodes from earlier renders.
  • Before the fix: it failed in all three render modes (renderToString, renderToNodeStream, pipeToNodeWritable) with "expected … to have a length of +0 but got 3".
  • After the fix: it passes in all three modes.
  • Wider check: renderSlot is used by client rendering as well as SSR, so I ran ./bt-test packages/runtime-core packages/server-renderer: 60 files and 1339 tests passed. tsc --noEmit reported nothing for the changed files.
  • Review: the reviewer found nothing blocking and confirmed no unrelated changes. git diff --stat shows only the two files above.

Requirements:

  1. A failed renderToString should not affect later renders: done. The new test checks that a healthy render after the failure produces the correct HTML.
  2. Apps rendered after the failure should be garbage collected: done. The test asserts that the stale block which kept those apps alive is gone. It does not measure garbage collection or heap size directly, the way the reproduction script does.
  3. Reproduction with <component :is> plus <slot />: done. The test uses exactly that Card and App.

One related gap I left alone: the custom-element branch of renderSlot (around lines 46–54) has the same openBlock() → fallback() pattern with no protection. It is not involved in this SSR scenario, so I did not change it.

All changes are uncommitted in the working tree.
