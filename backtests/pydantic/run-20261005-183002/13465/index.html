Generic pydantic_extra typevar substitution lost in non-generic subclasses of parametrized models

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the reported case. For `class Sub(M[int])`, when `__pydantic_extra__` is only inherited, each reuses the parent's already-substituted `PydanticExtraInfo`, so `Sub` gets `dict[str, int]`, validates extras, and emits `additionalProperties: {'type': 'integer'}`.

The patches differ at the edges.

**Incomplete parent annotations.** Patch A reuses the parent's extra info even when it is incomplete, and only substitutes when `typevars_map` is non-empty. Take a parent with a forward reference that couldn't be resolved at its own definition time, such as `'dict[str, Later]'` defined in another module. A subclass created after `Later` exists would then inherit an incomplete info instead of re-evaluating the hint. On main today, the hint would be re-evaluated in the declaring class's namespace and resolve correctly. So Patch A risks a regression here, and it imports the #12000-style limitation into a path that currently works. Patch B explicitly falls back to `type_hints['__pydantic_extra__']` when the parent info is incomplete, avoiding this. It also adds a cross-module test for exactly that scenario.

**Choosing the parent.** Patch A takes the first direct base whose `getattr(base, '__pydantic_extra_info__')` is non-None. Patch B walks the MRO to find the class that actually declares the annotation, then takes the most-derived class at or before it that has its own `__pydantic_extra_info__`. This matches how annotation resolution works and is more robust under multiple inheritance and diamonds.

**Tests.** Patch A adds one test covering the basic case. Patch B covers the basic case, a two-level non-generic subclass (`SubSub`), extra-info inherited from a second base, and the cross-module incomplete case. Patch B's tests are broader and target real edge cases.

**Craft.** Patch B's helper adds some code but is well documented. It keeps the existing `replace_types` flow intact instead of branching on `typevars_map`.

Overall, Patch B is more correct at the edges and better tested.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Description

Follow-up to #13369 / #13391 (__pydantic_extra__ typevar substitution, currently main-only): the substitution works for direct parametrization (M[int]) but is lost in a plain (non-generic) subclass of a parametrized model (class Sub(M[int])). Extras on the subclass are silently unvalidated and the JSON schema loses the extras type.

M[int](x='nope')  -> ValidationError (correct, fixed by #13391)
Sub(x='nope')     -> accepted; m.x == 'nope'          # BUG
Sub(x='5').x      -> '5' (str)  vs  M[int](x='5').x == 5

M[int].model_json_schema()['additionalProperties']  -> {'type': 'integer'}
Sub.model_json_schema()['additionalProperties']     -> {}                  # BUG
Sub.__pydantic_extra_info__                          -> PydanticExtraInfo(annotation=dict[str, ~T], complete=True)

Root cause (from stepping through collect_model_fields in pydantic/_internal/_fields.py): for Sub, typevars_map is empty (its own __pydantic_generic_metadata__ is empty) and the inherited hint for __pydantic_extra__ is the parent's raw annotation dict[str, T] — so _generics.replace_types(ann, typevars_map) is a no-op and the raw ~T survives, producing extras_schema = {'type': 'any'}. Regular fields don't have this problem because they're copied from the parent's already-substituted model_fields; the extra-info path never consults the parent's __pydantic_extra_info__ (which on M[int] correctly holds dict[str, int]).

Note the 2-level generic chain (class Mid(M[T], Generic[T]); Mid[int]) works on main — only the plain-subclass case is broken.

I have a small fix working locally (reuse the parent's substituted PydanticExtraInfo annotation when __pydantic_extra__ is only inherited, mirroring how fields inherit; brings extra-info to exact parity with fields, including the same known deferred-annotation limitation as #12000), with a regression test in the style of test_extra_generic_class — it passes the test_main.py / test_generics.py / test_forward_ref.py / test_edge_cases.py suites with no new failures. Per the contributing guidelines I'd like to be assigned before opening the PR — happy to submit it right away.

Example Code

from typing import Generic, TypeVar
from pydantic import BaseModel, ConfigDict

T = TypeVar('T')

class M(BaseModel, Generic[T]):
    model_config = ConfigDict(extra='allow')
    __pydantic_extra__: dict[str, T]
    y: T

class Sub(M[int]):
    pass

print(Sub(y=1, x='not_an_int').x)  # 'not_an_int' — should raise ValidationError
print(Sub.model_json_schema().get('additionalProperties'))  # {} — should be {'type': 'integer'}
