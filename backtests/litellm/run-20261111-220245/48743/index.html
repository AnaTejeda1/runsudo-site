[Bug]: Gemini grounding annotations drop additional sources for a passage

Tie

The judges split evenly between our patch and the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the root cause the same way: they replace the `chunk_indices[0]` lookup with a loop over every index in `groundingChunkIndices`, skipping indices absent from `chunk_to_uri_map`. The independent tests confirm both pass all three scenarios (two web sources, non-web first source, several multi-source passages) where base fails. Correctness is equal; Patch B dropping the `chunk_indices` truthiness check is harmless since iterating an empty list emits nothing.

The difference is in tests and craft. Patch B adds two explicit, separately named tests that map one-to-one onto the two scenarios called out in the issue (multiple web sources per passage, and web sources following a non-web first index), with literal expected annotations that are easy to read and that reproduce the issue's own example exactly. They are placed next to the existing `test_vertex_ai_annotation_conversion` tests, matching the surrounding file's conventions. Patch A's single parametrized test does cover both scenarios (via `[2, 1, 0]` with a retrievedContext chunk) plus an extra support, but its expected value is built by a list comprehension over the input, which is harder to read and edges toward re-deriving the result rather than stating it. Patch B's early `continue` on a missing segment also flattens nesting and its comment states why multiple annotations are emitted.

These are small margins, but B's tests communicate the fix more directly and sit with related tests, so B is the better patch.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours. The issue

View on GitHub

Description

Gemini can attach several sources to the same grounded passage, but LiteLLM converts only the first source index to an annotation. The other source associations are lost even when Google returned them

Config

This reproduces directly in the Google grounding converter, without credentials or a proxy configuration

LiteLLM Version

1.109.0, current main at f1795e6d447a4e5a3660de0d2fde5e1f44f52929

Steps to Repro

Run the following against an unmodified checkout

from litellm.llms.vertex_ai.gemini.vertex_and_google_ai_studio_gemini import VertexGeminiConfig

metadata = {
    "groundingChunks": [
        {"web": {"uri": "https://example.com/a", "title": "A"}},
        {"web": {"uri": "https://example.com/b", "title": "B"}},
    ],
    "groundingSupports": [
        {
            "segment": {"startIndex": 0, "endIndex": 5},
            "groundingChunkIndices": [0, 1],
        }
    ],
}
annotations = VertexGeminiConfig._convert_grounding_metadata_to_annotations([metadata], "Claim")
print(annotations)

Actual output

[{'type': 'url_citation', 'url_citation': {'start_index': 0, 'end_index': 5, 'url': 'https://example.com/a', 'title': 'A'}}]

Expected output

[
    {'type': 'url_citation', 'url_citation': {'start_index': 0, 'end_index': 5, 'url': 'https://example.com/a', 'title': 'A'}},
    {'type': 'url_citation', 'url_citation': {'start_index': 0, 'end_index': 5, 'url': 'https://example.com/b', 'title': 'B'}},
]

The converter reads chunk_indices[0] instead of iterating over all source indices. If the first index points to a non-web chunk, later valid web sources are lost too

This reproduces locally using synthetic grounding metadata. Fresh direct Gemini API calls through a local LiteLLM proxy also reproduced it on 2026-10-28. The unmodified base retained 12 of 18 source associations. The fixed converter retained all 19 of 19 source associations in a separate generation, with matching URLs, titles and text ranges. Each call contained six passages with multiple web sources, and counts were compared within each response
