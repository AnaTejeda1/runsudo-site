Issue #15878 Merged fix PR #16109 Run 6 Nov 2026 · run-20261106-192752 vuejs/core

KeepAlive deactivates its current child instead of unmounting it when unmounted after re-rendering under a pending ancestor Suspense (instance leaks)

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches make the four independent tests pass, so both fix the exact reported scenario (same-root re-render of the KeepAlive'd Suspense while the ancestor is pending, then unmount). The difference is where and how broadly they intervene.

Patch A fixes the invariant that actually breaks in KeepAlive's onBeforeUnmount: when the subTree is a Suspense whose patch was skipped, the mounted vnode is `suspense.activeBranch`, not `ssContent`, so it resets the flag on the active branch and also on the cached entry (the same approach #15711 already uses in pruneCacheEntry, and the exact fix the reporter validated). When the inner Suspense is in a normal state activeBranch === ssContent, so there is no behaviour change outside the broken case. Its four tests cover the issue scenario, a second non-visible cached child, and switching the KeepAlive child (new or cached) while the ancestor is pending; tracing the 'cached' variant shows A correctly unmounts both Tab (active branch) and Other (storage container), whereas the unchanged KeepAlive code under B would pick the never-activated `Other` ssContent as 'current', re-queue a deactivated hook on it, and leave it in the storage container.

Patch B rewrites the Suspense early-return so a nested boundary in retained (on-screen) content is patched while the parent is pending, except for root replacements. This does address the underlying skip the issue traced, and it is thoughtfully done (suspenseId-based 'retained' detection, deps-without-pendingBranch handling, a #8678 regression test). But it is a semantic change in a region with a documented history of regressions (#8678 → #10055 → #10184): retained content now visibly re-renders while the parent is pending (its own test asserts `tab 1`), which the issue did not ask for and which widens the blast radius. It also deliberately keeps the skip for root replacements, so the same KeepAlive flag-reset bug persists for the child-switch-while-pending variants, because KeepAlive's onBeforeUnmount is left assuming `getInnerChild(subTree)` is the mounted vnode.

On correctness for the reported issue both hold; on robustness across the issue's related KeepAlive cases A covers more; on scope and risk A is the narrower, lower-risk change consistent with existing conventions, while B's extra work adds risk rather than earning credit. A wins.

Steps to reproduce

The reproduction runs by itself on mount, just open it and read the log. The tree is:

<Suspense>                     <!-- root boundary -->
  <Shell v-if="page === 'shell'">
    <KeepAlive>
      <Suspense>
        <Tab :count="count" />
      </Suspense>
    </KeepAlive>
  </Shell>
  <NextPage v-else />          <!-- async setup, resolves after 100ms -->
</Suspense>
  1. Switch the root <Suspense> from Shell to NextPage. NextPage has an async setup, so the root boundary goes pending and keeps Shell mounted.
  2. While it is pending, change count, so the <KeepAlive> inside Shell re-renders.
  3. Let NextPage resolve. The root boundary unmounts Shell.

What is expected?

Tab is unmounted together with Shell and its <KeepAlive>: the log shows Tab deactivated and then Tab unmounted, the same as without step 2.

What is actually happening?

The log shows Tab deactivated twice and never Tab unmounted. Tab is moved into the storage container of a <KeepAlive> that no longer exists:

  • isUnmounted stays false and its effect scope stays active, so its watchers, intervals and other side effects keep running.
  • onUnmounted / onScopeDispose never run, and nothing can unmount or reactivate it anymore.

Without step 2, or without the inner <Suspense>, Tab is unmounted as expected.

Any additional comments?

Where we hit it. This is the tree Nuxt renders for a page with <NuxtPage keepalive>, where each page is wrapped in a <Suspense> inside the root boundary. Navigating from such a page to a page with an async setup changes the route, so the old page's <NuxtPage> re-renders while the root boundary is pending. The visible child route then leaks on every such navigation. In our app the leaked tabs kept polling the API every 10 s after the user had left the page.

Cause, as far as I could trace it:

  1. On the re-render, the inner <Suspense> is patched while an ancestor boundary is pending, so SuspenseImpl.process takes its early return (parentSuspense.deps > 0). It adopts the new vnode as suspense.vnode but never patches it, so suspense.activeBranch is still the vnode that is actually mounted.
  2. KeepAlive's instance.subTree now points to the new Suspense vnode, whose ssContent was never mounted.
  3. When the root boundary resolves and Shell unmounts, KeepAlive's onBeforeUnmount finds the current entry (cached.type === vnode.type && cached.key === vnode.key) and calls resetShapeFlag(vnode) with vnode = getInnerChild(subTree). That is the never-mounted ssContent, not the mounted activeBranch.
  4. The mounted vnode keeps COMPONENT_SHOULD_KEEP_ALIVE, so unmounting the inner <Suspense> calls deactivate on it instead of unmounting it. The first Tab deactivated is the da hook that onBeforeUnmount queues, the second one is this deactivate.

At onBeforeUnmount time in the reproduction, subTree.ssContent !== subTree.suspense.activeBranch: the first one has both keep-alive flags (768, it went through the cached path), the mounted one only COMPONENT_SHOULD_KEEP_ALIVE (256).

Since when. Bisected with the same reproduction: 3.4.8 and earlier unmount Tab. From 3.4.9 to 3.4.19 the root boundary never resolves in this scenario. From 3.4.20 on, Tab leaks as described. That lines up with the early return added in #10055 (3.4.9) and changed in #10184 (3.4.20).

Related. #15288 (the same early return, with KeepAlive caching a never-mounted vnode on a switch) and #15710 / #15711 (the same kind of flag reset on a vnode that is not the mounted one, in pruneCacheEntry). Neither covers the onBeforeUnmount path, and it still reproduces on 3.5.44.

Possible fix. In onBeforeUnmount, also reset the flag on the cached vnode, like #15711 does in pruneCacheEntry:

if (cached.type === vnode.type && cached.key === vnode.key) {
  resetShapeFlag(vnode)
  resetShapeFlag(cached)
  // ...
}

I checked this by patching the 3.5.44 global build: Tab is then unmounted, also when the <KeepAlive> holds a second, non-visible child. Resetting subTree.suspense.activeBranch instead works too.

Workaround we use until then: a router.beforeResolve guard sets the KeepAlive's include to [] when the navigation leaves the page, so the cache is pruned while the tree is still mounted normally, before the root boundary goes pending.

I am happy to open a PR with the fix and a regression test.
