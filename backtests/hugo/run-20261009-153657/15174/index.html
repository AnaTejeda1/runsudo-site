Panic when deleting a directory in static when server is running

Worse

The merged fix was judged better than our patch.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches add a `files.ComponentFolderStatic` case to the switch in `processPartialFileEvents`, so both remove the panic itself. They differ in what else they do.

**Correctness.** Patch A also goes after why static events reach the site build at all. `SourceFilesystem.Contains` only matched mounts where `dir.IsDir()` was true. That check needs the path to exist on disk, so a deleted directory or a file mount was never recognized as part of the static filesystem. The event then skipped the static syncer and fell through to the build path. Replacing that check with the stat-free `ReverseLookup` lets the static syncer claim deleted static paths, including file mounts and deleted mount roots. So A fixes both the symptom (the panic) and the routing gap behind it. Patch B only stops the panic and logs a line. Its own comment admits that a deleted static mount root can end up there, which suggests the syncer may still miss the deletion, leaving stale files in the publish dir.

The `Contains` change does add some risk, because other callers depend on its semantics. However, `ReverseLookup` is the canonical way to map a filename back to a component, so the change is well grounded.

**Tests.** Patch A adds server testscripts for deleting a file mount and a directory mount under static, run against a live `hugo server` and asserting no stderr. That directly matches the issue's scenario of a running server with a deleted directory. Patch B adds `TestRunning`-based Go tests, including deletion of a static subdir and of the static root. Some of these would likely panic before the fix, but they only assert home page content, not static sync behavior. Both test sets are reasonable. A's are closer to the reported scenario and cover mount edge cases that B ignores.

**Scope and craft.** Both changes are small and focused. B's `logger.Println` is harmless noise. A's comment that static changes are "handled by the static file syncer" is accurate once `Contains` is fixed.

Overall, A addresses the root cause more completely.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
