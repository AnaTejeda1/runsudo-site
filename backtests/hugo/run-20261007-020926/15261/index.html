The failure comes from input validation inside dessant/lock-threads v6.0.0, which rejects the new GitHub token length of more than 100 characters. Patch A bumps the pinned action to a newer release (v6.0.2) by commit SHA. That fixes the root cause where it lives, in the action's validation, and keeps the existing config and the repo's SHA-pinning convention. It is a one-line, low-risk change. Its correctness depends on the newer release relaxing the token validation, which this diff alone cannot confirm, but that is the obvious upstream fix and matches the scope of the issue. Patch B abandons the action and reimplements its behaviour in an ad-hoc bash script calling gh api. That is a broad redesign with real regression risk: it handles only 50 search results per type per run with no pagination. It posts a comment and adds labels before locking, so a mid-loop failure under set -e leaves threads half-processed. It relies on search-API `updated:` semantics, which only approximate lock-threads' inactivity logic. It drops the action's built-in handling of discussions, rate limits and dry-run/log output. It also hard-codes defaults such as PR_INACTIVE_DAYS=365 that were previously implicit. None of this is needed to resolve the token-length error, and it makes the workflow harder to maintain. Neither patch adds tests, which is expected for a workflow file. On correctness, scope and craft, Patch A is the better fix.
