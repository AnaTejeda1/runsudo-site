LinkExtractor calls process_value before applying allow and deny

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

The issue's stated expected behaviour is that allow/deny filter links before process_value is invoked. Patch A implements exactly that: when process_value is given, LxmlParserLinkExtractor builds a Link from the raw attribute value and runs the extractor's _link_allowed check before calling process_value, then still filters the processed result. It sensibly lets non-URL values (e.g. javascript: hrefs that process_value converts) through to process_value so the documented javascript example keeps working, only wires the filter when process_value is set (no cost otherwise), and updates the docstring to describe the new semantics. It adds meaningful tests covering each filter parameter, the javascript case, and the re-filtering of the returned value; the independent tests derived from the issue go from FAIL on base to PASS with A. Weaknesses of A: it is a behaviour change that can break users whose process_value rewrites a valid URL into one that only then matches allow (A's own test enshrines that this is now dropped), and it does a redundant safe_url_string/Link construction per link; these are real but modest risks. Patch B is docs-only, declaring the existing order intentional and pointing to Rule.process_links. The issue did allow for 'by design, but document it', so B is a defensible stance, but it leaves the reporter's actual expected behaviour unmet, adds no tests, and every independent test still fails under B. On correctness against the reported expectation and on tests, A is clearly ahead; its scope and craft are reasonable, so A wins.

Description

I'm rather new to scrapy, created some 100 spiders and now moved the data to a MySql database.
To check if the page is scraped before I decided to use a process_value function, in connection with a list retrieved from the database.
That part is working OK.

But, when I did that, I saw multiple "new" links in my tests, which should be filtered by "allow".

This can be by design, but at least the documentation does not state that.

Expected behavior: [What you expect to happen]

"allow" and "deny" lists should filter the links before calling process_value callable.

Actual behavior: [What actually happens]

"allow" and "deny" lists are ignored.

Reproduces how often: [What percentage of the time does it reproduce?]

Tried on 2 test spiders with the same results.

Additional context

I also could not find anything on web or in the issues here. Perhaps CrawlSpider/LinkExtractor/process_value seems not be used much...
