Fix some Plainify issues

Tie

The judges split evenly between our patch and the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the reported `<textarea><b>x</b></textarea>` -> `x` case and pass all five independent tests, so the decision rests on robustness, scope, and risk.

Patch B replaces the simplistic stripTags with golang.org/x/net/html's spec-compliant tokenizer, clearing the raw-text flag for everything except script/style so tags inside textarea/title/noscript are tokenized and stripped while script/style bodies are dropped. This directly addresses the issue's ask to make stripping 'more robust' by delegating tokenization (quoted attributes containing '>', comments, bogus comments, doctype, CDATA, case-insensitive names, '<' that isn't a tag) to a well-exercised library rather than hand-written code. The change is confined to StripHTML, keeps the existing '\n'->space and `<br>`/`</p>`->newline semantics and whitespace collapsing, and adds targeted tests in both template_test.go and the Plainify tests. Its only notable gap is a self-closing `<script/>` leaving the tokenizer in raw-text mode, which degrades gracefully (the following text is still emitted).

Patch A hand-rolls a new hhtml scanner, which is well tested and allocation-free, but it goes well beyond the ask: it refactors the unrelated summary-balancing scanner in page_markup.go to use the new package, deletes htmltemplate.StripTags, and introduces a new, unrequested output change (inserting a space between adjacent block elements, so `<h2>Title</h2><div>Text</div>` now yields 'Title Text' instead of 'TitleText'). That last change alters Plainify output for existing sites and is not something the issue asked for. The custom scanner also carries the usual hand-parser edge risks (e.g. `<!-->` is treated as an unterminated comment and swallows content until the next `-->`). A's benchmark and performance focus are nice but the issue explicitly trades 'simple/fast' for 'more robust'.

On correctness both resolve the root cause; on tests both are adequate (A's are broader, B's cover Plainify directly); on scope B is tightly focused while A's broader redesign and behavior change add risk; on craft both are clean. B is the better fix.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours. The reasoning above is one judge's, shown verbatim.
