--strict does not complain when non-existent markers are specified as args to pytest

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the root cause the same way: collect the identifiers from the compiled -m expression and, when strict/strict_markers is on, raise UsageError for any not in the `markers` ini list. Both pass all independent tests. The differences are in scope, tests, and craft. Patch B is tighter: it extracts idents with a single ast.walk over the already-built AST, factors the existing marker-name parsing and strict-check logic into two small helpers in structures.py that MarkGenerator now shares, and uses an error message that mirrors the existing '... not found in `markers` configuration option' wording so the -m failure reads like the decorator failure the issue asks to match. Its tests are considerably more thorough: parametrized over --strict-markers, --strict, ini strict_markers, ini strict, and addopts; over compound expressions, kwargs form, and multiple unknowns (checking sorted output); plus registered/builtin (skip, xfail) and non-strict regression cases. Minor nits: it reads expr._idents from outside the module and gives idents a default of frozenset() in __init__. Patch A reaches further than needed: it adds a RegisteredMarker NamedTuple and _iter_registered_markers to Config, rewrites the `--markers` output path (unrelated behavior with some risk), threads an idents set through Scanner and changes the internal expression() return type. Its unit tests rely on a FakeConfig cast to Config to call a Config method on a non-Config, which is brittle, and its pytester coverage is narrower (no ini-based strict, no kwargs/multiple-unknown cases). Patch B resolves the issue with less churn, a more consistent error, and stronger tests.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Each saw the issue and the two patches, labelled A and B in random order (two of them saw ours as A), with issue links and version numbers removed. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours. The reasoning above is one judge's, shown verbatim.

The issue

View on GitHub

I'm not seeing pytest complain in strict mode when filtering by markers that I haven't specified.
e.g. pytest --strict -m marker_that_i_tyoped_wrong mytests/
This will complete quite happily, deselecting all tests.

It would be nice if the behaviour were able to be changed, perhaps by another flag (to avoid causing sadness to anyone relying on the current behaviour), such that if the mark expression contained invalid marks it would cause a failure in the same way that a test containing invalid marks would.
