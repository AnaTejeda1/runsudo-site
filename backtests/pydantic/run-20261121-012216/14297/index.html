ByteSize float conversion changes exact byte counts and affects field bounds

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the root cause the same way: they replace the float round-trip with exact Fraction arithmetic, correct the stale '6.2EiB' expectation, and both pass every independent test (issue table values, le/ge bounds, other units, truncation preserved). The differences are in scope and edge handling. Patch A keeps the pre-existing overflow rejection (via an isinf check on the float product, raising the same error as before) and bounds cost by truncating the fractional part to 100 digits, with a comment that correctly argues the truncation cannot change the floored result given multipliers of the form 10**k or 2**k/8. Its tests cover decimal/binary/bit units, sub-byte truncation, >2**53 integers, and adversarial million-digit inputs, and assert the result type. Patch B is simpler to read, but it silently changes behaviour outside the issue: values like '1'*310 + 'KB' that were rejected on base are now accepted as 310-digit ints (it rewrites the existing test to encode this), and it adds unrelated ClassVar annotations. Its 4300-char cap is a reasonable guard for Fraction's int parsing, and the multiplier exactness test is a nice addition, but the unrequested acceptance of previously rejected inputs is a behaviour change the issue did not ask for and that the issue explicitly said should be preserved. On correctness they tie; on tests A is slightly more thorough; on scope A stays within the ask while B drifts. A wins narrowly.

Description

ByteSize converts the numeric part of a unit-bearing string through float before multiplying and truncating to an integer. This loses bytes even for ordinary decimal values: 1.005 KB validates as 1004 instead of 1005. Exact integers above 2**53 also lose precision when a unit is present.

The changed byte count affects validation constraints. With Field(le=1004), 1.005 KB is accepted even though it represents 1005 bytes. Conversely, Field(ge=1005) rejects that valid value. Python and JSON validation both reproduce the conversion error on current main (fa156283).

Examples of actual and expected byte counts:

InputActualExpected
1.005 KB10041005
1.003 KB10021003
9007199254740993 B90071992547409929007199254740993
9007199254740993 KB90071992547409920009007199254740993000

I have a focused patch that computes the scaled byte count using exact integer ratios, preserves fractional-byte truncation and the existing overflow check, and adds regression tests for both input modes and field bounds. All 31 ByteSize tests pass with the correction. May I be assigned this issue to submit the patch under the contribution guidelines?

AI assistance: this investigation, proposed patch, tests, and report were prepared with Codex assistance.

Example Code

from pydantic import BaseModel, ByteSize, Field


class Size(BaseModel):
    value: ByteSize


class LimitedSize(BaseModel):
    value: ByteSize = Field(le=1004)


print(Size(value='1.005 KB').value)  # 1004; expected 1005
print(Size.model_validate_json('{"value":"1.005 KB"}').value)  # also 1004
print(LimitedSize(value='1.005 KB'))  # accepted; expected ValidationError
print(Size(value='9007199254740993 B').value)  # loses one byte
