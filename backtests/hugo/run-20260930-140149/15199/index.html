related: Add option to tokenize headings

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Correctness decides this. Patch A indexes and queries tokenized heading words as StringKeyword, because it routes them through config.stringToKeyword. In searchDate, the applyFilter path only collects keywords that pass `kw.(FragmentKeyword)`, so ff.words is never populated for tokenized matches. With tokenize and applyFilter both on, no heading filter gets applied, and HeadingsFiltered would not return the matched headings. A's own TestRelatedFragmentsTokenizeApplyFilter expects filtered headings, so it likely fails. A also widens scope: it tokenizes ToKeywords for basic indices and adds an undocumented MinTokenLength option. The issue scopes the feature to fragment heading titles, so this adds behaviour beyond the ask. Patch B keeps tokenized words as FragmentKeyword and applies ToLower inside tokenize. Its filter closure re-tokenizes heading titles with the same config, so indexing, querying and applyFilter stay consistent. It falls back to the exact identifier for non-heading fragments and headings with no words, as the issue specifies. It also tokenizes opts.Fragments while keeping the exact id, strips HTML tags and entities, and adds the requested documentation text verbatim. B adds no tests, which is a real weakness, but A's tests exercise an apparently broken path. B is the correct, well-scoped implementation.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

I suggest using the name tokenize, documented as follows:

(bool) Whether to split multi-word values into individual keywords for indexing and matching. Currently applies to heading titles in indices of type fragments; non-heading fragments such as definition terms continue to use exact-identifier matching regardless of this setting. This increases index size in proportion to the average number of words per heading; use cardinalityThreshold to prune common words and reduce build time. Default is false.

What was wrong: related-content indices of type fragments only matched whole heading IDs. Two headings that share words, such as "Installing Hugo on Linux" and "Hugo Installation Guide", never matched each other.

What I changed (uncommitted, in related/inverted_index.go and docs/content/en/configuration/related-content.md):

  • New option: IndexConfig.Tokenize (tokenize). The config decoder ignores case, so no decoding change was needed.
  • Splitting: when it's on, heading titles are split into words (on anything that isn't a letter or digit), lower-cased when toLower is set. HTML tags and entities are removed first, because goldmark heading titles can contain markup.
  • Non-heading fragments: identifiers that aren't headings, such as definition terms, still match by their exact ID. So does a heading whose title produces no words.
  • One entry per word: each word is recorded once per page, so a page isn't counted twice for the same word.
  • Indexing and page queries: both use the same logic.
  • Fragments you pass in a search: each value is still sent whole, so exact IDs keep matching, and its words are added when tokenize is on.
  • applyFilter: a heading is kept if its ID matches, or, with tokenize, if any word of its title matches.
  • With tokenize = false: behaviour is the same as before.
  • Docs: the tokenize entry is under "Per-index settings", with your wording.
