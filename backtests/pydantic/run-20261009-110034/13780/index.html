Concurrent TypeAdapter construction raises RuntimeError on free-threaded Python

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the root cause the same way: they snapshot the class namespace in `_decorator_infos_for_class` before iterating. A uses `vars(typ).copy().items()` and B uses `list(vars(typ).items())`. On free-threaded CPython, both the dict copy and the list-extend fast path for dict items run under the dict's lock, so each snapshot is atomic. Both also harden `LazyLocalNamespace.data`. A copies only `MappingProxyType` namespaces; B snapshots every namespace with `list()`. Either is adequate.

The differences are in tests and scope. B adds a deterministic regression test. A `Mutating` object's `__class__` property, which `isinstance` reaches as a fallback, mutates the TypedDict's namespace during iteration. That test fails before the fix and passes after it, on any build, without depending on thread timing. B also adds stress tests that run a concurrent mutator thread.

A's tests all skip unless the build is free-threaded, and they are purely probabilistic. On a standard CI build they verify nothing.

A also bundles an unrelated behavioral change to `BaseModel.model_rebuild`. It replaces the selective `delattr` of the schema, validator and serializer with `set_model_mocks(cls)` when the model is already complete. This changes rebuild semantics in core model code. That is outside the issue's ask, adds regression risk and obscures the fix.

B's extra hardening in `_known_annotated_metadata` is small, low-risk and covered by its own test.

B wins on tests (deterministic, would fail before the fix) and on scope (no risky unrelated change).

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Description

Constructing separate TypeAdapter instances concurrently for the same new TypedDict can raise RuntimeError: dictionary changed size during iteration on free-threaded Python.

A full run produced 91 failures in 800 attempts with the GIL disabled and none with PYTHON_GIL=1. It also reproduces on Pydantic main at 1c8a330acc3077e77da64e3672c7c875fb4c6eaa.

Lazy annotation evaluation adds __annotations_cache__ while another thread iterates vars(typ).items() in _decorator_infos_for_class.

Example Code

from __future__ import annotations

import threading
from concurrent.futures import ThreadPoolExecutor

from pydantic import TypeAdapter
from typing_extensions import TypedDict


def run_round() -> None:
    class Record(TypedDict):
        value: int

    for index in range(1000):
        setattr(Record, f'metadata_{index}', index)

    barrier = threading.Barrier(8)

    def build(_: int) -> None:
        barrier.wait()
        TypeAdapter(Record).validate_python({'value': '42'})

    with ThreadPoolExecutor(max_workers=8) as executor:
        list(executor.map(build, range(8)))


for _ in range(100):
    run_round()

The synthetic attributes only widen the iteration window. They are not modified after the threads start.
