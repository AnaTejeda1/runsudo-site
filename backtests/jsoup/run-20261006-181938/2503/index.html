Both patches fix the root cause the same way. Each replaces the lower-case/upper-case `nextIndexOf` probes in `containsIgnoreCase` with a linear case-insensitive scan of the buffer, so mixed-case closers like `</TiTLE>` are now found. Both keep the scan cache consistent: Patch A stores `bufPos + offset` after `bufferUp`, and Patch B stores the absolute index after calling `bufferUp` up front. Correctness is effectively equal.

Tests are comparable. Both replace the old `assertFalse("one")` with a positive assertion and add a mixed-case `CharacterReader` test. Both add parser-level tests for the issue's `<title><p>` and `<textarea>` cases that would fail before the change. A's parser test checks a little more (the following `<p>Bar</p>` and `textarea.val()`), and B's checks that no `fake` or `body p` element is created. Neither is meaningfully weaker.

The difference is in craft. Patch B extracts `rangeMatchesIgnoreCase` from the existing `matchesIgnoreCase`, so the new scan reuses the comparison logic already in the class rather than duplicating it. Patch A adds a separate `charsEqualIgnoreCase` helper and a new `nextIndexOfIgnoreCase` method. That is a parallel implementation of the same comparison, with slightly different semantics (an extra lower-case-of-upper check), which adds a second place to maintain. B also calls `bufferUp()` before the cache check, which makes the cached-index comparison against `bufPos` more obviously sound. B adds a CHANGES entry, which is neutral-to-positive. On balance B is the slightly cleaner, more cohesive fix.

The issue

View on GitHub

RCDATA elements like <title> and <textarea> should match their end tags case-insensitively. A direct mixed-case closer works as expected: <title>Foo</TiTLE> closes the title. But when tag-shaped text appears before the closer, jsoup can miss the mixed-case end tag and leave RCDATA early.

For example, <title><p>Foo</TiTLE> creates a real body p element instead of keeping <p>Foo as title text. Similarly, <textarea><img src=x></TeXtArEa> creates an img element.

This was a premature optimization: the implementation only looked for consistent-case matches. I’ll fix it with a real case-insensitive scan.
