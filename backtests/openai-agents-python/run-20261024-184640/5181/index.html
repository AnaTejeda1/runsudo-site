Responses streaming: the error event is not treated as terminal, so a teardown failure masks the provider's error

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches apply the identical root-cause fix: adding "error" to `_ResponseStreamWithRequestId._TERMINAL_EVENT_TYPES`, which is exactly what the issue asks for, and both pass the independent tests (base FAIL-EXC with the masking RuntimeError, A and B PASS). Correctness on the reported scenario is therefore equal.

The difference is in scope and test quality. Patch A adds a second production change: a `break` out of the `async for` in `stream_response` once `terminal_failure_error` is set. With the terminal-set fix in place this is redundant (the next `__anext__` would hit `_cleanup_after_exhaustion`, which now debug-logs the teardown failure), so it is unrequested hardening that changes the post-terminal control flow for `response.failed`/`response.incomplete` as well as `error`: the stream is now closed via the explicit close path instead of being exhausted. Nothing in the issue motivates this, and it obscures which change actually fixes the bug. Patch B keeps the production change to the single line the issue identifies.

On tests, B adds a parametrised `_ResponseStreamWithRequestId` unit test over `error` and `response.failed` (fails on base for `error` with the RuntimeError, passes after) and an end-to-end `stream_response` test asserting the `ModelBehaviorError` carries the provider's code and message. These are focused, obviously runnable, and mirror the issue's own repro table. A's tests are broader (a parametrised rewrite of an existing test, a unit test, and a real httpx MockTransport SSE test with failing `aclose`), and the SSE-level test is attractive because it exercises real transport teardown. But it depends on an undefined-in-diff helper (`_response_with_terminal_status`) and on exact SDK SSE parsing of `event: error`, which cannot be confirmed here, and its `None` case locks in behaviour (teardown error surfacing when no terminal event) that the issue does not ask for. Since patch-authored test outcomes are not in evidence, A's extra coverage is unverified while B's is straightforward.

Net: equal correctness, adequate and precise tests on both sides, but A carries an unrequested behavioural change in the hot streaming loop and heavier, less certain tests. B is the cleaner fix for the issue as stated.

Describe the bug

_ResponseStreamWithRequestId._TERMINAL_EVENT_TYPES at src/agents/models/openai_responses.py:261 lists "response.error" but not "error". The SDK's error event is ResponseErrorEvent, whose type is Literal["error"]:

# openai/types/responses/response_error_event.py  (openai 3.0.0)
    type: Literal["error"]
    """The type of the event. Always `error`."""

So an error-terminated stream never sets _yielded_terminal_event. _cleanup_after_exhaustion then re-raises a transport teardown failure rather than debug-logging it. That teardown error escapes, and it masks the ModelBehaviorError built from the provider's own code and message.

The same file already holds the correct set. stream_response carries its own at :761-767, and that one lists both:

if chunk_type in {
    "response.completed",
    "response.failed",
    "response.incomplete",
    "error",
    "response.error",
}:

One line brings :261 into line with :761.

This is not a test-only path. _ResponseStreamWithRequestId is built at :916 with cleanup=lambda: api_response_cm.__aexit__(...), so the cleanup is a real httpx teardown.

Debug information

  • Agents SDK version: repository main at 588826c
  • Related library versions: openai 3.0.0 (the pin is openai>=3.0.0,<4)
  • Python version: 3.12
  • Operating system: Ubuntu 24.04
  • Model and model provider: OpenAI Responses API, any model. The trigger is the provider emitting an error event, not a particular model.
  • Does the issue reproduce with the latest release? Yes, on main at 588826c.
  • Does it occur consistently or intermittently? Consistently, whenever an error event arrives and the transport teardown then fails.

Repro steps

Driving _ResponseStreamWithRequestId with a cleanup that raises, one working event type and one that does not:

event type           terminal_seen   what __anext__ raised
------------------------------------------------------------------------------
response.failed      True            StopAsyncIteration (cleanup error suppressed)
error                False           RuntimeError: transport close failed

End to end on the real stream_response path, with the provider emitting an error event and the teardown failing:

on main:      caller sees -> RuntimeError: transport close failed
with the fix: caller sees -> ModelBehaviorError: Responses stream ended with terminal
              event `error`. code=server_error; message=the provider gave up.

The first hides the diagnosis the provider sent behind a transport artefact.

Expected behavior

An error event ends the stream, so the teardown failure is debug-logged and the ModelBehaviorError carrying the provider's code and message reaches the caller. That is what response.failed already does.

One related place that is not a second instance

A third terminal set at :1437-1442, in the websocket _stream_response, also omits "error". It is unreachable. event_type == "error" raises ResponsesWebSocketError at :1426, before that set is read. I left it alone.
