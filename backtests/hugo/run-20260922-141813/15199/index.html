related: Add option to tokenize headings

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Correctness (top criterion): Both add a `tokenize` option that splits heading titles into per-word FragmentKeywords for indexing, search, and applyFilter, and both correctly gate on the fragments HeadingsMap so non-heading fragments keep exact-identifier matching. But tokenization introduces a new failure mode that only B handles: when one document has multiple headings sharing a word (or a heading repeats a word), Patch A does `setm[kw] = append(setm[kw], doc)` once per occurrence, so the same doc lands in a keyword's posting list multiple times and its rank is inflated on every duplicated match. B guards this with a per-document `seenKW` set and has a dedicated regression test (TestRelatedFragmentsTokenizeDeduplication) showing the inflated-rank case. B also normalizes HTML entities in titles via `html.UnescapeString` (headings routinely contain `&amp;`, `&nbsp;`, smart-quote entities), with the &nbsp; fast-path edge case explicitly tested; A tokenizes the raw title with FieldsFunc and would mis-split entity-laden headings. Tests (criterion 2): B is markedly stronger — a splitWords unit test plus integration tests for basic fragments, HTML entities, applyFilter, case sensitivity, and dedup, all meaningful (fail-before/pass-after); A has a single (good) integration test. Where A leads: scope and completeness of the requested doc. A adds the exact documentation the issue asks for and stays tightly confined to fragments; B ships no docs at all, generalizes tokenization to the ToKeywords string/[]string path (all index types), adds an undocumented, unrequested MinTokenLength option (a separate issue), and carries whitespace/formatting churn in existing tests. That scope creep and missing documentation are real marks against B. However, the weighting order puts correctness and tests first, and B is clearly better on both — most importantly it fixes a genuine rank-inflation defect that A silently ships. The scope/doc advantages of A rank lower and don't outweigh that. Not a tie: the differences are substantial in both directions, and the higher-priority axes favor B.

I suggest using the name tokenize, documented as follows:

(bool) Whether to split multi-word values into individual keywords for indexing and matching. Currently applies to heading titles in indices of type fragments; non-heading fragments such as definition terms continue to use exact-identifier matching regardless of this setting. This increases index size in proportion to the average number of words per heading; use cardinalityThreshold to prune common words and reduce build time. Default is false.

What the agent reported

The change is complete and verified. Here's my final report.

What was wrong

Hugo's related content feature matched fragments-type indices only by exact heading identifier. Two pages with headings that share words but produce different anchor IDs (e.g. installation-on-linux vs installation-on-windows) were never considered related. The report asked for a new per-index tokenize option to split heading titles into individual word keywords so such pages match.

What I changed

related/inverted_index.go (production):

  • Added a Tokenize bool field to IndexConfig (default false; decoded automatically via the existing mapstructure.WeakDecode).
  • Added helpers tokenizeFragmentTitle (splits a title on non-alphanumeric runes), IndexConfig.fragmentToKeywords (tokenizes a heading title into per-word FragmentKeywords when Tokenize is set; falls back to the exact single FragmentKeyword(identifier) for non-heading fragments and whenever tokenize is off), and IndexConfig.headingTokens.
  • Routed both indexing (Add) and matching (Search) of a document's own fragments through fragmentToKeywords. Explicit opts.Fragments strings stay exact.
  • Taught searchDate's applyFilter path to keep a heading when its tokens (not just its exact ID) are among the matched keywords, so .HeadingsFiltered stays correct under tokenization.
  • The heading-vs-non-heading distinction uses tableofcontents.Fragments.HeadingsMap: only identifiers present there (real headings) are tokenized; definition-list terms and other fragments keep exact-identifier matching, exactly as the report requires.

docs/content/en/configuration/related-content.md: added the tokenize entry under "Per-index settings" with the report's exact wording.

related/related_integration_test.go (test): added TestRelatedFragmentsTokenize.

Test evidence

  • ./bt-test ./related/ → the related package passes; 0 packages failed.
  • New TestRelatedFragmentsTokenize passes now. Before the production change it failed: with tokenize = true the build produced Related p1::END (option silently ignored) instead of the expected Related p1: p2|Installation on Windows:END. The test also asserts the tokenize = false branch yields Related p1::END, proving the match depends on the new code.
  • Pre-existing tests still pass: TestRelatedFragments, TestSearch, TestDecodeConfig, TestCardinalityThreshold, TestToKeywordsToLower, TestToKeywordsAnySlice — confirming no regression in the exact-identifier path (byte-identical when tokenize=false).

Requirements checklist

  1. Add per-index tokenize (bool) option — ✅ implemented; decodes from config, default false.
  2. Splits multi-word values into individual keywords for indexing and matching — ✅ in both Add and Search.
  3. Applies to heading titles in fragments indices — ✅ tokenizes only identifiers found in HeadingsMap.
  4. Non-heading fragments (e.g. definition terms) keep exact-identifier matching regardless — ✅ they fall through to FragmentKeyword(identifier).
  5. Works with cardinalityThreshold to prune common words — ✅ no code needed; tokens are ordinary keywords already pruned by Finalize.
  6. Default false — ✅ zero value, verified by the tokenize=false test branch.
  7. Documentation with the given wording — ✅ added under "Per-index settings".

Known limitation (non-blocking)

The reviewer flagged, and I confirm, that searchDate keeps a single fragmentsFilterCfg: if a site configures multiple fragments indices with applyFilter=true that differ in their tokenize setting, the last-matched index's flag governs filtering for all of them. This does not affect the common single-fragments-index case, introduces no regression to existing behavior, and mirrors the pre-existing flat-fragmentsFilter design. I left it as-is to keep the change minimal.
