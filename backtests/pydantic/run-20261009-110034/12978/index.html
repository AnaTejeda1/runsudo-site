mypy [arg-type]-error when passing in type that can be converted to RootModel

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches make the same core fix. They register `_RootModelMetaclass` with the metaclass hook so it is treated as a pydantic model metaclass. They also let the plugin generate `__init__` for `RootModel` itself, overriding its hand-written typed `__init__`. With `init_typed` unset, `RootModel[float]('1.0')` is then accepted, which resolves the issue.

The difference is a side effect of generating `__init__` for the bare `RootModel`. The plugin has always built the `root` argument as `ARG_OPT`, even when there is no default. Under Patch A, `RootModel[float]()` therefore type-checks cleanly with the plugin enabled. Before the change, `RootModel`'s own `__init__` reported a missing argument. So Patch A fixes the issue but removes an existing check.

Patch B avoids this. It makes the root argument `ARG_POS` when there is no default and keeps it `ARG_OPT` when there is a default or `force_optional` is set. Missing `root` is now reported for both `RootModel[float]()` and subclasses. This brings the plugin in line with the non-plugin behavior instead of loosening it.

Tests: Patch B covers more ground:
- positional and keyword `root`
- `assert_type` on `.root`
- `RootModel[int]`
- a subclass
- the missing-argument case
- a new `mypy-plugin-strict.ini` run showing typed init still reports `arg-type` errors

Patch A tests only the positional call for the alias and a subclass. Its tests do not exercise the regression it introduces.

Patch B's extra `kind` change touches a little more code, but it is directly motivated by the new `__init__` generation and closes a hole the fix would otherwise open. B is the more correct and better-tested fix.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Initial Checks

  • I confirm that I'm using Pydantic V2

Description

The below example code (named foo.py) passes when running python foo.py as the input "1.0"-string gets converted to float. However, running mypy foo.py (with or without --strict) gives the following error:

foo.py:11: error: Argument 1 to "RootModel" has incompatible type "str"; expected "float"  [arg-type]
Found 1 error in 1 file (checked 1 source file)

I would expect the BaseModel-fields and the RootModel-field to behave the same in this case. That is, if the value can be converted – either via a custom made validator or through the conversion table – then mypy should not raise an error.

Example Code

import pydantic


class Foo(pydantic.BaseModel):
    f: float


RFoo = pydantic.RootModel[float]

f = Foo(f="1.0")
rf = RFoo("1.0")

assert isinstance(f.f, float)
assert isinstance(rf.root, float)
assert f.f == rf.root
