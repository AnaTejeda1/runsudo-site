compiler-sfc: loadTSConfig re-parses the whole tsconfig extends chain for every config it walks

Worse

The merged fix was judged better than our patch.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the root cause the same way: a module-level `Map<string, TS.ExtendedConfigCacheEntry>` passed as the 8th argument of `parseJsonConfigFileContent`. They differ in how `invalidateTypeCache` handles the new cache.

Patch B clears the extended-config cache on every `invalidateTypeCache` call, including each `.vue` or `.ts` edit. That is correct but needlessly throws away the cache on routine HMR edits. More importantly, B never clears `tsConfigCache`. In real dev/HMR, editing `tsconfig.base.json` only deletes the base's own entry and the ref-map entry. The already-parsed configs of the root tsconfig that extends it stay stale. B's test of base edits likely passes only because the spec's `resolve` helper invalidates every file in the fixture, which masks the gap.

Patch A clears both `extendedConfigCache` and `tsConfigCache` when a `.json` file changes. This directly answers the issue's caveat that an edited `tsconfig.base.json` must not go stale. It also keeps the cache intact across ordinary source edits. Clearing on any `.json` file is broad, but the cost is low and it is safe.

Tests: both count reads of the shared base and would fail without the fix. A uses three referencing configs; B uses two. B additionally exercises the edit scenario, but as noted that test does not truly cover the HMR path. Scope and craft are comparable.

A's invalidation logic is more correct and preserves the cache's benefit, so A wins.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Vue version

Link to minimal reproduction

Steps to reproduce

git clone https://github.com/cainrus/vue-compiler-sfc-tsconfig-repro
cd vue-compiler-sfc-tsconfig-repro
npm install
npm run repro

The generator builds a workspace of 150 packages, each with its own tsconfig.json that
extends one shared base and declares references to its group, plus one SFC per package whose
props type is imported from another package by alias. Both arms compile the same components; the
cached arm differs only in that it supplies an extendedConfigCache, through the public
registerTS hook, as the 8th argument the package leaves undefined.

What is expected?

Parsing the same extends chain repeatedly should reuse the parsed parent configs, as TypeScript's
own extendedConfigCache parameter exists to allow.

What is actually happening?

loadTSConfig calls ts.parseJsonConfigFileContent with five arguments, so the 8th
(extendedConfigCache) is always undefined:

https://github.com/vuejs/core/blob/main/packages/compiler-sfc/src/script/resolveType.ts

const config = ts.parseJsonConfigFileContent(
  ts.readConfigFile(configPath, fs.readFile).config,
  parseConfigHost,           // 2
  dirname(configPath),       // 3
  undefined,                 // 4
  configPath,                // 5
)                            // 6, 7, 8 omitted -- the 8th is extendedConfigCache

and then recurses through project references:

res.unshift(...loadTSConfig(refPath, ts, fs, visited))

So in a workspace whose packages all extend a shared base, that base is re-read and re-parsed once
per config the traversal reaches, and each parse allocates its own fully expanded paths map.
visited is a default parameter: it de-duplicates within one top-level call, never across calls.

Measured on the reproduction — node 22.23.2, @vue/compiler-sfc 3.5.41, typescript 5.9, one arm
per process (tsConfigCache is module scope):

stock2900290011.1 s1346.8 MB
cached2900**1**1.9 s30.2 MB

The parse count is identical in both arms. The cache does not remove parses — it makes each one
cheap and stops the expanded options object from being rebuilt. Retained heap is heapUsed after a
forced GC.

On a production Vue monorepo (2432 components, 514 tsconfigs, 4051 project references, a 118 KB
shared base with 1342 paths entries), compiling 400 of its real components through
compileScript with the same two arms:

cached7351**3**8.0 s188.7 MB

That is what led to this report: tsconfig parsing dominated the allocation profile of that
application's production build.

Does the cache change the result?

node parity.mjs in the reproduction re-implements loadTSConfig verbatim and runs it twice per
entry config, differing only in the 8th argument, comparing resolved compilerOptions,
projectReferences and fileNames for every parse the traversal produces:

runparses comparedpaths entries comparedmismatches
node parity.mjs400176 000**0**
MUTATE=1 node parity.mjs (cached arm reads a different config)400176 000336
MUTATE=2 node parity.mjs (one paths entry altered after parsing)400176 000400

The two controls are there because a comparator that always prints zero proves nothing. The same
comparison over the production monorepo's configs: 831 parses, 1 116 033 paths entries, 0
mismatches, with the controls reporting 114 and 831.

One consequence worth stating explicitly: with the cache, the expanded options object is **shared
by reference** (that is where the memory saving comes from), so it must not be handed to a consumer
that mutates it. resolveWithTS only reads matchedConfig.config.options, so that holds today.

Suggested fix

A module-level Map threaded into the 8th argument. One caveat a fix has to answer:
invalidateTypeCache currently clears tsConfigCache and tsConfigRefMap, and would need to clear
the new cache too, or an edited tsconfig.base.json would go stale in dev/HMR — TypeScript keys
extendedConfigCache by resolved path, so that is a targeted delete.

PR: #15480 — it also explains why a plain Map rather than createCache(), and why
invalidateTypeCache clears the cache instead of deleting one entry.

What the agent reported

I fixed it: tsconfigs that extends the same base now share one parsed copy of that base, so it's no longer re-read and re-parsed for every config the project-reference walk reaches. The full compiler-sfc suite passes and the new regression test fails without the fix.

What was wrong: loadTSConfig (packages/compiler-sfc/src/script/resolveType.ts) called ts.parseJsonConfigFileContent with only 5 arguments, so the 8th (extendedConfigCache) was always undefined. Each config reached through references therefore re-read and re-parsed the shared base, building its own expanded paths map each time.

What I changed (resolveType.ts, 9 added lines, uncommitted):

  • A module-level tsExtendedConfigCache = new Map<string, TS.ExtendedConfigCacheEntry>() is passed as the 8th argument. I checked the position against TypeScript's signature.
  • invalidateTypeCache now clears that cache entirely. A deleted entry is not enough, because the cached entry for a middle config in an extends chain already contains its parent's parsed content. Without the clear, an edited tsconfig.base.json would be served stale in dev/HMR.
  • The cached options object is now shared by reference. resolveWithTS only reads matchedConfig.config.options and never changes it, so this is safe today; the reviewer confirmed it.

Test evidence: a new test in resolveType.spec.ts, "ts module resolve w/ project references sharing an extended config". A root tsconfig.json references tsconfig.a.json and tsconfig.b.json, which both extend tsconfig.base.json (with a paths alias). The component imports its props type through that alias.

  • It checks that the props resolve correctly and that the base is read once.
  • Without the fix: it fails with expected 2 to be 1.
  • With the fix: it passes.
  • It then edits the base's paths and resolves again, expecting the new type.
  • With the .clear() temporarily removed: it fails with expected { foo: ['String'] } to strictly equal { bar: ['Number'] }, i.e. stale config.
  • With the clear restored: it passes.
  • Full suite: ./bt-test packages/compiler-sfc gives 19 files passed, 472 tests passed, 1 skipped. No existing tests were changed.
  • Review: the reviewer found no blocking issues and nothing unrelated in the diff.

Requirements:

  1. Reuse parsed parent configs through extendedConfigCache: done, as a plain module-level Map in the 8th argument, as the report suggests. Covered by the read-count assertion.
  2. Make invalidateTypeCache clear the new cache so an edited base doesn't go stale: done, with a full clear for the reason above. Covered by the edit-the-base step.
  3. Don't hand the shared options object to anything that changes it: checked; resolveWithTS only reads it, so no change was needed.
  4. tsConfigCache being capped at 500 entries: not addressed. The report says it is being filed separately.

Trade-off: invalidateTypeCache runs on every file change, not just tsconfig edits, so in dev/HMR the new cache is cleared often. That only costs re-parses when configs are actually reloaded, and the main benefit is within one walk of the references. Clearing only on tsconfig changes would mean tracking which files are tsconfigs, which I left out to keep the change minimal.
