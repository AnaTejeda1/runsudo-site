Investigate simplifying static checks for initialized Crawler

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches reach the issue's goal: the late-initialized Crawler attributes become non-Optional for mypy and every `assert crawler.stats`-style narrowing is removed, and the independent static-type tests pass on both. They differ in how they get there.

Patch A replaces the attributes with a `_LateAttribute` descriptor that raises RuntimeError on read before the crawl starts. That is honest typing with runtime enforcement, but it is a public behavior change with real risk beyond the issue's ask: `crawler.engine`/`crawler.stats` went from returning None to raising, so any third-party `from_crawler` or pre-crawl code that reads them (even just to check `is None`) now crashes; worse, because the error is RuntimeError rather than AttributeError, `hasattr(crawler, 'stats')` and `getattr(crawler, 'stats', None)` also raise, which is a surprising trap. It also removes the attributes from the instance dict and adds ~50 lines of descriptor/overload machinery. A's new tests only exercise the new RuntimeError behavior and class-level access; none check the static types the issue is actually about.

Patch B keeps runtime behavior identical (attributes stay None until set) and just annotates them as non-Optional with `# type: ignore[assignment]`, documenting the arrangement in the class comment and the API docs. It is a type-level simplification exactly matching the issue's 'investigate simplifying static checks' framing, with zero runtime risk to Scrapy or third-party code. It also extends the treatment to `spider`, consistent with the issue's 'components such as'. Its runtime test is largely tautological against base, but its new `tests_typing/test_crawler.mypy-testing` file with `reveal_type` checks and an assert-free component sample is a direct regression test for the reported problem that would fail on base and pass after.

A's downside is the type lie it accepts, but the project already relies on documented lifecycle guarantees (and RuntimeError-raising getters like get_extension) for these attributes, so the lie is bounded and documented. Weighing correctness/risk, the more on-target tests, and scope, B is the better fix; A's broader redesign adds API breakage without being required by the issue.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Each saw the issue and the two patches, labelled A and B in random order (two of them saw ours as A), with issue links and version numbers removed. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours. The reasoning above is one judge's, shown verbatim.

The issue

View on GitHub

After we changed the Crawler logic to initialize components such as Crawler.stats later, static checkers (specifically mypy) don't know that when code like self.crawler.stats.inc_value() is called, self.crawler.stats is already initialized, so we need to add asserts in all methods that do this. We should try to find a way to do the same with fewer asserts. This also applies to 3rd-party code (middlewares etc.).
