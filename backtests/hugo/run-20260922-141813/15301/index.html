Patch A documents the same behavior more briefly but pivots into a substantial new feature — a `security.http.proxyFromEnvironment` config field, a proxyTransport wrapper, and a per-request-context proxy decision — that addresses a *different* vector (env-proxy bypass) the issue never raises. But that stronger test only exercises A's out-of-scope feature, so it does little to resolve *this* issue. Weighing correctness against what the issue actually wants (documentation of an intentionally-correct behavior) plus scope discipline, B is the better-fitting fix; A is impressive engineering aimed partly at a different problem.

The issue

View on GitHub

In d6e6f9e500eebdeae8e28de830fff2e3bfc7d534 (unreleased) we added a dial-time URL validation to catch URLs that's valid according to the whitelist but that resolves to a loopback, private or link-local IP addresses. That check is skipped it if the user has a custom security.http.urls setup, as it would not make sense to block local development servers.

See CheckAllowedHTTPAddress.

This has been reported by @Reload3d as a potential security issue, and while I think the current behaviour is the pragmatic correct approach, I'm creating this issue for visibility and to see if this can be improved further (e.g. better documentation).

What the agent reported

Done. Here's the summary.

What the report asked for

Issue 15301 is a visibility/documentation ticket, not a behavior-change request. An unreleased commit added a dial-time IP validation (CheckAllowedHTTPAddress in config/security/securityConfig.go) that denies URLs which pass the security.http.urls text allowlist but resolve to loopback/private/link-local IPs. That check is deliberately skipped when the user customizes security.http.urls (so local dev servers aren't blocked). The maintainer considers the current behavior the pragmatic correct approach and explicitly does not want it changed — the ask is "better documentation."

What was wrong

Investigation (via explorer) confirmed the behavior was correct and working, but entirely undocumented for end users: docs/content/en/configuration/security.md never mentioned the connection-time address check or the customize-to-opt-out behavior, and the skip-when-customized branch (securityConfig.go:232) had no dedicated test (existing TestCheckAllowedHTTPAddress only covers the default-config enforced path).

What I changed

  1. docs/content/en/configuration/security.md — expanded the http.urls entry with a cross-reference and added a new "Remote resource address validation" section that documents (a) why the URL-text allowlist alone can be bypassed by a hostname resolving to an internal IP, (b) the connection-time IP check applied under the default config, and (c) that customizing security.http.urls opts out of that check and shifts responsibility to the user.
  2. config/security/securityConfig_test.go — added TestCheckAllowedHTTPAddressSkippedWhenURLsCustomizedIssue15301, a regression test that decodes a config with urls = ['.*'] and asserts CheckAllowedHTTPAddress returns nil for internal addresses (127.0.0.1, 10.0.0.1, 169.254.169.254, [::1]) that the default config denies — locking in the documented override contract.

No production code was changed (behavior must stay as-is, per the report).

Test evidence

  • ./bt-test ./config/security/... -run 'TestCheckAllowedHTTPAddress' → EXIT=0. The new test and the pre-existing TestCheckAllowedHTTPAddress both pass.
  • Reviewer confirmed the doc accurately describes the code, the anchor/reference links resolve, the test genuinely proves the bypass (addresses chosen are ones the default config denies), and nothing unrelated changed. I applied its one wording-precision fix (the check rejects several global-unicast-but-not-public ranges, so the doc now says "publicly routable" and enumerates the rejected ranges rather than equating public with "global unicast").

Honest note on the test: because this is a documentation-only ticket with no behavior change, the added test is a characterization/regression test — it passes both before and after, since it codifies existing (now-documented) behavior. Per the harness rules I'm disclosing this rather than presenting it as a fail-before/pass-after test; there is no behavioral fix for such a test to gate. I judged it worth shipping because it exercises the exact scenario the report describes and guards the documented contract against future silent regression.

Requirements checklist

  • "Better documentation" of the security.http.urls override behavior → Implemented. New docs section + cross-reference in security.md, verified accurate against the code by the reviewer.
  • Visibility of the skip-when-customized behavior (the reported concern) → Implemented + test-guarded. Documented for end users and covered by the new regression test.
  • Change the skip behavior itself → Intentionally skipped. The report states the behavior is the pragmatic correct approach and should not change; evidence: securityConfig.go is unmodified in the diff (git diff shows only the docs and test files).
