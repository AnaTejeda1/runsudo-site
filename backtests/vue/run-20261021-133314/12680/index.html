$el of templateRef points to comment VNode instead of first real child of component

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches share the same core approach: when the component's subTree is a DEV_ROOT_FRAGMENT, use filterSingleRoot to find the lone real root and expose its el as $el, and both follow HOC chains. The decisive difference is that Patch A gates the entire fix behind `__DEV__`, so a template compiled with comments preserved (DEV_ROOT_FRAGMENT set) but running on a production runtime still gets the comment node as `$el`. That is precisely the reporter's setup: the linked reproduction is in the playground's `__PROD__` mode, which pairs a dev-built compiler-sfc with the prod runtime. Patch B explicitly notes this case in its doc comment and resolves it unconditionally, so it fixes the issue as reported; Patch A would leave the reporter's own repro broken. Patch B's resolution also degrades safely: if the inner component has no subTree yet or no dev fragment, `getSingleRootEl` falls through to the existing `vnode.el`. On tests, Patch B adds a compiler-integration test in packages/vue that mirrors the issue (real `<!-- comment --><div>` template, click listener via $el, and v-if swap of the ref target), plus runtime-test unit cases for nested fragments, HOC chains with re-render, and a guard that true multi-root components keep the fragment anchor. Patch A's tests are hand-built block vnodes and include useful Suspense and mounting-safety cases, and its Suspense traversal is a genuine extra that B lacks, but that is adjacent to the ask. Scope and craft are comparable; A's `found` flag and B's mutual recursion are both readable. The `__DEV__` gating is a correctness gap on the reported scenario, so B wins.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Steps to reproduce

Hi, I just spent some hours debugging a very strange behavior when accessing the underlying element of a component ref by using templateRef.$el. The component I placed the template ref on had only one root level <div> inside its template, however there was a comment above it. It looks like this leads to the element being referenced by the template ref being the VNode of this comment instead of the <div> element.

Steps to reproduce:

  1. Open the Playground
  2. Open the console and see that the element referenced by childRef.value.$el is a text VNode
  3. Click on the text "Test" in the preview (Nothing should be logged to the console)
  4. Go into the component "Child.vue" and remove the comment in line 2
  5. After a hot reload (or manual one) childRef.value.$el should point to the div element as logged to the console. Clicking on the text "Test" in the preview should now also log "Clicked Test" to the console

What is expected?

I would expect templateRef.$el to point to the first real element inside the component excluding comments.

What is actually happening?

templateRef.$el points to a VNode for the comment inside the components template.
