Regression in 2.35.x: JSON property named toString cannot be evaluated correctly in expressions / IF node

Tie

The judges split evenly between our patch and the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches make the identical root-cause change: they drop the six Object.prototype method names (toString, valueOf, toLocaleString, hasOwnProperty, isPrototypeOf, propertyIsEnumerable) from the runtime sanitizer denylist in safe-globals.ts, so `obj[key]` no longer throws for those keys and matches the transform-time denylist that already allowed `obj.key`. That resolves the issue's dot, bracket, and computed-key scenarios equally. The independent harness crashed on all three trees, so it provides no separation. The differences are in tests and craft. Patch B's tests reproduce the issue faithfully: the exact `.some(item => item.toString === 'To Do')` IF expression over Jira-shaped changelog data, the bracket-notation variant inside the callback, root-level `$json.toString`, a runtime-computed key, Object.keys iteration, and an object literal with a toString key, plus sibling prototype names. Its in-place comment explains why the names are deliberately absent. Patch A's tests are also solid and add a useful check that prototype members still resolve when no data field exists, and it corrects the header comment from 'superset' to 'must match'. However, A's new parity test calls `isSafeObjectProperty` without any import change visible in the diff; the existing parity file most plausibly imports the denylist set rather than that helper, so there is a real risk the added test does not compile, which would count as no test. B carries no such risk and its tests are more directly tied to the reported scenario, so B edges out A on tests and reliability while matching it on correctness and scope.

Bug Description

After upgrading from n8n 2.34.x to 2.35.x, expressions that access a JSON property literally named toString no longer evaluate correctly.

This affects payloads from external systems that legitimately use toString as a JSON property name. In my actual use case, the payload originates from a Jira webhook, so I do not control the upstream property name.

The same workflow works correctly on n8n 2.34.x.

I created a minimal reproduction that does not require Jira or any external service.

To Reproduce

  1. Import the workflow below.
  2. Click Execute workflow.
  3. Set Test Data1 creates objects containing "toString": "To Do".
  4. Create Safe Alias copies the same value to JiraToString while preserving the original toString property.
  5. Two IF nodes evaluate the same value:
  6. item.JiraToString === 'To Do'
  7. item.toString === 'To Do'
  8. On n8n 2.35.x, observe that the JiraToString condition follows the true branch while the toString condition follows the false branch.
  9. On n8n 2.34.x, both conditions work correctly.

Bracket notation (item['toString']) also does not resolve the issue.

Expected behavior

Given an object containing:

{
  "toString": "To Do",
  "JiraToString": "To Do"
}

both expressions should evaluate to true:

item.toString === 'To Do'
item.JiraToString === 'To Do'

Actual behavior

On n8n 2.35.x:

PropertyResult
JiraToStringTrue
toStringFalse

On n8n 2.34.x, both evaluate to True.

Renaming or aliasing toString to another property name works around the problem.

Additional context

In the real workflow, toString comes directly from Jira changelog data, for example:

{
  "field": "status",
  "fromString": "Pending For Approval",
  "toString": "To Do"
}

Because this is an upstream Jira payload, changing the source schema is not an option. A Code node alias is currently required as a workaround.

This appears to be a regression introduced in the 2.35.x release line.
