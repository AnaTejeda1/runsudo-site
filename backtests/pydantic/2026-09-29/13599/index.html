PEP 695 type aliases don't work with callable discriminators

Worse

The merged fix was judged better than our patch.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches share the identical root-cause fix: passing `definitions` through `apply_discriminator` into `Discriminator._convert_schema` and teaching that method to resolve `definition-ref` schemas from the definitions dict when no `handler` is present (the deferred/callable discriminator path). Correctness is essentially equivalent; both resolve M3 by resolving the type-alias-produced definition-refs both at the root and per-choice. Patch A consolidates the resolution logic into a single `_resolve_ref` helper used in both places, which is cleaner and removes the duplicated try/except pattern; it does broaden the root guard from `handler is not None` to always checking `definition-ref` (raising MissingDefinitionForUnionRef when unresolved), a minor defensive change that in practice never fires without handler-or-definitions and matches `_apply_to_root`'s intent. Patch B is more conservative, keeping `(handler is not None or definitions is not None)` guards, but at the cost of duplicated resolve logic and a manual `raise LookupError`. The decisive difference is tests: Patch A adds a concise, idiomatic test using `TypeAliasType` placed directly beside the existing analogous test, matching surrounding conventions. Patch B's test relies on `exec` of a source string with a version-gated skip and mutable globals — more faithful to the raw issue text but noticeably uglier and harder to maintain, with no added coverage value over A's equivalent runtime type-alias construction. A wins on craft and test quality with no correctness regression.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

What the agent reported

Summary

What was wrong: PEP 695 type X = ... statement aliases failed as the annotation for a field with a callable Discriminator when union members carried Tag(...), raising PydanticUserError:Tagnot provided for choice {'type': 'definition-ref', ...} used withDiscriminator``.

The root cause: a PEP 695 type statement wraps its union in a definition-ref (unlike the old-style TypeAlias, which produces an inline union). The callable-discriminator path in apply_discriminator (_discriminated_union.py:68) called Discriminator._convert_schema(schema) without forwarding the definitions dict, and _convert_schema only dereferenced definition-ref schemas when a handler was present. With no handler and no definitions, it couldn't resolve the ref to reach the tagged union, so it errored.

What I changed (minimal, 2 files):

  • pydantic/_internal/_discriminated_union.py:68 — forward the definitions dict: discriminator._convert_schema(schema, definitions=definitions).
  • pydantic/types.py — Discriminator._convert_schema gained a definitions parameter and a local resolve_ref_schema helper that resolves a definition-ref via the handler when present, else via the definitions dict, else raises LookupError. Both the top-level and per-choice definition-ref guards were broadened from handler is not None to (handler is not None or definitions is not None). Existing MissingDefinitionForUnionRef, except LookupError, and pydantic_internal_union_tag_key behavior preserved.

Test evidence:

  • Added test_callable_discriminator_pep695_type_alias in tests/types/unions/test_discriminated_union.py — gated with skipif(sys.version_info < (3, 12)), uses exec() to keep PEP 695 syntax out of module top-level, and asserts the discriminator routes {'type': 'A1'}→A1 and {'type': 'A2'}→A2. Confirmed failing before the fix (callable-discriminator-no-tag) and passing after.
