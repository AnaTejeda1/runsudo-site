Description

The below example code (named foo.py) passes when running python foo.py as the input "1.0"-string gets converted to float. However, running mypy foo.py (with or without --strict) gives the following error:

foo.py:11: error: Argument 1 to "RootModel" has incompatible type "str"; expected "float"  [arg-type]
Found 1 error in 1 file (checked 1 source file)

I would expect the BaseModel-fields and the RootModel-field to behave the same in this case. That is, if the value can be converted – either via a custom made validator or through the conversion table – then mypy should not raise an error.

Example Code

import pydantic


class Foo(pydantic.BaseModel):
    f: float


RFoo = pydantic.RootModel[float]

f = Foo(f="1.0")
rf = RFoo("1.0")

assert isinstance(f.f, float)
assert isinstance(rf.root, float)
assert f.f == rf.root

What the agent reported

I've reached a well-evidenced conclusion. No code change is safe here, and the reason is concrete.

Summary

What the report asks: that mypy stop raising error: Argument 1 to "RootModel" has incompatible type "str"; expected "float" [arg-type] for pydantic.RootModel[float]("1.0"), so it behaves like BaseModel(f="1.0") (which produces no error without the plugin), since pydantic coerces "1.0" → float at runtime.

What I found: The reported behavior is intended by design and locked in by a deliberate existing test — implementing the request would require weakening that test, which I will not do.

Evidence gathered:

  • pydantic/root_model.py:60 — def __init__(self, /, root: RootModelRootType = PydanticUndefined, **data). root is deliberately typed with the model's generic root type, so RootModel[float](...) requires a float. This is exactly what triggers the reported [arg-type] error.
  • tests/typechecking/root_model.py:8 — bad_root_model = IntRootModel('1') # type: ignore[arg-type] # pyright: ignore[reportArgumentType]. This is an explicit negative test (variable literally named bad_root_model, following the valid IntRootModel(1) on line 7) asserting that passing str into RootModel[int] must produce an [arg-type] error. Added intentionally by a maintainer in PR #10623.
  • tests/typechecking/pyproject.toml — warn_unused_ignores = true (mypy) and reportUnnecessaryTypeIgnoreComment = true (pyright): an ignore comment with no matching error is itself a failure.
  • tests/typechecking/README.md:7 — this suite explicitly "do[es] not relate to the Mypy plugin"; it tests the raw type hints — i.e. precisely the no-plugin scenario in the report.
  • Runtime — confirmed via uv run python: the example runs and coerces correctly. The problem is purely about static typing.

The report's requested case (str → float root) and the tested case (str → int root) are the same shape. A static type checker has no access to pydantic's runtime coercion table, so any change broad enough to silence the float case (widening root to Any, adding a str overload, etc.) necessarily also silences the int case on line 8 — making its ignore comments unnecessary and failing the type-checking suite. An independent reviewer verified all of this adversarially and found no static-checker-compatible fix.

The apparent inconsistency with BaseModel is not a bug: BaseModel.__init__(self, /, **data: Any) accepts Any only because keyword fields can't be typed without the plugin (a loss of checking, not a feature) — and with the plugin, Foo(f="1.0") would be flagged too. RootModel has a single typed positional root, so it can and does verify it. This is a deliberate design difference.

Test note (required by my rules): tests/typechecking/root_model.py:8 directly contradicts the report. Per the constraint never to weaken, skip, or loosen an existing test, I did not modify it and made no production change that would.

Requirements checklist

  1. "mypy should not raise [arg-type] for RootModel[float]("1.0")" (main ask) — Not implemented. Doing so requires typing root loosely, which makes the # type: ignore[arg-type] / # pyright: ignore[reportArgumentType] on tests/typechecking/root_model.py:8 unused and fails the type-checking suite under warn_unused_ignores/reportUnnecessaryTypeIgnoreComment. Evidence: pydantic/root_model.py:60, tests/typechecking/root_model.py:8, tests/typechecking/pyproject.toml, tests/typechecking/README.md, PR #10623.
  2. "RootModel-field should behave the same as BaseModel-fields" — Skipped as intended behavior. The asymmetry stems from BaseModel.__init__(**data: Any) being untypable per-field without the plugin; under the plugin both are strict. Evidence: pydantic/main.py:253 vs pydantic/root_model.py:60.

No files were changed; the working tree is clean. No live mypy/pyright output was captured because neither is installed in this offline environment (uv cannot fetch them with the network disabled); the conclusion rests on the source and the deliberate typechecking test, independently confirmed.

If the pydantic maintainers decide this should change, it is a policy decision that must also update/remove the assertion at tests/typechecking/root_model.py:8 — which is outside what I'm permitted to do here.
