looseEqual() reports Map and Set instances with different contents as equal

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the root cause. Each adds explicit Map/Set handling before the generic `Object.keys` path, so the `String(a) === String(b)` fallthrough no longer reports any two Maps or Sets as equal. Each also adds a v-model `<select>` regression test that would fail before the change.

The difference is Map semantics. Patch A's `looseCompareMaps` checks keys with `b.has(key)`, which is strict SameValueZero identity, and only compares values loosely. As a result, two Maps with structurally equal object keys (`new Map([[{id:1}, x]])` vs another `{id:1}` key) compare unequal. So do Maps keyed by `1` vs `'1'`, even though `looseEqual(1, '1')` is true and arrays and objects elsewhere get fully loose comparison. That makes Map behavior inconsistent with the function's own loose semantics. The issue asks for consistency with `looseEqual`'s semantics, using object elements in Sets as its example.

Patch B treats Map entries as `[key, value]` pairs and matches them one-to-one with `looseEqual`. Keys and values are therefore both compared loosely and order-insensitively. This matches the Set treatment, and B's tests cover it explicitly (object keys `{id:1}` vs `{id:'1'}`). Both use one-to-one greedy matching for Sets, which is sound given `looseEqual` behaves as an equivalence. Both place the checks safely: A before `isObject`, B inside the both-objects branch.

On tests, A's v-model test is slightly more thorough because it toggles the model back to `mapA`. B's looseEqual tests cover more edge cases (loose keys, a swapped-values map, `1`/`'1'` vs `1`/`2` sets). On craft, A is O(n) for Maps and a bit more readable, while B shares a single helper. These are minor.

B's more consistent loose semantics for Map keys tips the balance.

Vue version

3.5.x / main (verified at a2b40db)

Link to minimal reproduction

Reproducible directly against the repo (see below) — looseEqual is not exported publicly, so the SFC Playground can only show the v-model symptom, not the root cause.

Steps to reproduce

looseEqual() in packages/shared/src/looseEqual.ts reports unrelated Map and Set instances as equal:

import { looseEqual } from '@vue/shared'

looseEqual(new Map([['a', 1]]), new Map([['b', 2]])) // true, expected false
looseEqual(new Set([1]), new Set([2]))               // true, expected false
looseEqual(new Map([['a', 1]]), new Map())           // true, expected false

This surfaces to users through v-model on <select>. The following selects the wrong option:

const mapA = new Map([['id', 1]])
const mapB = new Map([['id', 2]])
const selected = ref(mapB)
<select v-model="selected">
  <option :value="mapA">A</option>
  <option :value="mapB">B</option>
</select>

el.selectedIndex is 0 (option A) when it should be 1, because looseEqual(mapA, mapB) returns true and the loop in setSelected stops at the first option.

What is expected?

Map/Set values with different contents compare as not equal, so v-model selects the option that actually matches.

What is actually happening?

Map and Set fall through to the generic object branch. Object.keys() on either is always [], so the key-count check passes and the for...in loop body never executes — entries are never compared. Execution then reaches the final line:

return String(a) === String(b)

Every Map stringifies to '[object Map]' and every Set to '[object Set]', so any two of the same type are reported equal.

Note this differs from Date and Symbol, which are given explicit branches above, and from arrays and plain objects, which compare correctly:

looseEqual([1], [2])       // false, correct
looseEqual({ a: 1 }, { a: 2 }) // false, correct

packages/shared/__tests__/looseEqual.spec.ts has 13 cases but none for Map/Set, which is why this hasn't been caught.

Possible fix

Add explicit branches before the generic object check, mirroring the existing Date/Symbol pattern. isMap and isSet already exist in packages/shared/src/general.ts. Set needs content comparison rather than reference lookup to stay consistent with looseEqual's semantics (e.g. new Set([{ a: 1 }]) vs new Set([{ a: 1 }])).

Worth confirming the intended semantics first: should Map comparison be key-order-insensitive, and should Set compare loosely (looseEqual per element) or strictly? Happy to open a PR with tests once the direction is confirmed.

What the agent reported

looseEqual() now compares Map and Set by their contents, so <select v-model> with Map option values selects the right option. The new regression tests failed before the fix and pass after it, and 445 tests across the nearby suites pass. Nothing is committed; all changes are in the working tree.

What was wrong: looseEqual had no branch for Map or Set, so they were handled like plain objects. Object.keys() returns [] for both, so no entries were ever compared, and the function ended at String(a) === String(b). That is always '[object Map]' or '[object Set]', so any two Maps, or any two Sets, came out equal. In setSelected, that made the first option with a Map value match every time.

What I changed:

  • Fix (packages/shared/src/looseEqual.ts): two new branches, placed before the generic object branch and following the existing Date/Array pattern. They use the isMap and isSet helpers that already exist, plus two small helpers:
  • Maps: equal only if they are the same size and every key in one is in the other with a loosely equal value. Key order doesn't matter, and keys must be the same key (identity), not just look alike.
  • Sets: equal only if they are the same size and each element pairs with a different loosely equal element of the other Set, in any order. So new Set([{a:1}]) equals new Set([{a:1}]), but Set([{a:1},{a:1}]) does not equal Set([{a:1},{b:2}]).
  • A Map or Set compared with any other type (Map vs Set, plain object, array) is unequal.
  • Tests:
  • packages/shared/__tests__/looseEqual.spec.ts: two new tests, compares maps correctly and compares sets correctly, covering the report's three examples plus the cases above.
  • packages/runtime-dom/__tests__/directives/vModel.spec.ts: new test should work with single select (option value is Map). It is the report's mapA/mapB example and checks that selectedIndex is 1, then 0 after switching the model to mapA.

Test evidence:

  • Before the fix: all three new tests failed — looseEqual(Map a:1, Map b:2) returned true, looseEqual(Set [1], Set [2]) returned true, and selectedIndex was 0 instead of 1. The other 51 tests in those two files passed.
  • After the fix: both files pass, 54 of 54.
  • Wider run (./bt-test packages/shared packages/runtime-dom/__tests__/directives packages/server-renderer/__tests__ packages/runtime-core/__tests__/rendererComponent.spec.ts): 28 files, 445 tests, all passed. No existing test was modified.

Other code affected: looseEqual and looseIndexOf are also used by:

  • v-model on checkboxes, radios and selects (vModel.ts);
  • server-side rendering of v-model (ssrVModelHelpers.ts);
  • the Vue 2 compatibility helpers _q and _i;
  • the style-prop change check in componentRenderUtils.ts.

Only comparisons involving a Map or Set behave differently; everything else follows the same path as before. The Set-as-model <select multiple> logic in vModel.ts has its own check and doesn't go through looseEqual. The reviewer found no blocking issues.
