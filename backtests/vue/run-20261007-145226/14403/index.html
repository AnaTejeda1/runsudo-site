Preserve input values entered during hydration

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches use the same core approach. In `created`, they detect that the element is being hydrated (`el.parentNode` is set). In `mounted`, if the live DOM value differs from the server-rendered default, they keep that value and push it into the model instead of overwriting it.

Patch A only handles `el.type === 'text'` and textarea. Inputs typed `email`, `password`, `number`, `tel`, `search` and so on, plus checkboxes, radios and selects, would all still be reset on hydration. Those are common in the forms the issue describes. A also normalizes newlines with hand-written regexes to approximate browser sanitization, which only works because it is limited to text and textarea.

Patch B fixes the root cause across every v-model directive:
- **Text-like inputs:** it handles any type. It compares against a clone that has the default value applied, so browser sanitization for range, color and stripped line breaks is respected generically.
- **`.number` and `type=number`:** these are cast correctly when syncing to the model.
- **Checkboxes:** it handles single checkboxes and groups bound to arrays or Sets. Several checkboxes toggled before hydration have their updates chained through a WeakMap, because `binding.value` is stale until the next render.
- **Radios:** it keeps the user's checked state and assigns the model only from the checked radio.
- **Selects:** it handles single and multiple selects. It works out the browser-default selection, including the fallback to the first non-disabled option.

B refactors the listener bodies into `assignCheckboxValue` and `assignSelectValue` so the hydration path can reuse them. That adds some complexity, most notably the pending-checkbox map. However, the logic is coherent, and the refactor keeps the existing listener behavior the same.

On tests, A adds a single text-input test. B adds a thorough suite that would fail before its change: text, trim/number modifiers, textarea, dynamic type, checkbox, Set-bound checkbox group, radio, single and multiple select. It also adds regression tests confirming that untouched elements, including sanitized range, color and text values, are not falsely treated as user-edited.

B is clearly the more correct and better-tested fix for the reported UX problem. Its extra complexity is justified by the breadth of the bug.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Steps to reproduce

user loads a page with a slow internet connection
starts entering some values ​​into the input with v-model
after all browser resources loaded - input v-model reset to default value

What is expected?

entered input value is preserved once hydration completes

What is actually happening?

input value is reset to its default value

System Info

Any additional comments?

This is affecting UX when interacting with inputs/forms in slowly loading apps, where values entered during hydration phase are erased and the progress is lost. I have been blocking all forms myself until mounted hook fires to workaround this issue - it would be great to not have to!
