Issue #10745 Merged fix PR #14903 Run 7 Nov 2026 · run-20261107-005830 pytest-dev/pytest

Test with infinite recursion error slows down pytest even if the exception is not shown to the user (because it’s marked as xfail).

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

The issue names the root cause explicitly: `TestReport.from_item_and_call()` formats the failure via `repr_failure()` even though an xfailed test's traceback is never shown. Patch B fixes exactly that. The skipping plugin stashes a predicate on the item during report creation, and `_format_failed_longrepr` uses the cheap `value` style when the exception will be reported as an expected failure. It correctly leaves the full formatting in place when the traceback will be shown (`--runxfail`, `--xfail-tb`, or an `xfail(raises=...)` mismatch that becomes a real failure), covers setup-phase xfails, and also skips the recursion-origin search for the `value` style since only the message is used. Its tests are meaningful: they spy on `getrepr`/`repr_traceback_entry` to assert that no long-style rendering happens for marker, marker-raises, imperative, and setup xfails, that real failures still render `long`, and an end-to-end RecursionError test checks zero long entries while `--xfail-tb` and `--runxfail` still show the traceback. These would fail on base and pass after.

Patch A never touches the reporting path. It speeds up rendering (memoizing statement line numbers per AST node) and truncates undetectable recursion tracebacks to 20 frames when `tbfilter` is on. That makes the issue's specific scenario fast enough to pass the independent tests, but it is symptom mitigation: an xfailed test with any other slow-to-render traceback (deep but non-recursive, large modules) is still fully formatted for no reason. It also changes user-visible output for every real RecursionError failure whose origin cannot be located, hiding the middle frames by default. That is beyond the issue's ask and carries risk, even if consistent with the existing 'error locating origin' branch. The memoization by setting a private attribute on `ast` nodes is a bit hacky but harmless.

Both patches pass all independent tests, so the decision rests on correctness at the root cause and scope. B resolves the reported problem where the issue says it lives and confines changes to xfail reporting; A masks the symptom with a general speedup plus an unrelated output change. B's tests are also more directly tied to the reported behaviour. B wins.

The issue

View on GitHub

In the following code, calling f() fails with a RecursionError. Because test_recursion is marked as xfail, the test suite still passes.

import pytest

def f(x):
    f(x + 1)

@pytest.mark.xfail
def test_recursion():
    f(0)

Running with --durations 10 -vv gives the following output:

test_recursion.py::test_recursion XFAIL                                 [100%]

============================ slowest 10 durations =============================
0.00s call     test_recursion.py::test_recursion
0.00s teardown test_recursion.py::test_recursion
0.00s setup    test_recursion.py::test_recursion
============================= 1 xfailed in 0.41s ==============================

When commenting out the body of test_recursion():

test_recursion.py::test_recursion XPASS                                 [100%]

============================ slowest 10 durations =============================
0.00s setup    test_recursion.py::test_recursion
0.00s call     test_recursion.py::test_recursion
0.00s teardown test_recursion.py::test_recursion
============================= 1 xpassed in 0.01s ==============================

When putting the body of test_recursion() in an exception handler that suppresses the exception:

test_recursion.py::test_recursion XPASS                                 [100%]

============================ slowest 10 durations =============================
0.00s call     test_recursion.py::test_recursion
0.00s setup    test_recursion.py::test_recursion
0.00s teardown test_recursion.py::test_recursion
============================= 1 xpassed in 0.01s ==============================

Pytest takes much longer when the test function raises the exception, even though the test function itself completes quickly in all cases and the exception is not shown to the user if xfailing.

One issue is that TestReport.from_item_and_call() calls Function.repr_failure() (which is slow because of the long traceback) although the error is never shown to the user.

Another issue is that the durations don’t include the part of pytest where the majority of the time is spent. When trying to find why my test suite was slow, --durations didn’t help. It’s probably meant to help finding slow tests instead of performance problems in pytest. Still, I think it could be worthwhile to include timings for some of the code outside of the actual test (like for example generating the test report), as it’s not reasonable to expect users to profile pytest when running into a slowdown like this.
