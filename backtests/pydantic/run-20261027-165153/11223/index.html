Type variables wrongly replaced when two models share the same type variable instance

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

The issue is that an unparameterized generic model (Model2) whose type variable T is shared with Model1 gets T substituted by Model1[int]'s typevars map. Patch B addresses this at the root: `replace_types` now returns an unparameterized generic model unchanged (treating it as implicitly parameterized with Any), `iter_contained_typevars` no longer reports parameters for unparameterized models, and `get_model_typevars_map` zips the origin's own parameters. Its added tests directly exercise the issue snippet (forward ref, direct reference, list container, Model2[T] still substituted) and all five independent tests fail on base and pass on B. Patch A instead changes which namespace/typevars map is used when rebuilding fields of a parametrized generic during schema generation. That fixes adjacent forward-ref problems (and un-xfails two tests), but it does not touch `replace_types`, so Model2 still has T replaced when Model1[int] is built; all five independent tests still raise ValidationError on A, and A's own nested-model test only covers a non-generic Inner, not the issue's shared-TypeVar scenario. Patch B does carry extra semantic churn (Model[T] is no longer `Model`, a new PydanticUndefinedAnnotation raise during self-referencing definition, updated existing test expectations), which adds some risk, but it is the only patch that resolves the reported behaviour.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
