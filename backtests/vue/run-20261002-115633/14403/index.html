Preserve input values entered during hydration

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches use the same core idea. During hydration, `created` runs on an element that is already attached to the DOM. Each patch detects there whether the user edited the server-rendered value, then in `mounted` writes the DOM value back to the model instead of overwriting the DOM.

Patch A only treats the element as dirty when `el.type === 'text'` or `'textarea'`. Inputs typed `email`, `password`, `search`, `tel`, `url` or `number` still get reset to the server value. Those are exactly the kinds of form fields the issue is about. Patch A also does not apply the `type=number` cast in its `mounted` sync, though that path is unreachable given the type gate. Its comparison of `defaultValue` with CR/LF normalization is reasonable but hand-rolled. It ships one test, which covers only the plain text case.

Patch B detects edits for any text-like input by cloning the element and setting `defaultValue` on the clone, which yields the browser-sanitized default. This correctly handles types that sanitize their value, such as `range` and `number`. It applies the `.trim`/`.number` modifiers and `type=number` casting when syncing.

Patch B also extends preservation to checkboxes, including shared array and Set models across multiple boxes, radios, and single and multiple selects. These are all v-model form controls whose user changes would be lost in the same way. The checkbox `pendingModelValues` logic adds some complexity. However, it addresses a real ordering problem: several checkboxes share one model in the same flush before re-render. The added tests cover that case.

Patch B's radio handling avoids clobbering the user's choice in the group. It syncs in `mounted` so that a non-string `:value` is resolved first. Its test suite is extensive and includes a regression guard that untouched elements still reflect the client model, including `range` and `select` with no match.

Overall, Patch B is more correct for the realistic scenarios in the issue (arbitrary forms) and is much better tested. Its extra scope is coherent and covered by tests rather than risky churn.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

entered input value is preserved once hydration completes
