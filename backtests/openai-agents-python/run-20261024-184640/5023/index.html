BackendSpanExporter drops the whole batch on HTTP 429 instead of retrying with Retry-After

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the root cause the same way: 408/409/429 join the retry path, Retry-After / retry-after-ms are parsed with the existing agents.models._retry_runtime helpers, and the wait is bounded by max_delay. The independent tests confirm both deliver the batch on retry, stop at max_retries, honour both headers, cap large values, and leave other 4xx non-retried. The difference is scope and craft. Patch B is a tight change: a module constant, a small helper that reuses the existing header_lookup utility (case-insensitive, None-safe), and `max(backoff, min(retry_after, max_delay))` which matches the issue's wording exactly while leaving the existing backoff/jitter untouched. Its tests cover retry, give-up at max_retries, header precedence (ms over seconds), the max_delay bound, and the deadline interaction (a 30s Retry-After against a 5s drain deadline is cut at the deadline), all of which fail on base. Parsing Retry-After on 5xx too is a small, low-risk extension. Patch A does the core fix correctly but bundles unrelated work: it introduces new `x-should-retry: false` semantics that change existing 5xx behaviour (a 503 with that header is now dropped instead of retried), rewrites `_sleep_before_retry` in a way that is behaviourally equivalent to the old code (pure churn in the deadline path), adds a timed-shutdown drain test that would already pass on base since the deadline branch never consulted the shutdown event, and edits an existing test's patch target for no functional reason. The lazy import with a 'must not become an import-time dependency' comment is unsupported given B's top-level import works in the harness. A's `min(max(sleep, retry_after), max_delay)` also silently clips jitter above max_delay only when a header is present, an inconsistent side effect. A's tests are fine (including unparsable/negative cases), but the extra behaviour change on 5xx and the unrelated refactor add risk and obscure the fix, so B is the better patch.

Describe the bug

BackendSpanExporter._export_with_deadline() treats every 4xx response as final:

# If the response is a client error (4xx), we won't retry
if 400 <= response.status_code < 500:
    logger.error("[non-fatal] Tracing client error %s: %s", ...)
    break

That includes 429 Too Many Requests. A single rate-limited response from /v1/traces/ingest discards the whole batch, up to max_batch_size (128) traces and spans, with no retry and without looking at Retry-After. The run itself succeeds, so the only symptom is a gap in the dashboard and one [non-fatal] log line. The same applies to 408 and 409, which the OpenAI Python client (_base_client._should_retry) retries together with 429 and 5xx; the exporter only mirrors the 5xx half of that policy.

The export path already has everything needed to retry: max_retries, base_delay, max_delay, the backoff loop, and agents.models._retry_runtime.parse_retry_after_value / parse_retry_after_ms for the header.

Expected behavior

408, 409 and 429 are retried with the existing backoff up to max_retries, waiting at least the advertised Retry-After / retry-after-ms (bounded by max_delay), the way the OpenAI client and the SDK's own model retry helpers already treat these statuses. Other 4xx responses stay non-retried. In the script above the second call succeeds and post calls is 2.
