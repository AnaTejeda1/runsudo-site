In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches add a guard in `performHydrate` inside `__asyncHydrate`, which is where the issue says the fix belongs. Both stop the reported `getContainerType(null)` crash when the SSR root node itself is removed.

The difference is coverage. Patch B only checks `!el.parentNode`. The issue's expected behavior is that a node no longer connected to the document should not be hydrated. In the common real-world case (route change or re-render), an ancestor is removed rather than the component's own root. Patch A checks `isConnected`, which also catches ancestor detachment. It records `wasConnected` at setup so that hydration into a container that was never attached (common in tests and some setups) is not wrongly skipped. That is a careful edge-case consideration.

Patch B's two tests cover only root detachment, using a custom strategy and `hydrateOnVisible`; they are reasonable but miss the ancestor case.

Patch B's extra `getContainerType` null-tolerance is harmless defense-in-depth that the issue suggested, but it earns no credit on its own. Overall, A covers the issue's semantics more completely, with tests to match.

The issue

View on GitHub

Vue version

3.5.33

Link to minimal reproduction

https://stackblitz.com/edit/vitejs-vite-ktsycrrc?file=repro.mjs

Steps to reproduce

  1. SSR-render an async component that uses hydrate: hydrateOnVisible().
  2. On the client, hydration is deferred and the strategy registers an IntersectionObserver on the component's SSR node.
  3. The node gets detached from the document before the observer's callback executes (in production this is a route change / re-render while the intersection callback is already queued).
  4. The observer callback runs and invokes hydrate() against the now-detached node.

What is expected?

A node that is no longer connected to the document should simply not be hydrated (there's nothing to hydrate), no exception thrown.

What is actually happening?

hydrate() reaches hydrateNode, which computes the container type from the node's parent:

// packages/runtime-core/src/hydration.ts — inside hydrateNode, async-component branch
nextNode = vnode.type.hydrate(
  node, vnode, parentComponent, parentSuspense,
  getContainerType(parentNode(node)),   // parentNode(node) === null for a detached node
  slotScopeIds, optimized, rendererInternals, hydrateNode,
)
// packages/runtime-core/src/hydration.ts
const getContainerType = (container) => {
  if (container.nodeType !== 1) return undefined   // <-- container is null -> throws
  ...
}

For a detached node parentNode(node) is null, so getContainerType(null) throws TypeError: Cannot read properties of null (reading 'nodeType').

The async-component hydration wrapper only guards against the patched case, never against disconnection:

// packages/runtime-core/src/apiAsyncComponent.ts — __asyncHydrate
const performHydrate = () => {
  if (patched) { /* warn + */ return }   // only guards `patched`
  hydrate()                              // no isConnected check
}

Because the strategy runs inside load().then(...), the throw surfaces as an unhandledrejection, so app-level try/catch around the component can't catch it.

System Info

vue: 3.5.33
@vue/server-renderer: 3.5.33
Environment where it triggers: Android WebView (Chrome), production SSR + client hydration

Any additional comments?

We see this almost exclusively on Android Chrome WebView (~43k occurrences / ~12.8k users over a rollout window) on a page that lazy-hydrates several below-the-fold sections via hydrateOnVisible. The IntersectionObserver callback is dispatched asynchronously; when the user navigates/re-renders in the WebView, the observed node is detached between the intersection being recorded and the callback running, exactly the sequence above. Desktop rarely hits the race.

Skip hydration when the anchor node is no longer connected. the semantically correct place is the async performHydrate (or each built-in strategy's trigger), e.g. bail when no observed/anchor element isConnected:

const performHydrate = () => {
  if (patched) { return }
  if (el && !el.isConnected) return   // detached before hydration → nothing to hydrate
  hydrate()
}

As defense-in-depth, getContainerType could also tolerate a null container (if (!container || container.nodeType !== 1) return undefined), since it's called with parentNode(node) at several sites.

We're currently shipping a userland wrapper around hydrateOnVisible that applies exactly the isConnected guard, which fully stops the crash.

What the agent reported

The crash is fixed: a lazily hydrated async component whose server-rendered node is removed before its hydration strategy fires now skips hydration instead of throwing. The new regression tests failed before the change and pass after it, and the existing hydration, async-component and server-renderer tests still pass.

What was wrong: the wrapper in packages/runtime-core/src/apiAsyncComponent.ts that runs a deferred hydration (performHydrate) only checked whether the component had been updated in the meantime. It never checked whether the node was still in the DOM. For a removed node, hydrateNode called getContainerType(parentNode(node)!) with null, and getContainerType read .nodeType from it, which threw.

What I changed:

  1. packages/runtime-core/src/apiAsyncComponent.ts: performHydrate now returns early with if (!el.parentNode) return before calling hydrate(). Every strategy goes through this function, including hydrateOnVisible, hydrateOnIdle, hydrateOnMediaQuery and custom ones.
  2. packages/runtime-core/src/hydration.ts: getContainerType now accepts null and returns undefined for it. I also removed the ! assertion at the async-component call site.

Why parentNode rather than the suggested isConnected: I tried !el.isConnected and it broke 3 existing tests ("async component", "Suspense + async component", "nested async wrapper"). Those tests hydrate into a container that was never added to the document, and apps can legitimately do the same. The parentNode check targets exactly the null parent that causes the crash.

Tests (added in packages/runtime-core/__tests__/hydration.spec.ts):

  • "lazy hydration of async component should be skipped if its node is detached": a custom strategy captures hydrate. The test removes the server-rendered button, calls hydrate, and asserts that nothing throws and that clicking the button does not fire its handler.
  • "hydrateOnVisible should not throw if the node is detached before it becomes visible": this reproduces your scenario. The test environment has no IntersectionObserver, so the test installs a minimal stand-in and restores the original afterwards. It removes the node, then fires the intersection callback, and makes the same two assertions.

Results:

  • Before the fix: both tests failed with TypeError: Cannot read properties of null (reading 'nodeType').
  • After the fix: the hydration, async-component and server-renderer tests all pass: 19 files, 444 tests.
  • Type check: tsc --noEmit passes.
  • Review: the reviewer found no blocking issues and nothing unrelated in the diff.
