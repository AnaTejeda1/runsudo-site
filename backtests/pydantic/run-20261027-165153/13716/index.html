validate_by_alias=False still produces a validation JSON schema keyed by the alias

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches make the same core change in `_get_alias_name`: when `validate_by_alias` is False in the current config, the validation schema uses the field name. That fixes the model, pydantic dataclass, and configured TypedDict cases, and both patches add regression tests covering the main scenario, serialization being untouched, and scoping between nested models. The independent tests confirm both pass those.

Patch A goes further where the same defect still exists after Patch B's one-liner. Config-less TypedDicts and stdlib dataclasses nested in a `validate_by_alias=False` model inherit the parent's core config, so validation of them really uses the field name, yet with Patch B their schema still names the alias (the independent test `test_validate_by_alias_false_nested_configless_types_follow_model` fails on B, passes on A). Patch A handles this by reading `validate_by_alias` from the core schema's `config` when pushing the config wrapper for typed-dict and dataclass schemas. It also covers named-tuple field titles, arguments schemas (`validate_call`/`TypeAdapter` of a function), and threads `validate_by_alias` into the generated arguments core schemas so the JSON schema can read it per schema rather than from an ambient config. These are not unrelated churn; they are the same 'schema names a key the validator rejects' bug in other containers the generator handles, and each path has a dedicated test.

Risk assessment: Patch A's added surface (a context manager for arguments schemas, a helper to merge core-config `validate_by_alias`) is small, clearly named, and consistent with the existing config-wrapper-stack pattern. The `_generate_schema.py` change only passes a setting that core already reads from config, so validation behavior should be unchanged. Patch B is minimal and correct for the headline case but leaves a real, reachable instance of the issue unfixed. Patch A wins on correctness and test coverage without meaningful added risk.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Initial Checks

Description

With validate_by_alias=False, the validation JSON schema still names the alias — which is the one key the model refuses.

class Model(BaseModel):
    model_config = ConfigDict(validate_by_alias=False, validate_by_name=True)
    my_field: str = Field(alias='myAlias')

Model.model_json_schema()
#> {'properties': {'myAlias': ...}, 'required': ['myAlias'], ...}

Model(my_field='x')                          # accepted
Model.model_validate({'myAlias': 'x'})       # ValidationError

So the schema describes the opposite of the model: it requires the rejected key and omits the accepted one. model_json_schema(by_alias=False) produces the right document, but a caller has to know the model's config to know to ask for it.

Why this looks like an oversight rather than a decision

_get_alias_name already picks the alias per mode, and it already returns the field name when no alias applies in that mode:

elif self.mode == 'validation':
    alias = field.get('validation_alias', name)
else:
    alias = field.get('serialization_alias', name)

Which is visible in behaviour today:

fieldvalidation schemaserialization schema
Field(serialization_alias='sAlias')my_field ✅sAlias ✅
Field(validation_alias='vAlias')vAlias ✅my_field ✅
Field(alias='myAlias') + validate_by_alias=FalsemyAlias ❌myAlias

The principle "use the alias only in the mode where it applies" is already implemented. validate_by_alias=False turns the validation alias off, and the generator simply does not consult it.

I have a fix and regression tests ready, and will open a PR without a closing reference so it does not trip enforce-issue-assignment.

A related asymmetry I did not touch, because it is your call

serialize_by_alias defaults to False, so with nothing but a plain Field(alias=...) the serialization schema already disagrees with the default dump:

class Model(BaseModel):
    my_field: str = Field(alias='myAlias')

Model(myAlias='x').model_dump_json()
#> {"my_field":"x"}

Model.model_json_schema(mode='serialization')['properties']
#> {'myAlias': ...}

By the argument above that is the same defect. But unlike validate_by_alias=False, which is an explicit opt-out affecting only the people who set it, serialize_by_alias=False is the default, so honouring it would change the serialization schema of every aliased model. That is a breaking change and a product decision, not a drive-by fix, so I have deliberately left it alone and am raising it here instead. Happy to follow up either way you decide.
