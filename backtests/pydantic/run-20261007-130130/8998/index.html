Missing type for PEP695 TypeAliasType vs TypeAlias when using TypeAdapter

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

The issue is that a PEP 695 `TypeAliasType` matches the `type[T]` overload, so checkers infer `TypeAdapter[TypeAliasType]`. The root cause is that pydantic types its type-form parameters as `type[T]` or `Any`, because type expressions could not be expressed before PEP 747.

Patch B fixes that root cause. It replaces the overload pair on `TypeAdapter.__init__` with a single `type: TypeForm[T]` and applies `TypeForm` across `ValidateAs`, the pipeline `validate_as`, `FieldInfo.annotation`, serializer `return_type` and `create_model`. With `TypeForm`, a checker evaluates `type my_type = list[...]` as the aliased type, so `validate_python` returns `list[dict[str, list[int]]]`. This matches the issue's expectation. It also fixes the related cases the codebase had marked as TODO PEP 747: `Annotated`, unions and `Union`. B's typechecking tests drop the previous `reportAssertTypeFailure` and `assert-type` ignores and now assert precise inference for `Annotated[int, ...]`, `int | str` and `Union[int, str]`. That shows the mechanism works under the configured checkers.

B's weaknesses:
- It adds no explicit `TypeAliasType` test.
- It carries unrelated churn: pyrefly config and ignore comments everywhere, and a CI pyright version pin.
- A few `pyright: ignore` comments are needed for `PydanticUndefined` defaults.

Patch A only masks the symptom. It adds overloads that map any `TypeAliasType` to `TypeAdapter[Any]` (and `Any` for `parse_obj_as`, `validate_as` and `ValidateAs`). The bogus `TypeAliasType` inference goes away, but users lose all type information; the issue wants the real aliased type. Its own comment admits the aliased type cannot be inferred and tells users to annotate explicitly. A's tests do target `TypeAliasType` directly, which is a plus. But they assert `Any`, which enshrines the degraded behavior.

On the first criterion, correctness at the root cause, B clearly wins despite its extra scope. A's targeted tests do not outweigh delivering `Any` instead of the real type.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Description

There seems to be a difference between the type that is returned from TypeAdapter when used on a PEP695 TypeAliasType compared to when it is used on a TypeAlias. See example below. When TypeAdapter is used on a TypeAlias, the correct type is shown. However, when the TypeAliasType is used, the type is shown as TypeAliasType. This causes the type-checker to see red.

Example Code

from typing import TypeAlias, reveal_type

from pydantic import TypeAdapter

my_type_alias: TypeAlias = list[dict[str, list[int]]]
x: my_type_alias = [{"a": [1, 2, 3]}]

res = TypeAdapter(type=my_type_alias).validate_python(x)
reveal_type(res)  # type of res is "list[dict[str, list[int]]]"


type my_type = list[dict[str, list[int]]]
x: my_type = [{"a": [1, 2, 3]}]

res = TypeAdapter(type=my_type).validate_python(x)
reveal_type(res)  # type of res is "TypeAliasType"
