Initial Checks

Description

pydantic_core.to_json (and to_jsonable_python) documents timedelta_mode and temporal_mode as independent parameters governing disjoint type sets:

  • timedelta_mode: How to serialize timedelta objects, either 'iso8601' or 'float'.
  • temporal_mode: How to serialize datetime-like objects (datetime, date, time), either 'iso8601', 'seconds', or 'milliseconds'.

(This is what both the API docs and the shipped _pydantic_core.pyi type stub say.)

Given that contract, to_json(..., timedelta_mode="float", temporal_mode="iso8601") should serialize datetime/date/time as ISO 8601 strings and timedelta as a float. Instead, datetime/date/time are also coerced to unix-timestamp floats, timedelta_mode="float" silently overrides temporal_mode="iso8601" for all temporal types.

There is no combination of the two parameters that yields ISO datetimes with float-second timedeltas, even though the documented parameters imply there should be.

Root cause / regression. This regressed in #1743. Before that PR, SerializationConfig had a dedicated timedelta_mode: TimedeltaMode field and to_json had no temporal_mode parameter, so timedelta_mode was genuinely independent. #1743 replaced the dedicated field with a single unified temporal_mode and retrofitted timedelta_mode as a legacy alias that maps into it.

Either the docs/.pyi should be corrected to state that timedelta_mode is a deprecated alias that affects all temporal types, or (preferably) timedelta should retain an independent setting so the documented behavior holds. Personally I have a requirement to be able to set the timedelta format independent of the other datetime types.

Example Code

import datetime
import pydantic_core

payload = {
    "dt": datetime.datetime(2026, 7, 9, 12, 0, 0),
    "d": datetime.date(2026, 7, 9),
    "t": datetime.time(12, 0, 0),
    "td": datetime.timedelta(hours=1, minutes=30),
}

# Per the docs: temporal_mode governs dt/d/t; timedelta_mode governs td.
actual = pydantic_core.to_json(
    payload, timedelta_mode="float", temporal_mode="iso8601"
).decode()

expected = '{"dt":"2026-07-09T12:00:00","d":"2026-07-09","t":"12:00:00","td":5400.0}'

print("actual  :", actual)
print("expected:", expected)
assert actual == expected, "timedelta_mode='float' wrongly coerced datetime/date/time to floats"
# AssertionError: actual == {"dt":1783598400.0,"d":1783555200.0,"t":43200.0,"td":5400.0}

What the agent reported

The fix is complete and verified. Here is my final report.

What was wrong

pydantic_core.to_json / to_jsonable_python document timedelta_mode (governs only timedelta) and temporal_mode (governs datetime/date/time) as independent, but PR #1743 collapsed them into a single temporal_mode field, retrofitting timedelta_mode as a lossy alias (float → Seconds). Because the shared SerializationConfig stored only one temporal_mode, setting timedelta_mode='float' silently coerced datetime/date/time to unix-timestamp floats too. There was no combination yielding ISO datetimes with float-second timedeltas.

What I changed

  • pydantic-core/src/serializers/config.rs — Added a separate timedelta_mode: TemporalMode field to SerializationConfig. temporal_mode (datetime/date/time) is now resolved purely from ser_json_temporal/temporal_mode, so the legacy timedelta alias no longer leaks onto them. timedelta_mode follows the explicit temporal setting when one is present (preserving the ser_json_temporal-priority behavior), otherwise the dedicated timedelta alias. Applied symmetrically in both from_config and from_args.
  • pydantic-core/src/serializers/infer.rs — Switched the three timedelta serialization sites (to_python, serde_serialize, json_key) from config.temporal_mode to config.timedelta_mode. Datetime/date/time sites unchanged.
  • pydantic-core/tests/serializers/test_any.py — Added regression test test_timedelta_mode_independent_of_temporal_mode asserting the exact reported scenario for both to_json and to_jsonable_python.

No .pyi change was needed — the docstrings already describe the now-correct behavior.

Test evidence

  • Regression test failed before the Rust change (datetime/date/time came back as 1783598400.0 etc.) and passes after ({"dt":"2026-07-09T12:00:00","d":"2026-07-09","t":"12:00:00","td":5400.0}).
  • I rebuilt the Rust extension in the test container (maturin develop), then ran the gate: ./bt-test on the serializers directory → 802 passed, 5 skipped, 1 xfailed. Notably test_config_timedelta_timedelta_ser_flag_prioritised (which asserts ser_json_temporal priority over ser_json_timedelta) still passes, confirming backward compatibility.
  • Reviewer confirmed the fix resolves the report, preserves backward compat, touches nothing unrelated, and leaves no scratch files.

Requirements disposition

  1. timedelta_mode='float', temporal_mode='iso8601' must give ISO datetimes + float timedelta — ✅ Implemented; covered by the new regression test (was failing, now passes).
  2. Preferred fix: timedelta retains an independent setting — ✅ Implemented via the separate timedelta_mode field, rather than the alternative "just fix the docs."
  3. Alternative offered (correct docs/.pyi to say timedelta_mode is a deprecated alias affecting all temporal types) — ⏭️ Skipped in favor of the report's stated preference; the existing .pyi docstrings (_pydantic_core.pyi:452-453, 537-538) already describe the independent contract and now match actual behavior, so no doc change was needed. Evidence: reviewer confirmed the docstrings match post-fix behavior.
  4. Don't break existing ser_json_temporal-priority behavior — ✅ Preserved; test_config_timedelta_timedelta_ser_flag_prioritised and all other serializer tests pass.

One non-blocking note from review: from_config detects an explicit temporal setting by key presence while from_args uses temporal_mode != "iso8601". This asymmetry is inherent to the args API (a default and an explicit "iso8601" are indistinguishable) and preserves prior config behavior, so it is not a regression.
