The issue

View on GitHub

I argued with @jmooring that it would be very unlikely that e.g. the CSS dark class would collide with existing classes in a project. After thinking a little, I still don't think that is a likely issue, but:

  1. I suspect there are JS/CSS frameworks with other naming standards for these mode classes (e.g. theme-dark)
  2. I would be an annoyed Hugo user if I needed to customise this class and had to do ugly string replacements.
  3. The cost for us adding these 2 new options is small.

Summary

What was wrong / requested: The Chroma stylesheet generator hardcoded the mode-selector CSS class names as .light and .dark. The reporter wanted these to be user-overridable (some CSS/JS frameworks use conventions like theme-dark, and forcing string replacements is annoying) via two new options classDark/classLight on both the css.ChromaStyles template function and the hugo gen chromastyles CLI command, defaulting to "dark"/"light".

What I changed (production code):

  • markup/highlight/chromastyles.go — Added ClassLight and ClassDark fields to ChromaStylesOptions. In the ModeSelector block of ChromaStylesCSS, the prefix now derives from these options, defaulting to "light"/"dark" when empty, so existing behavior is unchanged.
  • commands/gen.go — Added --classLight (default "light") and --classDark (default "dark") flags wired into ChromaStylesOptions. (Fixed a stray over-indentation so the file is gofmt-clean.)
  • tpl/css/css.go — no change needed; it squashes highlight.ChromaStylesOptions, so the new classLight/classDark dict keys are accepted automatically.

Tests added (fail before, pass after):

  • tpl/css/chromastyles_integration_test.go — TestChromaStylesCustomModeClasses: template path with classLight "theme-light" / classDark "theme-dark", asserting the emitted CSS uses .theme-light .chroma/.theme-dark .chroma.
  • testscripts/commands/gen_chromastyles_mode.txt — CLI cases for --classDark theme-dark / --classLight theme-light, asserting the custom classes appear and the defaults do not.

Test evidence:

  • Baseline: the 3 existing chroma tests passed before the change; the new TestChromaStylesCustomModeClasses failed before implementation (Got: .light .bg vs expected .theme-light).
  • After implementation: full tpl/css package passes (24 tests incl. TestChromaStyles, TestChromaStylesKeepDefaultForegroundTokens, TestChromaStylesErrors, and the new TestChromaStylesCustomModeClasses). CLI testscripts TestCommands/gen_chromastyles and TestCommands/gen_chromastyles_mode both PASS. gofmt -l reports no formatting issues.
  • Reviewer confirmed the diff is clean, minimal, defaults preserved, and nothing unrelated changed.

Requirements disposition:

  1. classLight option on css.ChromaStyles (default "light") — implemented, covered by TestChromaStylesCustomModeClasses.
  2. classDark option on css.ChromaStyles (default "dark") — implemented, covered by TestChromaStylesCustomModeClasses.
  3. --classLight flag on gen chromastyles (default "light") — implemented, covered by gen_chromastyles_mode.txt.
  4. --classDark flag on gen chromastyles (default "dark") — implemented, covered by gen_chromastyles_mode.txt.
  5. Defaults unchanged for existing users — verified; existing .light/.dark assertions in TestChromaStyles and the original CLI cases still pass.

All changes are left uncommitted in the working tree. Note: the auto-generated docs (docs/content/en/commands/hugo_gen_chromastyles.md) were intentionally not regenerated — that is a generated artifact outside the scope of this code fix and not part of the test gate.
