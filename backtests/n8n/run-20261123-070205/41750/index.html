The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches implement the core ask: wrap remote sandbox calls (exec and filesystem ops) so a `404 sandbox not found` drops the cached running state via markNeedsStart, re-POSTs /sandboxes with the deterministic id through ensureRunning, and retries the op exactly once. Neither independent test run produced results on any tree, so the verdict rests on the diffs.

Patch A detects the condition by regex-matching the error message (`/sandbox not found/i`) and also adjusts `exists()` so a missing sandbox is not reported as a missing file. It wraps getInfo as well. Tests are focused and cover recovery, retry-once, non-matching 404s, getInfo and exists. Weaknesses: detection is coupled to the service's message text, and concurrent failures each trigger their own recreate (harmless since POST with the same id is idempotent, but unguarded).

Patch B detects by probing `GET /sandboxes/{id}` on any 404 (bounded by a 10s timeout) and only recreates when the probe itself 404s, which is independent of message wording and still distinguishes file-not-found from sandbox-not-found. It dedupes concurrent recoveries with a shared promise and tests that explicitly. Crucially, B also addresses the second half of the issue's expectation ("the thread keeps working"): after recreation the sandbox is empty, but the cached RuntimeSandboxEntry still has setupComplete=true, so setupSandboxWorkspace (templates, skills, knowledge base) would never re-run until n8n restarts, leaving the agent on a bare sandbox. B checks the `.sandbox-initialized` marker for the n8n-sandbox provider and re-runs setup when it is gone, with tests at the service layer. That is extra scope, but it is directly needed for the recovered thread to actually function, not unrelated churn. Costs: an extra marker read per message for the n8n-sandbox provider, an extra probe roundtrip on ordinary file-not-found 404s, getInfo is left unwrapped, and the probe passes a promise (not a thunk) to raceWithAbort, which I cannot verify from the diff but is consistent with the existing `creation` promise pattern in createSandbox.

On correctness B is more robust in detection and more complete in restoring a working thread; on tests both are substantive, B slightly broader (concurrency, probe timeout, service-layer re-setup). A is cleaner and smaller, but B's advantages outweigh its added complexity.

Bug Description

With the n8n-sandbox provider, an existing Agent / n8n Assistant thread stays broken after its remote sandbox disappears (for example after the sandbox runner restarts). n8n keeps calling POST /sandboxes/{id}/executions for the thread's deterministic sandbox id, gets 404 sandbox not found every time, and never calls POST /sandboxes to recreate it. The agent replies that the sandbox is unreachable and gives up. New threads work fine.

This persists even after n8n itself has restarted, so it is not only the in-process sandbox cache: on a cache miss n8n reuses the id directly instead of re-creating the sandbox.

The sandbox service already supports the recovery path. docs/API.md in n8n-io/n8n-sandbox-service says a runner restart makes a sandbox return 404, and that POST /sandboxes with a caller-supplied id returns the existing sandbox or recreates it with the same id. Calling POST /sandboxes {"id": "<thread sandbox id>"} by hand fixed the broken thread immediately.

Timeline from the sandbox-api logs (UTC, one thread):

  • 20:15:16 POST /sandboxes 201, sandbox df02d17e-... created for the thread, then executions 200
  • 20:40:33 Docker Engine upgrade restarts all containers (sandbox-api, runner, n8n); n8n back at 20:40:45
  • 20:44:35 to 21:13:51 POST /sandboxes/df02d17e-.../executions 404, 26 times, no POST /sandboxes for that id in between
  • 21:15 manual POST /sandboxes {"id":"df02d17e-..."} 201, the thread works again
{"level":"INFO","msg":"request","method":"POST","path":"/sandboxes/df02d17e-08d3-5cb7-900b-7d53f03c4cc4/executions","query":"","status":404,"duration_ms":0}

To Reproduce

  1. Self-hosted n8n with the n8n-sandbox provider (services as in docker/get-n8n-compose.yml), connected from Settings > Agents > Shared sandbox.
  2. Open an Agent builder or n8n Assistant thread and send a message that uses the workspace, so the thread's sandbox is created.
  3. Restart the sandbox runner. In our case this happened through a Docker Engine upgrade, which restarted every container including n8n. Restarting only the runner (docker compose restart sandbox-runner-1) should be enough according to the API docs, but we did not test that variant.
  4. Send another message in the same thread.

The sandbox-api logs show only 404s on /sandboxes/{id}/executions for the thread's id, and the agent reports "sandbox not found".

Expected behavior

When the sandbox service answers 404 sandbox not found, n8n should drop the cached entry, call POST /sandboxes with the thread's deterministic id (which returns the existing sandbox or recreates it), and retry the request once, as the API docs already recommend for 409 sandbox_restarted. Workspace files are lost, but the thread keeps working.

Workaround we use for now: a cron job on the host that records the ids from GET /sandboxes every minute and re-POSTs them when the runner's start time changes.
