Sandbox memory consolidation selects older rollouts when updated_at timestamps use different UTC offsets

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the root cause (comparing instants instead of raw strings) and pass all seven independent tests, including the cap-of-1 mixed-offset case and equal-instant tie-break. The differences are in policy, clarity, and tests. Patch B parses with datetime.fromisoformat, explicitly handles Z, treats naive timestamps as UTC, and groups unparseable values with 'unknown' so they sort after every valid timestamp. That policy is documented in a docstring, exactly what the issue asked for ('a documented compatibility policy for naive/unparseable/unknown timestamps'). Patch A instead returns the original string for anything its regex does not fully match, so an unparseable value like 'yesterday' sorts as (1, 'yesterday'), ahead of every valid timestamp, and naive timestamps are compared as raw strings against normalized ones that have a trailing '.' appended. That mixing of normalized and unnormalized strings in one key is undocumented and fragile, even though it happens to work for common inputs. A's hand-written regex and separate fraction handling add complexity mainly to support nanosecond fractions, which the issue does not ask for; it is neutral at best and makes the fix harder to verify. On tests, B adds focused unit tests for the key (offsets, naive, unparseable) plus two end-to-end selection tests, one with cap=1 that would clearly fail on base (base selects the older rollout), and one covering naive/invalid/unknown ordering and the rollout-id tie-break. A parametrizes an existing added/retained/removed test; whether the mixed-offset params actually fail on base depends on that test's cap and assertions, which the diff does not show, so its regression value is less certain. B also updates the type annotation of the items list to match the new float key and keeps the change minimal and readable. B is the better fix.

The issue

View on GitHub

Summary

Sandbox-memory consolidation chooses the "most recent" raw rollouts by lexicographically sorting unnormalized updated_at strings, not comparing instants. When valid ISO 8601 timestamps carry different UTC offsets, this can select an older memory and exclude a newer one at the configured max_raw_memories_for_consolidation cap.

Pinned source and reachability

Commit 5789c7c555b5d3e26104859d84286e412d7b6a9b:

  • src/agents/sandbox/memory/storage.py (blob 019b5b8df2b5dee50da65f730e712dc9dfe3bf56), _updated_at_sort_key(), returns (1, updated_at) with the original string for every nonempty, non-unknown timestamp.
  • SandboxMemoryStorage._list_current_selection_items() sorts (_updated_at_sort_key(raw_memory), rollout_id, item) in reverse order, and build_phase_two_input_selection() takes only the first max_raw_memories_for_consolidation entries.
  • src/agents/sandbox/memory/manager.py: the public enqueue_rollout_payload(payload, rollout_id=...) preserves an incoming updated_at field; _process_rollout_file() reads it and _format_raw_memory() copies it into the text subsequently sorted.

Minimal deterministic reproduction

from datetime import datetime

newer = "2026-11-16T23:30:00-05:00"  # 2026-11-17 04:30 UTC
older = "2026-11-17T03:30:00+00:00"  # 2026-11-17 03:30 UTC

assert datetime.fromisoformat(newer) > datetime.fromisoformat(older)
assert older > newer  # this is what descending string sort uses

With max_raw_memories_for_consolidation=1, the source sorter selects the older rollout. This is not a mere display-order issue: the wrong rollout feeds the subsequent consolidation prompt.

I independently ran an isolated harness with the unchanged _updated_at_sort_key implementation copied from source, plus a candidate UTC-normalizing key: 7/7 Python tests passed, including mixed-offset inversion, same-offset control, Z, missing and invalid timestamps. This is not an end-to-end installed-package memory-consolidation run.

Suggested fix

For valid offset-aware ISO timestamps, normalize to the actual instant before sorting (datetime.fromisoformat(...).timestamp() handles offsets; explicitly handle Z), while choosing a documented compatibility policy for naive/unparseable/unknown timestamps. Include an explicit stable tie-breaker by rollout id, and regression coverage for mixed UTC offsets at a selection cap of 1, naive timestamp policy, and existing UTC-only behavior.

I searched existing issues for sandbox memory updated_at timezone/string sorting/selection and found no matching report; #5459 concerns SQLAlchemy session item ordering, a separate subsystem.
