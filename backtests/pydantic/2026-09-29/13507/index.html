Experimental pipeline: every constraint chained after ge/lt/le is dropped from the JSON schema

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the reported root cause (the unconditional fallback function wrapper on Ge/Lt/Le that buries later constraints inside an opaque function-after schema invisible to JSON schema generation), and both add regression tests for the exact table cases in the issue. The decision comes down to completeness, tests, and alignment with the issue's own analysis.

Patch A is the surgical, low-risk fix: it introduces the `native_constraint_applied` flag on Ge/Lt/Le, mirroring the established convention, and gates the fallback so validation is provably unchanged (native path when the field is set, function path on type mismatch). It cleanly handles the Interval decomposition and the trailing multiple_of case. Its weakness is that it only touches three branches and its tests, while adequate, are narrower.

Patch B implements the single symmetric change across all five branches (Gt/Ge/Lt/Le/MultipleOf) that the issue explicitly argues is the right shape ('one symmetric change across all five branches rather than three separate patches'). It removes the redundant isinstance type-narrowing and lets the fallback live in an `else:` (the same structure Gt used correctly), relying on pydantic-core to cast the bound when building the validator. This is a broader behavioral change (mismatched-type bounds now go native instead of a Python function), which is the one real risk, but Patch B deliberately validates exactly those cases: it adds parametrized validation tests for float bounds on int schemas, int bounds on float/Decimal schemas, and multiple_of type mismatches, plus a `transform()` case demonstrating the fallback still fires for non-numeric core schemas, plus JSON-schema tests for both ge/le and gt/lt chains. That test coverage is markedly more thorough and directly exercises the assumption the fix rests on.

Weighing correctness (both correct; A is risk-free on validation, B's casting assumption is sound for pydantic-core and is explicitly tested), tests (B clearly stronger and non-tautological), scope (A tighter, B broader but matching the issue's stated architectural preference rather than gratuitous churn), and craft (B cleaner and more symmetric, with honest pyright-ignore annotations for the type mismatch), Patch B is the better overall fix. The scope expansion is the kind the issue itself recommends and its risk is mitigated by targeted tests, so it edges out A's safer but less complete approach.

Initial Checks

  • I confirm that I'm using Pydantic V2

Description

In the experimental pipeline API, chaining constraints silently drops every bound after the first from the generated JSON schema. Validation stays correct - only the published schema is wrong, which makes it easy to miss.

All bounds below are non-zero, so this is not #13450 (falsy zero bounds in Interval). Observed identically on released 2.13.4 and on main (2.14.0a1).

expressionJSON schemavalidation
validate_as(int).ge(1).le(100){"minimum": 1, "type": "integer"}0 reject, 50 accept, 200 reject
validate_as(int).le(100).ge(1){"maximum": 100, "type": "integer"}0 reject, 50 accept, 200 reject
validate_as(int).constrain(Interval(ge=1, le=100)){"minimum": 1, "type": "integer"}0 reject, 50 accept, 200 reject
validate_as(int).ge(1).le(100).multiple_of(5){"minimum": 1, "type": "integer"}correct
validate_as(int).gt(1).lt(100) (control){"exclusiveMinimum": 1, "exclusiveMaximum": 100, ...}correct
Annotated[int, Ge(1), Le(100)] (control){"minimum": 1, "maximum": 100, ...}correct

So .ge(1).le(100).multiple_of(5) publishes a schema advertising any integer >= 1, while the validator rejects 200 and 52. For FastAPI that means the OpenAPI component and every generated client disagree with the server.

Cause

In _apply_constraint(), the Ge, Lt and Le branches apply their fallback function validator unconditionally - including when the native core-schema field was just set:

elif isinstance(constraint, annotated_types.Ge):
    ge = constraint.ge
    if s and s['type'] in {'int', 'float', 'decimal'}:
        s = s.copy()
        if s['type'] == 'int' and isinstance(ge, int):
            s['ge'] = ge          # native constraint applied...
        ...

    def check_ge(v: Any) -> bool:
        return v >= ge

    s = _check_func(check_ge, f'>= {ge}', s)   # ...and then wrapped anyway

_check_func wraps the schema in function-after. The next constraint in the chain sees s['type'] == 'function-after', which is not in {'int', 'float', 'decimal'}, so it cannot set its own native field and survives only inside an opaque callable that JSON-schema generation cannot read. Core schema for .ge(1).le(100):

{'type': 'function-after',
 'function': ...,                       # <- le(100) lives in here, invisible to the schema
 'schema': {'type': 'function-after',
            'function': ...,            # <- redundant ge check
            'schema': {'type': 'int', 'ge': 1}}}

Gt is the control that works, and only by accident: its fallback sits in an else:, so nothing is wrapped when the native constraint applies.

Relationship to the open PRs in this function

Two in-flight PRs each fix one branch of this, for unrelated reasons, and between them they leave Ge, Lt and Le untouched:

  • #13473 adds a native_constraint_applied flag to MultipleOf to avoid a float parity problem. Same shape as the fix needed here.
  • #13446 restructures Gt so the fallback lands inside the numeric branch.

Worth flagging on the second one: #13446's description argues that Gt is uniquely broken and holds up Ge/Lt/Le/MultipleOf as the correct model, because they "always apply" the check and so enforce the bound on a type mismatch. That is true of validation, but always applying it is exactly what destroys the schema. Gt is uniquely broken for validation; the other four are broken for schema. Whichever way this is fixed, it probably wants to be one symmetric change across all five branches rather than three separate patches.

What the agent reported

Done. Here is the final report.

What was wrong

In pydantic/experimental/pipeline.py, _apply_constraint() handled the Ge, Lt, and Le constraints by setting the native core-schema field (s['ge']/s['lt']/s['le']) and then unconditionally wrapping the schema in a fallback function-after validator via _check_func. That function-after node hid the underlying numeric schema from the next constraint in a chain: when the following constraint checked s['type'] in {'int','float','decimal'} it saw 'function-after' instead, so it couldn't set its own native field and its bound survived only inside an opaque callable that JSON-schema generation can't read.

Result: .ge(1).le(100) published {"minimum": 1} (no maximum), even though validation still rejected 200. Gt happened to work only because its fallback sat in an else:.

What I changed

Applied the native_constraint_applied flag pattern (the shape from #13473) to the Ge, Lt, and Le branches: the fallback _check_func validator is now added only when the native field could not be set (non-numeric schema, or a bound whose type doesn't match the schema). On the matched numeric path the native field alone enforces the bound and the schema stays intact for downstream constraints. Gt and MultipleOf were left untouched (out of scope; not part of the reported broken scenarios).

Files: pydantic/experimental/pipeline.py (fix), tests/test_pipeline.py (regression tests).

Test evidence

  • Before the fix, the 4 new test_json_schema cases failed (schema dropped the second/later bound); test_ge_le_validation passed (validation was already correct).
  • After the fix: ./bt-test tests/test_pipeline.py → 74 passed.
  • Reproduction against repo source now yields both bounds for every reported expression:
  • .ge(1).le(100) → {'minimum': 1, 'maximum': 100, 'type': 'integer'}
  • .le(100).ge(1) → same
  • .constrain(Interval(ge=1, le=100)) → same
  • .ge(1).le(100).multiple_of(5) → {'minimum': 1, 'maximum': 100, 'multipleOf': 5, ...}
  • controls .gt(1).lt(100) and Annotated[int, Ge(1), Le(100)] unchanged.
  • Reviewer confirmed validation is preserved on all type-mismatch/non-numeric paths (no bound becomes silently unenforced), no existing tests weakened, no unrelated changes.
