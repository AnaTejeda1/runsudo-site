Add importContext to resources.Copy

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

The issue asks for an `importContext` option on `resources.Copy`, with the signature changed to `resources.Copy [STRING or MAP] RESOURCE`. The context would be stored as internal state on the resource and honored by css.Build, js.Build/Batch, css.Sass and TailwindCSS.

Patch A implements exactly that. `resources.Copy` now accepts a target path, an options map, or nothing, and validates unknown options. An `ImportContext` is stored in an unexported field on `genericResource` and forwarded via `ResourceTransformationCtx.ImportContext`. It is consumed by:
- esbuild (js.Build/css.Build via `ApplyImportContext`)
- js.Batch, as a fallback through `InternalResourceImportContext`
- the PostCSS/Tailwind inline-import resolver
- Dart Sass
- LibSass

Patch A also handles cache correctness. The import context's key, including content hashes for in-memory resources, is folded into both the copy cache key and the resource `Key()`. Copies of the same resource with different contexts therefore don't collide, and a test covers this. Its tests are thorough and meaningful: CSS build with precedence and fallback to assets, JS build, cache separation, a Page as context, Mount, rebuild on edit, option validation, Dart Sass, LibSass, js.Batch, and unit tests for the resolver and getter. Docs are updated too.

Patch B does not touch `resources.Copy` at all, so the requested API is absent. Instead it adds `importContext` as an option to css.Build/js.Build, css.Sass (Dart) and TailwindCSS/PostCSS. To make those options hashable for transformation keys, it makes broad, risky changes:
- bumps `hashstructure` to v1.0.0 and rewrites hashing to use an UnwrapFunc
- removes `pageState.Key()` and adds `pageOutput.Key()`
- changes `Color.Hash` to `Key`
- changes `FromString` resource keys to include content hashes
- adds a new `testinginternal` template namespace exposed to all templates

These changes affect cache keys globally and add regression risk well beyond the issue. Its hash test hardcodes magic numbers, which is brittle. LibSass support is missing.

Patch A matches the issue's requested design, covers more transformers, and is better tested with less collateral risk.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The issue

The example below (and variations of it) isn't possible in Hugo:

{{ $r := resources.FromString "foo.css" "body { color: blue; }" }}
{{/* How do I get $r to resolve as an import in main.css?  */}}
{{ $css := resources.Get "css/main.css" | css.Build }}

And in assets/css/main.js:

@import "foo.css" screen;
@import "bar.css" print;

The example above uses css.Build, but this is also relevant for (at least) css.Sass, js.Build and js.Batch. There are more or less ugly workardounds for the above (e.g. resources.Concat or passing in css vars in a map), but it would be nice to have a direct way that worked for all (I have a new proposal in mind that would need this).

I suggest we add importContext to resources.Copy and make the logic that's currently implemented in js.Batch also work for the other relevant funcs, e.g:

{{ $foo := resources.FromString "foo.css" "body { color: blue; }" }}
{{ $bar := resources.FromString "bar.css" "body { color: green; }" }}
{{ $main := resources.Get "css/main.css" | resources.Copy (dict "importContext" (slice $foo $bar)) }}
{{ $css := $main | css.Build }}

The current signature of resources.Copy is:

resources.Copy TARGETPATH RESOURCE

I suggest we

resources.Copy [STRING or MAP] RESOURCE

And make it optional (we can determine a path from RESOURCE). So for the MAP options it would look like:

{{ $opts := dict
   "targetPath" "foo.css"
   "importContext" (slice $foo $bar)
}}

In the above importContext is the same as described in inputContext -- which also allows constructs ala:

{{ $common := resources.Match "/js/headlessui/*.*" }}
{{ $importContext := (slice $.Page ($common.Mount "/js/headlessui" ".")) }}
{{ $opts := dict
   "importContext" $importContext
}}

Some implementation hints:

  • We would store this new importContext in some unexported field. I suggest we follow the pattern in the funcs resources.Internal* to access this internal state.
  • js.Batch takes importContext as an option. That import handling is more advanced than we need here, but we look at that for inspiriation/reuse.
  • I suggest that we start with css.Build and, once that looks good, implement it in js.Build/Batch, css.Sass and css.TailwindCSS.
