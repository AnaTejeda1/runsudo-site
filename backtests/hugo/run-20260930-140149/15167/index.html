The issue

View on GitHub

I argued with @jmooring that it would be very unlikely that e.g. the CSS dark class would collide with existing classes in a project. After thinking a little, I still don't think that is a likely issue, but:

  1. I suspect there are JS/CSS frameworks with other naming standards for these mode classes (e.g. theme-dark)
  2. I would be an annoyed Hugo user if I needed to customise this class and had to do ugly string replacements.
  3. The cost for us adding these 2 new options is small.

What the agent reported

I added classDark and classLight options to css.ChromaStyles and matching --classDark / --classLight flags to hugo gen chromastyles, defaulting to dark and light. The new tests fail without the change and pass with it, but I ran them directly with go test because ./bt-test couldn't build the code.

What was wrong: with modeSelector on, the top-level class was hard-coded as .dark / .light in markup/highlight/chromastyles.go. The only way to get a different name, such as theme-dark, was to edit the generated CSS text.

What I changed:

  • markup/highlight/chromastyles.go: two new fields, ClassDark and ClassLight, in ChromaStylesOptions. When ModeSelector is set, the prefix is "." + class + " ", and an empty value falls back to dark / light, so existing output is unchanged. The fields have no effect without modeSelector.
  • commands/gen.go: new --classDark (default dark) and --classLight (default light) flags, passed through to the options.
  • tpl/css/css.go: no change needed. The template function already decodes its options map straight into ChromaStylesOptions, so classDark / classLight work in templates automatically.

Tests:

  • TestChromaStylesClassDarkLight (in tpl/css/chromastyles_integration_test.go): builds a site with "classLight" "theme-light" and "classDark" "theme-dark". It checks the output contains .theme-light .chroma, .theme-light .bg {, .theme-dark .chroma and .theme-dark .bg {, and does not contain .light .chroma or .dark .chroma.
  • testscripts/commands/gen_chromastyles_mode.txt: two new CLI cases, one using --classDark theme-dark and one using --classLight theme-light, each checking the new prefix appears and the default one doesn't.

Test evidence:

  • ./bt-test couldn't build anything. Its runs download Go modules from the internet, which the sandbox blocks (dial tcp: lookup proxy.golang.org ... server misbehaving). So there is no ./bt-test result for this change.
  • Direct runs: instead I ran go test against the local module cache in /bt/cache/go-mod, with the network turned off.
  • All TestChromaStyles* tests pass, including the new one.
  • TestCommands/gen_chromastyles and TestCommands/gen_chromastyles_mode pass.
  • The full ./markup/highlight/ and ./tpl/css/ packages pass, and go vet is clean.
  • Before the fix: with only the two production files reverted, TestChromaStylesClassDarkLight fails and the CLI test fails with unknown flag: --classDark.
  • Blast radius: only the modeSelector path is affected, and the defaults keep its output identical. The existing tests covering .dark .chroma / .light .chroma still pass unchanged.

Requirements:

  1. classDark option in css.ChromaStyles: implemented and tested by the template test.
  2. classLight option in css.ChromaStyles: implemented and tested by the template test.
  3. --classDark / --classLight in hugo gen chromastyles: implemented and tested by the CLI test (it failed with "unknown flag" before the change).
  4. Defaults of dark / light: implemented, and the existing tests confirm the default output is unchanged.

Not done:

  • Docs: docs/content/en/commands/hugo_gen_chromastyles.md is generated by hugo gen doc, and it is already missing the existing --mode / --modeSelector flags. I left it alone rather than hand-edit a generated file; running hugo gen doc will add the new flags.
  • Input checking: a value written with a leading dot, like .theme-dark, produces ..theme-dark. I left the class names unchecked to keep the change minimal.

Nothing is committed. AGENTS.md and CLAUDE.md were already deleted in the working tree before this session; I didn't touch them.
