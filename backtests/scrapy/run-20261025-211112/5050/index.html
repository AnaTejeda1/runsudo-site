H2DownloadHandler: make acceptable server frame size configurable

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches add a setting that is advertised to the server and both pass all seven independent tests, so the core ask is met by either. The differences are in robustness, edge handling and tests.

Correctness: Patch A builds the setting into the initial SETTINGS frame and also sets `conn.max_inbound_frame_size` directly, so larger frames are accepted immediately, independent of whether the server ever ACKs the client's settings. That matters for the issue's second use case (servers that ignore the advertised maximum, which are also the servers least likely to behave well). Patch B sends a second SETTINGS frame via `update_settings`; h2 only raises `max_inbound_frame_size` when the server ACKs, so acceptance of large frames depends on ACK ordering. In normal flows the ACK precedes response data, so B works in practice (the independent tests confirm), but it is strictly less robust. The issue explicitly names the standard's limits; A validates the range with a clear ValueError at handler init and in the protocol constructor, while B does no validation, so an out-of-range value surfaces as an h2 `InvalidSettingsValueError` thrown from `connectionMade` on every connection, which is a poor failure mode (logged by Twisted, requests likely hang). A's replacement of `conn.local_settings` reaches into h2 state more than B's use of the public `update_settings` API, but `local_settings`/`max_inbound_frame_size` are public attributes, A preserves the other defaults (and tests that), and the comment explains why.

Tests: A adds a focused in-memory h2 server suite that covers the default being advertised, a custom value being advertised with other settings preserved, rejection above the default, acceptance when configured, rejection above a custom value, both boundary values, and invalid values at both the protocol and handler level, including the exact 'server ignores the advertised maximum' scenario by forcing the server's outbound frame size. B adds one parametrized end-to-end test against the Twisted server; it would fail on base only on the final `local_settings.max_frame_size` assertion, never asserts that frames larger than 16384 were actually sent or received, and does not cover rejection, boundaries or invalid values.

Scope/craft: Both remove the known-limitation note and document the setting. B's docs add a useful caveat about DOWNLOAD_MAXSIZE/WARNSIZE being per-frame and note that the httpx handler ignores the setting, and `HTTP2_MAX_FRAME_SIZE` arguably fits settings naming slightly better than `H2_MAX_FRAME_SIZE`; these are minor pluses for B. A's double validation (handler and protocol) is slight duplication but intentional fail-fast. On balance A resolves the issue more completely, handles the standard's limits the issue calls out, and backs it with far stronger tests.

The issue

View on GitHub

The current implementation of HTTP/2 support in Scrapy requires servers to limit the frame size of the data that they send to the lowest maximum size that the standard defines, which is 16 384 bytes.

We should make this maximum configurable, at least within the limits that the standard defines (16 384 - 16 777 215), so that:

  • The value can be fine-tuned for performance reasons.
  • Scrapy can work with servers that ignore the maximum frame size indicated by Scrapy and send larger frames, which Scrapy does not allow (and should probably not allow, for security reasons).
