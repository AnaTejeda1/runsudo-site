Deprecate the download_delay spider attr after refactoring AutoThrottle

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches resolve the core ask: AutoThrottle stops writing `spider.download_delay` (each adds a downloader-level default delay that AutoThrottle overrides), and a user-defined `download_delay` attribute now triggers a ScrapyDeprecationWarning while still being honored. All four independent tests pass on both, so the decision rests on risk, scope, and craft.

Patch A is the conservative, focused fix. It keeps the existing precedence (spider attribute still overrides the setting, and AutoThrottle's start delay still replaces it, exactly as before), emits the warning in the same spot and style the base code already uses for `max_concurrent_requests`, adds a news entry under Deprecations, updates the settings/autothrottle/faq docs, and adds tests that cover the warning, the new `_default_slot_delay` precedence vs DOWNLOAD_SLOTS, the updated AutoThrottle unit tests, and an end-to-end mockserver crawl asserting the slot delay and that the spider attribute is no longer set.

Patch B takes a broader redesign: it deletes `_get_concurrency_delay`, bridges deprecated attributes into settings in `Crawler._apply_settings`, and makes the Downloader read only settings. That is architecturally tidy, but it carries extra risk and churn beyond the ask: (1) it changes precedence so that DOWNLOAD_DELAY set at spider or higher priority now silently wins over the attribute (previously the attribute always won), which is a behavior change folded into a deprecation step; (2) it remaps the already-deprecated `max_concurrent_requests` from CONCURRENT_REQUESTS to CONCURRENT_REQUESTS_PER_DOMAIN and rewrites a historical release-notes entry to match, which is unrelated to this issue; (3) it reads the attribute from `spidercls` when `_apply_settings` runs before spider creation, so instance-level attributes set in a spider `__init__` can be missed in flows that apply settings early, whereas the base read the instance at slot-creation time; (4) it adds no news entry for the new deprecation, removes the settings.rst note while leaving the `spider-download_delay-attribute` label dangling, and rewrites the FAQ example to DOWNLOAD_SLOTS (unrelated churn). B's tests are reasonable (bridge applied/ignored, downloader `_delay`), but it drops the AutoThrottle test matrix that covered the spider attribute as the min delay and adds no integration test.

On correctness both work; on tests A is somewhat stronger (end-to-end coverage, keeps attribute-vs-setting matrix); on scope A is tighter while B's extra changes add real risk; on craft A includes the news entry and consistent doc updates. A is the better patch.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Each saw the issue and the two patches, labelled A and B in random order (two of them saw ours as A), with issue links and version numbers removed. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours. The reasoning above is one judge's, shown verbatim.
