Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches stop the deletion of in-use mixed-case cache files by lowercasing the walked name and comparing against the lowercased keys in `seen`, and both would fix the reported case-insensitive scenario. The decisive difference is correctness on case-SENSITIVE filesystems (Linux, most CI). Patch A applies `!seen.Has(name) && !seen.Has(strings.ToLower(name))` unconditionally, so if a genuinely stale mixed-case entry (`MyBundle/foo`) coexists with the currently-used lowercase entry (`mybundle/foo`) as two distinct files, Patch A will never prune the stale one — it silently defeats --gc for those files and lets cruft accumulate forever. Patch B defers the decision: it collects lower-case-collision candidates during the walk and only removes one if the true lowercase key `id` was ALSO independently visited by the walk (i.e., they are two distinct physical files → the mixed-case one is stale). On a case-insensitive FS only one physical file appears, so the candidate is correctly kept; on a case-sensitive FS both appear, so the stale duplicate is correctly pruned. That is the actual root-cause-correct behavior, discriminating the two filesystem semantics rather than blanket-suppressing pruning. Tests reinforce this: Patch A adds one MemMapFs test that only exercises the survives-when-only-mixed-case-exists path and never tests the case-sensitive distinction (a case-sensitive-distinct test would expose Patch A keeping the stale file). Patch B adds (1) a real-OS case-insensitive test guarded by a new `IsCaseInsensitiveFs` helper, (2) a MemMapFs case-sensitive test asserting the stale entry IS pruned (count 1) — directly validating the behavior Patch A gets wrong, and (3) a full end-to-end testscript reproduction with `hugo --gc` matching the issue's repro, gated on a `caseinsensitivefs` condition. Patch B is larger, but the extra surface is justified test infrastructure and a more precise fix; the added craft (issue references, clear deferred-decision comments) is solid. Patch A is smaller and conservative (it never deletes an in-use file), but it is a less complete fix that regresses prune completeness on the majority-case filesystem. Weighing correctness first, then the markedly stronger test evidence, B is the better fix despite its larger scope.

The issue

View on GitHub

What happens

On a case-insensitive filesystem (macOS APFS, Windows), hugo --gc deletes image cache files under resources/_gen that the build actively uses, if the on-disk path case differs from the cache key. The build itself works fine (the case-insensitive filesystem resolves the read), but the pruner's usage check is a case-sensitive string comparison, so the just-used file is considered unused and removed.

The relevant code is in cache/filecache/filecache_pruner.go (unchanged on master):

if !shouldRemove && c.entryLocker.seen.Len() > 0 {
    // Remove it if it's not been touched/used in the last build.
    shouldRemove = !c.entryLocker.seen.Has(name)
}

seen contains the cache key (for images: the lowercased target path, via ImageCache.getOrCreate → c.fcache.ReadOrCreate(relTargetPath, …)), while name is the real on-disk name from the filesystem walk. If they differ only in case, seen.Has(name) is false and the file is deleted.

Why the case can differ in practice

Page paths have been lowercased since the v0.123 page-system rewrite, so cache keys for page-bundle images are lowercase. Caches created by older Hugo versions preserve the source directory case (e.g. resources/_gen/images/collections/PastFuture/…). Such caches are common in the wild: committed to git for CI cold-start speed, restored by CI cache plugins, or simply carried forward on a developer machine across Hugo upgrades.

The result is a permanent rebuild/evict cycle: --gc deletes the in-use entries → the next build silently re-processes all of them → the new files land inside the surviving mixed-case directory (the prune walk visits directories before deleting their files, so the directory is never seen empty and survives; on a case-insensitive filesystem the re-created file then lands in it) → the next --gc deletes them again. On the real site where we found this, every build re-scaled 267 images (~35 s per build, forever).

Minimal reproduction (macOS)

hugo new site repro && cd repro
mkdir -p content/MyBundle layouts/_default
printf 'baseURL = "https://example.org/"\ndisableKinds = ["taxonomy", "term", "rss", "sitemap"]\n' > hugo.toml
printf -- '---\ntitle: My Bundle\n---\n' > content/MyBundle/index.md
cp /path/to/any.jpeg content/MyBundle/cover.jpeg
printf '{{ with .Resources.GetMatch "cover.jpeg" }}{{ with .Resize "100x" }}<img src="{{ .RelPermalink }}">{{ end }}{{ end }}' > layouts/_default/single.html
printf 'home' > layouts/_default/home.html

hugo                      # creates resources/_gen/images/mybundle/cover_hu_<hash>.jpeg
# simulate a cache written by an older Hugo (or copied from elsewhere):
mv resources/_gen/images/mybundle resources/_gen/images/tmp
mv resources/_gen/images/tmp resources/_gen/images/MyBundle

hugo --gc                 # build succeeds (16 ms, cache hit), but reports "Cleaned 1"
find resources -type f    # -> empty: the file the build just used is gone

hugo                      # re-processes the image (474 ms) — and writes it back
                          # into the surviving MyBundle/ dir, so the cycle repeats

Observed output of the --gc build:

Processed images │  1
Cleaned          │  1
Total in 16 ms

A cache file that was read 16 ms earlier is deleted as "not been touched/used in the last build".

What I expected

--gc should never delete a cache entry that the same build read. On case-insensitive filesystems the usage check should match the way the filesystem resolved the read — e.g. compare case-insensitively (or normalize walk names against the seen set) when the cache filesystem is case-insensitive. Renaming the on-disk entry to the key's case would even self-heal old caches.

What the agent reported

The fix is complete, verified, and reviewed. Here is the summary.

What was wrong

On case-insensitive filesystems (macOS, Windows), hugo --gc deleted image cache files under resources/_gen that the build had just used. In cache/filecache/filecache_pruner.go, the pruner's "still in use?" test — c.entryLocker.seen.Has(name) — is a case-sensitive comparison. seen holds cache keys, which have been lowercased since the v0.123 page-system rewrite (e.g. mybundle/cover_hu_x.jpg), while name is the real on-disk name from the filesystem walk, which older caches keep in the source directory case (e.g. MyBundle/cover_hu_x.jpg). The case-insensitive filesystem resolves the build's read fine, but the pruner's exact-match lookup misses, so the in-use file is deleted — producing a permanent rebuild/evict cycle.

What I changed

  • cache/filecache/filecache_pruner.go — the usage check now also matches the lowercased on-disk name, so a file whose key was lowercased still counts as in-use: go seen := c.entryLocker.seen shouldRemove = !seen.Has(name) && !seen.Has(strings.ToLower(name)) Added the strings import and an explanatory comment. This is testable on the case-sensitive Linux filesystem used in CI, unlike an FS-case-insensitivity probe (which can't be triggered there). Any stale file this might conservatively keep on a genuinely case-sensitive FS is still removed by the existing MaxAge/isExpired fallback.
  • cache/filecache/filecache_pruner_test.go — added TestPruneCaseInsensitiveInUse, which mirrors the report's reproduction (create entry with the lowercase key, rename on disk to mixed case, prune, assert nothing pruned and the file survives).

Note: an intermediate step mistakenly rewrote the pre-existing TestPrune in this file; I restored TestPrune verbatim and added the new test alongside it. The reviewer confirmed TestPrune is fully intact.
