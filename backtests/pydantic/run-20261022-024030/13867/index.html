FieldInfo.get_default is 5-6x slower on 2.13 because of a relative import in the function body

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

The source changes in both patches are byte-identical: both hoist `smart_deepcopy` into the existing module-level `from ._utils import ...` line and delete the per-call relative import from `resolve_default_value`. This addresses the root cause named in the issue (the `resolve_name` cost paid on every call of the relative in-body import), and the independent tests confirm both patches move all six base failures to PASS. So correctness and scope are a wash. The difference is tests: Patch A adds none, so nothing would catch a regression if someone reintroduced a lazy import on this hot path. Patch B adds regression tests that record calls to `builtins.__import__` during `get_default()`, `model_construct()`, and private-attribute default resolution, asserting none occur. These would fail on the base commit (the independent harness used the same technique and saw `_utils` imports recorded on base) and pass after the fix, so they are non-tautological and cover the exact scenarios the issue describes, including the `model_construct` case and both `default`/`default_factory` branches. The tests warm up before recording and restore `__import__` via `monkeypatch.undo()`, which is careful enough. Monkeypatching `__import__` is slightly unusual but is the only direct way to assert the absence of an import statement, and it is scoped to the call under test. Patch B is the better fix because it delivers the same correct change plus meaningful protection against recurrence.

The issue

View on GitHub

FieldInfo.get_default() costs about five to six times more on 2.13 than on 2.12.

On 2.13 the call is delegated to pydantic._internal._fields.resolve_default_value, whose body starts with a relative import that runs on every call:

def resolve_default_value(...):
    from ._utils import smart_deepcopy

On 2.12 the plain-default branch was return _utils.smart_deepcopy(self.default), with no import at call time. In 2.13 the import sits before the default_factory branch, so every call pays it.

_fields.py already has a module-level import from ._utils, so the in-body import is not breaking an import cycle, and moving the name up adds nothing to import time.

Measured with timeit, best of 5 runs of 200000 calls:

2.12.32.13.52.13.5, import moved up
FieldInfo(default=123)55 ns300 ns85 ns
FieldInfo(default_factory=list)35 ns271 ns60 ns

The cost is the import statement rather than module loading, since the module is already in sys.modules. With the relative form, resolve_name runs before the sys.modules lookup, so it is paid on every call even though the module is cached. A three-function package, identical except for the import form used to obtain the same callee:

formper call
from ._helper import work inside the body234 ns
from pkg._helper import work inside the body108 ns
module-level import32 ns

Moving the import up removes most of the gap but not all of it. What is left is the extra resolve_default_value call and the sentinel checks added to smart_deepcopy.

This is visible in model_construct(), where get_default runs once per field. For a five-field model with defaults: 1.18 us on 2.12.3 against 2.49 us on 2.13.5. Passing every field explicitly, so that no default is resolved, gives 1.12 us on both.

Version info

pydantic 2.13.5, CPython 3.13, macOS on arm64. The in-body import is still on main. Not measured on Linux or x86_64, so the absolute numbers will differ there, though the ratios should hold.
