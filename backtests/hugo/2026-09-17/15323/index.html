tpl/collections: union silently returns an empty list when the two slice types differ

Worse

The merged fix was judged better than our patch.

In this judgment, Patch B = our agent, Patch A = the merged fix.

The issue's core evidence of a real bug is the sibling disagreement: intersect treats mixed numeric lists as compatible (intersect (slice 1 2) (slice 2.0 3.0) -> [2], matching 2==2.0), while union returns []. Patch A fixes this at the root by letting numeric-vs-numeric mismatches fall through to the existing convertNumber path, so union (slice 1 2) (slice 2.0 3.0) -> [1 2 3] with cross-type dedup (1.0 dedups against 1) — exactly the 'accept mixed types the way intersect does' direction the reporter described, and it makes the two functions consistent. Patch A also adds a genuinely necessary AssignableTo guard: when l1 is empty its result prototype derives from l2, and appending a converted number without the guard would append a wrong-typed value; its added test {[]int{}, []float64{1.0}, []int{}} exercises that edge. Its tests are additive, fail-before/pass-after, and it preserves the existing (still-tested) []string∪[]int behavior where no true typed union is possible. Patch B changes 'return empty' to 'return l1', which does eliminate all silent empties but replaces one silent-wrong-answer with another: it silently drops all of l2, still raises no error on the uncomparable case the issue flagged, and — despite its comment — does NOT make union consistent with intersect (union (slice 1 2) (slice 2.0 3.0) -> [1 2], no 2==2.0 matching, not a real union). The reporter asked for either an error or a true union; B delivers neither, and its claimed 'Union doc contract' justifying return-l1 is asserted, not demonstrated. B also rewrites pre-existing test expectations (the []string{}/[]int{} cases) rather than extending coverage, a larger contract change than its one-line code delta suggests. A's only shortfall is that non-numeric mismatches (int/string, nested slices) still return empty without an error, so it doesn't close every case — but it fixes the specific inconsistency the issue centers on, does so more principledly and consistently with intersect, and its tests are stronger. On correctness of the root cause and test quality, A is clearly the better fix.

What did you expect to see?

union either returning the union of its two arguments, or returning an error. It already errors for the other argument shapes it cannot handle, for example union does not support slices or arrays of uncomparable types and can't iterate over ....

What did you see instead?

union returns an empty slice, with no error, whenever the two arguments have different slice types and neither has an interface element type.

layouts/index.html:

{{ printf "%T" (slice 1) }}
{{ printf "%T" (slice 1.0) }}
union int,int    -> {{ union (slice 1) (slice 2) }}
union int,float  -> {{ union (slice 1) (slice 1.0) }}
union int,string -> {{ union (slice 1) (slice "a") }}
union lists      -> {{ union (slice 1 2) (slice 2.0 3.0) }}
intersect lists  -> {{ intersect (slice 1 2) (slice 2.0 3.0) }}

Output:

[]int
[]float64
union int,int    -> [1 2]
union int,float  -> []
union int,string -> []
union lists      -> []
intersect lists  -> [2]

intersect handles the same two mixed-type lists and returns [2], so the sibling functions disagree about whether these arguments are usable at all.

The cause is this early return in Union:

if l1v.Type() != l2v.Type() &&
	l1v.Type().Elem().Kind() != reflect.Interface &&
	l2v.Type().Elem().Kind() != reflect.Interface {
	return ins.r.Interface(), nil
}

ins.r is the empty slice made just above, so a caller gets an empty list rather than an error. It is reachable from ordinary templates because slice 1 is []int and slice 1.0 is []float64, and it also runs before the uncomparable-types check, so union (slice (slice 1)) (slice 2) returns [] instead of the error that check would raise.

Adding one element of another type to the first argument avoids it, since the slice then becomes []interface {}: union (slice 1 "x") (slice 1.0) returns [1 x].

Happy to send a PR. Returning an error here would be a small change; making union accept mixed types the way intersect does is bigger, so I would rather you pick the direction first.

Summary

What was wrong
(*Namespace).Union in tpl/collections/collections.go had an early-return that fires when the two arguments are slices of different concrete element types (neither being []interface{}). It returned ins.r.Interface() — a freshly-made empty slice — with no error. So union (slice 1) (slice 1.0), union (slice 1 2) (slice 2.0 3.0), etc. silently returned []. This directly contradicted the function's own doc comment (line 635): "If l1 and l2 aren't of the same type then l1 will be returned."

Direction chosen
Honor the documented contract rather than the issue's two suggested options (error / merge-like-intersect). The doc comment and the existing design — where []interface{} operands already merge with numeric conversion — show the intended behavior for two differing concrete types is to return l1. This is the smallest correct change.

What I changed

  • tpl/collections/collections.go:660 — return ins.r.Interface(), nil → return l1, nil (one line, inside the type-mismatch guard).
  • tpl/collections/collections_test.go — the two TestUnion rows at 667–668 asserted the buggy empty-slice output and thus contradicted the report; I corrected their expectations to l1 and added four regression rows (numeric-type mismatch and nested-slice mismatch) documenting the contract. This corrects wrong expectations to the documented behavior; it does not weaken coverage. All pre-existing same-type, []interface{}-merge, struct, nil, and uncomparable-error rows are unchanged.

Test evidence

  • Fail-before: with the corrected/added test rows but before the fix, TestUnion failed at row 3 — Got [] expected [1 2], reproducing the bug.
  • Pass-after: ./bt-test -run 'TestUnion|TestIntersect' → both pass; full-package ./bt-test ./tpl/collections/ → package PASS, zero failures. TestIntersect (the sibling) and the uncomparable-types error rows are unaffected.

All changes are left uncommitted in the working tree.
