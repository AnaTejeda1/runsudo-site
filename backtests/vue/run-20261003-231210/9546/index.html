defineProps options object loses properties when using generics

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches make the same root-cause change. They remove the conditional in `PropMethod`, which was making `PropType<T>` a deferred generic and causing `RequiredKeys`/`OptionalKeys` to drop non-required props. Both therefore restore the missing keys `a` and `b`. They differ in how `InferPropType` resolves the value type.

Patch A short-circuits when no default is present (`unknown extends D`) and returns `V` directly. A generic `T` then resolves cleanly to `T` instead of getting stuck in the deferred `unknown extends V` check. When a default exists or `D` is `any`, it falls back to the original logic via `InferPropValueType`. Tracing the non-generic cases (V = unknown, {}, any, concrete types), the behavior is identical to before, so regression risk is low.

Patch B only tweaks the innermost `IfAny` branch. The result is still a deferred conditional (`unknown extends T ? ... : T`) that happens to be assignable to `T` because every branch collapses to `T`. This works for assignability but leaves an unresolved conditional type in the props. That is less clean for hover display, inference and further type manipulation, and it fixes the symptom more than it normalizes the type.

On tests, Patch A is broader. It covers `ExtractPropTypes`, `ExtractPublicPropTypes`, `ExtractDefaultPropTypes`, `defineComponent` and `defineProps`, all with generics. Patch B adds a single `defineProps` test, though it usefully includes a `default: null` case and a negative check against `string`.

Overall, Patch A gives a more direct resolution of generic prop types and more thorough test coverage at similar scope.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
