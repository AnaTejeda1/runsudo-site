Google Service Account with Domain-Wide Delegation fails with unauthorized_client although impersonation works using Google's official library

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

The reported failure is credential validation: the Google Service Account credential is shared across Google nodes, and its test is supplied by the Sheets (v1/v2) and Chat nodes, which request Sheets or Chat scopes with `sub` set to the delegated user. Google rejects that with `unauthorized_client` whenever the Workspace admin delegated only Gmail scopes, exactly the issue scenario. Patch A targets that root cause: it adds `getGoogleCredentialTestAccessToken`, which validates the service account and key without impersonating unless the user explicitly listed scopes (HTTP Request setup), in which case it impersonates with those scopes. All three credential-test providers (SheetsV1, SheetsV2 credentialTest, Chat) are switched to it, the Chat node's duplicated JWT code is removed, and new unit tests cover the impersonating-with-node-scopes case, the explicit-scopes case, the non-impersonating case, and error propagation. The trade-off (delegation isn't verified at save time unless scopes are listed) is stated in a doc comment. Patch B only shrinks the `gmail` runtime scope list to `https://mail.google.com/`. That helps the Gmail node at execution time when the admin delegated only that single scope, but it leaves the credential test untouched: saving/testing an impersonating credential still requests Sheets or Chat scopes under the delegated subject and still fails with `unauthorized_client`. Its test exercises `getGoogleAccessToken` with the 'gmail' service, not the credential-test path the issue describes, so it would not have caught the reported bug. The independent tests crashed on all three trees and provide no signal, but the diffs alone show B does not resolve the reported validation failure while A does. A's broader refactor of the Chat node is low-risk and consolidates duplicated logic rather than obscuring the fix.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Each saw the issue and the two patches, labelled A and B in random order (two of them saw ours as A), with issue links and version numbers removed. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours. The reasoning above is one judge's, shown verbatim.

The issue

View on GitHub

Describe the problem/error/question

I'm trying to use a Google Service Account with Domain-Wide Delegation to access multiple Gmail mailboxes in n8n Cloud.

The Service Account is configured correctly in Google Cloud, Gmail API is enabled, and Domain-Wide Delegation is configured in Google Workspace Admin.

However, enabling "Impersonate a User" in the Google Service Account credential always fails during credential validation.

Without impersonation enabled, the credential saves successfully.

The problem appears to be specific to n8n's credential validation, because the exact same Service Account, private key, scopes and impersonated user work correctly using Google's official Python library.

What is the error message (if any)?

Couldn't connect with these settings

Private key validation failed:
401
{
  "error": "unauthorized_client",
  "error_description": "Client is unauthorized to retrieve access tokens using this method, or client not authorized for any of the scopes requested."
}

Steps to reproduce

  1. Create a Google Cloud project.
  2. Create a Service Account.
  3. Enable Domain-Wide Delegation.
  4. Enable the Gmail API.
  5. Configure Domain-Wide Delegation in Google Workspace Admin using the Service Account Client ID.
  6. Authorize Gmail scopes (tested with both https://mail.google.com/ alone and multiple Gmail scopes).
  7. Create a Google Service Account API credential in n8n.
  8. Fill in:
  • Service Account Email
  • Private Key
  • Impersonate a User
  • Click Save or Test.

Result:

The credential validation fails with unauthorized_client.

Expected result:

The credential should successfully obtain an OAuth access token and save correctly.

Additional investigation

I verified that the Google configuration is working correctly outside of n8n.

Using the exact same Service Account JSON, impersonated user and scope with Google's official Python library:

from google.oauth2 import service_account
import google.auth.transport.requests

credentials = service_account.Credentials.from_service_account_file(
    "service-account.json",
    scopes=["https://mail.google.com/"],
    subject="mgalarza@merlindataquality.com"
)

request = google.auth.transport.requests.Request()
credentials.refresh(request)

print(credentials.token)

The access token is generated successfully.

This confirms:

  • The Service Account is valid.
  • The private key is valid.
  • Domain-Wide Delegation is configured correctly.
  • The impersonated user works.
  • Google issues an access token successfully.

Therefore, the problem appears to be specific to n8n's Google Service Account credential implementation or validation process.

Environment

  • n8n Cloud
  • n8n Version: 1.123.67
  • Google Workspace
  • Gmail API
  • Google Service Account with Domain-Wide Delegation
