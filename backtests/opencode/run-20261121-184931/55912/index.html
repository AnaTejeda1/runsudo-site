Bug: Right-click context menu in the prompt input is not localized on Linux

Summary

The right-click context menu inside the prompt/composer textarea shows English labels
(Cut, Copy, Paste, Select All) even when OpenCode is set to a translated language
(e.g. 简体中文). The rest of the UI is correctly translated.

This menu is rendered by electron-context-menu@5.0.0, which hardcodes English label
strings. Because explicit labels override Electron's role-based localization, the app's
existing translation system never reaches this code path.

Environment

OpenCode Desktop2.0.18
Chromium / Electron152.0.7977.130
OSopenEuler 24.03 LTS-SP3 (x86_64)
DesktopUKUI
App language简体中文 (Settings → General → Language)
System localeLANG=zh_CN.UTF-8

Steps to reproduce

  1. Launch OpenCode Desktop on Linux.
  2. Set the app language to 简体中文 (the UI translates correctly).
  3. Focus the prompt input and type some text.
  4. Right-click inside the prompt input.

Expected

剪切 / 复制 / 粘贴 / 全选.

Actual

Cut / Copy / Paste / Select All.

Root cause

The context menu is built by electron-context-menu, called from
out/main/desktop-KkXTWBJy.js:

Bv = P(function* () {
  let { default: e } = yield* _t(() => import(`electron-context-menu`))
  e({ showSaveImageAs: !0, showLookUpSelection: !1, showSearchWithGoogle: !1 })
})

electron-context-menu@5.0.0 ships a default template with hardcoded English labels
(node_modules/electron-context-menu/index.js):

label: 'Cu&t',
label: '&Copy',
label: '&Paste',
label: 'Select &All',

Because these items set an explicit label, Electron's `role: 'cut' | 'copy' | 'paste' |
'selectAll'no longer localizes them.electron-context-menu@5.0.0` also has **no
translate option**, so there is currently no hook to override the labels.

Meanwhile the app's own i18n is wired up for native menus:

  • The translation bundles already contain the strings — out/renderer/assets/zh-DvrsSppn.js has "desktop.menu.cut": 剪切, "desktop.menu.copy": 复制, etc.
  • The main process builds its application menu from labelKeys and resolves them through W(), and onNativeTranslations pushes renderer translations into the main process.

However, that menu is only installed on macOS — in out/main/desktop-KkXTWBJy.js:

function Bg(e) {
  if (process.platform !== `darwin`) return
  ...
  Ia.setApplicationMenu(Ia.buildFromTemplate(t))
}

So on Linux there is no application menu, and the electron-context-menu path used for
right-click is never connected to the translation system at all.

Supporting evidence

  • The Chromium children are launched with --lang=zh-CN, and locales/zh-CN.pak is present, so the OS/Chromium locale is correct — the labels are English purely because they are hardcoded in the library.
  • Settings → General → Language already offers 简体中文 and it works for the web UI, so the translation pipeline itself is functional.

Suggested fix

Either of these would resolve it:

  1. Pass a translated template to electron-context-menu built from the dictionaries the app already loads (the renderer can send them over via the existing onNativeTranslations channel, or the main process can load them directly).
  2. Use Electron's built-in default context menu by not intercepting contextmenu on Linux. Electron localizes it from the active locale, so it would follow the app language automatically. (Tracked upstream as electron/electron#32133.)

Option 2 is preferable: it removes a dependency and gets localization for free.

Notes

  • Image/video/link items (Save Image As…, Copy Video Frame, Inspect Element, etc.) in the same template are untranslated too, for the same reason.
  • Not verified on macOS/Windows — I only have a Linux box to test on.
