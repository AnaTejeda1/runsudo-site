Issue #5290 Merged fix PR #5294 Run 24 Oct 2026 · run-20261024-184640 openai/openai-agents-python

After an approval, the resumed run records the approved tool span outside the agent span

Worse

The merged fix was judged better than our patch.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the root cause the same way: they open the agent span before `resolve_interrupted_turn` on resume in both the blocking (`run.py`) and streamed (`run_loop.py`) paths, remove the later span-open block so it is not duplicated, and add `attach_generic_agent_error` to the streaming top-level exception handler so a resumed tool failure that bypasses the per-turn handler still marks the agent span with 'Error in agent run'. The independent tests confirm both resolve every scenario in the issue (parenting with task/turn spans on and off, streamed and not, stop_on_first_tool, and the error case). The differences are in completeness and testing. Patch A additionally threads the agent span into `resolve_interrupted_turn` and populates `span_data.tools`/`span_data.handoffs` from the resolved tools, so an agent span whose run ends on the approved tool (stop_on_first_tool or a raising tool) carries the same tool/handoff metadata it would have had without the interruption; Patch B leaves those lists empty in that case, a small but real inconsistency with the non-approval span the issue uses as its reference. Patch A's test is substantially more thorough: 16 parametrized cases covering continue, stop, error and handoff outcomes across streamed/non-streamed and task/turn spans on/off, and it asserts span parenting, tool/handoff metadata, both error messages, that every span ends, that span_start/span_end counts balance, and that no span is left current after the run — the last three guard against the main regression risk of opening the span earlier (a leaked or unbalanced span on a handoff or early return). Patch B's two tests cover success and error for both modes but do not cover stop_on_first_tool, handoff, or span-balance. Patch B's `start_agent_span` helper is a nice de-duplication and slightly cleaner craft, and its minimal placement right before `resolve_interrupted_turn` is tidy, but that does not outweigh A's broader verification and more complete agent span. A's extra parameter on `resolve_interrupted_turn` is a modest scope extension but directly serves the issue's expected behaviour and adds little risk.

Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours. Describe the bug

After state.approve(...), the resumed run executes the approved tool before it opens its agent span. The function span becomes a child of the task span, or of the trace root when task and turn spans are off. Only the paused span from the first run (docs/tracing.md:147) sits inside an agent span. If the approved tool has failure_error_function=None, as below, and raises, the resumed run ends without an agent span or Error in agent run.

resolve_interrupted_turn runs at src/agents/run.py:1115 while current_span is still None (:928). The agent span opens later, at :1492-1504. The streamed path has the same order, at src/agents/run_internal/run_loop.py:1323 and :1564-1576.
