v-model on <select multiple> uses stale collection type after switching between Array and Set

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

The two source fixes are functionally identical, so the decision rests on tests and craft. Both stop capturing `isSet(value)` once in `created`. Instead they store the current binding value on the element in `created` and refresh it in `beforeUpdate`. The change listener then reads `isSet(el._modelValue)` when it fires. This addresses the root cause: the stale closure over the initial collection type. It works in both directions.

Tests: Patch A's single test starts with an Array, switches to a Set and checks the next change emits a Set. It then switches back to an Array. The first half would fail before the fix. The second half would pass even without the fix, because the original captured type was Array. So the Set→Array direction is never really exercised from a Set-initialized model. A also adds an unneeded `value: null` prop on the select.

Patch B adds two tests, one starting from an Array and one from a Set. Each switches type at runtime and would fail before the fix, so both directions the issue mentions are covered. B also checks that `setSelected` reflects the new model after the switch. It confirms the type persists across several subsequent changes and uses exact order checks with `toEqual`.

Craft: B types the element as `HTMLSelectElement & { _modelValue?: any }` rather than repeating `(el as any)` casts, and adds a short explanatory comment. That is cleaner and closer to how other directives in the file type their element extensions.

B wins on test thoroughness and slightly better craft.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Steps to reproduce

  1. Bind a <select multiple v-model> to an Array.
  2. Switch the bound value to a Set at runtime.
  3. Interact with the select again.
  4. The emitted model becomes an Array again.
  5. Switching back from Set -> Array shows the same stale-type behavior in reverse.

What is expected?

The current collection type should be respected after the model switches at runtime.

What is actually happening?

The change handler keeps using the collection type captured when the directive was created, so the first user interaction after a runtime Array/Set switch emits the old type.
