TOML config opts verbosity_assertions, verbosity_subtests, & verbosity_test_cases no longer accept numeric string values in 9.2.0

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches make every independent test pass, so they are equal on the issue's headline scenarios. The difference is in how they get there and what else they change.

Patch A fixes the problem where it actually lives: the TOML value-conversion path in Config._getini. It adds an explicit opt-in set on the Parser and, for options in that set, coerces a numeric TOML string to int the same way an INI value would be coerced. The option keeps its precise `int | Literal["auto"]` type, `getini` keeps returning an int (so `get_verbosity`'s `int(level)` and any other caller see a consistent type), the existing rejection of `"loud"` at `getini` time is preserved, and `"2.5"` is explicitly tested as still rejected. Its tests cover all three options, a real pyproject.toml run that checks the assertion diff appears, the inicfg path, and the negative case. The behaviour matches exactly what the 9.2.0 changelog promised: numeric strings still accepted, silently, for backward compatibility.

Patch B instead loosens the option type to `int | str`, so `getini` now returns the raw string `"2"` (and also accepts `"loud"`), and moves validation into `get_verbosity`, which converts, raises UsageError for non-numeric strings, and emits a new PytestRemovedIn10Warning. It also removes the existing `verbosity_assertions = "loud"` case from the getini rejection test, which is a small regression in validation timing: bad values now only surface when some plugin happens to call `get_verbosity`. Beyond the fix, B introduces a brand-new deprecation (warning text, deprecation changelog, docs section) and extends it to `tmp_path_retention_count`, which was not broken on base. Deciding to deprecate something the 9.2.0 changelog explicitly promised to keep accepting is a project-policy decision, not part of the reported bug, and it adds risk (users upgrading from a config error to a deprecation warning they did not ask for) and churn across four files. Its `_warned_verbosity_strings` dedup set and the ad-hoc str check in tmpdir.py are also more scattered than A's single conversion-layer fix.

On correctness both resolve the issue; on root cause A is at the conversion layer while B works around the type by widening it; on tests both are real and would fail before the change, with A's slightly broader on the issue's own options and B's covering the extra deprecation it invented; on scope A is tight and B adds a policy change and an unrelated option; on craft A keeps types and `getini` semantics intact. A is the better fix.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Each saw the issue and the two patches, labelled A and B in random order (two of them saw ours as A), with issue links and version numbers removed. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours. The reasoning above is one judge's, shown verbatim.

The issue

View on GitHub

As of version 9.2.0, the options verbosity_assertions, verbosity_subtests, & verbosity_test_cases no longer accept numeric string values in pyproject.toml configuration files.

Despite the changelog entry stating that they still accept numeric string values for backwards compatibility, they only accept integer values or 'auto'.
