Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

The issue is specifically about SQLiteSession replay: a triage agent's empty reasoning item is persisted, every stored item is sent back each turn, and a later turn 404s on the stale rs_ id. The existing `reasoning_item_id_policy="omit"` only applied when the SDK built follow-up input and (per Patch B's comment) on session write, so history already in the database still carried ids and the mitigation could not rescue an existing conversation. Patch B closes exactly that gap: it threads the resolved policy into `prepare_input_with_session` (both `Runner.run` and the streamed path, including the resumed-state branch), strips ids from converted session history on read, and correctly moves the policy resolution ahead of session preparation in run.py so it is available when needed. Its tests simulate a realistic server-side 404 for a revoked id, store the item in a session before opting in, and verify the replayed input no longer carries the id, in both streamed and non-streamed modes. The independent session-replay tests fail on base and Patch A and pass only with B, matching the issue's stated configuration. Patch A instead threads the policy through nested handoff history (which only forwards raw reasoning items when a custom `handoff_history_mapper` is supplied) and into error-handler `history`/`output` data; neither is the path the issue describes (default session management, no custom mapper), and the error-handler data is not sent to the model at all. A's tests are solid and it fixes a real adjacent gap, but it leaves the reported session scenario broken, as the independent tests confirm. B is also smaller and more targeted. Neither patch changes user-supplied initial input (the issue's literal repro), but that is documented behaviour and applies equally to both.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours. Describe the bug

In certain scenarios, the Agents SDK returns the following error:

Example:

openai.NotFoundError: Error code: 404 - {'error': {'message': "Item with id 'rs_3c4caff36e34c099006900f0e3c66481909c15ac262a15b060' not found.", 'type': 'invalid_request_error', 'param': 'input', 'code': None}}

Configuration:

  • Store is not set to False
  • Using default session management: SQLiteSession
  • All items stored in the database are sent back to the agent for each turn
  • Multi-agent system architecture with handoffs:
  • Agent 1: gpt-5 with minimal reasoning (acts as the triage agent)
  • Agent 2: gpt-5 with medium reasoning
  • Agent 3: gpt-5 with low reasoning

Issue:
Agent 1 generates an empty reasoning item as shown below:

8|f00b2f3b-770b-4f40-9ca3-ae7700940a19_6555bacd-f286-42b3-9f25-e7a9ae94e3de|{"id":"rs_3c4caff36e34c099006900f0e3c66481909c15ac262a15b060","summary":[],"type":"reasoning"}|2025-10-28 16:36:16

After several steps (including outputs produced by Agent 2 and Agent 3), when Agent 1 regains control and any new message is passed, the error above is triggered.

Debug information

  • Agents SDK version: 0.2.8
  • Python version: Python 3.11.6
