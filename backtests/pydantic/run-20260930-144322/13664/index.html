Description

ser_json_temporal landed in v2.12 and controls how datetime, date, time and timedelta are serialized to JSON. GenerateJsonSchema was never told about it, so a mode='serialization' schema still says these fields are strings even when model_dump_json() writes numbers.

With ser_json_temporal='seconds' (same with 'milliseconds'), every temporal field is affected:

schema:  {'dt': {'type': 'string', 'format': 'date-time'}, 'td': {'type': 'string', 'format': 'duration'}}
dump:    {'dt': 1577836800.0, 'td': 86400.0}

Running that payload through a JSON Schema validator fails with 1577836800.0 is not of type 'string', so the schema pydantic publishes rejects the output pydantic itself just produced. date_schema, time_schema and datetime_schema read no config at all right now.

There is a second mismatch that goes the other way, on timedelta. timedelta_schema only looks at the older ser_json_timedelta setting. The docs for ser_json_temporal say it takes precedence over ser_json_timedelta, and pydantic-core implements exactly that: SerializationConfig::from_config and TimeDeltaSerializer::build both check whether ser_json_temporal is present in the config before falling back to ser_json_timedelta. The JSON schema layer does not, so setting ser_json_temporal='iso8601' together with ser_json_timedelta='float' gives you the reverse problem:

schema:  {'td': {'type': 'number'}}
dump:    {'td': 'P1D'}

For anyone generating an OpenAPI document from a model this is a silent wrong answer rather than a crash, which is probably why it has gone unnoticed since the setting was added.

I have a patch that mirrors the pydantic-core resolution in the four temporal schema methods, plus tests. Happy to open a PR if you want to assign this to me.

What the agent reported

I fixed both schema mismatches from the report, and the tests pass. The changes are uncommitted in the working tree.

What was wrong

In pydantic/json_schema.py, GenerateJsonSchema never read ser_json_temporal:

  • date_schema, time_schema and datetime_schema always returned string schemas. With 'seconds' or 'milliseconds', model_dump_json() writes numbers, so the published schema rejected pydantic's own output.
  • timedelta_schema only looked at ser_json_timedelta. pydantic-core lets an explicitly set ser_json_temporal take precedence, so ser_json_temporal='iso8601' with ser_json_timedelta='float' produced {'type': 'number'} while the dump was 'P1D'.

What I changed

  • pydantic/json_schema.py: date_schema, time_schema and datetime_schema return {'type': 'number'} when ser_json_temporal is 'seconds' or 'milliseconds'. Otherwise they return the same strings as before.
  • timedelta_schema: if ser_json_temporal is set in the config and isn't None, it decides the result (number or duration string). Otherwise the old ser_json_timedelta logic applies, so existing configs behave the same.
  • It has to check whether the key is set: the config object fills in 'iso8601' for an unset ser_json_temporal, which would otherwise always override ser_json_timedelta.
  • It also ignores a None value, because pydantic-core never sees None-valued keys. The reviewer flagged this and I applied it.
  • The new behaviour applies in both validation and serialization mode, the same way ser_json_timedelta and ser_json_bytes already work. One side effect: in validation mode these fields are now described as numbers, even though pydantic also accepts strings on input.
  • tests/test_json_schema.py has two new tests:
  • test_model_ser_json_temporal: checks iso8601, seconds and milliseconds for all four types.
  • test_model_ser_json_temporal_precedence_over_timedelta: checks iso8601 with float, and seconds with iso8601.

Both assert the exact schema and also check that each value in model_dump_json() is a number exactly when the schema says number.

Test evidence

  • Before the fix: 4 of the 5 new cases failed (seconds, milliseconds and both precedence cases). The iso8601 case passed, as expected.
  • After the fix: ./bt-test tests/test_json_schema.py tests/test_datetime.py tests/test_types.py tests/test_config.py gave 1135 passed, 6 skipped, 2 xfailed, 0 failed. That run includes the existing ser_json_timedelta tests for models, dataclasses and TypedDicts.
  • No existing test was changed, and no scratch files were left behind.

Requirements

  1. ser_json_temporal='seconds' makes the schema say number for datetime, date, time and timedelta: done, covered by test_model_ser_json_temporal[seconds].
  2. Same for 'milliseconds': done, covered by [milliseconds].
  3. iso8601 still gives string schemas: unchanged, covered by [iso8601].
  4. ser_json_temporal takes precedence over ser_json_timedelta for timedelta: done, covered by both precedence cases.
  5. The report's example, where the schema contradicted the dump: covered. Both tests check the dumped JSON types against the schema.
  6. Default values in the schema: I changed nothing here. The reviewer checked encode_default: defaults are dumped with the model's own config first, so ser_json_temporal already applies to them. No test covers this case specifically.

The new tests only cover BaseModel. Dataclasses and TypedDicts go through the same config lookup, and their existing ser_json_timedelta tests still pass, but there's no new test with ser_json_temporal for them.
