js.Build: browser:false modules with extensionless require fail with lstat in v0.168.0

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the reported failure and pass all three independent tests, so the decision rests on where the fix lives and on test quality.

Patch A keeps the fix local to the esbuild OnLoad hook that introduced the regression: it Lstats the path first, and when the path does not exist it returns an empty OnLoadResult so esbuild falls through to its own handling (the disabled-module stub, or its normal 'Could not resolve' error for genuinely missing files). CheckReadPath keeps its strict contract, so any other in-process caller still gets a hard error for nonexistent or dangling paths. Its test is also stronger: it covers the extensionless case, the explicit-extension control, asserts the excluded content is absent, and adds a negative case confirming a truly missing require still fails. Minor nit: the extra Lstat per loaded file is a small cost, and an import of strings is assumed present.

Patch B instead relaxes the shared security primitive CheckReadPath so any nonexistent path passes, flipping an existing hexec unit-test expectation to do so. The sentinel-error trick to avoid caching is correct but adds subtlety, and it widens the behavioural change beyond the esbuild hook (e.g. a dangling symlink now passes the boundary check rather than erroring). Its integration test covers only the extensionless case with no negative or control case. The semantics B chooses are defensible, but A resolves the issue with less change to a security-relevant contract and with more thorough tests, so A is the better fix.

Summary

js.Build fails when a dependency uses an extensionless CommonJS require that is disabled by a browser field mapping to false.

The target .js file exists. However, Hugo reports lstat .../util.inspect: no such file or directory for the extensionless path instead of allowing esbuild to produce the disabled module stub.

This reproduces without any theme, content, external npm installation, or custom security settings.

Minimal reproduction

Run the following in an empty directory. The small package under node_modules is a synthetic fixture, not an installed dependency.

mkdir -p assets layouts node_modules/browser-disabled-repro

cat > hugo.toml <<'EOF'
baseURL = "https://example.org/"
disableKinds = ["taxonomy", "term", "rss", "sitemap"]
EOF

cat > layouts/index.html <<'EOF'
{{ $js := resources.Get "main.js" | js.Build }}
<script src="{{ $js.RelPermalink }}"></script>
EOF

cat > assets/main.js <<'EOF'
import value from "browser-disabled-repro";
console.log(value);
EOF

cat > node_modules/browser-disabled-repro/package.json <<'EOF'
{
  "name": "browser-disabled-repro",
  "version": "1.0.0",
  "main": "index.js",
  "browser": {
    "./util.inspect.js": false
  }
}
EOF

cat > node_modules/browser-disabled-repro/index.js <<'EOF'
module.exports = require("./util.inspect");
EOF

cat > node_modules/browser-disabled-repro/util.inspect.js <<'EOF'
module.exports = "This file must be excluded from browser builds.";
EOF

hugo --noBuildLock

Actual result

On v0.168.0 the build exits with code 1. Relevant error excerpt (absolute project path normalized):

error calling RelPermalink: JSBUILD: failed to transform "/main.js" (text/javascript): lstat /path/to/repro/node_modules/browser-disabled-repro/util.inspect: no such file or directory

Expected result

The build should succeed, with the dependency replaced by an empty browser module according to browser: { "./util.inspect.js": false }, without including the excluded file's content.

Comparison and control

ConfigurationResult
v0.166.0, require("./util.inspect")Build succeeds, exit 0
v0.168.0, require("./util.inspect")Build fails with the lstat error, exit 1
v0.168.0, changing only the require to require("./util.inspect.js")Build succeeds, exit 0

The v0.166.0 output explicitly contains a disabled-module stub:

// (disabled):node_modules/browser-disabled-repro/util.inspect
var require_util = __commonJS({
  "(disabled):node_modules/browser-disabled-repro/util.inspect"() {
  }
});

The explicit-extension control is only diagnostic; it is not a proposed fix for third-party dependencies.

Possibly related change

Commit https://github.com/gohugoio/hugo/commit/2aa51f3485054bca4a2e368bed4be32367b229e6 adds an OnLoad hook in the file namespace that calls CheckReadPath(args.Path). CheckReadPath uses filepath.EvalSymlinks, which requires the path to exist.

The failure appears consistent with that hook checking esbuild's disabled-module path as though it were a file to load. This is a suspected explanation, not a bisected root cause; v0.167.0 and current master have not been tested.

The original occurrence was through instantsearch.js -> qs -> side-channel -> object-inspect@1.13.4. That package uses require('./util.inspect') and maps "./util.inspect.js" to false in its browser field.

I searched open and closed issues and pull requests for util.inspect, object-inspect, CheckReadPath, and related browser-disabled/esbuild errors and did not find a matching report.

This report and the synthetic reproduction were prepared with GitHub Copilot assistance; the version comparison and control were executed locally.
