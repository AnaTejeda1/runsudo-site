Node.before(Node) / after(Node) throw NPE and detach the node when given the node itself

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

The two code changes are identical. Both add `if (node == this) return this;` in `Node.before(Node)` and `Node.after(Node)`, after the null validations and before the sibling-removal step. That is the root cause: when `node == this`, the `node.parentNode == parentNode` check is always true, so the node removes itself and `parentNode` becomes null. Returning early restores the 1.15.4 no-op behavior the issue describes, and returning `this` matches the method's existing return contract. Correctness and scope are therefore equal. Patch A's CHANGES.md entry is neutral. Patch B's inline comment is a small clarity gain but not significant.

The difference is in the tests. Both patches add before-self and after-self tests on an Element that would throw an NPE before the fix and pass after it. Both check the return value, the parent, and the child count. Patch A checks the position with `ul.child(1)` and the order with text. Patch B checks `siblingIndex()` and the exact serialized HTML, which is a slightly stronger structural check. Patch B also adds a test on a TextNode. Element overrides `before` and `after` and delegates to `Node`, so this test exercises the base `Node.before/after` directly on a non-Element node type and covers both methods. That broadens coverage of the fixed code path in a meaningful way.

One small risk: Patch B relies on `TextUtil` being imported in NodeTest. It is already used in jsoup's test suite, so this is likely fine.

With identical fixes, Patch B's more thorough tests give it the edge.

Test

@Test
public void test_before_self() {
    Document doc = Jsoup.parse("<ul><li id=a>A</li><li id=b>B</li><li id=c>C</li></ul>");
    Element ul = doc.expectFirst("ul");
    Element b = doc.expectFirst("#b");

    try {
        b.before(b);
    } catch (ValidationException expected) {
        // Rejecting a self-insert may also be reasonable.
    }

    assertSame(ul, b.parent());
    assertEquals(3, ul.childrenSize());
}

Description

Calling before(Node) or after(Node) with the node itself throws a NullPointerException, and the node has already been removed from the document when the exception is thrown:

java.lang.NullPointerException: Cannot invoke "org.jsoup.nodes.Element.addChildren(int, org.jsoup.nodes.Node[])" because "this.parentNode" is null
 at org.jsoup.nodes.Node.before(Node.java:410)
 at org.jsoup.nodes.Element.before(Element.java:1032)

After this, b.parent() is null and the list only contains A and C.

This looks like a regression from 62de0a18, first released in 1.16.1. The test above passes on 1.15.4, where b.before(b) and b.after(b) leave the document unchanged.

Since that commit, when node == this, the check node.parentNode == parentNode is always true, so node.remove() removes this node and clears this.parentNode before parentNode.addChildren(...) runs. The validateChild check from #2558 runs inside addChildren, so it isn't reached.

This can happen when the node being moved and the reference node come from separate lookups and turn out to be the same element.
