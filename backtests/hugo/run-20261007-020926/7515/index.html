Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Patch B resolves the issue directly and is the better fix. It adds an opt-in `splitWords` flag for string indices such as title. Values are split on characters that are not letters, numbers or marks, which is Unicode-aware. Words are deduplicated per document, so repeated words cannot inflate rank. It also adds configurable `stopWords`, which the issue explicitly suggests for ignoring common words in an i18n-friendly way. The routing goes through the existing StringsToKeywords/ToKeywords paths, so both indexing and querying are consistent. It rejects the unsupported fragments combination at config decode time with a clear error and documents the new options. Its tests are meaningful and would fail before the change: unit tests cover splitting, Unicode, stop words and dedup; search tests cover named slices, document search and stop-word exclusion; there is a config decode test including the fragments error; and an integration test compares results with and without splitWords.

Patch A adds `tokenize` and `minTokenLength` and extends tokenization to fragment heading titles, which adds complexity and risk:
- For fragments, tokenized heading words become `StringKeyword` (via stringToKeyword), not `FragmentKeyword`. The ApplyFilter branch only collects words when `kw.(FragmentKeyword)` succeeds, so `ff.words` appears never to be populated. The tokenized applyFilter path therefore looks broken, which casts doubt on its own ApplyFilter test.
- The plain string/[]string tokenize path does not deduplicate repeated words within a value, so rank can be inflated. Dedup was added only for fragments.
- It has no stop-word support; minTokenLength is a cruder substitute.
- It mixes in unrelated whitespace churn in an existing test file.
- It has no docs and no config validation.

Overall, B is more correct, better scoped, better tested and better documented.

The issue

View on GitHub

When specifying the indices for related content, it would be useful to specify that some of them were split by word, so that their text could be matched partially. This would allow the title to be used for more in-depth indexing, rather than requiring the user to specify tags / keywords.

This would likely increase memory usage and decrease performance, so should definitely be opt-in!

I suspect common words (a, an, the etc) might want to be ignored? Although doing that in a sane, i18n-friendly manner might be a challenge!
