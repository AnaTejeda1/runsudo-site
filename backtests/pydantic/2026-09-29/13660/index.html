In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches resolve the root cause identically by treating a bare `none` core schema as equivalent to `Literal[None]` (returning `[None]`) in `_infer_discriminator_values_for_inner_schema`. The deciding factor is completeness of the fix. Patch B additionally fixes JSON schema generation: without the `k is None -> 'null'` branch, a None discriminator would serialize to the Python `str(None)` = `'None'` in the discriminator mapping, which does not match the JSON-serialized payload value `null`, producing a subtly broken schema. Patch A leaves this defect in place and only tests validation. Patch B's tests are stronger: `test_none_discriminated_union` asserts both the correct `'null'` mapping AND validation behavior for both branches, directly reproducing the issue. Patch B also correctly loosens the overly-narrow `list[str | int]`/`Hashable` type annotations that are inconsistent with `None` being a valid discriminator value (a real correctness/typing improvement). The downsides of B are genuine scope creep: the wholesale conversion of the if/elif chain to a `match` statement is unrelated churn that enlarges the review surface, and the test-file changes rewrite the existing `test_bool_discriminated_union` assertion style. Patch A is admirably minimal and its test would pass. But weighting correctness first, B fixes both the validation path and the JSON schema path that A misses, making B the more complete and defensible fix despite the refactor churn.

Description

Literal[None] and None should be semantically equivalent type annotations, to the point that flake8-pyi and ruff have warnings for the former: https://docs.astral.sh/ruff/rules/redundant-none-literal/

Pydantic does however not treat them as semantically equivalent for the purposes of discriminated unions.

Example Code

from typing import Annotated, Literal

from pydantic import BaseModel, Field


class A(BaseModel):
    field: Literal["A"] = "A"


class B(BaseModel):
    field: None = None


class Foo(BaseModel):
    a_or_b: Annotated[A | B, Field(discriminator="field")]

# Results in the error below. 
# If `: None` is replaced with `: Literal[None]` then there is no error.
# ...
# pydantic.errors.PydanticUserError: Model 'B' needs field 'field' to be of type `Literal`
# 
# For further information visit https://errors.pydantic.dev/2.13/u/discriminator-needs-literal

Summary

What was wrong: In discriminated unions, a member whose discriminator field was annotated with a bare None (e.g. field: None) was rejected with PydanticUserError: needs field '...' to be of type Literal (code discriminator-needs-literal), while the semantically-equivalent field: Literal[None] worked. The cause: _infer_discriminator_values_for_inner_schema in pydantic/_internal/_discriminated_union.py dispatches on the field's core-schema type. A bare None produces {'type': 'none'}, which had no handler and fell through to the final else that raises the error, whereas Literal[None] produces {'type': 'literal', 'expected': [None]} and was handled.

What I changed:

  • pydantic/_internal/_discriminated_union.py: added an elif schema['type'] == 'none': branch returning [None], matching exactly what the 'literal' branch yields for Literal[None]. Minimal, additive (a path that previously errored now succeeds), no annotation or other behavior touched.
  • tests/types/unions/test_discriminated_union.py: added test_discriminated_union_none_discriminator, which builds a discriminated union with a bare-None member, asserts the model builds and the correct member is selected for {'field': None} and {'field': 'a'}, plus a Literal[None] parity block.

Test evidence:

  • Confirmed the bug reproduces before the fix (PydanticUserError ... discriminator-needs-literal).
  • The new test failed before the production change, passes after.
  • Gate: ./bt-test tests/types/unions/test_discriminated_union.py → 80 passed, 4 xfailed (the 4 xfails are pre-existing). No previously-passing test regressed.
  • Reviewer confirmed the fix is correct and complete, scope-limited, no scratch files, no weakened tests.

Requirements list:

  1. Treat bare None as equivalent to Literal[None] for discriminator fields — implemented ('none' schema branch) with a passing regression test that exercises the exact reported scenario.
  2. Alternative from the report: replacing : None with : Literal[None] avoids the error — verified still works and asserted as a parity check in the same test.
