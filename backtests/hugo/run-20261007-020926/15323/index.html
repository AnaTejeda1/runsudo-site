tpl/collections: union silently returns an empty list when the two slice types differ

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

The issue is that `union` silently returns an empty list when the two slice types differ. It asks for either a real union or an error, never a silent empty result.

**Patch A only partly fixes this.** It bypasses the early return when both element types are numeric, so `union (slice 1 2) (slice 2.0 3.0)` now yields `[1 2 3]`. Every other mismatched case still hits the unchanged `return ins.r.Interface(), nil` with no error:
- `union (slice 1) (slice "a")` still returns `[]`.
- `union (slice (slice 1)) (slice 2)` still returns `[]` instead of the uncomparable-types error the issue calls out.

A's own test suite keeps the existing `[]string ∪ []int → []string{}` expectations, preserving the silent behavior the issue reports as a bug. Its added guard (`AssignableTo(l1v.Type().Elem())`) patches a prototype mismatch that A's partial approach itself exposes. It also makes `[]int{} ∪ []float64{1.0}` return `[]int{}`, which is arguably wrong: the union should contain 1.

**Patch B fixes the root cause.** It removes the early return and converts each l2 element to l1's element type, returning an error when that is impossible:
- Numeric mixes unify, matching how `intersect` already behaves.
- Incompatible types (int vs string, a lossy 1.5 → int) raise `union: failed to convert value`.
- The uncomparable check is now reached and raises its error.
- Interface-element slices keep the previous normalize-or-keep behavior.
- An empty l1 with numeric l2 correctly yields `[1 2]`.

B updates the outdated unit expectations to errors and adds wide coverage: int/float in both directions, int64, empty l1, `template.HTML` from string, pages ptr/vals, nested slices, and `[]any` cases. It also adds an integration test reproducing the issue's template exactly, plus error-case assertions. These tests would fail before the change.

B is a larger rewrite, which carries some risk around how `convertValue` handles struct and pointer elements. The retained `[]T ∪ []T` tests and the explicit pages cases mitigate that, and the doc comment was updated accurately.

Overall, B resolves every scenario in the issue while A leaves most of them silently broken.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Does this issue reproduce with the latest release?

I built master at ae07063 and reproduced it there. I did not run a tagged release binary, so I have not confirmed it against one directly, though Union is unchanged in tpl/collections/collections.go.

What did you expect to see?

union either returning the union of its two arguments, or returning an error. It already errors for the other argument shapes it cannot handle, for example union does not support slices or arrays of uncomparable types and can't iterate over ....

What did you see instead?

union returns an empty slice, with no error, whenever the two arguments have different slice types and neither has an interface element type.

layouts/index.html:

{{ printf "%T" (slice 1) }}
{{ printf "%T" (slice 1.0) }}
union int,int    -> {{ union (slice 1) (slice 2) }}
union int,float  -> {{ union (slice 1) (slice 1.0) }}
union int,string -> {{ union (slice 1) (slice "a") }}
union lists      -> {{ union (slice 1 2) (slice 2.0 3.0) }}
intersect lists  -> {{ intersect (slice 1 2) (slice 2.0 3.0) }}

Output:

[]int
[]float64
union int,int    -> [1 2]
union int,float  -> []
union int,string -> []
union lists      -> []
intersect lists  -> [2]

intersect handles the same two mixed-type lists and returns [2], so the sibling functions disagree about whether these arguments are usable at all.

The cause is this early return in Union:

if l1v.Type() != l2v.Type() &&
	l1v.Type().Elem().Kind() != reflect.Interface &&
	l2v.Type().Elem().Kind() != reflect.Interface {
	return ins.r.Interface(), nil
}

ins.r is the empty slice made just above, so a caller gets an empty list rather than an error. It is reachable from ordinary templates because slice 1 is []int and slice 1.0 is []float64, and it also runs before the uncomparable-types check, so union (slice (slice 1)) (slice 2) returns [] instead of the error that check would raise.

Adding one element of another type to the first argument avoids it, since the slice then becomes []interface {}: union (slice 1 "x") (slice 1.0) returns [1 x].

Stack traceback or browser console output

None, no error is raised. That is the problem.

This is a different mechanism from #3411, which was closed in 2017 and is now locked with a note asking that related bugs be opened as new issues.

Happy to send a PR. Returning an error here would be a small change; making union accept mixed types the way intersect does is bigger, so I would rather you pick the direction first.
