Concurrent TypeAdapter construction raises RuntimeError on free-threaded Python

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the root cause the same way: `_decorator_infos_for_class` iterates `vars(typ).copy().items()`. `mappingproxy.copy()` delegates to an atomic `dict.copy()`, so a concurrent insertion of `__annotations_cache__` can no longer invalidate the iterator.

Both also harden the second iteration site, the lazy namespace built from `vars(typ)`. Patch A copies at iteration time in `LazyLocalNamespace.data`. Patch B snapshots at push time in `NsResolver`. Both are reasonable, and B additionally covers `collect_known_metadata`.

The key difference is scope and risk. Patch A also rewrites the `model_rebuild` logic, replacing conditional `delattr` of the core schema, validator and serializer with `set_model_mocks(cls)` when `already_complete`. That is a behavioral change to `BaseModel.model_rebuild`, unrelated to the reported TypedDict/TypeAdapter race. It carries regression risk and obscures the actual fix.

On tests, Patch B adds a deterministic regression test (`test_class_namespace_mutated_during_decorator_collection`). It uses an object whose `__class__` property mutates the class dict during the `isinstance` check. This fails before the fix and passes after it on any Python build, so the regression is checked in normal CI. B also adds a concurrent stress test covering TypedDict, BaseModel and `PydanticMetadata`.

Patch A's tests are all skipped unless running on a free-threaded build. They are probabilistic, so they give no coverage on standard CI. Part of them (`model_rebuild` with `force` plus instantiation) test the unrelated change.

Patch B delivers an equally correct fix with better, deterministic tests and no unrelated behavioral changes.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Description

Constructing separate TypeAdapter instances concurrently for the same new TypedDict can raise RuntimeError: dictionary changed size during iteration on free-threaded Python.

A full run produced 91 failures in 800 attempts with the GIL disabled and none with PYTHON_GIL=1. It also reproduces on Pydantic main at 1c8a330acc3077e77da64e3672c7c875fb4c6eaa.

Lazy annotation evaluation adds __annotations_cache__ while another thread iterates vars(typ).items() in _decorator_infos_for_class.

Example Code

from __future__ import annotations

import threading
from concurrent.futures import ThreadPoolExecutor

from pydantic import TypeAdapter
from typing_extensions import TypedDict


def run_round() -> None:
    class Record(TypedDict):
        value: int

    for index in range(1000):
        setattr(Record, f'metadata_{index}', index)

    barrier = threading.Barrier(8)

    def build(_: int) -> None:
        barrier.wait()
        TypeAdapter(Record).validate_python({'value': '42'})

    with ThreadPoolExecutor(max_workers=8) as executor:
        list(executor.map(build, range(8)))


for _ in range(100):
    run_round()

The synthetic attributes only widen the iteration window. They are not modified after the threads start.
