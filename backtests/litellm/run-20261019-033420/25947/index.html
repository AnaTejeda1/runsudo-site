[Bug]: Vector stores from config.yaml are not added

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches identify the same root cause: list_vector_stores and pop_vector_stores_to_run_with_db_fallback treat the database as the source of truth and evict any in-memory store without a DB row, which silently drops every store loaded from config.yaml. Both mark config-loaded stores and skip eviction for them in both code paths, and the independent tests pass identically on A and B. Patch B does this with a small, focused change: a config_vector_store_ids set on the registry, an is_config_vector_store() check, an upsert on reload so re-loading config does not duplicate entries, and marker cleanup on delete. Its five unit tests target the exact failure (listing twice, eviction of genuinely deleted DB stores still works, pre-call lookup, reload, delete) and would fail on base. Patch A reaches the same fix but wraps it in a much larger change: a new is_config field on the public TypedDict, Pydantic model and OpenAPI snapshot; new 400 errors on /vector_store/new, /update and /delete for config stores (an unrequested API behavior change that alters what admins could previously do); registry changes that refuse DB-row sync for config IDs; dashboard UI columns, badges and read-only alerts; and unrelated churn in .circleci/run_integration.sh and the integration-test harness (INTEGRATION_PROXY_ROOT, worker count, upstream search route) to support heavy integration/chaos tests. None of that is needed to resolve the issue, and it widens the blast radius and obscures the actual fix. A does handle one edge B does not (a DB row with the same id overwriting the config entry), but B handles config reload without duplicates, which A does not. Weighing correctness as equal, tests as both adequate, and scope/risk favoring the minimal patch, B is the better fix.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Each saw the issue and the two patches, labelled A and B in random order (two of them saw ours as A), with issue links and version numbers removed. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours. The reasoning above is one judge's, shown verbatim.
