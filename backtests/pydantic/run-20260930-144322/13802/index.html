Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches make the same three doc fixes. `complex_type` now uses a string input. The `string_sub_type` section is deleted. `invalid-for-json-schema` now uses a `Callable` field, which really has no JSON schema, so the `except` branch runs again. On those three fixes the patches are equivalent.

They differ elsewhere.

Patch A also deletes the `StringSubType` variant from pydantic-core's Rust enum, the Python `ErrorType` Literal, and the core error test. That removes part of the public error-type surface, which the issue explicitly left as the maintainers' decision. Patch A also edits `docs/concepts/experimental.md`, changing the partial-JSON example input from an unterminated string `"12` to a terminated `"12"`. That change is unrelated to the issue and may alter what the example is meant to show about partial validation. Both are risky scope changes.

Patch A also adds no test for the blind spot the issue emphasises, so a future regression like the `complex` one would still pass silently.

Patch B keeps the core error type. It updates `test_validation_error_codes` to exclude `string_sub_type`, with a comment explaining it is never raised; this is needed because the doc section is gone. It also adds `test_docs_error_examples_raise`. That test parses each error-page example and injects an `else: raise AssertionError` into every module-level `try`/`except` that has no `else`. It then executes the example, so any example that stops raising fails loudly. This test would have caught all three reported cases (it fails before the doc fixes and passes after), and it directly addresses the root cause the issue describes. It also respects the existing skip and requires settings.

Patch B therefore fixes the issue more completely, with real regression tests and less risky churn.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Description

Three examples on the error-reference pages no longer raise the error they document, and the documentation test suite cannot detect it.

Every example on those pages has the same shape: do something that should fail, catch it, then print or assert the error code. The only assertion lives inside the except branch. When the operation stops failing, that branch never runs, so nothing is printed and no assert is evaluated. run_print_check compares printed output against the #> comments, and an example whose print never ran produces no output to disagree with, so the example exits 0 and CI stays green while the page documents behaviour that no longer exists.

I checked this exhaustively rather than by sampling. I injected a sentinel as the first statement of every except block on both error pages and ran each example. Of the 152 examples containing a try/except at v2.13.5, all 152 run, and exactly 3 never enter their except branch. On main the count is 3 of 157. None of the three is marked test="skip", so all three are executed by CI today.

1. complex_type, docs/errors/validation_errors.md

Model(num=False) now validates successfully to 0j, so the #> 'complex_type' line never prints. This changed in 2.13.0b1 with #12498, which made complex validation call the complex() constructor unconditionally in Python mode, and complex(False) is 0j.

2. string_sub_type, docs/errors/validation_errors.md

The section says a strict str field rejects an instance of a str subclass. It does not: the example returns a plain str with the value 'foo', and #> 'string_sub_type' never prints. pydantic_core 2.49.0 still declares the error ("Input should be a string, not an instance of a subclass of str"), but I could not find any str schema that raises it. Building core_schema.str_schema() directly with strict=True, without strict, and with strict=True plus a pattern all accept a str subclass and return a plain str.

This looks intentional rather than accidental. #6261 reported exactly this behaviour as a bug in June 2023, was labelled bug V2, and was closed with the conversation moved to pydantic-core#786. So the check appears to have been removed on purpose and this documentation section was left behind describing it.

3. invalid-for-json-schema, docs/errors/usage_errors.md

ImportString has had a JSON schema since 2.8.0 via #9344, so Model.model_json_schema() succeeds and returns a plain string schema. The assert exc_info.code == 'invalid-for-json-schema' inside the except block has not executed since that release.

Output of the example code below

Identical on 2.13.5 and on main at 2.14.0b2:

1. no exception; num = 0j
2. no exception; accepted 'foo'
3. no exception; {'properties': {'a': {'title': 'A', 'type': 'string'}}, 'required': ['a'], 'title': 'ImportStringModel', 'type': 'object'}

Suggested fixes

  1. complex_type is a one-word fix. Model(num='not a complex number') still raises complex_type, and so do [], {} and a bare object(). Replacing False with any of those restores the example.
  2. string_sub_type needs a decision rather than a fix, which is the main reason I am opening an issue instead of sending a patch. Given the trail through #6261, the section probably wants deleting rather than repairing, and possibly the error variant too, but that is your call.
  3. invalid-for-json-schema needs a type that genuinely has no JSON schema, in place of ImportString.

Separately, the blind spot itself is fixable. If an example on these pages had to demonstrate that the error occurred, for instance by printing inside the except and also failing loudly when nothing was raised, then a future change like #12498 would turn the docs red instead of silently making a section untrue. I am happy to send a PR for any or all of this, including that check as a test, if you tell me which direction you prefer.

What the agent reported

All three examples now raise the error they document, and a new docs test fails if an example on either error page stops raising. The docs tests for the error pages pass: 321 passed, 29 skipped, 0 failed. Nothing is committed; the changes are in docs/errors/validation_errors.md, docs/errors/usage_errors.md and tests/test_docs.py.

What was wrong: Model(num=False) now validates to 0j. A strict str field accepts str subclasses, so nothing raises string_sub_type any more. ImportString has had a JSON schema since 2.8. In each case the only check sat inside the except block, so when nothing was raised the example printed nothing and still passed.

Changes:

  1. complex_type: the example now uses Model(num='not a complex number'). I checked that it raises complex_type.
  2. string_sub_type: I deleted the section, following #6261 and pydantic-core#786. The existing test_validation_error_codes expects every ErrorType to have a section in the docs. So I added string_sub_type to its exclusion list, next to the existing timezone_offset exclusion, with a comment explaining why.
  3. This is a change to an existing test, and it makes that check skip one error code.
  4. The only alternative was to keep an example that wrongly claims to print 'string_sub_type'.
  5. I didn't remove the error variant from pydantic-core: that needs a Rust change and a rebuild, and I've left it for the maintainers to decide.
  6. invalid-for-json-schema: the example now uses a: Callable[[], int] (from collections.abc). I checked that it raises the error with this code.
  7. The detection gap: I added test_docs_error_examples_raise to tests/test_docs.py. For every example on the two error pages, it adds else: raise AssertionError(...) to each top-level try/except and runs the example. It follows the same test="skip" and requires= settings as the existing docs test.

Test results:

  • The new test on its own: 153 passed, 19 skipped.
  • With the docs temporarily put back to num=False and ImportString, it failed on exactly those two examples ("no exception raised by the try block"), so it catches the reported problem.
  • ./bt-test tests/test_docs.py -k "error_codes or errors": 321 passed, 29 skipped, 0 failed.
  • An earlier run caught a lint error (UP035) on from typing import Callable; switching to collections.abc fixed it.

Limits of the new test: it only checks try blocks at the top level of an example, not ones inside functions. It only proves that the caught exception type was raised somewhere in the try, not which statement raised it.
