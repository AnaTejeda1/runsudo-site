[Bug]: litellm_content_filter evaluations missing from request logs and Guardrails Monitor

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Patch A diagnoses the bug as a metadata-bucket merge problem (content filters recording into litellm_metadata while the logging payload takes metadata's list whole) and adds a merge step in get_standard_logging_metadata. The independent tests contradict that diagnosis: every one of the five issue-derived tests fails on base+A with exactly the same assertion as on base (content filters still have no evaluation record, no Monitor index rows, zero Monitor counts). A's first two unit tests only exercise a hand-built split-bucket request and so pass by construction; its end-to-end test runs the real six-guardrail flow, which the independent evidence shows still drops the content filters. A therefore does not fix the reported behavior.

Patch B finds the actual root cause: when message scoping (e.g. skip_system_message) leaves a content filter nothing to scan, the OpenAI chat translation handler never records any guardrail_information, so the guardrail appears in applied_guardrails but not in the persisted evaluation list. B records a `not_run` entry in that path, plumbs the new status through usage tracking (index rows so per-request drill-down finds the request, dedup by name/id), compliance checks, and the UI (badges, counts, timeline). Four of the five independent tests pass on B, including the end-to-end request-log tests for streaming and non-streaming and the Monitor per-request index test. The one remaining failure is the daily request-count test: B deliberately excludes not_run from requests_evaluated, so the daily rollup still shows zero for guardrails that never scanned. That is a defensible design choice (counting a skipped scan as a pass would inflate pass rates) but it leaves part of the issue's Monitor expectation unmet, and the UI/compliance changes are a sizable surface for a bug fix. B's tests cover the new handler behavior with genuine regressions (system-only, null content, image-only, self-recording guardrails) plus tracking, endpoint, compliance and UI cases.

On correctness B clearly wins: it addresses the real cause and makes the issue's primary scenario observable in request logs and Monitor drill-down, while A changes nothing in practice. B's broader scope is coherent with introducing a new status and does not obscure the fix.

What happened?

Guardrails Monitor does not show evaluations for five configured global litellm_content_filter guardrails, even though the associated request metadata lists all six guardrails in applied_guardrails.

For recent successful LLM requests:

  • applied_guardrails contains all six configured global guardrails.
  • guardrail_information contains only one entry: Block Code Execution.
  • The five litellm_content_filter guardrails have no individual guardrail_information entries.

In Guardrails Monitor for the same one-day date range:

  • Total Evaluations: 33
  • Active Guardrails: 6
  • Block Code Execution: 33 requests
  • Each of the following guardrails: 0 requests
  • Prompt Injection: System Prompt
  • Prompt Injection: Malicious Code
  • Prompt Injection: SQL
  • Prompt Injection: Data Exfiltration
  • Prompt Injection: Jailbreak

User Flow

Expected behavior

Every guardrail listed in applied_guardrails should have a corresponding persisted evaluation record when it completes successfully, so Guardrails Monitor and Export Data accurately show request counts and outcomes for each configured guardrail.

Actual behavior

Only Block Code Execution has persisted detail and Monitor request counts. The five litellm_content_filter guardrails are listed in applied_guardrails but have no corresponding individual evaluation records in guardrail_information.

  1. Configure these global guardrails through the Admin UI/API, each with mode: pre_call and default_on: true:
  2. block_code_execution
  3. Five litellm_content_filter guardrails
  4. Send successful chat-completion requests through the proxy.

  7. Open Guardrails Monitor for the same date range.
  8. Observe that only Block Code Execution has request counts; the five content filters show zero requests.
