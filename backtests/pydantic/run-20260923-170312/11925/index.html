In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the reported symptom, but they differ sharply on the top-weighted criterion (root-cause correctness). Patch A is a targeted workaround: it wraps the existing positional `arguments`/`call` schema in a Python before-validator that detects a NamedTuple *instance* and remaps it to a dict keyed by field name, thereby routing it through the keyword path so error locs use names. This is clever (it even shares the metadata dict so `schema['arguments_schema']['metadata']` mutation in `__get_pydantic_core_schema__` still works, and it leaves plain-tuple positional behavior untouched so existing tests like `test_namedtuple_right_length` pass), and it is admirably small. But it treats the disease at the symptom level: namedtuples still abuse the function-arguments machinery, so the whole class of confusing behaviors that stems from that (positional-argument errors, the `arguments_type` message the docs call out, inconsistent locs between plain tuples and instances) remains, and it adds per-validation Python-call overhead. Patch B removes the root cause by introducing a first-class `named-tuple` core schema (Rust validator + serializer, error type `named_tuple_type`, Python schema generation via `_generate_namedtuple_field_schema`, schema-gather traversal, and JSON-schema generation). Positional inputs report index locs, dict/mapping inputs and instances report field-name locs, and it correctly handles aliases, missing/extra fields, defaults, smart-union class preservation, and serialization. Its tests are far more thorough and include the exact issue scenario (`test_namedtuple_from_attributes_error_locs`) plus regressions across serialization, JSON schema, aliases, and unions — all of which fail-before/pass-after. Patch B loses on the scope criterion (it is a large change touching Rust, docs, and five test files, and carries build risk if pydantic-core is not rebuilt), but the diff is internally complete and coherent, the repo clearly vendors buildable pydantic-core source and its own tests, and the large surface is the genuine fix rather than incidental churn. Given correctness-at-root-cause is the primary criterion and B's superior, better-covered fix, B is the stronger patch despite its size.

The fix is complete, reviewed, and verified. Here is my final report.

What was wrong

A ValidationError raised for a field inside a NamedTuple used the tuple position index (e.g. tuple_attr.1) instead of the field name (e.g. tuple_attr.sequence_number) when the NamedTuple was validated from an object attribute (from_attributes=True). Validating from a dict already produced the name.

Root cause: Pydantic generates a call(arguments(...)) core schema for a NamedTuple. The arguments validator (in the prebuilt pydantic-core) labels errors by field name only when it consumes the input via the keyword path (dict input); a tuple/NamedTuple-instance input is consumed positionally, so errors are labelled by index. from_attributes=True reads the attribute — a NamedTuple instance — and feeds it positionally.

Environment constraint that shaped the fix

The proper fix is a one-line, opt-in flag in the Rust arguments validator. I implemented it, but the test container runs uv run --no-sync pytest against a prebuilt pydantic-core and never recompiles Rust (confirmed: the new schema key was silently ignored and runs took ~8s). So I reverted all Rust/core_schema.py changes and implemented an equivalent pure-Python fix that works against the frozen binary.

What I changed

pydantic/_internal/_generate_schema.py — _namedtuple_schema: wrap the NamedTuple's arguments schema in a no_info_before_validator_function that, when the input is an instance of that NamedTuple class, converts it to dict(zip(field_names, value)). This routes it through the arguments validator's keyword path, so errors use the field name. The wrapper shares the same metadata dict as the inner arguments schema, keeping schema['arguments_schema']['metadata'] reachable for __get_pydantic_core_schema__ overrides.

The trigger is deliberately narrow (isinstance(input_value, namedtuple_cls)), so plain tuples/lists and dicts are untouched — no existing behavior or test changes.
