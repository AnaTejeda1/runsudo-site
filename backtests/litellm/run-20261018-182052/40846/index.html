[Bug]: Completed /v1/responses requests retain max_parallel_requests slots during deferred logging

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the root cause the same way: they release the stashed max_parallel_requests acquisition in async_post_call_success_hook, which the proxy awaits before returning a non-streaming response, and both guard against the deferred async_log_success_event releasing the same slot a second time. The independent tests pass on both. The difference is in how the double-release is prevented and in scope. Patch A detaches the acquisition from the stash before the first await, so under asyncio's single-threaded model the post-call hook and the deferred callback cannot both see a live slot; it needs no new state and touches only the two relevant sites. Patch B introduces an asyncio.Lock field on the per-request RequestRateLimiterStash dataclass and reroutes six release sites (pre-call rejections, failure event, disconnect, post-call failure) through the new locked helper. That refactor is consistent but goes well beyond the issue's ask and adds a synchronization primitive to a dataclass that is created per request, which is extra surface for little gain given the lockless pattern suffices. On tests, Patch A's first test runs the real ProxyLogging callback ordering with a slow logger ahead of the limiter, verifies the slot is free while logging is blocked, admits a follow-up request in a separate request context, and then verifies the late success event does not free the follow-up's slot; its second test forces a genuine interleave of the two releasers. Patch B's tests cover the same ground reasonably (including a Redis-failure concurrent release) but with more reliance on internal attributes like parallel_release_script. Patch A also documents why the post-call hook now owns the release. Patch B's one advantage is that keeping parallel_slot set until the release succeeds preserves retry-on-failure, but the release path already has an in-memory fallback, so this is marginal. A's narrower, lockless fix with strong tests is the better change.

What happened?

A completed non-streaming /v1/responses request can continue occupying its max_parallel_requests slot until asynchronous success logging finishes. With a virtual key limited to one parallel request, the first request returns 200, but an identical request sent immediately afterward can incorrectly receive 429. The next request succeeds once success logging completes.

The slot should be released before the completed response is returned to the caller. Slow logging integrations should not extend the request's concurrency lifetime.

This is related to #27955, but differs from the persistent slot leaks reported there: in this case the slot is eventually released, just too late. A proposed fix is in #40843.

User Flow

Before a fix: a developer using the Responses API receives a false rate-limit response after the previous request has already completed.

  1. The proxy administrator creates a virtual key with max_parallel_requests: 1.
  2. The developer sends a non-streaming POST http://localhost:4000/v1/responses request.
  3. The completed request returns 200.
  4. The developer immediately sends the same request again and receives 429.
  5. After success logging finishes, the developer retries and receives 200.

After a fix: the completed request releases its slot before returning, so the next request is admitted immediately.

  1. The proxy administrator creates a virtual key with max_parallel_requests: 1.
  2. The developer sends the same non-streaming POST http://localhost:4000/v1/responses request.
  3. The completed request returns 200.
  4. The developer immediately sends the same request again and also receives 200.
  5. Later requests continue receiving 200 after success logging finishes.

Proof the bug occurs

The issue was reproduced against a real OpenAI-compatible Responses deployment with a local LiteLLM proxy, a virtual key limited to one parallel request, and a custom success logger that takes three seconds to complete. Secrets and provider-specific endpoint values are represented by environment variables below.
