Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches make the same core change: add `tool.action.metadata?.toolName` to the fallback chain in `resolveToolName`, which fixes the reported root cause (the canonical name is already stored by `createEngineRequests` but never read). The differences are in ordering, adjacent coverage, and tests.

Ordering: Patch A inserts `metadata.toolName` after `hitl.toolName` and before `input.tool`, preserving the existing HITL precedence the issue explicitly lists as a control that must keep passing. Patch B puts `metadata.toolName` ahead of `hitl.toolName`, changing which identity wins for gated actions. Nothing in the diffs shows what `metadata.toolName` holds on a HITL-routed action, so B's reordering is an unverified behavioral change with no justification given, whereas A's placement is the conservative one that matches the issue's stated expectation ('node display name should only be a final fallback').

Adjacent coverage: Patch A also stamps `toolName: hitl.toolName` onto the replayed gated-tool action in `processHitlResponses`, so the same class of name drift cannot occur on the post-approval replay path, and adds a test for it. This is small, low-risk, and directly in the spirit of the issue.

Tests: Patch A's tests mirror the issue's reproduction exactly: they build real `DynamicStructuredTool`s with a differing `sourceNodeName`, run `createEngineRequests` -> `buildSteps` -> `createEngineRequests` and assert the round-trip yields an executable action rather than an empty list. They also cover the subtle case where a standalone tool has an argument literally named `tool`, which A's comment explains is why `metadata.toolName` must precede `input.tool`. Patch B's single unit test hand-crafts an action with `metadata.toolName` and asserts the reconstructed name; it would fail before and pass after, but it does not demonstrate the silent-drop round trip the issue centers on.

Craft: Patch A keeps the existing comment explaining the toolkit/MCP infinite-loop hazard and adds rationale for the new precedence. Patch B deletes that explanatory comment and replaces it with a one-liner, losing context for future maintainers.

The independent test runs crashed on all three trees, so they provide no signal. On the diffs alone, A is the more careful fix with stronger, issue-faithful regression coverage; B is minimally correct for the standalone case but takes an unjustified ordering risk and has thinner tests.

Bug Description

AI Agent V3 can reconstruct tool-call history with a node-derived tool name instead of the canonical LangChain tool name that was originally selected by the model.

On current master (f7f92c7107e72f8151392b7fdf22bdf660df6892), createEngineRequests() already stores the canonical tool name in action.metadata.toolName, but buildSteps.resolveToolName() does not read that field. For standalone tools it can fall back to nodeNameToToolName(action.nodeName) instead.

If the node display name and the registered tool name differ — for example after a node rename/paste suffix or when a Tool Workflow uses a custom tool name — the reconstructed history can therefore expose a different tool name to the model. If the model reuses that reconstructed name on the next turn, createEngineRequests() cannot find it in the canonical tool list and silently filters the action out. The agent can then continue with no tool observation and eventually hit max iterations.

I reproduced this deterministically on current master without model/network nondeterminism.

To Reproduce

A focused source-level reproduction is enough:

  1. Register a standalone tool whose canonical LangChain name is Ingredient_Glossary_Lookup.
  2. Give its source node the display name Ingredient Glossary Lookup1.
  3. Let createEngineRequests() create an engine action. The action correctly contains: metadata.toolName = "Ingredient_Glossary_Lookup".
  4. Pass that action through buildSteps().
  5. Current behavior reconstructs steps[].action.tool as Ingredient_Glossary_Lookup1 instead of the canonical name.
  6. Feed that reconstructed name into createEngineRequests() with only Ingredient_Glossary_Lookup registered.
  7. The result is an empty action list because the tool lookup fails and the item is filtered out.

Fail-before proof:

  • canonical-name reconstruction test: fails
  • round-trip executable-action test: fails
  • matching-name control: passes
  • HITL precedence control: passes
  • toolkit input.tool precedence control: passes
  • silent-drop behavior control: passes

A narrow local fix — reading action.metadata.toolName before falling back to nodeNameToToolName(action.nodeName) — makes all 6 proof cases pass while preserving HITL/toolkit precedence. The existing neighboring buildSteps + createEngineRequests suites also pass: 74/74, for 80/80 total.

Expected behavior

When reconstructing Agent V3 tool-call history, n8n should preserve the canonical LangChain tool name that createEngineRequests() already stores in action.metadata.toolName.

The node display name should only be a final fallback when no canonical tool identity is available.
