BaseSettings.update() does not accept iterable key-value pairs

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches make the identical functional change: extend the _SettingsInput alias with Iterable[tuple[str, Any]] and branch on hasattr(values, 'items') so non-mapping iterables are consumed directly as pairs. Both preserve the BaseSettings per-key-priority path and the JSON-string path, and the independent tests confirm both resolve every scenario (lists, tuples of two-item lists, generators, repeated keys, priority handling, Settings subclass). So correctness is a wash and the difference lies in tests and craft.

Tests: Patch A is noticeably stronger. It un-xfails the existing test and makes it assert both an overwrite and a new key with default priority, adds a priority test using a plain iterator (not just a list) that checks a higher-priority existing value is not overridden, and adds tests for setdict() and the BaseSettings/Settings constructors taking iterables, which are real entry points that delegate to update() and are now typed as accepting iterables. Patch B un-xfails the single test and adds a value + priority assertion, which is adequate but minimal and only exercises a list.

Craft: Patch B's single-loop structure with an `items` variable is slightly tidier than A's duplicated loop body, and B correctly narrows the stale 'doesn't support all inputs' comment to the remaining kwargs gap, whereas A leaves that comment unchanged (still technically true, just less precise). On the other hand, A's docstring explicitly explains the new iterable form and references dict.update, while B only tweaks the :type: line. These craft points roughly cancel.

Scope is equivalent for both. Given tests rank above craft and A's tests cover more of the surface the type change actually opens up, A is the better patch by a modest margin.

The issue

View on GitHub

BaseSettings inherits from MutableMapping, but BaseSettings.update() does not accept iterable key-value pairs like dict.update() does.

Example:

from scrapy.settings import BaseSettings

settings = BaseSettings({"KEY": 0})
settings.update([("KEY", 1)])

This raises:

AttributeError: 'list' object has no attribute 'items'

There is already an xfailed test for this in tests/test_settings/__init__.py::TestBaseSettings::test_update_iterable.
