Suspense timeout + Transition out-in: parent update during the fallback swap permanently drops the resolved branch

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

The two source fixes are essentially the same. Both skip the `patch(activeBranch, newFallback)` call in both `isInFallback` paths of `patchSuspense` while `isFallbackMountPending` is set. Both also mount the latest `suspense.vnode.ssFallback` when the deferred `mountFallback` finally runs. That addresses the root cause traced in the issue: the active branch was being hijacked into the fallback, so `resolve()` attached the content move to an `afterLeave` that never fires.

The small source differences:
- A uses `suspense.vnode.ssFallback || fallbackVNode`, which is a slightly safer fallback.
- B uses a non-null assertion.
- B's comments explain the reasoning more thoroughly. This is a minor craft plus.

The deciding difference is the tests.

Patch A adds three deterministic unit tests in `runtime-core`. They use `BaseTransition` with manually held `onLeave` callbacks, so event ordering is exact and does not depend on timing.
- Test 1 reproduces the reported scenario: a parent re-render during the leave, then resolve.
- Test 2 checks that the latest fallback is mounted.
- Test 3 switches to a different async component while the leave is pending. This exercises the second guarded path, the `else if (!suspense.isFallbackMountPending)` branch where the new branch is not the same vnode type as the pending branch.

Patch B adds two e2e tests. They rely on wall-clock timeouts, `:duration`, and buffers, so they are more timing-sensitive and heavier to run. Both only change props on the same keyed component, so they exercise only the first guarded path. The second patched branch is left untested.

Correctness is equal and B's comments are somewhat better, but A's tests are more deterministic and cover both modified code paths. A is the stronger patch.

Steps to reproduce

Open the playground with Vue 3.5.41 selected (the banner in the preview shows the actually running version). The repro is fully event-ordered (JS transition hooks hold the leave open), so it fails on the first run, every run:

  1. A keyed component inside <Suspense :timeout="100"> inside <Transition mode="out-in"> navigates to a cold async component (defineAsyncComponent, chunk not loaded yet).
  2. timeout elapses → Suspense starts the fallback swap; the old content's leave transition begins.
  3. While the leave is in progress, the parent re-renders (in a real app: a ResizeObserver callback, a store update — anything).
  4. The async component resolves; the leave finishes.

What is expected?

The resolved page is mounted (with the fallback shown in between).

What is actually happening?

@resolve fires and the module is loaded, but the page is never inserted — the fallback stays on screen forever. No error, no warning. A later unrelated parent re-render "un-sticks" it, which is why this is so hard to catch in the wild.

Removing any one of the three ingredients — the timeout, mode="out-in", or the mid-swap parent re-render — makes it pass (all three controls verified).

The bug is deterministic: 3.5.30 passes, 3.5.31+ fails (bisected).

Root cause (bisected + traced)

Regression introduced by 908c6ad05 (#9392, first released in 3.5.31), which added isFallbackMountPending:

  • fallback() sets isFallbackMountPending = true and defers mountFallback to the leaving branch's afterLeave.
  • A parent re-render hits patchSuspense's isInFallback path, which patches activeBranch → newFallback and calls setActiveBranch(suspense, newFallback) — mounting the fallback early without clearing isFallbackMountPending.
  • resolve() then skips unmount(activeBranch) because the flag is still true, yet hooks the content move onto activeBranch.transition.afterLeave — where activeBranch is now the fallback, which is never unmounted. The afterLeave never fires; the resolved branch is lost.

Before #9392, resolve() unconditionally unmounted the active branch, so the fallback left and its afterLeave inserted the content.

A guard in patchSuspense fixes it — while isFallbackMountPending is true, activeBranch is still the leaving content, so the patch(activeBranch, newFallback) + setActiveBranch(suspense, newFallback) calls in the isInFallback paths must be skipped. Happy to submit a PR with the fix and an e2e regression test (prepared and passing locally, including the #9392 test for #7966).

Real-world impact: in our production SPA (layout = RouterView → Transition out-in → Suspense timeout, per the documented pattern) roughly 1 in 10 cold first navigations ended on an infinite spinner — console clean, all network requests succeed.

What the agent reported

I fixed the bug: when the parent re-renders during the fallback swap, the resolved page now mounts instead of the fallback staying up forever. The runtime-core, server-renderer and vue unit suites pass (77 files, 1540 tests), including three new regression tests that each fail without the fix.

What was wrong. It is the cause described in the report:

  • With out-in, fallback() sets isFallbackMountPending and waits for the old content to finish leaving before it mounts the fallback.
  • A parent re-render in that window hits patchSuspense's isInFallback paths. These patch the old content (still leaving) into the new fallback and make the fallback the active branch.
  • resolve() then skips the unmount because the flag is still set, and attaches the content move to the fallback's afterLeave. The fallback is never unmounted, so that hook never fires and the resolved content is lost.

What I changed (all in packages/runtime-core/src/components/Suspense.ts):

  1. In patchSuspense, both isInFallback paths now skip the fallback patch and the active-branch switch while isFallbackMountPending is set. These are the same-type path (~line 272) and the toggled-branch path (~line 322). At that point the active branch is still the leaving content.
  2. mountFallback now mounts suspense.vnode.ssFallback, the latest fallback, instead of the one captured when fallback() ran. Without this, a re-render during the leave would mount an outdated fallback (e.g. "fallback 0" instead of "fallback 1"). This also applies when timeout is used without a Transition: the latest fallback is mounted, not the one from when the timer started. That's harmless, but it is a small behaviour change beyond the report.

Tests. I added three unit tests to packages/runtime-core/__tests__/components/Suspense.spec.ts. Each uses BaseTransition in out-in mode, a JS onLeave hook that holds the leave open, and <Suspense timeout: 0>:

  • Content resolves after a re-render during the leave: the screen ends on <div>two</div>. Before the fix it stayed on <div>fallback 1</div>. Removing the re-render makes it pass on the old code, so the re-render is what triggers the bug.
  • Leave finishes before the content resolves: the latest fallback, <div>fallback 1</div>, is shown, then two. Removing change 2 makes it fail with fallback 0.
  • Switching to another async component during the leave: the screen ends on <div>three</div>. Turning the line-322 guard back into a plain else makes it fail.

The full Suspense.spec.ts passes (62 tests).
