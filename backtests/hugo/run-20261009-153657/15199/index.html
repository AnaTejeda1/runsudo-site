related: Add option to tokenize headings

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Patch A is the more correct fix.

**Patch A**
- It adds `Tokenize` as a purely additive feature for `fragments` indices.
- Heading identifiers are still indexed as `FragmentKeyword`, so exact front-matter references keep working. Its test checks this with p4 referencing p1's heading ID.
- Heading word tokens go in under a distinct `HeadingTokenKeyword` type.
- Titles have HTML stripped (`tpl.StripHTML`), are unescaped, honor `ToLower`, and are split on non-letter/digit runes.
- `applyFilter` handles the new keyword type and re-tokenizes heading titles with the matching `ToLower` setting. It even covers multiple indices whose `ToLower` settings differ.
- It updates the docs exactly as the issue proposes.
- Tests cover unit tokenization, config decoding, the enabled/disabled integration paths, multiple indices with mixed `ToLower`, and `cardinalityThreshold` pruning.

**Patch B has real correctness problems**
1. When `Tokenize` is on, heading identifiers are replaced by tokens and never indexed as `FragmentKeyword`. Front-matter fragment references to heading IDs therefore stop matching.
2. Tokens are created through `stringToKeyword`, which yields `StringKeyword`. The `applyFilter` branch only checks for `kw.(FragmentKeyword)`, so `ff.words` is never filled. Heading filtering on token matches cannot work, and its own `ApplyFilter` test looks like it would fail.
3. `splitWords` does not strip HTML tags, so headings with markup (e.g. `<em>`) produce polluted tokens.
4. It widens scope with tokenization of basic-index `ToKeywords` and an unrequested `MinTokenLength` option. These change semantics beyond the issue and add risk.
5. It also includes whitespace churn in existing tests.

Patch A is correct, tightly scoped, documented and well tested; Patch B breaks existing behavior and has a broken filter path.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

(bool) Whether to split multi-word values into individual keywords for indexing and matching. Currently applies to heading titles in indices of type fragments; non-heading fragments such as definition terms continue to use exact-identifier matching regardless of this setting. This increases index size in proportion to the average number of words per heading; use cardinalityThreshold to prune common words and reduce build time. Default is false.
