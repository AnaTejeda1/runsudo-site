In this judgment, Patch B = our agent, Patch A = the merged fix.

Patch B fixes the root cause directly. It rewrites the decimal pattern generator so no look-around assertions are emitted, and it keeps the existing behavior of including a `pattern` describing `max_digits`/`decimal_places`. It also handles pattern size: above `_DECIMAL_PATTERN_MAX_DIGITS_LIMIT`, it falls back to checking integer and fractional digits separately, so the regex stays within pydantic-core's limits. Its new tests match the issue's scenario: they feed the emitted pattern back through `TypeAdapter(Annotated[str, StringConstraints(pattern=...)])`, including large `max_digits` values (51, 300). They also check accept/reject behavior for a model in both validation and serialization modes. These tests would fail before the change. Patch A changes default behavior instead: it drops the `pattern` from Decimal JSON schemas entirely and adds an opt-in `get_decimal_pattern`/`build_decimal_pattern` hook backed by a much larger new regex builder (exponents, inf/nan, a separate serialization grammar). That does make the issue's symptom go away. However, it is a user-visible behavior change and a broad redesign well beyond the ask. Its new builder is never tested by compiling it in pydantic-core, which is the exact failure the issue reports; it only tests with Python's `re`. Its docs also contain two consecutive `version-changed` blocks that contradict each other: one says the pattern is included, the next says it no longer is. B is the more focused, behavior-preserving fix, with tests that exercise the reported failure.

Description

Pydantic v2 emits a JSON schema for Decimal fields that includes a regex pattern with a negative lookahead ((?!...)). This pattern cannot be compiled by pydantic-core's Rust regex crate, which does not support look-around assertions.

This means the JSON schema pydantic produces for Decimal cannot be round-tripped back through pydantic's own validation e.g. constructing a TypeAdapter with StringConstraints(pattern=...) using the emitted pattern fails with a SchemaError.

This is a practical problem for any tooling that reconstructs pydantic types from emitted JSON schemas (e.g. MCP structured content parsing via FastMCP).

Example Code

"""Minimal reproduction: Decimal JSON schema pattern uses lookahead unsupported by pydantic-core.

Pydantic generates a JSON schema for Decimal fields with a regex pattern that uses
a negative lookahead (?!...). When that schema is round-tripped back through pydantic
(e.g. via TypeAdapter with StringConstraints), pydantic-core's Rust regex engine
rejects it because it does not support look-around assertions.
"""

from decimal import Decimal
from typing import Annotated

from pydantic import BaseModel, StringConstraints, TypeAdapter


class MyModel(BaseModel):
    amount: Decimal


def test_decimal_json_schema_pattern_roundtrips_through_pydantic_core():
    schema = MyModel.model_json_schema()

    # Decimal emits an anyOf with a string variant carrying the pattern
    string_variant = next(v for v in schema['properties']['amount']['anyOf'] if v.get('type') == 'string')
    pattern = string_variant['pattern']

    # The emitted pattern contains a negative lookahead:
    assert '(?!' in pattern

    # Feeding it back into StringConstraints fails with:
    #   SchemaError: regex parse error: look-around ... is not supported
    ConstrainedStr = Annotated[str, StringConstraints(pattern=pattern)]
    TypeAdapter(ConstrainedStr)


if __name__ == '__main__':
    test_decimal_json_schema_pattern_roundtrips_through_pydantic_core()
