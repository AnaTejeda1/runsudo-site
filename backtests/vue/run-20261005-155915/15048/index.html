Scoped slot transforms array argument if rendered conditionally

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the root cause the same way: the compiler-generated branch key becomes a separate 6th `renderSlot` argument instead of being merged into the slot props, so a single `v-bind` array reaches the slot unchanged. Both runtimes use that key for the fragment key and add it to the real `<slot>` element in custom-element mode.

Correctness: Patch A applies the new path only where the bug occurs, in `injectProp`, when the slot props are a single `v-bind` expression. Every other slot case keeps its existing codegen (plain object or object-literal injection), which lowers regression risk. Patch A also removes the `ref_for` marker from slot outlets. Without that, `<slot v-for v-bind="arr">` would still emit `mergeProps({ref_for: true}, arr)` and turn the array into an object, which is the same symptom in a sibling scenario. Patch B does not handle that case. Instead, Patch B routes every slot key injection through the new argument, which changes codegen even for slots that were never affected. B does keep user-key priority (`props.key || branchKey`), slightly closer to the old merge semantics. A gives the compiler key priority, a minor edge case.

Tests: Patch A adds compiler tests for v-if, template v-for and v-for slot cases. It also adds end-to-end compiler+runtime tests that check the slot receives a real array (`Array.isArray(list)` is true), that it survives toggling, and that v-if/v-else branch keys still cause a remount, plus a custom-element test. These would fail before the fix and target the reported behaviour directly. Patch B's tests are compiler snapshots plus unit tests of `renderSlot` with the new argument. They are reasonable but do not show the full compiled-template scenario working, and do not cover the v-for/`ref_for` variant.

Scope and craft: Patch B rewrites existing snapshots for unaffected cases and adds a stray `transformElement.spec.ts.snap` containing v-for snapshot content, which is churn and looks like a mistake. Patch A's change is localized and clearly commented.

Overall, Patch A is more targeted, covers more manifestations of the bug, and has stronger tests.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Steps to reproduce

  1. Create a component with a scoped slot that is rendered conditionally
  2. Pass an array as the sole argument to the slot

What is expected?

Array is rendered normally.
If you render items of that array in v-for loop, you only see items inside that array

What is actually happening?

Array is transformed into object. Items and their indexes are staying the same, key field is added
