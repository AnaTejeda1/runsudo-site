Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches make the essentially identical core fix to the TYPE_CHECKING signature (include/exclude → IncEx | None, context → Any | None, add fallback and polymorphic_serialization), so correctness of the runtime-signature fix is a wash. The decisive differences are in tests, scope, and craft. Patch B adds regression cases exactly where the issue asks and where they matter — tests/typechecking/root_model.py — which are consumed by the mypy/pyright/pyrefly suites that actually exercise the reported bug (type-checkers rejecting valid calls). Its cases mirror the issue's example precisely (non-dict context, fallback=, polymorphic_serialization=) and would fail type-checking before the fix and pass after. Patch B is otherwise minimal: it leaves the original docstring untouched. Patch A instead adds a runtime test in tests/test_root_model.py that monkeypatches typing.TYPE_CHECKING=True and re-execs the module to compare inspect.signature parameter lists. This is fragile and, more importantly, tests the wrong thing: it verifies runtime signature/docstring parity, not that type-checkers accept the calls — the actual regression. Worse, its assertion that RootModel.model_dump.__doc__ must equal BaseModel.model_dump.__doc__ forces Patch A to wholesale replace RootModel's intentionally distinct docstring (which explained the RootModelRootType return semantics) with a copy of BaseModel's, demoting the original explanation to a comment. That is real scope creep driven by the test's own artificial requirement, plus added churn and coupling. Patch A's use of collections.abc.Callable is marginally more modern than Patch B's typing.Callable, but that minor craft point does not outweigh Patch B's superior test placement, faithful adherence to the issue's proposal, and tighter scope.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The issue

View on GitHub

Initial Checks

  • I confirm that I'm using Pydantic V2

Description

RootModel inherits the runtime implementation of BaseModel.model_dump(), but defines a separate declaration under TYPE_CHECKING to preserve its more precise return type.

That declaration has diverged from the base method:

  • context is restricted to dict[str, Any] | None instead of Any | None.
  • fallback is missing.
  • polymorphic_serialization is missing.

As a result, Mypy, Pyright, and Pyrefly reject valid calls that succeed at runtime.

All three calls in the example below succeed at runtime.

Mypy currently reports errors equivalent to:

Argument "context" to "model_dump" of "RootModel" has incompatible type "str"
Unexpected keyword argument "fallback" for "model_dump" of "RootModel"
Unexpected keyword argument "polymorphic_serialization" for "model_dump" of "RootModel"

Pyright and Pyrefly report the same signature incompatibilities.

Expected behavior

The type-checking-only RootModel.model_dump() declaration should accept the same parameters, annotations, defaults, and ordering as BaseModel.model_dump(), while preserving the more precise RootModel return annotation.

Cause

The declaration appears to have drifted as the base method evolved:

  • Serialization context originally updated both signatures.
  • BaseModel.context was later widened to Any.
  • fallback was subsequently added to BaseModel.model_dump().
  • polymorphic_serialization was later added to BaseModel.model_dump().

Those later changes were not propagated to the manually maintained RootModel declaration.

Proposed fix

Update only the static RootModel.model_dump() signature and add focused regression cases to tests/typechecking/root_model.py.

No runtime serialization behavior needs to change.

I have prepared and locally validated a focused two-file fix. The following checks pass:

  • Mypy type-checking suite
  • Pyright type-checking suite
  • Pyrefly type-checking suite
  • Focused RootModel serialization tests
  • Ruff lint and formatting checks
  • git diff --check

I would be happy to submit the PR after the issue is reviewed and assigned.

What the agent reported

The fix is complete and verified.

What was wrong

RootModel.model_dump() has a TYPE_CHECKING-only signature stub (in pydantic/root_model.py) whose sole purpose is to give type checkers a more precise -> Any return type. This stub had drifted from the authoritative BaseModel.model_dump():

  • context was typed dict[str, Any] | None instead of Any | None
  • fallback was missing
  • polymorphic_serialization was missing

As a result, mypy/pyright/pyrefly rejected three calls that succeed at runtime.

What I changed

pydantic/root_model.py (the only runtime-adjacent edits are two import lines; the signature itself is inside the existing if TYPE_CHECKING: block, so no runtime behavior changes):

  • Added Callable to the typing import and IncEx to the from .main import ... line.
  • Aligned the stub's parameters/annotations/defaults/ordering exactly with BaseModel.model_dump(): include/exclude → IncEx | None, context → Any | None, added fallback: Callable[[Any], Any] | None = None and polymorphic_serialization: bool | None = None. Return annotation kept as -> Any.

tests/typechecking/root_model.py: added the three regression cases from the report (non-dict context, fallback=, polymorphic_serialization=), with no suppression comments so they must type-check cleanly.
