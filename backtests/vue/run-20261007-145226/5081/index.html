Throw an error on createVNode with using innerHTML and children at the same time

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

The issue is a render function that sets `innerHTML: undefined` together with children. It crashes, and the user wants to toggle between innerHTML and children dynamically, rendering whichever is provided.

Patch B only adds a dev-mode warning in createBaseVNode when a non-nullish innerHTML/textContent prop sits alongside children. It changes no runtime behavior. For the reported case (`innerHTML: undefined`) it explicitly emits nothing. It does nothing about the broken toggle: children mounted while innerHTML is set get overwritten and become detached, and switching back can leave stale or empty content. Its tests only assert warning messages, so they don't exercise the bug at all. B is a diagnostic, not a fix.

Patch A fixes the root cause by making client mount/patch semantics match SSR and hydration: when innerHTML/textContent is non-null, children are not mounted.
- mountElement skips children in that case.
- patchElement handles all transitions:
  - children → override: unmount old children and reset the new vnodes' mounted state.
  - override → children: clear the content and mount the new children fresh.
  - override → override: no-op.
  - It also guards TEXT patch flags.
- patchBlockChildren and unmount skip never-mounted vnodes reached through a parent block's dynamicChildren.
- traverseStaticChildren avoids inheriting els in that case.
- SSR now uses `!= null` instead of truthiness.

This is a larger and riskier change; for example, `isNeverMounted` relies on el/component being null. But it is coherent, and it is backed by thorough tests that would fail before the change:
- the exact issue reproduction
- text and array toggling, including component mount/unmount counts
- textContent toggling
- hydration with an override
- SSR edge cases
- a compiled template where a `:innerHTML` element sits inside a block with dynamic children

A addresses the requested behavior; B does not.
