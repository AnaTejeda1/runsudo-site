SSR hydration warning: dynamic props on SVG elements are patched as properties instead of attributes

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches make the same core fix. During hydration they derive 'svg' or 'mathml' from the element's own namespaceURI and pass it to patchProp in place of `undefined`. This resolves the root cause, because patchProp then takes the SVG/MathML attribute path, just as in client rendering. Both correctly treat `<foreignObject>` itself as an SVG element by reading el.namespaceURI rather than reusing getContainerType. A is slightly more defensive about a null namespaceURI and puts the logic in a named helper. B uses a non-null assertion, but elements hydrated from parsed HTML always have a namespace, so the practical risk is negligible. On correctness they are effectively equal.

The tests are the deciding factor. jsdom implements few SVG IDL properties and no MathML ones. In A's tests, `viewBox`, `width` and `display` are probably not present as properties, so `shouldSetAsProp` would fall back to setAttribute even without the fix. A's tests therefore likely pass on the unfixed code and don't guard the regression. B's foreignObject test defines a getter-only `width` property on the element, explicitly to work around jsdom's gap. This reproduces the issue's read-only IDL scenario: without the fix, patchDOMProp tries to assign the property, fails, and the attribute stays at 24. With the fix, the attribute becomes 48. B also uses differing server and client values, so the assertions show the patch actually happened. That makes B's test a genuine regression test that fails before the fix and passes after.

Scope is equally minimal in both. A's helper is slightly cleaner craft, but B's meaningfully stronger test coverage outweighs that.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Steps to reproduce

  1. Open the reproduction.
  2. Open the browser devtools Console.
  3. Observe the [Vue warn]: Failed setting prop … error logged during hydration.

What is expected?

During hydration, dynamic props on SVG (and MathML) elements width, height, viewBox, etc. should be patched as attributes (via setAttribute) exactly as they are during normal client-side rendering. Hydration should be silent.

What is actually happening?

Since 3.5.39, dynamic props on SVG elements are patched as DOM properties during hydration, which throws for read-only SVG IDL properties:

[Vue warn]: Failed setting prop "viewBox" on <svg>: value 0 0 24 24 is invalid.
TypeError: Cannot set property viewBox of #<SVGSVGElement> which has only a getter
    at patchDOMProp
    at patchProp
    at hydrateElement
    at hydrateNode
    at hydrateSubTree
    at <App>

Nothing is visually broken but the console is flooded with warnings.

We ran across this issue in a Nuxt app but I believe the issue is coming from Vue core
