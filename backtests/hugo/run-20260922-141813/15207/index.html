Issue #15207 Merged fix PR # Run 22 Sep 2026 · run-20260922-141813 gohugoio/hugo

panic: slice bounds out of range in contentNodeShifter.Delete when removing draft pages from a multilingual taxonomy

Worse

The merged fix was judged better than our patch.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches correctly diagnose the root cause: the `contentNodes` case of `Delete` mutates the slice with `v = append(v[:i], v[i+1:]...)` while ranging over the original header, so when two or more nodes match the delete vector the reslice indices run past the shrunken length and panic `[5:4]` — exactly the reported crash and the `0x35`/multi-page-in-one-taxonomy-term trigger. The difference is completeness. Patch B applies a minimal filter-in-place (write-pointer `n`, `v = v[:n]`) that stops the panic, but it (a) leaves the compacted slice unwritten to the tree — the doctree still holds the original-length header whose stale tail now contains the deleted nodes AND a duplicated *kept* node (e.g. `[keep0,keep2,keep5,del3,del4,keep5]`); the deleted ones are MarkStale'd but the duplicated kept node is not, so a surviving page can be double-referenced — and (b) ignores the identical mutate-while-ranging bug in `DeleteFunc`'s `contentNodes` case, leaving a second latent panic of the same class unfixed. Patch A restructures the loop to build fresh `remaining`/`deleted` slices (no shared-backing-array aliasing), extends the shifter interface so `Delete`/`DeleteFunc` return the updated node, and re-inserts that compacted node into the tree (`r.tree.Insert(key, updated)`) whenever something was deleted but the node isn't empty — so the tree ends up holding exactly the remaining nodes, and it fixes the twin `DeleteFunc` bug too. That is the true root-cause fix rather than a panic-suppression that relies on downstream staleness to mask a corrupt slice. On tests both are meaningful (interleaved and all-match cases that panic pre-fix); B's are tied more directly to the reported scenario, A's additionally assert the remaining-slice contents are correct, though A leaves its own changed `DeleteFunc` untested. Patch B wins clearly on scope — A's interface-signature change ripples through nodeshifttree.go, the interface definition, and the doctree test shifter, which is real churn. But correctness outranks scope, and A's larger footprint is the necessary cost of a complete fix: it eliminates the duplicate/stale-reference hazard B introduces and closes the second bug B leaves open. The scope cost is not enough to offset A's correctness advantage, so this is not a tie.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

What I ruled out

Site: 8 languages, ~1,490 pages per language, ~11,455 content files, categories taxonomy.

  • Not a regression. 0.159.1 and 0.164.0 behave identically.
  • Not the number of drafts. 96 draft pages build fine; 16 panic.
  • Not slug length. The panicking key was 47 chars, but renaming an unrelated post to exactly 47 chars builds fine.
  • Not the slug. Renaming the offending page does not help.
  • Not byte layout. Deleting a front-matter line, or adding a blank one, still panics.

Swapping page content at a fixed path isolates it to front matter. Changing categories = ["Airport Operations"] on the offending page to any other value clears the panic — and so does moving a different page out of that same category while leaving the offending one alone. So the trigger is combinatorial: some particular set of pages being deleted from one taxonomy term corrupts the shifter, rather than any single page being malformed.

What the agent reported

All changes are in place and uncommitted, as required. The AGENTS.md/CLAUDE.md deletions were pre-existing in the starting snapshot, not part of this work.

Summary

What was wrong

contentNodeShifter.Delete (hugolib/content_map_page_contentnodeshifter.go) mutated a slice while ranging over it. In the case contentNodes: branch it did v = append(v[:i], v[i+1:]...) inside for i, nn := range v. The range fixes its bound to the original length, but each match shrinks v, so once i+1 exceeds the shrunken length the expression v[i+1:] panics with slice bounds out of range (the reported [5:4]). Other interleavings silently drop the wrong elements instead.

This path is hit from createAllPages's droppedPages cleanup (content_map_page_assembler.go:102-110) → treePages.Delete → NodeShiftTree.delete → shifter.Delete. It fires only when a page is removed from the tree — exactly the draft (no -D) and future-publishDate production-build cases in the report, and only when a single tree key holds a multi-element contentNodes slice with several nodes matching the site vector being deleted (the combinatorial multilingual-taxonomy condition the reporter observed). render/list = "never" avoids it because those pages are never added, so nothing is deleted.

What I changed

One branch in Delete: replaced the mutate-while-ranging loop with a filter-in-place using a separate write index (v[n] = nn; n++, then v = v[:n]). This deletes exactly the matching nodes, keeps the rest, and computes isEmpty correctly. No other branch or method was touched. 8 lines changed.

  • TestContentNodeShifterDeleteAllMatchesNoPanicIssue15207 (all match, recover-guarded) — before fix: FAIL with the literal runtime error: slice bounds out of range [3:2]; after: PASS.
