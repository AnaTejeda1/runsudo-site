tpl/compare: eq, le and ge disagree when comparing an int with an equal float

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the reported inconsistency. The question is which does so without adding risk.

**Patch B: targeted fix in `tpl/compare`.**
- It adds `eqMixedNumbers` to `Eq`. When one normalized operand is a float64 and the other is an int64 or uint64, it compares them as float64. That is the same conversion `compareGet` uses for `lt`, `le`, `gt` and `ge`, so the six functions now apply one rule.
- Because both halves share the float64 conversion, they agree even for very large integers.
- It also fixes a latent bug: a uint64 compared with a non-uint value left `left`/`right` at 0. For example, `uint64(5)` vs `4.5` compared as 0 vs 4.5. The patch fills in `float64(av.Uint())`.
- Tests cover every pair the issue lists, in both argument orders, through `doTestCompare`. They include uint64/float cases and an integration test asserting all six functions agree. These tests would fail before the patch and pass after.

**Patch A: correct for the issue, but a broad redesign with real regression risk.**
- It adds an exact `CompareNumbers` in `hreflect`. This is more precise for values above 2^53.
- It rewrites `Eq` normalization and `where.go`'s `checkCondition`.
- It changes the semantics of `hreflect.ConvertIfPossible`, which other code also calls:
  - Pointers are no longer dereferenced.
  - Conversions that lose precision now fail, e.g. float64(3.14)→float32 and MaxInt64→float64.
  - Existing tests in `convert_test.go` were rewritten to expect the new behavior, which is the 17 removed test lines.
- `convertNumber` in collections needed a compensating hack to keep float narrowing working, which shows the ripple effects.
- None of this is needed to resolve the issue. It risks breaking other `ConvertIfPossible` callers and `where` behavior, and it obscures the core fix.
- Its tests are thorough, but much of that coverage protects the extra scope rather than the issue.

On correctness for the reported scenario, the two are effectively equal. Patch B is the safer, focused fix with adequate tests, so it wins.

Does this issue reproduce with the latest release?

I built master at ae07063 and reproduced it there. I did not run a tagged release binary, so I have not confirmed it against one directly, though the code path is unchanged in tpl/compare/compare.go.

What did you expect to see?

eq, ne, lt, le, gt and ge agreeing with each other. Whatever the rule for comparing an int against a float, exactly one of lt/eq/gt should hold for a given pair, le should mean lt or eq, and ge should mean gt or eq.

What did you see instead?

For 1 against 1.0, the six functions contradict each other. le and ge are both true while lt, gt and eq are all false, so the value is reported as neither less than, nor greater than, nor equal to itself.

layouts/index.html:

eq  1 1.0 = {{ eq 1 1.0 }}
ne  1 1.0 = {{ ne 1 1.0 }}
lt  1 1.0 = {{ lt 1 1.0 }}
le  1 1.0 = {{ le 1 1.0 }}
gt  1 1.0 = {{ gt 1 1.0 }}
ge  1 1.0 = {{ ge 1 1.0 }}

Rendered output:

eq  1 1.0 = false
ne  1 1.0 = true
lt  1 1.0 = false
le  1 1.0 = true
gt  1 1.0 = false
ge  1 1.0 = true

eq normalises an int to int64 and a float to float64 and then compares them as any, so they are never equal. lt/le/gt/ge go through compareGet, which converts both to float64, so they compare numerically. The two halves of the API use different rules.

Same result for 0 vs 0.0, -1 vs -1.0, int64(3) vs float64(3) and uint(4) vs 4.0. Mixed values where the numbers genuinely differ (1 vs 2.0) are consistent, so this only shows up when the two are numerically equal.

This is adjacent to #3721, which asked for eq to be more lenient and was closed by the stale bot in 2018 without a decision. This report is narrower: whichever convention you prefer, the current combination is not self-consistent.

I have not sent a patch because the fix is a semantics choice, either making eq compare numerically or making le/ge strict about mixed types, and that is your call. Happy to send a PR once you say which.
