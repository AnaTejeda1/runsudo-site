KeepAlive caches a never-mounted vnode when a switch lands while an ancestor Suspense is pending

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches add the guard the issue suggests: inside the post-render effect, only cache the inner child when `innerChild.component` is non-null. That stops the poisoned cache entry that caused the null `suspenseId` and `bum` crashes, and both tests reproduce the reported A→B (pending) → resolve → A → B sequence.

Patch A also handles a consequence the issue does not mention. KeepAlive's render calls `keys.add(key)` before the post-render effect runs. When the guard skips the cache write, the key for B stays in `keys` with no matching `cache` entry. With `max` set, a later prune can pick that orphan key as the oldest. `pruneCacheEntry` then finds `cached` undefined and takes the `else if (current) resetShapeFlag(current)` branch. That clears the keep-alive flags on the currently rendered vnode (A), so A is really unmounted on the next switch instead of being deactivated. This hits the issue's real-world setup, `<NuxtPage :keepalive="{ max: 5 }" />`.

Patch A deletes the key when no cache entry exists for it, and its second test covers this case with `max: 2`. It checks `unmountedA` / `mountedA` counts, which would fail under Patch B's guard alone. Patch B fixes the reported crash but leaves this cache-eviction bug in place.

Both patches are small and match the surrounding code. Patch A's tests are more thorough. A is the more complete and correct fix.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Steps to reproduce

The reproduction drives itself from onMounted — just open it and read the log. The tree is the one Nuxt renders for a page with <NuxtPage keepalive>:

<Suspense>            <!-- root boundary, still pending -->
  <RootDep />         <!-- async setup, resolves after 300ms -->
  <KeepAlive>
    <Suspense>        <!-- per-page boundary -->
      <component :is="page" :key="key" />
    </Suspense>
  </KeepAlive>
</Suspense>
  1. While RootDep is still pending (so parentSuspense.deps > 0), switch the inner page from PageA to PageB.
  2. Let the root boundary resolve.
  3. Switch back to PageA, then to PageB again.

What is expected?

The inner page follows the switches, and no errors are raised.

What is actually happening?

The rendered page is stuck on PageA forever — every later switch is a no-op — and the renderer throws:

Cannot read properties of null (reading 'suspenseId')   // patchSuspense
Cannot read properties of null (reading 'm')            // unmountComponent

In a production build the second one is the more familiar
Uncaught (in promise) TypeError: Cannot destructure property 'bum' of 'instance' as it is null.

Removing the <KeepAlive> and changing nothing else makes both errors go away and navigation work.

Any additional comments?

The chain, as far as I could trace it:

  1. The route change re-renders KeepAlive, so the inner <Suspense> is patched with n1 != null. Because an ancestor boundary is still pending, SuspenseImpl.process takes its early return:
   if (parentSuspense && parentSuspense.deps > 0 && !n1.suspense.isInFallback) {
     n2.suspense = n1.suspense
     n2.suspense.vnode = n2
     n2.el = n1.el
     return
   }

The incoming page vnode is therefore never patched: vnode.component === null, vnode.el === null.

  1. KeepAlive's onUpdated → cacheSubtree still caches it, unconditionally:
   if (isSuspense(instance.subTree.type)) {
     queuePostRenderEffect(() => {
       cache.set(pendingCacheKey, getInnerChild(instance.subTree))
     }, instance.subTree.suspense)
   }
  1. The next render for that key hits the poisoned entry: KeepAlive copies cachedVNode.component (null) onto the new vnode and sets COMPONENT_KEPT_ALIVE, so patchSuspense reads newBranch.component.suspenseId on null, and the teardown that follows calls unmountComponent(null).

Suggested fix — the same shape as the two guards already at that site, i.e. do not cache a vnode that never finished mounting:

const innerChild = getInnerChild(instance.subTree)
if (innerChild.component) {
  cache.set(pendingCacheKey, innerChild)
}

With that guard the page is simply not cached that one time, and the reproduction runs clean.

This looks like a third path into the defect class fixed by #10912 (avoid caching vnode that not been mounted, for #10899) and #11479 (for #6028) — both guard KeepAlive's own subtree, while here it is an ancestor Suspense that is pending.

Real-world context: this is how it surfaced for us — a Nuxt 4 app rendering <NuxtPage :keepalive="{ max: 5 }" />, where a link clicked before hydration finished intermittently left the user on a blank page with Cannot destructure property 'bum' of 'e' as it is null in the console. The window widens with slower hydration, so it shows up under load / on slow clients.

What the agent reported

I fixed the bug. KeepAlive no longer caches a page that never mounted, so the switch sequence from the report runs without errors. All 44 runtime-core test files pass (1070 tests). The changes are uncommitted in the working tree.

What was wrong: your trace is correct. While the outer <Suspense> is still pending, SuspenseImpl.process skips patching the inner <Suspense>, so the new page vnode never gets a component. KeepAlive's cacheSubtree cached it anyway. The next switch to that key reused the empty cache entry, which caused the suspenseId error in patchSuspense and the unmountComponent(null) crash.

What I changed (packages/runtime-core/src/components/KeepAlive.ts, cacheSubtree, Suspense branch):

  • Your suggested guard: the inner child is cached only if innerChild.component is set.
  • One extra step you didn't suggest: if caching is skipped and that key has no older valid entry, the key is also removed from keys. The render function adds the key before caching runs. Left in place, it can make a later max prune remove the wrong page: with max: 2, the left-over key made page A count as the oldest, so switching to page C wrongly unmounted A, as the second test shows.

Tests (both in packages/runtime-core/__tests__/components/Suspense.spec.ts):

  • KeepAlive + nested Suspense switch while ancestor Suspense is pending: follows the report: switch A→B while the outer boundary is pending, let it resolve, then A, then B. It checks the exact rendered output at every step. Before the fix it failed on the final switch with TypeError: Cannot read properties of null (reading 'suspenseId') in patchSuspense; now it passes.
  • KeepAlive (max) + nested Suspense switch while ancestor Suspense is pending: the same scenario with max: 2 and a third page, C. It checks that pages A and C are each mounted once and never unmounted. With the key-removal step taken out it fails (A gets unmounted); with it, it passes.
  • Gate: ./bt-test packages/runtime-core/__tests__ gives 44 files and 1070 tests passed. Prettier is clean on both changed files.

Requirements:

  1. Inner page follows switches, no errors: done; the first test checks the rendered output after every switch.
  2. Both errors (suspenseId, null instance in unmountComponent) gone: done; the first test reproduced the suspenseId error before the fix and passes after it. The second error happens in the teardown that follows the first one.
  3. Suggested fix (don't cache a vnode that never mounted): done as suggested, plus the key removal above.
  4. Without <KeepAlive> it works: no change needed, since the fix only touches KeepAlive's caching.
  5. Same defect class as #10912 / #11479: those guards are unchanged and their existing tests still pass.

Still open: right after the outer boundary resolves, the screen shows A even though B was selected while it was pending. The switch made during the pending window is lost, because the inner <Suspense> skipped that patch. The first test records this exact current output, and the next switch works normally. Fixing it would mean changing that skip in Suspense.ts, which I left out to keep the change minimal.

The reviewer also flagged two existing weak spots that this change doesn't make worse, and I left them alone:

  • The queued cache step reads pendingCacheKey when it runs rather than when it was queued.
  • KeepAlive's record of the current page can still point at the never-mounted B after the outer boundary resolves.
