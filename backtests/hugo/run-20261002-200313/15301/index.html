Improve/document security.http.urls override behavior

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

The issue asks for better visibility and documentation of how the security.http.urls override disables the dial-time resolved-address check. Patch B targets that ask directly. It adds a dedicated docs section explaining the behavior, its caveats (permissive allowlists, deny-only lists, repeating defaults plus additions), and a narrow-allowlist recommendation. It also factors the condition into IsResolvedHTTPAddressCheckEnabled with a clear doc comment and adds a hint to AccessDeniedError, so users who hit the denial learn why and how to opt out. Its tests cover the enabled and disabled cases across several custom policies, including the default patterns plus an addition, and assert the new error message. Those tests would fail before the change, since the method and hint don't exist yet. Patch A adds a short doc paragraph about the override, which partly answers the issue. Most of the patch, though, is an unrelated new feature: proxyFromEnvironment, with a custom proxyTransport, context-carried proxy URLs, a reimplemented canonicalAddr, and a new golang.org/x/net dependency. It also changes default behavior by setting base.Proxy = nil, so environment proxies, which were honored before via the cloned DefaultTransport, are now ignored unless the user opts in. That is a regression risk for existing users behind proxies. The added complexity (address matching to bypass the check for the proxy dial) adds risk and obscures the documentation fix the issue asked for. B is focused, lower-risk, better tested for the issue's concern, and improves user-facing diagnostics.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The issue

View on GitHub

In d6e6f9e500eebdeae8e28de830fff2e3bfc7d534 (unreleased) we added a dial-time URL validation to catch URLs that's valid according to the whitelist but that resolves to a loopback, private or link-local IP addresses. That check is skipped it if the user has a custom security.http.urls setup, as it would not make sense to block local development servers.

See CheckAllowedHTTPAddress.

This has been reported by @Reload3d as a potential security issue, and while I think the current behaviour is the pragmatic correct approach, I'm creating this issue for visibility and to see if this can be improved further (e.g. better documentation).
