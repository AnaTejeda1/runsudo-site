Add config option security.http.proxyFromEnvironment = false

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches correctly identify the root cause: the secure transport clones http.DefaultTransport, whose Proxy=ProxyFromEnvironment means the env proxy is honored by default and the dial-time CheckAllowedHTTPAddress only ever sees the proxy address. Both default the new flag to false and null out base.Proxy in that case, so both fix the reported default-off hardening. The decisive difference is the opt-in path. Patch A, when proxyFromEnvironment=true, leaves the Control hook (CheckAllowedHTTPAddress) applied to every dial, including the dial to the proxy itself. Since real HTTPS_PROXY/CI proxies are almost always on loopback or private/internal addresses — exactly the scenario the issue cites — Patch A's dial to such a proxy would be rejected by the resolved-address check under the default urls allowlist, so the opt-in silently fails to reach the proxy unless the user also overrides http.urls (undocumented). Patch A's test only asserts tr.Proxy==nil is true/false and never exercises an actual fetch through a loopback proxy, so it doesn't catch this. Patch B handles the enabled case properly: it routes proxy dials through a separate dialer that skips the address check (the user has explicitly opted into trusting the proxy) while still validating direct dials — and still validates the proxy's own address when it is the direct destination — carrying the proxy decision per-request via context so both the Proxy and DialContext hooks agree. Patch B's test actually stands up proxy and target servers and verifies: default ignores the proxy and fetches directly; enabled dials a loopback proxy even under the hardened default policy; and direct loopback dials (including to the proxy's address) still return AccessDenied. That is a strong before/after test targeting the real behavior. Patch B also updates docs (security.md with newIn, docs.yaml) which Patch A omits. Patch B costs more scope/complexity (context key, proxyTransport wrapper, canonicalAddr mirroring net/http, httpproxy import), but that complexity is justified by delivering a working, tested opt-in rather than one that breaks in the exact environment the issue describes. B wins on correctness, tests, and craft; A wins only on minimal scope, which does not outweigh a partially non-functional opt-in.

The issue

View on GitHub

This is a security hardening issue.

In d6e6f9e500eebdeae8e28de830fff2e3bfc7d534 (unreleased) we added a dial-time URL validation.

If proxied (e.g. HTTPS_PROXY set on users machine or in CI) the above validation will only see the proxy address. There's no workaround for that, but I suggest by adding a new security.http.proxyFromEnvironment bool config flag (default disabled).

Thanks to @Reload3d for reporting this issue.
