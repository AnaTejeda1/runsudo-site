Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches make the independent tests pass for both resolvers, so the decision rests on how they get there and what else they change.

Patch A fixes the failure at the point it occurs: when `migrate deploy` reports P3018 with SQLSTATE 0A000 (or a P3009 whose ledger logs show that error), it parses the shipped migration, builds the index the way Postgres documents for partitioned tables (metadata-only index ON ONLY the parent, CONCURRENTLY per partition, ATTACH PARTITION, recursing into sub-partitions, redoing an interrupted invalid child build), verifies the parent index is valid, and then marks the migration applied. It leaves the already-applied migration file untouched, which respects the checksum caveat the file itself documents, falls back to the plain CONCURRENTLY build on an unpartitioned table, refuses to touch any migration that is not purely `CREATE INDEX CONCURRENTLY IF NOT EXISTS`, and gives a clear manual-fix message when psycopg is absent. It wires into both the legacy and v2 resolver paths. Its unit tests run without a database (fake catalog that rejects CONCURRENTLY on a partitioned relkind and models parent-index validity), cover the P3018 flow, the P3009 leftover row, the replica race on `resolve --applied`, and that unrelated migrations with the same error still stop startup; a real-Postgres test is DB-gated but exercises the actual statements.

Patch B solves the issue by redesigning how request-log indexes are delivered: it rewrites two migration files (including one that is not involved in the issue) to `SELECT 1`, moves index creation out of Prisma entirely into a post-deploy job or a daemon thread in the serving proxy, filters those indexes out of drift scripts and the schema-sync test, changes the data-rewrite lint checker (adding three more grandfathered migrations including the baseline), extends `repair_invalid_indexes`, changes integration test harness defaults, and modifies the CLI exit semantics. This does make partitioned deployments succeed, and the partitioned build itself is careful (equivalent-index adoption, lock handover, bounded parent lock). But the scope far exceeds the ask and introduces real risk: already-applied migration files are edited despite Prisma checksumming; a fresh database now has a finished ledger row for an index that may not exist yet; deployments that migrate from the serving proxy only get the (api_key, startTime) and call_id indexes after readiness on a best-effort background thread; and the drift filtering means schema.prisma deliberately disagrees with the migrations. Those are behavioral changes outside the issue that an operator did not ask for, and they obscure the fix.

On correctness both hold up under the issue's scenarios; on tests both are reasonable, with A's core logic testable without a database; on scope A is tightly targeted while B's redesign adds risk; on craft both are clean. A is the better fix.

What happened?

When running database migrations via prisma migrate deploy, migration 20260831120001_spend_logs_litellm_call_id_index fails if LiteLLM_SpendLogs is a PostgreSQL partitioned table.

PostgreSQL does not support CREATE INDEX CONCURRENTLY directly on partitioned tables, throwing:

Database error code: 0A000
Database error:
ERROR: cannot create index on partitioned table "LiteLLM_SpendLogs" concurrently

Expected behavior:
Database migrations should succeed on deployments where LiteLLM_SpendLogs has been partitioned (e.g. for retention and high-volume spend logging).

User Flow

Before a (hypothetical) fix: an operator deploying LiteLLM on a PostgreSQL database with partitioned LiteLLM_SpendLogs runs migrations and encounters a hard deployment failure.

  1. Operator runs prisma migrate deploy against the PostgreSQL database.
  2. Migration 20260831120000_add_litellm_call_id_spend_logs applies successfully.
  3. Migration 20260831120001_spend_logs_litellm_call_id_index executes: sql CREATE INDEX CONCURRENTLY IF NOT EXISTS "LiteLLM_SpendLogs_litellm_call_id_idx" ON "LiteLLM_SpendLogs"("litellm_call_id");
  4. PostgreSQL rejects the statement with ERROR: cannot create index on partitioned table "LiteLLM_SpendLogs" concurrently (SQLSTATE 0A000).
  5. Prisma marks the migration as failed (P3018), blocking all subsequent migrations.

After a (hypothetical) fix: the migration succeeds on both partitioned and non-partitioned tables.

  1. Operator runs prisma migrate deploy against the PostgreSQL database.
  2. Migration 20260831120000_add_litellm_call_id_spend_logs applies successfully.
  3. The migration detects or handles partitioned tables (e.g., standard non-concurrent index creation on the parent table which automatically propagates to all child partitions, or indexing partitions individually before attaching).
  4. All migrations apply cleanly with status 0.
