Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches close the three routes named in the issue, and the independent tests confirm it: all four denied-URL cases go from FAIL-ASSERT on base to PASS on both A and B, with the controls unchanged. The difference is in how each gets there and what else it risks.

Patch A changes `get_model_from_request` to prefer the URL model whenever the FastAPI-dispatched handler actually binds a `model`/`model_name` path parameter or a `model` query parameter, read from `scope["route"]`. That is route-agnostic in the sense the issue asks for: generateContent, streamGenerateContent, the deployment image routes, `/engines/{model}/...`, `/openai/deployments/{model}/chat/...` and `?model=` are all covered without a template list, and any future `{model}` handler is covered automatically. It also only trusts path params the handler declares, so the budget-fallback's planted `path_params["model"]` does not leak into routes that never read it (tested explicitly). It keeps the rest of the existing resolution flow intact by assigning into `model` and letting the remaining post-processing run. The change is confined to auth_utils, and its tests are end-to-end through the real app with TestClient, asserting both the 403 and that the premium deployment's mock output never appears, plus positive cases (allowed URL model with denied body model is served, streaming, multipart edits). Those are exactly the issue's reproduction scenarios.

Patch B hardcodes three regexes for the affected routes and replays `resolve_inference_model` with general_settings/user_model to mirror the handler's precedence, then threads `path_params` through the budget-reservation estimators. It is correct for the listed routes and the reservation work is a reasonable adjacent improvement, but it is the template-list approach the issue explicitly warns leaves other routes (e.g. `/engines/{model}/`, `?model=`) and future routes open. It also returns early before the remainder of `get_model_from_request`'s candidate/post-processing logic, skipping whatever normalization follows, and it spreads the change across five production files (including a new `user_model_view` in proxy_server and an intra-function import of proxy_server), which widens the blast radius for a fix the issue scopes to the access check. Its tests are solid unit tests but mostly exercise `get_model_from_request` directly rather than the served path.

On correctness both resolve the reported bypass; A addresses the root cause more generally and with less churn, and its tests more directly reproduce the issue. B's extra reservation plumbing is neutral-to-slightly-risky scope. A wins on a moderate margin.

The issue

View on GitHub

what happens

a virtual key is scoped to one model with models: ["cheap-model"]. the proxy correctly blocks the denied model when it is named in the request body (403 key_model_access_denied). but on three routes the key is served the denied model anyway, as long as the denied model is in the url and an allowed model is in the body:

  • POST /v1beta/models/{model}:generateContent
  • POST /v1beta/models/{model}:streamGenerateContent
  • POST /openai/deployments/{model}/images/generations (and /images/edits)

the model that actually runs is not bounded by the key's allowed list on these routes.

this is the same class as the open report #41810 (chat route) and its open fix #41852. that fix only lists the chat / completions / embeddings routes, so these routes stay open after it. i applied #41852 and re-tested: the chat routes become 403, but generateContent, streamGenerateContent and images still return 200 and serve the denied model.

why it happens

two parts of the proxy read the requested model from different places.

flowchart TB
    R["one request"] --> B["body says: cheap-model (allowed)"]
    R --> U["url path says: premium-model (denied)"]
    B --> G{"access check reads the BODY<br/>get_model_from_request -> allow"}
    U --> H{"handler routes on the URL<br/>resolve_inference_model prefers endpoint model"}
    G --> P["request passes the check"]
    H --> S["denied model is served and billed"]
    P --> S
  • the access check get_model_from_request (litellm/proxy/auth/auth_utils.py) reads the body model first, and only falls back to the url model when the body has none. with an allowed model in the body, it approves.
  • the handler passes the url path model into the request processor (litellm/proxy/google_endpoints/endpoints.py, litellm/proxy/image_endpoints/endpoints.py), and resolve_inference_model (litellm/proxy/common_utils/http_parsing_utils.py) prefers that endpoint model over the body. so routing uses the denied model.

the safety net only works when the body is silent: with no body model the access check reads the url model and correctly returns 403. the bypass needs both fields, an allowed body model to pass the check and a denied url model for the handler to route on.

why this matters

the per-key models list is the operator's way to bound cost and model access for a key (for example a key limited to one cheap or local model for a tenant). on these routes that boundary is not enforced, so a key holder reaches and spends on models the operator never granted. it is a 403 on the body today, so the gap is a per-route inconsistency, not a design choice.

honest scope: this needs a valid authenticated key and a hand-written request (the google genai sdks send the model only in the url, no body model, which is correctly blocked). so it is a scoped key holder bypassing their own scope, not an unauthenticated attack or a cross-tenant data leak. by the categories in SECURITY.md this is a p2 (authenticated action beyond permissions). i am raising it here because the same class is already public in #41810 and #41852; happy to move it to a private advisory with a screen recording if you prefer that channel.

suggested fix (route-agnostic, so new routes are covered too)

#41852 fixes this by listing route templates. that works for the routes it lists, but any route not on the list (these three, and any added later) stays open.

flowchart LR
    Fix["#41852 route list"] -->|covers| Chat["chat / completions / embeddings"]
    Fix -.->|misses| Gc["generateContent / streamGenerateContent"]
    Fix -.->|misses| Img["images routes"]
    Fix -.->|misses| New["any future route"]

every model-serving route funnels through one place, ProxyBaseLLMRequestProcessing.base_process_llm_request in litellm/proxy/common_request_processing.py, right after resolve_inference_model sets self.data["model"] to the model that will actually run. re-checking the key and team allowlist against that resolved model there (reusing can_key_call_model / can_team_access_model from auth_checks.py, and honoring the existing router-fallback access rules) closes every route at once, because it checks the model that is truly dispatched rather than guessing per route.

flowchart TB
    A["chat"] --> F
    B["generateContent / stream"] --> F
    C["images"] --> F
    D["responses, messages, video, ocr, ... (one funnel)"] --> F
    F["base_process_llm_request<br/>self.data['model'] = resolve_inference_model(...)"] --> K{"re-check the resolved model<br/>against the key/team allowlist"}
    K -->|allowed| Run["dispatch"]
    K -->|not allowed| Deny["403 key_model_access_denied"]

i have this fix working locally and can open a pr with tests that cover generateContent, images and a chat route if that direction is welcome. i am also glad to add the image and generateContent templates to #41852 instead if you would rather keep the current approach.
