Both patches fix the two paths named in the issue: they add `content=chunk.delta` to the streaming `ResponseReasoningTextDeltaEvent` handler (identical fix), and they populate `ThinkingPart.content` from `raw_content` in the non-streaming path. Both update the same tests to fail-before/pass-after. Patch B's extra edit is a necessary correctness fix, not scope creep. The guard is slightly subtle but justified. Patch B is the more complete and internally consistent fix.

Description

When using OpenAIResponsesModel with providers that emit response.reasoning_text.delta events (instead of response.reasoning_summary_text.delta), the reasoning content is dropped — ThinkingPart.content remains empty (or "").

This affects providers like:

  • gpt-oss via LM Studio / OpenRouter
  • vLLM (both native /v1/responses and via litellm bridge)
  • Any OpenAI-compatible provider that uses reasoning_text content type instead of reasoning_summary_text

The official OpenAI Responses API only emits response.reasoning_summary_text.delta, but third-party implementations use response.reasoning_text.delta for raw chain-of-thought. The ResponseReasoningTextDeltaEvent handler was added in response to #3191, but it is incomplete — it does not pass content=chunk.delta to handle_thinking_delta().

Two code paths are affected:

  1. Streaming (openai.py ~line 3704): ResponseReasoningTextDeltaEvent handler calls handle_thinking_delta() without content=chunk.delta. The delta text only goes to provider_details via _make_raw_content_updater. Compare with the ResponseReasoningSummaryTextDeltaEvent handler (~line 3690) which correctly passes content=chunk.delta.
  1. Non-streaming (openai.py ~line 2004): When item.summary is empty but item.content has reasoning_text entries, ThinkingPart(content='') is created. The raw content is only stored in provider_details['raw_content'].

Expected: ThinkingPart.content should contain the actual reasoning text, not an empty string.

Minimal, Reproducible Example

# Simulated streaming response with reasoning_text.delta events
# (as emitted by vLLM, LM Studio with gpt-oss, or litellm bridge)

from pydantic_ai.models.openai import OpenAIResponsesModel, OpenAIResponsesStreamedResponse

# When a provider sends:
#   {"type": "response.reasoning_text.delta", "item_id": "rs_123", "delta": "Let me think...", "content_index": 0}
#   {"type": "response.reasoning_text.delta", "item_id": "rs_123", "delta": "The answer is 4.", "content_index": 0}
#
# The handler processes the event but NEVER passes chunk.delta as content:
#
#   elif isinstance(chunk, responses.ResponseReasoningTextDeltaEvent):
#       for event in self._parts_manager.handle_thinking_delta(
#           vendor_part_id=chunk.item_id,
#           # MISSING: content=chunk.delta,
#           id=chunk.item_id,
#           ...
#       ):
#
# Result: ThinkingPart(content='') instead of ThinkingPart(content='Let me think... The answer is 4.')

You can verify by running the existing tests test_openai_responses_raw_cot_only, test_openai_responses_raw_cot_stream_openrouter, and test_openai_responses_raw_cot_sent_in_multiturn — all assert content='' for ThinkingPart when raw CoT is present, which is the bug.
