Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches register `_RootModelMetaclass` in `get_metaclass_hook`, so both fix the subclass case. They differ in how they handle a `RootModel[float]` type alias.

Patch A adds a `get_function_signature_hook` for `RootModel` calls. When `init_typed` is unset, it replaces the `root` argument type with `Any`, so `RFoo('1.0')` passes both positionally and by keyword. It skips generic signatures, so a bare `RootModel(1)` still infers `RootModel[int]`. The change is narrow and leaves `RootModel`'s own class definition alone. The default `init_typed` behaviour is kept, and the docs note the new behaviour. Its tests cover:
- the alias called positionally and by keyword,
- the subclass,
- `assert_type` on `.root`,
- that bare `RootModel(1)` still infers `int`,
- the strict and default configurations producing the expected errors.

Patch B removes the guard that stops the plugin from replacing the explicitly declared `__init__` on `RootModel` itself. `RootModel` then gets a plugin-synthesized `__init__` whose `root` parameter is untyped (`Any`) by default. That fixes the alias case, but it likely breaks generic inference for unparametrized `RootModel(x)`, which would now produce `RootModel[Any]`. It also swaps the hand-written signature, including its `PydanticUndefined` default and `**data` handling, for a synthesized one, which is a broader and riskier change. Its tests do not check that inference is preserved or that the keyword form works.

Patch A is the more targeted and safer fix, and its tests are more thorough.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Description

The below example code (named foo.py) passes when running python foo.py as the input "1.0"-string gets converted to float. However, running mypy foo.py (with or without --strict) gives the following error:

foo.py:11: error: Argument 1 to "RootModel" has incompatible type "str"; expected "float"  [arg-type]
Found 1 error in 1 file (checked 1 source file)

I would expect the BaseModel-fields and the RootModel-field to behave the same in this case. That is, if the value can be converted – either via a custom made validator or through the conversion table – then mypy should not raise an error.

Example Code

import pydantic


class Foo(pydantic.BaseModel):
    f: float


RFoo = pydantic.RootModel[float]

f = Foo(f="1.0")
rf = RFoo("1.0")

assert isinstance(f.f, float)
assert isinstance(rf.root, float)
assert f.f == rf.root
