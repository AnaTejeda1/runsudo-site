looseEqual: comparing Map/Set values with circular references throws RangeError (regression in 3.5.42)

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches stop the unbounded recursion by threading a per-call 'seen' state through arrays, objects, Maps and Sets. Both handle the issue's three repro shapes: mutually-referencing Set elements, Map values with peers, and self-containing Sets. Both also fix the plain-object cycle case.

Correctness: Patch A tracks (a, b) pairs currently on the recursion stack and returns true when a pair is met again. This is exactly the approach the issue suggests, and it gives coinductive structural equality. A wraps the comparison in try/finally so the state is always cleaned up, and it keeps the public `looseEqual(a, b)` signature unchanged by adding an internal `looseEqualImpl`.

Patch B enforces a bijection between visited nodes. That is also cycle-safe, and it deliberately treats a self-loop and a 2-cycle as unequal (a stricter semantics than the issue asks for, but defensible). However, B adds an optional third `seen` parameter to the exported `looseEqual`. This leaks an internal detail into the public API. It is also risky: any caller that passes `looseEqual` directly as a callback which supplies a third argument would hand it a bogus state tuple. B also has no try/finally, though that matters little because the state is per call.

Tests: A adds unit tests for Sets, Maps (including self-reference), and cyclic objects and arrays. It also adds a runtime-dom `vModel` test that reproduces the issue's actual scenario (`<select v-model>` with cyclic Set and Map option values) and checks that the correct option is selected. B only adds shared unit tests, including a reasonable symmetry test, but has no component-level coverage of the reported failure.

Scope and craft: Both are comparably scoped. A's change is a cleaner wrapper around the existing logic. B moves the object, Map and Set logic into a new helper and introduces a callback indirection (`looseCompareNested`), which is somewhat harder to follow.

Overall A is the better fix: it follows the issue's suggested semantics, keeps the API clean, and tests the reported scenario end-to-end.

Steps to reproduce

Open the reproduction above: a <select v-model> whose option :values are Sets containing mutually-referencing objects. The component throws during mount, before any interaction.

<script setup>
import { ref } from 'vue'

const makeGraph = () => {
  const n1 = { id: 1 }
  const n2 = { id: 2 }
  n1.peer = n2
  n2.peer = n1  // circular reference
  return new Set([n1, n2])
}

const optA = makeGraph()
const optB = makeGraph()
const selected = ref(optB)
</script>

<template>
  <select v-model="selected">
    <option :value="optA">A</option>
    <option :value="optB">B</option>
  </select>
</template>

What is expected?

Mounting the select should not throw. looseEqual should safely terminate on cyclic structures (e.g. by tracking already-visited pairs) and return true for two structurally identical cyclic Sets/Maps.

Any additional comments?

This is a regression introduced by #15328 ("fix(shared): correctly compare Map and Set values", released in v3.5.42), which added looseCompareCollections in packages/shared/src/looseEqual.ts:

function looseCompareCollections(
  a: Map<any, any> | Set<any>,
  b: Map<any, any> | Set<any>,
) {
  if (a.size !== b.size) return false
  const candidates = Array.from(b)
  const matched = new Uint8Array(candidates.length)
  for (const item of a) {
    let index = -1
    for (let i = 0; i < candidates.length; i++) {
      if (!matched[i] && looseEqual(item, candidates[i])) {
        index = i
        break
      }
    }
    if (index < 0) return false
    matched[index] = 1
  }
  return true
}

looseEqual(item, candidates[i]) recurses into each [key, value] pair (Map) or element (Set), so a Map/Set whose entries point back to the collection itself or to each other causes unbounded recursion. Before 3.5.42, Maps/Sets never recursed into their entries (they fell through to String() comparison), so this exact code path — a <select v-model> with Map/Set values, which is precisely the scenario #15320/#15328 added support for — did not throw on 3.5.41; it silently compared wrong, which #15328 fixed.

Note: #5318 covers the same root cause for cyclic plain objects (pre-existing, still open). The Map/Set case is new in 3.5.42: cyclic Maps/Sets did not throw before.

Suggested fix: make looseEqual cycle-safe by tracking visited (a, b) pairs (e.g. with a WeakMap<object, Set<object>> and returning true on re-encounter), which also fixes #5318.

Additional local repro cases that all throw RangeError on current main:

  • looseEqual(new Set([a1, a2]), new Set([b1, b2])) where a1.peer = a2; a2.peer = a1 and b1.peer = b2; b2.peer = b1
  • looseEqual(mapA, mapB) where both maps hold mutually-referencing values
  • looseEqual(s1, s2) where s1.add(s1) and s2.add(s2)
