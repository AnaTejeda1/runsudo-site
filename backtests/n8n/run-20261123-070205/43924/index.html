Bug Description

When n8n uses PostgreSQL and the PostgreSQL session time zone is not UTC (e.g. the server's timezone setting is a local zone, which is the Debian initdb default), the startedAfter / startedBefore filters of the executions list are applied shifted by the zone's UTC offset. With a UTC+2 server time zone, both bounds act 2 hours earlier than requested.

Affected: the instance-level MCP tool search_workflow_executions and the date filter of the executions list (same query path). The stored startedAt values and the values returned in responses are correct; only the filter is shifted.

Root cause (from the source of n8n@2.47.7):

  1. packages/@n8n/db/src/repositories/execution.repository.ts, startedAtCondition(): MoreThanOrEqual(DateUtils.mixedDateToUtcDatetimeString(new Date(startedAfter))) (same for startedBefore).
  2. DateUtils.mixedDateToUtcDatetimeString (@n8n/typeorm) builds YYYY-MM-DD HH:mm:ss.SSS from getUTC*() — a UTC wall-clock string without a zone designator.
  3. On Postgres, execution_entity."startedAt" is timestamptz (datetimeColumnType).
  4. Postgres interprets a zone-less literal compared against timestamptz in the session TimeZone. n8n does not set the session time zone in its connection options, so the server default applies.

So 08:20:00 (meant as UTC) is read as 08:20:00+02 = 06:20:00Z.

The same pattern is used in getIdsSince() and getWorkflowIdsWithExecutionsSince(). The waitTill queries only use it for SQLite and pass Date objects on Postgres, so they are not affected.

Related: #25054 (same helper, write path of startedAt, also non-UTC Postgres) was closed without merge; the write path is correct in 2.47.7, the filter path is not.

To Reproduce

  1. Run n8n with DB_TYPE=postgresdb against a Postgres whose timezone is a non-UTC zone with a positive offset (e.g. ALTER DATABASE n8n SET timezone = 'Etc/GMT-2', i.e. UTC+2), restart n8n.
  2. Have an execution with startedAt = 2026-11-14T06:20:30Z.
  3. Call search_workflow_executions with startedAfter=2026-11-14T06:20:00Z, startedBefore=2026-11-14T06:21:00Z → empty result.
  4. Call it with startedAfter=2026-11-14T08:20:00Z, startedBefore=2026-11-14T08:21:00Z → the 06:20:30Z execution is returned.
  5. Set the session zone to UTC for the n8n role (ALTER ROLE n8n IN DATABASE n8n SET timezone = 'UTC'), restart n8n → step 3 returns the execution, step 4 is empty.

Expected behavior

The filter bounds are compared as absolute instants, independent of the Postgres session time zone — e.g. pass Date objects (or ISO strings with an offset) for Postgres instead of zone-less UTC strings, or set the session time zone to UTC in the Postgres connection options.

Debug Info

Self-hosted, official Docker image n8nio/n8n:2.47.7, container TZ=UTC, GENERIC_TIMEZONE set to a UTC+2 zone (not relevant to the bug; the shift follows the Postgres session time zone). External PostgreSQL 17 with server timezone UTC+2. Workaround applied: role-level timezone = 'UTC'.
