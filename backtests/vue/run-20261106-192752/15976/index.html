KeepAlive + Suspense: async descendant resolving while inactive causes an infinite microtask retry loop on return

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the reported hang at the same root: the `pendingId` mismatch guard in `registerDep` no longer abandons an instance that is still alive (kept-alive or still in the active branch), so its setup/render actually completes instead of leaving `asyncResolved=false` for the renderer's async-root retry to spin on. All six independent tests pass on both, and each patch adds a repro test that fails on base.

The difference is in how they treat the issue's explicit constraint: 'keep the stale-branch guards and pending dependency counts correct for unrelated branches.' Patch A renders the stale instance immediately, even while the boundary is pending on a different tree. That render uses the same `suspense` as parent, so any async children the resolved component mounts call `registerDep` and increment `suspense.deps` under the *other* branch's `pendingId`. A slow or stuck descendant of the inactive cached page would then hold back the unrelated pending branch (e.g. navigating to an async page while the cached page's child finishes). A only patches around the symptom of this by splicing post-effects out of `suspense.effects`; it does not address the dep-count contamination. Its hydration branch simply reverts to base behaviour (abandon), which is not a regression but also not handled.

Patch B parks the stale instance's render in a `REQUEUE_ON_SUSPENSE_DISCARD` job until the boundary has no pending branch, re-parks it across discards, and explicitly excludes it from the dep count (`isPendingDep`). This keeps unrelated cycles' `deps` correct, which it verifies with the 'off-cycle async dep must not add its own async children to the pending cycle' test, plus cases for nested pending ancestors, out-in transitions, and hydration toggles. It also removes the `COMPONENT_KEPT_ALIVE` `pendingId` restoration, replacing that special case with the general stale-dep path; the `test.each` kept-alive scenarios cover what that line previously guaranteed, including that a discarded cycle is not counted down.

B is larger and touches the scheduler and three Suspense sites, which is real added risk, and I cannot confirm the existing suite still passes on either tree. But the extra machinery is targeted at a hole A leaves open and is backed by specific tests, whereas A's minimal change is cleaner but only partially honours the issue's stated requirement on unrelated branches. On correctness and test depth B is the better fix.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Each saw the issue and the two patches, labelled A and B in random order (two of them saw ours as A), with issue links and version numbers removed. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours. The reasoning above is one judge's, shown verbatim.

Vue version

Link to minimal reproduction

Open the single-file Vue Playground reproduction

Warning: clicking the button intentionally triggers an unresponsive preview.

The import map pins Vue's production runtime to 3.5.44.

No router, SSR, Nuxt, external requests, or application dependencies are required.

Steps to reproduce

  1. Open the reproduction and wait until the button is enabled.
  2. The status should read: Ready: the inner async child is still pending.
  3. Click Run reproduction once.
  4. The preview becomes unresponsive; the success status never appears.

The button performs this deterministic sequence, rather than relying on network timing:

  1. Cache a page shell containing a still-pending async descendant.
  2. Switch to another page and flush the update with nextTick().
  3. Resolve the descendant's loader while its cached page is inactive.
  4. Wait for its Promise callbacks to run, using a macrotask boundary.
  5. Return to the cached page and change the descendant's revision prop.

The page shell uses a non-suspensible async wrapper to finish mounting first.

Its inner async child retains the default suspensible: true behavior.

What is expected?

  • Returning to the cached page displays Async child loaded.
  • The existing cached page remains usable, without an infinite update loop.
  • A retained child's async setup can finish, either while inactive or on reactivation.

What is actually happening?

  • The loader Promise fulfills, but the retained instance stays asyncResolved === false.
  • Returning and updating its parent repeatedly retries an already-fulfilled Promise.
  • The resulting microtask loop prevents subsequent timers and UI work from running.

This is an async retry loop, not a synchronous call-stack overflow.

Complete App.vue

Replace App.vue in a Vue SFC project with the following; no other files are needed.

<script setup>
import {
  defineAsyncComponent,
  h,
  nextTick,
  onMounted,
  ref,
} from 'vue'

const route = ref('page')
const revision = ref(0)
const ready = ref(false)
const status = ref('Waiting for the page shell')
let resolveChild
const childReady = new Promise(resolve => {
  resolveChild = resolve
})
const AsyncChild = defineAsyncComponent(() => childReady)
const Page = {
  setup() {
    onMounted(() => {
      ready.value = true
      status.value = 'Ready: the inner async child is still pending'
    })
    return () => h(AsyncChild, { revision: revision.value })
  },
}
const AsyncPage = defineAsyncComponent({
  loader: () => Promise.resolve(Page),
  suspensible: false,
})
const Entry = {
  name: 'Entry',
  render: () => h('div', [h(AsyncPage)]),
}
const Other = { render: () => h('div', 'Other page') }

async function reproduce() {
  ready.value = false
  route.value = 'other'
  await nextTick()
  resolveChild({ render: () => h('span', 'Async child loaded') })
  await new Promise(resolve => setTimeout(resolve, 0))
  status.value = 'The child resolved while its page was inactive. Returning...'
  route.value = 'page'
  revision.value++
  await nextTick()
  await new Promise(resolve => setTimeout(resolve, 0))
  status.value = 'Returned successfully; the UI is still responsive'
}
</script>

<template>
  <p>{{ status }}</p>
  <button :disabled="!ready" @click="reproduce">Run reproduction</button>
  <KeepAlive include="Entry">
    <Suspense>
      <component :is="route === 'page' ? Entry : Other" />
      <template #fallback>Loading...</template>
    </Suspense>
  </KeepAlive>
</template>

State observations and preliminary diagnosis

The following states were captured in a focused runtime-test fixture against current main.

The async child remains mounted in a cached ancestor; it has not been unmounted.

Inner async child starts loading00false
Switch to the other page01false
Loader fulfills while away01false
Return and update the cached page00false

The last stage reaches nextTick(), but a subsequent timer never runs.

An external watchdog terminated the isolated reproduction after three seconds.

Relevant source, pinned to the tested commit:

  • Suspense.registerDep
  • Renderer async-root retry

The failure appears to cross these two paths:

  1. Leaving switches the shared Suspense boundary to a different pending ID.
  2. The cached page and its pending descendant are retained instead of unmounted.
  3. When the loader fulfills, registerDep() rejects the mismatched pending ID.
  4. It returns before asyncResolved = true and before handleSetupResult().
  5. Returning restores the old boundary ID, but the skipped Promise callback is not rerun.
  6. The parent's component-root chain still contains that unresolved async instance.
  7. locateNonHydratedAsyncRoot() finds it and schedules a retry after asyncDep.
  8. That Promise has already fulfilled, so the retry immediately runs again.
  9. The instance is still unresolved, so the same retry is scheduled indefinitely.

Changing a fulfilled loader into a cached factory is not sufficient to finish this instance.

The component definition has loaded; the retained instance's setup/render initialization has not.

Tests performed:

  • The complete SFC above was compiled and mounted in jsdom 26.1.0 with Vue 3.5.44.
  • Its original sequence timed out; both controls completed and rendered the child.
  • A focused fixture against current main reproduced the state table and retry hang.
  • Earlier isolated production-runtime fixtures reproduced it on 3.5.22 and 3.6.0-rc.12.

The RC test used the VDOM renderer, not Vapor. This is not a claim about all Vue versions.

The SFC compiler used for the jsdom test was 3.5.22; the runtime under test was 3.5.44.

No full repository test suite, build, or type check was run for this report.

Possible fix direction — not a validated patch

  • Preserve or resume async initialization for descendants retained in a KeepAlive cache.
  • Distinguish a retained inactive branch from an abandoned/unmounted branch.
  • Prevent retries from looping when the awaited Promise is settled but setup is unresolved.
  • Keep the stale-branch guards and pending dependency counts correct for unrelated branches.

Simply deleting the pending-ID guard could revive genuinely abandoned work.

Simply setting asyncResolved = true would skip the missing setup/render initialization.

Using separate cached, page-owned Suspense boundaries also passed an isolated 3.5.22 control.

That is an application-level workaround, not a proposed or validated core patch.

The distinguishing condition here is loader completion while the retained page is inactive.

The child has a real component instance; this is not the null cached-vnode case in #15288.
