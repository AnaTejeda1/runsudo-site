TypeAdapter config not used for JSON Schema generation

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the reported case the same way. They push the adapter's `_config` onto the generator's `_config_wrapper_stack` around `generate()` in `TypeAdapter.json_schema`. That addresses the root cause: the TypeAdapter config is not part of the core schema, so the JSON Schema generator never saw it. Patch B also fixes the sibling entry point, `TypeAdapter.json_schemas()`, which has the same defect. That path calls `generate_definitions` with core schemas only, so per-adapter configs (e.g. `ser_json_bytes='base64'`) would still be ignored there. B passes a per-input config list and pushes each config in both passes of `generate_definitions` (the definition-collection pass and the remap pass), so `$defs` and the top-level schemas stay consistent. Pushing `None` is a no-op on the stack, so the default path is unchanged. On tests, A adds one test, for `list[bytes]` with `ser_json_bytes`; it would fail before the fix and is adequate. B covers the exact issue example, a no-config control case, `ser_json_temporal`, `json_schema_mode_override` (which takes effect through the stack-aware mode lookup), and the `json_schemas` multi-adapter path with mixed configs. B's tests exercise more of the behaviour the fix enables. B's extra mutable `_inputs_configs` attribute on the generator is slightly awkward as a side channel, but it is private and defaults safely. Overall, B resolves the issue more completely across both TypeAdapter schema APIs and tests it more thoroughly.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
