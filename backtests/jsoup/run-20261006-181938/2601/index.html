The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the same core problems in nearly the same way. Each puts a synthetic html element at the bottom of the stack instead of the context copy. Each routes the adoption agency's step 14 through the 'appropriate place' insertion with fostering. Each walks the stack so a template more recent than the last table receives fostered content. Each saves and restores the foster flag around nested InTable processing, which fixes the consecutive-paragraph case. Each ignores an errant </col> in column-group mode, sends column-group EOF through InBody handling, and uses the adjusted current node for namespace and CDATA checks.

The key difference is what fragment output looks like. Patch A detaches the context copy and returns the synthetic html root's children. Parsed fragment nodes therefore now have an <html> element as their parent, and streaming emits 'html' instead of the context tag. Patch A had to rewrite existing tests to accept this (parseFragmentOnCreatedDocument, nestedPFragments, canStreamFragment, canIterateFragment). That is a user-visible behaviour change the issue never asked for.

Patch B keeps the context copy as the visible result container in the document. It redirects insertions aimed at the hidden root into that container, covering elements, text, comments and fostered nodes. It also maps the root to the container in onNodeInserted, onNodeClosed, isOpen and copyOpenElementsTo. Streamed nodes therefore sit in the context-named container from the moment they are inserted, which is exactly what the issue describes. Existing parent expectations remain valid, and Patch B removes only the one test line whose expectation the issue explicitly calls wrong (the nested tr). It also keeps DataNode handling for script contexts by redirecting to the context before checking the tag.

Patch B's tests are broader on the issue's scenarios:
- parameterized adoption cases for tbody, thead, tfoot and tr, plus template-in-table and table-in-template orderings, run in both document and fragment form;
- live streaming parentage checks for p and table contexts;
- stop() behaviour;
- a check that real column groups still close correctly.

Patch A has two advantages:
- It guards against pos == 0 in the stack-parent fallback; Patch B's stack.get(pos - 1) would throw there, though that state is practically unreachable.
- It tightens the body/frameset fragment checks, an adjacent fix outside the issue's ask.

These do not outweigh the API regression in Patch A's fragment container. Patch B is the better fix.

The issue

View on GitHub

There are a few related issues in table parsing, affecting both full documents and fragments.

The adoption agency algorithm moves blocks into a table instead of applying foster parenting.
For example:

<table><b><p>X</b>

Currently produces:

<b></b><table><p><b>X</b></p></table>

Expected:

<b></b><p><b>X</b></p><table></table>

Consecutive paragraphs also lose foster parenting when the second paragraph implicitly closes the first:

<table><tr><p id=first><p id=second>

Both paragraphs should appear before the table, in input order, but the second ends up inside the row. These cases also affect table sections and fragment parsing.

Also foster parenting needs to respect an intervening template instead of moving content outside the older table.

And: column-group fragments can incorrectly close their parsing context. Setting either of these as a colgroup element’s HTML should produce just <col id="kept">, without introducing row or column-group wrappers:

<tr><col id=kept>
</colgroup><col id=kept>

Also an errant </col> incorrectly closes the current column group, splitting subsequent columns into another group. EOF handling in column-group mode also needs to follow the normal body/template cleanup rules.

The root cause is that fragment parsing currently uses a copy of the context element as its stack root.
That can introduce redundant structure. For example, setting a tr element’s HTML to <tr><td>One</td></tr> nests another row instead of producing just <td>One</td>. It can also leave parsed nodes outside the result container during streaming, only moving them back at fragment completion.
