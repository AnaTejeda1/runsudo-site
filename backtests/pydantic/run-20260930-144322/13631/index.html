Initial Checks

Description

When a discriminated union uses a bool discriminator (Literal[True] / Literal[False]), the generated JSON schema's discriminator.mapping uses the Python string representations "True" and "False" as keys:

"discriminator": {
    "mapping": {"False": "#/$defs/Disabled", "True": "#/$defs/Enabled"},
    "propertyName": "enabled"
}

Per the OpenAPI discriminator specification, mapping keys must match the serialized payload value of the discriminator property. For a boolean property, that value serializes to JSON true/false, so the keys should be "true" and "false". Tooling that resolves the mapping against the payload (code generators, validators such as openapi-generator or Redocly) fails to match either variant.

Expected:

"mapping": {"false": "#/$defs/Disabled", "true": "#/$defs/Enabled"}

Note that Enum discriminator keys are already normalized to their value (k.value) before stringification in GenerateJsonSchema.tagged_union_schema; bool keys just fall through to str(k).

Example Code

from typing import Literal

from pydantic import BaseModel, Field


class Enabled(BaseModel):
    enabled: Literal[True]
    config: str


class Disabled(BaseModel):
    enabled: Literal[False]


class Model(BaseModel):
    setting: Enabled | Disabled = Field(discriminator='enabled')


print(Model.model_json_schema()['properties']['setting']['discriminator'])
# {'propertyName': 'enabled', 'mapping': {'True': '#/$defs/Enabled', 'False': '#/$defs/Disabled'}}

What the agent reported

I fixed the bug: bool discriminators now produce "true" / "false" as mapping keys instead of "True" / "False". The new regression test failed before the change and passes after it, and the nearby existing tests still pass.

What was wrong: In GenerateJsonSchema.tagged_union_schema (pydantic/json_schema.py), Enum keys were already converted to their .value, but every other key went through str(k). For a bool, that gives Python's "True" / "False", which doesn't match the JSON value true / false that OpenAPI tooling compares against.

What I changed:

  • pydantic/json_schema.py:1383: after the Enum step, a bool key now becomes 'true' or 'false'. Because this runs after the Enum step, an Enum whose value is a bool gets the same treatment.
  • Test: I added test_discriminated_union_literal_bool_mapping_keys to tests/test_json_schema.py. It uses the exact Enabled / Disabled models from the report and checks that the discriminator is {'mapping': {'false': '#/$defs/Disabled', 'true': '#/$defs/Enabled'}, 'propertyName': 'enabled'}.

Test evidence:

  • Before the fix, the new test failed on the mapping assertion.
  • After the fix, ./bt-test tests/test_json_schema.py: 533 passed, 3 skipped, 1 xfailed.
  • The other test files that use discriminators (test_forward_ref, test_validate_call, test_dataclasses, test_edge_cases, test_root_model): 671 passed, 3 skipped, 5 xfailed.

Blast radius: The change only affects discriminator keys that are bool, and it changes their JSON schema output. A search found no existing test or doc expecting 'True' / 'False' mapping keys. Keys that are strings, ints or other Enums are unchanged. Validation itself is untouched, since the change is only in JSON schema generation.

Requirements:

  1. bool discriminator mapping keys should be "true" / "false": done, covered by the new test.
  2. Output should match the report's expected mapping: done; the test asserts that exact dict.
  3. Handle this like the existing Enum normalisation in tagged_union_schema: done, placed right after the Enum step.
