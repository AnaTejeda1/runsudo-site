suspense.resolve() is called without a pending branch.

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Patch B fixes the cause of the warning in the issue; Patch A fixes a different, narrower scenario.

The warning appears when a dep is registered while the boundary is pending and settles after the boundary has already resolved. This happens when a pending branch is toggled back to the active one, as when navigating away during setup. When that late dep settles, registerDep's callback decrements `deps` to 0 and calls `resolve()` with `pendingBranch === null`. That is exactly the warning.

Patch B adds two guards:
- It checks `suspense.pendingBranch` before decrementing and resolving.
- It resets `deps = 0` on resolve, so stale counts cannot leak into the next pending cycle.

Its tests reproduce this flow: switch to an async branch, switch back while the active branch mounts a new async child (or a nested suspensible Suspense), then check that `onResolve` is not called again and that the next cycle still resolves normally. Before the fix, these tests would trigger an extra resolve or warning, or leave a stale dep count.

Patch A wraps the same-root-type patch in `patchSuspense` with `deps++`/`deps--`. This only targets nested suspensible Suspense boundaries resolving the parent mid-patch. It does not touch the registerDep path, where a dep settles after the boundary has resolved, so the reported warning is still possible. Its tests are reasonable, but they exercise a different bug from the one in the issue.

On correctness and relevance to the issue, Patch B is clearly better.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
