[Bug]: Unable to re-edit Model LiteLLM Params on LiteLLM UI

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches make the independent tests pass and both fix the actual mechanism behind the bug: the model PATCH merges submitted litellm_params over the stored blob, so a key deleted from the JSON editor is merely omitted and survives the save. Patch A fixes this with a small, coherent change on both sides: the UI diffs the keys it showed in the editor against the edited JSON and sends an explicit null for each removed key, and update_db_model pops explicitly-nulled undeclared (model_extra) keys from the merged litellm_params/model_info, while refusing to clear secret-looking keys. It adds backend unit tests (removal, omission keeps, secret-looking null ignored, model_info custom key removed but team_id kept) and UI tests that drive the editor and assert the payload and post-save view, plus unit tests for the small helper. Weaknesses: it only handles undeclared keys, so declared runtime defaults shown in the editor (use_litellm_proxy, use_in_pass_through) still cannot be removed, and the comment admits access_groups now becomes null-clearable, slightly relaxing a prior guard. Patch B is a much broader redesign: a new PatchModelRequest schema with litellm_params_to_remove replacing updateDeployment on the PATCH route, a new use_stored_params query flag on /v2/model/info with an extra DB lookup, exclude_unset=True on the stored-params dump (changing what gets written back for every PATCH), frozen request models requiring a rewrite of the team-update path, new PTU/aws_session_tags/strategy-router removal checks, removal of the modelInfoV1Call fallback, a change in editor semantics (form-managed params hidden from the JSON box, altering existing test expectations), a test-file rename, and eslint-suppression edits. It does address the defaults-reappearing aspect more completely and its tests are substantial, but the amount of behaviour touched (API contract, write path for all patches, editor contents) carries materially more regression risk than the issue warrants, and several changes (exclude_unset, dropping the v1 fallback) are hard to validate from the diff alone. Weighing correctness on the reported scenario (both pass), tests (both adequate), scope (A tight, B expansive with added risk) and craft, A is the better fix for this issue.
