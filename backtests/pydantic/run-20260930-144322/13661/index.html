In this judgment, Patch B = our agent, Patch A = the merged fix.

The Rust changes are functionally identical. Both add `by_alias`/`by_name` fields to `InternalValidator`, capture them from `extra` in `new`, and forward them in both `validate` and `validate_assignment` instead of hardcoding `None`. This fixes the root cause: the runtime alias settings were being reset when the wrap handler re-entered validation. The only difference in the Rust code is where the struct fields sit, which does not matter. The decision therefore rests on the tests.

Patch B adds a parametrized test in `test_aliases.py`. It closely mirrors the issue (alias_generator, TypeAdapter, wrap model validator) and covers all four by_alias/by_name × input combinations in both python and json modes. It is clean and well placed, and it would fail before the fix.

Patch A's first test covers the same four combinations with a wrap model validator via `model_validate`. It also exercises the nested case, where an outer model's field-level wrap validator (which also goes through `InternalValidator`) passes data to an inner model. That checks propagation through a second wrap-handler path that Patch B does not test. Patch A's second test checks context, strict, extra and from_attributes propagation through wrap handlers. These were likely already forwarded before the change, so that test is neutral hardening rather than a regression test for this issue. It adds some noise but no risk.

Neither patch tests the assignment path. On balance, Patch A's tests cover more of the code the fix touches (both model and field wrap handlers, including nesting), while Patch B adds json-mode coverage of the same path. This is a narrow edge, and I give it to A.

Description

The handler passed to a wrap-mode model validator appears to silently drop the passed-in by_name/by_alias arguments from the top-level validate_python methods.

Example Code

from typing import Self
from pydantic import BaseModel, TypeAdapter, ValidatorFunctionWrapHandler, model_validator

CFG = {"alias_generator": lambda s: s.replace("_", "-"), "validate_by_name": True}

class Plain(BaseModel):
    model_config = CFG
    build_depends: list[str] = []

class Wrapped(BaseModel):
    model_config = CFG
    build_depends: list[str] = []

    @model_validator(mode="wrap")
    @classmethod
    def _noop(cls, data, handler: ValidatorFunctionWrapHandler) -> Self:
        return handler(data)

data = {"build_depends": ["x"]}  # field name, not the alias
print(TypeAdapter(Plain).validate_python(data, by_alias=True, by_name=False))    # build_depends=[]    correct
print(TypeAdapter(Wrapped).validate_python(data, by_alias=True, by_name=False))  # build_depends=['x'] wrong

What the agent reported

Fixed: a @model_validator(mode="wrap") handler now keeps the by_alias/by_name values you pass to validate_python/validate_json. The new regression test passes with the change, and 4 of its 8 cases failed before it.

What was wrong: when a wrap validator calls handler(data), pydantic-core validates again through an internal object called InternalValidator (in pydantic-core/src/validators/generator.rs). That object copied settings like strict, context and from_attributes from the current run, but always set by_alias and by_name to None. So the handler fell back to the model config (validate_by_name=True), and {"build_depends": ["x"]} was accepted even with by_alias=True, by_name=False.

What I changed:

  • The fix (pydantic-core/src/validators/generator.rs): InternalValidator now stores by_alias and by_name when it is created and passes them on in both validate() and validate_assignment(). Nothing else changed in production code.
  • Side effect: generator validators use the same object, so items validated lazily inside a generator now also respect these settings. That is the expected behavior.
  • Other places: the reviewer checked every other spot that sets these values to None. They are entry points or URL helpers that never receive runtime values, so nothing else drops them.
  • Build: I rebuilt the extension with maturin develop --release. uv.lock, pyproject.toml and Cargo.lock are unchanged. cargo fmt and cargo clippy aren't installed for the toolchain here, so neither was run; the code compiled cleanly.

Regression test: test_runtime_alias_settings_with_wrap_model_validator in tests/test_aliases.py uses the report's model, with validate_python and validate_json, and four cases:

  • the reported case (by_alias=True, by_name=False with the field name gives []);
  • the reverse settings (by_alias=False, by_name=True with the alias gives []);
  • two cases with allowed input that fill the field, to check the fix doesn't reject too much.

Test results:

  • Before the fix: 4 of the 8 cases failed with assert ['x'] == [].
  • After the fix: ./bt-test tests/test_aliases.py tests/test_validators.py tests/test_model_validator.py tests/test_main.py tests/test_types.py gave 852 passed, 60 skipped, 4 xfailed and 1 failed.
  • The failure is test_validators.py::test_v1_validator_deprecated, which expects the warning's file path to be /workspace/tests/test_validators.py but gets /work/tests/test_validators.py. /work is a symlink to /workspace in this container, so this comes from the environment, not the fix. I didn't run it without the fix to confirm.
  • pydantic-core tests: test_function.py, test_generator.py, test_model_fields.py and test_model.py gave 448 passed and 2 skipped.
  • Your example: now prints build_depends=[] for both Plain and Wrapped.

Requirements:

  1. handler in a wrap model validator must respect runtime by_alias/by_name from validate_python: fixed, and covered by the new test.
  2. The report's example should give build_depends=[] for Wrapped, like Plain: fixed; that exact case is in the test and the script output confirms it.
  3. "The top-level validate_python methods": the fix is in the shared handler, so it also applies to validate_json (tested) and validate_strings (not tested).

Both changes are left uncommitted and no scratch files were added.
