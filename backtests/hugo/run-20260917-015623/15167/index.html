The issue

View on GitHub

I argued with @jmooring that it would be very unlikely that e.g. the CSS dark class would collide with existing classes in a project. After thinking a little, I still don't think that is a likely issue, but:

  1. I suspect there are JS/CSS frameworks with other naming standards for these mode classes (e.g. theme-dark)
  2. I would be an annoyed Hugo user if I needed to customise this class and had to do ugly string replacements.
  3. The cost for us adding these 2 new options is small.

Summary

Feature request: Add classDark and classLight options to css.ChromaStyles and hugo gen chromastyles, so users can customize the CSS mode-selector class names (instead of the hardcoded .dark/.light), defaulting to dark/light for backward compatibility.

What was changed (all uncommitted in the working tree):

  1. markup/highlight/chromastyles.go — Added ClassDark and ClassLight string fields to ChromaStylesOptions. In the ModeSelector block, the scoping prefix is now built from these options, falling back to "light"/"dark" when empty — so existing output is byte-identical unless a user opts in.
  1. commands/gen.go — Added --classDark / --classLight persistent string flags, wired them into the ChromaStylesOptions literal, and registered completion funcs following the existing flag pattern. Help text notes the defaults and the --modeSelector dependency.
  1. tpl/css/css.go — No change needed; it embeds ChromaStylesOptions via mapstructure:",squash", so the new dict keys flow through automatically.

Tests added (test-writer only):

  • tpl/css/chromastyles_integration_test.go — TestChromaStylesCustomModeClass asserts custom .theme-light .chroma / .theme-dark .chroma output via the template function.
  • testscripts/commands/gen_chromastyles_mode.txt — new CLI cases for --classDark/--classLight with positive and negative assertions.
