Issue #12569 Merged fix PR # Run 30 Sep 2026 · run-20261001-022054 vuejs/core

Custom directive's unmounted event is not triggered on v-for element

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Root cause: in a keyed v-for with a constant source (a stable fragment), `:key` forces `shouldUseBlock`. That makes `buildProps` skip adding NEED_PATCH for elements that have runtime directives, refs or vnode hooks. vFor then downgrades the child to a plain vnode with no patch flag, so it is missing from the fragment's dynamicChildren. As a result, unmount and update hooks are never run.

Patch A adds NEED_PATCH in vFor only when `childBlock.directives` is set. That fixes the reported directive case, and its integration test reproduces the issue. It leaves the same bug in place for static or setup-const refs (ref arrays are never cleared) and for `@vue:unmounted` vnode hooks. These share the identical root cause. Patch A also still downgrades children that were blocks for beforeUpdate ordering (custom directive or vnode before-update hook with children).

Patch B records the condition in the element transform via `needsPatch` and `isBlockRequired`, and vFor consumes it. NEED_PATCH is applied whenever a ref, vnode hook or runtime directive needs tracking and no other patch flag already tracks the vnode. Blocks are kept when beforeUpdate ordering requires them.

The refactors inside buildProps preserve behavior:
- moving `hasRef` earlier;
- excluding `ref` from dynamicPropNames, which matches the old else-if chain;
- camelize-based detection of `vue:beforeUpdate`, which also covers the camelCase spelling.

Patch B's tests cover directives, refs, function refs, vnode hooks, beforeUpdate ordering and patch-flag non-duplication, at both compiler and runtime level, and would fail before the change. B is larger, but it addresses the root cause comprehensively and with low risk, while A is a narrow symptom fix.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

What the agent reported

I fixed the bug: a directive's unmounted hook now fires for elements rendered with v-for when the list is constant. The fix is a small compiler change, and both new tests failed before it and pass after.

What was wrong
I compiled the reproduction to see what it produces:

  • The arr constant makes the v-for a "stable" fragment (patch flag STABLE_FRAGMENT). When such a fragment unmounts, Vue only visits the children it is tracking for updates.
  • transformElement.ts first compiles an element that has a dynamic :key or a custom directive with children as its own block. Because of that, it skips adding the NEED_PATCH flag, which is what normally gets such an element tracked.
  • vFor.ts then turns that element back into a plain node for the stable fragment, but never gives it a patch flag.
  • So each <h1> was not tracked, unmount never reached it, and its directive hooks (unmounted, and also beforeUpdate/updated) never ran. The <div> with v-if in the report is its own block, which is why its hook did fire.

What I changed (packages/compiler-core/src/transforms/vFor.ts, in the "Normal element v-for" branch)
When an element with directives becomes a plain node inside a stable fragment and has no patch flag, it now gets NEED_PATCH. This also covers an element whose only flag is NEED_HYDRATION, the same way transformElement.ts handles it; the reviewer pointed that case out.

Tests added

  • packages/compiler-core/__tests__/transforms/vFor.spec.ts, "v-for with constant expression on keyed element with custom directive": checks that the <div> inside a stable fragment is a plain node with patchFlag: NEED_PATCH. Before the fix it failed with "patchFlag": 512 expected but undefined received.
  • packages/vue/__tests__/index.spec.ts, "custom directive unmounted hook on keyed v-for with constant source": compiles the reported template (<template v-if> around a keyed <h1 v-for> with a custom directive), sets visible to false, and expects unmounted to be called 3 times. Before the fix it was called 0 times.

Test results

  • After the first version of the fix, the full suite passed: 182 files, 3653 tests, 6 skipped.
  • After adding the NEED_HYDRATION case, I re-ran compiler-core, runtime-core, compiler-sfc, compiler-dom, compiler-ssr, server-renderer and vue, not the whole suite: 144 files, 2914 passed, 1 skipped.
  • Prettier reports no formatting issues.

Requirements

  1. The H1's unmounted hook should run when "hide" is clicked: done, covered by the runtime test.
  2. Directive unmounted should fire on v-for elements in general: done for constant-source v-for, which is the only case where it was broken. With a reactive list, the fragment already visits every child on unmount, so those hooks already fired.
  3. The Div's hook should keep working: no change needed, because a v-if element is its own block and is always tracked; the full suite still passes.

Not fixed: a template ref or a @vue:unmounted handler on a keyed element in a constant-source v-for has the same root cause and will still be skipped on unmount. Fixing that needs a check on the element's props, not just its directives, so I left it out to keep this change limited to the report.

The changes are uncommitted in the working tree, and no scratch files are left.
