Issue #12569 Merged fix PR # Run 21 Oct 2026 · run-20261021-133314 vuejs/core

Custom directive's unmounted event is not triggered on v-for element

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches identify the same root cause: transformElement skips NEED_PATCH for elements it compiles as blocks (keyed elements, elements with runtime directives/vnode hooks plus children), and transformFor then demotes those blocks to plain vnodes inside a stable fragment without restoring the flag, so the vnode is never in the parent block's dynamicChildren and optimized unmount never runs the directive's unmounted hook. Both add NEED_PATCH back at demotion time, and both pass all five independent reproduction tests.

Patch A does this with a new `needsPatchWithoutBlock` helper that re-inspects the VNodeCall's props/directives from inside vFor. It is small and localized, but it duplicates buildProps's own analysis (hasRef/hasVnodeHook/runtimeDirectives) in a second place that can drift, and it unconditionally demotes the block. That discards a guarantee buildProps deliberately encodes: elements with a runtime directive or vue:before-update hook plus children are forced into blocks specifically so beforeUpdate runs before children patch. Under A, `<div v-for="i in 3" v-dir><span>{{x}}</span></div>` becomes a non-block vnode whose children are tracked ahead of it in dynamicChildren, so hooks now fire but in the wrong order.

Patch B threads the decision data out of buildProps (`needsPatch`, `isBlockRequired`) onto the VNodeCall, so vFor uses the same analysis the element transform used rather than re-deriving it. It only demotes when the block was not required for ordering, and keeps the block (which is still tracked by the parent block) when a before-update hook or directive with children needs it. It also correctly recomputes needsPatch after transformElement may have added TEXT, and tests that case. The hasRef reorder (so setup-const function refs are tracked) and the camelized `vue:beforeUpdate` match are adjacent fixes outside the issue's ask, but they are coherent with the same root cause, are covered by tests, and don't add meaningful risk. B is more invasive (ast.ts field additions, buildProps return shape), which costs it some scope/craft points, and the shadowed `needsPatch` plus `as PatchFlags` cast are slightly awkward.

Tests: both add compiler-level assertions and runtime integration tests that fail on base. B's tests additionally cover the ordering and non-NEED_PATCH cases that distinguish the approaches.

On balance B resolves the issue more correctly: it restores tracking without breaking the before-update ordering invariant the compiler already relies on, and it uses a single source of truth for the decision. A is a reasonable minimal fix but leaves a semantic regression path in the demoted-block case.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Each saw the issue and the two patches, labelled A and B in random order (two of them saw ours as A), with issue links and version numbers removed. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours. The reasoning above is one judge's, shown verbatim.
