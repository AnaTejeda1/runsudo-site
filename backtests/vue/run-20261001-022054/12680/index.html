$el of templateRef points to comment VNode instead of first real child of component

Worse

The merged fix was judged better than our patch.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Root cause: in dev builds, a template with a comment plus a single element compiles to a Fragment flagged DEV_ROOT_FRAGMENT. Because `vnode.el` is the fragment's start anchor, `$el` returns that anchor instead of the element. Both patches change the `$el` accessor to look through this fragment with `filterSingleRoot`, so both fix the exact scenario in the issue (a ref placed directly on Child).

Patch A is more correct in the cases around that scenario. It walks the root chain through nested component subTrees and Suspense active branches. So a component whose root is another component that has a comment-prefixed root also resolves `$el` to the real element. That inherited-root case is common, and it fails the same way as the original. Patch B only checks the immediate subTree, so in that case `$el` still returns the anchor node.

Patch A also preserves existing behaviour where no dev root fragment is found: it falls back to `i.vnode.el`, including when the value is null. It also gates the extra work behind `__DEV__`, where the flag can actually exist, so production `$el` access costs nothing extra. Patch B runs the flag check in production too. That is harmless but pointless.

Tests: Patch A covers the direct case, a single-root child component, nested dev fragments across component boundaries, Suspense, safe access during mount, and fallback for an unresolved async root. Patch B covers only the direct case.

Patch B is smaller and simpler, but it leaves a closely related variant of the bug unfixed. Patch A is the more complete and better-tested fix.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

What the agent reported

I fixed it: when a component's template is a comment followed by one element, templateRef.$el now points to that element instead of an empty text node. The new test failed before the fix and passes after, and all existing tests still pass.

What was wrong

  • How the template compiles: the dev template compiler keeps comments. So <!-- … --><div class="child"> becomes a root Fragment (a wrapper with several root nodes) holding the comment and the div. It is flagged DEV_ROOT_FRAGMENT, which marks "a single real root plus comments".
  • Where it broke: the runtime already treats that as a single root when passing attributes down. But $el was simply i.vnode.el, and for a Fragment that is the empty text node marking where the Fragment starts. That's the "text VNode" in the report, and why the click listener never fired.
  • Not only the playground's prod mode: I reproduced the same empty text node in a plain dev-mode test.
  • Why the playground's prod mode also hits it: the @vue/repl playground always compiles with isProd: false. Its PROD toggle only swaps in the production runtime, so the dev-compiled output (comment and flag included) runs against the prod runtime.
  • Normal production builds: these compile with comments stripped, so the root is already a single element there.

What I changed (packages/runtime-core/src/componentPublicInstance.ts)

  • The $el getter now checks whether the rendered root carries DEV_ROOT_FRAGMENT.
  • If it does, it uses the existing filterSingleRoot helper (which skips comments) and returns that root's element.
  • Otherwise it returns i.vnode.el exactly as before. That covers "not mounted yet" and genuine multi-root components, which still get the placeholder node as documented.
  • The check is deliberately not limited to development builds, so the playground's PROD mode is fixed too. filterSingleRoot is already included in production bundles.
  • Nothing else in the runtime reads $el, and vnode.el itself is unchanged, so moving, unmounting, hydration and transitions are unaffected.

Test evidence

  • New test: $el should be the single root element when root fragment contains comments in packages/runtime-core/__tests__/componentPublicInstance.spec.ts. It renders the reported structure (comment, then div.child) and checks that the comment is still rendered and that $el is the div.
  • Before the fix: it failed with expected undefined to be 'div', because $el was the anchor text node.
  • After the fix: ./bt-test on packages/runtime-core packages/runtime-dom packages/vue packages/vue-compat packages/server-renderer gave 93 files passed, 1784 tests passed, 1 skipped.
  • Prettier check passes on both files. I couldn't run the TypeScript type-check: the environment's guard hook blocked pnpm exec tsc as a package installation.

Limits the reviewer noted (not fixed, uncommon)

  • If the single real root is another component whose own template also starts with a comment, the outer component's $el is still that inner component's start marker.
  • Templates compiled in dev mode but run on the production runtime (the playground setup) have one more nested case the fix doesn't unwrap.

Requirements

  1. "templateRef.$el should point to the first real element, excluding comments": done; the new test covers it and passes.
  2. Clicking "Test" should log "Clicked Test" with the comment present: done. The listener is attached to $el, which is now the real div; the same test covers this.
  3. Removing the comment already works: unchanged. Without a comment there is no Fragment, so $el still comes from i.vnode.el, and the existing tests pass.
