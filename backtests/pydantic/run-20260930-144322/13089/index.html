Description

model_json_schema(mode="serialization") pattern for Decimal breaks on scientific notation

The serialization schema for Decimal fields generates a regex that rejects values that model_dump_json() itself produces.

Specifically: pydantic-core's serializer calls str() on Decimal objects, which outputs scientific notation for small/large values. E.g. Decimal('0.0000001') becomes "1E-7". But the pattern added in #11987 (^(?!^[-+.]*$)[+-]?0*\d*\.?\d*$) has no [eE] component, so it'll never match those strings.

As a result, any downstream consumer validating model_dump_json() output against model_json_schema(), such as OpenAPI validators and codegen + validation tools like Orval + Zod, will intermittently reject perfectly valid serialized values. Intermittent because only certain Decimal values trigger scientific notation.

v2.11:

{"anyOf": [{"type": "string"}, {"type": "null"}]}

v2.12:

{"anyOf": [{"pattern": "^(?!^[-+.]*$)[+-]?0*\\d*\\.?\\d*$", "type": "string"}, {"type": "null"}]}

Two possible fixes:

  • Append (?:[eE][+-]?\d+)? to the pattern in serialization mode
  • Normalize Decimal to fixed-point during serialization before it ever hits the schema

Example Code

import json
import re
from decimal import Decimal
from pydantic import BaseModel

class MyModel(BaseModel):
    value: Decimal | None

schema = MyModel.model_json_schema(mode="serialization")
pattern = next(
    v for v in schema["properties"]["value"]["anyOf"] if v.get("type") == "string"
)["pattern"]
regex = re.compile(pattern)

# pydantic serializes this as "1E-7" which fails its own schema's pattern
m = MyModel(value=Decimal("0.0000001"))
serialized = json.loads(m.model_dump_json())["value"]

print(f"Pattern: {pattern}")
print(f"Serialized: {serialized!r}")
print(f"Matches: {bool(regex.match(serialized))}")
# Pattern: ^(?!^[-+.]*$)[+-]?0*\d*\.?\d*$
# Serialized: '1E-7'
# Matches: False

What the agent reported

The Decimal JSON schema pattern now accepts scientific notation, so values like "1E-7" from model_dump_json() match the schema's own pattern. The JSON schema and docs tests pass.

What was wrong: pydantic-core serializes Decimal with str(), which switches to scientific notation for very small or large values (Decimal('0.0000001') becomes "1E-7"). The pattern for an unconstrained Decimal in get_decimal_pattern (pydantic/json_schema.py, around line 764) had no exponent part, so it rejected those strings.

What I changed:

  • The fix: one line in that no-constraints case. The pattern is now ^(?!^[-+.]*$)[+-]?0*(?:\d+\.?\d*|\.\d+)(?:[eE][+-]?\d+)?$. Just appending (?:[eE][+-]?\d+)? to the old pattern would also have matched junk like "e5", so the number part now requires at least one digit. Every valid number the old pattern accepted still matches (0, 00, 1., .5, -0.5, +3).
  • Both modes: the change applies to validation and serialization schemas, since they share this string and validation accepts "1E-7" too.
  • Existing tests and docs: 15 places in tests/test_json_schema.py and 2 in docs/concepts/json_schema.md checked the exact old pattern text. I replaced only that string; nothing was skipped or loosened.
  • New tests in tests/test_json_schema.py:
  • test_decimal_pattern_matches_serialized_scientific_notation is the report's scenario: a value: Decimal | None model, the pattern from model_json_schema(mode='serialization'), and a full match of model_dump_json() output for 1E-7, 1E+30, -1.5E-10, 12.34, -0.5 and 100. It also asserts the first three really serialize with an E.
  • test_decimal_pattern_reject_invalid_scientific_notation checks the new pattern still rejects '', -, ., e5, E, 1e, 1e+, abc and 1.2.3.

Test evidence:

  • ./bt-test tests/test_json_schema.py tests/test_docs.py tests/test_types.py tests/test_main.py: 1725 passed, 131 skipped, 3 xfailed, 0 failures.
  • After the reviewer's cleanups, ./bt-test tests/test_json_schema.py tests/test_docs.py: 1188 passed, 103 skipped, 1 xfailed.
  • Before-fix check: I didn't run the test file against the old code. Instead I ran Python's re.fullmatch on the old and new patterns: 1E-7, 1E+30 and -1.5E-10 fail the old one and pass the new one, so the new test would have failed before the fix.
  • ruff isn't installed here, so lint wasn't run. The reviewer's style points (an extra blank line, re.match instead of the file's usual re.fullmatch) are fixed.

Requirements:

  1. Serialization pattern rejects "1E-7": fixed, covered by the regression test above.
  2. Fix option 1, add an exponent to the pattern: done, in a slightly stricter form so "e5" isn't accepted.
  3. Fix option 2, serialize Decimal without scientific notation: not done. That output comes from pydantic-core, not this repository, and changing it would alter the JSON every user currently gets. The pattern fix resolves the mismatch on its own.
  4. The report's example (Decimal | None, serialization mode, 1E-7): covered by the regression test.

Still open (not in the report):

  • Fields with max_digits or decimal_places: these use separate patterns I didn't change, and they still reject scientific-notation output (e.g. Decimal('1E+3') with decimal_places=2 serializes as "1E+3"). Counting digits across an exponent isn't practical in a regex.
  • NaN and Infinity: these were already rejected by the old pattern and still are.
