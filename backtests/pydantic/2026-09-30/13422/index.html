Description

pydantic_core.to_json (and to_jsonable_python) documents timedelta_mode and temporal_mode as independent parameters governing disjoint type sets:

  • timedelta_mode: How to serialize timedelta objects, either 'iso8601' or 'float'.
  • temporal_mode: How to serialize datetime-like objects (datetime, date, time), either 'iso8601', 'seconds', or 'milliseconds'.

(This is what both the API docs and the shipped _pydantic_core.pyi type stub say.)

Given that contract, to_json(..., timedelta_mode="float", temporal_mode="iso8601") should serialize datetime/date/time as ISO 8601 strings and timedelta as a float. Instead, datetime/date/time are also coerced to unix-timestamp floats, timedelta_mode="float" silently overrides temporal_mode="iso8601" for all temporal types.

There is no combination of the two parameters that yields ISO datetimes with float-second timedeltas, even though the documented parameters imply there should be.

Root cause / regression. This regressed in #1743. Before that PR, SerializationConfig had a dedicated timedelta_mode: TimedeltaMode field and to_json had no temporal_mode parameter, so timedelta_mode was genuinely independent. #1743 replaced the dedicated field with a single unified temporal_mode and retrofitted timedelta_mode as a legacy alias that maps into it.

Either the docs/.pyi should be corrected to state that timedelta_mode is a deprecated alias that affects all temporal types, or (preferably) timedelta should retain an independent setting so the documented behavior holds. Personally I have a requirement to be able to set the timedelta format independent of the other datetime types.

Example Code

import datetime
import pydantic_core

payload = {
    "dt": datetime.datetime(2026, 7, 9, 12, 0, 0),
    "d": datetime.date(2026, 7, 9),
    "t": datetime.time(12, 0, 0),
    "td": datetime.timedelta(hours=1, minutes=30),
}

# Per the docs: temporal_mode governs dt/d/t; timedelta_mode governs td.
actual = pydantic_core.to_json(
    payload, timedelta_mode="float", temporal_mode="iso8601"
).decode()

expected = '{"dt":"2026-07-09T12:00:00","d":"2026-07-09","t":"12:00:00","td":5400.0}'

print("actual  :", actual)
print("expected:", expected)
assert actual == expected, "timedelta_mode='float' wrongly coerced datetime/date/time to floats"
# AssertionError: actual == {"dt":1783598400.0,"d":1783555200.0,"t":43200.0,"td":5400.0}

What the agent reported

I fixed it: timedelta_mode now affects only timedelta values, and datetime/date/time follow temporal_mode alone. The report's example now prints the expected output, and the targeted tests pass.

What was wrong. Since #1743, SerializationConfig in pydantic-core/src/serializers/config.rs held one temporal_mode for every temporal type. from_args (behind to_json/to_jsonable_python) converted timedelta_mode into that shared mode whenever temporal_mode was 'iso8601', so timedelta_mode='float' made all temporal types floats. from_config did the same with ser_json_timedelta when ser_json_temporal wasn't set. That second path hit untyped (any_schema) values, so config-driven serialization had the same bug. Typed fields were already correct, because the dedicated timedelta serializer has its own setting.

What I changed (all uncommitted):

  • config.rs: added a separate timedelta_mode field to SerializationConfig. datetime/date/time now use only temporal_mode (or ser_json_temporal). For timedeltas, a temporal_mode other than 'iso8601', or ser_json_temporal in config, still takes priority as it did before; otherwise timedelta_mode/ser_json_timedelta applies. This matches the typed timedelta serializer (type_serializers/timedelta.rs).
  • infer.rs: the three timedelta code paths (Python/JSON-mode output, direct JSON output, dict keys) now read the new field.
  • Tests: three new tests in pydantic-core/tests/serializers/test_any.py:
  • test_timedelta_mode_float_does_not_affect_other_temporal_types is the report's exact example through to_json and to_jsonable_python.
  • test_ser_json_timedelta_float_config_does_not_affect_other_temporal_types covers the any_schema config path.
  • test_timedelta_mode_float_does_not_affect_other_temporal_dict_keys covers datetime and timedelta dict keys.

Test evidence:

  • Before the fix: I reproduced the bug (b'{"dt":1783598400.0,"td":5400.0}'). The test-writer built the unmodified code in a temporary worktree and all 3 new tests failed with datetimes as floats. That worktree has been removed.
  • After the fix: I rebuilt the extension (maturin develop --uv). The example prints {"dt":"2026-07-09T12:00:00","d":"2026-07-09","t":"12:00:00","td":5400.0}.
  • ./bt-test pydantic-core/tests/serializers pydantic-core/tests/test_json.py: 854 passed, 5 skipped, 1 xfailed, including the 3 new tests.
  • ./bt-test tests/test_json.py tests/test_datetime.py tests/test_serialize.py tests/test_json_schema.py: 911 passed, 4 skipped, 1 xfailed.
  • Not run: cargo fmt and cargo clippy, because those components aren't installed. The code compiles cleanly.

Blast radius. Before the fix, ser_json_timedelta='float' also made untyped (Any) datetimes into floats in config-driven serialization. That combination now gives ISO strings, which is the documented behavior. The existing timedelta, datetime, Any and JSON tests all pass.

Requirements:

  1. timedelta_mode='float' with temporal_mode='iso8601' gives ISO datetime/date/time and a float timedelta: done, covered by the first test.
  2. A way to set the timedelta format independently of other temporal types: done for to_json/to_jsonable_python and for config on Any values; typed fields were already independent. Covered by the first two tests.
  3. Report's alternative, correcting the docs to call timedelta_mode a deprecated alias: not done, because the preferred option was implemented. The .pyi wording (lines 452 and 537) already describes the new behavior, so no doc change was needed.
  4. Behaviour not in the docs: a temporal_mode of 'seconds' or 'milliseconds' still applies to timedeltas as well. I kept it so existing callers don't break. No test covers it; I didn't add one because it would pass both before and after the change.
