Experimental Codex tool validates JSON parameters in Python mode, so strict parameters are rejected

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Patch A applies the fix the issue asks for at the root: `_parse_tool_input` in codex_tool.py now validates the raw string with `model_validate_json`, so a user-supplied strict `parameters` model accepts the JSON values its advertised schema describes while still rejecting mistyped values. It keeps the pre-existing `json.loads` pass only to preserve the distinct malformed-JSON error path, and adds tests covering date/datetime/UUID/Enum/tuple acceptance, continued rejection of `["1","5"]` for `tuple[int,int]`, empty input, and an end-to-end invocation with a strict model. The agent.py change applies the same one-line fix to the `as_tool` structured-input path with its own tests; it is extra scope but small, consistent with the issue's stated remedy, and low-risk. All seven independent tests fail on base and pass on A.

Patch B does not fix the reported behaviour. It adds an opt-in `parameter_validation_mode` option that defaults to "python", so the default codex tool still rejects every strict argument its own `params_json_schema` advertises, exactly as reported; all seven independent tests still fail with `Invalid JSON input for codex tool`. It also widens the public API (`CodexToolOptions` field, new keyword argument, new UserError), changes `_parse_tool_input`'s signature, and does a redundant second decode in the error path, all to avoid the one-line change the issue identifies. Its tests exercise the new flag rather than demonstrating the default path works. B masks the symptom behind configuration rather than correcting the format-aware validation, so A wins decisively on correctness, with better targeted tests and less API churn.

The issue

View on GitHub

Summary

@function_tool parameters are validated in Pydantic's Python mode, which rejects the JSON representation of strict fields — date, datetime, UUID and Enum arrive as strings, tuple as an array. Every argument the tool's own params_json_schema advertises is refused and the tool never runs. A patch is up as a pull request (see below); this issue tracks the same defect in one place the patch does not touch.

Where it also happens

src/agents/extensions/experimental/codex/codex_tool.py:549:

return parameters_model.model_validate(json_data)

Same shape: a JSON payload validated with the Python-mode entry point. parameters_model comes from resolved_options.parameters (codex_tool.py:316), so it is user-supplied — passing a model with ConfigDict(strict=True) reproduces the rejection there too. codex_tool.py:323 also broadcasts ensure_strict_json_schema(parameters_model.model_json_schema()), so it advertises the same JSON values it then refuses.

Why the fix is not in the patch

The patch that fixes this for @function_tool is scoped to function_tool and its own tests. This path is an experimental extension in a different module, and mixing the two would make the change harder to review than either one alone.

The fix is the same one line: validate the raw JSON string with model_validate_json rather than constructing from decoded values. Pydantic's strictness is input-format aware — in JSON mode a strict field accepts its JSON representation while still rejecting values the schema cannot express — so the user's strict setting keeps its meaning.

Related

  • #5448 — the @function_tool case, with the pull request.
  • The model-output path (AgentOutputSchema.validate_json), handoff input_type, and the sandbox tools already validate their JSON payloads in JSON mode; these two are the remaining callers that validate a JSON payload in Python mode.
