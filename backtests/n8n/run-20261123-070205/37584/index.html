In this judgment, Patch A = our agent, Patch B = the merged fix.

Root cause: the VM expression engine's __prepareForTransfer converts Luxon DateTime/Duration/Interval to ISO strings at the isolate boundary, so Set's resolveRawData (which only quotes via JSON.stringify when the value is an object) now splices a bare timestamp into the JSON text. Patch B fixes this at the boundary: Luxon values cross as typed marker objects and the host rebuilds real DateTime/Duration/Interval instances in both the isolated-vm and QuickJS bridges, restoring the contract the legacy engine (2.33.3) honoured. Set and every other consumer of evaluateExpression then behave as before; the Set raw-mode test with a DateTime value and the engine integration tests ($now, plus(-24,'hour'), nested values, invalid instances) would fail before and pass after. Patch A instead patches two consumers (Set and Form JSON templates) with a heuristic in resolveResolvables that sniffs resolved strings: if a string is not valid JSON but parses as a Luxon DateTime/Duration/Interval ISO and sits outside a JSON string literal, it is quoted. That fixes the issue's exact inputs and its tests are real, but it masks the symptom: the engine still returns strings, any other code expecting DateTime objects stays broken, and correctness rests on string sniffing and a hand-rolled JSON string-literal tracker rather than on the value's type. Scope and risk cut against B: it reverses an explicit design (deleting the 'Luxon serialization at boundary' tests and the helper TODO that anticipated string results), rewrites the QuickJS escaping logic, adds a pre-walk over every result, and its zone handling (falling back to 'local' when no zone name is carried) is not verifiable here. The independent test harness crashed on all three trees, so it provides no discrimination. Weighing correctness first, B resolves the regression at its origin while A only works around it in two call sites, so B is the better fix despite its size.
