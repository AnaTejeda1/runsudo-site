Concurrent TypeAdapter construction raises RuntimeError on free-threaded Python

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the root cause the same way: `_decorator_infos_for_class` iterates over a snapshot of the class `__dict__` instead of the live view. Patch A uses `list(vars(typ).items())` and Patch B uses `vars(typ).copy().items()`; both take the snapshot atomically on the underlying dict. Both also harden `LazyLocalNamespace.data`. Patch A snapshots every namespace, while Patch B copies only `MappingProxyType` namespaces. Patch A additionally hardens the `vars(annotation)` iteration in `_known_annotated_metadata`. On correctness for the reported issue, the two are roughly equal.

Tests are the clearest difference. Patch A adds two deterministic tests that fail before the fix on any CPython build, GIL or not. One mutates the class dict from a `__class__` property that `isinstance` triggers during decorator collection. The other mutates a namespace from a key's `__hash__` while `LazyLocalNamespace` merges namespaces. It also adds the concurrent reproduction from the issue. Patch B's tests are all concurrency stress tests, skipped unless the build is free-threaded, so they give no regression protection in ordinary CI and are probabilistic even where they run.

On scope, Patch B also rewrites `BaseModel.model_rebuild`. It replaces the conditional `delattr` of the core schema, validator and serializer with `set_model_mocks` when the model is already complete. That is a behavioral change to a different code path, unrelated to the reported TypedDict/TypeAdapter race, and it adds regression risk. It also brings a new test file and conftest changes with it.

Patch A is the tighter, lower-risk fix and has better-targeted tests that fail before the change.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Description

Constructing separate TypeAdapter instances concurrently for the same new TypedDict can raise RuntimeError: dictionary changed size during iteration on free-threaded Python.

A full run produced 91 failures in 800 attempts with the GIL disabled and none with PYTHON_GIL=1. It also reproduces on Pydantic main at 1c8a330acc3077e77da64e3672c7c875fb4c6eaa.

Lazy annotation evaluation adds __annotations_cache__ while another thread iterates vars(typ).items() in _decorator_infos_for_class.

Example Code

from __future__ import annotations

import threading
from concurrent.futures import ThreadPoolExecutor

from pydantic import TypeAdapter
from typing_extensions import TypedDict


def run_round() -> None:
    class Record(TypedDict):
        value: int

    for index in range(1000):
        setattr(Record, f'metadata_{index}', index)

    barrier = threading.Barrier(8)

    def build(_: int) -> None:
        barrier.wait()
        TypeAdapter(Record).validate_python({'value': '42'})

    with ThreadPoolExecutor(max_workers=8) as executor:
        list(executor.map(build, range(8)))


for _ in range(100):
    run_round()

The synthetic attributes only widen the iteration window. They are not modified after the threads start.
