Add config option security.http.proxyFromEnvironment = false

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the default case the same way. Each adds `security.http.proxyFromEnvironment` (default false) and sets `base.Proxy = nil` unless it is enabled. With the flag off, the dial-time `CheckAllowedHTTPAddress` therefore sees the real destination again, which is the core of the issue. Both update the TOML output test, docs.yaml and the security docs.

The difference is what happens when the flag is enabled.

- **Patch A** sets `Proxy = http.ProxyFromEnvironment` but keeps the dial-time control hook on every dial, including the dial to the proxy. Its own docs admit that with the default `http.urls` policy, a proxy on a loopback or private address is denied. Corporate and CI proxies are very often on private addresses, so the opt-in is largely unusable in exactly the setting the issue describes.
- **Patch B** makes the opt-in work as intended. It resolves the proxy per request, carries it in the request context, and skips the address check only when the dial address matches that request's proxy (`canonicalAddr`). All other direct dials, including a direct request to the proxy's own address, are still validated. This scoping is careful and keeps the hardening intact for non-proxied traffic.

Tests: Patch A's transport test only checks whether `tr.Proxy` is nil or non-nil. That does fail before the fix, but it is shallow. Patch B's test is behavioral, using real httptest proxy and target servers with hit counters. It shows the proxy is ignored by default, used when enabled even under the hardened policy, and that loopback destinations, including the proxy's own URL, are still denied on direct dials.

Scope and craft: Patch B is more complex. It adds a wrapper `RoundTripper`, the `x/net/httpproxy` package, and a doc paragraph on `http.urls` that goes slightly beyond the ask. However, the code is well commented and the complexity serves the feature's correctness rather than obscuring the fix.

On balance, Patch B delivers a working, well-tested option, while Patch A's enabled mode is self-defeating for common proxy setups.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

View on GitHub

This is a security hardening issue.

In d6e6f9e500eebdeae8e28de830fff2e3bfc7d534 (unreleased) we added a dial-time URL validation.

If proxied (e.g. HTTPS_PROXY set on users machine or in CI) the above validation will only see the proxy address. There's no workaround for that, but I suggest by adding a new security.http.proxyFromEnvironment bool config flag (default disabled).

Thanks to @Reload3d for reporting this issue.
