Reduce quadratic string assembly in streamed response parts

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches attack the root cause the same way — per-part `_string_buffers` of string deltas materialized lazily — and both keep incomplete tool args out of `get_parts()` so the issue's benchmark stays linear. The decision turns on correctness and tests.

Correctness: Patch A is elegant (apply metadata with content zeroed, buffer the content, so callback atomicity and event payloads come 'for free'), but it has two real defects it never addresses. (1) It declares `_string_buffers` with `repr=False` but WITHOUT `compare=False`, so the dataclass's auto-generated `__eq__` compares raw buffer lists. Since materialize is non-destructive (it never writes the joined value back into `_parts`, which stays at content=''/args=''), two managers that streamed identical final content with different chunk boundaries (e.g. ['he','llo'] vs ['hello']) now compare unequal — a behavior regression versus the original where equality depended only on final content. (2) For the same reason, the auto `__repr__` prints stale empty content. The issue explicitly lists equality and repr as validation gates; Patch A fails them. Patch A is also less faithful on dict→str args transitions: it blindly does `replace(args_delta='').apply` and would drop existing dict args, whereas Patch B falls back to a full `apply` when current args are a dict. Patch B addresses all of these (compare=False plus materializing `__eq__`/`__repr__`, atomic rollback on typed-promotion and callback failure, snapshot isolation, dict-vs-str guards).

Tests: Patch B adds a large suite of deterministic, mechanism-focused tests using spies to assert that `apply`/`_materialize_part` are NOT called during buffering, plus atomicity, reentrancy, isolation, and equality/repr — all fail-before/pass-after and mapping directly onto the issue's stated validation. Patch A ships a single timing-based scaling test (`large < small*8`), the most fragile kind, whose only non-timing assertions are correctness of the joined output.

Scope favors A (B is much larger, adds `__eq__`/`__repr__` overrides, and a `__repr__` with mutation side-effects is a genuine smell and a risk). Craft is mixed: A's core mechanism is cleaner, but it leaves `_parts` permanently stale and has the equality oversight; B is complex but its complexity is largely in service of the transparency properties the issue demands, and its tests give real confidence. Weighing correctness first, then tests, B's fidelity on the equality/repr/atomicity contract plus its far stronger deterministic tests outweigh A's smaller footprint. It is a real tradeoff, not a tie, and B is the better fix.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The issue

View on GitHub

Problem

ModelResponsePartsManager currently applies each text, thinking, and string tool-argument delta by building a new complete string. For a long response split into many small chunks, this copies the accumulated prefix on every chunk, so assembly time grows quadratically with the number of chunks.

This is provider-independent because streamed model responses share the same parts manager.

Measurement

I measured current main at 3adb9b0260383d0f9f2b2a9433f07e1ecfc768c1 and the final focused candidate using the locked repository dependencies. The primary metric is the sum of two median single-thread CPU workloads: 32,000 interleaved 16-byte deltas for text, thinking, and complete string-valued tool arguments, plus 12,000 incomplete tool-argument deltas with an intermediate public read after each delta.

MetricCurrent mainCandidateChange
stream_parts_assembly_cpu_ms1211.740 ms250.617 ms-79.32% (4.84x faster)

The candidate also scales approximately linearly when chunk counts double. A callable thinking-metadata workload measured 23.930, 47.729, and 95.103 ms at 4k, 8k, and 16k deltas; current main measured 26.425, 83.150, and 277.418 ms.

This measures local assembly CPU only, not provider or network latency.

Proposed approach

Keep private per-part lists of string deltas and materialize concrete strings when public reads or snapshots require them. Stream events still carry each delta immediately. Metadata and signature updates remain eager, failed metadata callbacks remain atomic, and replacing a part discards its old buffer.

There is no public API change. get_parts() and get_part_by_vendor_id() continue to return the same concrete part types and values. Incomplete tool arguments remain hidden from public parts without rebuilding the growing internal string on every read.

What the agent reported

All stages complete and confirmed by the reviewer. Here is the final report.

What was wrong

ModelResponsePartsManager (pydantic_ai_slim/pydantic_ai/_parts_manager.py) applied every streamed text, thinking, and string tool-argument delta by rebuilding the entire accumulated string (part.content + delta, (part.args or '') + delta) via dataclasses.replace. Each chunk copied the whole accumulated prefix, so assembling a response split into *n* chunks was O(n²) in CPU time. This is provider-independent because all streamed responses share this manager.

What I changed

pydantic_ai_slim/pydantic_ai/_parts_manager.py — introduced lazy per-part buffering:

  • Added _string_buffers: dict[int, list[str]]. Each streamed string delta is appended to the part's buffer (O(1)) instead of concatenated onto the stored part.
  • The stored part keeps its string field at the value it held when buffering began (empty for new parts), so it never grows. Metadata/signature updates stay eager by applying the existing *PartDelta.apply() with the string component emptied (content_delta=''/None, args_delta='') — this reuses the tested apply logic, so str/dict mismatch errors, delta→part promotion, tool_call_id back-patching, and atomic provider-details-callback failures are all preserved unchanged.
  • Added _materialize/_materialize_part to join a buffer only when a public read (get_parts(), get_part_by_vendor_id()) or a PartStart/promotion event needs the concrete string. get_parts() still filters out ToolCallPartDelta, so incomplete tool args are never materialized on a public read.
  • Overwrite paths (handle_tool_call_part, handle_part) now discard the replaced part's buffer.
  • Extracted _create_tool_call/_update_tool_call helpers (keeps handle_tool_call_delta under the mccabe limit). No public API change.

tests/test_parts_manager.py — appended test_stream_parts_assembly_scales_subquadratically, which streams many text/thinking/string-tool-arg deltas, asserts the fully-joined strings are correct, and asserts a 4× longer stream costs < 8× (quadratic ≈ 16×, linear ≈ 4×). get_parts() is inside the timed region so a lazy-but-still-quadratic materialize would also be caught.
