resources/images: Poor overlay quality when background image is an indexed (not true color) PNG

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the root cause of the issue: the paletted PNG source's palette was being forced onto the result of `Filter`, so overlay and text colors were clamped to the background's palette. Both regenerate the overlay and text golden images to match.

**Correctness.** Patch B is more precise. It quantizes to the source palette only when every filter in the chain cannot introduce new colors (`ImageProcessSpecProvider` such as resize, or orientation filters). Any other filter (overlay, text, grayscale and other color adjustments) disables quantization. So an indexed PNG passed through `images.Process "resize"` or an orientation filter stays indexed, matching normal Resize behavior. Patch A disables palette preservation for every `filter` action. That fixes the issue but changes output for Process/orientation filters on paletted PNGs, which now come out true-color.

**Scope.** Patch A also carries a sizable unrelated change. It switches hex color parsing from `color.RGBA` to `color.NRGBA`, rewrites `ColorGoToHexString`, normalizes `Color.init`, and changes `AddColorToPalette` equality. Its own comment cites a different issue. This churn changes behavior elsewhere: it alters an unrelated golden file (padding-transparent-chained.png) and modifies existing test expectations. That adds risk and obscures the actual fix.

**Tests.** Patch B adds a thorough integration test that would fail before the change and pass after it. It checks that:
- every opaque overlay pixel is reproduced exactly;
- the exact text color appears in the text result;
- the grayscale result contains only gray pixels;
- resize and Process outputs remain paletted.

Patch A's only coverage of the issue itself comes from the regenerated golden images. Its new unit tests cover the unrelated color change.

**Craft.** Patch B's explicit `keepSourcePalette` parameter is clear and well documented. Patch A's `ActionFilter` constant is tidy, but the fix is coarser.

Overall, Patch B is the better, more targeted fix with stronger tests.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Before getting into the details, I have verified that this is not an upstream issue with disintegration/gift. I tested with this:

<summary>main.go</summary>

package main

import (
	"image"
	"image/png"
	"log"
	"os"

	_ "image/png"

	"github.com/disintegration/gift"
)

func main() {
	// Get the background image (24 bit: indexed not true color)
	f, err := os.Open("background.png")
	if err != nil {
		log.Fatal(err)
	}
	bgImage, _, err := image.Decode(f)
	if err != nil {
		log.Fatal(err)
	}

	// Get the foreground image (24 bit with 8 bit alpha channel)
	f, err = os.Open("foreground.png")
	if err != nil {
		log.Fatal(err)
	}
	fgImage, _, err := image.Decode(f)
	if err != nil {
		log.Fatal(err)
	}

	// Create a new image with dimensions of the bgImage.
	dstImage := image.NewRGBA(bgImage.Bounds())
	// Copy the bgImage to the dstImage.
	gift.New().Draw(dstImage, bgImage)
	// Draw the fgImage over the dstImage at the (20, 20) position.
	gift.New().DrawAt(dstImage, fgImage, image.Pt(20, 20), gift.OverOperator)

	// Create the composite file.
	f, err = os.Create("composite.png")
	if err != nil {
		log.Fatal(err)
	}
	defer f.Close()

	// Encode the composite image.
	err = png.Encode(f, dstImage)
	if err != nil {
		log.Fatal(err)
	}
}

Details:

  • Background image is a 24 bit indexed PNG file with 256 colors in its palette
  • Foreground image is a 24 bit true color PNG with an 8 bit alpha channel
  • The final (composite) image seems to be limited to the palette of the background image
