Transition should sniff for teleport in custom components

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the root cause the same way. When a component's root is a <Teleport>, they forward the transition hooks to the teleported child element instead of leaving them on the Teleport vnode, which cannot be animated. Both use findNonCommentChild semantics, matching how BaseTransition already handles a direct Teleport child.

Patch B does this in one place, a new Teleport branch inside setTransitionHooks. That single branch covers both paths:
- the initial render path (renderComponentRoot calls setTransitionHooks(root));
- the leave/update path (the component branch recurses into subTree, which hits the Teleport branch).

It also handles nested component → component → Teleport chains naturally. Patch A instead repeats the `isTeleport(x) ? getInnerChild(x) || x : x` unwrapping at two call sites (renderComponentRoot and the component branch of setTransitionHooks) and exports getInnerChild to do it. This works, but the logic is scattered rather than centralized.

On the dev warning, Patch A keeps it meaningful for a Teleport with no element child. Patch B suppresses it for any Teleport root. This is a minor edge-case difference.

On tests, Patch B adds thorough unit tests in the existing BaseTransition style. They cover the full enter/leave lifecycle through a component with a Teleport root, check hook call counts and the element arguments, verify the element stays in the target until the leave finishes, and add an out-in mode case. These would fail before the fix. Patch A adds a useful e2e test plus unit tests. However, one of them (KeepAlive root) is unrelated to the issue, and the others only cover empty Teleport and hook updates rather than the core enter/leave behavior at the unit level.

Overall, Patch B delivers the fix more cohesively and with stronger targeted tests.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

This is a follow up from

  • #5836

My Intention in #5836 was, that a user should be able to do this:

<Transition>
  <CustomComp />
</Transition>

<!-- Custom Comp -->
<Teleport>
  <div></div>
</Teleport>

However, the fix for #5836 only allows:

<Transition>
  <Teleport>
    <div></div>
  </Teleport>
</Transition>

For me as a user those 2 should feel equivalent.
The way it is now is not really useful. If you are not gonna use a custom component inside transition, you could just easily swap teleport and transition around (which already worked before the fix):

<teleport>
  <transition>
    <div></div>
  </transition>
</teleport>

But the whole point of #5836 was to allow to transition any component that teleports internally.
And since nesting a custom component into a transition works already, teleport should just be transparent in this case

Usecase:

  • modals <transition><Modal /></transition>
  • popovers
  • ...

What the agent reported

<Transition><CustomComp/></Transition>, where the component's root is a <Teleport>, now animates the teleported element on enter and leave, and the warning is gone. The full ./bt-test run passes: 3637 passed, 6 skipped, 0 failed.

What was wrong: When a component sits inside <Transition>, its transition hooks are handed down to whatever the component renders at its root. The earlier fix for #5836 only unwrapped a <Teleport> placed directly inside <Transition>. When the Teleport was the component's root, the hooks stopped at the Teleport, which isn't a real element. So the <div> inside never animated, and Vue warned "Component inside <Transition> renders non-element root node that cannot be animated."

What I changed (code edits are uncommitted; nothing was committed):

  • packages/runtime-core/src/components/BaseTransition.ts, setTransitionHooks: if the node is a Teleport with children, the hooks now go to its first non-comment child. This is the same lookup the direct <Transition><Teleport> case already uses.
  • A first version also attached the hooks to the Teleport itself. Review caught that this breaks mode="out-in": removing the Teleport fires the "leave finished" step straight away, so the next child mounted before the old one finished animating out. I removed that line.
  • I also added a check so a Teleport with no children is skipped instead of crashing.
  • packages/runtime-core/src/componentRenderUtils.ts: the warning no longer fires when a component's root is a Teleport. The similar warning for directives is unchanged.

Tests (added to packages/runtime-core/__tests__/components/BaseTransition.spec.ts):

  • w/ component that renders Teleport as root: the reported scenario. It checks that enter and leave run on the teleported div, the div stays in the target until the leave finishes, and the warning is not shown. Before the fix it failed: no enter hooks were called and the warning appeared.
  • w/ component that renders Teleport as root (out-in): checks that the next component doesn't mount until the old one's leave finishes. It passes with the fix and fails if the hooks are also attached to the Teleport.
  • Both are unit tests. The original #5836 test is a browser (e2e) test, and ./bt-test can't run those. It also refuses arguments, so I ran it without them (the full suite); the subagents used vitest directly for single-file checks.

Requirements:

  1. "Both should transition in" (the reproduction): done. The first test covers enter, and I checked leave too.
  2. No warning in that case: done. Both tests assert it isn't shown.
  3. The Teleport should be transparent, so <Transition><CustomComp/></Transition> behaves like <Transition><Teleport>…</Teleport></Transition>: done. It reuses the same lookup, and the existing #5836 test and the rest of the suite still pass.
  4. Use cases (modals, popovers): these follow the same component-with-Teleport-root pattern, so the same tests cover them, including switching between components with out-in.

Known limitation: the warning is now silenced for any component whose root is a Teleport. That includes a Teleport whose first child is text or that has several children, cases that still can't animate. I left it that way to keep the change small.
