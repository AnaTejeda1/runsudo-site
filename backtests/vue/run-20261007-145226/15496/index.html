looseEqual: comparing Map/Set values with circular references throws RangeError (regression in 3.5.42)

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches stop the unbounded recursion by threading comparison state through `looseEqual`, `looseCompareArrays` and `looseCompareCollections`. Both cover Maps, Sets, arrays and plain objects, so both also fix the cyclic-object case the issue mentions.

Correctness:
- Patch A follows the issue's suggested approach. It tracks `(a, b)` pairs that are in progress and returns true when it meets one again, so it treats two structures as equal if they look the same no matter how far you follow them.
- Patch A also caches pairs already proven unequal. This is safe: optimistic 'true' assumptions can only make a result more equal, so a false result reached under them is genuinely false. The cache avoids repeating work in the matching loop for Set/Map entries, and A tests this with a densely cyclic 8-node Set graph.
- Patch B uses a stricter rule. It keeps two maps along the current path and only accepts a re-encounter if the same pairing reappears. This always terminates. However, it returns false for structures that look the same no matter how far you follow them but have a different cycle layout (e.g. `self.next = self` vs a 2-cycle). B tests that as intended behaviour, but it departs from the issue's stated expectation.
- Patch B has no protection against repeated work, so dense cyclic Sets can take exponential time in its candidate-matching loop.
- Patch B adds an optional third `seen` parameter to the exported `looseEqual`. That leaks internal state into the public signature and could misbehave if `looseEqual` is passed directly as a callback that receives extra arguments. Patch A keeps the public signature unchanged by wrapping a private `looseEqualImpl`.

Tests:
- Patch A adds unit tests for cyclic Sets, cyclic Maps (including a map containing itself), cyclic objects and arrays, unequal cases, and the dense-cycle performance case.
- Patch A also adds a component-level `vModel` test matching the reported `<select v-model>` scenario.
- Patch B adds unit tests only. They are reasonable but have no component-level test and no Map self-reference test.

Craft: Patch A's dispatch is a bit redundant (it checks Map/Set, then `looseCompareObjects` re-dispatches), but it is clear, uses try/finally, and is well commented. Patch B's `looseCompareNested` helper is tidy, but the API leak and missing performance guard weigh against it.

Overall, A is more faithful to the requested semantics, more robust, and better tested.

Steps to reproduce

Open the reproduction above: a <select v-model> whose option :values are Sets containing mutually-referencing objects. The component throws during mount, before any interaction.

<script setup>
import { ref } from 'vue'

const makeGraph = () => {
  const n1 = { id: 1 }
  const n2 = { id: 2 }
  n1.peer = n2
  n2.peer = n1  // circular reference
  return new Set([n1, n2])
}

const optA = makeGraph()
const optB = makeGraph()
const selected = ref(optB)
</script>

<template>
  <select v-model="selected">
    <option :value="optA">A</option>
    <option :value="optB">B</option>
  </select>
</template>

What is expected?

Mounting the select should not throw. looseEqual should safely terminate on cyclic structures (e.g. by tracking already-visited pairs) and return true for two structurally identical cyclic Sets/Maps.

Any additional comments?

This is a regression introduced by #15328 ("fix(shared): correctly compare Map and Set values", released in v3.5.42), which added looseCompareCollections in packages/shared/src/looseEqual.ts:

function looseCompareCollections(
  a: Map<any, any> | Set<any>,
  b: Map<any, any> | Set<any>,
) {
  if (a.size !== b.size) return false
  const candidates = Array.from(b)
  const matched = new Uint8Array(candidates.length)
  for (const item of a) {
    let index = -1
    for (let i = 0; i < candidates.length; i++) {
      if (!matched[i] && looseEqual(item, candidates[i])) {
        index = i
        break
      }
    }
    if (index < 0) return false
    matched[index] = 1
  }
  return true
}

looseEqual(item, candidates[i]) recurses into each [key, value] pair (Map) or element (Set), so a Map/Set whose entries point back to the collection itself or to each other causes unbounded recursion. Before 3.5.42, Maps/Sets never recursed into their entries (they fell through to String() comparison), so this exact code path — a <select v-model> with Map/Set values, which is precisely the scenario #15320/#15328 added support for — did not throw on 3.5.41; it silently compared wrong, which #15328 fixed.

Note: #5318 covers the same root cause for cyclic plain objects (pre-existing, still open). The Map/Set case is new in 3.5.42: cyclic Maps/Sets did not throw before.

Suggested fix: make looseEqual cycle-safe by tracking visited (a, b) pairs (e.g. with a WeakMap<object, Set<object>> and returning true on re-encounter), which also fixes #5318.

Additional local repro cases that all throw RangeError on current main:

  • looseEqual(new Set([a1, a2]), new Set([b1, b2])) where a1.peer = a2; a2.peer = a1 and b1.peer = b2; b2.peer = b1
  • looseEqual(mapA, mapB) where both maps hold mutually-referencing values
  • looseEqual(s1, s2) where s1.add(s1) and s2.add(s2)
