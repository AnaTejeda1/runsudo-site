Throw an error on createVNode with using innerHTML and children at the same time

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

The issue asks that a render function using `innerHTML` and children together not throw. It should render `innerHTML` when that prop is set and the children otherwise, including when the prop changes dynamically.

Patch B fixes this behavior in `patchElement`. When `innerHTML`/`textContent` goes from set to null or undefined, the old children's DOM has already been wiped. Patch B re-attaches it: it moves array children back into `el`, or restores the text children. The later children diff then runs against live DOM instead of detached nodes.

Patch B also tightens the condition from truthy to `!= null`, so an empty string still counts as a previously set prop. Its tests cover the reported mount case with `innerHTML: undefined`, which should no longer throw. They also cover toggling between a value and undefined/null with text children, with array children, and with a compiled block containing optimized children and a component. The block test also checks the component is not unmounted.

The repeated value → undefined toggles would likely fail on unpatched code, because the old children's DOM would be lost. These tests directly exercise what the user asked for.

Patch A changes no runtime behavior. It only adds a dev warning when a non-null `innerHTML`/`textContent` is combined with non-empty children. The tests are tidy and consistent, but they only check for the warning. They do not address the crash or the dynamic toggle the user described, and they do not make children render again after `innerHTML` is removed.

On correctness, which weighs most, Patch B addresses the actual problem and Patch A does not. Patch B carries some risk from moving vnodes during patch, but its block/component test reduces that concern.

What the agent reported

I fixed the bug, but the crash from the report no longer happens on this branch: mounting h('div', { innerHTML: undefined }, 'a') already renders <div>a</div> without an error. The part of the request that was still broken was switching dynamically. If innerHTML went from a value back to undefined/null while the children stayed the same, the element was left empty (<div></div>) instead of showing the children. The full suite passes with the fix (3654 tests, 0 failures, 6 skipped).

What was wrong: Setting innerHTML wipes the element's existing child DOM. When it was later unset, patchElement in packages/runtime-core/src/renderer.ts cleared the element and then compared old and new children. They were identical, so nothing was put back.

What I changed (renderer.ts, in the existing #9135 block of patchElement):

  • After clearing the element, the old children's DOM is put back in order: element and component children through move(child, el, null, MoveType.REORDER), text children by setting the text again. The normal children comparison then runs against live DOM.
  • The condition is now oldProps.innerHTML != null (and the same for textContent) instead of a truthiness check. An old value of '' also wipes the children, so it has to trigger the same restore.

My first version unmounted the old children and mounted new ones. The review found that this breaks compiled templates: a child component's live instance would be torn down while the template's update tracking still pointed at it, so later updates would never reach the page. I replaced that version with the one above.

Tests (new, in packages/runtime-dom/__tests__/patchProps.spec.ts; no existing tests changed):

  1. Mount with innerHTML: undefined and text children → <div>a</div>, no error.
  2. The same with array children → <div><span>a</span></div>.
  3. Toggle undefined → '<b>x</b>' → undefined → '<b>x</b>' → null with text children.
  4. The same toggle with array children.
  5. The compiled-template case: an innerHTML toggle inside a block, with a child component, then a second update to check the page still changes and the component is never unmounted.

Tests 3 and 4 failed before the fix (expected '<div></div>' to be '<div>a</div>'). Test 5 failed against my first version. All of them pass now. Tests 1 and 2 already passed before the fix; I kept them because they are the exact scenario from the report and guard against the old crash returning.

./bt-test refused file arguments (exit 64), so every run used the full suite.

Requirements:

  • h("div", { innerHTML: undefined }, "a") mounts without error: already true before my change (tests 1 and 2 passed beforehand); the __asyncLoader error never appeared in any run.
  • Use innerHTML when it is provided: covered by tests 3–5 (<div><b>x</b></div>).
  • Otherwise show the children: this was broken when switching back from a value. Fixed, and covered by tests 3–5 for undefined and null, with text children, array children, and the compiled case.
