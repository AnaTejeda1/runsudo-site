Transition should sniff for teleport in custom components

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the root cause the same way. When a component inside <Transition> renders a <Teleport> root, the transition hooks are moved from the teleport vnode onto its single inner child. Enter then fires when the teleport mounts its children, and leave fires when the teleport unmounts them.

Patch A puts this unwrapping in one place, `setTransitionHooks`. That single change covers three paths: the initial render through `renderComponentRoot`, the component branch that recurses into `subTree`, and any other caller. It also deliberately never sets hooks on the teleport vnode itself, so the teleport's start anchor is not treated as a leaving element. The dev warning is updated through `isTransitionRoot`, which allows comment-only content (a v-if switch inside the teleport) and nested teleports, and still warns when there are multiple children.

Patch B adds the same unwrap logic in two places, `renderComponentRoot` and the component branch of `setTransitionHooks`. It reuses `getInnerChild`, which picks the first non-comment child. When the teleport has no inner child, Patch B falls back to setting hooks on the teleport vnode. That matches the old behaviour for this edge case and does not improve it.

Tests: Patch A's unit tests check the full sequence of enter and leave hooks with the exact elements, and confirm that the teleported element stays in the target until leave completes. They also cover nested components, a v-if inside the teleport, disabled teleports, and the multiple-children warning. All of these would fail before the fix.

Patch B has a valuable e2e test that reproduces the issue with real class transitions. Its unit tests are weaker:
- The KeepAlive-root test is unrelated to the issue.
- The empty-teleport test only checks that nothing throws and that a warning appears.
- The hook-update test may pass even on the old code, because the hooks were previously attached to the teleport vnode.

Overall, correctness is roughly equal. Patch A's implementation is more centralized and handles edge cases more carefully, and its unit tests are more thorough and targeted, so A is the better patch.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

This is a follow up from

  • #5836

My Intention in #5836 was, that a user should be able to do this:

<Transition>
  <CustomComp />
</Transition>

<!-- Custom Comp -->
<Teleport>
  <div></div>
</Teleport>

However, the fix for #5836 only allows:

<Transition>
  <Teleport>
    <div></div>
  </Teleport>
</Transition>

For me as a user those 2 should feel equivalent.
The way it is now is not really useful. If you are not gonna use a custom component inside transition, you could just easily swap teleport and transition around (which already worked before the fix):

<teleport>
  <transition>
    <div></div>
  </transition>
</teleport>

But the whole point of #5836 was to allow to transition any component that teleports internally.
And since nesting a custom component into a transition works already, teleport should just be transparent in this case

Usecase:

  • modals <transition><Modal /></transition>
  • popovers
  • ...
