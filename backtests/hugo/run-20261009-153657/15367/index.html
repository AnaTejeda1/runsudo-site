The production code change is effectively identical in both patches: each wraps the `isSymlinkOrHasSymlinkParent` check in `if !rm.IsProject`, so main-project mount roots may be symlinks while theme/module mounts are still dropped. Correctness is equal, and the difference lies in tests and comments. Patch A's tests are more thorough and track the issue more closely. It adds a content mount whose source is a symlinked directory (`projectcontentlink` -> `projectcontentsrc`, mounted at `content/project-a`), which is the exact scenario in the issue, and asserts the page `p1/` is built. It also adds a nested symlink inside the symlinked project mount root (`rootdir/subdir/nestedsymlink.txt`) and verifies it is still excluded, both via `resources.Get` and via a `resources.Match` count of 3. This confirms the exemption only covers the mount root and does not weaken the per-file symlink filtering. Patch B covers only the assets mount root and parent cases, and does not test that nested symlinks remain blocked. A's code comment also states the security boundary more accurately ('Symlinks below the mount root are still dropped, see statRoot'). B's rationale, that absolute mount sources mean a symlink gains nothing, is reasonable but says less about what remains protected. Neither patch adds unrelated churn. A wins on test quality and clarity.

The issue

View on GitHub

Hugo 0.166.0 introduced commit https://github.com/gohugoio/hugo/commit/938c820626bd0a524dc1482cbe83b6c2e1171d20 (hugofs: Drop symlinked mount roots) that breaks a legit use-case of symlinks.

In my case, I mount a directory in my hugo.yaml:

module:
  mounts:
    - source: "content"
      target: "content"
    # Mount content generated in another repository
    - source: "_build/includes/project-a"
      target: "content/project-a"

_build/includes/project-a itself can be a symlink to another local directory, e.g. ../../../project-a, which allows quick local debugging. In production, a CI workflow may clone the Git repo of project-a to this destination which does not trigger the problem.

I am not familiar with the internals of hugofs and the security concept, but would appreciate if users could trust certain mounts, and therefore bypass the newly introduced hard drop of symlinks.
