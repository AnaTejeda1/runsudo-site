What the task asked

Add FastMCP (jlowin/fastmcp) and MCP's python-sdk (modelcontextprotocol/python-sdk) to pydantic's third-party test suite — the daily/labelled CI that runs downstream libraries' test suites against a local pydantic checkout to catch regressions.

What I found

The third-party test mechanism is not a Python test suite with a ./bt-test runner — it lives entirely in one GitHub Actions workflow, .github/workflows/third-party.yml. Each downstream library is a single job that: checks out the library, checks out pydantic into pydantic-latest, installs the library's deps, force-reinstalls pydantic/pydantic-core editable from ./pydantic-latest, then runs the library's tests. docs/contributing.md:264 directs contributors to request inclusion rather than documenting mechanical steps, so no docs change is required. There is nothing to reproduce with ./bt-test; the applicable gate for a workflow file is YAML validity plus fidelity to the in-file idiom.

What I changed (.github/workflows/third-party.yml, uncommitted)

  1. Added job test-fastmcp (jlowin/fastmcp) — uv-based, mirroring the existing FastAPI/FastDepends jobs: pinned action SHAs, the fork/third-party-tests-label guard, uv sync --locked, editable reinstall of both pydantic and pydantic-core, uv run --no-sync pytest tests, matrix Python 3.10–3.13.
  2. Added job test-mcp-python-sdk (modelcontextprotocol/python-sdk) — same idiom, using uv sync --locked --all-extras (the SDK ships optional extras) and uv run --no-sync pytest.
  3. Registered both jobs in the create-issue-on-failure job's needs: list and its if: failure-aggregation condition, keeping the boolean chain valid.

Network was blocked (backtest barrier), so I could not fetch the two projects' upstream workflows to copy exact sync flags; I modeled the jobs on the file's own established uv convention (uv sync --locked), which is the closest defensible match.
