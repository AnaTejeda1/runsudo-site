defineProps options object loses properties when using generics

Worse

The merged fix was judged better than our patch.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the root cause the same way. They replace the conditional `PropMethod<T>` with an unconditional function-like constructor type. The old conditional kept `PropType<T>` deferred when `T` was a generic parameter, so `RequiredKeys`/`OptionalKeys` could not resolve and non-required props were dropped from `ExtractPropTypes`. Correctness on the reported symptom (missing keys) is therefore equivalent.

Patch A goes one step further in `InferPropType`. In the `unknown extends V` / `keyof V extends never` branch, it falls back to `V` when `D` is `unknown`, instead of returning `D`. For a generic `T` this makes the inferred prop type `T` rather than an opaque `D`. The issue asks for "the props to be declared correctly", not just present as keys, so this matters. The change only alters results when `V` is an unresolved generic (for concrete `unknown`/`any`, `V` and `D` coincide or `IfAny` short-circuits), so it adds little risk.

Tests are the clearer differentiator. Patch B's test only asserts that `keyof typeof props` equals `'a' | 'b' | 'c'`. That covers the regression but not whether the prop types are right. Patch A asserts:
- the key set;
- the value types: `T | null` with a null default, `T` when required, `T | undefined` for shorthand, `string | undefined` for a non-generic prop;
- negative `@ts-expect-error` cases;
- assignability of `props` to `{ bar: T }`.

These would catch regressions that Patch B's test would miss.

Scope: Patch A's extra `InferPropType` tweak is small and well commented. Craft is similar; both explain why `PropMethod` must not be conditional. Overall Patch A is the more complete and better-verified fix.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

What the agent reported

I fixed the bug: inside a generic <script setup generic="T">, the optional props a and b from the report now show up on props. One thing is still open: those props' types stay unresolved for an unknown T, so const x: T | undefined = props.a still gives a type error (details below).

What was wrong

In packages/runtime-core/src/componentProps.ts, every PropType<T> includes a member called PropMethod<T>. It's what lets Function as PropType<(a: string) => void> compile. It was written as a conditional type that depends on T. When T is a generic, TypeScript can't evaluate that conditional yet, so it puts it off. The step that sorts props into required and optional was then put off too for a: Object as PropType<T>, and that took the whole required/optional split with it. As a result, keyof on the props lost every non-required prop: a and b disappeared. Only c stayed, because required: true decides it directly.

What I changed

  • The fix (componentProps.ts:75-82): PropMethod no longer depends on T. It is now always { new (): TConstructor; (): T; readonly prototype: TConstructor }. Before, this was what you got for function types and never for everything else. The new member is a narrower version of the { (): T } member that is already in the same union, so what you can assign to PropType<T> doesn't change. I added a 3-line comment explaining why it must not depend on T.
  • The test (packages-private/dts-test/setupHelpers.test-d.ts): a new describe('defineProps w/ runtime props + generics') block with the exact a/b/c case from the report. It reads props.a, props.b and props.c, and checks that the prop keys are exactly 'a' | 'b' | 'c'.

Requirements

  2. props.b ({ type: PropType<T> }) is declared: done; same test.
  3. props.c (required) stays declared, with no extra keys: done; the key check passes before and after.

For the same reason the test doesn't check the props' value types (expectType<T | undefined>(props.a)): that would fail even with the fix.
