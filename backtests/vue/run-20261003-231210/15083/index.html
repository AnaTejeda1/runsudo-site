EffectScope stop() causes runtime crash (Cannot read properties of undefined) when dynamic scope cleanup mutates parent.scopes array during traversal

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the root cause the same way. They iterate over a shallow copy of `this.scopes` in `pause()`, `resume()` and `stop()`, and over a copy of `this.effects` in `resume()`. This stops a sibling's self-removal from the parent's array from shifting indices or causing out-of-bounds access. On correctness they are effectively equal for the reported crash and for the resume/watcher variant.

Patch A also copies `this.effects` in `pause()` and `stop()`. In `stop()`, `_active` is already false, so watch handles don't remove themselves from `scope.effects`, and pausing an effect doesn't run user code. These extra copies are therefore unnecessary but harmless defensive hardening, and they neither add risk nor obscure the fix.

On tests, both include a regression test for the issue's scenario (a child cleanup stops a sibling during `parent.stop()`) that would throw before the fix. Both also include a test where a watcher stopping a sibling watcher during `resume()` would hit an undefined entry before the fix. Patch A's tests are more thorough:
- The stop test uses three children, stops the last sibling, and asserts that every child is inactive, every cleanup ran exactly once, and `parent.scopes` is emptied.
- It adds a nested-scope resume test, where an effect in child A stops sibling B during resume and the test checks that C still resumes and stays reactive afterward.
- Its watcher resume test checks that a third watcher still resumes and keeps firing.

Patch A's final onStop test likely passes even without the fix, so it adds little, but it does no harm. Patch B's tests are leaner and check fewer outcomes.

On craft, Patch A adds a short explanatory comment at the key site; otherwise the two are stylistically equivalent. With equal correctness, Patch A wins on stronger tests.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Steps to reproduce

Open the reproduction link.
Click the "Trigger сrash" button.
Observe the output status on the screen or check the browser console.

What is expected?

The parent scope should stop all its children successfully. When a child scope stops a sibling scope during the cleanup phase, the parent traversal loop should handle the array mutation gracefully without throwing errors.

What is actually happening?

The application crashes with the following error: TypeError: Cannot read properties of undefined (reading 'stop')

This happens because EffectScope.stop loops over this.scopes using a cached length l. During iteration, one child's onScopeDispose calls stop() on its sibling. The sibling removes itself from the parent's scopes array, reducing the array size. When the parent loop continues to the cached index l, it tries to access an element out of bounds (which is undefined), causing the runtime crash.

System Info

System: OS: macOS, Browser: Chrome, Node: v20.19.5

Any additional comments?

The bug lies in packages/reactivity/src/effectScope.ts.

Inside EffectScope, the methods pause(), resume(), and stop() loop over this.scopes using a cached length without accounting for array mutations. Creating a shallow copy of the array before iterating (e.g. const scopes = this.scopes.slice()) safely resolves the issue.
