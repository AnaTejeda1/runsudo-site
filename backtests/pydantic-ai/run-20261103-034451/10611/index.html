Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches make the independent tests pass for both capability orders, including the Shell `run_command` case, so both fix the reported BackgroundTools symptom. They differ at the root cause. Patch B implements the issue's second suggested fix: a private `_set_tool_metadata` phase that the agent dispatches before every capability's `prepare_tools`, routed through `CombinedCapability` and `WrapperCapability` and honoring deferred-loading via `_ctx_for_active_cap`. B keeps the wrapper toolset so tools added by later wrappers (e.g. CodeMode's `run_code`) are still tagged, and the double application is idempotent. Its tests cover BackgroundTools (both orders, True and 'optional', schema advertisement and foreground isolation), plus CodeMode and IncludeToolReturnSchemas metadata selectors, and wrapper-added tools. Patch A instead changes only BackgroundTools, moving its tool preparation from `prepare_tools` into a wrapper toolset ordered outside `SetToolMetadata`. A also had to special-case `defer_loading` because core skips hooks but not wrapper toolsets, a sign the approach fights the framework (though A does add a test for it). A's `wraps=[SetToolMetadata]` also would not help if SetToolMetadata is nested inside a WrapperCapability, which B handles. B's cost is a private hook on the abstract base and a pyright-ignore in the agent, which is modest and documented. On correctness, breadth of tests, and robustness, B is the better fix.

The issue

View on GitHub

What's wrong

The Background Tools docs say you can mark tools as background with SetToolMetadata instead of editing each tool. That doesn't work. The tool runs normally and the agent waits for it, with no error or warning.

Setting the same metadata on the tool itself does work. The difference is only in how the metadata gets there.

Example

from pydantic_ai import Agent
from pydantic_ai.capabilities import SetToolMetadata
from pydantic_ai.messages import ModelResponse, TextPart, ToolCallPart
from pydantic_ai.models.function import AgentInfo, FunctionModel
from pydantic_ai_harness import BackgroundTools


def build() -> str:
    return 'BUILD_OK'


def model(messages, info: AgentInfo) -> ModelResponse:
    if len(messages) == 1:
        return ModelResponse(parts=[ToolCallPart('build', {})])
    return ModelResponse(parts=[TextPart(messages[2].parts[0].content)])  # what the tool call returned


direct = Agent(FunctionModel(model), capabilities=[BackgroundTools()])
direct.tool_plain(metadata={'background': True})(build)

via_set_tool_metadata = Agent(
    FunctionModel(model), capabilities=[SetToolMetadata(tools=['build'], background=True), BackgroundTools()]
)
via_set_tool_metadata.tool_plain(build)

print('metadata on the tool:        ', direct.run_sync('go').output[:60])
print('metadata via SetToolMetadata:', via_set_tool_metadata.run_sync('go').output)

Output:

metadata on the tool:         Tool 'build' is running in background (task pyd_ai_403e609cd
metadata via SetToolMetadata: BUILD_OK

With the metadata on the tool, the model gets "running in background" straight away and the result later. With SetToolMetadata, the model gets the result straight away, so the tool ran in the foreground.

background='optional' fails the same way: the model is never offered the run_in_background argument. Changing the order of the two capabilities in the list makes no difference.

Why it matters

SetToolMetadata is the only way to mark tools you didn't write yourself. Harness's Shell is one example: there's no way to reach its run_command tool to set metadata on it. So today you can't let the model choose to run a long shell command in the background.

We found this while running a 75-second build in an E2B sandbox with Shell + SetToolMetadata(tools=['run_command'], background='optional') + BackgroundTools(). The model never saw run_in_background, the build ran in the foreground, and the model said so in its reply.

The only workaround is BackgroundTools(tools=['run_command']). It selects by name, so it doesn't depend on metadata. But then every run_command call runs in the background, including ls, and each one costs the model an extra turn before it sees the result.

Cause

A capability can change the tools the model sees in two places: its prepare_tools hook, or a wrapper toolset (get_wrapper_toolset). The agent runs every capability's prepare_tools first, then the wrappers around them (3, around line 3527).

BackgroundTools checks for background in its prepare_tools. SetToolMetadata adds background in its wrapper. So BackgroundTools checks before the metadata is there:

model asks for the tool list
  └─ SetToolMetadata wrapper              (runs second: adds background=True)
       └─ every capability's prepare_tools
            └─ BackgroundTools.prepare_tools   ← checks here: no background key yet

Other capabilities that read tool metadata in prepare_tools would have the same problem with SetToolMetadata. We haven't checked which ones do.

Possible fixes

  • Have SetToolMetadata add its metadata in prepare_tools instead of a wrapper, so that it runs alongside the others in list order. Users would need to put it before BackgroundTools.
  • Or apply SetToolMetadata before every capability's prepare_tools runs, so that any capability can rely on it, whatever the list order.

Either fix needs a regression test like the example above, for both True and 'optional'.
