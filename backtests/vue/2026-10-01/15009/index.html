v-model on <select multiple> uses stale collection type after switching between Array and Set

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the root cause the same way. Neither captures the collection type once in a closure inside `created`. Instead, each stores the current model state on the element and refreshes it in `beforeUpdate`. The change handler then reads the up-to-date value, so Array→Set and Set→Array switches both work in either patch.

Tests: both add tests that would fail before the fix and pass after it, and both cover both directions. Patch A puts the two directions in one sequential test. Patch B uses two separate, focused tests, which isolates any failure to a single direction slightly better.

Scope: both are minimal and touch only `vModelSelect`.

Craft is the deciding factor, and it favours B:
- Patch B adds a typed `_isSetModel?: boolean` field to the `ModelDirective` element type. This matches the existing `_assigning?: boolean` convention. It stores only the boolean the handler needs.
- Patch A uses `(el as any)._modelValue` casts with leading-semicolon statements. This bypasses the type system and departs from the surrounding typed pattern. It also keeps a reference to the whole model value on the DOM element when only its Set-ness is needed. The harm is minor, but it is less precise.

The behaviour is equivalent, but B is cleaner, type-safe, and more consistent with the codebase.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Steps to reproduce

  1. Bind a <select multiple v-model> to an Array.
  2. Switch the bound value to a Set at runtime.
  3. Interact with the select again.
  4. The emitted model becomes an Array again.
  5. Switching back from Set -> Array shows the same stale-type behavior in reverse.

What is expected?

The current collection type should be respected after the model switches at runtime.

What is actually happening?

The change handler keeps using the collection type captured when the directive was created, so the first user interaction after a runtime Array/Set switch emits the old type.

What the agent reported

I fixed it: after the bound value switches between an Array and a Set, <select multiple v-model> now emits the current type. Both directions are covered by new tests that failed before the fix and pass after it.

What was wrong: In packages/runtime-dom/src/directives/vModel.ts, vModelSelect.created checked once whether the value was a Set and kept that answer for the element's whole life. The change handler always used that first answer. So after a runtime switch, the next user selection emitted the old type.

What I changed (only in vModel.ts):

  • The Set check is now stored on the element as el._isSetModel. It is set in created and refreshed in beforeUpdate from the new bound value.
  • The change handler reads el._isSetModel instead of the value it captured at creation.
  • I added the optional _isSetModel?: boolean field to the element type, next to the existing _assigning. That type is shared by all the v-model directives, but only vModelSelect sets or reads the field. No existing code path was removed or put behind a condition.

Tests (added to packages/runtime-dom/__tests__/directives/vModel.spec.ts):

  • multiple select (model switches from Array to Set). Before the fix it failed with expected [ 'foo' ] to be an instance of Set.
  • multiple select (model switches from Set to Array). Before the fix it failed with expected Set{ 'bar' } to be an instance of Array.
  • After the fix, ./bt-test packages/runtime-dom/__tests__/directives/ passes 49 of 49, covering the vModel, vOn, vShow and vCloak specs. That includes the 2 new tests and the 28 vModel tests that were already there.

Requirements:

  1. Respect the current type after switching Array → Set: done. The first test above shows a Set is emitted on the first change after the switch.
  2. Same for Set → Array: done. The second test shows an Array is emitted.
  3. Change handler must not use the type captured at creation: done. It now reads the flag that beforeUpdate refreshes, as shown in the diff.

I didn't run the reviewer subagent; I read the four-line diff myself and found nothing outside the fix. No existing tests were modified, no scratch files were left, and nothing is committed.
