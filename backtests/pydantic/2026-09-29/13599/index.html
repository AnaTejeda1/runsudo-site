PEP 695 type aliases don't work with callable discriminators

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches take the identical root-cause approach: thread a `definitions` map into `Discriminator._convert_schema` and resolve `definition-ref` schemas against it when `handler` is None (the deferred/callable-discriminator path). Correctness is essentially equal for the reported scenario (M3). The one behavioral divergence is in the root `definition-ref` block when both `handler` and `definitions` are None: Patch A funnels everything through its `_resolve_ref` helper and then raises `MissingDefinitionForUnionRef` on any None result, whereas Patch B only raises inside each populated branch and safely skips the union-unwrap otherwise. Patch B's behavior more conservatively preserves prior fall-through for paths that don't supply definitions, avoiding a potential spurious raise. Patch A's shared helper is DRYer, but it also stamps `# pragma: no cover` on the LookupError path that the choice-resolution loop previously treated as covered/expected, a small coverage regression, and it conflates two callers with different error semantics. On tests, Patch B is meaningfully more thorough: it asserts both discriminator branches ('foo' and 'bar'), exercising the choice-resolution loop for multiple tags, while Patch A only checks the 'foo' case. Scope and structure are comparable. The edge weight goes to B for the stronger test and the safer non-raising guard; the difference is small but real, not a tie.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Description

New type aliases prefixed with the type keyword are not supported as the type annotation for a callable discriminator.

M1, M2, M4 ok
M3

pydantic.errors.PydanticUserError: `Tag` not provided for choice {'type': 'definition-ref', 'schema_ref': '__main__.TaggedAnyA:2210408548368'} used with `Discriminator`

What the agent reported

The fix is complete and verified. Here is my final report.

What was wrong

PEP 695 / referenceable type aliases (type X = ..., or the portable TypeAliasType(...)) failed when used as a field annotation with a callable Discriminator applied via Field(discriminator=...) — the M3 scenario in issue #13598:

pydantic.errors.PydanticUserError: `Tag` not provided for choice {'type': 'definition-ref', ...} used with `Discriminator`

Root cause: Discriminator._convert_schema (pydantic/types.py) could look through a definition-ref schema to find the union / Tag metadata only when a handler was available. The deferred code path — apply_discriminator in pydantic/_internal/_discriminated_union.py:68 — called _convert_schema(schema) with no handler and dropped the definitions map it had received. So the alias's definition-ref couldn't be resolved, the tag was never found, and the error fired. The direct Annotated[..., Discriminator] path passes a handler, which is why M1/M2/M4 worked.

What I changed

  • pydantic/_internal/_discriminated_union.py:68 — forward the definitions map: discriminator._convert_schema(schema, definitions=definitions).
  • pydantic/types.py Discriminator._convert_schema — added a definitions parameter; both the root-level and per-choice definition-ref resolution now fall back to the definitions map when handler is None. The root block raises MissingDefinitionForUnionRef on a missing ref (mirroring the string-discriminator path), which lets the existing deferral mechanism retry once definitions are ready; the per-choice block is best-effort.
  • tests/types/unions/test_discriminated_union.py — added test_discriminated_union_type_alias_type_field_callable_discriminator, reproducing M3 with a TypeAliasType union of Annotated[..., Tag(...)] members under Field(discriminator=Discriminator(...)).
