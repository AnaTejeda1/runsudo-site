resources/jsconfig: Address VS Code linting notice in jsconfig.json

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Patch A fixes the root cause. The VS Code notice fires because a mapping target is non-relative while baseUrl is unset. Patch A prefixes './' to every generated target that does not already start with '../', so all source roots become valid relative mappings. That includes the reported "*": ["*"] case, which becomes "./*", and nested roots like 'c/*', which become './c/*'. The '*' mapping is kept, so editors can still resolve non-relative imports such as 'js/util.js' from the assets directory. Without baseUrl, removing that mapping would leave those imports unresolved. Patch B instead skips the source root equal to the config directory. For the single-root example this makes Build return nil, so the lint warning goes away only because the mapping is gone, and the import-resolution benefit is lost with it. B also leaves the problem in place for any other root under the directory: Build('/a/b') with root '/a/b/c' still emits the non-relative 'c/*'. On tests, A adds a unit test covering same-dir, child and parent roots, plus an integration test that checks the exact jsconfig.json content. Both would fail before the fix. B adds only a nil-config assertion for the single-root case. Both patches are small in scope. A wins on correctness and on test coverage.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The issue

View on GitHub

When building a site that calls js.Build, the assets/jsconfig.json file looks like this:

{
 "compilerOptions": {
  "paths": {
   "*": [
    "*"
   ]
  }
 }
}

VS Code lints line 5 as follows:

Non-relative paths are not allowed when 'baseUrl' is not set. Did you forget a leading './'?
