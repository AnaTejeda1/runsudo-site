SessionSettings(limit=...) can pass an unmatched function_call_output to the model

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the reported scenario at the right layer (drop_orphan_function_calls, gated on a configured limit, restricted to history-origin indexes so caller-provided outputs survive), and both pass every independent test. The differences are at the edges.

Patch A adds a single additive flag (`drop_orphan_outputs`) and leaves the existing filtering loop intact; orphan outputs are dropped only for items already in `pruning_indexes`, which the existing code computes for both the no-callback path and the session_input_callback path. That makes output pruning consistent with the pre-existing orphan-call pruning: a user who combines `SessionSettings(limit=n)` with a `session_input_callback` still gets the fix, and A tests that explicitly. Its unit tests also cover type-mismatched call_ids, hosted tool_search pairs, and the interaction with reasoning-item dropping.

Patch B deliberately disables output pruning when a session_input_callback is present (`session_input_callback is None and limit is not None`) and adds a test locking that in, so the issue's bug still reproduces for limit + callback, even though the same function already prunes orphan calls from callback history. B does handle one extra edge better (an output whose call was dropped alongside an orphan program, via excluding dropped indexes when computing available call ids), but that scenario arises from an interrupted run rather than limit truncation, which is the issue's subject. B also rewrites the main loop (removing the `filtered` accumulator and changing the private reasoning-helper signature) and rewrites an existing test, which is more churn than the fix needs.

A's minor gap (present call ids are computed before orphan-call dropping) only matters in the program-owned edge case outside the issue. Weighing correctness in the issue's scenarios, test coverage of the limit-related paths, and minimal scope, A is the better fix by a modest margin.

The issue

View on GitHub

Describe the bug

When SessionSettings(limit=n) truncates stored history between a function_call and its corresponding function_call_output, the Runner can pass the output to the model without the matching call.

For example, given this stored history:

  1. user message
  2. function_call with call_id="call_1"
  3. function_call_output with call_id="call_1"
  4. assistant message

Using SessionSettings(limit=2) correctly retrieves the last two stored items, but the prepared model input still contains the unmatched function_call_output.

The existing model-input sanitization removes a retained call when its output is absent, but does not remove a retained output when its call is absent.

This report does not propose changing the exact item-count semantics of Session.get_items(limit=n) or introducing run/turn-aware session storage. The issue is limited to ensuring that the model input does not contain one side of a required call/output pair after history pruning.

Debug information

  • Agents SDK version: 0.19.4
  • Related library versions: openai==2.45.0, pydantic==2.12.3
  • Python version: 3.12.9
  • Operating system: macOS 26.6
  • Model and model provider: Local CaptureModel; no external provider is required to observe the prepared input
  • Does the issue reproduce with the latest Agents SDK release? Yes
  • Does the issue occur consistently or intermittently? Consistently when the limit boundary excludes the call but retains its output

No exception is raised by the local capture model. The malformed dependency is visible in the input prepared for the model:
