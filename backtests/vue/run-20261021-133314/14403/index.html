Preserve input values entered during hydration

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches use the same detection idea (directive `created` running on an element that already has a parentNode means hydration) and both defer the decision to `mounted`, which correctly covers the Suspense/async-deps case. The difference is coverage. Patch B only preserves input when `el.type` is exactly 'text' or 'textarea', so a v-model on type=email, password, number, search, url or tel is still reset after hydration, and checkboxes, radios and selects are untouched. The issue is about inputs and forms generally, and the independent tests confirm B still fails for email, checkbox and select while A passes all of them. B's `mounted` also calls `castValue(el.value, trim, number)` without the `type === 'number'` fallback that `created` uses, so a `<input type=number v-model>` would sync a string instead of a number. Patch A handles vModelText (with a cloned-node probe to distinguish browser sanitization from user input, e.g. color lowercasing and range clamping), vModelCheckbox (including shared array/Set models across several checkboxes synced in the same tick), vModelRadio and vModelSelect (single and multiple, with correct default-selection logic). Its test suite is substantial and targeted: typed text, modifiers, textarea, dynamic type, untouched inputs, boolean and true/false-value checkboxes, multiple checkboxes, radio, select single/multiple, sanitized values, and input during pending async hydration. A is considerably larger and the per-tick `hydrationModelValues` map for shared checkbox models is somewhat intricate, but it is scoped to the hydration path, documented, and exercised by tests. B's single test covers only the narrowest case. On correctness and tests A clearly wins; its extra breadth is in service of the issue rather than unrelated churn.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

after all browser resources loaded - input v-model reset to default value

entered input value is preserved once hydration completes

input value is reset to its default value

Any additional comments?

This is affecting UX when interacting with inputs/forms in slowly loading apps, where values entered during hydration phase are erased and the progress is lost. I have been blocking all forms myself until mounted hook fires to workaround this issue - it would be great to not have to!
