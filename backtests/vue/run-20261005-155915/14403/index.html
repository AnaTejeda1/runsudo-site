Preserve input values entered during hydration

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches use the same detection idea: in `created`, an element that already has a parent is being hydrated. In `mounted`, if the DOM value differs from the server-rendered default, the patch syncs the DOM value back to the model instead of overwriting it.

Patch B only applies this when `el.type` is 'text' or 'textarea'. It does not cover:
- other text-like input types handled by vModelText (email, password, search, number, tel, url);
- checkboxes, radios and selects, which are common in the forms the issue describes.

B also approximates the browser's value sanitization by hand with CR/LF regexes. Its only test is a single plain text-input case.

Patch A covers every v-model variant:
- **Text inputs:** handles all input types. It detects sanitization robustly by cloning the element and assigning `defaultValue`, so the browser's own sanitization is the reference (e.g. color lowercasing, range defaults). It respects the `.trim`, `.number` and `type=number` casts.
- **Checkboxes:** handles both boolean and array/Set models. It tracks sibling checkboxes that share one model during the same flush, so they do not overwrite each other's assignments.
- **Radios:** skips forcing `checked` in `created` when the user changed it, then syncs the checked radio in `mounted`.
- **Selects:** detects a changed selection for single and multiple selects, including the browser's implicit first-enabled-option default.

It refactors the change handlers into shared helpers without changing their behavior. Its tests are thorough and would fail before the fix: text, modifiers, textarea, sanitized types, dynamic type, checkbox bool/array, radio, select single/multi, and untouched fields staying reactive.

The module-level `hydratedCheckboxModels` map adds some complexity, but it is cleared on `nextTick` and is limited to hydration. Overall, A resolves the issue far more completely and is better tested, while B is a narrow partial fix.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Steps to reproduce

user loads a page with a slow internet connection
starts entering some values ​​into the input with v-model
after all browser resources loaded - input v-model reset to default value

What is expected?

entered input value is preserved once hydration completes

What is actually happening?

input value is reset to its default value

System Info

Any additional comments?

This is affecting UX when interacting with inputs/forms in slowly loading apps, where values entered during hydration phase are erased and the progress is lost. I have been blocking all forms myself until mounted hook fires to workaround this issue - it would be great to not have to!
