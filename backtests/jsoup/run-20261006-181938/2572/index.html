W3CDom drops some XML node types

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches convert CDataNode to CDATASection, convert `<?...?>` nodes other than `xml` to ProcessingInstruction, and walk the document's children so comments and PIs outside the root are kept.

Patch A changes less of the existing code. Doctype creation stays where it was, at document creation. A tracks whether a node came before the doctype and moves it in front when needed, so document order holds. It resets `builder.dest = out` before each top-level traverse, which avoids changing the delicate `tail` ascend logic. PI detection uses the real `isDeclaration` flag, exposed through NodeInternals, so `<!ENTITY>` declarations are excluded reliably.

Patch B is riskier:
- It removes doctype creation from `fromJsoup` and recreates the doctype only during whole-document traversal. As a result, `fromJsoup(Element)`, which previously got the owner document's doctype, silently loses it. That is a behavioural regression outside the issue's scope.
- It widens the `tail` ascend condition from `getParentNode() instanceof Element` to `!= null`. That logic exists to handle elements emitted as text, so the change adds risk.
- It detects PIs with `outerHtml().startsWith("<?")`, which is fragile and costly compared with using the flag.
- Its CDATA fallback is harmless.

On tests, Patch A is clearly stronger. It checks the exact child sequence and count at document level, ordering around a doctype, PIs inside elements, exclusion of the XML declaration and markup declarations, the source user data link, CDATA in both XML and HTML (SVG), subtree conversion, and serialized output. Patch B's three tests are thinner and do not check full child counts or exclusion of declarations.

Patch A is the safer and better-tested fix.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The issue

View on GitHub

W3CDom.fromJsoup(...) currently drops XML processing instructions and comments outside the root element, and converts CDataNode instances to ordinary text nodes.

All three have direct W3C DOM equivalents, so conversion should preserve them and their document order. XML declarations and doctype internal subsets remain out of scope.
