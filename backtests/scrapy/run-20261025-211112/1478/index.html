Adding support to FTP file listing

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches make a trailing-slash FTP URL perform a listing, and both pass all four independent tests. The differences are in what the listing is and how edges are handled.

Correctness: Patch A issues the FTP LIST command (via twisted's FTPFileListProtocol) and returns a JSON array of structured entries including filetype, size, and name. That matches the issue's wording ('calls FTP list') and actually enables the stated goal of scanning repositories, since a crawler needs to know which entries are directories to recurse. Patch B uses NLST, returning bare names one per line, which gives no way to distinguish files from subdirectories. Patch A also preserves the existing error semantics: a nonexistent directory raises CommandFailed and maps to a 404 like a nonexistent file does. Patch B's own test codifies that a nonexistent directory returns 200 with an empty body, indistinguishable from an empty directory, which is a regression in error reporting relative to the handler's existing conventions. Patch A also keeps ftp_local_filename working for listings and sets the response class to JsonResponse only when the body is the listing itself. Patch B does handle an empty path (ftp://host with no slash) where A would still call retrieveFile(''), a small point in B's favor.

Tests: Patch A adds four tests covering root listing (names, sizes, filetypes, headers), subdirectory listing with a quoted space in the path, nonexistent directory -> 404, and the local-filename path, and extends both fixture trees with a subdirectory so the dir/file distinction is exercised. Patch B adds two tests: root listing names only, and the nonexistent-directory-returns-200-empty behavior, which locks in the weaker semantics.

Scope/craft: Both update the docs. Patch A also updates the module docstring that describes the handler's response shape; B leaves it stale. A's local import inside the helper is slightly unusual but harmless. A's reliance on Unix ls-style LIST parsing is a portability caveat, but NLST's lack of type information is the bigger practical gap for the issue's goal.

Overall A resolves the issue more completely, with better error handling and substantially stronger tests.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Each saw the issue and the two patches, labelled A and B in random order (two of them saw ours as A), with issue links and version numbers removed. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours. The reasoning above is one judge's, shown verbatim.
