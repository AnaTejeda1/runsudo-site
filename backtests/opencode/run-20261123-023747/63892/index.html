Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches reach the behaviour the issue asks for: the packaged pwsh.exe ends up created without PROC_THREAD_ATTRIBUTE_JOB_LIST and then placed in the job via AssignProcessToJobObject while suspended, and both pass the independent test. They differ in how they get there and in what they verify.

Correctness: Patch A keeps the atomic job-list creation as the primary path and adds a fallback keyed on an `is_access_denied` check that accepts raw ERROR_ACCESS_DENIED plus the NTSTATUS/HRESULT-wrapped forms (0xC0070005, 0x80070005), which is exactly the missed case the issue identifies. The fallback creates the child suspended, assigns it to the job, resumes it, and only drops to jobless if assignment also fails, so the tree remains killable in the Store PowerShell case. Patch B removes the job list entirely and always does suspended-create + assign + resume. That also fixes the issue and is simpler, but it changes the spawn path for every process rather than the failing one, and its code comment attributes the failure to 'another process of that package is running', which contradicts the issue's standalone probe showing the job list fails unconditionally. B does add a Drop guard that terminates a never-resumed child, a nice robustness touch; A handles the only fallible step after suspended creation (resume) by terminating explicitly, so the practical gap is small.

Tests: A adds unit tests that run on any Windows CI box: `is_access_denied` is checked against the exact 0xC0070005 code from the issue plus negative cases, and `spawn_with` injects the job-list refusal so the suspended-create/assign/resume path is exercised, verified with IsProcessInJob, and shown to still kill the tree. These would fail on base (the functions do not exist) and pass after. B's single test returns early unless Store PowerShell is installed under LOCALAPPDATA, so on CI it is effectively a no-op and per the rules counts as no test; it also depends on `rand::random` and a `Process::kill` helper whose availability cannot be confirmed from the diff.

Scope and craft: A is the targeted change with a SPEC update that documents the new wrapped-code handling and the two-level fallback precisely. B's broader rewrite is defensible but earns no credit on its own and carries more blast radius; its SPEC edit drops the specific error documentation. A's diff also carries unrelated bun.lock churn, which I treat as lockfile noise per the ground rules rather than a substantive mark against it.

A wins on tests that actually run, on precisely matching the issue's root cause (the wrapped error code), and on a narrower behavioural change.

Description

Description

After updating OpenCode from 2.2.7 to 2.3.0 on Windows, shell tool calls using Microsoft Store PowerShell 7 fail before executing even a one-line command:

failed to spawn C:\Program Files\WindowsApps\Microsoft.PowerShell_7.7.0.0_x64__8wekyb3d8bbwe\pwsh.EXE:
OS Error -1073283067 (FormatMessageW() returned error 317) (os error -1073283067)

-1073283067 is 0xC0070005. Expected: the command executes and returns its output. Actual: process creation fails, in both a project directory and a separate temporary directory.

Isolated Win32 reproduction

A standalone C# P/Invoke probe, independent of OpenCode/plugins, called CreateProcessW for the same packaged executable with -NoLogo -NoProfile -NonInteractive -Command "exit 0" and CREATE_NO_WINDOW. Changing only the job attachment strategy produced:

Creation strategyStore PowerShell 7.7Windows PowerShell 5.1
No explicit job attributeSuccess, exit 0Success, exit 0
STARTUPINFOEXW + EXTENDED_STARTUPINFO_PRESENT + PROC_THREAD_ATTRIBUTE_JOB_LIST containing one newly created unnamed jobFails: 0xC0070005Success, exit 0
Normal creation, then AssignProcessToJobObjectSuccess, assignment succeeds, exit 0Success, exit 0

Three additional consecutive rounds reproduced the same Store executable results. Normal ProcessStartInfo creation also succeeds for both the real packaged EXE and its app-execution aliases. Get-AppxPackage Microsoft.PowerShell reports Status=Ok and IsPartiallyStaged=False.

At the failing timestamps, Microsoft-Windows-AppModel-Runtime/Admin records:

  • Event 212, 0x80070005: cannot add the process to the package's Desktop AppX container.
  • Event 208, 0x80070005: cannot create the package process while configuring its runtime, [FinishPackageActivation].

Relevant implementation

The running shell process is launched through opencode-pty 0.5.2, in pipe mode. The current Windows pipe implementation supplies PROC_THREAD_ATTRIBUTE_JOB_LIST during CreateProcessW.

Its jobless retry only accepts raw ERROR_ACCESS_DENIED (5); the packaged EXE returns 0xC0070005, so that retry is skipped. The standalone probe returns 5 when given the app-execution alias instead of the real packaged path. This error-code distinction appears relevant to the missed fallback.

The 2.2.7 shell service directly spawned commands; 2.3.0 delegates local commands to the process daemon. Related introduction: #63196; follow-up: #63346. The previous 2.2.7 binary was not rerun during this diagnosis, so the version boundary is based on observed upgrade history and source comparison, not a binary bisect.

This differs from closed #62512: that issue returned exit 0 with empty output through the Store alias; this one fails to create the real packaged process.

Workaround verified: explicitly selecting Windows PowerShell 5.1 restores shell execution. MSI/ZIP PowerShell 7 was not installed or tested. No WindowsApps ACL changes or package repairs were made.

Plugins

@tarquinen/opencode-dcp@latest, oh-my-opencode-slim. OpenCode itself was not retested with plugins disabled; the standalone Win32 probe has no plugin dependency.

OpenCode version

opencode v2.3.0, latest/release channel, installed through Scoop; managed serve --service process. Process daemon: opencode-pty 0.5.2.

Steps to reproduce

  1. On Windows, use Microsoft Store PowerShell 7 (observed package: Microsoft.PowerShell_7.7.0.0_x64__8wekyb3d8bbwe), with OpenCode 2.3.0 selecting that shell.
  2. Ask the shell tool to run Write-Output 'probe'.
  3. Observe the spawn failure above, before any command output. Changing the working directory does not help.
  4. For an API-level comparison, create that same EXE with and without PROC_THREAD_ATTRIBUTE_JOB_LIST, as described in the table.

Operating System

Windows x64, Windows_NT 10.0.26300 ([Environment]::OSVersion: 10.0.26300.0). Store PowerShell reports 7.7.0. System Windows PowerShell reports 5.1.26100.9818.

Terminal

Exact frontend terminal application unavailable. Shell-tool environment has TERM=xterm-256color (injected by OpenCode); TERM_PROGRAM, COLORTERM, and WT_SESSION are unset. ComSpec=C:\WINDOWS\system32\cmd.exe.
