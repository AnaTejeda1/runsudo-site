[Bug]: /tag/update 500s "BudgetNewRequest() got multiple values for keyword argument 'budget_id'" on any tag that has a budget

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches apply the identical root-cause fix the issue suggests: drop budget_id from the LiteLLM_BudgetTable field set so it is no longer copied into _budget_data and collides with the explicit budget_id kwarg in the existing-budget branch. Independent tests confirm both resolve every scenario, including the access-group path. The difference is in the follow-through. Patch B also changes the update branch so that when a different budget_id is sent alongside budget settings, those settings are written to the budget the entity is being re-pointed at rather than to the budget it is leaving. With Patch A, that combination (previously unreachable because it 500'd) would mutate the old budget and then re-point, which silently edits a budget the tag no longer uses; the issue's expectation that a different budget_id re-points the tag makes B's semantics the coherent one, and since the path never worked before there is no regression risk for existing callers. On tests, B is stronger: it covers the helper for same/different budget_id, exercises /tag/update end-to-end with a four-case parametrization asserting both the tag-row re-point and which budget row receives the settings, and adds two access-group tests for the second affected endpoint the issue calls out. Patch A adds one helper unit test and an integration test that depends on a tests/integration/_support/client module whose existence cannot be confirmed from the diff, and does not cover the re-point or access-group cases. Scope-wise B's extra behavioral change is small, well-commented, and tested, so it does not obscure the fix. B wins on tests and on handling the edge the issue's expected behavior implies.

Description

What happens
POST /tag/update returns 500 whenever the request carries budget_id and the tag already has a budget, even when it is the tag's own budget id, unchanged. Nothing is updated:

500 {"detail":"litellm.proxy._types.BudgetNewRequest() got multiple values for keyword argument 'budget_id'"}

The Terraform provider's litellm_tag sends budget_id on every update once it is in state, so a litellm_tag with budget_id = litellm_budget.x.budget_id can't be updated at all, whichever field changed. (A tag with no budget updates fine.)

Root cause (v1.105.1; unchanged on main today)
handle_budget_for_entity (litellm/proxy/management_helpers/utils.py) collects the request's budget fields by iterating LiteLLM_BudgetTable.model_fields (utils.py:211-222). LiteLLM_BudgetTable declares budget_id (litellm/models/budget.py:24), so a request that sends budget_id puts it in _budget_data, and the "existing budget" branch then calls

BudgetNewRequest(budget_id=existing_budget_id, **_budget_data)   # utils.py:255

which raises TypeError. update_tag's except Exception (tag_management_endpoints.py:481-483) turns it into the 500. A side effect is that lines 259-261 ("a different budget_id is explicitly provided, use that instead") can never run for a tag that already has a budget, so a tag can't be moved to another budget either.

Expected
/tag/update with the tag's current budget_id (plus any other fields) succeeds. With a different budget_id, the tag is re-pointed to that budget.

Suggested fix
In handle_budget_for_entity (litellm/proxy/management_helpers/utils.py:180), the request's budget_id is read twice:

  1. as a budget setting: budget_params (:211) is every field of LiteLLM_BudgetTable, which includes budget_id, so the request's budget_id is copied into _budget_data (:214-222) alongside max_budget, tpm_limit and the rest;
  2. as "which budget this tag should point at": data_budget_id = getattr(data, "budget_id", None) (:225). The create branch returns it (:228-230), and the update branch re-points the tag when it differs from the current one (:260-261).

Only the second is wanted. The first is what breaks BudgetNewRequest(budget_id=existing_budget_id, **_budget_data) (:255). So exclude budget_id from budget_params, and leave the data_budget_id handling to do its job:

-    budget_params: Final = LiteLLM_BudgetTable.model_fields.keys()
+    # budget_id selects the budget (data_budget_id below); it is not a budget setting
+    budget_params: Final = LiteLLM_BudgetTable.model_fields.keys() - {"budget_id"}

With that change, step 2 of the repro updates the description and keeps the budget. A budget_id that names a different budget re-points the tag (:260-261) instead of 500ing.

Related, from the same helper (please confirm which is intended)

  • Licence gating depends on whether the tag already has a budget. When there is no budget yet, the helper writes the row directly (utils.py:234-243) without validate_model_max_budget (key_management_endpoints.py:7809, which holds the Enterprise check and the shape validation). When a budget exists, the update goes through update_budget, which does call it (budget_management_endpoints.py:168-176). So without a licence, model_max_budget is accepted, unvalidated, by /tag/new and by /tag/update on a tag with no budget. It is refused ("You must have an enterprise license to set model_max_budget") by /tag/update once the tag has a budget, and by /budget/new and /budget/update. A tag created with model_max_budget therefore can't have it changed later without a licence.
  • PUT /access_group/{access_group}/budget uses the same helper (model_access_group_management_endpoints.py:1173), and AccessGroupBudgetRequest also has budget_id. From reading the code, the same TypeError should hit it once the group has a budget row. Not reproduced.
