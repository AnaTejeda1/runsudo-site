(Windows) passing a file path collects the whole suite, on a network drive where st_ino is 0

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the reported collection bug at the same place: samefile_nofollow() now returns False when either lstat() reports st_ino == 0, so Session.collect()'s Windows fallback stops matching every node and plain path comparison takes over. The independent tests confirm both pass every scenario from the issue (relative/absolute file arg, file::Class, running, subdirectory, --deselect), so on the issue's own scenarios correctness is equal.

Patch A goes further on the same root cause: os.path.samefile()/samestat() is also used in _is_same() (import_path's module/file mismatch detection) and LocalPath.samefile(). On a zero-inode drive those would silently treat two different files as the same, e.g. import_path returning an already-imported module from another directory instead of raising ImportPathMismatchError. A routes all three through one _samestat() helper that refuses to conclude identity without inode numbers, and keeps the UNC path-equality short-circuit. The non-Windows behaviour change in _is_same (adding a Path equality short-circuit before stat) is benign. The `p1 == p2 or` added to samefile_nofollow is redundant with the caller but harmless.

Tests: A adds an end-to-end regression test that reproduces the issue (zero-inode lstat plus a win32 sys proxy, relative and absolute args, and the file::TestProcess case), plus unit tests for import_path mismatch detection and LocalPath.samefile under zero inodes, and correctly updates test_samefile_false_negatives since _is_same no longer calls samefile. The sys proxy and global os.stat monkeypatching are somewhat hacky but scoped via monkeypatch. B adds two focused unit tests for samefile_nofollow (a sanity test and a zero-file-ID test that would fail before the fix); they are clean but never exercise collection itself.

Scope/craft: B is the minimal fix exactly as proposed in the issue, with a precise comment citing the underlying CPython behaviour and a good changelog; it is tidy and low-risk. A touches more code (including the legacy _py path module), which carries some risk, but the extra changes address the identical failure mode in sibling call sites rather than unrelated churn, and its tests demonstrate the actual user-visible bug is fixed. On balance A is the stronger fix: same core change, broader coverage of the root cause, and a regression test that reproduces the issue scenario.

The issue

View on GitHub

Hi,
when developing psutil on Windows, I do it by mapping X: to a sshfs share, so from Linux I can SSH into Windows and run tests there. Problem: pytest ignores the file I pass and collects everything:

$ python -m pytest tests/test_memleaks.py --collect-only -o addopts=""
platform win32 -- Python 3.14.6, pytest-9.1.1, pluggy-1.6.0
rootdir: X:\svn\psutil
collected 961 items

That file ( tests/test_memleaks.py ) has 130 tests, while 961 is the whole repo. Using absolute paths does the same.

I think the culprit is samefile_nofollow(), which Session.collect() falls back to on Windows when two paths don't compare equal. On this drive every file has st_ino == 0, so it says any two files are the same one:

$ python -c "
import os
a = os.stat('tests/test_memleaks.py')
b = os.stat('tests/test_process.py')
print(a.st_dev, a.st_ino)
print(b.st_dev, b.st_ino)
print(os.path.samestat(a, b))
"
3816903231 0
3816903231 0
True

So every node matches, nothing gets pruned, and I get the whole tree. The name parts still work, which fits: :: filtering happens after the path level.

$ python -m pytest "tests/test_memleaks.py::TestProcess" --collect-only -q
tests/test_windows.py::TestProcess::test_wait
175 tests collected

That's TestProcess from every file, not the one I asked for.

Maybe the fallback should just bail out when either st_ino is 0, since it can't tell anything apart at that point:

 def samefile_nofollow(p1: Path, p2: Path) -> bool:
-    return os.path.samestat(p1.lstat(), p2.lstat())
+    s1, s2 = p1.lstat(), p2.lstat()
+    if not s1.st_ino or not s2.st_ino:
+        return False
+    return os.path.samestat(s1, s2)

Returning False falls back to plain path comparison, which is what the other platforms do anyway. The short-path case this was added for (#11895) is on local NTFS, so it keeps working.

-m and -k work fine. Anything taking a path (--ignore, --deselect, plain args) doesn't.
