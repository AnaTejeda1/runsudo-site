- empty strings

The issue

View on GitHub

See https://github.com/gohugoio/hugo/issues/15060#issuecomment-4790405347

It's clumsy that you need to create a resource (making up an unique filename) to get a SRI hash.

I suggest we add crypto.Fingerprint with a similar signature to https://gohugo.io/functions/resources/fingerprint/

hash.Fingerprint [ALGORITHM] any -> string

The function name is a little clumsy, but we need to keep the two very similar functions in line.

Where any typically is a string (but can also be a Resource -- we have similar unwrappers elsewhere).

It would then return e.g. sha256-Yuh...rfE=.

Note to implementer: There's some obvious code reuse potential here.

What the agent reported

I added encoding.HexEncode and encoding.HexDecode. With them you can get an SRI hash from a string without creating a resource:

sha256-{{ "Hello world" | crypto.SHA256 | encoding.HexDecode | base64Encode }}
→ sha256-ZOyIygCyaOW6GjVnihtTFtIS9PNmskdyMlNKiuyjfzw=

What was wrong: crypto.SHA256 returns a hex string, but SRI needs the base64 of the raw digest bytes. No template function converted between the two, so the only way to get an SRI hash was to create a resource (with a made-up filename) and call fingerprint on it.

What I changed: I followed the issue title rather than the crypto.Fingerprint idea in its body. The two new functions plus the existing ones produce the SRI string.

  • tpl/encoding/encoding.go: HexEncode and HexDecode, written the same way as Base64Encode/Base64Decode. Bad hex input (odd length or non-hex characters) returns an error.
  • tpl/encoding/init.go: registers both with examples, including the SRI one. They have no short alias, so you call them as encoding.HexEncode / encoding.HexDecode. Other recently added functions don't have aliases either.

Test evidence:

  • New unit tests: TestHexDecode and TestHexEncode in tpl/encoding/encoding_test.go, in the same table style as the Base64 tests. They cover upper-case hex, empty input, a number input, and the error cases.
  • New integration test: TestHexEncodeDecodeSRI in tpl/encoding/encoding_integration_test.go builds a site. It checks that the SRI string equals fingerprint "sha256"'s .Data.Integrity for the same content.
  • Before and after: without the production change the tpl/encoding package doesn't compile ("ns.HexDecode undefined"). With it, all three tests pass, and so does TestTemplateFuncsExamples, which runs the new examples.
  • How I ran them: ./bt-test couldn't build anything because the container has no network to download Go modules. I ran go test against the local module cache instead (GOMODCACHE=/bt/cache/go-mod GOPROXY=off).
  • Other tpl packages: everything under ./tpl/... passes except TestVimeoShortcode in tpl/tplimpl. That test fails the same way on the unchanged code, so the change didn't cause it.

Requirements:

  1. Add encoding.HexDecode/HexEncode (the title): done, with tests.
  2. Get an SRI hash without creating a resource: done. The integration test checks the output matches fingerprint's integrity value.
  3. hash.Fingerprint / crypto.Fingerprint from the body: not added. The title asks for the hex functions, and those cover this use case with less new code. If you still want a one-call Fingerprint, it's a small follow-up.
  4. Accept a Resource as input: not handled specially. The new functions accept the same inputs as the existing Base64 and crypto functions, which don't unwrap resources either.
  5. Code reuse: fingerprint "sha256"'s internals weren't touched. The template pipeline reuses the existing crypto.SHA256 and base64Encode.

Also note:

  • No doc pages: I didn't add HexDecode.md/HexEncode.md under docs/content/en/functions/encoding/, and the generated docs/data/docs.yaml isn't updated.
  • Existing deletions: AGENTS.md and CLAUDE.md were already deleted in the working tree before I started, and I left them as they were.
