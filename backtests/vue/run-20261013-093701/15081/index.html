SSR hydration warning: dynamic props on SVG elements are patched as properties instead of attributes

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the root cause the same way. In hydrateElement, the forced patchProp call now passes the element's real namespace ('svg' or 'mathml') instead of undefined. runtime-dom's shouldSetAsProp then routes SVG props through setAttribute rather than property assignment, which resolves the read-only viewBox/width errors. Both derive the namespace from the element's own namespaceURI, so <foreignObject> is correctly treated as SVG. Correctness is effectively equal. Patch A also passes the namespace on the onClick-only branch. That is harmless but irrelevant, because event keys are handled before the namespace matters. Its null-guarded helper is slightly more defensive than B's `!` assertion, but elements in a real DOM always have a namespaceURI.

The tests are the deciding difference. Patch A's tests hydrate with client values identical to the server markup and then check the attributes. Those attributes already exist from SSR, so the assertions pass whether or not patching happened. The only discriminating check is that 'Failed setting prop' is not warned. That depends on jsdom exposing getter-only viewBox/width on SVG elements, which jsdom largely does not implement. A's tests therefore likely pass before the fix as well. Patch B uses different client values (48 vs 24), so the patch is observable. Its foreignObject test explicitly defines a getter-only `width` property to simulate the real browser behavior. Before the fix, Vue would try property assignment, fail, and leave the attribute at '24'. After the fix it uses setAttribute and gets '48'. That is a genuine regression test that fails before and passes after. B's first SVG test is weaker for the same jsdom reason, but the second one makes B's coverage meaningful. Both changes are minimal in scope. B wins on test quality.

Steps to reproduce

  1. Open the reproduction.
  2. Open the browser devtools Console.
  3. Observe the [Vue warn]: Failed setting prop … error logged during hydration.

What is expected?

During hydration, dynamic props on SVG (and MathML) elements width, height, viewBox, etc. should be patched as attributes (via setAttribute) exactly as they are during normal client-side rendering. Hydration should be silent.

What is actually happening?

Since 3.5.39, dynamic props on SVG elements are patched as DOM properties during hydration, which throws for read-only SVG IDL properties:

[Vue warn]: Failed setting prop "viewBox" on <svg>: value 0 0 24 24 is invalid.
TypeError: Cannot set property viewBox of #<SVGSVGElement> which has only a getter
    at patchDOMProp
    at patchProp
    at hydrateElement
    at hydrateNode
    at hydrateSubTree
    at <App>

Nothing is visually broken but the console is flooded with warnings.

We ran across this issue in a Nuxt app but I believe the issue is coming from Vue core
