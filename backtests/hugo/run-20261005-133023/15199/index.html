related: Add option to tokenize headings

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Patch B is the more correct and better-scoped fix.

**Correctness.**
- Patch B adds `fragmentsToKeywords`. With `tokenize` on, it walks the heading tree and splits each title into `FragmentKeyword` tokens. Before splitting, it strips HTML tags and unescapes entities, which matters because heading titles hold rendered HTML such as `<code>` and `&quot;`.
- Non-heading identifiers, such as definition terms, keep exact-ID matching. That is exactly what the proposed documentation says.
- Keywords are de-duplicated on both the index and query side.
- Explicit `opts.Fragments` are tokenized as well, so a heading ID can match tokenized titles.
- ApplyFilter still works because the tokens remain `FragmentKeyword`s. The heading-title token filter is built per index config, so lowercasing stays consistent.

Patch A has a real flaw. For heading words it uses `config.stringToKeyword(word)`, which returns a `StringKeyword`. But `searchDate` only collects filter entries when `kw.(FragmentKeyword)` succeeds. So with tokenize on, `ff.words` is never populated, and the ApplyFilter path for tokenized headings is effectively dead code. This also mixes keyword types within a fragments index.

Patch A's `splitWords` also does not strip HTML tags. A title like `Upgrading <code>hugo</code>` would yield tokens like `<code>hugo</code>` trimmed to `code>hugo</code`. In addition, A does not tokenize `opts.Fragments`.

**Scope.**
- Patch A goes beyond the ask. It changes `ToKeywords` behaviour for basic indices and adds a `MinTokenLength` option that was not requested. It also makes whitespace-only churn in an existing test file.
- Patch B stays focused on the ask and adds the requested documentation entry verbatim.

**Tests.**
- Patch B's integration test covers several cases with tokenize on and off: HTML in headings, `cardinalityThreshold` pruning of common words, definition terms keeping exact matching, ApplyFilter results, and querying by explicit fragment. It also adds a config-decode assertion.
- Patch A has more tests, but its ApplyFilter test relies on the path that appears broken, and several tests exercise the out-of-scope features.

Overall, Patch B wins.
