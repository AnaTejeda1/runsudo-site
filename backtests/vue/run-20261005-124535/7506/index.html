suspense.resolve() is called without a pending branch.

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the same root cause. A nested suspensible Suspense can resolve synchronously while its parent's pending branch is still being patched in patchSuspense's same-type path. When that happens, it decrements the parent's deps to 0 and resolves the parent mid-patch. patchSuspense then calls suspense.resolve() a second time on a boundary that no longer has a pending branch, which triggers the reported warning. Both patches defer the parent's resolution until the patch finishes, so the post-patch `deps <= 0` check performs the single resolve. Patch A adds an explicit isPatchingPendingBranch flag that suppresses the nested-propagation resolve. Patch B temporarily bumps deps to hold the boundary pending. Both work, both leave a sibling registered later in the same patch counted before the final check, and neither handles an exception mid-patch (A's flag or B's extra dep would leak), so correctness is roughly equal. B is slightly more general, since it blocks any deps-reaching-zero path during the patch, but no other synchronous path exists in practice. A's flag follows the existing isFallbackMountPending convention and states its intent more explicitly than B's piggybacking on the dep counter, which other code also reads. On tests, A reproduces the issue's actual scenario: a page component whose async setup navigates to another page, both during setup and after an await. It covers single-root and multi-root layouts and asserts onResolve fires once, the final DOM, and mount order. B's tests are valid but more synthetic: they toggle routes on a never-resolving child, and one targets a sibling-dep edge case rather than the reported navigate-during-setup flow. Given equivalent correctness, A's more faithful and thorough regression coverage of the reported scenario and its clearer, convention-consistent mechanism give it the edge.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
