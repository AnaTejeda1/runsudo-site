Issue #15496 Merged fix PR #15499 Run 1 Oct 2026 vuejs/core

looseEqual: comparing Map/Set values with circular references throws RangeError (regression in 3.5.42)

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the root cause. Each threads a recursion-stack 'seen' structure through array, Map/Set, and plain-object comparison, and removes entries after each comparison. That removal keeps failed trial matches in looseCompareCollections from leaking into later comparisons. Both handle the issue's three repro cases: mutually-referencing Sets, Maps holding cyclic values, and self-containing Sets.

The difference is cycle semantics. Patch A tracks in-progress (a, b) pairs and assumes a re-encountered pair is equal. This is the standard coinductive approach the issue suggests ('tracking visited pairs … returning true on re-encounter'), and it gives true for structures that unroll identically. Patch B enforces a strict on-stack bijection: if either side was seen paired with a different partner, it returns false. That produces false negatives for structurally indistinguishable graphs. A self-loop node compared with a 2-cycle is one example, and Patch B's own test asserts false for it. Another is X.child = X versus Y.child = Y', Y'.child = Y'. For a 'loose' equality used by v-model, this is a more surprising rule than the issue asked for.

Patch B also widens the public `looseEqual` signature with an optional third `seen` parameter. If looseEqual is ever passed directly as a callback, such as to an array method, an unrelated third argument would be misread as state. Patch A keeps the public signature unchanged and uses an internal `looseEqualImpl`, which is safer.

On tests, Patch A is more thorough. It adds a component-level vModel test matching the issue's `<select v-model>` scenario. Its unit tests cover Sets and Maps of mutually-referencing objects (both equal and unequal cases), self-containing Sets and Maps, and cyclic plain objects. It also explicitly checks that failed trial matches don't leak into later comparisons. Patch B's tests are fewer and include only one negative cyclic case.

On craft, both are similar. Patch A's helper comment clearly explains why entries are removed after each comparison. Overall, Patch A is the better fix.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Any additional comments?

This is a regression introduced by #15328 ("fix(shared): correctly compare Map and Set values", released in v3.5.42), which added looseCompareCollections in packages/shared/src/looseEqual.ts:

function looseCompareCollections(
  a: Map<any, any> | Set<any>,
  b: Map<any, any> | Set<any>,
) {
  if (a.size !== b.size) return false
  const candidates = Array.from(b)
  const matched = new Uint8Array(candidates.length)
  for (const item of a) {
    let index = -1
    for (let i = 0; i < candidates.length; i++) {
      if (!matched[i] && looseEqual(item, candidates[i])) {
        index = i
        break
      }
    }
    if (index < 0) return false
    matched[index] = 1
  }
  return true
}

looseEqual(item, candidates[i]) recurses into each [key, value] pair (Map) or element (Set), so a Map/Set whose entries point back to the collection itself or to each other causes unbounded recursion. Before 3.5.42, Maps/Sets never recursed into their entries (they fell through to String() comparison), so this exact code path — a <select v-model> with Map/Set values, which is precisely the scenario #15320/#15328 added support for — did not throw on 3.5.41; it silently compared wrong, which #15328 fixed.

Note: #5318 covers the same root cause for cyclic plain objects (pre-existing, still open). The Map/Set case is new in 3.5.42: cyclic Maps/Sets did not throw before.

Suggested fix: make looseEqual cycle-safe by tracking visited (a, b) pairs (e.g. with a WeakMap<object, Set<object>> and returning true on re-encounter), which also fixes #5318.

Additional local repro cases that all throw RangeError on current main:

  • looseEqual(new Set([a1, a2]), new Set([b1, b2])) where a1.peer = a2; a2.peer = a1 and b1.peer = b2; b2.peer = b1
  • looseEqual(mapA, mapB) where both maps hold mutually-referencing values
  • looseEqual(s1, s2) where s1.add(s1) and s2.add(s2)

What the agent reported

looseEqual no longer recurses forever on cyclic data. The <select v-model> from the report now mounts without the RangeError, and the targeted tests pass (112/112).

What was wrong: #15328 added looseCompareCollections, which calls looseEqual on every Map entry and Set element. Nothing tracked what had already been compared. So once the values pointed back at each other or at the collection itself, the recursion never ended. Cyclic plain objects (#5318) had the same problem from before 3.5.42.

What I changed (packages/shared/src/looseEqual.ts only):

  • looseEqual(a, b) keeps its public signature. It now calls an internal looseEqualImpl(a, b, seen?), where seen records which (a, b) pairs are currently being compared.
  • A new helper, compareGuarded, wraps every array, Map, Set and plain-object comparison. If the same pair comes up again while it is still being compared, it is treated as equal. Otherwise the pair is recorded, compared, and then removed.
  • Removing the pair matters: when a Set or Map tries an element against a candidate and the match fails, a leftover record would make a later comparison of that pair wrongly return true.
  • The old object-key loop moved into looseCompareObjects unchanged. Plain objects still fall through to the final String(a) === String(b) check. The seen map is only created when the first object-level comparison is reached, not for primitives, dates or identical values.

Test evidence:

  • Shared tests: a new test, compares circular structures without infinite recursion, covers cyclic Sets, Maps and plain objects. It also checks that failed trial matches don't carry over into later comparisons.
  • Component test: a new test, selects the matching option when values are cyclic sets, sits next to the #15320 test in vModel.spec.ts. It uses the report's makeGraph setup.
  • Before the fix: the test-writer ran both new tests against the original code and both failed with RangeError.
  • Pair removal: the reviewer pointed out that the first version of the trial-match check would pass even without removing pairs. I added a case that compares the same pair twice and confirmed it fails when the removal line is deleted (expected true to be false), then restored the line.
  • Test runs:
  • ./bt-test packages/shared packages/runtime-dom/__tests__/directives/vModel.spec.ts: 7 files, 112 tests passed.
  • The other code that calls looseEqual (v-model directives, SSR directive helpers, component props/rendering): 156 + 44 tests passed.
  • Prettier check passed.
  • Review: the reviewer found no correctness problems, no API change and nothing unrelated in the diff.
