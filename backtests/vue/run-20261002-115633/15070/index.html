SSR memory leak after a render error in a dynamic component

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Root cause: during SSR, a dynamic component's vnode-based slot path calls `renderSlot`, which runs `openBlock()` and then the slot. When the slot throws, nothing closes that block. Unlike the client, `renderComponentRoot`'s catch does not cover this path. So `blockStack` and `currentBlock` stay dangling, and every vnode created afterwards is pushed into the stale block, which retains all later apps.

Both patches fix the reported scenario.

Patch A:
- Adds `resetBlockStack(depth)`, which truncates the stack and also restores `currentBlock`.
- Applies it on throw in `renderSlot`, in `normalizeChildren` (the slot-object branch used by `<component :is="'div'">`) and in `normalizeSuspenseSlot`.
- Restores the compiled slot `_d` flag in each of those places.
- Fixes a latent bug in `renderComponentRoot`: it previously did `blockStack.length = 0` without resetting `currentBlock`, leaving a stale reference.
- Nested blocks opened inside the throwing slot (e.g. `v-if`) are handled by truncating to the recorded depth.
- Tests are deterministic and directly assert `blockStack`/`currentBlock` balance and `_d` restoration. They would fail before the change. They cover renderSlot, Suspense, normalizeChildren, the render-function error path, and SSR end-to-end cases including nested `v-if` blocks.

Patch B:
- Adds unwinding in `withCtx` and `renderSlot` via a `closeBlock` loop, which also covers the inline `v-if` case.
- Does not touch the stale-`currentBlock` issue in `renderComponentRoot`, Suspense slot normalization, or `_d` restoration in `normalizeChildren`.
- Changing `withCtx` (a very hot path) to scan the block stack on every call is a broader behavioral change with slightly more risk.
- Its tests are GC/WeakRef based: they test the real symptom, but are skipped unless `--expose-gc` is available and are less precise.

Overall, A fixes the root cause more completely and consistently, through a single helper that keeps `currentBlock` correct. Its tests are stronger and deterministic, so A is the better fix.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Steps to reproduce

  • download the reproduction from stackblitz (won't work there, needs to be run locally)
  • run pnpm i && pnpm leak
  • see the heap size & alive app instances grow with each request after the single failed render

The script renders 500 fresh SSR apps, which all get garbage-collected. Then renders one app whose slot content throws, then renders 500 more identical healthy apps, which will never be garbage collected afterwards.

A dynamic component <component :is> with a <slot /> is needed for this to reproduce.

Card

<script setup>
    defineProps({ tag: { type: String, default: 'div' } })
</script>

<template>
    <component :is="tag" class="card">
        <slot />
    </component>
</template>

app:

<script setup>
    defineProps(['payload'])  // one request renders with `payload: null` → throws
</script>

<template>
    <main>
        <Card>{{ payload.title }}</Card>
    </main>
</template>

What is expected?

A failed renderToString should not affect subsequent renders and all apps rendered after it should get garbage collected.

What is actually happening?

Every app created after the single failed render is kept in memory forever.
