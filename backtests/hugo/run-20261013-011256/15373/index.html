Support relative path calls in partials

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches take the same basic approach. They resolve `./` and `../` names against the directory of the calling partial, found via `tpl.Context.CurrentTemplate`. Both walk a `decoratorOwner` chain so that `inner` blocks in partial decorators resolve against the template that defines them. Both resolve the name before computing the `partialCached` key, so relative names from different directories do not share a cache entry.

The decisive difference is deferred templates. Deferred blocks are deduplicated by a hash of their body, plus the plain-text flag. Suppose two partials in different directories contain the same `templates.Defer` body, such as `{{ partial "./util.html" . }}`. They hash to the same deferred template. In Patch A, that template is registered once with the first owner's PathInfo, so the second partial's relative call silently resolves against the wrong directory. Patch B adds the owning partial's directory to the hash input, keeping these blocks distinct. Its `TestIncludeRelativePathInDefer` (a/main and b/main with identical defer bodies) checks exactly this case. Patch A's defer test uses only one partial, so it would not catch the bug.

Patch B is also more robust at the edges:
- It uses a checked type assertion on `CurrentTemplateInfoOps`; Patch A uses an unchecked one that could panic.
- It verifies that the partial's path actually lies under the partials container.
- It rejects a trailing slash and a name that resolves to `.`.
- Its not-found error shows both the given and resolved names.
- It skips the legacy `partials/` prefix warning for resolved names, which is tested.
- It tests the legacy `layouts/partials` directory and nested decorators.

Patch A adds documentation, which is nice but does not offset the defer-sharing correctness bug. Both test suites are meaningful, but Patch B's is broader and targets the real edge cases.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The issue

View on GitHub

Right now partial calls only supports path relative to layout/partials and themes/<THEME>/layouts/partials/*<PARTIALNAME> (taken from the documentation).

This is fine when we have few partials but can become a pain if we need to organize them in subdirectories.

What i propose is to add support for relative paths like in this example :

{{ partial "./foo" ... }}
{{ partial "../bah" ... }}

Why ?

Having this feature could be beneficial in a lot or ways :

  • it avoid us having to remember and write the full partial path when it's not needed (for example utility partials that are only called and only used by a on partial)
  • It could allow us to reorganize partials way more easily, as relative paths would full path independent

How to implement

If the path in a partial call starts with "./" or "../", it's a relative path. Otherwise it's an "absolute" path (relative to layout/partials).

I'm against adding the current directory of the current partial to the lookup search directly though, as theme and site authors currently assume this would call to the partial root directory. Perhaps we could add this to the future, if my proposal is adopted by the community.
