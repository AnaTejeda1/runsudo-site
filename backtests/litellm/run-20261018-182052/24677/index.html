[Bug]: Incorrect TPM limiting for virtual keys

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches identify the same root cause: the RPM `:requests` and TPM `:tokens` counters share one `{key:value}:window` key, and whichever counter observes expiry resets only itself, so the sibling carries prior-window usage forward indefinitely. Both fix this in BATCH_RATE_LIMITER_SCRIPT, CHECK_AND_INCREMENT_BY_N_SCRIPT, the in-memory sliding window, and the in-memory atomic path, and both pass all five independent tests that fail on base.

Patch B goes further on the issue's second symptom (cooldowns of 2-5 minutes). In a Redis-backed multi-pod deployment, the local pre-check in is_cache_list_over_limit rejects on the locally mirrored counter before consulting Redis; after a sibling reset in Redis, that local mirror of the sibling is never refreshed (a local rejection short-circuits the Redis call), so stale rejection persists until the local TTL lapses. Patch B treats a counter whose window start is expired as 0 in the local pre-check and invalidates local sibling mirrors when Redis reports a freshly reset window. Patch A leaves the local mirror stale, so under the multi-pod scenario the issue describes it only partially shortens the cooldown.

Patch B also handles a consequence the fix itself introduces: once counters reset at rollover, settling a reservation made in the old window (`actual - reserved`) into the new window corrupts it. It records reservation window identities and routes those settlements through the existing window-guarded reservation path, with parametrized success/failure tests. Patch A ignores this.

Patch A's added `_check_and_increment_lock` around in_memory_cache_sliding_window is a reasonable concurrency guard but introduces a non-reentrant asyncio.Lock on a path whose callers I cannot see; if any caller already holds that lock this deadlocks. Patch B's Lua helper also guards on the ':window' suffix before deriving the prefix, where Patch A derives blindly.

On scope, Patch B is considerably larger and the reservation-settlement rework adds risk, but it is coherent with the fix rather than unrelated churn, and the new test file exercises in-memory, fake-Redis multi-pod, atomic, and post-rollover settlement scenarios. Patch A's tests are focused and valid but narrower. B is the more complete fix for both reported symptoms.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Each saw the issue and the two patches, labelled A and B in random order (two of them saw ours as A), with issue links and version numbers removed. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours. The reasoning above is one judge's, shown verbatim.

What happened?

This was initially reported on #18953 for v1.80.0. It was marked as solved, but we are still seeing this behaviour in v1.82.3

Actual rate limit enforcement is usually ~30% below the configured limit, and the cooldown period is longer than a minute. Usually 2, but can reach 5 minutes in some instances.

This is with the default rate limit type and configuration.

Steps to Reproduce

  1. Configure an API key with TPM limit (e.g. 500k)
  2. Use the API key
  3. Rate limit enforcement hits at approximately 300-350k.
