Initial Checks

Description

When a discriminated union uses a bool discriminator (Literal[True] / Literal[False]), the generated JSON schema's discriminator.mapping uses the Python string representations "True" and "False" as keys:

"discriminator": {
    "mapping": {"False": "#/$defs/Disabled", "True": "#/$defs/Enabled"},
    "propertyName": "enabled"
}

Per the OpenAPI discriminator specification, mapping keys must match the serialized payload value of the discriminator property. For a boolean property, that value serializes to JSON true/false, so the keys should be "true" and "false". Tooling that resolves the mapping against the payload (code generators, validators such as openapi-generator or Redocly) fails to match either variant.

Expected:

"mapping": {"false": "#/$defs/Disabled", "true": "#/$defs/Enabled"}

Note that Enum discriminator keys are already normalized to their value (k.value) before stringification in GenerateJsonSchema.tagged_union_schema; bool keys just fall through to str(k).

Example Code

from typing import Literal

from pydantic import BaseModel, Field


class Enabled(BaseModel):
    enabled: Literal[True]
    config: str


class Disabled(BaseModel):
    enabled: Literal[False]


class Model(BaseModel):
    setting: Enabled | Disabled = Field(discriminator='enabled')


print(Model.model_json_schema()['properties']['setting']['discriminator'])
# {'propertyName': 'enabled', 'mapping': {'True': '#/$defs/Enabled', 'False': '#/$defs/Disabled'}}

Summary

What was wrong: In GenerateJsonSchema.tagged_union_schema (pydantic/json_schema.py), discriminator keys for a bool discriminator (Literal[True]/Literal[False]) fell through to str(k), producing Python-style JSON schema discriminator.mapping keys "True"/"False". The OpenAPI discriminator spec requires mapping keys to match the serialized payload value, which for a boolean is JSON true/false, so tooling (openapi-generator, Redocly, etc.) could not match either variant. Enum keys were already normalized via k.value, but bool had no equivalent handling.

What I changed:

  • pydantic/json_schema.py — added a bool normalization branch alongside the existing Enum branch in tagged_union_schema: python if isinstance(k, Enum): k = k.value elif isinstance(k, bool): k = 'true' if k else 'false' Ordering is Enum-first, so IntEnum members equal to 0/1 remain unaffected (caught by the Enum branch).
  • tests/test_json_schema.py — added test_discriminated_union_bool, exercising the exact reported scenario and asserting mapping keys "true"/"false".

Test evidence:

  • Reproduced the bug directly: mapping emitted {'False': ..., 'True': ...}.
  • The new regression test failed before the fix ({'True', 'False'} vs expected {'true', 'false'}) and passes after.
  • Gate: ./bt-test tests/test_json_schema.py -k discriminat → 7 passed (all discriminator tests, including test_discriminated_annotated_union_literal_enum covering the Enum/int-enum paths — no regressions).
  • Diff limited to the two intended files; no scratch files; no existing tests weakened. Reviewer confirmed the fix is correct and minimal.

Requirements disposition:

  • Fix bool discriminator mapping keys to JSON-style "true"/"false" — Implemented, with a passing regression test that was confirmed failing beforehand.

All changes are left uncommitted in the working tree.
