Improve/document security.http.urls override behavior

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

The issue asks to improve or document how `security.http.urls` overrides skip the dial-time resolved-address check. Patch B targets exactly that, and Patch A spends most of its weight on an unrelated, risky change.

Patch B:
- Extracts the default-allowlist comparison into a named `IsDefaultHTTPURLs` method.
- Adds an explanatory hint to `AccessDeniedError`, so a user who hits the resolved-address denial is told why an allowed URL was refused and that customizing `urls` disables the check.
- Adds a dedicated docs section with an IMPORTANT callout that any change, even appending one pattern, disables the check. It includes practical guidance (narrow allowlists, negation rules and their text-only limitation) and a worked example.
- Cross-links the section from the `GetRemote` docs.
- Adds meaningful tests: the error-message assertions fail before the change, and a new test confirms that restating the default patterns keeps the check while customized lists (including default plus one extra pattern) disable it.

Patch A:
- Adds only one paragraph documenting the override behavior.
- Its main change is a new `proxyFromEnvironment` option that turns off `HTTP_PROXY`/`HTTPS_PROXY` handling by default. The issue never asks for this.
- That default silently breaks remote fetches for users behind corporate proxies.
- It adds substantial transport machinery (a context-carried proxy URL, a reimplemented `canonicalAddr`, a custom `RoundTripper`) that could drift from `net/http` behavior.
- It brings in a new import (`golang.org/x/net/http/httpproxy`).
- The proxy work is arguably adjacent hardening, but it adds real regression risk and obscures the issue's actual ask.

On correctness for the stated issue, test relevance, and scope, Patch B is clearly better.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The issue

View on GitHub

In d6e6f9e500eebdeae8e28de830fff2e3bfc7d534 (unreleased) we added a dial-time URL validation to catch URLs that's valid according to the whitelist but that resolves to a loopback, private or link-local IP addresses. That check is skipped it if the user has a custom security.http.urls setup, as it would not make sense to block local development servers.

See CheckAllowedHTTPAddress.

This has been reported by @Reload3d as a potential security issue, and while I think the current behaviour is the pragmatic correct approach, I'm creating this issue for visibility and to see if this can be improved further (e.g. better documentation).
