Clearing select's value in change handler behaviour changed since 3.4.15 via webdriver

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the same root cause. Since the select performance change, `updated` skips `setSelected` whenever `_assigning` is true. So if the model changes again in the same tick (for example, reset to null in an `@change` handler), the DOM is never resynced.

Patch A records the assigned value and resyncs when `toRaw(value) !== toRaw(_assignedValue)`. That covers the reported case: a single select reset to null, or a multiple select reassigned to a new array. However, it relies on reference identity. If the handler mutates the emitted array or Set in place (for example `value.pop()`, `value.length = 0` or `set.delete(x)`), the reference is unchanged. A then still skips the resync and the DOM stays stale. That is the same class of bug the issue describes, so A only partly closes it. A's two tests are reasonable and would fail before the fix.

Patch B stores a snapshot of the pending value, copying `selectedVal` for array models. In `updated` it compares that snapshot to the current model by content: `looseEqual` for single and Array values, and a membership check for Sets. It also detects a `multiple` flip, clears the pending state after the first `updated`, and uses try/finally plus an identity check so a throwing assigner cannot leave stale state. As a result it handles both reset-by-reassignment and reset-by-mutation, while still skipping redundant DOM writes when nothing changed, which preserves the purpose of the original performance optimization.

B's tests are broader and meaningful. They include the issue's change-handler reset, in-place Array and Set mutation, Set override, duplicate option values, and write-counting tests confirming no extra `selected` writes in the common case. B is more code, but it is coherent and low-risk, and the extra comparison helper is clearly named. On correctness, B is more robust within the issue's scenario space, so B wins.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
