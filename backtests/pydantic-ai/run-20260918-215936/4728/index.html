Description

The problem

Multi-turn conversations with tools can accumulate broken message history — tool calls without matching results, or results referencing calls that don't exist. This is just structurally invalid (a tool call without a result before the next turn doesn't make sense), and providers rightfully reject it. Anthropic is the strictest about enforcement — you get a 400 — but even providers that silently tolerate it will produce worse results from garbled history.

The ways this happens in practice:

  • A streaming response with ToolCallPart gets persisted, but the agent times out before ToolReturnPart arrives. Next turn inherits a dangling tool call.
  • Deferred tools (UI-resolved via Vercel AI adapter) get their results dropped or arrive with a different tool_call_id than the original call.
  • Multi-run conversations that span many agent.run() calls accumulate orphans from each interrupted run. Once one bad pair gets in, every subsequent run 400s on the same history. The conversation is permanently broken.

That last one is the real pain point. There's no self-healing — once a conversation is poisoned, it stays poisoned until someone manually fixes the stored messages.

What we built

We wrote a ~120-line sanitize_message_history function that plugs in as a HistoryProcessor:

  • Strips trailing ModelResponse messages with unmatched tool calls
  • Injects synthetic ToolReturnPart ("Tool call was not completed") for orphaned regular calls, BuiltinToolReturnPart for orphaned builtin calls (in the same response, since Anthropic requires that)
  • Strips ToolReturnPart/RetryPromptPart whose tool_call_id doesn't exist in the preceding ModelResponse. If that empties the ModelRequest, drops in a placeholder UserPromptPart to keep the user/assistant alternation intact
agent = Agent('anthropic:claude-sonnet', history_processors=[sanitize_message_history])

It works, we've been running it in production. But it feels like something that shouldn't live in userland — maintaining valid tool call/result pairing in persisted history seems like a framework-level concern.

The ask

Would it make sense to ship a built-in history processor for this? If it's not something Pydantic AI wants to maintain then it's okay and we can close the issue, was thinking this is going to be a very common use case. Something like:

from pydantic_ai.history_processors import repair_tool_orphans

agent = Agent('anthropic:claude-sonnet', history_processors=[repair_tool_orphans])

The HistoryProcessor abstraction is already the right place for this. The logic is provider-agnostic (it operates on ModelMessage types), though the one Anthropic-specific wrinkle is that builtin tool results need to live in the same ModelResponse as the call, not the next ModelRequest.

How we got here

We run a chat agent with deferred tools in production. The pattern that broke things: each run ends with a deferred get_editor_content call that times out. The next run starts with a tool_return for edit_content with a different tool_call_id (generated by the frontend). After a few runs, the conversation has multiple orphaned calls and mismatched results, and Anthropic starts rejecting everything.
