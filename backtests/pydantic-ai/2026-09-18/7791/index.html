Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the root cause identically and soundly: promote the sampling-param tuple into profiles/anthropic.py (avoiding the anthropic-SDK import cycle in bedrock.py), then filter temperature/top_p/top_k from the merged settings inside BedrockConverseModel.prepare_request when profile.anthropic_disallows_sampling_settings is set. Both pop top_k, which correctly neutralizes the additionalModelRequestFields injection leg (bedrock.py:956 only adds top_k when it's present in settings) as well as the inferenceConfig leg, and both filter a copy so the caller's dict is untouched and both collapse an emptied dict to None. So correctness (criterion 1) is a wash. The decision turns on tests (criterion 2), where B is clearly stronger: A ships a single unit test asserting on prepare_request's returned dict, which never proves top_k actually stops reaching additionalModelRequestFields on the wire. B asserts on the recorded request body (inferenceConfig=={'maxTokens':16}, additionalModelRequestFields absent), adds a gating test proving a non-flagged model (Haiku 4.5) still forwards temperature+top_k — directly closing the coverage gap the issue names — plus a count_tokens test (that path also routes through prepare_request) and a no-op/no-warning case, and a raw-client cassette documenting the actual 400 so the fix's premise can't silently drift. Craft also favors B: its bedrock _drop_unsupported_sampling_settings mirrors AnthropicModel's in-place signature and its docstring correctly explains both the import-cycle placement and the deliberate decision to leave the bedrock_additional_model_requests_fields escape hatch alone; A leaves a slightly awkward `_ANTHROPIC_SAMPLING_PARAMS = ANTHROPIC_SAMPLING_PARAMS` alias lingering rather than migrating call sites. A wins only on scope (smaller diff, less churn in anthropic.py), but the extra scope in B is almost entirely justified test infrastructure (cassettes) and a clean constant rename. Since tests and craft outrank scope, B is the better fix.

Description

AnthropicModel honors anthropic_disallows_sampling_settings (warn + drop temperature/top_p/top_k, models/anthropic.py:857), but BedrockConverseModel never reads the flag, so every request with a sampling setting hard-fails with a 400 on the Claude 5 generation over Bedrock:

pydantic_ai.exceptions.ModelHTTPError: status_code: 400, model_name: eu.anthropic.claude-opus-5,
body: {'Error': {'Message': 'The model returned the following errors: `temperature` is deprecated for this model.', 'Code': 'ValidationException'}, ...}

The same Agent(..., model_settings={'temperature': 0.5}) on anthropic:claude-opus-5 works (settings are dropped with a UserWarning). A global temperature in shared model_settings therefore breaks an app the moment a model is switched to Opus 5 / Sonnet 5 on Bedrock, which is how we hit it in production.

Live probe matrix (raw bedrock-runtime converse, eu-central-1, 2026-08-26):

eu.anthropic.claude-opus-5400 "deprecated for this model"400400
eu.anthropic.claude-sonnet-5400400not probed
eu.anthropic.claude-haiku-4-5-...okokok

Root cause (current main):

  • The profile is resolved correctly: BedrockProvider.model_profile('eu.anthropic.claude-opus-5') carries anthropic_disallows_sampling_settings=True (providers/bedrock.py:248-289 merges the downstream Anthropic profile). It's one missed read, not a missing profile.
  • models/bedrock.py:1062-1076 _map_inference_config maps temperature/top_p unconditionally, and as a @staticmethod it can't even see self.profile.
  • models/bedrock.py:928-930 injects top_k into additionalModelRequestFields for every Anthropic model (bedrock_top_k_variant == 'anthropic'), same failure.
  • Repo-wide, models/anthropic.py:857 is the flag's only enforcement site; models/bedrock.py / providers/bedrock.py never mention it. #6723 verified the rejection against the direct API and deliberately scoped Bedrock out ("No Bedrock/Heroku model ids"); #7283 already names the pattern ("the Anthropic fix wasn't widened to Bedrock" pending sibling reproduction), which the probes above now provide.

This also contradicts the docs: docs/models/anthropic.md promises "Pydantic AI drops those keys automatically" for Opus 4.7/4.8/5 with no Bedrock exclusion (unlike e.g. task budgets, which are explicitly scoped to "not Bedrock, Vertex, or Microsoft Foundry"), and the ModelSettings reference lists Bedrock under temperature/top_p.

Proposed fix (bounded): mirror AnthropicModel in BedrockConverseModel.prepare_request (models/bedrock.py:666-704): when profile.get('anthropic_disallows_sampling_settings'), pop temperature/top_p/top_k from the prepared settings with the same UserWarning ("These settings will be ignored."). Popping top_k there also covers the additionalModelRequestFields leg. Promote _ANTHROPIC_SAMPLING_PARAMS (models/anthropic.py:316) to profiles/anthropic.py, whose docstring already declares it shared with "any provider that translates to the Anthropic wire shape (e.g. Bedrock Converse)", and import it next to ANTHROPIC_THINKING_BUDGET_MAP in models/bedrock.py:79. Add an Opus-5 Bedrock case to tests/models/test_model_settings_support.py (the existing Bedrock case at :373-394 uses Sonnet 4.5, whose flag is False, so this combination has no coverage).

Open design question for maintainers: is prepare_request the right site, or would you rather make _map_inference_config profile-aware / add a bedrock_* mirror flag in bedrock_anthropic_model_profile like the existing bedrock_supports_adaptive_thinking mirror?

Noted while auditing, deliberately not claimed here (separate issues if you want them, per AGENTS.md sibling rule): resolve_anthropic_effort(..., supports_xhigh=False) is hardcoded at models/bedrock.py:955 (silent xhigh→max downgrade), and bedrock_supports_tool_choice is hardcoded True for all Anthropic ids (providers/bedrock.py:268), which puts forced toolChoice on the wire for claude-fable-5/claude-mythos-5 Bedrock ids.

Workaround: use AnthropicModel with AsyncAnthropicBedrock (that route resolves the same profile and goes through the working prepare_request), or unset temperature/top_p for these models.

Happy to open a PR once a maintainer agrees on the approach and assigns this.

(Root-cause analysis and drafting done with Claude Code; the Bedrock probes above were run against a live account and reviewed by me.)
