Preserve input values entered during hydration

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches use the same approach. In `created`, they detect hydration via `el.parentNode` and compare the live `el.value` against what the server rendered. In `mounted`, if the user changed the value, they push it into the model instead of overwriting the DOM.

Correctness: Patch A only records an initial value when `el.type` is 'text' or 'textarea'. That leaves out common form input types such as email, password, search, tel, url and number, where the issue's data loss would still happen. Patch B applies to all text-like types and excludes only types whose values the browser normalizes on parse (range, color, date/time), avoiding false positives there. Patch B also handles `type="number"` casting correctly via `vnode.props.type`, matching the existing `created` logic. Patch A's `castValue` call ignores that, although A never reaches number inputs anyway.

Patch A's CR/LF normalization of `defaultValue` is a careful touch for a rare edge case (newlines in a value attribute). It does not outweigh A failing the issue for most non-'text' input types.

Tests: Patch B adds three focused tests covering an input, a textarea, and a no-op case that asserts the model is not updated when the value is unchanged. These use explicit `withDirectives`/`vModelText` render functions that work in the runtime-core test environment. Patch A adds a single test that relies on `template` compilation and `renderToString` inside runtime-core's hydration spec, which is less clearly runnable there. It also covers only the text-input happy path.

Scope and craft: both are tightly scoped to vModel.ts. Patch B's comment explains the `isConnected` versus `parentNode` choice and why some types are excluded.

Overall, B fixes the issue more completely and tests it better.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

What the agent reported

I fixed the bug: text you type into a server-rendered <input v-model> or <textarea v-model> before hydration finishes is now kept, and the bound model is updated to match. The new regression tests failed before the change and pass now. The full runtime-core, runtime-dom, server-renderer and vue suites pass (1756 passed, 1 skipped), and tsc --noEmit is clean.

What was wrong: During hydration, the mounted hook of vModelText (packages/runtime-dom/src/directives/vModel.ts) always ran el.value = value. That replaced whatever the user had typed into the server-rendered element with the model's starting value.

What I changed (only in vModel.ts):

  • Spotting hydration (created): in a normal client-side mount the element isn't attached yet when created runs, but during hydration it is already in the page (I checked el.parentNode, not isConnected, so it also works when the container isn't attached to the document).
  • Spotting typed text: if the element is already attached and el.value !== el.defaultValue (the live value differs from the server-rendered value), I mark the element.
  • Using the typed text (mounted): for a marked element, I send el.value to the model (applying the trim/number modifiers the same way the input listener does) instead of overwriting it.
  • Excluded input types: range, color, date, datetime-local, month, week and time are left out. The final review pointed out that browsers already adjust these values while loading the page (clamping range, lowercasing colours, clearing invalid dates). Without the exclusion, hydration would have changed the model even though nobody typed anything.

Tests: three new tests in packages/runtime-core/__tests__/hydration.spec.ts. Each puts server-rendered HTML in a container, changes the value to mimic a user typing, then hydrates:

  1. A text input typed from foo to bar keeps bar, and the model becomes bar. This failed before the fix with "expected 'foo' to be 'bar'".
  2. The same check for a <textarea>, which also failed before the fix.
  3. An input nobody touched keeps foo and the model update handler is never called. This passes both before and after; it guards against updating the model without user input.

Requirements:

  • Typed value preserved after hydration: done; tests 1 and 2.
  • Model reflects the typed value: done; the text.value === 'bar' assertions in tests 1 and 2.
  • No change when nothing was typed: done; test 3, and all existing client-side mount and v-model tests pass.

Remaining gaps:

  • Checkboxes, radios and selects are not covered. A box ticked or option picked before hydration finishes can still be reset. The report only described text entry.
  • Some types still lose typed text: for the excluded date/time, range and colour inputs, anything entered before hydration is still reset, as before.
  • Rare unprompted model changes: in a few unusual cases the browser still adjusts the value while loading the page, and the model would then be updated without any typing. Examples are leading or trailing spaces in an email or URL field, a line break in a single-line field, or an invalid string in a number field.
  • Untested paths: the trim/number/lazy modifiers and dynamic :type inputs follow the same code but have no dedicated tests. I also didn't add a test for the excluded types, because jsdom may not adjust values the way real browsers do.

Changes are uncommitted in the working tree.
