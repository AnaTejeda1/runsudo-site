Make default baseUrl https://example.org/

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches make the default baseURL https://example.org/. Patch A puts it in `newDefaultConfig()`, the function that already holds Hugo's other defaults (taxonomies, sitemap, environment). User config, language config and the `--baseURL` flag then override it through the normal merge. Patch B instead overwrites an empty `c.BaseURL` inside `CompileConfig`. That works, but it replaces any empty value, including one the user set explicitly, and it hides a default inside compilation logic instead of the defaults table. It also leaves the raw config value empty for any code that reads it before compilation. Patch A's placement addresses the root cause more cleanly.

Tests: Patch A adds focused integration tests for the default value (checking both `Configs.Base.BaseURL` and the per-site compiled BaseURL), the multilingual non-multihost case, and an explicit override. It also adds a command testscript covering the `--baseURL` flag and a server testscript showing the default is rewritten to localhost in `hugo server`. That is much broader scenario coverage. Patch B adds one simple test for set, unset and "/" cases. Its other test changes mostly pin `baseURL = "/"` to keep old expectations, which tests less of the new behaviour than A's approach of updating expectations to the new absolute URLs.

Scope and craft: Patch B includes a lot of unrelated reformatting (splitting `AssertFileContent(` arguments onto new lines across many tests). This obscures the actual change and accounts for most of its diff. Patch A's diff is limited to the behaviour change and its test consequences.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
