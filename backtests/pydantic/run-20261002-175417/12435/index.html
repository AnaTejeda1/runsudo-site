Add FastMCP and MCP's python-sdk to third-party tests

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches add the two requested jobs (FastMCP and the MCP python-sdk) to third-party.yml and wire them into create-issue-on-failure, so both address the issue's ask.

Patch A is tightly scoped and follows the surrounding conventions. It installs both the local pydantic and `./pydantic-latest/pydantic-core` after uninstalling both packages. This matters if pydantic main depends on an unreleased pydantic-core in the same repo.

Patch B has some genuinely useful refinements for FastMCP:
- unsets FORCE_COLOR
- excludes integration and subprocess markers
- adds a timeout
- disables the MCP smoke tests
- uses the PrefectHQ repo name

However, Patch B only uninstalls and reinstalls `pydantic`, not `pydantic-core`. That diverges from the pattern Patch A uses and risks a version mismatch or resolution failure against pydantic main.

Patch B also brings substantial unrelated churn across other jobs:
- adds `tests/` arguments to Beanie, Django Ninja and FastDepends
- replaces actions/checkout with a raw `git clone` for ODMantic
- duplicates the `tests` path in the ODMantic command
- adds a redis service to Polar
- rewrites Dify's uv setup and its test command

None of this is requested, and it changes the behavior of existing jobs, which adds risk and obscures the fix.

Neither patch adds tests, which is expected for CI config. Weighing correctness of the dependency install and scope, A is the cleaner, lower-risk fix. B's FastMCP filtering is a plus but does not outweigh the unrelated modifications and the missing pydantic-core install.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
