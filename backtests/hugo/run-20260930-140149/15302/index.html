Add config option security.http.proxyFromEnvironment = false

Worse

The merged fix was judged better than our patch.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches add `security.http.proxyFromEnvironment`, defaulting to false. With the flag off, both clear the transport's Proxy, so the dial-time address check sees the real destination. That fixes the core issue in both.

The difference is what happens when the flag is enabled.

- **Patch B** keeps the default `ProxyFromEnvironment`, and the dial check then validates the proxy address. Its own docs admit that a typical local or corporate proxy on a loopback or private address is refused under the default policy. Users must loosen `http.urls`, which also disables the resolved-address hardening entirely. That makes the opt-in awkward and pushes users toward weaker settings.
- **Patch A** resolves the proxy per request and passes it through the request context. It skips the address check only for the dial to the chosen proxy, and still validates every direct dial, including a direct request to the proxy's own address. This is a more careful design that keeps the hardening intact when the flag is on. It is more complex, but the logic is well commented, and `canonicalAddr` mirrors `net/http`.

**Tests:** Patch A adds a real transport test with httptest servers. It checks that the proxy is ignored by default, used when enabled even though it is on loopback, and that direct loopback dials, including to the proxy address, are still denied. It also updates the TOML and default-decode tests. Patch B adds no tests.

**Craft:** Patch A updates `docs.yaml`, documents the resolved-address validation, and adds a newIn marker. Patch B uses `omitempty`, which hides the option from the default config dump.

Overall, Patch A is more usable and safer when enabled, and it is well tested.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The issue

View on GitHub

This is a security hardening issue.

In d6e6f9e500eebdeae8e28de830fff2e3bfc7d534 (unreleased) we added a dial-time URL validation.

If proxied (e.g. HTTPS_PROXY set on users machine or in CI) the above validation will only see the proxy address. There's no workaround for that, but I suggest by adding a new security.http.proxyFromEnvironment bool config flag (default disabled).

Thanks to @Reload3d for reporting this issue.

What the agent reported

I added the security.http.proxyFromEnvironment option, off by default, but none of it has been tested: this sandbox has no network and no Go module cache, so the affected packages don't build here. I wrote regression tests, but since I never saw them compile or pass, I removed them as the task rules require. The final diff therefore contains no test, even though the rules require one; I couldn't meet both rules here.

What was wrong: the remote-fetch transport (newSecureBaseTransport in resources/resource_factories/create/create.go) is a copy of Go's default HTTP transport, which uses whatever proxy HTTP_PROXY/HTTPS_PROXY/NO_PROXY point to. When one of those is set, Hugo connects to the proxy, so the new check on the connection address saw only the proxy's address and never the real remote host. That let a proxied request get past the check for internal addresses.

What I changed:

  • config/security/securityConfig.go: new field ProxyFromEnvironment bool \json:"proxyFromEnvironment,omitempty"\`inHTTP, defaulting tofalse. It is set with[security.http] proxyFromEnvironment = trueorHUGO_SECURITY_HTTP_PROXYFROMENVIRONMENT=true. Theomitemptykeeps the default printed security config unchanged, soTestToTOML` keeps its current expected output.
  • create.go: newSecureBaseTransport turns off the environment proxy (base.Proxy = nil) unless the option is set. Without a proxy, the address check sees the real destination.
  • docs/content/en/configuration/security.md: documented http.proxyFromEnvironment, including the limit below.

Test evidence: ./bt-test ./config/security/ ./resources/resource_factories/create/ reported [setup failed] for both packages because Go couldn't download modules (lookup proxy.golang.org ... server misbehaving). No test compiled, old or new. I considered restoring the tests to the diff, but the rules say to drop tests you haven't seen pass, so they're gone. They were:

  • Transport: with the default config the transport has no proxy; with the option on, it uses http.ProxyFromEnvironment.
  • Config: decoding proxyFromEnvironment = true works, and the default is false.

These need to be re-added and run once dependencies are available. A reviewer subagent read the change and found it correct: the proxy is dropped by default, the setting decodes from config and from the env var, and no other remote-fetch code was missed.

Things to know:

  • Breaking change: anyone using resources.GetRemote behind HTTPS_PROXY today will bypass the proxy after upgrading until they turn the option on. The issue asks for this, but it needs a release note.
  • Proxies on private addresses: with the option on, the address check still runs against the proxy. Under the default security.http.urls, a proxy on a loopback or private address (for example 127.0.0.1:3128 or 10.x) is refused. I kept this strict behaviour rather than weaken the check, and the docs tell users they must then also customize security.http.urls. Skipping the check whenever a proxy is used would be the alternative.

Requirements:

  1. Add security.http.proxyFromEnvironment as a bool: implemented in securityConfig.go; the reviewer confirmed it decodes, but no test has run.
  2. Default disabled: implemented (the default is false); the test for this was removed because it couldn't run.
  3. Stop the environment proxy from hiding the real address from the check: implemented in newSecureBaseTransport; the reviewer confirmed the logic, but no test has run.
  4. Document the option: done.
