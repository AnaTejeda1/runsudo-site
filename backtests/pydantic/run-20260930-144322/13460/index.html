Unexpected serialization schema with ValidateAs

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the core problem the same way. They build a serialization schema from the annotated `source` type (int) and wrap it in a `wrap_serializer_function_ser_schema`, so dumping no longer checks against `list[int]` and the warning goes away. Both fall back to an any-schema when the source type cannot produce a schema.

Patch B is more complete in two ways:

1. **Serialization-mode JSON schema.** B passes `return_schema=source_schema` to the wrap serializer. Without it, JSON schema generation for a function-wrap serializer has no return schema and falls back to the validation schema (an array). B's test asserts that serialization mode gives `{'type': 'integer'}` and validation mode gives the array. Patch A omits `return_schema`, so its serialization JSON schema would likely still report `list[int]`.

2. **Test strength.** B's test runs the issue's exact reproduction with warnings turned into errors. That fails before the fix and directly checks the reported symptom. It also checks `model_dump`, `model_dump_json` and both JSON schema modes. A's first test only checks `model_dump_json` output. Before the fix that output was already `{"x":8}`, only with a warning, so the test would likely pass without the fix. A's second test (arbitrary-type fallback) is useful but only a small check.

On craft: A calls `handler(source)`, which re-applies the remaining annotation pipeline. B's `handler.generate_schema(source)` is cleaner. A catches the broader `GENERATE_SCHEMA_ERRORS`, which is a slightly more robust fallback than B's `PydanticSchemaGenerationError`. A also sets `schema['serialization']` by direct mutation instead of passing the constructor argument.

B's removal of two `pyright: ignore` comments in `PlainValidator` is unrelated churn. It could at most surface a type-checker complaint, with no runtime effect. That is a minor ding and does not outweigh B's advantages in correctness and testing.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

What the agent reported

I fixed the ValidateAs bug: model_dump() now returns {'x': 8} with no warning, and the regression test for your example passes. Only the two files below are changed, left uncommitted.

What was wrong: ValidateAs.__get_pydantic_core_schema__ (in pydantic/functional_validators.py) built the whole core schema from from_type (list[int]). The value that actually gets stored is the annotated type (int), so the serializer expected a list, got an int, and raised PydanticSerializationUnexpectedValue. The serialization-mode JSON schema was also wrong: it described x as an array instead of an integer.

What I changed:

  • The fix: ValidateAs now serializes using the schema of the annotated type. This follows the pattern PlainValidator already uses in the same file.
  • Unsupported annotated types: if pydantic can't build a schema for the annotated type (for example an arbitrary class, as in the existing test_validate_from), serialization falls back to working out the type from the value at runtime.
  • Reviewer's point: the reviewer found that reusing the annotated type's own serializer could break for custom types with wrap or include/exclude serializers. I changed it to always serialize through the annotated type's full schema, which avoids that.
  • New test: test_validate_as_serialization in tests/test_types.py runs your exact example with warnings turned into errors. It checks d.x == 8, model_dump() == {'x': 8} and model_dump_json() == '{"x":8}'. It also checks that the JSON schema is an array of integers in validation mode and an integer in serialization mode.

Test evidence:

  • Before the fix: the new test failed at model_dump() with PydanticSerializationUnexpectedValue(Expected list[int] ... input_value=8, input_type=int).
  • After the fix, targeted run: 9 passed, covering the new test, test_validate_from and the docstring examples in functional_validators.py.
  • After the fix, wider run: ./bt-test tests/test_types.py tests/test_validators.py tests/test_serialize.py tests/test_json_schema.py gave 1738 passed, 1 failed, 7 skipped, 4 xfailed.
  • The one failure: test_v1_validator_deprecated also fails with my changes stashed. It compares file paths (/work/... against /workspace/...), so it's a mismatch in the test environment, not something this fix caused.

Risks I didn't address:

  • A custom class whose own __get_pydantic_core_schema__ delegates to ValidateAs(..., cls) would now recurse forever, because building the annotated type's schema calls itself again. The docs don't show this pattern.
  • Errors other than "can't build a schema" for the annotated type, such as an unresolved forward reference, now show up when the model is defined, not later.

Requirements:

  1. No serialization warning for ValidateAs in the reported scenario: done; the new test turns warnings into errors and passes.
  2. model_dump() returns {'x': 8}: done; asserted, along with model_dump_json().
  3. Serialization-mode JSON schema describes the stored type: done; asserted integer in serialization mode and array in validation mode.
