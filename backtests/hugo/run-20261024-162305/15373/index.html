Support relative path calls in partials

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches implement the same core design: intercept names beginning with "./" or "../" in Include/IncludeCached, resolve them against the calling partial's directory taken from the current-template context, reject use outside partials and escapes above the partials root, and track a decoratorOwner so relative calls inside a `with partial` block resolve against the enclosing partial. Both pass eight of nine independent tests. The difference is the templates.Defer case. Patch A tries to support it by copying category and decoratorOwner into the deferred TemplInfo in addDeferredTemplate, but deferred templates are shared between owners with identical bodies, so the stored PathInfo belongs to whichever owner registered first. Two partials in different directories with textually identical defer blocks calling "./util.html" therefore both resolve to the first owner's sibling. The independent test TestBtJudgeRelativeInsideDeferIdenticalBodies confirms this: FAIL-ASSERT on A, PASS on B. Patch A's own defer test only has a single owner, so it does not catch the bug. Patch B instead resolves deferred templates via cur.Parent, the template that actually called templates.Defer, with an explicit comment about body sharing and a test with two identical defer blocks in different directories. This is a genuine correctness gap in A on a scenario the issue's "full path independent" goal implies, and A's change to addDeferredTemplate (setting category on deferred templates) also adds some risk of side effects elsewhere. B additionally covers the degenerate "./" case and flattens nested decoratorOwner chains at construction time; A's loop handles the chain equivalently. Tests are comparable in quality otherwise, with B also asserting that partialCached keys differ per directory. Docs are adequate in both. B wins on correctness.

The issue

View on GitHub

Right now partial calls only supports path relative to layout/partials and themes/<THEME>/layouts/partials/*<PARTIALNAME> (taken from the documentation).

This is fine when we have few partials but can become a pain if we need to organize them in subdirectories.

What i propose is to add support for relative paths like in this example :

{{ partial "./foo" ... }}
{{ partial "../bah" ... }}

Why ?

Having this feature could be beneficial in a lot or ways :

  • it avoid us having to remember and write the full partial path when it's not needed (for example utility partials that are only called and only used by a on partial)
  • It could allow us to reorganize partials way more easily, as relative paths would full path independent

How to implement

If the path in a partial call starts with "./" or "../", it's a relative path. Otherwise it's an "absolute" path (relative to layout/partials).

I'm against adding the current directory of the current partial to the lookup search directly though, as theme and site authors currently assume this would call to the partial root directory. Perhaps we could add this to the future, if my proposal is adopted by the community.
