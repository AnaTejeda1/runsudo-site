suspense.resolve() is called without a pending branch.

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

The issue's scenario: an async-setup component navigates away during setup, so it is unmounted while the suspense is still pending. Its setup promise later settles, and the registerDep callback runs `suspense.resolve()` after the boundary has already resolved or switched branches. That triggers the 'resolve() called without a pending branch' warning.

Patch B targets this root cause directly, in three ways:
- It adds a `!instance.scope.active` check in the registerDep `.then`. `isUnmounted` is set in a post-render effect that is buffered while the suspense is pending, so the existing `isUnmounted` guard misses this case.
- When a component with an unresolved async dep is unmounted, it decrements the suspense's `deps`. If that empties the boundary, it defers `resolve()` to a post-flush callback with pendingId and pendingBranch re-checks, so the boundary still resolves to the replacement content.
- It handles the analogous case of a pending suspensible nested Suspense being unmounted, and removes the placeholder comment of a still-pending async component.

B's tests reproduce the issue directly: a component reassigns the view during async setup, then its setup resolves. The tests cover sync replacement, async replacement, removal by a nested update, and a nested suspensible suspense. They check that nothing stale renders and that onResolve fires exactly once. These would fail before the change.

Patch A only brackets the same-root pending-branch patch with `deps++`/`deps--`. This stops a nested suspensible suspense from resolving the parent mid-patch. It does nothing about an unmounted async component whose setup promise later settles and calls resolve on a boundary with no pending branch. Its tests cover a different nested-suspensible scenario, not the navigate-during-setup case.

B touches more code (renderer unmount path), which adds some risk. But it is guarded carefully and is the only patch that actually fixes the reported bug.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
