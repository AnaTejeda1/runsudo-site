Make .Render take additional data

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches change the Render signature to variadic `any` across the interface, lazy provider, nop page, and test helper, and both thread a custom data context into executeToString. The decisive difference is argument order. The issue explicitly proposes `PAGE.Render [DATA] NAME` with the optional data before the template name, and Patch A implements exactly that (0 args error, 1 arg = name, 2 args = data then name). Patch B instead implements `VIEW [CONTEXT]`, reversing the order, so the call form the issue specifies (`.Render (dict ...) "summary"`) would fail in B with a cast error on the dict. The independent tests passing on both suggests those tests did not pin the order, so they do not rescue B here. Patch A is also more complete: it updates the user-facing docs (Render.md signature, example, and the partial-comparison table that previously said extra context could not be passed), and its tests cover the no-data path, data path, subdir view resolution, nil/empty layout, too-many-args, invalid layout type, and template-not-found with data. Patch B's tests are narrower (one happy path, two error cases) and it ships no documentation. Both handle errors reasonably; A's error messages reference the documented `[DATA] NAME` form while B's reference its own invented `VIEW [CONTEXT]` form. A resolves the issue as specified; B solves a slightly different API.

View on GitHub

See https://gohugo.io/methods/page/render/#article
See #15076

PAGE.Render NAME

This has been discussed before.

  • The contract has always been that the templates that .Renders gets the data context as e.g. page.html, a page.Page.
  • We can only pass 1 argument to Go's template renderer, which I guess is the blocking reason for not having done this sooner.

So, if we want to do:

PAGE.Render [DATA] NAME

I'm guessing we have 2 top-level options:

  • We say that if DATA is set, we use that as the context passed to the templates,. else PAGE.
  • We somehow (e.g. by embeding it in a { DataAdditionalContext, Page } struct or putting it into the current context.Context) wrap the Page so you can do both .RelPermalink and .DataAdditionalContext (naming of the latter is just picked out of a hat without thinking too hard.
