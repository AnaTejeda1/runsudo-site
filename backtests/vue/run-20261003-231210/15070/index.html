SSR memory leak after a render error in a dynamic component

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

The leak happens because `openBlock()` runs, the content throws before `createBlock()`/`closeBlock()`, and a stale `currentBlock` is left behind. That block then collects every block-tracked vnode created later. Both patches stop this for the reported case, but in different ways.

Patch B handles it at the error boundaries. It adds `resetBlockStack()`, which clears both `blockStack` and `currentBlock`, and calls it in two places: when `ssrRender` throws inside `renderComponentSubTree`, and in `renderComponentRoot`'s catch. The second call fixes a real latent bug: that catch previously did only `blockStack.length = 0` and left `currentBlock` stale. So B covers the reported dynamic-component slot case plus any other open-block-then-throw path, including render-function components and inline `v-if` blocks. It does this without touching hot paths.

Resetting the whole stack is safe here. Blocks are opened and closed synchronously, and the error propagates to reject the render anyway.

Patch A unwinds locally. It adds try/catch to `renderSlot` and stack-size bookkeeping in a `finally` inside `withCtx`. That fixes slot-originated errors, and it also restores `_d` correctly. However:
- It adds work to two very hot runtime paths (`renderSlot`, and every `withCtx` call).
- It leaves the stale-`currentBlock` bug in `renderComponentRoot` untouched, so an open block thrown from a render function outside a slot can still leak.

Tests: B's tests check `blockStack` and `currentBlock` directly after a failed render, both in SSR (including the `v-if` case) and in runtime-core. They are deterministic, run in the normal suite, and would fail before the fix. A's tests are GC-based. They need `--expose-gc` and a vitest config change, and they are skipped when GC isn't exposed. They are closer to the issue's symptom but more brittle.

Overall, B is the more complete fix at the root cause, with lower runtime cost and more reliable tests.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Steps to reproduce

  • download the reproduction from stackblitz (won't work there, needs to be run locally)
  • run pnpm i && pnpm leak
  • see the heap size & alive app instances grow with each request after the single failed render

The script renders 500 fresh SSR apps, which all get garbage-collected. Then renders one app whose slot content throws, then renders 500 more identical healthy apps, which will never be garbage collected afterwards.

A dynamic component <component :is> with a <slot /> is needed for this to reproduce.

Card

<script setup>
    defineProps({ tag: { type: String, default: 'div' } })
</script>

<template>
    <component :is="tag" class="card">
        <slot />
    </component>
</template>

app:

<script setup>
    defineProps(['payload'])  // one request renders with `payload: null` → throws
</script>

<template>
    <main>
        <Card>{{ payload.title }}</Card>
    </main>
</template>

What is expected?

A failed renderToString should not affect subsequent renders and all apps rendered after it should get garbage collected.

What is actually happening?

Every app created after the single failed render is kept in memory forever.
