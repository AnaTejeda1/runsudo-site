Fix timezone handling in FilesPipeline stores

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches make the same correct S3/GCS fix (call `.timestamp()` on the tz-aware datetime instead of `time.mktime(dt.timetuple())`, which reinterpreted UTC wall-clock as local time), and both replace the FTP `float(MDTM)` nonsense with real `YYYYMMDDHHMMSS[.fff]` UTC parsing. The decisive difference is the FTP fractional-seconds edge. RFC 3659 allows an arbitrary number of fraction digits (`1*DIGIT`); Patch A's `_mdtm_to_timestamp` splits on '.' and parses the fraction with `float(f"0.{fraction}")`, so any length works. Patch B uses `strptime` with `%f`, which only accepts 1-6 digits; a longer fraction raises `ValueError`, which `stat_file`'s broad except swallows into `{}` (hence the independent test's `KeyError: 'last_modified'`), silently forcing a re-download. The independent tests confirm: A passes all 9, B fails `test_mdtm_reply_with_long_fraction`. On tests, A's `non_utc_local_timezone` fixture (TZ=+05:45 via tzset, skipped only where tzset is unavailable, i.e. Windows) makes the S3/GCS tests genuinely fail before the fix and asserts hard UNIX constants; its FTP tests cover plain and fractional MDTM against constants and tighten the real-server test to `approx(time.time())`. B's approach of feeding a +09:37-offset datetime is also a valid regression check and is portable, but its FTP test omits the >6-digit case its implementation breaks on. Scope is equivalent; craft slightly favors A's documented helper with doctest examples over inline conditional format selection. A is the better fix.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours.
