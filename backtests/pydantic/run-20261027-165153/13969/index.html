Huge int input to a timedelta field wraps to a small wrong timedelta

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches make the same root-cause change in int_as_duration: replace the truncating `as u32` on the day count with `u32::try_from` and map the failure to ParseError::DurationDaysTooLarge via map_timedelta_err, so both produce the same time_delta_parsing error as the float path. The independent tests confirm this: all issue scenarios (Python and JSON, positive and negative, 86400*2**32 and 86400*(2**32+5)) go from failing on base to passing under both, and the two i64-extreme cases fail identically under both with time_delta_type, so neither patch separates on correctness. A's combinator chain and B's let-else are both idiomatic; A's rewritten comment is slightly more precise about why seconds is still safe to cast. The difference is in tests and scope. Patch A adds regression cases in the pydantic-core test_timedelta.py, which is the layer where the fix lives, covering the boundary (999,999,999 days passes, 1,000,000,000 fails), the exact issue values, and negative inputs, plus a pydantic-level test that checks the error type on both Python and JSON paths. Some of A's extra cases (the i64 extremes and the string-input variants) carry risk of not matching the expected message given the time_delta_type result seen in the harness, but that is an unverified concern rather than evidence. Patch B only adds pydantic-level tests, and bundles an unrelated refactor of the TimedeltaModel fixture into a TypeAdapter fixture, rewriting two existing tests; its new test also oddly re-asserts the in-range case inside every parametrized run and carries a placeholder docstring. That churn obscures the fix and earns no credit. With equal fixes, A's tests at the core layer and narrower scope make it the better patch.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Description

A timedelta field accepts an integer number of seconds that is far outside the timedelta range and returns a small, wrong value instead of raising a ValidationError. Any integer of at least 86400 * 2**32 seconds has its day count wrapped modulo 2**32, so 86400 * (2**32 + 5) validates to timedelta(days=5), from Python and from JSON, and the negative value gives timedelta(days=-5). The same number passed as a float is rejected with time_delta_parsing, so only the int path is affected. This matters for untrusted JSON input: a client can send a huge number and the model silently holds a plausible small duration.

Output of the example below:

python, int input:    datetime.timedelta(days=5)
python, -int input:   datetime.timedelta(days=-5)
json, int input:      datetime.timedelta(days=5)
python, int 86400*2**32: datetime.timedelta(0)
python, float input:  ValidationError time_delta_parsing
expected for all int inputs: ValidationError time_delta_parsing, like the float input

I expected every one of the int inputs to fail with time_delta_parsing, the same as the float input. Strict mode is not affected, since strict JSON rejects an int with time_delta_type.

Cause: int_as_duration in pydantic-core/src/input/datetime.rs (lines 709-716 at 68a839f07) computes let days = (total_seconds / 86400) as u32; on a u64. The as cast truncates, and the comment above it only covers seconds and microseconds. It is reached from the lax int branch of validate_timedelta in pydantic-core/src/input/input_python.rs (line 741) and pydantic-core/src/input/input_json.rs (line 396). float_as_duration a few lines below casts an f64 with as u32, which saturates, so Duration::new rejects the value there.

Proposed fix: use u32::try_from(total_seconds / 86400) and map the failure to the same TimeDeltaParsing error the float path ends up with. A Python and JSON test with 86400 * 2**32 and 86400 * (2**32 + 5) would cover it, since test_timedelta.py has no int case above timedelta.max today.

I'm happy to open a PR for this.

Example Code

from datetime import timedelta

from pydantic import BaseModel, ValidationError


class M(BaseModel):
    d: timedelta


big = 86400 * (2**32 + 5)  # 2**32 + 5 days in seconds, far above timedelta.max

print('python, int input:   ', repr(M(d=big).d))
print('python, -int input:  ', repr(M(d=-big).d))
print('json, int input:     ', repr(M.model_validate_json(f'{{"d": {big}}}').d))
print('python, int 86400*2**32:', repr(M(d=86400 * 2**32).d))

try:
    M(d=float(big))
except ValidationError as e:
    print('python, float input:  ValidationError', e.errors()[0]['type'])

print('expected for all int inputs: ValidationError time_delta_parsing, like the float input')
