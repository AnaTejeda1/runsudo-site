Experimental pipeline: every constraint chained after ge/lt/le is dropped from the JSON schema

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the reported root cause: they stop wrapping the schema in a `function-after` validator once the native `ge`/`lt`/`le`/`multiple_of` field has been set. That lets later constraints in the chain reach the JSON schema. The difference is what happens when the same constraint appears twice.

**Patch A introduces a validation regression.** It writes the native field unconditionally and drops the fallback check, so a repeated constraint overwrites the earlier one. `validate_as(int).ge(5).ge(1)` ends with `ge=1` and accepts 3. `multiple_of(2).multiple_of(3)` ends with `multiple_of=3` and accepts 3. Before the patch, the earlier bound survived inside the function wrapper, so validation was correct; Patch A breaks that. The issue specifically stresses that validation is currently correct, so this is a real step backward.

Patch A also removes the type-match guards (int bound on int schema, float on float, Decimal on decimal). It relies on its own comment that pydantic-core will cast a mismatched bound, such as `gt=1.5` on an int schema. That is unverified and riskier than keeping the guarded fallback. It does add tests for mixed-type bounds and the chain cases from the issue, but nothing for repeated constraints.

**Patch B avoids that regression.** It follows the `native_constraint_applied` shape the issue proposes, consistently across Gt/Ge/Lt/Le/MultipleOf. It keeps the type-match guards, so mismatched bounds still go through the fallback validator. When a bound is repeated it merges them, keeping the stricter value via `max`/`min`. For a second `multiple_of`, which can't be merged, it keeps the first native and adds a function check for the second.

Patch B also extends the same treatment to `Len` and adjusts `str_strip` so a length check placed before stripping still sees the unstripped value. That goes beyond the issue, but it is coherent, needed for the `Len` change to be correct, and tested.

Patch B's tests check both the JSON schema and validation for every scenario in the issue, plus float and Decimal variants. They also cover repeated constraints keeping the strictest bound, len-then-strip ordering, and the Gt fallback on a type mismatch.

On correctness, which is the most important criterion, Patch B is clearly better.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The issue

Initial Checks

  • I confirm that I'm using Pydantic V2

Description

In the experimental pipeline API, chaining constraints silently drops every bound after the first from the generated JSON schema. Validation stays correct - only the published schema is wrong, which makes it easy to miss.

All bounds below are non-zero, so this is not #13450 (falsy zero bounds in Interval). Observed identically on released 2.13.4 and on main (2.14.0a1).

expressionJSON schemavalidation
validate_as(int).ge(1).le(100){"minimum": 1, "type": "integer"}0 reject, 50 accept, 200 reject
validate_as(int).le(100).ge(1){"maximum": 100, "type": "integer"}0 reject, 50 accept, 200 reject
validate_as(int).constrain(Interval(ge=1, le=100)){"minimum": 1, "type": "integer"}0 reject, 50 accept, 200 reject
validate_as(int).ge(1).le(100).multiple_of(5){"minimum": 1, "type": "integer"}correct
validate_as(int).gt(1).lt(100) (control){"exclusiveMinimum": 1, "exclusiveMaximum": 100, ...}correct
Annotated[int, Ge(1), Le(100)] (control){"minimum": 1, "maximum": 100, ...}correct

So .ge(1).le(100).multiple_of(5) publishes a schema advertising any integer >= 1, while the validator rejects 200 and 52. For FastAPI that means the OpenAPI component and every generated client disagree with the server.

Cause

In _apply_constraint(), the Ge, Lt and Le branches apply their fallback function validator unconditionally - including when the native core-schema field was just set:

elif isinstance(constraint, annotated_types.Ge):
    ge = constraint.ge
    if s and s['type'] in {'int', 'float', 'decimal'}:
        s = s.copy()
        if s['type'] == 'int' and isinstance(ge, int):
            s['ge'] = ge          # native constraint applied...
        ...

    def check_ge(v: Any) -> bool:
        return v >= ge

    s = _check_func(check_ge, f'>= {ge}', s)   # ...and then wrapped anyway

_check_func wraps the schema in function-after. The next constraint in the chain sees s['type'] == 'function-after', which is not in {'int', 'float', 'decimal'}, so it cannot set its own native field and survives only inside an opaque callable that JSON-schema generation cannot read. Core schema for .ge(1).le(100):

{'type': 'function-after',
 'function': ...,                       # <- le(100) lives in here, invisible to the schema
 'schema': {'type': 'function-after',
            'function': ...,            # <- redundant ge check
            'schema': {'type': 'int', 'ge': 1}}}

Gt is the control that works, and only by accident: its fallback sits in an else:, so nothing is wrapped when the native constraint applies.

Relationship to the open PRs in this function

Two in-flight PRs each fix one branch of this, for unrelated reasons, and between them they leave Ge, Lt and Le untouched:

  • #13473 adds a native_constraint_applied flag to MultipleOf to avoid a float parity problem. Same shape as the fix needed here.
  • #13446 restructures Gt so the fallback lands inside the numeric branch.

Worth flagging on the second one: #13446's description argues that Gt is uniquely broken and holds up Ge/Lt/Le/MultipleOf as the correct model, because they "always apply" the check and so enforce the bound on a type mismatch. That is true of validation, but always applying it is exactly what destroys the schema. Gt is uniquely broken for validation; the other four are broken for schema. Whichever way this is fixed, it probably wants to be one symmetric change across all five branches rather than three separate patches.

Example Code

from typing import Annotated

from pydantic import TypeAdapter
from pydantic.experimental.pipeline import validate_as

ta = TypeAdapter(Annotated[int, validate_as(int).ge(1).le(100)])

print(ta.json_schema())      # {'minimum': 1, 'type': 'integer'}   <- no maximum
ta.validate_python(200)      # ValidationError, as it should be

# control: the same constraints without the pipeline
import annotated_types
print(TypeAdapter(Annotated[int, annotated_types.Ge(1), annotated_types.Le(100)]).json_schema())
# {'maximum': 100, 'minimum': 1, 'type': 'integer'}
