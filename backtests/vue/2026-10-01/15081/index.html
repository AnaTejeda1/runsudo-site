SSR hydration warning: dynamic props on SVG elements are patched as properties instead of attributes

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the root cause the same way. During hydration they derive the element's namespace ('svg' / 'mathml' / undefined) from `el.namespaceURI` and pass it to `patchProp` instead of `undefined`. `patchProp` then routes SVG props through `setAttribute`, as client rendering does. Patch A also passes the namespace on the `onClick`-only branch. That is harmless but does not matter for the reported bug, since event listeners ignore namespace.

The real difference is the tests. Patch A's test checks `viewBox` on a jsdom `<svg>`. jsdom does not appear to implement a getter-only `viewBox` IDL property on SVGSVGElement, so `shouldSetAsProp` would likely fall back to `setAttribute` even without the fix. The test would then pass before the change and gives little regression protection. Patch B's first test has the same jsdom limitation. Its second test, however, defines a getter-only `width` on a `<foreignObject>` inside an `<svg>`, reproducing the read-only IDL property behind the reported TypeError. Without the namespace fix, `patchProp` would try to set it as a DOM prop and fail, leaving the attribute at '24'. With the fix, the attribute becomes '48'. That test genuinely fails before and passes after. It also exercises nested SVG elements, not just the root `<svg>`, and runs with `__DEV__=false` to cover the production force-patch path.

Scope and craft are comparable. A's helper function is slightly tidier, and B inlines the computation inside the loop's guard branch. Neither matters much. B wins on stronger, more meaningful test coverage.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

  1. Open the reproduction.

What is expected?

During hydration, dynamic props on SVG (and MathML) elements width, height, viewBox, etc. should be patched as attributes (via setAttribute) exactly as they are during normal client-side rendering. Hydration should be silent.

What is actually happening?

Since 3.5.39, dynamic props on SVG elements are patched as DOM properties during hydration, which throws for read-only SVG IDL properties:

[Vue warn]: Failed setting prop "viewBox" on <svg>: value 0 0 24 24 is invalid.
TypeError: Cannot set property viewBox of #<SVGSVGElement> which has only a getter
    at patchDOMProp
    at patchProp
    at hydrateElement
    at hydrateNode
    at hydrateSubTree
    at <App>

Nothing is visually broken but the console is flooded with warnings.

We ran across this issue in a Nuxt app but I believe the issue is coming from Vue core

What the agent reported

I fixed it: during hydration, dynamic props on SVG elements are now set as attributes again, so the Failed setting prop "viewBox" on <svg> warning no longer appears. The changes are uncommitted in the working tree.

What was wrong: the hydration code always passed undefined instead of the element's namespace when it applied dynamic props. The DOM renderer therefore treated an <svg> like a plain HTML element and tried to write viewBox as a property. That property is read-only on SVG elements, hence the warning. The problem appeared when hydration started force-patching dynamic props (commit 024cf06da, #9033).

What I changed (packages/runtime-core/src/hydration.ts):

  • A new helper, getElementNamespace(el), returns 'svg', 'mathml' or undefined based on the element's own namespace. It uses the element itself so that <foreignObject> counts as SVG, which is how normal client rendering treats it.
  • Both places in hydrateElement that applied props now pass this namespace instead of undefined. One is the main props loop; the other is the shortcut for click listeners.

Test evidence:

  • I added a regression test in packages/runtime-core/__tests__/hydration.spec.ts: "patches dynamic props on SVG elements as attributes when hydrating". The server HTML has <svg viewBox="0 0 10 10"> and the client renders viewBox: '0 0 24 24' as a dynamic prop. The test checks that the warning is not logged and that the attribute ends up as '0 0 24 24'.
  • Before the fix this test failed with expected "Failed setting prop "viewBox" on <svg>" not to have been warned. The final reviewer suspected the test environment (jsdom) might not reproduce the bug, but this pre-fix failure shows it does. After the fix it passes.
  • The full hydration spec passes (113 tests). Running hydration together with the runtime-dom and server-renderer tests gives 650 passed and 2 failed. The 2 failures are GC tests in ssrRender.spec.ts ("render error leak"), and they fail the same way with my changes stashed, so they were already failing.

Requirements:

  1. Dynamic SVG props are patched with setAttribute during hydration, like client rendering: done; covered by the new test.
  2. Hydration is silent, with no "Failed setting prop" warning: done; the new test asserts the warning is not logged.
  3. The viewBox case from the report: this is the exact scenario the test covers.
  4. The same for width, height, etc.: these go through the same code path as viewBox, so the fix covers them. I didn't add a separate test for them.
  5. The same for MathML: the namespace is now passed as 'mathml', which matches client rendering. The DOM renderer's attribute-vs-property choice doesn't change on 'mathml', so nothing behaves differently in practice. There is no dedicated test.

The reviewer also found no unrelated changes. One side effect: class on SVG elements is now written with setAttribute during hydration instead of className, which also matches client rendering.
