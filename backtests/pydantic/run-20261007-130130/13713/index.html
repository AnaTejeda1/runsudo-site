str_min_length and str_max_length are enforced by the validator but absent from the JSON schema

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fill in `minLength`/`maxLength` in `str_schema` from config when the core schema leaves them unset. Both keep the precedence rule from the issue: a field-level length replaces the config value. The difference is where each patch reads the config and which strings it applies it to.

Patch B reads `self._config`, the ConfigWrapper stack, and applies it to every call that reaches `str_schema`. That includes strings pydantic-core never checks with the string validator:
- the string branch of `Decimal`;
- `format`/`to-string` serializer schemas;
- serializer `return_schema`s and computed-field return schemas in serialization mode;
- `json_schema_input_schema` of function validators;
- `ImportString`.
A model with `str_max_length=3` would therefore advertise `maxLength: 3` on decimal strings and serialized outputs. That is a new mismatch between schema and behaviour, the same class of bug the issue reports. B also does not model pydantic-core's config scoping. It cannot handle top-level `definitions` generated outside the model's config push, such as type aliases and recursive aliases, or typed dicts without their own config inheriting the parent's core config.

Patch A tracks the actual core `config` blocks that pydantic-core uses: a stack pushed in `model_schema`, `typed_dict_schema` and `dataclass_schema`. It falls back to the TypeAdapter config at top level. It resolves the root config for `definitions` schemas. It explicitly suppresses the config for each non-validated string path listed above. It also changes `ImportString`'s JSON schema so it no longer goes through `str_schema`. This matches the issue's root-cause analysis: the config is applied by pydantic-core at validation time, so the schema should reflect the config in effect where validation happens.

On tests, A covers every precedence row from the issue's table and checks each case against real validation. It also tests nested models, typed dicts with and without config, dataclasses, lists and dict keys, TypeAdapter config, unvalidated strings in both modes, and alias/recursive definitions. B has a single test with config-only and field-override cases; it would fail before the change, but it misses the false-positive cases above.

A is larger, but the added scope is needed for correctness rather than being churn.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Description

str_min_length and str_max_length are enforced by the validator but do not appear in the JSON schema, so a JSON Schema validator silently accepts input the model rejects.

class Model(BaseModel):
    model_config = ConfigDict(str_min_length=3)
    s: str

Model.model_json_schema()['properties']['s']
#> {'title': 'S', 'type': 'string'}       <-- no minLength

Model(s='ab')                             #> ValidationError
jsonschema.validate({'s': 'ab'}, Model.model_json_schema())   #> accepted

The same holds for str_max_length. This is the same class of defect as #13704 — a constraint pydantic applies that a consumer of the schema cannot see — but it comes from a different place, so that fix will not cover it.

Why it happens

A field-level constraint lands on the core schema, where GenerateJsonSchema.str_schema finds it:

'schema': {'type': 'str', 'min_length': 3}

A config-level one does not. It stays in the model's config block and is applied by pydantic-core at validation time, leaving the string node bare:

{'type': 'model',
 'schema': {'type': 'model-fields',
            'fields': {'s': {'type': 'model-field', 'schema': {'type': 'str'}}}},   # <-- nothing here
 'config': {'str_min_length': 3, 'title': 'Model'}}

str_schema only reads the core schema node, so the constraint is invisible to it.

Precedence

Worth stating because it decides what the schema should say when both are present: a field-level length replaces the config one rather than narrowing it. Measured on main (952c239):

configfieldrejected lengthsschema today
str_max_length=5—8, 12{} — nothing emitted
—max_length=1012maxLength: 10 ✅
str_max_length=5max_length=1012maxLength: 10 ✅
str_max_length=10max_length=58, 12maxLength: 5 ✅
str_min_length=3—1{} — nothing emitted
str_min_length=3min_length=1noneminLength: 1 ✅

So only the config-only rows are wrong, and the fix is to fall back to the config value when the field left the key unset — the rows that already work keep working untouched.

str_strip_whitespace, str_to_lower and str_to_upper are not affected: they transform rather than constrain, and the result is still a string, so the schema stays accurate.

Example Code

import jsonschema
from pydantic import BaseModel, ConfigDict, ValidationError


class Model(BaseModel):
    model_config = ConfigDict(str_min_length=3, str_max_length=5)

    s: str


schema = Model.model_json_schema()
print(schema['properties']['s'])
#> {'title': 'S', 'type': 'string'}

for value in ('ab', 'abcdef'):
    try:
        Model(s=value)
    except ValidationError:
        print(f'pydantic rejects {value!r}')
    jsonschema.validate({'s': value}, schema)
    print(f'jsonschema accepts {value!r} -- constraint lost')
