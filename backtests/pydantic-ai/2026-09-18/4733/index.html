Description

Bug Description

AGUIEventStream.handle_tool_call_delta receives a ToolCallPartDelta after handle_builtin_tool_call_end has already been called for the same tool_call_id. This causes a TOOL_CALL_ARGS SSE event to be emitted after TOOL_CALL_END for the same tool call, which violates the AG-UI protocol and crashes the @ag-ui/client verifier.

Observed SSE Output (from curling the backend)

TOOL_CALL_START  (id: mcp_22b...)
TOOL_CALL_ARGS   (id: mcp_22b..., delta: '{"action":"call_tool",...,"tool_args":')
TOOL_CALL_ARGS   (id: mcp_22b..., delta: '}')
TOOL_CALL_END    (id: mcp_22b...)
TOOL_CALL_ARGS   (id: mcp_22b..., delta: '}')   <- stray delta AFTER end

The final TOOL_CALL_ARGS event arrives after TOOL_CALL_END, which is invalid per the AG-UI protocol spec.

Steps to Reproduce

  1. Use MCPServerTool with the OpenAI Responses API model in streaming mode via the AG-UI endpoint.
  2. Trigger a tool call that emits multiple argument deltas.
  3. Inspect the raw SSE stream (e.g. with curl).
  4. Observe a TOOL_CALL_ARGS event emitted after TOOL_CALL_END for the same tool_call_id.

Expected Behavior

No TOOL_CALL_ARGS events should be emitted for a tool_call_id after TOOL_CALL_END has been sent for that ID. The stream should be ordered: TOOL_CALL_START → one or more TOOL_CALL_ARGS → TOOL_CALL_END.

Actual Behavior

A stray TOOL_CALL_ARGS delta is emitted after TOOL_CALL_END, violating the AG-UI protocol and causing the @ag-ui/client verifier to crash/error.

Related Issues

  • ag-ui-protocol/ag-ui#1275 — TOOL_CALL_START events suppressed after tool result

Neither of the above covers this exact scenario (stray post-end delta).

  • Component: AGUIEventStream (AG-UI integration)

Summary

What was wrong

AGUIEventStream (pydantic_ai_slim/pydantic_ai/ui/ag_ui/_event_stream.py) could emit a TOOL_CALL_ARGS SSE event after TOOL_CALL_END for the same tool_call_id, violating the AG-UI protocol. The model stream can deliver a ToolCallPartDelta (dispatched to handle_tool_call_delta) after the part's PartEndEvent (dispatched to handle_builtin_tool_call_end/handle_tool_call_end). Nothing tracked which tool-call IDs had already ended, so the stray delta re-emitted args — and for builtin calls the ID still lived in _builtin_tool_call_ids, so it was even remapped and re-emitted.

What I changed (production, _event_stream.py, +11 lines)

  • Added _ended_tool_call_ids: set[str] field to track IDs whose TOOL_CALL_END was already emitted.
  • handle_tool_call_end and handle_builtin_tool_call_end now record the emitted (protocol-resolved) ID into that set.
  • handle_tool_call_delta resolves the ID (including the builtin pyd_ai_builtin|… remap) and returns early — suppressing the TOOL_CALL_ARGS — if that ID has already ended. The stored ID is the same resolved ID the delta handler compares against, so suppression works for both regular and builtin tool calls.

Test evidence

  • Added test_event_stream_no_tool_call_args_after_end in tests/test_ag_ui.py, reproducing the exact scenario (builtin tool-call start → delta → end → stray delta after end). It asserts both a full snapshot ending START → ARGS → ARGS → END → RUN_FINISHED and an explicit check that no TOOL_CALL_ARGS for that ID appears after TOOL_CALL_END.
  • The test failed before the fix (stray TOOL_CALL_ARGS {'delta': '}'} after TOOL_CALL_END) and passes after.
  • Gate: ./bt-test tests/test_ag_ui.py tests/test_ui.py → 50 passed, no regressions.

Requirements disposition

  • No TOOL_CALL_ARGS after TOOL_CALL_END for a tool_call_id; ordering must be START → ARGS → END* — Implemented, covered by the new regression test (builtin path) and verified by the full AG-UI/UI suite.
  • Reported scenario is builtin (MCPServerTool / OpenAI Responses streaming) — Implemented and tested on the builtin path with provider_name='mcp' and the prefixed pyd_ai_builtin|mcp|mcp_1 ID.

Reviewer note (non-blocking): the fix also guards the regular (non-builtin) tool-call path, which is correct by inspection but not directly covered by a dedicated test. I kept the change minimal and did not add a second test, since the reported and reproduced scenario is the builtin path; the regular path shares the identical suppression logic.
