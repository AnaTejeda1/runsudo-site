TypeAdapter config not used for JSON Schema generation

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the reported root cause the same way. Each wraps `GenerateJsonSchema.generate()` in `TypeAdapter.json_schema()` with `_config_wrapper_stack.push(self._config)`. Pushing `None` is a no-op, so adapters without config are unaffected. Either patch therefore makes the issue's example produce `base64url`.

Patch B goes further, in ways that are closely tied to the issue rather than unrelated churn:

1. It applies the same fix to the static `TypeAdapter.json_schemas()` path, which has the identical bug. It stores per-input configs and pushes them around both `generate_inner` passes in `generate_definitions()`. Without this, A still ignores adapter config when multiple adapters' schemas are generated together.
2. It stops TypedDicts and plain dataclasses without their own config from resetting to an empty config during JSON schema generation. Instead they inherit the parent config, which matches core-schema generation. B's test asserts that `dump_json` really emits base64 for these nested types. Under A, `TypeAdapter(list[TD], config={'ser_json_bytes': 'base64'}).json_schema()` would still report `binary` for the nested field, so the schema would disagree with actual serialization. That is the same class of inconsistency the issue complains about.

The edits are small and careful: `config or {}` keeps `_update_class_schema` safe, and `_get_typed_dict_config` now returns `None`.

Tests: A adds one test, `list[bytes]`, which fails before and passes after. B adds broader tests that also fail before the change: the bytes case, `ser_json_temporal` in serialization mode, base64 defaults, no config leakage to later adapters, `json_schemas()` with mixed configs, and nested TypedDict/dataclass inheritance.

B carries slightly more change surface, but the added behavior aligns JSON schema with real validation/serialization semantics and is well tested. Overall B is the more complete and correct fix.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
