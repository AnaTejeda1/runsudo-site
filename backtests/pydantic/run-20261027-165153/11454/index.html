AssertionError for the mypy plugin if type variables are defined before their bound

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the root cause the same way: before generating methods, check whether the class's type variables still contain placeholder types (the forward-referenced bound) and defer so the generated `self`/return types do not carry placeholders into the final iteration. Both pass all four independent tests. Differences: (1) Control flow. Patch A mirrors the existing field-placeholder check exactly: it defers when not in the final iteration and returns False either way, so methods are never generated with placeholder types. Patch B only returns early when it can defer; on the final iteration it falls through and generates methods with placeholders still present, which is the very state that produced the internal error. That is an edge case, but it is an inconsistency with the surrounding pattern and a residual risk. (2) Coverage. Patch A explicitly checks bound, default and constraint values; Patch B relies on mypy's `has_placeholder` type visitor, which also recurses into those for TypeVarType, so B is not less correct there, just more implicit. (3) Patch A also fixes a latent bug in `add_method`: plugin-generated classmethods are stored as a `Decorator` symbol while only the `FuncDef` lives in the class body, so the existing cleanup never removed stale generated classmethods on re-runs. This is adjacent but directly relevant once the transformer can now be re-run after deferring, and it is small and low risk. (4) Tests. Patch A adds a dedicated regression module exercising bound, constraints and default TypeVars plus assert_type checks on instantiation and model_construct; Patch B adds a minimal bound-only case to an existing module (with double-quoted strings inconsistent with the file's style). A's tests are broader and would fail before the fix. Overall A is the more careful, consistent and better-tested fix.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Description

Running mypy with the pydantic.mypy plugin enabled fails with an error if it encounters a BaseModel with a bound TypeVar, where the type variable is defined _before_ its bound. (See the minimal example below for an illustration) With the pydantic.mypy plugin disabled, type checking is successful.

In my experience, it is quite common to define type variables at the top of the module, see for example the mypy docs on Generics.

Issue #11025 describes a different problem, but may be related.

Example Code

from typing import Generic, TypeVar

from pydantic import BaseModel

# Defined before Mouse: Causes internal error below
M = TypeVar('M', bound='Mouse')

class Mouse:
    pass

# Defined after Mouse: Works without problem
# M = TypeVar('M', bound='Mouse')

class Cat(BaseModel, Generic[M]): # INTERNAL ERROR
    pass
