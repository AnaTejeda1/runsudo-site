Improve open_in_browser function's handling of base tags in response.py

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches make every independent test pass, so the decision rests on robustness, scope, and tests. Patch A inserts the base tag after the real opening <head> if present, else after <html>, else after a doctype, else at the start (preserving a UTF-8 BOM), with HTML comments masked so commented-out <head>/<base> tags are ignored and offsets stay exact. It keeps the existing 'do not inject when a base tag already exists' behaviour, matches <base> case-insensitively without false-matching <basefont>, HTML-escapes the URL in the attribute, and skips injection for encodings like UTF-16 where ASCII bytes would corrupt the body. Its tests cover each fallback position, uppercase tags, newline-separated attributes, commented heads, basefont, escaping, BOM and UTF-16. Patch B takes a simpler route: always prepend a base tag (after a doctype only if the doctype is at the very start) and rely on the browser to hoist it into <head>. That works in browsers, but it changes semantics (a second base tag is always injected even when the response has one, with the existing test deleted and replaced), does not escape the URL, and only recognises a doctype at byte 0 (modulo whitespace), so a leading comment before the doctype would put <base> ahead of it and push the browser into quirks mode, which its own code comment says it wants to avoid. It also bumps the minimum w3lib requirement in pyproject.toml and tox.ini, an unexplained dependency change unrelated to the reported issue that adds risk for users, and it deletes the _remove_html_comments helper and its unit tests. Patch B's updated tests are reasonable but less thorough than A's. A resolves the issue more faithfully, with stronger tests and no unrelated churn.

The issue

View on GitHub

The open_in_browser function in response.py uses a workaround to insert a <base> tag into the HTML response for local file viewing. As mentioned in the function's docstring, is "dirty" and could fail in situations where <head> tags are missing or improperly formed which can lead to unintended effects when rendering HTML.

Steps to Reproduce:

  1. Use open_in_browser with an HTML response that does not contain a proper <head> tag.
  2. Observe to see if the function does not handle this smoothly.

Suggested Fix:
Edit the function to handle missing or properly formed <head> tags so that a correct <base> tag can be inserted.
