Throw an error on createVNode with using innerHTML and children at the same time

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Patch A changes runtime behavior at the point where a crash or corruption can happen. In `patchElement`, when `innerHTML`/`textContent` goes from set to unset, the old children's DOM nodes have already been overwritten. Patching them in place therefore operates on nodes that no longer exist, which is the kind of failure the issue reports. A unmounts the old array children, which also runs component unmount hooks, and then mounts the new text or array children fresh. It also switches the guard from a truthiness check to `!= null`, so an empty-string `innerHTML` is handled correctly. Its tests cover the exact issue scenario (`innerHTML: undefined` with text children) and several transitions: undefined to html to undefined, empty string to undefined, array children, component children with an unmount count, and `textContent`. These transition tests would plausibly fail before the change, and an SSR test checks that undefined values fall back to children. Patch B only adds a dev-mode warning when a non-nullish `innerHTML`/`textContent` is combined with children. It explicitly does not warn for nullish values, which is the issue's case, and it makes no runtime change, so the reported error and the expected behavior (use children when `innerHTML` is undefined) are not addressed. B's tests only check warnings. On correctness, the primary criterion, A clearly wins.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
