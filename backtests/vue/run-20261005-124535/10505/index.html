Clearing select's value in change handler behaviour changed since 3.4.15 via webdriver

Worse

The merged fix was judged better than our patch.

In this judgment, Patch B = our agent, Patch A = the merged fix.

**Root cause.** The `_assigning` flag added for performance makes `updated` skip `setSelected` for the whole tick after a change. A handler that sets the model to `null` in the same tick therefore never reaches the DOM. Both patches fix this by syncing unless the bound value still matches what the select just assigned.

**Patch A** stores a pending `[multiple, snapshot]` and compares semantically with `looseEqual`. For a Set model it checks size and membership against the snapshot. Strengths:
- It resyncs when the value differs, when the bound Array or Set was mutated in place, or when `multiple` flipped.
- Because the comparison is by value, it still skips redundant DOM writes when the model is re-wrapped or copied, e.g. a computed setter that clones the array. This preserves the original perf goal.
- It consumes the pending marker on the first `updated` call and clears it in a guarded `nextTick`.
- It uses `try/finally` so a throwing assigner cannot leave stale state.

**Patch B** uses an identity check (`toRaw(value) === _assignedValue`) plus an element-wise snapshot to catch in-place mutation. This is also correct for the issue: `null !== 'foo'` triggers a resync, as do the `arr.length = 0` and `set.clear()` cases. However:
- Any value that is equal but not identical forces a full `setSelected` pass, a partial loss of the perf optimization that `_assigning` was introduced for.
- It keeps three separate fields (`_assigning`, `_assignedValue`, `_assignedSnapshot`).

**Tests.** Both add a single-select test that fails before the fix and passes after: clear in a change handler, then expect `selectedIndex` to be -1. B's tests are well targeted at Array/Set reset and in-place clear. A additionally covers duplicate option values, Set/Array object models, and mode switching. It also counts `selected` writes to verify that no unnecessary DOM rewrites happen, which directly guards the perf intent of the original change. A's suite is somewhat sprawling, but it is meaningful.

**Overall.** Both resolve the issue. A's semantic comparison is more robust and better preserves the optimization that caused the regression, and its tests verify that. B is simpler but has a slightly weaker no-rewrite guarantee.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
