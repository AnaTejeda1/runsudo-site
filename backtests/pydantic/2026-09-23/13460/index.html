Unexpected serialization schema with ValidateAs

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches diagnose the root cause identically: the serialization schema was built from `from_type` (list[int]) while the validated output is of `source` type (int), so both rebuild the ser schema from the output type. The decisive differences are in tests, craft, and scope. Patch B's test wraps model_dump/model_dump_json in `warnings.simplefilter('error')`, so it genuinely fails before the fix (the PydanticSerializationUnexpectedValue warning is raised as an error) and passes after — a real regression test. Patch A's tests only assert value equality (`model_dump_json() == '{"x":2}'`, `dump_python(...) == Arbitrary(1)`); but the issue shows the value was already correct ({'x': 8}) and only a warning was emitted, so Patch A's assertions pass both before and after the change and do not actually verify the bug is fixed — tautological per the 'weak tests count for little' rule. On craft, Patch B passes `serialization=` directly to `no_info_after_validator_function` (idiomatic), whereas Patch A mutates `schema['serialization'] = ...` after construction, which is hackier. Patch B also uses `handler.generate_schema(source)` to extract a clean schema for the output type, which is safer than Patch A's `handler(source)` that re-enters the current handler chain and could pick up other annotations. Scope: Patch B is smaller and focused; Patch A adds a test rename (test_validate_from -> test_validate_as) and extra churn. Patch A's one genuine advantage is broader handling of arbitrary (non-schema-generable) output types via an any_schema fallback, which Patch B leaves at pre-existing behavior — but that case is outside the reported issue and Patch B introduces no regression there. Given correctness parity on the actual reported issue plus Patch B's stronger regression test, cleaner idiomatic implementation, and tighter scope, B is the better fix.

Summary

What was wrong: ValidateAs.__get_pydantic_core_schema__ built its core schema from the source type (from_type, e.g. list[int]) and wrapped it in no_info_after_validator_function with no serialization override. Serialization therefore defaulted to the source-type schema, so dumping the actual output value (the annotated output type, e.g. int) emitted PydanticSerializationUnexpectedValue(Expected list[int] ...) — exactly the report's symptom.

What I changed (pydantic/functional_validators.py, ValidateAs.__get_pydantic_core_schema__): the serialization schema is now derived from the output type (source) via core_schema.wrap_serializer_function_ser_schema(function=lambda v, h: h(v), schema=handler.generate_schema(source)), guarded by try/except PydanticSchemaGenerationError with a serialization=None fallback. This mirrors the existing PlainValidator idiom in the same file, so output types whose schema can't be generated (e.g. arbitrary classes) keep the prior behavior. Validation still runs against from_type.

Test evidence:

  • Added test_validate_from_serialization in tests/test_types.py (next to test_validate_from), asserting d.x == 8, and under warnings-as-errors that model_dump() == {'x': 8} and model_dump_json() == '{"x":8}'.
  • Confirmed it fails before the fix (UserWarning: Pydantic serializer warnings: PydanticSerializationUnexpectedValue(Expected list[int]...)) and passes after.
  • Gate: test_validate_from + test_validate_from_serialization → 2 passed. Adjacent PlainValidator/serialization tests in test_validators.py → 5 passed, 1 xfailed.
