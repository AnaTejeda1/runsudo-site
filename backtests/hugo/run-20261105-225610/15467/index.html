Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches apply the identical root-cause fix: setting sourceFilenameIsHash(true) on the create path of ImageCache.getOrCreate so a processed image's Key() is the same whether it was built fresh or read from the file cache. Both pass all four independent stability tests (overlay, mask, not-processed-twice, cold vs warm cache). The difference is the side effect the issue explicitly warned about: sourceFilenameIsHash also gates Publish(), which skips writing when the target already exists. With Patch A, a resources.Copy of a processed image clones that flag into a resource whose target path is user-chosen and not a content hash, so after the source changes the copy is never republished. The independent test TestBtJudgeCopyOfProcessedImageRepublished passes on base and on B but fails on A, confirming A introduces a real regression in production behaviour. Patch B anticipates this by resetting the flag in genericResource.cloneTo with a clear comment, and adds a dedicated test for it alongside a 3-build stability test that also asserts the resource cache file count. B's tests are more thorough (exercise overlay, mask, key format, file count, and the copy regression); A's single test is adequate but narrower. Scope-wise B's extra cloneTo change is a necessary companion to the fix rather than unrelated churn. B is the better patch on correctness and tests.

Does this issue reproduce with the latest release?

Yes. It also reproduces with v0.167.0, and the code involved is unchanged on master (77230eb).

Description

When the image passed to images.Overlay (or images.Mask) was itself processed, the filtered image's file name depends on whether that processed image was created in this build or read from the file cache. With an empty resource cache, build 1 publishes the overlay under one name and build 2 under another. The bytes are identical. From build 2 onwards the name stays the same.

Expected: the same name in every build.
Actual: one name in the first build after the overlaid image is (re)processed, and a different name in later builds.

Reproduction

$s.Key has a _<hash> suffix in build 1 and none in build 2. Both overlay files in public/ have the same MD5. Replacing images.Overlay $s 0 0 with images.Mask $s gives the same pattern: two names, identical bytes.

Cause

  • On a file cache hit, ImageCache.getOrCreate marks the image with setSourceFilenameIsHash(true). The create path just below it does not: https://github.com/gohugoio/hugo/blob/77230eba0469604d28434a8eacee868f3274e6ac/resources/image_cache.go#L67
  • genericResource.Key() appends _<hash> only when !l.sourceFilenameIsHash (includeHashInKey is always true for images, resource_spec.go#L204): https://github.com/gohugoio/hugo/blob/77230eba0469604d28434a8eacee868f3274e6ac/resources/resource.go#L465
  • Overlay and Mask put the other image's Key() into the filter options, and the filter options feed into the output name: https://github.com/gohugoio/hugo/blob/77230eba0469604d28434a8eacee868f3274e6ac/resources/images/filters.go#L51 https://github.com/gohugoio/hugo/blob/77230eba0469604d28434a8eacee868f3274e6ac/resources/images/filters.go#L59

Impact

  • The overlay is processed a second time in build 2, under its new name.
  • With --gc, build 2 deletes the build-1 file, so the cache only settles on the second build after a processed overlay source changes.
  • The published URL depends on the state of the resource cache. Two builds of the same commit, one with a warm cache and one with a cold cache, publish the same bytes under different URLs. That causes needless uploads on deploy and churns CDN caches.

Possible fix

Making the key of a processed image the same whether it was created in this build or read from the cache would fix this, for example by setting the flag in both paths, or by having Overlay/Mask use a key that does not depend on where the image came from. Note that sourceFilenameIsHash also affects Publish() (resource.go#L513), so the first option may have other effects. I have not tested either option.

Related: #8066 (which image's name an overlay's output takes; it does not cover this instability) and #11856 (a processed image's name differing after a cache read, now closed).
