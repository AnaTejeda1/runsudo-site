defineProps options object loses properties when using generics

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches make the same core change: `PropMethod` stops being a conditional on `T`. That removes the deferral of `PropType<T>` that broke `RequiredKeys`/`OptionalKeys` and dropped the non-required props. They differ in `InferPropType`.

Patch A keeps the `unknown extends V ? keyof V extends never ? ...` chain and only changes the innermost branch to `unknown extends D ? V : D`. When `V` is a generic type parameter, `unknown extends V` is still deferred. The resulting prop type is an unresolved conditional that happens to be assignable to `V` because every branch is `V`. This hides the problem rather than resolving the type, and property access or narrowing on such a deferred type can behave poorly.

Patch B checks `unknown extends D` first. `D` is concrete when no default is given, since it is inferred as `unknown`. So in the common case the result resolves immediately to `V`, with no deferral. The default-fallback logic moves to a separate helper, `InferPropTypeWithDefault`, used only when a default exists. This fixes the root cause more directly.

Patch B's tests are also much broader. They cover all three forms from the issue, a `default: undefined` case, array and function `PropType`s with generics, an array default, a plain `String` prop, and property access on the generic (`props.c.foo`, `props.a?.foo`). They also test `ExtractPropTypes`, `ExtractPublicPropTypes` and `ExtractDefaultPropTypes` directly with generic options. Patch A's tests are thinner and lean on assignability, which its deferred-type approach would satisfy anyway.

Both patches are tidy and well commented. Patch B has the more robust fix and stronger tests.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
