TypeError: unhashable type: 'list' in match_type for PEP 695 aliases with a ParamSpec (regression in 2.14.0b1)

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches stop the `TypeError` at `match_type`, but Patch B is the more reliable and better-tested fix.

Correctness: Patch B wraps the `DEPRECATED_ALIASES.get(obj)` lookup in `try/except TypeError` and treats an unhashable `obj` as 'not a deprecated alias'. The issue itself explains why this is always right: an unhashable object can never be a dict key. The change is local, needs no new dependencies, and keeps the original semantics for hashable objects. Patch A switches to `DEPRECATED_ALIASES_IDS.get(id(obj))` and raises the minimum `typing-inspection` version to 0.4.4. Avoiding hashing entirely is a reasonable idea, since the deprecated aliases are singletons. However, the fix only works if that new attribute exists in the bumped dependency, which cannot be verified from the diff. It also forces a dependency bump onto a regression fix. Patch B additionally hardens `_path_schema`, where `path_type not in {str, bytes}` would hit the same unhashable problem for `os.PathLike[[]]`. This adjacent fix is low-risk and tested.

Tests: Patch B's new test reproduces the reported scenario directly: a TypeAliasType with a ParamSpec, parameterized with `[]`, used in a model field with `| None`, plus a TypeAdapter and JSON schema check. It also adds a parametrized path test. Patch A's test uses a different route to the same problem, `list[Annotated[int, Meta()]]` with unhashable metadata. It would likely fail before the change, but it does not exercise the reported ParamSpec case. It also has a typo in its name (`unhasbable`) and a placeholder `<link>` docstring.

Craft: Patch B's comment explains why the exception is caught. Patch A is terser, but its test is sloppy. Overall, B has the safer fix, the more direct regression test, and no new dependency requirement.

The issue

View on GitHub

Reported downstream in Giskard-AI/giskard#2719 (breaks import giskard.checks); repro and analysis below. The report was drafted jointly with @davidberenstein1957, who invited it to be filed upstream as-is.

Description

_generate_schema.match_type added an unguarded dict lookup in 2.14 that assumes the annotation object is hashable. It is not, for a PEP 695 type alias with a ParamSpec parameterized by an empty list. Schema building for any model containing such an annotation crashes.

This is a regression: the same code builds fine on 2.13.4.

Example Code

from typing import Any
from pydantic import BaseModel

type Alias[**P, R] = Any

class M(BaseModel):
    f: Alias[[], int] | None = None

Raises immediately at class-definition time:

File ".../pydantic/_internal/_generate_schema.py", line 1127, in match_type
    if origin is not None and (aliased_obj := typing_objects.DEPRECATED_ALIASES.get(obj)):
TypeError: unhashable type: 'list'

Mechanism

Alias[[], int] is a types.GenericAlias whose __args__ is ([], int). Hashing the alias hashes that tuple, which contains a list — so it is unhashable. The line at _generate_schema.py:1127

if origin is not None and (aliased_obj := typing_objects.DEPRECATED_ALIASES.get(obj)):

calls .get(obj) without checking that obj can be hashed. dict.get propagates the TypeError rather than treating an unhashable key as absent.

Suggested fix

Guard the lookup, e.g.

if origin is not None and isinstance(obj, Hashable) and (aliased_obj := typing_objects.DEPRECATED_ALIASES.get(obj)):

or wrap it in try/except TypeError. An unhashable object cannot be a DEPRECATED_ALIASES key by construction, so skipping the lookup is always correct.

Python, Pydantic & OS Version

  • pydantic 2.14.0b1 (fails) / 2.13.4 (works)
  • Python 3.12.13
  • Reproduced on Linux and macOS

Real-world impact

Hit in giskard-oss, where type GeneratorType[**P, R, S] = ... parameterized as GeneratorType[[], InputType, None] makes import giskard.checks fail outright under 2.14.0b1. Instrumenting match_type confirms the offending object:

OFFENDING obj  = GeneratorType[[], InputType, None]
OFFENDING type = <class 'types.GenericAlias'>
OFFENDING args = ([], InputType, None)

There is no workaround on the library side short of pinning pydantic<2.14 (done in Giskard-AI/giskard#2752), which is what downstream has had to do.
