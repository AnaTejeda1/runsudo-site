RFC: Allow usage of file descriptors or stdin with runspider

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches make `/dev/fd/N` process-substitution paths and extensionless FIFOs work, and the independent tests confirm that for both. The issue explicitly names a second use case, `-` for stdin, which Patch A implements (reads sys.stdin.buffer, executes as a module named `<stdin>` for tracebacks) and Patch B does not: with B, `runspider -` still hits the `Path('-').exists()` check and fails, as the independent stdin test shows (PASS for A, FAIL-ASSERT for B). On root cause, A distinguishes regular files (still imported with the extension check) from non-regular files (read and exec'd), which is a direct answer to the issue's concern without loosening validation for ordinary files. B instead relaxes the extension check to 'any extension or none' and swaps `import_module` for a bare `SourceFileLoader.exec_module`, which also drops the sys.modules registration the old path had and gives modules names like `63`; it works but is a less targeted change with a small regression surface. On tests, A adds tests for stdin success, stdin no-spider, stdin unable-to-load, stdin traceback filename, /dev/fd pipe, and a named FIFO, with skips only on platforms lacking /dev/fd or mkfifo (the issue's scenarios are POSIX shells, so the skips would not hold there). B adds a single bash process-substitution test. A also documents the new behavior in commands.rst and the command's long description. One uncertainty for A is that its tests rely on `proc` accepting `input=` and `pass_fds=`, which I cannot verify here, but the independent runs show A's production code covers every scenario the issue names, while B leaves the stdin case unaddressed.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Each saw the issue and the two patches, labelled A and B in random order (two of them saw ours as A), with issue links and version numbers removed. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours. The reasoning above is one judge's, shown verbatim.

https://github.com/scrapy/scrapy/blob/004b40a7193a7c0c5138abe764cad6d1d9a4fc57/scrapy/commands/runspider.py#L14

If this check could be improved, more creative uses of runspider would be admitted. For example, using a file descriptor avoids creating a temporary file (following example taken from the home page):

$ pip install scrapy
$ scrapy runspider <(echo <<EOF)
import scrapy

class BlogSpider(scrapy.Spider):
    name = 'blogspider'
    start_urls = ['https://blog.scrapinghub.com']

    def parse(self, response):
        for title in response.css('.post-header>h2'):
            yield {'title': title.css('a ::text').get()}

        for next_page in response.css('a.next-posts-link'):
            yield response.follow(next_page, self.parse)
EOF

Currently, this raises an error because the filename ends up being something like /dev/fd/324. Perhaps the extension check could be removed entirely?

Another use case would be to use - for stdin.
