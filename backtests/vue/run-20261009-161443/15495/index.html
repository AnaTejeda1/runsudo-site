In this judgment, Patch A = our agent, Patch B = the merged fix.

The source changes are functionally identical. Both push `SwitchCase.consequent` onto the scope stack on enter and pop it on leave. That makes the `needsSemi` check see sibling statements inside a case branch, which is the root cause named in the issue. The only source difference is brace style in `leave`, which doesn't matter. The deciding factor is the tests. Patch A compiles the SFC, actually runs `setup()` with a stubbed `_withAsyncContext`, and checks execution order through a `calls` array. That proves the generated code behaves correctly at runtime, not just that a `;` appears in the output. Patch A also covers the variants the issue lists: an await after an expression statement in a case, consecutive awaits in one case (the `(...)(...)` problem the issue calls out), an await as the first statement of a case (should get no prefix), and a root-level await after a switch (checks the scope stack is popped correctly). Each of these would fail or misbehave before the fix. Patch B adds two snapshot tests with a regex for `;(`, covering the basic case and the nested-in-`if` case from the issue. They are valid regression tests but only check the text shape. They skip the consecutive-awaits variant and the scope-restoration edge cases, and they add snapshot churn. With equal correctness, Patch A's broader, behavior-level tests make it the better patch.

Steps to reproduce

  1. Open the playground link above (or compile the SFC below with @vue/compiler-sfc).
  2. The component setup() throws TypeError: object is not iterable (cannot read property Symbol(Symbol.iterator)).

SFC:

<script setup>
const a = true
const b = 1
function qux() {}
async function bar() { return 42 }
if (a) {
  switch (b) {
    case 1:
      qux()
      await bar()
  }
}
</script>

What is expected?

The compiled setup() should run fine: qux() and await bar() should be two independent statements.

What is actually happening?

The top-level await rewrite in compileScript emits the withAsyncContext wrapper expression without a leading semicolon when the await is inside a switch case that is not the first statement:

async setup(__props, { expose: __expose }) {
  ...
  if (a) {
    switch (b) {
      case 1:
        qux()
        (
  ([__temp,__restore] = _withAsyncContext(() => bar())),
  await __temp,
  __restore()
)
    }
  }
}

Because the next line starts with (, ASI does not insert a semicolon, so the two lines are parsed as a single call expression qux()(...). bar() is never awaited in the intended way and the runtime throws TypeError: object is not iterable.

The same code inside a plain block (not a switch) is compiled correctly with a leading ;:

if (a) {
  qux()
  ;(
  ([__temp,__restore] = _withAsyncContext(() => bar())),
  await __temp,
  __restore()
)
}

Additional comments

Root cause: in packages/compiler-sfc/src/compileScript.ts, the scope stack used to decide whether the rewrite needs a semicolon only pushes/pops on BlockStatement. A switch statement's SwitchCase.consequent statement list is not tracked, so needsSemi is misjudged as false for await expressions inside case branches (unless the await happens to be the very first statement of the case).

Related variants also affected:

  • Two consecutive top-level awaits inside one case produce (...)(...) back-to-back (second one also parsed as a call of the first result).
  • Any await that follows an expression statement inside a case branch.

No prior issue found for this.
