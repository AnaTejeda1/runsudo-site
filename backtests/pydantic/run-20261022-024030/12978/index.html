Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the root cause identically: they register the `_RootModelMetaclass` in the metaclass hook and stop `add_initializer` from bailing out on `RootModel` itself because it has a hand-written `__init__`, so the plugin-generated `__init__` (typed `Any` when `init_typed` is unset) replaces the stub signature and `RootModel[float]('1.0')` no longer errors under the plugin. Under the default (no-plugin) config both patches leave the error in place, which is the only sensible outcome there. On correctness for the reported issue they are equivalent.

Patch A goes further: it changes the `root` argument kind from unconditional `ARG_OPT` to `ARG_POS` unless a default exists (keeping it optional only on `RootModel` itself via a new `force_optional` condition). This is a behavior change outside the issue's ask: existing user code like `Pets1()` that previously type-checked now gets a new `call-arg` error (visible in A's updated expected outputs). It may well be the more accurate runtime model, but it is an unrelated tightening bundled into a bug fix, adding regression risk for downstream users and obscuring the minimal fix. It also adds a new `mypy-plugin-strict.ini` test case whose outputs mostly re-verify unchanged behavior.

Patch A's tests are somewhat broader (keyword `root=` form, strict config), which is a point in its favor. Patch B's tests cover the issue's exact scenario plus the subclass case across the plugin and non-plugin configs, which is adequate and would fail before the change under the plugin config.

Patch B's edit is narrower, uses an equally valid `self._cls.fullname` check, and leaves the established `ARG_OPT` semantics for `root` untouched. Given equal correctness, B wins on scope and risk; A's extra test coverage does not outweigh the unrequested semantic change.

Initial Checks

  • I confirm that I'm using Pydantic V2

Description

The below example code (named foo.py) passes when running python foo.py as the input "1.0"-string gets converted to float. However, running mypy foo.py (with or without --strict) gives the following error:

foo.py:11: error: Argument 1 to "RootModel" has incompatible type "str"; expected "float"  [arg-type]
Found 1 error in 1 file (checked 1 source file)

I would expect the BaseModel-fields and the RootModel-field to behave the same in this case. That is, if the value can be converted – either via a custom made validator or through the conversion table – then mypy should not raise an error.

Example Code

import pydantic


class Foo(pydantic.BaseModel):
    f: float


RFoo = pydantic.RootModel[float]

f = Foo(f="1.0")
rf = RFoo("1.0")

assert isinstance(f.f, float)
assert isinstance(rf.root, float)
assert f.f == rf.root
