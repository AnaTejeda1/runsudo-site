"dictionary changed size during iteration" during model_rebuild

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Root cause: `model_rebuild()` is not thread-safe. Several threads rebuild the same incomplete class at once. One mutates the class `__dict__` (delattr/setattr of schema, validator and serializer) while another iterates that live `vars(cls)` in `LazyLocalNamespace.data`, or races on the check-then-delete.

Patch A treats the two symptoms separately. It swaps the dict comprehension for `dict.update()`, relying on C-level iteration not releasing the GIL; the comment itself admits this holds only on GIL-enabled builds. It also swallows `AttributeError` from `delattr`. The rebuild still runs concurrently, so multiple threads redo schema generation, can call `__pydantic_on_complete__` more than once, and can briefly observe missing or parent attributes. On free-threaded Python (the issue is on 3.14) the dict race can still occur. Its tests are clever and deterministic (trace-function injection) and would fail before the fix, but they check the narrow symptom only.

Patch B fixes the cause by serializing rebuilds with a global reentrant lock. It keeps an unlocked fast path and re-checks completeness inside the lock, so a thread that waited returns `None` instead of rebuilding again. The class-dict mutations and the namespace iteration during another rebuild both happen under the lock, which removes both the RuntimeError and the AttributeError without depending on GIL atomicity. It also explains its design choices: an RLock for the nested rebuild triggered via generic `__class_getitem__`, and a global rather than per-class lock to avoid deadlocks. It tightens the mock check to include `MockCoreSchema` and applies the same check in `rebuild_dataclass`.

B's tests cover reentrancy during parametrization and a deterministic two-thread scenario. That scenario asserts the second thread returns `None` and the completion hook fires once; it would fail without the lock.

B carries some risks: a global lock could deadlock if user schema hooks wait on other threads, and class creation and dataclass rebuild are not locked. Even so, B addresses the actual concurrency problem, while A mostly masks symptoms under GIL assumptions.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Each round executes the module source into a fresh module (fresh, incomplete

        lines += [f"class Leaf{l}(BaseModel):", "    x: int = 0", ""]
    return "\n".join(lines)

def worker(barrier: threading.Barrier, model: type) -> None:
    barrier.wait()

        try:
            model()  # first call hits the mock validator -> lazy model_rebuild()

            with errors_lock:
                errors.append(traceback.format_exc())

What the agent reported

I fixed both errors from the report. The changes are left as uncommitted edits.

What was wrong

When several threads create the same not-yet-built model at the same moment (like FastAPI's first requests after startup), each thread calls model_rebuild() on that class.

  1. RuntimeError: dictionary changed size during iteration: while evaluating annotations, LazyLocalNamespace.data in pydantic/_internal/_namespace_utils.py copied the class's live __dict__ (vars(cls)) using a Python dict comprehension. Python can switch threads between steps of that loop. Meanwhile another thread's model_rebuild() was deleting and setting __pydantic_core_schema__, __pydantic_validator__ and __pydantic_serializer__ on the same class.
  2. The occasional AttributeError: ... has no attribute '__pydantic_core_schema__': model_rebuild() in pydantic/main.py first checks that the attribute is in cls.__dict__ and then deletes it. Another thread could delete it between those two steps.

What I changed

  • LazyLocalNamespace.data now builds its dict with data.update(ns) for each namespace instead of the comprehension. dict.update runs entirely in C, so on normal CPython no other thread can run while the copy is made. Later namespaces still override earlier ones, as before.
  • On free-threaded CPython builds (3.13t/3.14t) the copy is not fully protected. A badly timed deletion there could still raise a KeyError. The code comment says so.
  • model_rebuild(): the delattr is wrapped in try/except AttributeError, so an attribute another thread already deleted is simply skipped.

Test evidence

I added two tests. Each one makes the "other thread" act at the exact point of the race, using a trace function (sys.settrace) rather than real threads. Neither mocks any pydantic code.

  • tests/test_forward_ref.py::test_lazy_local_namespace_concurrent_mutation adds attributes to the class while LazyLocalNamespace.data is being built.
  • Before the fix: RuntimeError: dictionary changed size during iteration.
  • After the fix: passes.
  • tests/test_main.py::test_model_rebuild_concurrent_attribute_deletion deletes __pydantic_core_schema__ just before model_rebuild's own delattr runs.
  • Before the fix: AttributeError: type object 'Model' has no attribute '__pydantic_core_schema__'.
