[Bug]: LiteLLM Proxy 1.100.0 serializes image-edit uploads as strings for OpenAI GPT Image models

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the actual defect in the same way: the raw `image[]` / `mask[]` form parts remain in the parsed body after FastAPI binds them to the `image_array`/`mask_array` parameters, so they are forwarded as extra provider params and stringified into text multipart fields. A pops them from `data`; B filters them out in a dict comprehension. Both pass all three independent tests that fail on base, so correctness on the reported scenario is equal.

The differences are in tests and extra hardening. Patch A's regression test is materially stronger: it drives the request through the proxy endpoint and then through `litellm.aimage_edit` with an httpx MockTransport, and asserts on the actual multipart body sent to OpenAI (image[] and mask parts are file parts with the original bytes, no `UploadFile`/`BytesIO` repr anywhere), parameterized over both `image[]` and `image` spellings. That directly mirrors the failure the issue reports at the wire level. Patch B's tests only inspect the kwargs captured at `route_request`; they do fail on base (since `image[]` would be present) and cover mask[] and the canonical fields, but stop short of the provider serialization that actually produced the OpenAI error.

Patch A also makes `_form_field_value` raise a TypeError for bytes/file-like values instead of silently shipping a repr string. This is scope beyond the ask and carries a small risk of turning a previously-garbage request into an exception for any other caller, but on base such a request was already broken, so failing loudly is a reasonable guard against recurrence and is covered by unit tests. Patch B, by contrast, includes unrelated formatting churn in existing tests (reflowing `monkeypatch.setattr` lines and function signatures), which is neutral-to-slightly-negative noise.

Craft is comparable: B's named constants and comprehension are tidy; A's comment explains why the pop is needed. On balance A wins on the stronger, end-to-end regression test that targets the exact symptom in the issue, with the hardening being acceptable and tested.

What happened?

Image edits through the LiteLLM Proxy fail in version 1.100.0 for OpenAI GPT Image models. The uploaded image file is being converted to a string representation of a Python BytesIO object ("<_io.BytesIO object at 0x7f0d0bc73600>") before being sent to OpenAI.

OpenAI rejects this with:

{
  "error": {
    "message": "Invalid type for 'image[0]': expected a file, but got a string instead.",
    "type": "invalid_request_error",
    "param": "image[0]",
    "code": "invalid_type"
  }
}

The same request succeeds in LiteLLM version 1.95.0.

User Flow

Before a fix: A user sends an image-edit request through LiteLLM Proxy 1.100.0 using a multipart/form-data request to POST /v1/images/edits with an uploaded image file and a prompt (e.g., "Make this image photorealistic"). LiteLLM receives the UploadFile correctly but serializes it to a string before forwarding to OpenAI. OpenAI rejects the request because it expects a file object, not a string representation.

  1. User sends: curl -X POST "http://localhost:4000/v1/images/edits" -F "model=openai/gpt-image-2" -F "prompt=Make this image photorealistic" -F "image[]=@./input.png;type=image/png"
  2. LiteLLM receives UploadFile with filename, size, and content-type headers
  3. LiteLLM converts the UploadFile's BytesIO object to a string
  4. LiteLLM forwards stringified image to OpenAI
  5. OpenAI rejects with invalid_type error

After a fix: The same user flow succeeds. LiteLLM preserves the UploadFile/BytesIO object and forwards it to OpenAI as a multipart file, and OpenAI processes it successfully.
