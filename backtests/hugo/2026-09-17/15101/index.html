In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches identify the root cause correctly: `seen` holds lowercased cache keys while the walk yields the real on-disk (mixed-case) name, so a case-only difference makes an in-use entry look unused. The decisive difference is correctness on the two filesystem classes. Patch A simply also checks `seen.Has(strings.ToLower(name))`. This fixes the reported case-insensitive-fs deletion, but it is a blanket lowercase match with no notion of filesystem case-sensitivity. On a case-SENSITIVE filesystem (Linux CI, the common upgrade path where an old mixed-case `MyBundle/x` cache coexists with the new lowercased `mybundle/x`), `MyBundle/x` and `mybundle/x` are genuinely distinct files; Patch A would lowercase-match the stale `MyBundle/x` against the used key and never prune it — defeating `--gc` for exactly those entries and introducing a real (if benign) cache-leak regression. The issue text explicitly scopes the desired behavior to 'when the cache filesystem is case-insensitive,' which Patch A ignores. Patch B distinguishes the two situations without probing the fs: it defers case-only matches to `candidates`, and only prunes a candidate if the exact lowercased key `id` was ALSO walked (`visited[id]`) — which can only happen when both names exist as distinct files, i.e. a case-sensitive fs. On a case-insensitive fs only one physical name exists, so `visited[id]` stays false and the in-use entry is kept. This is the correct, root-cause behavior for both fs classes. On tests: Patch A's single test is portable (MemMapFs, simulating the case-insensitive resolution) and is a clean before-fail/after-pass regression test, which is a genuine point in its favor. But Patch B tests both directions — a real case-insensitive-fs integration test (via a proper new `htesting.IsCaseInsensitiveFs` helper and a testscript reproduction close to the issue's repro) plus a case-sensitive guard asserting the stale entry IS still pruned (count 1), which is precisely the behavior Patch A gets wrong and does not test. The case-insensitive test skips on Linux CI, a modest weakness, but the mechanism is sound and the case-sensitive guard runs everywhere. On scope, Patch A is clearly smaller and B touches more files (htesting helper, main_test base64decode/condition plumbing, new testscript); some of that is incidental infrastructure. But that added surface is in service of correctly covering both filesystem behaviors, and the core code change is well-commented and references the issue. Correctness is the top-weighted criterion, and B is meaningfully more correct — it resolves the reported bug AND avoids the case-sensitive-fs regression that A silently introduces — so the extra scope is justified. Patch B wins.

The issue

View on GitHub

What happens

On a case-insensitive filesystem (macOS APFS, Windows), hugo --gc deletes image cache files under resources/_gen that the build actively uses, if the on-disk path case differs from the cache key. The build itself works fine (the case-insensitive filesystem resolves the read), but the pruner's usage check is a case-sensitive string comparison, so the just-used file is considered unused and removed.

The relevant code is in cache/filecache/filecache_pruner.go (unchanged on master):

if !shouldRemove && c.entryLocker.seen.Len() > 0 {
    // Remove it if it's not been touched/used in the last build.
    shouldRemove = !c.entryLocker.seen.Has(name)
}

seen contains the cache key (for images: the lowercased target path, via ImageCache.getOrCreate → c.fcache.ReadOrCreate(relTargetPath, …)), while name is the real on-disk name from the filesystem walk. If they differ only in case, seen.Has(name) is false and the file is deleted.

Why the case can differ in practice

Page paths have been lowercased since the v0.123 page-system rewrite, so cache keys for page-bundle images are lowercase. Caches created by older Hugo versions preserve the source directory case (e.g. resources/_gen/images/collections/PastFuture/…). Such caches are common in the wild: committed to git for CI cold-start speed, restored by CI cache plugins, or simply carried forward on a developer machine across Hugo upgrades.

The result is a permanent rebuild/evict cycle: --gc deletes the in-use entries → the next build silently re-processes all of them → the new files land inside the surviving mixed-case directory (the prune walk visits directories before deleting their files, so the directory is never seen empty and survives; on a case-insensitive filesystem the re-created file then lands in it) → the next --gc deletes them again. On the real site where we found this, every build re-scaled 267 images (~35 s per build, forever).

Minimal reproduction (macOS)

hugo new site repro && cd repro
mkdir -p content/MyBundle layouts/_default
printf 'baseURL = "https://example.org/"\ndisableKinds = ["taxonomy", "term", "rss", "sitemap"]\n' > hugo.toml
printf -- '---\ntitle: My Bundle\n---\n' > content/MyBundle/index.md
cp /path/to/any.jpeg content/MyBundle/cover.jpeg
printf '{{ with .Resources.GetMatch "cover.jpeg" }}{{ with .Resize "100x" }}<img src="{{ .RelPermalink }}">{{ end }}{{ end }}' > layouts/_default/single.html
printf 'home' > layouts/_default/home.html

hugo                      # creates resources/_gen/images/mybundle/cover_hu_<hash>.jpeg
# simulate a cache written by an older Hugo (or copied from elsewhere):
mv resources/_gen/images/mybundle resources/_gen/images/tmp
mv resources/_gen/images/tmp resources/_gen/images/MyBundle

hugo --gc                 # build succeeds (16 ms, cache hit), but reports "Cleaned 1"
find resources -type f    # -> empty: the file the build just used is gone

hugo                      # re-processes the image (474 ms) — and writes it back
                          # into the surviving MyBundle/ dir, so the cycle repeats

Observed output of the --gc build:

Processed images │  1
Cleaned          │  1
Total in 16 ms

A cache file that was read 16 ms earlier is deleted as "not been touched/used in the last build".

What I expected

--gc should never delete a cache entry that the same build read. On case-insensitive filesystems the usage check should match the way the filesystem resolved the read — e.g. compare case-insensitively (or normalize walk names against the seen set) when the cache filesystem is case-insensitive. Renaming the on-disk entry to the key's case would even self-heal old caches.

Summary

What was wrong
On case-insensitive filesystems (macOS APFS, Windows), hugo --gc deleted image cache files that the current build actively used. In cache/filecache/filecache_pruner.go, Cache.Prune decided deletion with a case-sensitive lookup:

shouldRemove = !c.entryLocker.seen.Has(name)

Image cache keys stored in seen are lowercased (via helpers.PathSpec.MakePathSanitized → strings.ToLower), but name is the raw on-disk walk name. When an on-disk file kept a different case (e.g. a cache written by an older Hugo, or restored by CI), the case-only difference made seen.Has(name) false, so the just-used file was pruned — producing a permanent re-scale/evict cycle.

What I changed (uncommitted working-tree edits only)

  • cache/filecache/filecache_pruner.go: the seen check now also matches the lowercased on-disk name, and imports "strings": go shouldRemove = !c.entryLocker.seen.Has(name) && !c.entryLocker.seen.Has(strings.ToLower(name)) This is monotonic — it only ever keeps more entries, and for already-lowercase ids ToLower(name) == name, so existing behavior is unchanged. The reverse direction (mixed-case key vs lowercase disk) can't occur because image keys are always lowercased, so the one-directional match is sufficient.
  • cache/filecache/filecache_pruner_test.go: added one regression test, TestPruneKeepsUsedEntryWithCaseMismatch. It reproduces the bug without needing a case-insensitive OS — writes a mixed-case file to the (case-sensitive) MemMapFs, registers only the lowercased key in seen via NamedLock, prunes, and asserts the file survives. TestPrune is untouched.

Test evidence

  • Before the fix: the new test FAILED (exists = false; the in-use file was deleted).
  • After the fix (./bt-test -run 'TestPrune|TestPruneKeepsUsedEntryWithCaseMismatch' ./cache/filecache/): both TestPrune and TestPruneKeepsUsedEntryWithCaseMismatch PASS; the package compiles cleanly.

Reviewer verdict: the fix correctly and minimally addresses the reported root cause; no existing test was weakened, skipped, or mocked.
