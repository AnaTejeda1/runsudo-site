[Bug]: Router budget sync can overwrite memory cache with stale Redis spend

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the headline sync race: the sync now awaits the Redis pipeline before reading Redis back, and both snapshot/clear the queue and requeue on failure (independent tests 1-4 pass on both). The difference is the second path the issue names explicitly: `_PROXY_VirtualKeyModelMaxBudgetLimiter` awaits `_push_in_memory_increments_to_redis()` after logging and the issue says that await should mean Redis has been updated. Patch A keeps that method fire-and-forget (it just tracks the task in `in_flight_redis_pushes`), so the virtual-key path is unchanged; the independent test for it fails on A exactly as on base, and reading A's diff confirms the push still returns before the pipeline runs. A also leaves a residual window: a success callback can create a push task after sync's `gather` over in-flight tasks but before sync's own flush, so sync can still read Redis while that task is in flight. Patch B makes the push genuinely await the pipeline (through a shielded task so cancellation of the caller cannot lose or double-apply a batch), serializes flush/sync with a lock, requeues with per-key coalescing so the queue stays bounded while Redis is down, and folds any increments recorded during Redis I/O into the value written back to memory. That resolves every scenario in the issue, including the virtual-key limiter, and all five independent tests pass. B's tests are also stronger: they pin event ordering (pipeline before batch_get), requeue, in-flight increments surviving a flush, and cancellation edges. Costs on B's side: it is a considerably larger redesign with intricate cancellation handling, it adds a lock around the in-memory increment on the hot path, it flips the existing circuit-breaker test expectation (now requeues rather than drops), and it includes unrelated reformatting of existing tests. Those are real scope and risk concerns, but A leaves a path the issue names still broken, and correctness weighs first.

Check for existing issues

I found #20886, but it is closed as stale/not planned and cannot be reopened. This issue adds current-branch verification and additional affected code paths

What happened?

RouterBudgetLimiting._push_in_memory_increments_to_redis() still schedules redis_cache.async_increment_pipeline(...) with asyncio.create_task(...) and immediately clears the queue. _sync_in_memory_spend_with_redis() awaits that method, but the await only waits for task scheduling. It then fetches Redis and writes those values into in-memory cache before the pipeline has necessarily completed

On current litellm_internal_staging at 60729f733e, fetched on 2026-07-09, I reproduced memory being overwritten from 160 to stale Redis 100. After the background pipeline finishes, Redis is 160, but memory remains 100

Why this matters

async_filter_deployments() reads budget spend through DualCache.async_batch_get_cache(). DualCache returns in-memory values first and only checks Redis for misses, so the stale memory value is trusted by later provider, deployment, and tag budget checks

The same inherited flush method also affects _PROXY_VirtualKeyModelMaxBudgetLimiter: it awaits _push_in_memory_increments_to_redis() after logging virtual-key and end-user model spend, but that await does not currently mean Redis has been updated

A related implementation already uses a safer pattern. BaseRoutingStrategy._push_in_memory_increments_to_redis() awaits redis_cache.async_increment_pipeline(...) and _sync_in_memory_spend_with_redis() consumes that awaited result before merging values back into memory

from types import SimpleNamespace

from litellm.router_strategy.budget_limiter import RouterBudgetLimiting
from litellm.types.utils import BudgetConfig


class MockRedisCache:
    def __init__(self, values):
        self.values = values
        self.events = []

    async def async_increment_pipeline(self, increment_list, **kwargs):
        self.events.append("increment_pipeline:start")
        await asyncio.sleep(0.05)
        for op in increment_list:
            key = op["key"]
            self.values[key] = float(self.values.get(key, 0.0) or 0.0) + float(op["increment_value"])
        self.events.append("increment_pipeline:done")

    async def async_batch_get_cache(self, key_list, **kwargs):
        self.events.append("batch_get")
        return {key: self.values.get(key) for key in key_list}


class MockInMemoryCache:
    def __init__(self, values):
        self.values = values

    async def async_set_cache(self, key, value, **kwargs):
        self.values[key] = float(value)


async def main():

    redis_cache = MockRedisCache({spend_key: 100.0})
    in_memory_cache = MockInMemoryCache({spend_key: 160.0})

Expected result

_push_in_memory_increments_to_redis() should await the Redis increment pipeline before _sync_in_memory_spend_with_redis() reads Redis. It should snapshot and clear the queue before awaiting so new increments that arrive during the flush remain queued for the next sync, and it should requeue the flushed batch if the pipeline fails

There is an existing unmerged branch, origin/fix/issue-20886-budget-sync-race, with commit 620fa2dcfd fix(router-budget): await redis pipeline before sync reads, that appears to implement that queue snapshot, await, and requeue behavior
