Experimental pipeline: Interval bounds of zero are silently dropped

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

The source changes are byte-for-byte identical. Both replace the four truthiness checks in the `Interval` branch of `_apply_constraint` with `is not None`, which fixes the root cause for all four bounds. Correctness and scope are therefore equal, and the decision rests on tests.

Both patches add cases that would fail before the fix and pass after it.

Patch B strengthens the existing parametrized cases:
- `Interval(ge=0, le=10)` now also rejects `-5`.
- `Interval(gt=0.0, lt=10.0)` now also rejects `0.0` and `-5.0`.
- New int-only cases cover `gt=0`, `le=0` and `lt=0`.
This is tidy, since it fixes the weak existing case (which only checked `11` and so never exercised the zero bound) rather than adding a near-duplicate.

Patch A leaves the weak existing case in place but adds broader zero-bound coverage:
- All four bounds on int, matching every row of the issue's table.
- All four bounds individually on float, with the boundary value itself tested as valid or invalid as appropriate (`0.0` for `ge`/`le`, `0.0` rejected for `gt`/`lt`).
- A `Decimal` case with `ge=Decimal('0')`.
B has no `Decimal` zero-bound case and no float `ge`/`le`/`lt` zero cases in isolation.

B is marginally cleaner because it avoids a semi-duplicate case. However, tests outrank craft, and A's coverage across int, float and Decimal is more thorough. That gives A a small edge.

Description

In pydantic/experimental/pipeline.py, _apply_constraint() handles annotated_types.Interval by delegating to the individual comparison constraints, but it tests each bound for truthiness rather than is not None:

elif isinstance(constraint, annotated_types.Interval):
    if constraint.ge:
        s = _apply_constraint(s, annotated_types.Ge(constraint.ge))
    if constraint.gt:
        s = _apply_constraint(s, annotated_types.Gt(constraint.gt))
    if constraint.le:
        s = _apply_constraint(s, annotated_types.Le(constraint.le))
    if constraint.lt:
        s = _apply_constraint(s, annotated_types.Lt(constraint.lt))

Since 0 is falsy, a bound of exactly zero is skipped and the constraint is silently dropped - there is no error, validation simply accepts out-of-range values. Interval(ge=0, le=10) happily accepts -5.

All four bounds are affected. Observed on 2.12.5:

Interval(ge=0, le=10)-5ValidationErroraccepted
Interval(ge=0, le=10)20ValidationErrorValidationError (le=10 works)
Interval(gt=0)-5ValidationErroraccepted

Interval(le=0)5ValidationErroraccepted
Interval(lt=0)5ValidationErroraccepted
Interval(ge=1, le=10)-5ValidationErrorValidationError (control: non-zero bound is fine)

The non-zero control confirms the trigger is specifically the zero bound, not Interval in general. Zero is a very common lower bound, so this silently weakens validation in ordinary usage.

The fix looks like changing the four checks to if constraint.ge is not None: (and likewise for gt/le/lt).

This is related to, but distinct from, #13446 - that one is about Gt being dropped on a numeric type mismatch, whereas this is the Interval branch dropping zero bounds regardless of type.

Happy to open a PR if that would help.

Example Code

from typing import Annotated

import annotated_types
from pydantic import TypeAdapter
from pydantic.experimental.pipeline import validate_as

ta = TypeAdapter(Annotated[int, validate_as(int).constrain(annotated_types.Interval(ge=0, le=10))])

print(ta.validate_python(-5))  # -> -5   (expected: ValidationError, ge=0 is violated)
ta.validate_python(20)         # -> ValidationError (le=10 is enforced correctly)

# A non-zero lower bound behaves correctly:
ta2 = TypeAdapter(Annotated[int, validate_as(int).constrain(annotated_types.Interval(ge=1, le=10))])
ta2.validate_python(-5)        # -> ValidationError (correct)
