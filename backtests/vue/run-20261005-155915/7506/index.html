suspense.resolve() is called without a pending branch.

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

In the issue, the user navigates away from inside a pending page's setup(), which means the Suspense is toggled back to its current active branch while a pending branch still exists. In the 'toggled back' path, the active branch is patched while `suspense.pendingBranch` is still set. Any async dep or suspensible nested Suspense mounted during that patch therefore registers against the boundary: `registerDep` only increments deps when `pendingBranch` is non-null. The code then force-resolves, clearing the pending branch. When the leftover dep later settles, deps drops to 0 and `resolve()` runs with no pending branch, which produces exactly the reported error. Patch B fixes this root cause: it nulls `pendingBranch` during the toggle-back patch so new deps are not counted against the discarded pending branch, then restores it so `resolve(true)` works. Its tests reproduce the issue's flow (changing the view inside setup() and mounting a new async child, or a suspensible nested Suspense, in the active branch). They assert no error, correct output, that onResolve is not called twice, and that a later pending branch still resolves, so dep counts stay consistent. These tests would fail before the change. Patch A instead changes the same-root-type pending patch path, adding a deps++/-- guard against a nested suspensible Suspense resolving the parent mid-patch. That is a different scenario from the toggle-back race in the issue. Its tests target nested suspensible boundaries rather than navigation during setup, so it likely leaves the reported error in place. Patch B is targeted, correct, and well tested for the reported case.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
