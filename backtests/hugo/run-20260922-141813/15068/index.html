The issue

View on GitHub

See https://github.com/gohugoio/hugo/issues/15060#issuecomment-4790405347

It's clumsy that you need to create a resource (making up an unique filename) to get a SRI hash.

I suggest we add crypto.Fingerprint with a similar signature to https://gohugo.io/functions/resources/fingerprint/

hash.Fingerprint [ALGORITHM] any -> string

The function name is a little clumsy, but we need to keep the two very similar functions in line.

Where any typically is a string (but can also be a Resource -- we have similar unwrappers elsewhere).

It would then return e.g. sha256-Yuh...rfE=.

Note to implementer: There's some obvious code reuse potential here.

Summary

What was reported: It's clumsy to have to create a Resource (with a made-up unique filename) just to obtain a Subresource Integrity (SRI) hash. The report asks for a crypto.Fingerprint function mirroring resources.Fingerprint — signature Fingerprint [ALGORITHM] any -> string — that accepts a string (or a Resource, unwrapped) and returns e.g. sha256-Yuh...rfE=, with a note about obvious code-reuse potential.

(The ticket title mentions encoding.HexDecode/Encode, which is unrelated to the detailed body. I treated the body — which gives a full signature and rationale — as authoritative and implemented that.)

What I changed:

  • resources/resource_transformers/integrity/integrity.go — added an exported Fingerprint(r io.Reader, algo string) (string, error) that reuses the existing newHash, integrity (SRI algo-base64 formatter), and defaultHashAlgo ("sha256"). Coexists with the existing (*Client).Fingerprint method (no conflict). This realizes the "code reuse" note.
  • tpl/crypto/crypto.go — added (ns *Namespace) Fingerprint(ctx context.Context, args ...any) (string, error): optional algorithm first, then the value; unwraps a resource.ContentProvider via Content(ctx) with a cast.ToStringE string fallback; delegates hashing to integrity.Fingerprint.
  • tpl/crypto/init.go — registered the method (no global alias; documented example).
  • tpl/crypto/crypto_test.go — added TestFingerprint (test-writer).

Test evidence (./bt-test ./tpl/crypto/... ./resources/resource_transformers/integrity/..., both packages PASS):

  • New TestFingerprint PASS — covers default sha256, explicit sha256/sha384/sha512/md5 (exact SRI values), and error paths (unsupported algorithm, no arguments). This test could not compile before the change (the method didn't exist), so it directly exercises the new behavior.
  • All pre-existing tests still pass: TestMD5, TestSHA1, TestSHA256, TestHMAC, and integrity's TestHashFromAlgo/TestTransform.
  • Reviewer confirmed correctness, reuse, consistency, and no scope creep.

  3. Accept a Resource as the value (unwrap it) — Implemented via resource.ContentProvider.Content(ctx) with string fallback; verified by reviewer against the interface (the string path is exercised by tests).
  4. Reuse existing code — Implemented; the new integrity.Fingerprint reuses newHash/integrity/defaultHashAlgo.
  5. Title's encoding.HexDecode/Encode — Skipped; it contradicts the detailed body (which specifies the fingerprint function) and has no signature or rationale. Flagging the discrepancy rather than guessing at an unrelated feature.
