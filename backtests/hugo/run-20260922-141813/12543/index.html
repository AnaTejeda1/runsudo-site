Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches contain the identical root-cause fix for issue 12543: they add the `images.ActionFilter` constant, tag filter operations with it, and gate the source-palette re-application in `doWithImageConfig` with `conf.Action != images.ActionFilter` so overlay/text output is no longer clamped back to an indexed PNG's palette. On correctness of the reported issue they are equivalent. The deciding factors are tests and scope. Patch B adds a targeted regression test, `TestImagesFiltersPalettedIsTrueColor`, that overlays true-color content (sunset.jpg) onto an indexed PNG and asserts the published output is NOT `*image.Paletted`. That test would fail before the fix (paletted, quality-limited) and pass after, directly exercising the exact scenario the issue describes. Patch A adds no such assertion for the actual issue — its only evidence for the overlay fix is opaque updated golden binaries, and its new test additions (color_test.go) exercise a *different* concern. Which leads to scope: Patch A bundles a substantial, unrelated change to resources/images/color.go (NRGBA normalization, ColorGoToHexString un-premultiplication, AddColorToPalette value comparison, hexStringToColorGo returning NRGBA) explicitly attributed to issue 12536, not 12543. That is scope creep against this issue, and its ripple is visible: it forces an extra golden change (padding-transparent-chained.png) beyond the overlay/text goldens both patches touch, signaling broader behavioral impact unrelated to the overlay bug. Under the ordered criteria — equal correctness on the reported issue, superior and directly-relevant test coverage in B, and tighter scope in B — Patch B is the better fix. Patch A's color work may be valid on its own merits, but it belongs to a separate issue and dilutes a focused fix.

	"image"
	"image/png"
	"log"
	"os"

	_ "image/png"

func main() {
	// Get the background image (24 bit: indexed not true color)
	f, err := os.Open("background.png")
	if err != nil {
		log.Fatal(err)
	}
	bgImage, _, err := image.Decode(f)
	if err != nil {
		log.Fatal(err)
	}

	// Get the foreground image (24 bit with 8 bit alpha channel)
	f, err = os.Open("foreground.png")
	if err != nil {
		log.Fatal(err)
	}
	fgImage, _, err := image.Decode(f)
	if err != nil {
		log.Fatal(err)
	}

	// Create a new image with dimensions of the bgImage.
	dstImage := image.NewRGBA(bgImage.Bounds())
	// Copy the bgImage to the dstImage.
	gift.New().Draw(dstImage, bgImage)
	// Draw the fgImage over the dstImage at the (20, 20) position.
	gift.New().DrawAt(dstImage, fgImage, image.Pt(20, 20), gift.OverOperator)

	// Create the composite file.
	f, err = os.Create("composite.png")
	if err != nil {
		log.Fatal(err)
	}
	defer f.Close()

	// Encode the composite image.
	err = png.Encode(f, dstImage)
	if err != nil {
		log.Fatal(err)
	}
}

Summary

What was wrong

When a background image was an indexed (palette-based, ≤256-color) PNG, compositing filters like images.Overlay and images.Text produced palette-limited output of poor quality. The root cause was in resources/image.go's doWithImageConfig: for any PNG-target operation whose decoded source was *image.Paletted, a block re-applied the source's palette via Floyd–Steinberg dithering, throwing away the true-color result that doFilter had correctly produced. This palette clamping is a legitimate size optimization for geometric transforms (resize/crop/fit/fill), but for .Filter operations it destroys the newly composited true-color content. GIFs were unaffected because they flow through a separate animated code path.

What I changed

  • resources/images/config.go: added constant ActionFilter = "filter" (not added to the geometric-only Actions map).
  • resources/image.go: replaced the bare "filter" literal with images.ActionFilter, and gated the palette re-application block with conf.Action != images.ActionFilter so it is skipped for filter operations while still preserving indexed output for resize/crop/fit/fill.
  • resources/images/images_golden_integration_test.go: added regression test TestImagesFiltersPalettedIsTrueColor that overlays a true-color sunset onto an indexed PNG and asserts the published PNG is not *image.Paletted.
  • Regenerated the two buggy pre-fix golden binaries .../filters/paletted/overlay.png and text.png (colortype 3 → 2, true color). No other goldens changed.

Test evidence

  • New regression test failed before the fix (got: bool(true) — output was *image.Paletted) and passes after.
  • TestImagesGoldenFiltersPaletted passes against the corrected true-color goldens.
  • Full-package gates all green: ./resources/images/, ./resources/ (incl. TestImageResize8BitPNG, which confirms resize-of-indexed-PNG behavior is unchanged), and ./tpl/images/.
  • git diff --stat confirms only the two paletted filter goldens changed; resize/process goldens untouched.

Requirements checklist

  1. Fix poor overlay quality for indexed-PNG backgrounds → implemented; output is now true color (test + regenerated golden evidence).
  2. images.Text on indexed PNG (the report's second filter case) → implemented by the same gate; regression-guarded via the corrected text.png golden.
  3. Preserve "GIFs work fine" and don't regress geometric resize of indexed PNGs → verified unchanged: resize goldens byte-identical, TestImageResize8BitPNG still passes, GIF/animated path untouched.

All changes are left uncommitted in the working tree.
