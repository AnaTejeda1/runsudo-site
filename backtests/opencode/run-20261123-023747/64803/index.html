Description

On Windows 11, when I ask the agent to run two shell commands in the same step, one of them never starts:

Command failed: Write-Output REP-ONE: failed to spawn
C:\Users\<user>\AppData\Local\Microsoft\WindowsApps\pwsh.exe: 拒绝访问。 (os error 5)

The other call in the same step completes normally. Serial shell calls have never failed for me (dozens of commands today), and exit code is still 0 even when the tool call fails.

Controlled run: 6 rounds of the same prompt, 2 shell calls per round. 12 calls total, 6 succeeded, 6 failed, and every single round had exactly one failure. Which one fails is random (sometimes the first, sometimes the second).

This is not specific to the desktop app. opencode run from a clean process tree (both apps' pwsh processes fully gone) reproduces it, and the desktop app and the CLI share one opencode-pty daemon, so I believe the race is in the daemon's spawn path. Two pty daemons were running at the time (service.json shows protocol: 9, different instance ids), and the error appears from both clients.

Things I checked that are not the cause:

  • The App Execution Alias itself works: spawning "...\WindowsApps\pwsh.exe" 10 times in a row from a plain shell succeeded 10/10.
  • Concurrent AppX activation is fine: 6 Start-Process of the same alias at once succeeded 6/6.
  • No process buildup: Get-Process pwsh showed a single process while calls were failing.
  • Not the command text: the failing command is a bare Write-Output.
  • Not other agents or terminals: keeping a non-opencode pwsh alive changes nothing (test passes).
  • Not PATH: removing both WindowsApps directories from PATH before launching does not help, the daemon still tries the alias path, so it does not resolve the shell through PATH when spawning.

Workaround I use now: keep shell calls serial, do parallel work inside one command (ForEach-Object -Parallel, Start-Job, Start-Process). Starting the daemon over makes single calls work again but parallel calls still fail.
