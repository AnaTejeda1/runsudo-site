Splunk node: relative time specifiers become NaN and Splunk silently ignores the bound, returning ~8x the requested data with no error

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the headline problem: Splunk relative specifiers such as `-5m`, `now`, `-1d@d` and `@d` are no longer run through Date.parse and emitted as `NaN`, and absolute ISO timestamps are still converted to epoch seconds. The independent test runs crashed on every tree (the tests were placed in the wrong package), so they provide no signal and the verdict rests on the diffs.

Correctness: Patch A classifies the value explicitly (relative-time regex passthrough, bare-number epoch passthrough, Date.parse for absolutes) and throws a NodeOperationError with field name and item index for anything else. That satisfies the issue's stronger requirement that an unparseable bound must never become a silently wider search. Patch B passes anything Date.parse cannot read straight through to Splunk; that is fine for valid relative specifiers but delegates validation of garbage to a server the issue has already shown silently accepts at least one bad value (`NaN`). B's special case that keeps four-digit numbers as years (`'2024'` -> epoch of 2024-01-01 while `'1'` and `'1577836800'` pass through as strings) is an odd, inconsistent rule preserved only for backward compatibility. A's regex could in principle reject some exotic Splunk-accepted inputs (e.g. Splunk's `%m/%d/%Y:%H:%M:%S` form, bare `rt`), but it fails loudly rather than silently, which is the failure mode the issue asks for. A also fixes the v1 continueOnFail handler (`error.cause?.error ?? error.message`), which is necessary because the new locally thrown NodeOperationError has no `cause.error` and would otherwise produce a TypeError; without that, A's own throw path would have been broken in v1.

Tests: A adds unit tests for both v1 and v2 toUnixEpoch plus node-level tests for v1 execute and v2 search.create asserting the exact body sent to `/services/search/jobs`, including the mixed absolute/relative case and the continue-on-fail output. These would fail on base. B adds unit tests only for the helper; they are genuine and would fail on base for relative inputs, but do not exercise the callers.

Scope and craft: A's change is larger (signature change, four call sites per version, error-handler tweak) but all of it is in service of the fix and is coherent and well-commented. B is minimal and low-risk but leaves the 'reject with explicit error' half of the expected behaviour unaddressed and carries the year special case. A is the better fix.

The issue

View on GitHub

Describe the bug

Splunk node, Search Job > Create: earliest_time / latest_time / index_earliest / index_latest are passed through toUnixEpoch(), which is:

function toUnixEpoch(timestamp) {
    return Date.parse(timestamp) / 1000;
}

Date.parse returns NaN for every Splunk relative time specifier (-15m, -24h, -1d@d, now, @d). NaN / 1000 is NaN, and NaN is then sent to Splunk as the literal string NaN.

Splunk accepts earliest_time=NaN with HTTP 201 and silently ignores the bound. So the search runs over a different — much wider — time range than the user asked for, with no error anywhere.

Measured against Splunk 10.2.1, search index=_internal | stats count:

earliest_time sentevents returned
-5m (what the user typed)1,462
NaN (what the node actually sends)12,027
omitted entirely (all time)12,029

The node returns ~8× the requested data and reports success. For alerting, metrics or any rate-based logic this is silent data corruption rather than a visible failure.

Splunk's own API accepts relative specifiers directly — no conversion is needed:

earliest_timeHTTP
-1d@d201
-15m201
-24h201

Prior report

This was reported as #10447 (Aug 2024) and closed NOT_PLANNED as "working as expected… we don't currently support the relative time options". Respectfully, the measurement above shows the outcome is not merely an unsupported input: an unsupported input that is silently converted to NaN and then silently ignored by the server produces wrong results that look correct. Rejecting the input with a clear error would be "not supported"; this is not that.

To Reproduce

  1. Splunk node, Resource Search Job, Operation Create.
  2. Search: search index=_internal | stats count
  3. Additional Fields: Earliest Time = -5m, Latest Time = now.
  4. Execute, then fetch the job's results.
  5. Compare with the same search issued directly to /services/search/jobs with earliest_time=-5m.

The node's count matches an all-time search, not a 5-minute one.

Expected behavior

Pass relative specifiers through unchanged (Splunk parses them natively), and apply toUnixEpoch only to absolute timestamps — or validate and reject an unparseable value with an explicit error instead of emitting NaN. Under no circumstance should an unparseable time bound become a silently wider search.
