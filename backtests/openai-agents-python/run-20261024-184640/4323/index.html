The issue

View on GitHub

This is a narrowed follow-up to #2671.

#2671 requested better support for application state changes between agent turns. The discussion covered several related but distinct cases, including:

  • User input arriving while a tool is running.
  • Application state changing before the next model call.
  • Conversation history compaction.
  • General host control over turn transitions.

The current SDK provides separate solutions for much of that original scope:

  • RunConfig.call_model_input_filter can modify the prepared payload immediately before each model call.
  • cancel(mode="after_turn") can stop a streaming run after the current model and tool work completes.
  • A host can start a new run with result.last_agent, the same Session, and newly arrived input.
  • RunState supports durable pause and resume for interrupted runs.
  • Session compaction is handled separately by the compaction Session APIs.

The remaining gap is narrower:

Applications cannot attach durable pending input to a resumable RunState and have that input admitted exactly once immediately before the state's next model call.

Concrete scenario

A streaming run produces a tool call. While the tool is executing, a new user message arrives.

The application allows the current turn to complete:

result = Runner.run_streamed(
    agent,
    initial_input,
    session=session,
)

async for event in result.stream_events():
    if new_user_input_available():
        result.cancel(mode="after_turn")

After stream_events() finishes, the completed tool call and tool output are available in the result:

state = result.to_state()

The application should be able to attach the newly arrived input to that state, persist the updated state if necessary, and resume it later:

# Illustrative API only.
state.add_input("The user changed the requested destination.")

serialized = state.to_json()

# The state may be resumed immediately or by another worker.
state = await RunState.from_json(agent, serialized)
result = await Runner.run(agent, state, session=session)

The next model request should observe the following order exactly once:

initial user input
assistant tool call
tool output
late user input

The completed tool call must not be executed again.

Why existing approaches are not equivalent

Starting a new run

When a new run boundary is acceptable, the host can already use the same Session and pass the late message as the new run input:

result = await Runner.run(
    stopped_result.last_agent,
    late_input,
    session=session,
)

This is the recommended existing workaround. It correctly places persisted tool work before the new input.

However, it represents the continuation as a new run rather than as a continuation of the existing resumable state. Applications that need to preserve the existing RunState boundary, current agent, remaining turn budget, trace resume state, or durable workflow record cannot express that requirement through the new-run pattern.

Using call_model_input_filter

call_model_input_filter can add late input to the next model payload, but the added item is only part of that prepared request. It is not automatically represented in:

  • The client-managed Session.
  • RunResult.to_input_list().
  • A serialized RunState.
  • Other SDK-owned conversation history and provenance surfaces.

This makes it appropriate for model-view filtering and rewriting, but not a complete durable-input admission mechanism.

Compaction

Conversation compaction is a separate state-ownership problem and is not part of this proposal. Existing model-input filtering and Session compaction APIs should continue to own that behavior.

Proposed behavior

A possible public shape is:

state.add_input(input)

The exact API shape may differ, but the behavior should follow these rules.

Staging

  • Accept the same string or input-item forms supported by normal Runner input.
  • Normalize string input as a user message.
  • Preserve the order of multiple additions.
  • Store the pending input in RunState.
  • Preserve pending input through to_json(), to_string(), from_json(), and from_string().

Adding pending input does not itself execute guardrails, tools, or model requests.

Admission boundary

Pending input is admitted only when the resumed run is ready to make its next model call.

If the state contains unfinished work, the Runner completes that work first. For example, when the state contains pending tool approvals, the ordering is:

resolve approvals
execute approved tools
record tool outputs
admit pending input
make the next model request

If unresolved approvals remain and no model request can begin, the input remains pending.

The input must not be inserted into an already-running model request or tool execution.

Guardrails

Admitting pending input creates a new input-admission boundary.

Immediately before admitting it, the Runner should:

  • Run the input guardrails belonging to the agent that will receive the next model call.
  • Run applicable RunConfig.input_guardrails.
  • Evaluate only the newly pending input, not the complete replayed history.

If a guardrail trips or raises:

  • The next model request must not start.
  • Already completed tool work must not be rolled back or replayed.
  • The pending input must remain inspectable and recoverable so the application can remove, replace, or retry it deliberately.

Ordering and exactly-once behavior

After successful admission, pending input must appear exactly once:

  • After all previously completed tool and handoff items.
  • Before the next model response.
  • In client-managed Session history.
  • In normalized replay output.
  • In subsequent RunState snapshots.
  • In the server-managed conversation delta when that conversation strategy is active.

The pending input must be marked as consumed only after the applicable persistence and conversation-ownership boundary has accepted it. Retrying or serializing the state must not duplicate it.

Run continuity

Adding pending input must not itself consume a turn.

The next model request should advance turn accounting normally while preserving the existing resumed-run behavior for:

  • The current agent.
  • max_turns and the current turn count.
  • Trace resume state.
  • Tool-use tracking.
  • Session persistence.
  • Server-managed conversation tracking.
  • Sandbox and other serialized resume state.

This proposal does not require changing the existing usage-accounting semantics across resume segments.

Supported states

Pending input may be attached to any non-terminal RunState that can eventually reach another model call.

This includes states produced by:

  • cancel(mode="after_turn").
  • Tool approval interruptions.
  • Other supported resumable interruptions.

A terminal state with no possible next model call must reject the operation before side effects.

If a conversation strategy cannot provide the required ordering and exactly-once behavior, the SDK should reject pending input for that strategy before starting resume work rather than silently dropping or duplicating it.

Non-goals

This issue does not propose:

  • Mutating an active model request or tool execution.
  • A general on_turn_start or on_turn_end hook.
  • A mutable ActiveRun stepper API.
  • An SDK-owned cross-thread message queue.
  • Thread-safe input injection into a live run.
  • Arbitrary conversation-history replacement.
  • Conversation compaction.
  • Reordering or modifying already completed tool work.
  • Changing normal input-guardrail behavior for runs without pending state input.
  • Replacing the existing Session/new-run workaround.

Acceptance tests

A focused implementation should cover at least these cases:

  1. An after-turn state resumes with late input ordered after the completed tool output.
  2. The completed tool executes exactly once.
  3. Multiple pending input additions preserve their insertion order.
  4. Pending input survives a full RunState serialization round trip.
  5. A client-managed Session persists the input exactly once.
  6. Server-managed continuation sends the input exactly once as the appropriate unsent delta.
  7. Approval resolution and tool execution complete before pending input is admitted.
  8. Remaining unresolved approvals keep the input pending.
  9. A guardrail trip prevents the next model request and leaves the pending input recoverable.
  10. Streaming and non-streaming resume produce equivalent conversation history.
  11. Retrying a failed model request does not duplicate the admitted input.
  12. Adding input to a terminal state fails before side effects.

Compatibility

This should be an additive capability:

  • Existing Runner.run(...) calls remain unchanged.
  • Existing RunState snapshots deserialize with no pending input.
  • Existing input guardrails retain their current behavior unless pending input is explicitly attached.
  • Existing Session, explicit replay, and server-managed conversation strategies retain their current ownership rules.
  • The serialized RunState schema should be versioned according to the repository's durable-state compatibility policy.

Existing workaround

Applications that do not require continuation of the same RunState should continue using the simpler supported pattern:

  1. Call cancel(mode="after_turn").
  2. Consume stream_events() until completion.
  3. Start a new run with result.last_agent, the same Session, and the newly arrived input.

This issue is limited to applications for which that new-run boundary is materially insufficient.
