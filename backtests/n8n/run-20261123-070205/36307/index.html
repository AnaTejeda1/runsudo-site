Home Assistant node: State Upsert wipes existing attributes when none are set

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

The issue states the expected behaviour precisely: when no State Attributes are configured, the POST body should not include an `attributes` property, and attributes should only be sent when the user explicitly sets them. Patch B implements exactly that: it builds `body = { state }` and only adds `attributes` when `stateAttributes.attributes` is a non-empty list, which also covers the empty-list case and eliminates the `Cannot set properties of undefined` secondary bug by building the attributes object separately before assigning it. The change is minimal, readable, drops the `@ts-ignore`, and its tests exercise the real request path (real `homeAssistantApiRequest` through `helpers.request`), asserting method, URI, and that the body equals `{ state }` with no `attributes` key for both the empty-collection and empty-list cases, plus the positive case. Those tests would fail on base (base always sends `attributes: {}`) and pass after. Patch A diverges from the issue's stated expectation: instead of omitting `attributes`, it issues an additional GET `/states/<entity_id>` per item and echoes the fetched attributes back in the POST. That doubles API traffic, introduces a read-then-write race, adds new failure modes (any non-404 error on the GET now aborts the upsert, and the 404 check depends on `httpCode === '404'` string matching), and relies on `setSafeObjectProperty` being exported from `n8n-workflow`, which is unverified from the diff. Its tests mock `GenericFunctions` wholesale, so they verify the node's call arguments rather than the actual request body, and they encode the extra-GET behaviour the issue did not ask for. The prototype-pollution hardening is out of scope and neutral at best. The independent tests crashed on all three trees, so they provide no discriminating evidence. On correctness against the issue's stated expectation, scope, and test fidelity, B is the better fix.

The issue

Bug Description

When using the Home Assistant node with resource State and operation Upsert, the node always includes an empty attributes: {} object in the request body when no State Attributes are configured. The Home Assistant POST /api/states/<entity_id> endpoint replaces an entity's attributes with whatever is sent, so upserting only a state (without attributes) wipes any existing attributes on that entity.

Root cause: in packages/nodes-base/nodes/HomeAssistant/HomeAssistant.node.ts, the upsert body is built as { state, attributes: {} } and the empty attributes object is sent unconditionally.

Secondary issue found in the same code path: because the attributes object was initialized but then written via a computed key on a body that no longer had the key after a partial fix, setting attributes could also throw
Cannot set properties of undefined. The fix only sends attributes when the user actually provides them.

To Reproduce

  1. In Home Assistant, create/pick an entity that has attributes (e.g. a sensor with unit_of_measurement and friendly_name).
  2. In n8n, add a Home Assistant node → Resource: State → Operation: Upsert.
  3. Set the Entity ID and a new State, and leave State Attributes empty.
  4. Execute the node.
  5. Check the entity in Home Assistant → its previously set attributes have been removed (only the new state remains).

Expected behavior

Upserting a state without configuring any State Attributes should update only the state and leave the entity's existing attributes untouched - i.e. the request body should not include an attributes property when none are provided. Attributes should only be sent when the user explicitly sets them.
