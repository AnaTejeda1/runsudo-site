Issue #2619 Merged fix PR # Run 6 Oct 2026 · run-20261006-181938 jhy/jsoup

Should not print a void element's children

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the root cause in the same three places: html(), outerHtmlHead, and the Printer traversal. Each suppresses a void element's children only for HTML syntax and the HTML namespace.

Patch A changes how Printer traverses. It switches Printer from NodeVisitor to NodeFilter and returns SKIP_ENTIRELY for every HTML void element, including the ordinary childless ones. This has two costs:
- SKIP_ENTIRELY suppresses tail() for all void elements, so the pretty and outline printers' addTail logic no longer runs for normal <br>, <img> or <hr>. That is a behavioural change to the common case and risks whitespace regressions.
- Changing the interface type is a broad change. Any traverse helper or subclass that relies on NodeVisitor semantics must also adapt, and the diff does not show this.

Patch A also leaves outerHtmlTail unguarded, so it relies entirely on the traversal never reaching the tail.

Patch B is narrower:
- It enters skip mode only when a void element actually has children, so existing output for normal void elements is untouched.
- It also guards outerHtmlTail, so no </br> can leak out.
- It uses one well-named predicate, serializesAsVoid(out), in all four places.

Patch B's tests are stronger. They check that pretty, compact and outline output with injected children is identical to an unmodified document, cover html() and outerHtml(), and confirm the children stay in the DOM and still print in XML syntax. Patch A tests only compact mode, plus XML and a foreign-namespace case; it never exercises the pretty printer, which is where its riskier change matters.

B adds no CHANGES entry, which is minor. Overall, B is the safer and better-verified fix.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

https://html.spec.whatwg.org/multipage/parsing.html#serialising-html-fragments

If current node serializes as void, then continue on to the next child node at this point.

It's possible that via DOM manipulation, a void element gets children. In that case, we should not be printing their content, as it makes for inconsistent output.
