Automatic summary may generate invalid HTML with blockquotes and lists

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the core reported case. When an automatic summary would end inside a blockquote or list, each extends the cutoff until the open container elements are closed. Both add unit and integration tests that fail before the change and pass after it.

Patch A goes further, in ways that bear directly on the issue's goal that `.Summary` never emit unbalanced HTML:

1. **Unbalanced input.** When the input is malformed and no balanced position exists, `Summary()` appends end tags for any elements still open. Patch B returns the raw cut in that case; its own test expects `<div><p>foo</p>` with the `<div>` left unclosed. That is the same leak the issue describes.
2. **Manual `<!--more-->` divider.** Patch A handles a divider placed inside a blockquote or list. It closes the open elements in the summary, and in `ContentWithoutSummary` it drops the now-redundant end tags or re-opens the original start tags. Patch B leaves the divider path untouched, so a divider inside a blockquote still produces leaking HTML.
3. **Parsing.** Patch A uses the standard `golang.org/x/net/html` tokenizer. It handles case, attributes, comments and raw text robustly. Patch B hand-rolls a roughly 150-line custom tag scanner, which is more code to maintain and more room for edge-case bugs.

Patch A's tests cover:
- Markdown blockquotes, lists, and nested lists inside blockquotes.
- AsciiDoc and reStructuredText wrappers.
- The unbalanced fallback.
- Dividers inside blockquotes and lists, including uppercase tags and attributes.

Patch B also rewrites the existing benchmark and removes its correctness assertions on Content, Summary and ContentWithoutSummary. That is unrelated churn that weakens existing checks.

Overall, Patch A is more correct and complete with comparable scope risk.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Issue

Using a blockquote that extends past the .Summary cutoff causes the content below {{ .Summary }} to be treated as part of the blockquote until the end of the parent tag. Reproduction repo

<img width="848" height="652" alt="Image" src="https://github.com/user-attachments/assets/212f747c-af3c-4af5-89fe-78fe9dc04ebd" />

Hugo's .Summary may lead to blockquote end tag be below cutoff point

Explanation

In most modern browsers this html code will be parsed and rendered without errors

<!DOCTYPE html>
<html>
<head>
<meta charset="utf-8">
<meta name="viewport" content="width=device-width">
</head>
<body>
  <main>
    <blockquote>
      <p>1</p>
  </main>
</body>
</html>

Leading to shown in browser as a source

<!DOCTYPE html>
<html>
<head>
<meta charset="utf-8">
<meta name="viewport" content="width=device-width">
</head>
<body>
  <main>
    <blockquote>
      <p>1</p>
      <!-- This blockquote end tag was automatically inserted -->
    </blockquote>
  </main>
</body>
</html>

This is due to these parsing rules

An end tag whose tag name is one of: "address", "article", "aside", "blockquote", "button", "center", "details", "dialog", "dir", "div", "dl", "fieldset", "figcaption", "figure", "footer", "header", "hgroup", "listing", "main", "menu", "nav", "ol", "pre", "search", "section", "select", "summary", "ul"

If the stack of open elements does not have an element in scope that is an HTML element with the same tag name as that of the token, then this is a parse error; ignore the token.

Otherwise, run these steps:

Generate implied end tags.

If the current node is not an HTML element with the same tag name as that of the token, then this is a parse error.

Pop elements from the stack of open elements until an HTML element with the same tag name as the token has been popped from the stack.
