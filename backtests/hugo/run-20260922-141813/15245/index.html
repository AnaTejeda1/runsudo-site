The issue

View on GitHub

TL;DR: the generated package.json has no "private": true and a checkout-derived name, so committed copies are publishable under names sites don't control. Suggested fix: emit "private": true and a stable (ideally scoped) default name.

Does this issue reproduce with the latest release?

Yes (transcript below is v0.165.0). The behavior is in master's package_builder.go.

What happened

hugo mod npm pack writes packages/hugoautogen/package.json with:

  • a name derived from the checkout directory, so it varies per clone and can be a registry name the site doesn't control, and
  • no "private": true, npm's do-not-publish guard for internal packages.

The file is regenerated wholesale on each run, so hand-set fields don't survive. From a fresh clone of a repo whose committed copy was hand-normalized:

$ git clone https://github.com/google/docsy-example.git site-a && cd site-a
$ grep -E '"(name|version|private)"' packages/hugoautogen/package.json
  "name": "@docsy/hugoautogen",
  "version": "0.1.0",
  "private": true
$ hugo mod npm pack
$ grep -E '"(name|version|private)"' packages/hugoautogen/package.json
  "name": "site-a",
  "version": "0.1.0"

A sibling clone of the same repo into site-b yields "name": "site-b".

Why it matters

Sites that commit the generated workspace (e.g. so npm ci works without running Hugo first) end up carrying a manifest that npm workspace publishing and common release tools treat as publishable by default: npm publish --dry-run --workspaces packs it as site-a@0.1.0, while with "private": true npm skips the workspace. The name variance also churns the committed manifest, and the lockfile's workspace entry, across differently named checkouts.

What did you expect

The generated internal workspace is non-publishable ("private": true) and has a stable, project-controlled default name rather than the checkout directory's basename. Ideally the default is scoped: a bare name can be claimed on the registry by anyone, a scoped one only by the scope owner.

Workaround

docsy-example#487 follows each pack invocation with a single npm pkg set line restoring a scoped name and private.

Happy to send a PR for the private field (and for the name default, if you have a preference for what it should be).

Summary

What was wrong
hugo mod npm pack (modules/npm/package_builder.go, Pack) regenerated packages/hugoautogen/package.json with a "name" derived from the checkout/working-directory basename (sourceFs.Stat("") → rfi.Name()) and no "private": true. Committed copies of the generated manifest were therefore publishable by default (npm workspace tooling packs them), and the name churned across differently-named clones.

What I changed

  • modules/npm/package_builder.go:
  • Added constant defaultPackageName = "hugoautogen" (a stable, project-controlled name matching the packages/hugoautogen autogen folder).
  • Removed the directory-basename derivation and set "name": defaultPackageName.
  • Added "private": true to the generated autoGenPkg map.
  • modules/npm/package_builder_integration_test.go: added regression test TestPackageBuilderPackageJSON that runs npm.Pack, reads the generated packages/hugoautogen/package.json, and asserts private == true and name == "hugoautogen".
  • Updated the golden fixtures that encoded the old behavior (7 generated-package blocks across testscripts/commands/mod_npm.txt, mod_npm_withexisting.txt, mod_npm__moduleorder.txt): name → hugoautogen, added "private": true (alphabetical key order: dependencies, devDependencies, name, private, version). The site's own root package.json goldens and all hugo_packagemeta.json blocks were left untouched. These cmp assertions remain equally strict — only the expected value was corrected to match the intended fix.

Test evidence

  • Before fix: TestPackageBuilderPackageJSON FAILED — pkg["private"] was nil, want true.
  • After fix (all in-container via ./bt-test):
  • ./bt-test ./modules/npm/ → TestPackageBuilder (both npm and npm_test packages) PASS, TestPackageBuilderPackageJSON PASS, package ok.
  • ./bt-test . -run TestCommands/mod_npm → TestCommands/mod_npm, TestCommands/mod_npm_withexisting, TestCommands/mod_npm__moduleorder all PASS.

Blast radius: Grep confirmed no code in modules/npm/ (or modules/collect.go workspace-resolution logic) reads the generated package's name field — workspaces are referenced by path (FolderPackagesHugoAutoGen), so removing the basename derivation is safe. The pinned PackageFilesSum hash and hugo_packagemeta.json goldens are unaffected because that sum hashes input package files, not the generated output (verified: those goldens/hashes needed no change and the tests confirm it).

Requirements checklist

  1. Emit "private": true in the generated manifest — ✅ Implemented (package_builder.go), asserted by TestPackageBuilderPackageJSON (fails before, passes after) and by the three testscript goldens.
  2. Stable, project-controlled default name instead of checkout-directory basename — ✅ Implemented (defaultPackageName = "hugoautogen"), asserted by the regression test (name == "hugoautogen") and testscripts (previously script-<testname>, now hugoautogen).
  3. "Ideally the default is scoped" — Skipped by deliberate design decision (report offered this as optional and deferred to maintainer preference: "if you have a preference for what it should be"). With "private": true the manifest is never published, so the registry-squatting concern that motivates scoping does not apply; a bare stable name fully resolves the churn concern. Evidence: the report's own rationale ("a bare name can be claimed on the registry by anyone") is neutralized by the private flag, which the fix adds.
