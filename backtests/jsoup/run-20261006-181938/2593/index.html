jsoup bodyStream() silently truncates responses at Integer.MAX_VALUE despite maxBodySize(0)

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the root cause the same way. `SimpleBufferedInput` used `Integer.MAX_VALUE` as a stand-in for 'unlimited' and decremented it, so reads stopped after 2,147,483,647 bytes. Each patch replaces the sentinel with an explicit `capped` flag and an `uncap()` method, and applies it everywhere the sentinel was used (`read`, `reset`, `max`).

Patch A stops there. It is small and easy to verify. It covers the issue's scenario, because `bodyStream()` reads through `buff`, which now starts uncapped. Its unit tests use a virtual stream larger than `Integer.MAX_VALUE` and would fail before the change. They cover a fresh `bodyStream()`, the cap-then-uncap path via `max()`, and `mark`/`reset`. One gap: `readPos` can overflow on the direct-read path, but that only affects progress reporting, not the bytes delivered.

Patch B also fixes the bug, adds `readPos` saturation, and adds a good integration test with a gzip body that expands past 2GB. However, it bundles in a major behavior change. `bodyStream()` now goes through the `ControllableInputStream`, so it enforces `maxBodySize` and the timeout. Because the default max body size is 2MB, existing users who stream large downloads without `maxBodySize(0)` would silently get only 2MB. The patch also adds a new public API (`isTruncated`), single-byte lookahead probing, and a `skip` override. It rewrites existing tests (`remainingAfterFirstRead`, `noLimitAfterFirstRead`) to match the new semantics, which confirms the change breaks prior behavior.

This extra scope is not neutral: it adds real regression risk and makes the actual fix harder to see. Since both patches are equally correct on the reported issue and A's tests target it directly, A is the better fix.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The issue

View on GitHub

When using Connection.maxBodySize(0) together with Response.bodyStream() to download a large binary response, the response appears to be silently truncated at exactly Integer.MAX_VALUE (2,147,483,647) bytes.

I understand that jsoup is primarily an HTML parser rather than a dedicated large-file download tool. However, the documentation for maxBodySize(0) explicitly describes 0 as:

an infinite amount (bounded only by your patience and the memory available on your machine)

This makes the observed behaviour somewhat unexpected. More importantly, the truncation is silent: the InputStream reaches EOF normally, so the calling application has no indication that the response was incomplete.
