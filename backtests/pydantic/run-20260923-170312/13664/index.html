JSON Schema ignores ser_json_temporal, so serialization schemas contradict model_dump_json() output

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches correctly handle every scenario the issue explicitly describes (all issue cases set `ser_json_temporal`, so both read a concrete 'seconds'/'milliseconds'/'iso8601' value). The deciding factor is how each handles the *default* config path in date/time/datetime. Patch A returns a number only when the value is explicitly `in ('seconds','milliseconds')`, so any unset/default/unrecognized value fails safe to `{'type':'string','format':...}` — the correct default serialization schema regardless of what the config default actually resolves to. Patch B instead passes the raw `self._config.ser_json_temporal` into `_common_temporal_schema`, which returns `{'type':'number'}` for *anything that isn't exactly the string 'iso8601'*. Its correctness therefore depends on the resolved default of `ser_json_temporal` being literally 'iso8601'; if that default is `None` (as pydantic-core treats it — SerializationConfig checks presence rather than assuming a string), every temporal field's serialization schema silently becomes `number` by default, a fail-open regression worse than the original bug. Notably, B's own signature types `temporal_format` as `Literal['iso8601','seconds','milliseconds']`, which a `None` default would violate, and B's tests never exercise the unset-default case, so the risk is untested. Both timedelta-precedence implementations are equivalent and correct (guarding on `'ser_json_temporal' in config_dict`). On tests, B is actually stronger — its schema-vs-`model_dump_json` cross-check and 4-row precedence matrix are excellent and directly validate the issue's thesis, better than A's simpler asserts — and B's single-helper refactor is slightly cleaner. But correctness is the top-ranked criterion: A is robust across all configurations with no downside, whereas B couples core correctness to an unverifiable assumption about the config default. A is the safer root-cause fix.

Description

ser_json_temporal landed in v2.12 and controls how datetime, date, time and timedelta are serialized to JSON. GenerateJsonSchema was never told about it, so a mode='serialization' schema still says these fields are strings even when model_dump_json() writes numbers.

With ser_json_temporal='seconds' (same with 'milliseconds'), every temporal field is affected:

schema:  {'dt': {'type': 'string', 'format': 'date-time'}, 'td': {'type': 'string', 'format': 'duration'}}
dump:    {'dt': 1577836800.0, 'td': 86400.0}

Running that payload through a JSON Schema validator fails with 1577836800.0 is not of type 'string', so the schema pydantic publishes rejects the output pydantic itself just produced. date_schema, time_schema and datetime_schema read no config at all right now.

There is a second mismatch that goes the other way, on timedelta. timedelta_schema only looks at the older ser_json_timedelta setting. The docs for ser_json_temporal say it takes precedence over ser_json_timedelta, and pydantic-core implements exactly that: SerializationConfig::from_config and TimeDeltaSerializer::build both check whether ser_json_temporal is present in the config before falling back to ser_json_timedelta. The JSON schema layer does not, so setting ser_json_temporal='iso8601' together with ser_json_timedelta='float' gives you the reverse problem:

schema:  {'td': {'type': 'number'}}
dump:    {'td': 'P1D'}

For anyone generating an OpenAPI document from a model this is a silent wrong answer rather than a crash, which is probably why it has gone unnoticed since the setting was added.

I have a patch that mirrors the pydantic-core resolution in the four temporal schema methods, plus tests. Happy to open a PR if you want to assign this to me.

Example Code

# The timedelta precedence case, wrong in the opposite direction:
class Precedence(BaseModel):
    model_config = ConfigDict(ser_json_temporal='iso8601', ser_json_timedelta='float')

    td: timedelta


print(Precedence.model_json_schema(mode='serialization')['properties'])
#> {'td': {'title': 'Td', 'type': 'number'}}

print(json.loads(Precedence(td=timedelta(days=1)).model_dump_json()))
#> {'td': 'P1D'}

What the agent reported

The fix is complete and reviewed. Summary follows.

What was wrong

GenerateJsonSchema never consulted the ser_json_temporal config setting (added in v2.12). In pydantic/json_schema.py:

  • date_schema, time_schema, datetime_schema returned hardcoded string+format dicts, reading no config at all. With ser_json_temporal='seconds'/'milliseconds', model_dump_json() emits numbers, so the published serialization schema rejected pydantic's own output.
  • timedelta_schema only read the older ser_json_timedelta. But ser_json_temporal takes precedence (pydantic-core keys this off the presence of ser_json_temporal in the config dict), so ser_json_temporal='iso8601' + ser_json_timedelta='float' gave {'type': 'number'} while the dump was 'P1D'.

What I changed

pydantic/json_schema.py only (production):

  • Added a helper _temporal_serialized_as_number() returning True when ser_json_temporal is 'seconds'/'milliseconds'.
  • date_schema/time_schema/datetime_schema now return {'type': 'number'} in that case, else the original string+format.
  • timedelta_schema now mirrors pydantic-core precedence: if 'ser_json_temporal' in self._config.config_dict, use it (number vs. duration string); otherwise fall back to the existing ser_json_timedelta behavior — preserving ser_json_timedelta='float' → number.

tests/test_json_schema.py: three regression tests (test_ser_json_temporal_json_schema_number parametrized over seconds/milliseconds, ..._iso8601, and ..._takes_precedence_over_ser_json_timedelta).

Test evidence

  • Before the fix: ./bt-test tests/test_json_schema.py -k ser_json_temporal → 3 failed, 1 passed.
  • After the fix: ./bt-test tests/test_json_schema.py -k "ser_json_temporal or timedelta" → 11 passed, 531 deselected (includes the untouched existing *_default_timedelta tests, confirming no regression to the ser_json_timedelta fallback path).

Reviewer confirmed correctness, valid presence check, correct precedence, and no unrelated/scratch changes.

Requirements list

  1. datetime/date/time schemas honor ser_json_temporal numeric modes — implemented, tested (test_ser_json_temporal_json_schema_number), passing.
  2. ser_json_temporal='iso8601' still yields string+format — implemented, tested (test_ser_json_temporal_json_schema_iso8601), passing.
  3. timedelta precedence: ser_json_temporal overrides ser_json_timedelta — implemented, tested (test_ser_json_temporal_takes_precedence_over_ser_json_timedelta), passing.
  4. Preserve existing ser_json_timedelta='float' behavior when ser_json_temporal unset — preserved via presence-based fallback; existing *_default_timedelta tests still pass.
