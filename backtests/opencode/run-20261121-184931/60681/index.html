TUI: each prompt keystroke re-registers keymap layers (~15 ms JS per key)

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

The issue identifies a specific root cause in opencode's own code: several prompt keymap layers in packages/tui/src/component/prompt/index.tsx compute an eager `enabled` boolean from per-keystroke state (store.prompt.text, cursorVersion()), so every keystroke re-registers ~6 layers and triggers every useKeymapSelector/useShortcuts memo. The issue's own benchmark shows the lazy-`enabled` change dropping p50 from ~15 ms to ~4 ms.

Patch A implements exactly that fix: it converts each layer's `enabled` to a thunk evaluated on demand, removes the cursorVersion signal and its two setters (so cursor/content changes no longer invalidate the layer factories), introduces a hasText memo so the stash and prompt.clear layers only change when the prompt flips between empty and non-empty, and makes the shell-mode ctrl+c command read hasText too. This is consistent with the existing convention already used for command-level `enabled` (e.g. `enabled: () => store.prompt.text === ""`). It also adds a test that subscribes to the keymap's `state` event, types, moves the cursor, and deletes, asserting zero re-registrations — a test that would fail before the change and pass after — plus regression tests that the cursor-position-dependent `!` shell-mode and backspace-exits-shell behaviors still work without the cursorVersion signal, which is the main behavioral risk of removing it. The bun.lock libc churn is lockfile noise and is ignored per the ground rules.

Patch B only bumps @opentui/core, @opentui/keymap and @opentui/solid from 0.8.0 to 0.8.1 (plus the plugin peer range). Nothing in the diff or the issue indicates that 0.8.1 addresses layer re-registration or selector cost, and the issue states the cause lives in opencode's prompt code, which Patch B leaves untouched. Even if the new keymap version happened to cheapen re-registration, the eager `enabled` evaluation and per-keystroke cursorVersion bumps would remain, so at best it masks the symptom; judged on what is in front of me, it has no demonstrated connection to the fix and adds no tests.

On correctness and tests Patch A is clearly stronger; on scope it is focused on the issue; on craft it matches surrounding conventions and documents the hasText memo's purpose. Patch A wins.

Description

Every keystroke in the TUI prompt costs ~15 ms of JS before anything is drawn. strace shows the main thread on CPU for the whole interval from reading the key to writing the screen, and a JS sampling profile puts about half of it in useKeymapSelector memos.

Cause: several prompt keymap layers compute an eager enabled boolean from per-keystroke state inside their Keymap.createLayer factory, in packages/tui/src/component/prompt/index.tsx:

  • the prompt.clear layer reads store.prompt.text
  • the ! shell-mode, backspace-exits-shell and history ↑/↓ layers read cursorVersion(), which is bumped on every content and cursor change
  • the stashCommands memo reads !!store.prompt.text and returns a new array, so its layer re-registers too

So each key unregisters and re-registers about 6 layers. The keymap emits state, and every useKeymapSelector memo recomputes, including one useShortcuts() memo per caller, each of which rebuilds a formatted Map of every registered command (context/keymap.tsx).
