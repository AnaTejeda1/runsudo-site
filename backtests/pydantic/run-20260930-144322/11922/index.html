Some Field attributes lost in JSON schema when using RootModel

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the issue in the same place, `GenerateJsonSchema`'s model-level schema handling. For RootModel they add the root field's `examples` (made JSON-safe with `to_jsonable_python`) and `deprecated`, and apply the root field's `title` instead of the class name. The differences are in edge cases.

1. **How the title is detected.** Patch A reads `root_field.title` whenever it is set. In pydantic, `field_title_generator` can fill in `FieldInfo.title` during schema building. With Patch A, a generated field title could then replace the model's class-name title, which was never asked for. Patch B only uses the title if the user set it explicitly (`'title' in root_field._attributes_set`), and its test checks exactly this case: `Gen` with `field_title_generator` still gets the title 'Gen'.

2. **Title priority.** Patch B places the explicit field title after the config `title` but before `model_title_generator`. That is reasonable: something the user wrote on the field should beat a generic generator. In Patch A, the field title only applies when no generator is configured.

3. **Deprecated values.** Patch B also treats `deprecated=''` as deprecated, which is a small extra edge case.

4. **Tests.** Patch B's single test covers more ground:
   - title, description, examples and deprecated together;
   - the schema is the same when the model is nested under `$defs`;
   - a config title overrides the field title;
   - `field_title_generator` does not leak into the title;
   - a string deprecation message.

   Patch A's tests are clean and separate but only cover the basic cases and the config override.

5. **Craft.** Patch B computes `root_field` once and reuses it, including in the existing description branch. This is tidier than Patch A's repeated `issubclass` checks.

Overall, Patch B is more robust and better tested.

Description

When declaring a RootModel and adding a Field annotation to the root property that includes examples, those examples are not part of the generated JSON schema. This also applies to the deprecated attribute. The title attribute is also not applied or it is overwritten by the class name of the root model class.

Most other attributes, such as pattern or description are exposed as expected. Furthermore, placing examples in json_schema_extra also works as expected.

Example Code

from typing import Annotated
from pydantic import RootModel, Field

class Foo(RootModel):
    root: Annotated[str, Field(examples=["foo", "bar"], deprecated=True)]

print(Foo.model_json_schema())  # does not include examples or deprecated.

What the agent reported

RootModel.model_json_schema() now includes the root field's examples and deprecated, and uses its explicit title instead of the class name. The final test run passed: 1217 passed, 101 skipped, 1 xfailed, 0 failed.

What was wrong: Field(...) settings on a normal model field are attached to that field's schema. A RootModel's root field is handled differently: those settings are thrown away. The only compensation was in _update_class_schema (pydantic/json_schema.py), which copied the root field's description and json_schema_extra onto the model schema. That is why description, pattern and json_schema_extra worked. title, examples and deprecated had no such handling, and the title always fell back to the class name.

What I changed (all in _update_class_schema, pydantic/json_schema.py:1644-1681):

  • Lookup: the root field is looked up once, and the existing description branch now uses that lookup.
  • Title order: config title, then the root field's title, then model_title_generator, then the class name. The root field's title only counts if it was set explicitly with Field(title=...). The reviewer caught that a config field_title_generator also writes into the field's title; without this check, a RootModel using one would have gone from "Foo" to e.g. "ROOT" as its title.
  • Examples: the root field's examples are added to the schema.
  • Deprecated: deprecated is set to True when the root field is deprecated, using the same rule as normal fields, so a message string also counts.
  • json_schema_extra: still applied last, so it can still override all of the above.

Test evidence: I added test_model_with_field_examples_deprecated_title to tests/test_root_model.py. It uses the exact example from the report, adding title and description, and compares the whole schema. It also checks:

  • a model that contains Foo as a field gets the same schema for Foo under $defs;
  • a config title still wins over the root field title;
  • field_title_generator does not change the model title;
  • deprecated='some message' gives deprecated: True.

Before the fix it failed with {'title': 'Foo'} != {'title': 'Foo title'} and examples/deprecated missing. After the fix it passes. The final run covered tests/test_root_model.py, tests/test_json_schema.py and tests/test_docs.py.

Requirements:

  1. examples on root missing from the schema: fixed and tested.
  2. deprecated on root missing: fixed and tested, including the message-string form.
  3. title on root ignored or replaced by the class name: fixed and tested, with config title and field_title_generator behaving as before.
  4. description, pattern and json_schema_extra already worked: still the same. The description branch was only refactored to share the lookup, and the existing tests pass.

One limitation: like the existing description handling, root-field title and examples only fill in values the inner type's schema hasn't already set. So if the inner type brings its own examples, those win. I kept this for consistency with the existing code; ordinary model fields behave the other way round.

The changes are uncommitted in pydantic/json_schema.py and tests/test_root_model.py, with no scratch files.
