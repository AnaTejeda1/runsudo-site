The "failed to extract" error refers to outer shortcode instead of inner shortcode

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

In the issue, `img` has a template that uses `.Inner`, so the parser expects `img` to be closed. It never is. The parser nests `figcaption` inside `img`, then accepts `{{< /figure >}}` as the closer for `img` without checking the name. `figure` then reaches EOF and is reported as the unclosed shortcode. The root cause is that missing name check on closing tags.

Patch A adds exactly that check: when a closing tag's name differs from `sc.name`, it returns "shortcode %q must be closed or self-closed" for the inner shortcode. It also wraps nested errors with the nested item's position. Its test reproduces the issue's figure/img/figcaption structure. It asserts the new message names `img` and does not mention `figure`, and it checks the error position. That test would fail before the change.

Patch B only wraps nested extraction errors with the nested shortcode's position. That helps when the inner error is something like a missing template. It does nothing for the reported case: the mismatched close still silently closes `img`, and the error still says unclosed shortcode "figure". Its test covers a different scenario (inner template not found) rather than the issue's.

A fixes the root cause and tests the reported scenario. B addresses an adjacent symptom.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

What the agent reported

The error now names the inner shortcode that is actually unclosed (img) and points at its line. The new regression test fails without the fix and passes with it. ./bt-test could not run, so all test evidence comes from running go test directly.

What was wrong: In extractShortcode (hugolib/shortcode.go), a closing tag's name was never checked against the shortcode it was closing. In the reported content, img's template uses .Inner, so Hugo expects a closing tag for it. img took {{< /figure >}} as its own closing tag, which left figure reaching end of file unclosed. The error therefore blamed figure, at figure's line (4:1). Also, errors from a nested shortcode were reported at the outer shortcode's position.

What I changed (hugolib/shortcode.go, two small edits):

  1. Name check: if a shortcode that needs .Inner meets a closing tag with a different name, it now fails with shortcode "img" must be closed or self-closed. Self-closing tags, the existing "does not evaluate .Inner … yet a closing tag was provided" error, and errors the parser itself reports behave as before.
  2. Position: errors from a nested shortcode now carry that shortcode's own start position, unless they already have one. This is the same pattern fail() in page__content.go uses for top-level shortcodes.

Test: I added TestErrorNestedUnclosedShortcodeShouldReferenceInner in hugolib/hugo_sites_build_errors_test.go, next to TestErrorNestedShortcode. It builds the exact figure / img / figcaption content from the report and checks that the error names "img", does not mention "figure", and is reported at line 5, column 1.

Test evidence:

  • The gate couldn't run: ./bt-test exits 1 without running any tests. Its report shows the build failing because it can't download Go modules (lookup proxy.golang.org ... server misbehaving). So I ran go test directly with GOMODCACHE=/bt/cache/go-mod GOPROXY=off.
  • Without the fix: the new test fails with "/content/_index.md:4:1": failed to extract shortcode: shortcode "figure" must be closed or self-closed.
  • With the fix: the new test passes, as do the other error and shortcode tests (-run 'TestErrorNested|TestSiteBuildErrors|Shortcode|Inner') and ./parser/....
  • Full ./hugolib/ run (done by the implementer subagent): everything passes except three tests that try to download modules (TestModulePrivateRepo and two TestGitInfoFromGitModule… tests). They fail with permission denied on the module cache, and the implementer reported they fail the same way without the fix.

Blast radius: only shortcode extraction is affected. Content that was already malformed but used to build will now error. For example, in {{< a >}}{{< b >}}text{{< /a >}}, where a doesn't use .Inner, b used to quietly accept /a as its closing tag. The reviewer checked path names ({{< /a/b >}}), inline shortcodes, {{% %}} closing tags and self-closing tags, and none of them change.

Requirements:

  • The error names the inner shortcode, not the outer one: implemented; shown by the new test.
  • The "is closed" check misses shortcodes nested inside another shortcode's .Inner: fixed by the closing-name check; same test.
  • "Before v0.111.0 this compiled fine": not restored, on purpose. The content really does leave img unclosed, and the report only asks for a correct error. To build, the user needs to self-close it ({{< img ... />}}) or remove .Inner from the img template.

The changes are uncommitted. AGENTS.md and CLAUDE.md were already deleted in the working tree before this session, and I left them alone.
