[Bug]: streaming /v1/responses emits no reasoning item for signature-only thinking (Claude Fable 5.1 / Opus 5.5 default, Bedrock adaptive), so reasoning cannot be replayed

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

The production changes are functionally equivalent: both relax `_flush_thinking_block` to keep any signed block regardless of thinking text, and both open the reasoning item in `_ensure_output_item_for_chunk` when the delta carries a thinking block with a `signature` or redacted `data`. The independent tests confirm both fix the issue (all 5 base failures pass on A and B). The differences are in tests and scope. Patch A's streaming test is parametrized over sync/async and over both signature-only and redacted_thinking blocks, asserts the exact `[reasoning, message]` ordering for both the added events and `response.completed`, and checks that `encrypted_content` round-trips to the original block; it also pins the chunk-builder behaviour. Patch B's streaming test covers only signature-only thinking and asserts weaker properties (first item is reasoning, one reasoning item, signature matches), leaving its redacted-thinking (`data`) branch untested. More importantly, Patch B deletes an unrelated 93-line Vertex Gemma test file under `tests/test_litellm/...` and re-adds those tests into `tests/unit/llms/vertex_ai/...`, relying on a `_make_gemma_vertex_response` helper whose existence in that file is not visible in the diff. This is unrelated churn that has nothing to do with the issue, obscures the fix, and introduces risk of a broken test module. Patch A also documents the helper's intent with a docstring explaining why textless blocks still open the reasoning item. A is the cleaner, better-tested, correctly-scoped fix.

What happened?

On streaming /v1/responses backed by an Anthropic model (the chat -> Responses bridge, litellm/responses/litellm_completion_transformation/streaming_iterator.py), a thinking block that has a signature but empty thinking text never becomes a reasoning output item. No response.output_item.added for reasoning is streamed, and response.completed has no reasoning item, so there is no encrypted_content to replay on the next turn. The reasoning tokens are still billed (usage.output_tokens_details.reasoning_tokens is non-zero)

That shape is common: Claude Fable 5.1 and Claude Opus 5.5 return {"type": "thinking", "thinking": "", "signature": "..."} by default, and Bedrock adaptive thinking returns it with or without a reasoning effort. Non-streaming /v1/responses is not affected

Two places key on the thinking text:

  • LiteLLMCompletionStreamingIterator._ensure_output_item_for_chunk opens the reasoning item only when delta.reasoning_content is non-empty. A signature-only block arrives as delta.thinking_blocks=[{"type": "thinking", "thinking": "", "signature": "..."}] with no reasoning_content, so the first output item opened is the message
  • ChunkProcessor.get_combined_thinking_content (_flush_thinking_block) keeps an assembled block only when it collected thinking text, so the signed block is also missing from the assembled response that response.completed is built from

Measured through the proxy against real providers, streaming /v1/responses, is a reasoning item emitted?

backendno reasoning effortreasoning.effort: "high"
Bedrock (Claude Opus 4.8, Fable 5.1, Opus 5.5)nono
Vertex AI (Claude Fable 5.1, Opus 5.5)noyes
Vertex AI, deployment sets thinking: {"type": "adaptive", ...}nono

Reasoning tokens were billed in every cell. The "yes" cell is the only one where the provider returns thinking text, which is why the bug can look provider-specific

User Flow

Before a (hypothetical) fix: a client using streaming Responses with a Claude model loses its reasoning between turns

  1. They send POST https://litellm-domain/v1/responses with "stream": true and "include": ["reasoning.encrypted_content"] to a bedrock/us.anthropic.claude-opus-4-8 (or Fable 5.1 / Opus 5.5) deployment
  2. The stream opens only a message item, and response.completed.response.output is [message], while usage.output_tokens_details.reasoning_tokens is non-zero
  3. They replay output on the next turn. There is no reasoning item to replay, so the model continues without its earlier reasoning

After a (hypothetical) fix: the same request streams reasoning then message, and response.completed.response.output carries the reasoning item with encrypted_content, ready to replay. Responses whose thinking arrives as text are unchanged
