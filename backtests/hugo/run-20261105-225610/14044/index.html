Automatic summary may generate invalid HTML with blockquotes and lists

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches fix the reported markdown cases the same way: after the word-count cutoff they scan forward from the wrapper start and extend the summary end until the elements opened before the cutoff are closed. All five independent tests pass on both, and both add unit and integration tests that fail on base.

The decisive difference is what happens for the non-markdown formats that go through the same function. For AsciiDoc, reStructuredText and Org, the base code already cuts after the first `</div>` unit, leaving section wrappers like `<div class="sect1"><div class="sectionbody">` or `<div class="section">` open. Patch A balances every tag unconditionally, so with those formats the summary would expand to the end of the whole first section, and for a single-section document to the entire content (its scanner returns `sc.pos` when the stack empties exactly at `maxHigh`). That is a real regression in summary length for three supported formats, and Patch A has no test covering it. Patch B explicitly treats div/section/article as containers that do not force expansion, while still including end tags that directly follow the cut (so a markdown blockquote wrapped in a raw `<div>` is still fully closed). It documents this choice in code and pins it with AsciiDoc, RST and Org section tests plus a quoteblock test.

Patch B also reuses the existing golang.org/x/net/html tokenizer, which handles comments, quoted attributes, raw-text elements and case folding for free, and adds simple implied-end handling for repeated `<p>`/`<li>`. Patch A ships about 120 lines of bespoke tag scanning to cover the same ground; it is reasonably careful (and its fallback to the original cutoff on unbalanced input is arguably safer than B's include-the-rest fallback), but that is a narrow edge case compared with the section regression. Patch A also rewrote the existing benchmark and dropped its correctness assertions, which is unrelated churn.

Tests: B's coverage is broader on the issue's scenarios (nested blockquotes, ol, void `<br>`, ContentWithoutSummary and Truncated in the integration test) and on the format-specific tradeoff; A's unit tests focus on scanner edge cases. On correctness under realistic inputs, scope discipline and craft, B is the better fix.

Issue

Using a blockquote that extends past the .Summary cutoff causes the content below {{ .Summary }} to be treated as part of the blockquote until the end of the parent tag. Reproduction repo

<img width="848" height="652" alt="Image" src="https://github.com/user-attachments/assets/212f747c-af3c-4af5-89fe-78fe9dc04ebd" />

Hugo's .Summary may lead to blockquote end tag be below cutoff point

Explanation

In most modern browsers this html code will be parsed and rendered without errors

<!DOCTYPE html>
<html>
<head>
<meta charset="utf-8">
<meta name="viewport" content="width=device-width">
</head>
<body>
  <main>
    <blockquote>
      <p>1</p>
  </main>
</body>
</html>

Leading to shown in browser as a source

<!DOCTYPE html>
<html>
<head>
<meta charset="utf-8">
<meta name="viewport" content="width=device-width">
</head>
<body>
  <main>
    <blockquote>
      <p>1</p>
      <!-- This blockquote end tag was automatically inserted -->
    </blockquote>
  </main>
</body>
</html>

This is due to these parsing rules

An end tag whose tag name is one of: "address", "article", "aside", "blockquote", "button", "center", "details", "dialog", "dir", "div", "dl", "fieldset", "figcaption", "figure", "footer", "header", "hgroup", "listing", "main", "menu", "nav", "ol", "pre", "search", "section", "select", "summary", "ul"

If the stack of open elements does not have an element in scope that is an HTML element with the same tag name as that of the token, then this is a parse error; ignore the token.

Otherwise, run these steps:

Generate implied end tags.

If the current node is not an HTML element with the same tag name as that of the token, then this is a parse error.

Pop elements from the stack of open elements until an HTML element with the same tag name as the token has been popped from the stack.
