Memory leak: transient models using Enum methods or Field(exclude_if=...) survive GC

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

The Rust changes are the same in both patches. Each adds `serialization_exclude_if` to `SerField` traversal, `class` to `EnumSerializer` traversal, and `lookup` to all four `EnumValidator<T>` traversals. That matches the root cause the issue identified, so the two are equally correct, and the difference comes down to tests and scope.

Patch B's tests are stronger:
- It parametrizes the enum GC test over all four validator variants (plain, int, str, float) and over both `SchemaValidator` and `SchemaSerializer`. So each changed traversal impl is exercised.
- Its enum test builds the exact cycle from the issue: enum method closure -> model -> schema -> enum.
- Its `exclude_if` test uses a closure cycle back to the model.
- It adds end-to-end tests in `tests/test_main.py` using real `BaseModel`, `Enum`-with-method and `Field(exclude_if=...)`, mirroring the reported reproduction.
- It keeps the existing free-threaded xfail convention on its new core tests.

Patch A's new tests are valid regression tests:
- The enum class is kept alive through the untraversed `class` and `lookup` edges.
- The `exclude_if` lambda captures `cls` through a default argument.

However, Patch A only covers the `str` sub_type and adds no high-level pydantic test. It also churns the existing tests in ways the issue does not ask for:
- It removes the `is_free_threaded` xfail markers from the existing GC tests, which risks new failures on free-threaded Python below 3.14.
- It drops the `sys` and `is_free_threaded` imports.
- It renames the `__schema__`/`__validator__` attributes and rewrites comments as docstrings.

That churn adds risk and obscures the fix. B wins on test coverage and scope discipline.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Initial Checks

  • I confirm that I'm using Pydantic V2

Description

Transient BaseModel classes are not collected when either:

  • A model field references an Enum whose class defines a Python method.
  • A model field uses Field(exclude_if=<Python callable>).

After the defining module is removed from sys.modules and every ordinary strong reference is dropped, weak references to the model and enum classes remain alive after repeated full gc.collect() calls. Repeating this construction in disposable module namespaces causes linear memory growth.

Controls using an enum without methods or a field without exclude_if are collected normally.

I encountered this in combination with a Temporal workflow sandbox. With a large interconnected model graph and high volume Temporal workflows this can result in multi-GiB process growth relatively quickly.

The likely cause is missing PyGcTraverse edges for Python objects held by pydantic-core:

  • SerField owns serialization_exclude_if, but traverses only serializer: https://github.com/pydantic/pydantic/blob/c67a1397327c6abc1a2e2e921af01aebbbeedf1c/pydantic-core/src/serializers/fields.rs#L26-L38
  • EnumSerializer owns class, but traverses only serializer: https://github.com/pydantic/pydantic/blob/c67a1397327c6abc1a2e2e921af01aebbbeedf1c/pydantic-core/src/serializers/type_serializers/enum_.rs
  • Each EnumValidator<T> owns lookup, but traverses only class and missing: https://github.com/pydantic/pydantic/blob/c67a1397327c6abc1a2e2e921af01aebbbeedf1c/pydantic-core/src/validators/enum_.rs

Traversing py_schema does not compensate for another unreported direct reference: CPython’s collector accounts for every actual strong edge individually.

I tested a temporary build from Pydantic main at c67a1397327c6abc1a2e2e921af01aebbbeedf1c. Adding only these traversal edges made all objects in the reproduction collectible:

  • Add serialization_exclude_if to SerField traversal.
  • Add class to EnumSerializer traversal.
  • Add lookup to every EnumValidator<T> traversal.

For the enum case, changing only the serializer or only the validator was insufficient; both missing edges were required.

This appears related to earlier missing-traversal fixes such as:

  • https://github.com/pydantic/pydantic/issues/5136
  • https://github.com/pydantic/pydantic-core/pull/787
  • https://github.com/pydantic/pydantic-core/pull/1100

I would be happy to submit a focused patch.

Example Code

import gc
import sys
import types
import weakref

def transient_module(name, source, class_names):
    module = types.ModuleType(name)
    sys.modules[name] = module
    exec(compile(source, f"<{name}>", "exec"), module.__dict__)
    refs = tuple(
        weakref.ref(module.__dict__[class_name])
        for class_name in class_names
    )
    del sys.modules[name]
    del module
    return refs

enum_ref, enum_model_ref = transient_module(
    "_pydantic_enum_gc_repro",
    """
from enum import Enum
from pydantic import BaseModel
class Membership(str, Enum):
    FULL = "full"
    def label(self) -> str:
        return self.value

    membership: Membership
""",
    ("Membership", "Model"),
)

(exclude_if_model_ref,) = transient_module(
    "_pydantic_exclude_if_gc_repro",
    """
from pydantic import BaseModel, Field
class Model(BaseModel):
    value: int = Field(exclude_if=lambda value: False)
""",
    ("Model",),
)

for _ in range(5):
    gc.collect()

# All three should be False because no intentional strong references remain.
print("enum alive:", enum_ref() is not None)
print("enum model alive:", enum_model_ref() is not None)
print("exclude_if model alive:", exclude_if_model_ref() is not None)

What the agent reported

I fixed the leak: transient models whose fields use an Enum with methods, or Field(exclude_if=...), are now garbage-collected. The issue's script now prints False False False; before the fix it printed True True True. The changes are uncommitted in the working tree.

What was wrong: three pydantic-core objects hold references to Python objects but don't declare them to Python's cycle collector (the impl_py_gc_traverse! lists). The collector couldn't see those references, so it treated anything in a cycle through them as still in use, and the cycle was never freed.

  • SerField didn't list serialization_exclude_if.
  • EnumSerializer didn't list class.
  • None of the four EnumValidator<T> versions (plain, int, str, float) listed lookup, which holds the enum members.

What I changed: I added those fields to the traversal lists, and nothing else in production code:

  • pydantic-core/src/serializers/fields.rs:38: SerField { serializer, serialization_exclude_if }
  • pydantic-core/src/serializers/type_serializers/enum_.rs:51: EnumSerializer { class, serializer }
  • pydantic-core/src/validators/enum_.rs:171, 203, 219, 235: { class, lookup, missing }

The extension was rebuilt with make build-dev.

Tests added:

  • pydantic-core/tests/test_garbage_collection.py:
  • test_gc_enum: 8 cases, covering validator and serializer for each of the four enum kinds.
  • test_gc_serialization_exclude_if.
  • Both copy the existing tests in that file.
  • tests/test_main.py:
  • test_model_with_enum_with_method_gets_cleaned_up: a BaseModel with a str Enum field whose class has a method.
  • test_model_with_field_exclude_if_gets_cleaned_up: a BaseModel field with Field(exclude_if=lambda ...).
  • Both assert the model classes are collected.

The new tests build the reference cycle explicitly: the enum method or the exclude_if callable points back at the model. The issue's script gets the same cycle through the module's globals.

Test results:

  • Before the fix: all 11 new tests failed ("Timeout waiting for GC" in core, assert False in test_main.py). The 3 existing GC tests passed.
  • After the fix:
  • The core GC tests, the core enum validator tests and all core serializer tests: 835 passed, 6 skipped, 1 xfailed.
  • tests/test_main.py, tests/test_types.py and tests/test_serialize.py: 627 passed, 29 skipped, 2 xfailed.
  • No failures in either run, and no existing test was changed.

cargo fmt and clippy aren't installed here, so neither was run; each edit is a one-line change to a macro's field list.
