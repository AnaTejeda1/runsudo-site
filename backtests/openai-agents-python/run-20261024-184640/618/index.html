Resource tracker warning (leaked semaphores) with MCPServerStdio

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Patch A only adds a warnings.filterwarnings call in the SDK's own process. The leaked-semaphore warning is emitted by the multiprocessing resource_tracker, which runs in a separate helper process spawned by the MCP server child, so a filter installed in the agent's interpreter cannot reach it. Even if it could, it would be masking a symptom (the server being SIGKILLed before it can clean up) rather than fixing it, and it would hide a genuinely useful warning for unrelated leaks in user code. The independent tests confirm this: both scenarios still FAIL-ASSERT under Patch A, identical to base. Patch B identifies the actual mechanism: upstream stdio_client runs its close-stdin/wait/terminate shutdown inside the transport task group, so when those tasks are cancelled (asyncio.run teardown or owner-task cancellation) the graceful sequence is skipped and anyio SIGKILLs the child, which then cannot release its semaphores. B vendors a near-copy of stdio_client that runs the shutdown under a shielded CancelScope, still bounded by the same termination timeout and falling back to _terminate_process_tree. Both independent tests pass under B. B also adds three regression tests that spawn a real FastMCP server and verify via a marker file that the server reached post-mcp.run() code (i.e., exited gracefully) under transport-task cancellation, owner-task cancellation, and asyncio.run shutdown; these would fail on base and pass with the fix. Scope-wise B is larger (duplicating ~150 lines of the upstream transport and relying on private mcp helpers like _create_platform_compatible_process and _terminate_process_tree, which is a maintenance risk if upstream changes), but that risk is justified by a working fix and is clearly documented in the module docstring. A delivers no working fix and no tests, so B wins decisively on correctness and tests.

Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours. Describe the bug

When using an external MCP plugin with the OpenAI Agents SDK (MCPServerStdio in this case), I consistently receive a resource_tracker: There appear to be XX leaked semaphore objects to clean up at shutdown warning message during the program's shutdown. The exact number of leaked objects (e.g., 24) varies.
