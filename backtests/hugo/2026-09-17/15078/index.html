Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Root cause: `hugo new content` builds the site with a content-inclusion filter to locate the just-created placeholder page. The `_index.md` cascade sets `draft: true`, so the placeholder is filtered out of the build, the lookup fails, and Hugo emits the false 'target path conflicts with existing content' error (leaving only the placeholder). The existing code already sets `BuildFuture=true` in the `new content` config for exactly this class of problem — a newly created page must be discoverable regardless of publish state. Patch A extends that established convention by also setting `BuildDrafts` and `BuildExpired`, which is the principled, general root-cause fix: it makes the discovery build surface the target page whether cascade/archetype marks it draft, future, or expired. Its testscript reproduces the issue's exact cascade+draft scenario and would fail before / pass after. Patch B instead pins `draft: false` into the placeholder front matter, relying on page-front-matter-beating-cascade precedence. That does fix the reported (draft-only) case and its Go test is valid, and it is admirably minimal — but it is narrower (leaves expired cascade unaddressed) and is more of a targeted neutralization than the general mechanism the codebase already uses via BuildFuture. Patch A's real weakness is scope: its second hunk adds ~16 lines of unrelated leaf-bundle conflict-detection logic that the issue never asks for, adds filesystem reads, and could introduce new false-conflict behavior; a maintainer would likely strip it. That is a genuine strike under the scope criterion. However, correctness is weighted first, and Patch A's core fix is the more robust, convention-consistent root-cause resolution (the second hunk is inert for the index.md test path and does not compromise the fix or the reproduction). On balance A edges B.

What the agent reported

Summary

What was wrong

hugo new content posts/drafts/trip-to-puebla/index.md failed with a false no page found ...; the target path conflicts with existing content error whenever the target section's branch bundle (posts/drafts/_index.md) had a cascade setting draft: true.

The command works by writing a temporary placeholder file, running an intermediate SkipRender build to resolve that file to a Page (so the archetype can be applied), then looking the page up via HugoSites.GetContentPage. The placeholder inherited draft: true from the section cascade; Site.shouldBuild returns false for drafts, so the page was added to droppedPages and deleted from the page tree. GetContentPage walks only the page tree, so it returned nil, and applyArcheType reported the bogus conflict — leaving the "Content Placeholder" file behind. commands/new.go already set BuildFuture for the same class of problem (issue #12599) but not drafts/expired.

What I changed (production, 2 files)

  1. commands/new.go:58-59 — alongside the existing cfg.Set("BuildFuture", true), added cfg.Set("BuildExpired", true) and cfg.Set("BuildDrafts", true) so the transient path-resolution build no longer drops draft/expired pages. The written file is unaffected (the archetype is applied afterward; SkipRender publishes nothing).
  1. create/content.go (buildFile) — enabling drafts meant a draft leaf bundle is no longer dropped, which had been the coincidental mechanism detecting the "create a file inside an existing leaf bundle" conflict (issue #12786). I added a draft-independent check: if the target is a non-index content file whose parent directory already contains an index.* content file, return the conflict error. It is skipped when the target itself is an index file (so creating a new leaf bundle works) and matches only index. (leaf), not _index. (branch), so normal pages in a section are unaffected.

Regression test (testscripts/commands/new_content.txt) — added an "Issue 15078" case reproducing the exact scenario (a posts/drafts/_index.md with cascade.draft: true), asserting the command now succeeds and the created file contains the archetype (draft = true), not the placeholder.

Test evidence

  • Before the fix: the new case failed with no page found for ".../trip-to-puebla/index.md"; the target path conflicts with existing content (confirmed test-first).
  • After the fix: TestCommands and TestCommands/new_content PASS, with zero failures — including the pre-existing conflict cases (#12602, #12786, #14112), which all still correctly error.
  • The create, hugolib, and root hugo packages all pass.

These have no dependency on create/commands and are pre-existing environmental failures, not caused by this change.
