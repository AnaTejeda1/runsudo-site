[Bug]: Incorrect TPM limiting for virtual keys

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches identify the same root cause: the `:requests` and `:tokens` counters share one `:window` key, so a window reset triggered through the RPM counter left the tokens counter carrying the previous window's count, which explains both the ~30% under-enforcement and the multi-minute cooldown. Both fix this in BATCH_RATE_LIMITER_SCRIPT, CHECK_AND_INCREMENT_BY_N_SCRIPT, in_memory_cache_sliding_window, and the in-memory pass of atomic_check_and_increment_by_n, with per-run dedup so a later pair on the same window does not wipe a counter just started. Patch B goes one step further that matters for the issue: is_cache_list_over_limit now treats a mirrored counter as empty when its window start is missing or older than window_size, so the in-memory pre-check stops rejecting from a stale counter after the window ends. That is exactly the 'cooldown longer than a minute' symptom, and the independent tests confirm the gap: A still fails test_rate_limited_key_admitted_after_one_minute_without_reservation with the identical 363s stuck-limit as base, while B passes all six issue-derived scenarios. Patch A's extra asyncio lock around in_memory_cache_sliding_window is plausible hardening against a concurrent reset erasing a sibling increment, but it relies on an attribute not shown and does not close the stale pre-check path. On tests, A's are behavioral and include a concurrency case; B's include end-to-end time-advanced regressions for reservation, non-reservation, and RPM rollover plus a helper unit test, though its Lua tests are string assertions and count for little. Scope and craft are comparable; B's shared helper and comments make the invariant clearer. B resolves more of the reported behavior at the root.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours. What happened?

This was initially reported on #18953 for v1.80.0. It was marked as solved, but we are still seeing this behaviour in v1.82.3

Actual rate limit enforcement is usually ~30% below the configured limit, and the cooldown period is longer than a minute. Usually 2, but can reach 5 minutes in some instances.

This is with the default rate limit type and configuration.

Steps to Reproduce

  1. Configure an API key with TPM limit (e.g. 500k)
  2. Use the API key
  3. Rate limit enforcement hits at approximately 300-350k.
