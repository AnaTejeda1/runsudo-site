Source position tracking changes parsing of repeated formatting tags

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the root cause the issue names. Each makes `Attributes.equals()` skip internal keys and compare public `size()` instead of the raw `size` field, and each rewrites `hashCode()` as an order-independent sum over non-internal entries. Both would correct the Noah's Ark reconstruction with tracking on.

Patch A changes `equals()` minimally: it skips internal keys and keeps the existing `indexOfKey` lookup. That is correct, because the public sizes match and every public key is looked up on the other side. Its `hashCode` uses `key.hashCode() ^ Objects.hashCode(val)`, which is exactly the `Map.Entry`/`AbstractMap` convention. That fits the Javadoc's stated Map-like equality semantics. Its tests cover the exact issue scenario with tracking both on and off, plus an attributed variant. They also check equality with mixed order, internal keys and user data, and a negative case where an internal `/Two` must not match the public `Two`. The issue test and the source-range equality test would fail before the change.

Patch B swaps the lookup in `equals()` for an O(n²) duplicate-counting scheme that runs on every comparison, including the parser's Noah's Ark checks. This goes beyond the issue's ask and adds complexity and cost to a hot path. It handles duplicate attributes from `add()`, an edge case the original code never handled and the issue doesn't raise. Its `31*k+v` hash avoids name/value swap collisions, which is a minor quality gain but not needed for correctness. Its tests are decent, though the parser test only checks the tracking-on path. The CHANGES entry is nice but carries little weight.

On correctness and tests the two are about equal. Patch A delivers the fix with less risk and less churn, and it follows standard Map hashing conventions, so it is the better fix.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The issue

View on GitHub

Source tracking can impact the parse, due to how attributes are compared.

String html = "<p><b><b><b><b><p>x";
for (boolean track : new boolean[] {false, true}) {
    Document doc = Parser.htmlParser().setTrackPosition(track).parseInput(html, "");
    System.out.println(track + ": " + doc.body().child(1).outerHtml());
}

Expected in both cases: <p><b><b><b>x</b></b></b></p>

Actual with tracking enabled: <p><b><b><b><b>x</b></b></b></b></p>

The first paragraph retains all four original <b> elements, but only three identical formatting elements should be active for reconstruction in the second paragraph (per the _Noah's Ark_ clause). Source tracking adds internal range data to each element’s attributes; comparing that data prevents jsoup from recognising the three identical entries. Attributes.equals() and hashCode() should exclude internal attributes.
