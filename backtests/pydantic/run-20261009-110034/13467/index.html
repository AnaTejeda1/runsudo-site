Support Ellipsis

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Patch A is the more complete and useful fix. It maps `EllipsisType` to a schema built from existing pydantic-core primitives. Validation accepts the `Ellipsis` singleton in Python mode, plus the `'...'` string in lax mode, and accepts `'...'` from JSON. Serialization keeps `Ellipsis` in Python mode and emits `'...'` in JSON mode. JSON schema output is `{'const': '...', 'type': 'string'}`. As a result, the issue's scenario (`tuple[int | EllipsisType, int | EllipsisType]` in a model) fully round-trips: `model_dump`, `model_dump_json`, `model_validate_json` and `model_json_schema` all work. Its tests exercise these paths, including:
- strict vs lax behaviour
- custom error type and message
- union serialization with `int` and `str`
- the warning on unexpected values

The tests would fail before the change. It also documents the type and warns about the `...`-as-default pitfall.

Patch B adds a new Rust validator/serializer and core schema type, but support is Python-only:
- JSON validation always fails, because the validator only matches `as_python()`.
- `dump_json` raises an error.
- `model_json_schema()` raises `PydanticInvalidForJsonSchema`.

A model like the one in the issue therefore can't be serialized to JSON or have its schema generated. That is a significant gap for a pydantic type. B's tests mostly confirm these limitations, plus error and schema-function registration. B's approach also brings much more churn and risk (new core schema type, error type, Rust code) for less functionality.

A's approach is lighter, consistent with how other special types like `Hashable` are built in `_generate_schema.py`, and covers the issue's needs more fully.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

Description

Ellipsis is a builtin type that pydantic does not support. Its usage is infrequent, but it can be useful to express placeholders:

This is a bit of a contrived example, but:

class Model(pydantic.BaseModel):
    m: list[list[float]]
    subset: tuple[int | Ellipsis, int | Ellipsis]

    def subset_arr(self) -> np.NDArray:
        return np.asarray(self.m)[*self.subset]

Here's how I implement this right now with an adapter: https://github.com/psalvaggio/scientific_pydantic/blob/main/src/scientific_pydantic/ellipsis.py

However, since this is a standard library type, I think this would be a good thing to live in pydantic itself.

Affected Components

  • Compatibility between releases
  • Data validation/parsing
  • Data serialization - .model_dump() and .model_dump_json()
  • JSON Schema
  • Dataclasses
  • Model Config
  • Field Types - adding or changing a particular data type
  • Function validation decorator
  • Generic Models
  • Other Model behaviour - model_construct(), pickling, private attributes, ORM mode
  • Plugins and integration with other tools - mypy, FastAPI, python-devtools, Hypothesis, VS Code, PyCharm, etc.
