Make .Render take additional data

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches change the `Render` signature to `...any` across all implementers (`pageContentOutput`, `LazyContentProvider`, `nopPage`, `testPage`). Both fall back to the page as context when no data is given, so existing `.Render NAME` calls keep working. The difference is which argument orders they accept. The issue explicitly proposes `PAGE.Render [DATA] NAME`. Patch A supports that order and also accepts `NAME DATA` when DATA is not a string, via a small `ParseRenderArgs` helper. Patch B supports only `NAME DATA` ("VIEW [CONTEXT]"), which is the reverse of the signature in the issue. A user following the issue's form, e.g. `.Render (dict ...) "li"`, would get a cast error under B. Patch A has one ambiguity: with two strings it treats the first as DATA. That matches the issue's stated order but differs from B's reading, and the rule is documented. On tests, A is stronger. Its integration tests cover no data, DATA NAME, NAME DATA and string data. They also check that template lookup still follows the page's content type (`books/li.html` vs `li.html`) when data is passed, and that the page can be reached through the dict. A also adds unit tests for every parsing branch, including the error cases. B's test covers only NAME DATA with a dict that mimics `.Title`, plus two error cases. A also updates the user docs for the new signature and the comparison table with `partial`. B's change is smaller and clean, but it implements the opposite of the order the issue proposes. Overall A is more correct with respect to the issue and better tested.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

PAGE.Render NAME

This has been discussed before.

  • The contract has always been that the templates that .Renders gets the data context as e.g. page.html, a page.Page.
  • We can only pass 1 argument to Go's template renderer, which I guess is the blocking reason for not having done this sooner.

So, if we want to do:

PAGE.Render [DATA] NAME

I'm guessing we have 2 top-level options:

  • We say that if DATA is set, we use that as the context passed to the templates,. else PAGE.
  • We somehow (e.g. by embeding it in a { DataAdditionalContext, Page } struct or putting it into the current context.Context) wrap the Page so you can do both .RelPermalink and .DataAdditionalContext (naming of the latter is just picked out of a hat without thinking too hard.
