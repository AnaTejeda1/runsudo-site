github: Fix workflow for stale issues

Worse

The merged fix was judged better than our patch.

In this judgment, Patch B = our agent, Patch A = the merged fix.

The failure comes from input validation inside dessant/lock-threads v6.0.0: it rejects any github-token longer than 100 characters, and GitHub's tokens now exceed that. Patch A pins the action to a newer patch release (v6.0.2) by commit SHA and changes nothing else. A patch release published after the breakage is the natural place for the upstream fix that relaxes this validation, so A addresses the root cause in the dependency. It keeps the existing, well-exercised behavior: pagination limits, rate-limit handling, filtering, and the configured labels and comments. The diff alone can't prove v6.0.2 contains the fix, which leaves some uncertainty, but the change is minimal, low-risk and easy to review.

Patch B replaces the action with a 75-line custom bash script, a sparse checkout step and a Go test in the root `main` package. The script appears functional, but it re-implements an established action and brings new risks:
- The search API caps results at 1000, which matters on the first 21-day run.
- Comment, label and lock run as separate non-atomic calls, so a mid-loop failure under `set -e` leaves items commented or labeled but unlocked.
- Rate-limit handling is a fixed sleep.
- The script now needs ongoing maintenance in the Hugo repo.

B's test does exercise the script against a stubbed `gh`, but most of it checks B's own replacement logic rather than the original bug. It also puts a CI-workflow test into the main Go test suite, which is unrelated churn. Under the scope criterion, B's broader redesign adds risk and obscures what is a one-line dependency bump. A is the better fix: correct at the root, minimal and consistent with how the workflow already pins actions.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.
