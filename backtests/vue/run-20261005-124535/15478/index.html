compiler-sfc: loadTSConfig re-parses the whole tsconfig extends chain for every config it walks

Worse

The merged fix was judged better than our patch.

In this judgment, Patch A = our agent, Patch B = the merged fix.

Both patches fix the root cause the same way: a module-level `Map<string, TS.ExtendedConfigCacheEntry>` passed as the 8th argument to `parseJsonConfigFileContent`. Both add a test that counts reads of the shared base and asserts exactly one, which would fail before the change. The difference is in `invalidateTypeCache`.

Patch A calls `tsConfigExtendedCache.clear()` on every invalidation, regardless of file type. In dev/HMR, each `.vue` or `.ts` edit would wipe the extended-config cache, which undoes much of the benefit in exactly the workflow where invalidation fires. A also does not fix staleness when only the base config is edited. `tsConfigCache` is keyed by the referencing tsconfig, not by the base, so `tsConfigCache.delete('/tsconfig.base.json')` does nothing, and the already-resolved top-level config entries stay stale. A's second test passes only because the spec's `resolve` helper appears to invalidate every file in the fixture, including `/tsconfig.json`. It therefore does not exercise the real single-file HMR scenario the issue's caveat is about.

Patch B clears both `extendedConfigCache` and `tsConfigCache` only when a `.json` file changes. Editing a shared base then actually refreshes the configs that extend it, and ordinary source edits keep the cache. This directly answers the issue's stated caveat about an edited `tsconfig.base.json` going stale. Clearing all of `tsConfigCache` on a config edit is coarse but correct, and config edits are rare. The `.json` suffix check would miss unusually named config files, which is a minor edge case.

A has an extra test, but it is weakened by the helper's blanket invalidation. On correctness, which is weighted first, B is better.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The issue

Vue version

3.5.42 (latest release; also present on main at 5409708)

Link to minimal reproduction

https://github.com/cainrus/vue-compiler-sfc-tsconfig-repro

Steps to reproduce

git clone https://github.com/cainrus/vue-compiler-sfc-tsconfig-repro
cd vue-compiler-sfc-tsconfig-repro
npm install
npm run repro

The generator builds a workspace of 150 packages, each with its own tsconfig.json that
extends one shared base and declares references to its group, plus one SFC per package whose
props type is imported from another package by alias. Both arms compile the same components; the
cached arm differs only in that it supplies an extendedConfigCache, through the public
registerTS hook, as the 8th argument the package leaves undefined.

What is expected?

Parsing the same extends chain repeatedly should reuse the parsed parent configs, as TypeScript's
own extendedConfigCache parameter exists to allow.

What is actually happening?

loadTSConfig calls ts.parseJsonConfigFileContent with five arguments, so the 8th
(extendedConfigCache) is always undefined:

https://github.com/vuejs/core/blob/main/packages/compiler-sfc/src/script/resolveType.ts

const config = ts.parseJsonConfigFileContent(
  ts.readConfigFile(configPath, fs.readFile).config,
  parseConfigHost,           // 2
  dirname(configPath),       // 3
  undefined,                 // 4
  configPath,                // 5
)                            // 6, 7, 8 omitted -- the 8th is extendedConfigCache

and then recurses through project references:

res.unshift(...loadTSConfig(refPath, ts, fs, visited))

So in a workspace whose packages all extend a shared base, that base is re-read and re-parsed once
per config the traversal reaches, and each parse allocates its own fully expanded paths map.
visited is a default parameter: it de-duplicates within one top-level call, never across calls.

Measured on the reproduction — node 22.23.2, @vue/compiler-sfc 3.5.41, typescript 5.9, one arm
per process (tsConfigCache is module scope):

stock2900290011.1 s1346.8 MB
cached2900**1**1.9 s30.2 MB

The parse count is identical in both arms. The cache does not remove parses — it makes each one
cheap and stops the expanded options object from being rebuilt. Retained heap is heapUsed after a
forced GC.

On a production Vue monorepo (2432 components, 514 tsconfigs, 4051 project references, a 118 KB
shared base with 1342 paths entries), compiling 400 of its real components through
compileScript with the same two arms:

armconfig parsesdistinct expanded paths objectstimeretained heap
stock7351735025.4 s2615.8 MB
cached7351**3**8.0 s188.7 MB

That is what led to this report: tsconfig parsing dominated the allocation profile of that
application's production build.

Does the cache change the result?

node parity.mjs in the reproduction re-implements loadTSConfig verbatim and runs it twice per
entry config, differing only in the 8th argument, comparing resolved compilerOptions,
projectReferences and fileNames for every parse the traversal produces:

runparses comparedpaths entries comparedmismatches
node parity.mjs400176 000**0**
MUTATE=1 node parity.mjs (cached arm reads a different config)400176 000336
MUTATE=2 node parity.mjs (one paths entry altered after parsing)400176 000400

The two controls are there because a comparator that always prints zero proves nothing. The same
comparison over the production monorepo's configs: 831 parses, 1 116 033 paths entries, 0
mismatches, with the controls reporting 114 and 831.

One consequence worth stating explicitly: with the cache, the expanded options object is **shared
by reference** (that is where the memory saving comes from), so it must not be handed to a consumer
that mutates it. resolveWithTS only reads matchedConfig.config.options, so that holds today.

Suggested fix

A module-level Map threaded into the 8th argument. One caveat a fix has to answer:
invalidateTypeCache currently clears tsConfigCache and tsConfigRefMap, and would need to clear
the new cache too, or an edited tsconfig.base.json would go stale in dev/HMR — TypeScript keys
extendedConfigCache by resolved path, so that is a targeted delete.

PR: #15480 — it also explains why a plain Map rather than createCache(), and why
invalidateTypeCache clears the cache instead of deleting one entry.
