Improve/document security.http.urls override behavior

Better

Our patch was judged better than the merged fix.

In this judgment, Patch A = our agent, Patch B = the merged fix.

The issue asks to make the security.http.urls override behavior clearer, mainly through documentation, and to keep the current pragmatic behavior.

Patch A addresses this directly:
- It documents the resolved-address check in a dedicated docs section, with an important callout that any customization disables it, even a stricter allowlist.
- It cross-links that section from the negation-rules example and from the GetRemote docs.
- It extracts IsHTTPAddressCheckEnabled with a clear doc comment.
- It adds a hint to AccessDeniedError, so a denial explains why it happened and what customizing does.
- Its tests cover: no config, other http settings customized, urls set exactly to the defaults, and several customizations (including a stricter one). They also assert the new error message and that URL-text denials stay plain.
- These tests would fail before the change, since IsHTTPAddressCheckEnabled and the hint did not exist.

Patch B mostly adds an unrelated feature: a proxyFromEnvironment option with a custom proxy transport, a context-carried proxy URL and a canonicalAddr reimplementation.
- This changes behavior. Proxies are now disabled by default (base.Proxy = nil), which can break users who relied on HTTP_PROXY.
- It adds risk and new code paths beyond what the issue asks.
- Its only response to the actual issue is a short paragraph under http.urls in the docs.
- Its tests cover the proxy feature, not the override behavior.

On correctness relative to the issue, test relevance and scope, A is clearly better.

The judge saw only the two patches, labelled A and B in random order, with issue links and version numbers removed. The reasoning above is shown verbatim.

The issue

View on GitHub

In d6e6f9e500eebdeae8e28de830fff2e3bfc7d534 (unreleased) we added a dial-time URL validation to catch URLs that's valid according to the whitelist but that resolves to a loopback, private or link-local IP addresses. That check is skipped it if the user has a custom security.http.urls setup, as it would not make sense to block local development servers.

See CheckAllowedHTTPAddress.

This has been reported by @Reload3d as a potential security issue, and while I think the current behaviour is the pragmatic correct approach, I'm creating this issue for visibility and to see if this can be improved further (e.g. better documentation).
