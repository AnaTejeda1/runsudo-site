Image pipeline should allow to decide whether to auto-convert to jpg or not

Better

Our patch was judged better than the merged fix.

In this judgment, Patch B = our agent, Patch A = the merged fix.

Both patches add an opt-out setting and both pass the independent tests, so the difference lies in correctness at the edges, compatibility, and craft. Patch A changes the signature of `convert_image` to require a new keyword-only `image_format` argument with no default or deprecation path; any subclass that overrides `convert_image` with the old signature will raise TypeError when the base pipeline calls it, and A had to rewrite existing tests to match (the 5 removed test lines). Patch B leaves `convert_image` untouched and routes the no-convert case through a separate helper, so existing overrides keep working. On behaviour, A stores preserved-format files with no extension at all, while B reuses the FilesPipeline URL-extension logic (`.png`, `.gif`, etc.), which is more useful and consistent with the sibling pipeline. B also handles the MPO-opened-JPEG case, wraps unsupported-format thumbnail saves in ImageException with a clear message, and falls back to application/octet-stream for unknown MIME types; A has an unguarded `assert orig_image.format is not None` and would surface raw Pillow errors for formats that can't be saved. B's extra change to `_key_for_pipe` is scope beyond the issue, but it is directly motivated: without it a class-prefixed `*_IMAGES_CONVERT_TO_JPEG = False` would be silently ignored, and it is covered by a dedicated test; the risk is small since callers only use the returned key with a default. Tests: A covers file_path, convert_image, and image_downloaded for the new mode; B covers those plus the default content-type, min-size check in the new path, the custom-settings matrix, and the class-attr vs setting override, with end-to-end on-disk verification. Docs are comparable; B adds a news entry and versionadded. Overall B resolves the issue without breaking the existing API and with better edge handling.

Four judges ruled on this ticket in parallel, and the verdict comes from counting their votes. Each saw the issue and the two patches, labelled A and B in random order (two of them saw ours as A), with issue links and version numbers removed. Where tests could check the fix, they also saw the results of tests a separate agent wrote for the issue, run on both patches. None was told which patch was ours. The reasoning above is one judge's, shown verbatim.
